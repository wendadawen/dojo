# 数据流页质检

质检用于发现并修复已画出的问题，不改变页面的视图划分与节点粒度。

先跑机器核查，再交独立审查。机器能查的不用人审，机器查不了的必须人审。

## 1. 机器核查

    python3 .dojo/scripts/dataflow-01-check.py wiki/<name>/index.html \
        --source /path/to/modeling_x.py --shapes /tmp/shapes.json
    python3 .dojo/scripts/dataflow-01-check.py wiki/<name>/index.html --geometry
    python3 .dojo/scripts/ci-01-validate.py --all

三条命令分别查：节点名能否回查源码、权重形状是否与检查点头一致、连线是否穿框或叠在一起。

两条边界要知道：

- 形状比对只在页面与形状表**都有该键**时生效。键名写错会静默漏过，所以键名要逐个对照检查点头。
- `--source` 可带标签（如 `mtp=/path/mtp.py`），带标签的只作用于标题含该标签的视图。同页有多个来源时必须分标签，否则会把正确的名字误判成捏造。

## 2. 为什么还要独立复现

机器只能验证局部一致性：这个名字在源码里存在吗、这个形状与权重表一致吗。它验证不了三件事——

- **归属**：`nn.Linear` 在源码里出现几十次，grep 得到不代表这个节点就是那一层的
- **结构**：图是按理解画出的执行顺序，与源码实际顺序是否一致，需要语义判断
- **完备性**：要证明「没漏」，必须把源码逐行过一遍

所以核查方式不是「检查页面写得对不对」，而是：**独立读一遍源码，自己推导出数据流，再与图上画的逐项比对**。核查者给出的必须是「源码第几行做了什么」，而不是「页面这里看着不太对」。

## 3. 审查轮次与独立性

每轮派发 **3 个**独立审查者并行审查，三者互不可见。每轮结束后合并问题、修复，再进行下一轮；下一轮重新派 3 个新的审查者。**串行进行，直到通过。**

三个审查者盯不同的东西，避免重复劳动：

- **A 完备性与结构**：源码每一步是否都在图上、顺序与分支是否一致
- **B 归属与形状**：每个节点的模块归属、张量形状、命名
- **C 可读性与粒度和**：读者能否看懂、详略是否得当、连线是否可辨

每个审查者未参与画图，也未参与前序轮次。首条消息只给出：待审页面路径、源码与权重的获取方式、本规范路径，以及一句指令——按本规范审查，自行取得材料，只读取规范允许的输入。不得转发画图时的推理记录、修复意图或前序审查结果。

审查者自行获取材料，不依赖画图者提供的副本：

- 源码：模型的官方仓库（transformers、vLLM、SGLang 等），指明具体文件
- 权重形状：`safetensors` 头部即可，不必下载完整权重
- 配置：模型的 `config.json`

当前环境无法派发子代理时，不得由画图者自审代替。向上层返回「已画完，待独立审查」，由编排者派发。

## 4. 审查内容

### 4.1 完备性（审查者 A）

逐行读完 `forward` 及其调用的每个子模块，列出实际执行的步骤序列，与页面上的节点序列比对。目录树、`help()`、搜索关键词都不能替代通读。

必须抓住的遗漏：

- 只出现一次的步骤：mask 构造、位置编码、缓存更新、reshape/transpose
- 条件分支：某层走不同路径（首层用 dense FFN、其余用 MoE）、训练与推理不同
- 复用的量：同一份 cos/sin 被多层共用、上一层的输出传给下一层
- 循环体：`for` 循环里每个 token、每个专家的处理

页面写了源码里不存在的东西，与漏画同样算错。

### 4.2 结构与归属（审查者 A、B）

- **顺序**：节点顺序与源码执行顺序一致；分支与合并的位置正确
- **连接**：每条边两端的节点在源码里确实有数据依赖；没有把无依赖的两步连起来
- **归属**：节点所属的视图、分组与源码的类层次一致——某一步属于 `Qwen3Attention` 就不该画进 `Qwen3MLP`
- **跨视图**：`port` 标出的量确实从外部传入，不是视图内部产生
- **方向**：边的起点是产生数据的节点，终点是消费它的节点

### 4.3 命名与形状（审查者 B）

- **命名**：节点名用源码里被调用的符号。部署侧实现名（`VocabParallelEmbedding`）、自造变量（`reduced`）、源码中不存在的词（`einsum`）都算错。检查点键名与运行时属性名不一致时，页面须在 `detail` 中注明。
- **形状**：写出的形状与权重表、源码中的张量维度一致。检查维度的**来源**——`batch × heads × seq × head_dim` 这类，每个因子都要能在 config 或源码里找到。
- **层内特例**：首层与其余层不同、某些层用不同分支时，页面标注与实际一致。
- **关键参数**：出现在源码里的常量（`scaling`、`eps`、`topk`、`theta`），页面写的与来源一致。

### 4.4 可读性（审查者 C）

打开页面实际拖动、切换视图、点击下钻、开合参数面板。检查：

- 每个视图能否从头读到尾，箭头方向是否明确
- 连线是否穿框、是否叠在一起、是否绕很远
- 节点文字是否溢出，同一视图内节点宽度是否一致
- 粒度：该展开的展开了，该合并的没有堆成一片
- `detail` 写的是可回查的硬信息（权重键、开关、构成），不是复述节点名

## 5. 问题分级

每轮结果写入 `research/review-{轮次}.md`，每个问题单独记录：

```text
级别｜位置｜问题｜源码依据｜修复要求｜修复结果｜复验结果
```

「源码依据」一栏写核对时看到的文件与行号、或权重键与形状；可读性问题填「不适用」。

- **阻断**：画错或漏画的步骤会导致读者对模型的理解出错；数据流方向错误。
- **重要**：节点归属、形状、关键参数写错；重要步骤遗漏但主线仍成立。
- **轻微**：可读性、措辞、粒度小问题，不影响正确性。

严重度按「对理解模型的影响」确定，不按修改工作量。

## 6. 修复与复验

- 每轮三份记录合并后逐条修复，并在记录中填写修复与复验结果。
- 修完重跑机器核查：`dataflow-01-check.py`（事实与几何）与 `ci-01-validate.py`。
- 下一轮从修复后的页面重新开始，重新独立复现，不复用上一轮的结论。
- 涉及步骤增删的修复，必须回到源码重新核对相邻步骤，不能只改被指出的那一处。

## 7. 通过判据

一轮通过的条件：**3 个审查者均报告零阻断、零重要问题**。

达到后**再追加一轮**（仍派 3 个新审查者）。追加轮同样零阻断、零重要问题，才算通过；否则继续。

为什么不是「无限跑到没人能挑出毛病」：核查者本身会遗漏，一直跑到挑不出问题，只说明错误变得隐蔽，不说明没有错误。而每轮从源码独立复现，是能实际达到的最强检验。连续两轮三方零问题，是这套方法能给出的收敛信号。

## 8. 发布条件

- 最后一轮与追加轮均为 3 个独立审查者、零阻断、零重要问题
- 遗留轻微问题有明确的接受理由
- 每个形状、参数、算子都有源码或权重依据
- `dataflow-01-check.py` 的事实核查与几何自检均通过
- `ci-01-validate.py` 通过
- 页面 head 含纯文本 `description`、`dojo:summary`、`dojo:type=dataflow`、`dojo:topics`、`dojo:tag`
- 画图者已亲自打开页面逐视图确认可读

## 9. 审查记录模板

```markdown
# <模型名>数据流审查记录（第 N 轮 · 审查者 A/B/C）

- 页面版本：<index.html 的 sha256>
- 审查时间：<日期时间>
- 审查者：独立子代理，未参与画图
- 审查范围：<本审查者负责的维度>
- 独立复现方式：<读了哪个文件的哪些行，如何取得>

## 问题

- [阻断·结构] <视图/节点>：<问题>｜源码依据：<文件:行号 或 权重键>｜修复要求：<可复验的要求>｜修复：｜复验：
- [重要·形状] <视图/节点>：...｜源码依据：<...>｜修复要求：...｜修复：｜复验：
- [轻微·可读性] <视图/节点>：...｜源码依据：不适用｜修复要求：...｜修复：｜复验：

## 结论

- 统计：阻断 X / 重要 Y / 轻微 Z
- 处置：修复后进入下一轮 / 可发布
```

问题描述与修复要求必须能复验，不使用「表达不够清楚」「建议补充」这类无法判定完成状态的表述。
