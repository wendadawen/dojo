# Note：学完就记，留一张速查卡

用户明确表达留档意图时执行本场景：学习对话结束后要求整理成笔记，直接提供材料、链接、代码或主题要求记录，或任何其他明确表示要留档的时刻。不在对话中自行触发留档。

## 定位

把已经学完的内容整理成一张速查卡，写入 `wiki/<name>/index.html`，供日后快速查看。卡片必须反映用户自己的理解，不是聊天记录转录，也不是外部资料的搬运。内容不设边界：代码机制、数学概念、工程经验、调研结论、对话收获等均可，一篇卡片只聚焦一件事。想系统完整讲解时改用 `guides/concept.md` 或 `guides/paper.md`。

## 卡片结构

按速查卡组织，从顶部向下扫读即可掌握要点：

1. 一句话核心：直接回答“这次弄懂了什么”，表述贴近用户的理解方式。读者只看这一句就该知道卡片在说什么。
2. 要点：若干要点，每个点讲清一件事，可带一个具体例子（公式、代码片段、场景）。要点之间按逻辑组织，不按聊天顺序。
3. 来源：可核验的链接或出处，标注它支撑了哪个要点。

页面允许按内容增加必要部分（如数学公式区、代码区），但整体保持速查卡形态：短、可扫读、聚焦一件事。

## 生成规则

- 以 `.dojo/templates/note/index.html` 为外壳，将正文写入 `<!-- @content -->` 标记处，替换全部【…】占位符。
- 只整理已学内容（强制）：只写对话中实际学到并验证过的东西。评价、修复方向、推测、对话中未出现的结论一律不写；想补充自己的想法时先问用户，未经确认不写入。
- 独立可读：正文不依赖对话背景才能理解。对话中出现的日志、文件名、报错现场可以写入，但需补充必要上下文（它是什么、出现在哪、说明什么），使拿到页面的人无需对话记录即可读懂。
- 书面语：使用正式书面语，不用对话腔和口语词；保持速查卡简洁，但不因口语化而牺牲专业性。
- 涉及代码时保留文件路径、符号名和行号。
- 事实核查（强制）：
  - 禁止凭记忆断言。讲代码、API、库/框架行为、数值时不得仅凭记忆下结论。
  - 能查必须查。环境具备读文件或联网能力时，实际查证后再写；本地有源码就查源码（带路径与行号），查不到就搜索官方文档或网页。
  - 代码必须运行。声称可运行的代码实际执行核对；无法运行就标注“未运行”并说明原因。
  - 查不到必须声明。明确写“未核实/不确定”，不用“大概、应该”一带而过。
  - 来源与推断分离。关键论断注明依据；没有依据的一律标注为“推断”。
- 运行 `.dojo/scripts/validate.py <页面路径>`；通过后在 `content.json` 的 `notes` 分区登记，并运行 `.dojo/scripts/generate_index.py`。
- 对用户说明生成位置、卡片覆盖范围和未解决项。
