# 学习记录归档

适用于将已经确认的材料、结论、代码机制或工程经验整理为独立页面。只有收到明确归档要求时才执行。

## 目标

生成一篇可独立阅读的学习记录，写入 `wiki/<name>/index.html`。页面不是交流记录的转录，也不扩展为系统说明；需要完整结构时使用 `guides/concept.md` 或 `guides/paper.md`。

## 范围与结构

- 每篇记录只处理一个中心结论。
- 基础定义位于首次使用之前，内容按依赖关系排列。
- 同一主题集中在一个章节，避免重复和跨章节散落。
- 结构无法承载内容时，先调整结构，再写正文。

## 内容边界

- 只记录已经验证的事实和明确确认的判断。
- 推测、评价和修复建议必须有依据，并标记其性质。
- 通用机制优先；实现特例和边界条件保持必要篇幅。
- 机制说明应覆盖输入、状态、关键参数、主要步骤和输出。

## 事实核查

- 代码、API、库行为和数值在写入前重新核对源码或官方文档。
- 可运行代码实际执行并核对输出；无法运行时标记原因。
- 无法核实的内容明确标记为“未核实”或“推断”。
- 关键论断注明来源。

## 表述

- 标题给出具体结论，不使用仅表示主题或文档类型的标题。
- 导语概括支撑该结论的关键机制，不与标题重复。
- 使用正式书面语，删除会话指代、临场评价和口语化过渡。
- 文件名、日志和报错需补足出现位置及其说明。
- 正文引用代码时使用文件路径和符号名，行号集中列入来源。

## 图示

- 使用内联 SVG，不使用 ASCII 字符图。
- 每张图只表达一个关系，控制元素数量。
- 图示无法降低理解成本时，改用表格或文字。

## 发布前检查

- 正文没有会话指代或交流记录式表述。
- 标题和导语职责不同。
- 每个章节只承担一个主题。
- 每条事实有来源支撑，或已标记为推断。
- 图示只表达一个关系。
- 日志、文件名和报错具有完整上下文。
- `.dojo/scripts/validate.py <页面路径>` 通过。

## 发布

使用 `.dojo/templates/note/index.html`，替换全部占位符和 `<!-- @content -->`。页面元数据包括纯文本 `description`、可含 `$...$` 公式的 `dojo:summary`、类型、主题和标签。首页目录与 Graph 由 GitHub Pages 构建自动生成。
