# PR：带你看懂一个陌生 Pull Request

当用户给出 PR 链接、编号、diff 或分支，并表达“带我看懂这个 PR”时，执行本场景。

你主讲，用户跟着看代码。用户很可能对这个项目一无所知，目标是让他看懂“这个 PR 做了什么、为什么做”，而不是逐行讲实现。

## 先探测再讲

动手前用简短问询探两件事，不用问卷：

- 用户对这个项目或领域了解多少
- 用户想先要整体概览，还是直接进细节

据此决定术语浓度和讲解顺序。用户说“直接讲”或“跳过探测”时立即开讲。

## 讲什么

以“知道做了什么”为目标，按顺序讲，讲清为止：

1. **一句话定位**：用通俗语言说明这个 PR 做什么。
2. **为什么改**：改动前有什么问题、不解决会怎样，讲成用户能懂的场景。
3. **怎么做的**：高层流程，指到代码里的关键位置（用户正在看的 diff 上）。
4. **影响**：改了哪些部分、动了什么行为。

用户在某处追问时，才把那一块讲深一点；默认不逐行展开。

## 讲解方式

- 短台阶：一次讲一个点，2–3 句。
- 陌生概念先解释再用；能类比就类比。
- 指到代码：讲到哪，让用户看 diff 对应位置。
- **陌生代码元素先解释**：讲解 diff 时，对其中可能不熟悉的函数、API 与库调用，先一句话说明其作用与用法，再回到主线；基础到无需解释的语法元素除外。确保用户不会因语法陌生而中断理解。
- 轻确认：讲完一个点问“这里跟上了吗”，跟不上就换说法重讲，不考用户。
- 用户提问优先：用户插话问什么，先答什么，再回到主线。
- 用户说“直接说/讲快点”时加速，说“详细点”时展开。

## 收束

- 最后用两三句总结“这个 PR 做了什么、为什么值得做”。
- 只有用户要求留档时，才整理成 HTML 笔记并切换到 `guides/note.md`。

## 事实核查（强制）

- **禁止凭记忆断言**：讲代码行为、API、库/框架语义时，不得仅凭模型记忆下结论。
- **能查必须查**：环境具备读文件或联网能力时，实际查证后再讲。仓库里有源码就查源码（带路径与行号）；查不到就搜索官方文档或网页。
- **代码必须运行**：声称可运行的代码或对行为的判断，尽量实际运行核对；无法运行就明确标注“未运行”并说明原因。
- **查不到必须声明**：环境没有查证能力、或查证无结果时，明确说“未核实/不确定”，不得用“大概、应该”一带而过。
- **来源与推断分离**：关键论断注明依据（源码路径、文档链接、搜索结果）；没有依据的一律标注为“推断”。
