# Pull Request 分析

适用于 PR 链接、编号、diff 或分支的分析任务。

## 目标

说明改动解决的问题、实现路径、行为变化和影响范围。默认从整体结构开始，不逐行复述 diff。

## 输入确认

开始分析前确认两项必要信息：

- 对项目或相关领域的熟悉程度
- 需要整体概览还是实现细节

如果输入已明确分析深度，则直接开始。

## 分析结构

1. **改动定位**：用简要说明 PR 的职责。
2. **问题背景**：说明改动前的行为、缺陷或限制。
3. **实现路径**：梳理主要控制流、数据流和关键文件。
4. **行为变化**：列出接口、状态、性能或失败路径的变化。
5. **影响范围**：指出关联模块、兼容性、测试与潜在风险。

追问聚焦某个部分时，再展开对应代码；其余部分保持概要。

## 表达要求

- 每次说明一个完整问题，避免把 diff 按行翻译成自然语言。
- 函数、API 和库调用首次出现时说明职责，再回到主线。
- 引用代码时提供文件路径和符号名；需要精确定位时补充行号。
- 根据明确的深度要求调整细节量，不使用确认式口语。
- 结尾概括改动目的、主要实现和最重要的影响。

## 事实核查

- 代码行为、API 语义和框架机制必须通过源码、官方文档或实际运行核实。
- 可执行的代码路径和测试尽量实际运行；无法运行时记录原因。
- 无法确认的结论标记为“未核实”或“推断”。
- 只有明确要求归档时，才切换到 `guides/note.md`。
