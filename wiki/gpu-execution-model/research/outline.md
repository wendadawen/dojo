# GPU 执行模型与 kernel 调度 outline：教学大纲

## 1. 页面开头

- 钩子场景：一张 H100 上同时来了两件事情——一件「大活」（一个大矩阵乘，要跑约 2 毫秒），一件「小活」（一个小矩阵乘，只要 30 微秒）。小活已经就绪，大活正在跑。小活要等多久？要回答这个问题，得先知道 GPU 是怎么执行一段计算的。（数字标记为教学构造，与 ExpertPlex §4.1 的场景同构但不引用其测量值。）
- 一句话解释：本页讲 GPU 执行模型与 kernel 调度——GPU 怎样把一段并行计算组织成线程层级、放到上百个计算单元上执行，以及多个计算任务如何共享一张卡。
- 要解决的问题：不懂这套模型，就看不懂任何「在 tile 边界调度」「常驻 kernel」「SM 分区」的系统论文（本页是 ExpertPlex 论文解析页的前置知识页）。
- 学习承诺：读完能回答 Q1–Q5（learning-goals 组件，与 scope.md 一致）。
- 误解提示（misconceptions 组件，开头只放最关键两条）：「GPU 线程像 CPU 线程一样随时被切换」——CTA 跑完才释放 SM；「输入越长 tile 越大」——tile 尺寸由硬件容量决定，输入长只是 tile 变多。
- 前置说明：不需要 GPU 背景；矩阵乘法的基本形式正文内联复习；MoE/prefill/decode 等服务层概念由姊妹概念页负责（moe-serving 占位提示）。
- 过渡到第 1 章：要回答「小活等多久」，先看 GPU 这台机器长什么样。

## 2. 章节设计

### 第 1 章「先认识硬件：一块 GPU 里有什么」

- 教学问题：GPU 这台机器的计算单元和内存在哪、各自多大、差几个量级？（负责 Q1 的硬件一半）
- 范围：C5/C6/N1/N2/N3（部分）
- 正文要点：
  - SM 是独立计算单元，H100 有 132 个；每个 SM 里有通用计算单元和 4 个 Tensor Core（一次算一小块矩阵乘加）。
  - 内存层级：寄存器（SM 内）→ shared memory（SM 内，228KB/SM，单 CTA 最多 227KB）→ L2（全卡共享，50MB）→ HBM 全局内存（80GB，3.35TB/s）。越靠上越快越小；数据必须搬到 SM 附近才能算。
  - ASCII 图示：一张 H100 的层级图（132 SM 围着一个 L2、L2 连着 HBM），箭头标注容量与带宽量级。
  - 贯穿例子引入：大活/小活两个 kernel 的输入矩阵一开始都躺在 HBM 里。
- 完成检查：说出 SM/Tensor Core/shared memory/L2/HBM 各是什么；说出为什么 80GB 的数据不能全搬进 SM。
- 过渡：机器认识了，但「一段代码」是怎么变成在这 132 个 SM 上同时跑的几千个线程的？

### 第 2 章「kernel 是怎么跑起来的：线程、warp、CTA 与 stream」

- 教学问题：从 CPU 一句「启动」到 GPU 上千军万马执行，中间经过哪些层级？kernel 开始跑之后能不能被打断？（负责 Q1 的执行一半 + 支撑 Q5）
- 范围：C1/C2/C3/C4/N3
- 正文要点：
  - kernel = 一段要被大量线程同时执行的函数（消歧：不是操作系统内核）。
  - 组织层级：thread → warp（32 线程，SM 内调度发射的最小单位）→ CTA/thread block（≤1024 线程，整体驻留一块 SM，独享其 shared memory 份额）→ grid（一次启动的全部 CTA）。
  - 启动流程：CPU 把 kernel 提交到 stream（队列）→ GPU 前端把 CTA 分发给有空闲资源的 SM → SM 内 warp 调度器逐 warp 发射指令 → CTA 全部完成，kernel 结束。
  - 关键事实：CTA 一旦被分发到 SM，就运行到完成才释放；CUDA 不提供打断运行中 kernel 的用户接口。stream 内有序、stream 间无序可并发。
  - ASCII 图示：启动流水线（CPU→stream→GigaThread 分发→SM×132→warp 调度）。
  - 贯穿例子推进：大活的 grid 有几百个 CTA，铺满了 132 个 SM；小活的 CTA 排队等空位——这就是「小活要等」的直接原因。
- 完成检查：按层级说出一次 kernel 启动的路径；判断「把 stream 优先级调高能不能打断正在跑的 kernel」。
- 过渡：现在知道计算被切成了 CTA。但 CTA 内部的矩阵乘为什么还要继续切成更小的 tile？答案藏在第 1 章的内存容量数字里。

### 第 3 章「为什么矩阵乘要切成 tile：一次能搬多少数据说了算」

- 教学问题：为什么 GEMM 不切 tile 就慢？tile 的尺寸由什么决定？输入变长时什么变、什么不变？（负责 Q2，全页核心手算章）
- 范围：F1/C5/C6/N1/N2；误解 2 在此处理
- 正文要点：
  - 复习 GEMM：C[i][j] = Σ_k A[i][k]·B[k][j]，每个输出元素要 K 次乘加（30 字内联复习）。
  - 手算例子（教学构造）：4×4 @ 4×4。不切 tile：每个 A 元素被读 4 次，A 共被读 64 次；切成 2×2 tile：每个 A 元素从全局内存只读 2 次，共 32 次。结论：复用发生在 tile 内部，tile 越大读得越少——但 tile 放不进 shared memory 就无从复用。
  - tile 尺寸由 shared memory 容量约束：教学数字例子——fp16 下 128×128 的 A 块占 32KB，A、B 两块加输出缓冲在百 KB 量级，接近单 CTA 227KB 上限；所以 tile 是「128×128」这种由硬件决定的固定尺寸，不随输入变大。
  - 输入变长：M 从 8192 到 16384，tile 行数 64→128，数量翻倍，单个 tile 的搬运算节奏不变。这就是「长输入只是 tile 更多」。
  - 归纳（标注为本文归纳）：tile 是 GEMM kernel 内最小可独立完成的单位，tile 边界是与输入长度无关的天然调度刻度。
  - 折叠块：4×4 例子的完整展开（逐 tile 读数清单）。
- 完成检查：复算 4×4 例子的两种读取次数；判断「输入长度 ×4 后 tile 数量怎么变、单 tile 时间怎么变」。
- 过渡：切好 tile 之后，一个 tile 的生命周期是「搬数据→算→搬下一块」。搬和算谁来干、怎么不互相等？Hopper 给了一套专门工具。

### 第 4 章「Hopper 的协作工具箱：TMA、warp 分工与 CTA cluster」

- 教学问题：tile 流水线里「搬」和「算」如何重叠？相邻 SM 想直接交换数据怎么办？（负责 Q4）
- 范围：C7/C8/C9/C15/N4
- 正文要点：
  - 问题：tile 流水线 = 搬下一块与算当前块要重叠，否则计算单元一半时间在等数据。
  - TMA：单线程发起、引擎在后台搬运 1D–5D 张量块，搬运不占计算线程的指令流（C7）。
  - warp specialization：有了异步搬运，可以让一部分 warp 专职发起搬运（producer）、其余专职算（consumer），形成流水线（C9）。ASCII 时间线图：三级流水（搬 t+1 / 算 t）。
  - cluster + DSMEM：CTA 需要协作（如分摊一份大矩阵块）时，cluster 把 ≤8（H100 可到 16）个 CTA 共同调度到相邻 SM，彼此直接读写对方 shared memory，不必绕全局内存（C8/C15）；TMA 还可把一份数据组播给 cluster 内多个 CTA。
  - 代价与上限：cluster 越大，可并发的独立 block 数越少（C8 官方提示）；16 是不可移植的 H100 特例。
  - 教学解释标注：本章机制描述为概念级简化，省略 descriptor、mbarrier 等同步细节（列出省略项）。
- 完成检查：说出 TMA/warp specialization/cluster 各自解决什么；判断「cluster 内 CTA 交换数据要不要经过 HBM」。
- 过渡：以上都在讲一个 kernel 内部怎么跑快。换一个角度：如果 kernel 本身很小、要跑成千上万次，每次「启动」本身就是浪费。

### 第 5 章「反复启动太贵：persistent kernel 与 CUDA Graph」

- 教学问题：kernel 启动开销从哪来？persistent kernel 和 CUDA Graph 各消除哪部分？代价是什么？（负责 Q3）
- 范围：C3/C4/C10/N8；误解 5 在此处理
- 正文要点：
  - 启动开销拆解：CPU 侧逐次提交（微秒级，标注为量级说明）+ GPU 侧 CTA 分发与收尾。小 kernel 执行时间本身只有几十微秒时，逐次提交的占比不可忽视。
  - persistent kernel（教学解释：编程模式，非 API）：一次启动、长期驻留，kernel 内循环从任务队列领任务、做完再领。伪代码折叠块（language-text：输入/状态/循环/退出条件）。收益：把 N 次启动摊成 1 次；代价：常驻期间其 CTA 占着 SM，别的 kernel 用不了（呼应第 2 章「跑完才释放」）。
  - CUDA Graph：把一串 kernel 录制（capture）成图，之后整体重放（replay），CPU 只提交一次图；约束：图内形状、地址、参数基本固定，变化就要重新捕获（C10）。
  - 两者关系：正交可叠加——常驻 kernel 内部也可以用 graph 重放其周期性工作；共同点是都偏好「形状固定」的负载。
  - 扩展阅读链接：vLLM 中 CUDA Graph 的工程细节见 wiki/vllm-cudagraph/index.html。
- 完成检查：说出两种手段各消除哪部分开销；判断「输入长度每步都在变的循环能不能整体录进一张图」。
- 过渡：最后一个问题——两个任务都想要这张卡，系统层面有哪些分法？为什么现有分法都不够细？

### 第 6 章「分一张卡的四种机制：能力边界对照」

- 教学问题：stream 优先级、MPS、MIG、Green Context 各自能做什么、不能做什么？（负责 Q5）
- 范围：C11/C12/C13/C14/C16/N5/N6；误解 1/3/4 在此处理
- 正文要点：
  - 逐个讲（每个：是什么/能做什么/不能做什么/官方原文关键句）：
    - stream 优先级：对未开始工作的调度提示；不抢占、不保证顺序（C11 原文引用）。
    - MPS：多进程共享、kernel 真并发；限额只是上限不预留，客户端 kernel 可落同一 SM（C12）。
    - MIG：硬件级切片（SM+显存+缓存隔离）；H100 只有六档固定 profile（N5 表格）；改配置要停负载。
    - Green Context：进程内 SM 空间分区；Hopper 上 8 的倍数、最小 8（N6）；创建时固定；官方明示不保证并发与前进（C14）。
  - 对照表：四机制 × 切分对象/粒度/隔离强度/运行期可否改变。
  - 综合推断（标注本文归纳，C16）：没有任何一种能在 kernel 运行期间做微秒级 SM 重分配——这正是「要么切死、要么等」的根源，也是 tile 级调度（ExpertPlex APK）要补的空位。
  - 边界说明：本页数字以 H100/Hopper + CUDA 12.x 为准，跨代际会变。
- 完成检查：不看表复述四种机制各不能做什么；给定「decode 要在 50μs 内拿到 SM」判断四种机制谁能保证。
- 过渡（收束全页）：回到开头问题——小活要等多久，取决于大活何时让出 SM；让出的最小刻度，就是第 3 章的 tile。后面的故事（ExpertPlex 怎么在 tile 边界上做调度）在论文解析页讲。

## 3. 讲解顺序

硬件（有什么）→ 执行组织（怎么跑）→ tile（为什么切、多大）→ 协作工具（怎么流水）→ 启动开销（怎么省）→ 共享机制（怎么分）。每章只引入必要新变量：第 2 章引入线程层级但不谈 tile；第 3 章只用第 1 章的容量数字；第 4 章依赖 tile 生命周期；第 5 章依赖启动流程；第 6 章依赖「SM 是竞争资源 + kernel 不可抢占」。

## 4. 贯穿例子

一张 H100 上的「大活」（教学构造：约 2ms 的大 GEMM）与「小活」（教学构造：约 30μs 的小 GEMM）：
- 第 1 章：两者的数据都在 HBM，要算就得搬。
- 第 2 章：大活的 CTA 铺满 132 个 SM；小活的 CTA 排队。
- 第 3 章：大活 = 几千个 tile；小活 = 几个 tile；tile 是它们共同的刻度。
- 第 4 章：大活内部 tile 如何流水（小活 tile 太少流水不起来，提示小 kernel 吃不满硬件）。
- 第 5 章：小活每 30μs 启动一次，启动开销占比高；大活一次启动跑 2ms。
- 第 6 章：两者抢一张卡，四种机制各能给什么保证。
局部例子：4×4@4×4 手算（第 3 章）；tile 尺寸容量估算（第 3 章）。
