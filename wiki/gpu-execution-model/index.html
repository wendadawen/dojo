    GPU 执行模型与 kernel 调度

    一块 GPU 上同时来了两件事情。一件是「大活」：一个大矩阵乘，要跑大约 2 毫秒；一件是「小活」：一个小矩阵乘，只要大约 30 微秒。大活正在跑，小活已经就绪。小活要等多久？

    这不是假想题。在大模型推理服务里，长输入的预填充（prefill）会产生毫秒级的大计算，而已开始请求的逐字解码（decode）会产生几十微秒的小计算，两者撞在同一张卡上是日常。ExpertPlex（arXiv:2607.18002）这篇系统论文的全部设计，就建立在「小活到底要等多久、能不能只等一个极小的刻度」这个问题上。本页是它的前置知识页：不讲论文本身，只讲看懂它所需的 GPU 执行模型。上面的 2 毫秒与 30 微秒是教学构造的整数量级，用来制造反差，不代表任何测量值；prefill、decode、MoE 这些服务层概念本身由姊妹概念页《MoE 大模型推理与服务基础》负责，本页只在需要动机时点名。

    本页约定：kernel 指「在 GPU 上由大量线程并行执行的一段函数」，这是 CUDA 的用法，和操作系统内核（OS kernel）只是同名，没有任何关系。

    最容易误解

    • 「GPU 线程和 CPU 线程一样，随时会被系统切换」——GPU 的线程块（CTA）一旦被放到计算单元上，就运行到完成才释放，没有用户可控的中途打断（第 2、6 章）。
    • 「输入越长，每个 tile 就越大」——tile 的尺寸由硬件容量决定，与输入规模无关；输入变长只是 tile 的数量变多（第 3 章）。

    主要依据：NVIDIA 官方文档与白皮书——CUDA C++ Programming Guide、Hopper Tuning Guide、H100 架构白皮书、CUDA Driver API（stream 优先级 / Green Context）、MPS 与 MIG 官方文档。正文中的 [C1]–[C16]、[N1]–[N8] 编号在文末「来源与教学说明」逐条对应。

    先认识硬件：一块 GPU 里有什么

    要知道「小活要等多久」，先得知道大活跑在什么东西上面。一块 GPU 拆开看，真正需要记住的只有两类部件：计算单元和内存。

    计算单元叫 SM（Streaming Multiprocessor，流式多处理器）。可以把一块 SM 理解成一个小而完整的计算车间：它能独立执行指令、有自己的工人（通用计算单元）和一台专门机器（Tensor Core，一次完成一小块矩阵的乘加）。一块 H100 SXM5 上有 132 块 SM，每块 SM 有 4 个第四代 Tensor Core [C5][N1]。这就是 GPU「 massively parallel 」的全部含义：不是一个巨大的计算核心，而是一百多个独立车间同时开工。

    内存按离车间的远近分成几层，越近越快、越小：

    • 寄存器：SM 内部、线程私有的存储，最快也最小。
    • shared memory：SM 内部、同车间线程共享的可编程存储。H100 每块 SM 有 228KB，一个线程块最多能用 227KB [C6][N2]。
    • L2 缓存：全卡 132 块 SM 共享，H100 为 50MB [C5]。
    • HBM 全局内存：GPU 板载主存（H100 用的是 HBM3，第三代高带宽显存），H100 为 80GB，带宽 3.35 TB/s [C5][N1]。所有输入数据一开始都躺在这里。
    数据住在哪里、离计算多远（H100，数字为官方规格 [N1][N2]）：

  HBM3 全局内存   80 GB · 3.35 TB/s —— 输入数据的家
       │（经 L2 中转）
  L2 缓存         50 MB —— 全卡 132 块 SM 共享
       │
  SM 0 · SM 1 · …… · SM 131 —— 每块 SM 内部：
     228 KB shared memory + 寄存器 + 4 个 Tensor Core + 通用计算单元

  规则：数据必须搬进 SM 内部（shared memory / 寄存器）才能参与计算

    为什么分层？因为「搬数据」比「算数据」贵。HBM 有 80GB 但隔着整个芯片；shared memory 就在车间里，却只有 228KB。一个计算想跑快，就要尽量少从远处搬东西、搬来一次用多次。这条规则会在第 3 章直接决定 tile 的尺寸。

    回到贯穿例子：大活和小活的输入矩阵，此刻都躺在 80GB 的 HBM 里。它们要变成结果，都得先被搬到某块 SM 的 228KB 小柜子里。

    kernel 是怎么跑起来的：线程、warp、CTA 与 stream

    上一章是静态的硬件。这一章回答动态的问题：CPU 上一句「启动」，怎么变成 132 块 SM 上的千军万马？

    程序员写一个 kernel——一段函数。和普通函数不同的是，它不是被调用一次，而是被成千上万个线程同时执行，每个线程处理数据的一小块。这些线程按两级组织起来：

    • CTA（Cooperative Thread Array，也叫 thread block，线程块）：一组最多 1024 个线程 [C1]。关键性质：一个 CTA 整体驻留在同一块 SM 上执行，独占这块 SM 上分给它的那份 shared memory，CTA 内线程可以高效协作。
    • grid：一次启动的全部 CTA。一个 grid 可以有成百上千个 CTA。

    CTA 内部，SM 不是逐个线程调度，而是每 32 个线程组成一个 warp，以 warp 为单位发射指令 [C2][N3]——同一 warp 的 32 个线程齐步走，执行同一条指令、处理各自的数据。一块 SM 上可以同时常驻最多 64 个 warp [C2]，它们轮流占用计算单元：一个 warp 在等数据时，另一个 warp 立即补上。这就是 GPU 隐藏搬运延迟的基本手段，叫「用并行换等待」。

    一次 kernel 启动的旅程：

  CPU                                    GPU
  程序调用 kernel
     │  ① 提交到一个 stream（命令队列，同一队列内严格按提交顺序执行 [C4]）
     ▼
  stream ─────────────►  ② 硬件分发器把 grid 拆成一个个 CTA，
                            哪块 SM 有空位就放哪块
                            ┌──────┬──────┬──────────┐
                            │ SM 0 │ SM 1 │ …… SM 131│
                            └──────┴──────┴──────────┘
                            ③ 每块 SM 内，warp 调度器每周期
                               挑选一个就绪的 warp 发射指令
  ④ grid 里所有 CTA 全部跑完，kernel 结束，SM 空出

    现在说出本章最重要的事实：一个 CTA 被放到 SM 上之后，会运行到完成才释放这块 SM；CUDA 不提供任何让用户打断运行中 kernel 的接口 [C3]。官方文档在讲 stream 优先级时把这一点写得很直白：优先级只是「尽量先调度高优先级工作」的提示，「不会抢占已经在运行的工作，也不对执行顺序提供任何功能性保证」（CUDA Driver API，cuStreamCreateWithPriority，原文引用见第 6 章）[C11]。

    另一个需要记住的语义：同一个 stream 里的操作严格按提交顺序执行；不同 stream 之间没有顺序保证，资源允许时可以并发 [C4]。

    贯穿例子推进：大活的 grid 有几百个 CTA，一波波铺满了 132 块 SM；小活的 CTA 此刻提交到另一个 stream，只能排队等空位。小活要等多久，取决于大活的 CTA 什么时候跑完——这就是开头问题的第一层答案，也是「队头阻塞」（head-of-line blocking，即队列前面的长任务挡住后面的短任务，使短任务即使已就绪也无法开始）的来源。

    为什么矩阵乘要切成 tile：一次能搬多少数据说了算

    上一章说计算被切成 CTA。但一个 CTA 负责的那块矩阵乘，内部还要再切一层，切成 tile。为什么？这一章用一个可以手算的例子给出答案，并得出全页最关键的结构性结论：tile 的尺寸由硬件容量决定，输入变长只是 tile 变多。

    先复习矩阵乘的形式。$C = A \times B$，其中 $A$ 是 $M \times K$、$B$ 是 $K \times N$、$C$ 是 $M \times N$，每个输出元素是 $C[i][j] = \sum_{k=1}^{K} A[i][k] \cdot B[k][j]$——$A$ 的第 $i$ 行与 $B$ 的第 $j$ 列逐元素相乘再求和，共 $K$ 次乘加。

    不切 tile 的代价：手算一遍

    教学示例。取最小的可算规模：$M = N = K = 4$，两个 $4 \times 4$ 矩阵相乘。数一数「从内存读数据」的次数（这是第 1 章说的贵操作）。

    不切 tile 的算法：算每个 $C[i][j]$ 时，读 $A$ 的第 $i$ 行（4 个数）和 $B$ 的第 $j$ 列（4 个数）。于是 $A$ 的每个元素被它所在行的 4 个输出各读一次，共被读 $4$ 次；$A$ 有 16 个元素，总读取 $16 \times 4 = 64$ 次。$B$ 同理也是 64 次。合计 128 次读取。

    切 tile 的算法：把三个矩阵都切成 $2 \times 2$ 的小块（tile）。算输出 tile $C_{11}$（左上角的 $2\times2$）时，先把 $A_{11}$、$B_{11}$ 两小块搬进 SM 内的高速存储，算出部分和；再搬 $A_{12}$、$B_{21}$，累加进去。关键是：搬进车间的数据会被反复使用——$A_{11}$ 的 4 个元素服务了 4 次乘加，而不是读一次用一次。数下来，$A$ 的每个小块被 $N/2 = 2$ 个输出 tile 使用，即 $A$ 的每个元素只从内存读 $2$ 次，总读取 $16 \times 2 = 32$ 次；$B$ 同理 32 次。合计 64 次读取。

    算法（$4\times4$ 矩阵，教学示例）每个 $A$ 元素被读次数$A$ 总读取$B$ 总读取合计读取
    不切 tile$N = 4$$16 \times 4 = 64$64128
    切 $2\times2$ tile$N / T = 4 / 2 = 2$$16 \times 2 = 32$3264

    读取次数从 128 降到 64，省了一半。一般规律是：tile 边长为 $T$ 时，每个 $A$ 元素被读 $N/T$ 次——tile 越大，搬运越省 [F1]。

    补充：4×4 例子逐 tile 的读取清单

    切 $2\times2$ tile 后，$C$ 有 4 个输出 tile：$C_{11}, C_{12}, C_{21}, C_{22}$。每个输出 tile 沿 $K$ 方向要 2 步：$C_{11}$ 用 $(A_{11},B_{11})$ 再 $(A_{12},B_{21})$；$C_{12}$ 用 $(A_{11},B_{12})$ 再 $(A_{12},B_{22})$；$C_{21}$、$C_{22}$ 类似。$A_{11}$ 出现在 $C_{11}$ 和 $C_{12}$ 的计算中，共 2 次，且每次是整块搬入后块内 4 个元素都被复用——所以每个元素的「从内存读取」只有 2 次，而不是 4 次或 8 次。四个 $A$ 小块各被读 2 次，每次 4 个元素：$4 \times 2 \times 4 = 32$ 次，与正文一致。

    tile 能做多大：228KB 说了算

    既然 tile 越大越省，为什么不把 tile 做成 1000×1000？因为复用的前提是 tile 能整个搬进 SM 内的高速存储，而它的容量是硬件固定的。教学示例：用 fp16（每个数 2 字节）算，一个 $128 \times 128$ 的 $A$ tile 占 $128 \times 128 \times 2 = 32768$ 字节 $= 32$KB；$B$ tile 同样 32KB；为了不等待，通常要双缓冲（搬下一块的同时算这一块），搬运缓冲翻倍约 128KB；再加输出累加等开销，总量在百 KB 量级——已经逼近单 CTA 227KB 的上限 [C6][N2]。tile 再大就放不进车间了。

    所以 tile 的尺寸（实际高性能 GEMM 常用 $128 \times 128$ 这类档位）是由 shared memory 容量、数据类型和缓冲策略共同决定的固定值，跟你要算的矩阵总共有多大毫无关系。

    输入变长时，什么变、什么不变

    把例子的 $M$ 从 8192 加倍到 16384（教学构造数字），tile 边长仍是 128。行方向的 tile 数从 $8192 / 128 = 64$ 变成 $16384 / 128 = 128$——tile 数量翻倍，每个 tile 的搬运量和计算量完全不变。整活的耗时近似翻倍，但那是「同样的活干了两遍」，不是「每个活变大了」。

    把这一点翻译成调度语言（本文归纳）：tile 是 GEMM kernel 内部最小可独立完成的计算单位；单个 tile 的耗时由 tile 尺寸决定，与输入总长度无关。因此「一个 tile 执行完的那个瞬间」构成了一串与输入长度无关的天然调度刻度——一个跑 2 毫秒的 kernel 内部，其实每过一小段固定的时间就经过一个 tile 边界。记住这个结论，第 6 章末尾和 ExpertPlex 论文页都会用到它。

    贯穿例子推进：大活不是一个「2 毫秒的实心疙瘩」，而是几千个 tile 排成的长队；小活只有几个 tile。两者共用同一种刻度。

    Hopper 的协作工具箱：TMA、warp 分工与 CTA cluster

    第 3 章留下一个工程问题：一个 tile 的生命周期是「搬进车间 → 算 → 搬下一块」。如果搬的时候算闲着、算的时候搬闲着，一半时间就浪费了。要让搬和算重叠起来，还需要三件工具。这一章讲的都是 Hopper 架构（H100 这一代）引入的机制 [C7][C8][C9]。

    TMA：把搬运从计算线程手里解放出来

    在更早的 GPU 上，搬一个 tile 要靠计算线程自己一条一条指令地搬，搬运期间这些线程干不了别的。TMA（Tensor Memory Accelerator）是一个专门的异步拷贝引擎：只需要一个线程向它发出一条「把这整块张量从全局内存搬到 shared memory」的指令，引擎就在后台完成全部搬运，其他线程继续做计算，等数据到了再取 [C7]。它支持 1 到 5 维的张量块，也能在相邻 SM 的 shared memory 之间直接传输。

    warp specialization：搬运工与计算工的分工流水线

    有了异步搬运，就可以让一个 CTA 内的 warp 分工种：少数 warp 专职当 producer（发起 TMA 搬运、等数据到、通知大家），其余 warp 专职当 consumer（只负责算）。这就是 warp specialization [C9]。它的效果是一条流水线：

    tile 流水线（教学示意，时间向右）：

  producer warp：  搬 tile 1 ─┬─ 搬 tile 2 ─┬─ 搬 tile 3 ─┬─ 搬 tile 4
  consumer warp：             └─ 算 tile 1 ─┴─ 算 tile 2 ─┴─ 算 tile 3
                              ▲
                  算 tile t 的同时，tile t+1 已经在路上

    教学解释。这条流水线只说明「搬与算在时间上重叠」这一层关系。真实的实现还要处理同步（谁通知谁数据到了）、多级缓冲等细节，本页省略；正式机制以官方文档的 TMA 与 pipeline 章节为准 [C7]。

    CTA cluster 与 DSMEM：相邻车间直接递东西

    第 2 章说过，CTA 是协作的天花板：不同 CTA 在编程模型里互相看不见对方的车间内部。Hopper 打破了这堵墙——可以把最多 8 个 CTA 声明为一个 CTA cluster（H100 上通过显式 opt-in 可以到 16 个，但这是不可移植的特例）[C8][N4]。cluster 内的 CTA 被硬件共同调度到同一组相邻的 SM（同一个 GPC——Graphics Processing Cluster，图形处理集群，是 GPU 硬件层级中一组物理相邻的 SM，H100 有 8 个 GPC）上 [C15]，并且可以直接读写彼此 SM 里的 shared memory——这个机制叫 DSMEM（Distributed Shared Memory，分布式共享内存）[C8]。

    它解决的瓶颈是：当一块矩阵太大、一个 CTA 的车间放不下、必须几个 CTA 分摊时，没有 cluster 就只能绕远路——写回全局内存再让别人读；有了 cluster，相邻车间直接递。配合 TMA 的组播能力，同一份数据可以一次发给 cluster 内多个 CTA [C7]。

    代价同样由官方给出：cluster 越大，GPU 上能同时活跃的独立 block 数可能越少 [C8]——共同调度要求一组相邻 SM 同时有空位，比找单个空位更苛刻。

    本章的机制描述是概念级简化：省略了 TMA descriptor 的构造、mbarrier 同步原语等实现细节；这些不影响「搬运不占计算线程」「cluster 内直接互访」两个核心结论。

    贯穿例子推进：大活内部，tile 一个接一个在流水线上走；小活的 tile 太少（只有几个），流水线刚预热就结束了——小 kernel 天然吃不满硬件，这是它「单位效率低」的另一层原因。

    反复启动太贵：persistent kernel 与 CUDA Graph

    前几章都在讲一个 kernel 内部怎么跑。这一章换一个角度：如果一个 kernel 本身很小、一天要跑成千上万次，那么「启动」这个动作本身就值得审视。

    启动一次 kernel 有两部分开销。CPU 侧：每次启动都要走一遍「准备参数、提交到 stream」的流程，量级是微秒级（量级说明：官方文档没有给出单一数字，CUDA Graphs 章节定性指出「当 kernel 又多又小时，逐次启动的开销占比会变得显著」[C10][N8]）。GPU 侧：grid 的 CTA 要被逐波分发到 SM、跑完要收尾。大活跑 2 毫秒，这点开销无所谓；小活本身只要 30 微秒，逐次启动的占比就刺眼了。有两种主流手段把它压掉。

    persistent kernel：不退出，循环领活

    persistent kernel（常驻内核）不是一种 CUDA API，而是一种编程模式（这一点常被误解）：kernel 只启动一次，启动后不退出，在 kernel 内部写一个循环，不断从全局内存的任务队列里领取下一个任务、执行、再领，直到收到退出信号。启动开销从「每任务一次」摊成「全程一次」。

    伪代码：persistent kernel 的主循环（不是 Python，不可运行） 
    输入：全局内存中的任务队列 Q（每个任务描述一组 tile 的输入位置与输出位置）
状态：本 CTA 长期驻留 SM，不退出
循环：
    从 Q 领取下一个任务（队列为空时按实现等待或检查退出标志）
    按任务描述搬入数据 → 计算 → 写回结果
    标记该任务完成
直到：收到全局退出信号
输出：全部任务的结果

    说明：这是机制示意，省略了多 CTA 抢任务的原子操作、队列溢出处理等真实工程内容。

    代价同样直接，而且是第 2 章事实的推论：常驻期间，它的 CTA 一直占着 SM，别的 kernel 用不了这些 SM。常驻 kernel 省下了启动，却把「什么时候让出资源」这个问题从硬件手里拿回到了软件自己手里——这正是它既强大又危险的原因。

    CUDA Graph：录制一次，整体重放

    另一种手段解决的是 CPU 侧。深度学习的一步推理往往是几十上百个小 kernel 的固定序列。CUDA Graph 允许把这串操作录制（capture）成一张图，之后每次执行只需把整张图重放（replay）一次提交，消除了逐个 kernel 的 CPU 提交开销 [C10]。

    约束来自「录制」二字：图内 kernel 的数量、形状、内存地址在捕获时就固定了。输入长度变了、形状变了，就得换一张图或重新捕获。所以 CUDA Graph 天然适合形状固定的循环体（比如固定 batch 的逐字解码），不适合每步形状都变的工作负载。

    两种手段是正交的，可以叠加：一个常驻 kernel 内部，也可以把它周期性执行的那串小 kernel 录成图来重放。共同点是都偏好「形状固定」的负载。vLLM 推理引擎中 CUDA Graph 的工程细节（捕获哪些尺寸、捕获失败会怎样）属于另一个故事，见 torch.compile 与 CUDA Graph 笔记。

    贯穿例子推进：小活每 30 微秒来一次。若每次单独启动，开销占比高；若把它录进 CUDA Graph 或交给常驻 kernel 执行，启动开销被压掉——但前提是大活愿意让出 SM。绕了一圈，问题又回到了资源分配。

    分一张卡的四种机制：能力边界对照

    最后一章回答开头问题的完整版：大活小活要共享一张 GPU，系统层面到底有哪些分法？NVIDIA 官方提供四种机制，力度各不相同。逐个看它们能做什么、不能做什么——「不能」比「能」更重要。

    stream 优先级：只是提示，不是抢占

    给不同 stream 设不同优先级（如小活高优先级、大活低优先级）。官方文档的原文语义是：优先级「提供一个提示，让高优先级的工作在可能时被优先调度，但不会抢占已经在运行的工作，也不对执行顺序提供任何功能性保证」（CUDA Driver API，cuStreamCreateWithPriority）[C11]。翻译过来：它能决定「下一个空位给谁」，不能决定「现在让谁停下」。大活的 CTA 已经铺在 SM 上，小活优先级再高也得等空位。

    MPS：多进程真并发，但不预留资源

    MPS（Multi-Process Service）让多个操作系统进程（各自独立的程序）的 kernel 在同一张卡上真正并发执行 [C12]。它可以给每个客户端设资源限额，但官方文档明确：限额「不为任何客户端预留专用资源，只是限制它最多能用多少」，而且「不同客户端的 kernel 可能执行在同一块 SM 上，取决于负载均衡」[C12]。所以 MPS 提供的是「可以挤在一起」，不是「各自圈地」；干扰（缓存竞争、SM 争抢）依旧存在。

    MIG：硬件级隔离，但档位固定、改配置要停负载

    MIG（Multi-Instance GPU）是最硬的分法：把 GPU 在硬件层切成互相隔离的实例，各自独占 SM、显存和缓存切片。隔离最强，代价是只有固定档位。H100 有 7 个可用的 GPU 计算切片（对应 7 个 GPC，另留 1 个 GPC 给管理用）；profile 名称里的数字 g 表示该实例占用的计算切片数，数字后的 GB 表示它独占的显存量，7 个切片用满即整卡 [C13][N5]。H100（80GB）的全部 profile 如下：

    MIG profile显存每卡最多实例数
    1g.10gb10 GB7
    1g.20gb20 GB4
    2g.20gb20 GB3
    3g.40gb40 GB2
    4g.40gb40 GB1
    7g.80gb（整卡）80 GB1

    两个任务分一张卡，只能从这张表里挑组合（例如 3g + 4g 正好用满）。负载比例变化时想改配置，需要 GPU 上没有运行中的负载才能重配——它没有时间复用，也没有运行中调整 [C13]。

    Green Context：进程内按 SM 圈地，但创建后固定

    Green Context（CUDA 12.4 引入）在同一个进程内把 SM 集合切成空间分区：往某个 Green Context 的 stream 提交的 kernel，只会落在该分区的 SM 上 [C14]。它比 MIG 细：不需要切显存，粒度是 SM 个数——但 Hopper 上分区必须是 8 的倍数、最少 8 个 SM [C14][N6]。两条边界由 API 设计决定：其一，SM 分区在创建 Green Context 时通过 split API 指定，Green Context API 不提供运行期重分区接口，要改变分区需销毁并重建 Green Context，所以运行中的 kernel 期间不能重新划分；其二，「即使两个 Green Context 的 SM 分区互不相交，也不保证两者的 kernel 会并发执行或有前进保证」（CUDA Driver API，Green Contexts 章节）[C14]。

    对照与归纳

    机制切分对象粒度运行期可否改变关键短板
    stream 优先级 [C11]什么都不切，只是调度提示单个 kernel 的先后随时不抢占已运行的 kernel，不保证顺序
    MPS [C12]多进程并发执行进程级；限额是上限限额可调整不预留资源，kernel 可落同一 SM
    MIG [C13]硬件级实例（SM+显存+缓存）固定六档改配置需停负载档位粗，无时间复用
    Green Context [C14]进程内 SM 空间分区8 的倍数、最小 8 SM创建后固定kernel 期间不可重配置，无并发/前进保证

    把四行合起来，得到一个本文归纳（各分句均有官方来源，合取为推断）[C16]：四种机制中没有任何一种能在一个 kernel 运行期间，以微秒级粒度重新分配 SM。优先级不抢占；MPS 不预留；MIG 和 Green Context 都是空间切分、改起来要停负载或重建上下文。于是共享一张卡只剩两个极端：要么切死（空间固定分区，闲时浪费），要么等（长 kernel 挡短 kernel，队头阻塞）。

    这个空位正是「tile 级调度」要补的：如果 kernel 自身被设计成能在 tile 边界让出 SM（第 3 章的刻度），调度粒度就从「整个 kernel」细化到「一个 tile」——ExpertPlex 的 APK 走的就是这条路，具体机制在论文解析页展开，本页的任务到此为止。

    本章数字以 H100（Hopper）与 CUDA 12.x 文档为准；跨代际数字（SM 数、分区粒度、MIG 档位）会变，但「无运行期细粒度重分配」这一结构性结论在现有代际上均成立。
