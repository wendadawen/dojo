    vLLM V1 框架总览

    APIServer 进程经 AsyncLLM 与 EngineCoreClient 只做请求接发；调度与模型执行同处 EngineCore 进程，由 run_busy_loop 忙等循环逐回合推进，回合内经 Executor→Worker→Runner 三层下发，collective_rpc 以方法名字符串统一单卡直调与多卡广播。

    更新于 2026-08-21 · 类型：源码走读结论（源码基线 vLLM v0.20.0-718-gee4ed6d71d，TP=1 单机）

    1. 两进程的职责划分与证据

    vLLM V1（vllm serve 启动）运行时包含两个独立进程，各自持有不同的代码：

    进程持有的对象职责
    APIServer
    （主进程）    		 AsyncLLM、EngineCoreClient（实现类 MPClient）、OutputProcessor、IncrementalDetokenizer（按请求，由 OutputProcessor 持有）、多模态预处理 接收 OpenAI 请求、渲染 prompt、发送请求、接收结果并返回用户
    EngineCore
    （后台进程）    		 EngineCoreProc → EngineCore → Scheduler、UniProcExecutor → Worker → GPUModelRunner 与模型本身 调度、模型 forward、采样、KV cache 管理

    两份进程 trace 印证这一划分：APIServer 侧只出现 core_client、output_processor、renderers 等模块，不含调度器与 worker；EngineCore 侧则是 scheduler、gpu_worker、gpu_model_runner。两个进程如何拼成完整引擎——入口、引擎、执行、模型、编译五层与跨层子系统的地图见vLLM 框架全景。

    2. 忙等循环与回合结构

    EngineCore 进程的入口是 run_busy_loop，它以一个 while 循环交替执行两个动作：

    def run_busy_loop(self):
    while self._handle_shutdown():
        self._process_input_queue()   # 从输入队列收请求，无活时阻塞等待
        self._process_engine_step()   # 执行一步：调度→forward→采样→更新

    _process_input_queue 从输入队列取消息（该队列由 ZMQ socket 线程 process_input_sockets 投递），按类型分发：ADD 调用 add_request 将请求放入调度器，ABORT 取消请求，UTILITY 执行控制类调用。_process_engine_step 调用 step_fn 完成一个执行回合，把结果放入输出队列送回 APIServer。

    EngineCore 进程 trace 的主线程上，函数事件按时间排列呈现 _process_input_queue → _process_engine_step → step_with_batch_queue 的重复序列，一次采样中共出现 23 个完整回合。

    回合内的钩子、空转与容错

    _process_engine_step 内部依次调用 pre_engine_step、step_fn、post_engine_step、post_step。其中 pre_engine_step 与 post_engine_step 由本地 fork 的 vllm.hcf_mixin（vllm/hcf_mixin/v1/engine/core_mixin.py）注入，上游 vLLM 的同名流程中只有 post_step。两个"步后"钩子职责不同：post_engine_step 累计本回合耗时并写入调度统计（忙时统计）；post_step 在同步调度、使用推测解码、本回合执行了模型且 batch_queue_size == 1 时更新草稿 token，异步调度与批队列（batch_queue_size > 1）下草稿 token 改在 worker 进程或 step_with_batch_queue 内刷新。

    回合末尾有一个条件休眠：当本回合没有执行模型但调度器仍有请求时，调用 time.sleep(0.001) 让出 GIL，使后台的 KV 传输线程得以推进，避免忙等饿死后台线程。

    回合内的容错由 log_error_detail 上下文管理器承担：它用 @contextmanager 装饰，yield 处即为 with 块代码的执行位置；模型执行抛异常时，先 dump 引擎配置、调度输出与统计信息，再重新抛出异常。

    step 与 step_with_batch_queue 的选择

    step_fn 指向哪个函数由 batch 队列是否建立决定：batch_queue_size > 1 时建立队列并指向 step_with_batch_queue，否则指向 step。而 batch_queue_size 在 UniProcExecutor 下由 async_scheduling 决定（2 或 1）。async_scheduling 未显式设置时默认为 None，vLLM 会在配置阶段将其自动置为开启（除非模型类型或推测解码方式不兼容）。因此默认部署下实际执行的是 step_with_batch_queue：它优先填充深度为 2 的 batch 队列，队列已满或无可调度请求时才等待最早一批完成——这样 GPU 执行与下一批的调度准备得以重叠。

    3. 三层执行架构：Executor → Worker → Runner

    从 EngineCore 到模型 forward 之间有三层对象，各管一件事：

    层名字含义职责
    Executor执行者多卡组织：创建多少 worker、调用如何分发（广播）、结果如何收集
    Worker工人单卡生命周期：初始化设备、加载权重、每步执行、健康检查、休眠唤醒
    GPUModelRunnerforward 执行者forward 细节：准备输入、调用模型、处理采样输出

    由此可推，三层职责彼此隔离：更换并行度只需改 Executor，更换模型只需改 Runner。

    Worker 的具体职责

    Worker（GPU worker）的方法按生命周期分三组。启动阶段：init_device 初始化 GPU、load_model 加载权重、determine_available_memory 测量可用显存、initialize_from_config 初始化 KV cache、compile_or_warm_up_model 编译模型。每步执行：execute_model 跑模型、sample_tokens 采样。管理：check_health 健康检查、sleep/wake_up 休眠唤醒、LoRA 相关方法、profiler 启停。Worker 自己不实现 forward 细节，而是把这部分交给持有的 GPUModelRunner。

    WorkerWrapperBase 包装层

    Executor 持有的不是 Worker 本体，而是 WorkerWrapperBase。这层包装承担三件事：延迟初始化（构造时只记录 worker 的模块名与类名，init_worker 被调用时才真正实例化）；生命周期管理（shutdown、健康检查）；统一门面（__getattr__ 把所有属性访问转发给内部 worker，execute_model 等方法在转发前附加多模态缓存处理）。因此在 trace 中会先看到 worker_base.py 的转发帧，再看到 gpu_worker.py 的执行帧。

    worker_cls="auto" 的解析

    配置中 worker_cls 默认为字符串 "auto"，表示由平台决定。平台不是写死的：模块导入时不做探测，首次访问 current_platform 时才触发懒加载，逐个运行各平台插件函数；CUDA 插件用 NVML 检测本机 NVIDIA GPU 数量（nvmlDeviceGetCount() > 0），命中即选中 CudaPlatform。选中后由平台把 "auto" 替换为具体类名 vllm.v1.worker.gpu_worker.Worker，WorkerWrapperBase.init_worker 再用 resolve_obj_by_qualname 按类名导入并实例化。

    model_runner 的 v1/v2

    Runner 存在 v1/v2 两个实现，但两者都是 GPUModelRunner 类，差异在内部行为。v2 默认仅对单一架构集合启用（如 Qwen3ForCausalLM，且要求非 MoE、非量化、安装了 Triton）；不在名单内的架构（如 Qwen3_5ForConditionalGeneration）走 v1 实现。也可用环境变量强制指定。此区分与引擎的 V0/V1 代际无关——v1/v2 runner 都属于 V1 引擎。

    4. collective_rpc：统一的跨 worker 调用接口

    EngineCore 对 worker 的执行类调用（execute_model、sample_tokens 等）都走 collective_rpc 这一个入口，传入的是方法名字符串。该接口同时接受方法名字符串与可调用对象：字符串可直接广播，函数对象路径先经 cloudpickle 序列化为字节再广播。EngineCore 以方法名字符串调用，不区分卡数——TP=1 与 TP=8 使用同一行调用。

    4.1 UniProcExecutor 路径（TP=1）

    # collective_rpc 内部（非阻塞分支）
result = run_method(self.driver_worker, method, args, kwargs)
# run_method：按方法名字符串从对象上取方法再调用
func = getattr(obj, method)
return func(*args, **kwargs)

    TP=1 时 worker 与 EngineCore 同进程，run_method 直接以 getattr 找到方法并调用，没有跨进程开销。

    4.2 MultiprocExecutor 路径（TP>1）

    TP>1 时每个 GPU 一个独立 worker 进程（WorkerProc）。调用被序列化后放进广播消息队列 rpc_broadcast_mq：该队列对小消息用共享内存环形缓冲传输，对超过阈值的消息退化为 ZMQ 发布订阅（XPUB/SUB）。每个 worker 从队列收到同一份消息，各自在自己进程内解析并执行，结果写回各自的 response 消息队列。Executor 侧返回一个 future，其内部等待全部 worker 的 response 队列并聚合结果——因此 N 卡时调用方拿到的仍是单个 future，其中包含 N 份回复。方法名若传入的是函数对象而非字符串，则先经 cloudpickle 序列化为字节再广播。

    5. 每回合四动作与一次请求往返

    动作调用链产出
    调度Scheduler.scheduleSchedulerOutput：本步各请求的 token 数、KV block 分配
    执行model_executor.execute_model → collective_rpc → Worker.execute_model → GPUModelRunner.execute_modellogits
    采样model_executor.sample_tokens → sampler新 token id
    更新Scheduler.update_from_output更新请求状态与 KV cache，产出 EngineCoreOutputs

    调度器没有 prefill 与 decode 两个阶段：每个请求只维护 num_computed_tokens（已计算数）与 num_tokens_with_spec（目标数），每步在 token 预算内尽量推进前者追上后者。一个 983 token 的 prefill 请求表现为单回合内调度 983 个 token，之后的 decode 每回合只推进 1 个 token。同一个 983 token 的 prefill 回合在模型执行阶段退回 eager，随后的 decode 回合才命中捕获图重放（多模态统一输入与 cudagraph）。这一分布同样体现在 trace 中：EngineCore 主线程的高频事件集中在 forward 与 KV cache 管理函数上，调度函数的调用频率远低于前者。

    两进程间一次请求往返的五要素：输入为 EngineCoreRequest（普通字段经 MsgpackEncoder 序列化，张量走带外共享内存传输）；状态为 EngineCoreProc 的输入、输出与 abort 三类队列；关键参数为 ZMQ 地址（同机 ipc://，跨机 tcp://host:port）；主要步骤为 add_request_async 经 ZMQ 发送 ADD → _process_input_queue 收到并放入调度器 → 回合执行 → 结果放入输出队列 → APIServer 的 output_handler 循环拉取；输出为 EngineCoreOutputs，经 OutputProcessor 转为 RequestOutput 推给用户。

    6. 类与进程大全辨析

    这套架构中的多个类名后缀相近，按后缀归类如下。

    命名规律

    • Client 结尾：客户端——连接、驱动别人的那一端
    • Proc 结尾：进程入口——负责把自己装进一个独立进程
    • Executor / Worker / Runner：执行链三层，越往下越靠近模型本体
    • Wrapper / Base 结尾：包装壳或抽象基类，不自己干活
    • Async 前缀：异步版本（用 await，等待时让出控制权）

    APIServer 进程的类

    类是什么
    EngineClient（ABC）"引擎客户端"的抽象接口，定义 generate、encode、abort 等能力。位于引擎代际无关的公共层
    AsyncLLMEngineClient 的唯一实现，V1 引擎的前端对象。收请求、发请求、收结果；内部持有 EngineCoreClient 与 OutputProcessor，并运行 output_handler 后台循环
    EngineCoreClient（ABC）"连接 EngineCore 的客户端"抽象。EngineCoreClient 与 EngineClient 是两个不同的接口：后者是引擎总接口，前者专指跨进程通信
    MPClientEngineCoreClient 的 ZMQ 实现，实际部署使用的那个
    InprocClientEngineCoreClient 的同进程实现（不跨进程的场合）

    EngineCore 进程的类

    类是什么
    EngineCore引擎本体：持有 Scheduler 与 model_executor，提供 step 系列方法。注释自称 "Inner loop of vLLM's Engine"
    EngineCoreProcEngineCore 的进程包装：提供 ZMQ 服务端、把 EngineCore 装进后台进程、跑 run_busy_loop。TP=1 时后端进程的唯一创建点：run_engine_core 经 multiprocessing.Process 创建 EngineCore 进程。TP>1 时 MultiprocExecutor 另经 multiprocessing.Process 为每张 GPU 创建 WorkerProc 进程
    Scheduler调度器：选批、定 token 数、分配 KV block
    Executor（ABC）执行器抽象，经 get_class 按配置选择实现
    UniProcExecutorTP=1：单进程，worker 与 EngineCore 同进程，直接调用
    MultiprocExecutorTP>1：每 GPU 一个 worker 进程，广播调用
    RayDistributedExecutor用 Ray actor 管理 worker 的实现（集群部署）
    WorkerWrapperBaseworker 的包装壳：延迟初始化、生命周期、__getattr__ 门面转发。Executor 实际持有的是它
    WorkerBaseworker 基类
    WorkerGPU worker（gpu_worker.py）：单卡总管，init_device/load_model/execute_model/sample_tokens/check_health
    GPUModelRunnerforward 执行者：准备输入、调用模型、处理输出。worker 内最贴近模型的一层

    继承与持有关系全景

    最易混淆的对照

    混淆对区别
    EngineClient vs EngineCoreClient前者是引擎总接口（AsyncLLM 的父类）；后者是"连接 EngineCore 的通信客户端"（MPClient 的父类）。一个管接发请求，一个管跨进程连线
    EngineCore vs EngineCoreProc前者是引擎本体（干活）；后者是进程壳（把本体装进后台进程并提供 ZMQ 服务端）
    Worker vs WorkerWrapperBase前者是工人；后者是工人的包装壳（延迟初始化 + 门面）。Executor 持有的是后者
    Worker vs GPUModelRunner前者管单卡全生命周期；后者只管 forward 细节。前者持有后者
    UniProcExecutor vs MultiprocExecutorTP=1：worker 同进程直调；TP>1：每卡独立 worker 进程，广播调用
    AsyncLLM vs LLMEngineAsyncLLM 是 V1 的异步前端（EngineClient 的实现）；LLMEngine 是 V1 中保留的同步 / 离线 legacy 类（vllm/v1/engine/llm_engine.py，注释自称 "Legacy LLMEngine for backwards compatibility."），同样不继承 EngineClient。两者都属于 V1

    类与进程的边界

    所有上述名字都是类，没有哪个名字本身是进程。APIServer 进程即 vllm serve 的主进程；后端进程由 EngineCoreProc.run_engine_core 作为入口、经 multiprocessing.Process 创建，是 TP=1 时后端进程的唯一创建点。TP=1 时 UniProcExecutor 的 worker 与 EngineCore 共用后端进程；TP>1 时 MultiprocExecutor 另经 multiprocessing.Process 为每张 GPU 创建 WorkerProc 进程。

    trace 证据

    实测观察；原始 trace 记录已不随页面留存，其中的回合数与函数热点分布不可再复核。

    • APIServer 进程 trace：只含 core_client/output_processor/renderers 等模块
    • EngineCore 进程 trace：含 scheduler/gpu_worker/gpu_model_runner，主线程 23 个回合序列；step_with_batch_queue 出现而 step 未出现
    • 环境：实测环境为 vLLM 0.22.2.dev、torch 2.11.0+cu130、Qwen3.5-0.8B、TP=1 单机；该版本串在仓库内已无对应检出，源码核对基线为本地检出 v0.20.0-718-gee4ed6d71d

    范围与限定

    • 回合序列由 trace 中函数事件的时间序重建（该 torch 版本 profiler 的 with_stack 不能捕获调用栈），不是调用栈直接给出
    • 结论限定 TP=1 单机；MultiProc（TP>1）与 Ray 后端下 worker 进程归属不同，仅在相应章节说明其差异
    • UniProcExecutor CPU 线程管理的相关上游修复 PR（限制 torch intra-op 线程数）未在本地代码核实，仅确认本地 UniProcExecutor 无线程限制代码、MultiprocExecutor 有（置 OMP_NUM_THREADS=1）
