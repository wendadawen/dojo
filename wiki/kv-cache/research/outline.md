# kv-cache 文章大纲

## 1. 页面开头

- 开篇具体问题：一个客服模型读完 20,000 token 的产品手册要回答问题，回答第二个问题时还需要手册的哪些中间结果？重算一遍还是留着？留的话要留多少？
- 简要解释：KV cache 是推理时留下的注意力 key/value 张量，让每个新 token 直接读取历史信息而无需重算。本文讲清它是什么、怎么随两阶段产生与使用、有多大、为什么成为显存管理的主角。
- 核心问题（学习目标 Q1–Q4）。
- 首个示例：手册场景的第一次量化（第 1 章内展开）。
- 过渡：先看注意力计算到底需要什么。

## 2. 章节设计

### 第 1 章 注意力为什么需要缓存——K/V 与查询无关

- 章节问题：生成每个新 token 时，注意力计算要用到哪些历史数据？为什么这些数据可以只算一次？
- 答案要点：注意力公式里 $q_t$ 对全部 $k_{1..t}$ 点积、加权全部 $v_{1..t}$（standard-attention 页公式）；$k_i,v_i$ 由第 $i$ 个 token 的输入经该层权重矩阵得到，与 $q_t$ 是谁无关（C3，推断标记）；不缓存时每步重算全部历史 K/V，$n$ 步生成的总计算是 $O(n^2)$ 量级前缀计算（推断），缓存后历史 K/V 变纯读取。构造示例：4 token 序列「今天/天气/很/好」第 4 步注意力需要 $k_1..k_4,v_1..v_4$，其中 $k_1..k_3,v_1..v_3$ 在第 1–3 步已经算过且值不变。
- 正文要点：先复述注意力公式的计算依赖（链接 standard-attention 页），再给"与查询无关"观察，最后讲缓存收益；手算示例 4 token 每步的矩阵形状。
- 表达材料：注意力公式引用（$q_t$ 与历史 K/V 的关系式，来自 standard-attention 页结论的复述）；4 token 手算（数值示例）。
- 前置知识：standard-attention 页链接（首次引入注意力公式时）。
- 折叠块：展开：4 token 例子逐步写出第 1/2/3/4 步各自新算的 k/v 与读取的缓存（矩阵维度逐步）。

### 第 2 章 prefill 与 decode——缓存产生的两个阶段

- 章节问题：一个请求的生命周期里，KV cache 在什么时候写入、什么时候读取、什么时候追加？
- 答案要点：prefill 并行处理全部输入 token（手册 + 问题），一次算出所有输入的 K/V 写入缓存并产出第一个输出 token；decode 每步只算 1 个新 token 的 q/k/v，k/v 追加进缓存，q 读全部缓存（C2）；资源特征：prefill 计算密集（大矩阵乘）、decode 访存密集（每步计算少但读全部缓存）——该特征是后续 serving 机制的分析基础。构造示例沿用：prefill 处理 20,004 token（手册+问题+起始），decode 每步追加 1 token 缓存。
- 正文要点：两阶段用同一 4 token 例子演示；强调"decode 每步 KV cache 增长 1 token"与第 3 章大小公式的衔接。
- 表达材料：两阶段流程图（结构 A：输入 → prefill（并行算 K/V + 第一个 token）→ decode 循环（算 1 个新 token 的 k/v 追加 → 读全部缓存 → 输出）→ 至 EOS 停止）。
- 折叠块：无（机制简单，正文完整）。

### 第 3 章 缓存有多大——每 token 字节数公式

- 章节问题：20,000 token 的手册到底占多少显存？
- 答案要点：每 token 每层 K、V 各 $H_{\text{kv}}$ 头 × $d_{\text{head}}$ 维（F1：$2\cdot L\cdot H_{\text{kv}}\cdot d_{\text{head}}\cdot b$）；MHA 下 $H_{\text{kv}}=H_q$、GQA 下 $H_{\text{kv}}<H_q$（GQA 最小定义：多组查询头共享一组 KV 头）；Llama-3.1-8B 手算 128 KB/token（N2）、手册 2.5 GB；OPT-13B MHA 800 KB/token 对照（N1）；两个检查：GQA 头数比 8/32 → 恰为 MHA 的 1/4；token 数翻倍则总量翻倍（线性）。
- 正文要点：公式前先讲"每 token 每层都要存一份"的结构原因（第 1 章的 K/V 在每一层都各有一套）；GQA 只在此处给最小定义与大小影响，不展开训练动机；b 的取值（bf16=2、FP8=1）与量化一句话说明。
- 表达材料：F1 公式 + 符号列表；Llama-3.1-8B 与 OPT-13B 并排手算表（组件 14）。
- 折叠块：展开：128 KB/token 的完整代入（2 × 32 × 8 × 128 × 2 = 131,072 B）与 20,000 token → 2.56 GB 的乘法。

### 第 4 章 为什么显存成为瓶颈——动态缓存与权重的争夺

- 章节问题：单看一条公式似乎不大，为什么 KV cache 会挤爆显存？
- 答案要点：三个因素相乘——token 数线性增长 × 并发请求数 × 与静态权重共用同一块显存；数字：13B 模型 A100 40GB 约 30% 显留给 KV cache（N3/C4）；OPT-13B 单请求最长 1.6 GB（N1）；128K 窗口单请求 16 GB（N5，Llama-3.1-8B）；40 GB 只放 0.3M token（N4，与 Strata 论文交叉验证）。误解处理：KV cache 不是部署时固定的（动态）；窗口 128K ≠ 存得下（Q3 误解 2）；缓存省计算不省存储——放不下时逐出重算或分层（引出后续两页的一句话过渡 + 链接 paged-attention、prefix-caching）。
- 正文要点：以"容量账"收束：给三个数字（0.3M token / 16 GB 单请求 128K / 30% 显存占比）说明量级；结尾一句过渡到存储管理问题域（不展开 Strata）。
- 表达材料：容量数字表（组件 14：模型、每 token 字节、单请求 128K、40GB 可存 token 数）。
- 折叠块：补充：GQA/MQA 一句话谱系与 $b$ 的精度取值（FP16/bf16/FP8/INT4 对应 2/2/1/0.5 字节，量化只改 $b$ 不改公式结构）。
