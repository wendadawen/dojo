    KV cache（键值缓存）：让每个新 token 免于重算全部历史

    主要依据：Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention"（SOSP 2023, arXiv:2309.06180）§1、§3；Xie et al., "Strata: Hierarchical Context Caching for Long Context Language Model Serving"（OSDI 2026, arXiv:2508.18572v2）§1、§2.1；Zheng et al., "SGLang: Efficient Execution of Structured Language Model Programs"（NeurIPS 2024, arXiv:2312.07104）§1、§3。

    一个客服模型读完 20,000 token 的产品手册后回答了一个问题。紧接着第二个问题到来，仍然以这本手册开头。回答第二个问题时，模型还需要手册 20,000 个 token 的哪些中间结果？从头再算一遍，还是留在显存里备用？如果留下，要留多少、够不够放？本文回答四个问题：注意力计算为什么需要全部历史 token 的 K/V，缓存到底省了什么计算；prefill 与 decode 两阶段各自怎么产生和使用缓存；一份上下文的 KV cache 有多大；以及为什么它会成为显存瓶颈。后两个问题的答案，是理解一切 KV cache 管理机制（分页、前缀复用、分层存储）的定量基础。

    本文讨论的是推理阶段的 KV cache。注意力计算本身（缩放点积、多头结构）见 标准 Transformer 注意力，本文直接使用其结论，不重复推导。

    核心问题

    1. 注意力计算为什么需要全部历史 token 的 K/V？缓存到底省了什么计算？

      解答：K/V 与查询无关，算一次可反复用

      注意力中第 $t$ 个 token 的查询 $q_t$ 要与序列中全部 $k_1,\ldots,k_t$ 做点积，再按权重聚合全部 $v_1,\ldots,v_t$。而 $k_i$、$v_i$ 只由第 $i$ 个 token 自身的输入经该层权重矩阵映射得到，与"现在在算哪个查询"无关，因此对每个 token 算一次即可跨步复用。不缓存时每生成一个 token 都要重算全部历史的 K/V，生成 $n$ 个 token 的总前缀计算量是 $O(n^2)$ 量级；缓存后历史 K/V 变成纯读取。完整推导见「注意力为什么需要缓存」一章。

    2. prefill 与 decode 两阶段各自如何产生和使用 KV cache？

      解答：prefill 批量写入，decode 每步追加一个 token

      prefill 一次性并行处理全部输入 token，算出它们的 K/V 写入缓存并产出第一个输出 token；decode 逐个生成后续 token，每步只算 1 个新 token 的 q/k/v，其中 k/v 追加进缓存，q 读取全部缓存做注意力。两阶段资源特征不同：prefill 是计算密集的大矩阵乘，decode 是访存密集的小步计算。见「prefill 与 decode」一章。

    3. 一份上下文的 KV cache 有多大？

      解答：每 token 字节数公式，Llama-3.1-8B 为 128 KB

      每 token 的 KV cache 占 $2\cdot L_{\text{layers}}\cdot H_{\text{kv}}\cdot d_{\text{head}}\cdot b$ 字节（K 与 V 两份、层数、KV 头数、头维度、每元素字节数）。Llama-3.1-8B（32 层、8 个 KV 头、头维 128、bf16）算得 128 KB/token，20,000 token 手册约 2.44 GB；对照 MHA 模型 OPT-13B 为 800 KB/token。GQA 通过减少 KV 头数直接缩小缓存。见「缓存有多大」一章。

    4. KV cache 为什么会成为显存瓶颈？常见误解有哪些？

      解答：线性增长 $\times$ 并发数 $\times$ 与权重共用显存

      缓存大小随 token 数线性增长、随并发请求数相乘，且与静态模型权重争夺同一块显存：13B 模型在 40GB A100 上约 30% 显存留给 KV cache；40 GB HBM（GPU 高带宽显存）对 Llama-3.1-8B 只够缓存约 0.3M token。缓存只省计算不省存储，放不下时只能逐出（丢缓存重算）或分层（搬到 CPU/SSD）。常见误解包括"KV cache 是部署时固定的"与"上下文窗口 128K 说明显存放得下 128K"。见「为什么显存成为瓶颈」一章。

    1. 注意力为什么需要缓存——K/V 与查询无关

    先看注意力计算到底依赖哪些数据。标准 Transformer 注意力的结论是：第 $t$ 个位置的输出由三组量决定——该位置的查询向量 $q_t$、序列中所有位置的 key 向量 $k_1,\ldots,k_t$ 与 value 向量 $v_1,\ldots,v_t$：

    $$\text{Attention}(q_t)=\mathrm{softmax}\!\left(\frac{q_t\,k_1^{\top},\ldots,q_t\,k_t^{\top}}{\sqrt{d_k}}\right)\!\cdot(v_1,\ldots,v_t).$$

    也就是说，生成第 $t$ 个 token 时，注意力必须拿到全部历史 token的 $k$ 和 $v$——一个都不能少，因为 $q_t$ 要与每一个 $k_i$ 算相似度，再用权重聚合每一个 $v_i$。

    关键观察是这些 $k_i$、$v_i$ 的来源。对第 $i$ 个 token 的输入向量 $x_i$：

    $$k_i=x_i W_K,\qquad v_i=x_i W_V,$$

    其中 $W_K$、$W_V$ 是该层的参数矩阵。$k_i$、$v_i$ 只取决于第 $i$ 个 token 自己的输入和模型参数，与"当前在算第几个查询"完全无关。生成第 4 个 token 需要 $k_1,\ldots,k_4$，但 $k_1,\ldots,k_3$ 在前几步已经算过，而且值不会变。这一观察是 KV cache 可行性的全部基础：既然历史 K/V 只依赖该 token 的输入与模型参数（其输入 $x_i$ 由前 $1\ldots i$ 个 token 逐层计算得到），就可以算一次、存下来、之后纯读取。[C3]

    不缓存的代价是平方级的。构造示例。取 4 个 token 的序列「今天 / 天气 / 很 / 好」，第 $t$ 步生成时需要算出第 $t$ 个 token 的 $k_t,v_t$（若无缓存还要重算 $k_1,\ldots,k_{t-1},v_1,\ldots,v_{t-1}$）：

    生成步 $t$需要的 K/V无缓存时需计算的 K/V（含当步新算）有缓存时新算的 K/V
    1（今天）$k_1,v_1$$k_1,v_1$$k_1,v_1$
    2（天气）$k_1,k_2,v_1,v_2$$k_1,k_2,v_1,v_2$$k_2,v_2$
    3（很）$k_1,k_2,k_3,v_1,v_2,v_3$$k_1,k_2,k_3,v_1,v_2,v_3$$k_3,v_3$
    4（好）$k_1,\ldots,k_4,v_1,\ldots,v_4$$k_1,\ldots,k_4,v_1,\ldots,v_4$$k_4,v_4$

    无缓存时四步总共算了 $1+2+3+4=10$ 组 K/V；有缓存时只算 4 组。序列长为 $n$ 时，无缓存的总计算量是 $1+2+\cdots+n=n(n+1)/2$ 组，即 $O(n^2)$ 量级；缓存后是 $n$ 组[C3]。对 20,000 token 的手册，这就是 2 亿组与 2 万组的差别——前者每步都在重算早已确定的结果。

    展开：4 token 例子的逐步 K/V 计算

    以第 3 步（token「很」）为例。模型先把「很」的输入向量 $x_3$ 分别乘 $W_K$、$W_V$ 得到 $k_3,v_3$（新算，写入缓存）。随后计算 $q_3$ 与缓存中 $k_1,k_2,k_3$ 的三个点积，经 softmax 得权重，再聚合 $v_1,v_2,v_3$。若没有缓存，$k_1,k_2,v_1,v_2$ 必须用 $x_1 W_K,x_2 W_K,x_1 W_V,x_2 W_V$ 现算——但 $x_1,x_2$ 与参数都没变，算出的值与前两步完全相同。四个 token 的例子里每组 K/V 是一个 $d_k$ 维向量；真实模型中每层每头各有一套，规模随层数与头数放大，结构与本例一致（「缓存有多大」一章给出精确换算）。

    本章问题

    1. 生成第 $t$ 个 token 时注意力需要哪些历史数据，其中哪些可以不重算？

      解答：需要全部 $k_1..k_t,v_1..v_t$，全部可不重算

      $q_t$ 要与每一个 $k_i$（$i\le t$）算点积并聚合每一个 $v_i$，因此需要全部历史的 K/V。而 $k_i=x_i W_K$、$v_i=x_i W_V$ 只由第 $i$ 个 token 的输入与参数决定，与查询无关，在第 $i$ 步算过一次后值不再变化，后续步骤直接读缓存即可。生成第 4 个 token 时需要 $k_1..k_4,v_1..v_4$，其中 3 组来自缓存，只有 $k_4,v_4$ 需要新算。

    2. 不缓存时计算量随序列长度怎么恶化？

      解答：线性步数 $\times$ 线性重算 = 平方量级

      生成 $n$ 个 token 需要 $n$ 步；无缓存时第 $t$ 步要重算 $t$ 组 K/V，总计算为 $1+2+\cdots+n=n(n+1)/2$ 组，$O(n^2)$ 量级（此为对注意力输入准备部分的推断，标注为基于注意力结构的直接推论）。缓存后每步只算 1 组新 K/V，总量 $n$ 组，历史部分变为读取。4 token 例子中即 10 组对 4 组；序列越长差距越大。

    2. prefill 与 decode——缓存产生的两个阶段

    缓存的写入与读取发生在推理的两个阶段[C2]。prefill（预填充）阶段一次性并行处理请求的全部输入 token——用户的问题、文档上下文、对话历史——算出它们在每一层的 K/V 并写入缓存，同时产出第一个输出 token。decode（解码）阶段随后逐个生成其余 token：每步只计算 1 个新 token 的 $q,k,v$，其中 $k,v$ 追加进缓存，$q$ 读取全部缓存完成注意力。

    沿用手册场景：prefill 处理 20,100 个输入 token，缓存从 0 涨到 20,100 token；decode 生成回答的每个 token 都让缓存多 1 token——回答 200 token，缓存最终 20,300 token。多轮对话时，下一轮请求的输入等于「上一轮全部输入 + 上一轮输出 + 新问题」，其前 20,300 token 的缓存恰好已经存在，这正是前缀复用的基础（见 前缀缓存）。

    两个阶段的资源特征不同，这个差别贯穿后续所有 serving 机制的分析。prefill 是一次大矩阵乘：全部输入 token 并行过模型，计算量大、每字节访存的计算量高，属于计算密集。decode 每步只处理 1 个 token：计算量很小，但注意力要读取全部缓存（$20{,}000\times 128\,\text{KB}\approx 2.44\,\text{GB}$），属于访存密集。因此优化 prefill 与 decode 的手段不同，部署形态上也衍生出把它们分开调度的方案。

    本章问题

    1. prefill 与 decode 各自怎么操作 KV cache？

      解答：prefill 批量写入，decode 每步追加

      prefill 一次性并行处理全部输入 token（用户问题与上下文），算出它们在每层的 K/V 全部写入缓存，并产出第一个输出 token；decode 逐 token 生成，每步只算当前新 token 的 $q,k,v$，把 $k,v$ 追加进缓存，用 $q$ 读全部缓存计算注意力输出。手册场景：prefill 后缓存 20,100 token，decode 每生成一个 token 缓存加 1。

    2. 为什么说两阶段"计算密集"与"访存密集"不同？

      解答：prefill 大并行矩阵乘，decode 小步读全量缓存

      prefill 把 20,100 个 token 并行送入模型，是大型矩阵乘，计算量与输入长度成正比且高度并行，瓶颈在算力。decode 每步只算 1 个 token 的 q/k/v（计算量极小），但注意力必须读取全部 2.44 GB 缓存，瓶颈在显存带宽。资源特征不同意味着两阶段的优化手段与部署考量不同（例如后续机制按阶段区分调度），本文不展开部署形态。

    3. 缓存有多大——每 token 字节数公式

    第 1 章的 4 token 例子只看依赖关系，没看尺寸。真实模型中，每个 token 在每一层都有自己的一套 K/V（注意力逐层进行，每层的 $W_K,W_V$ 不同），每层内的 K/V 又按注意力头分组。因此每 token 的 KV cache 字节数为：

    $$\text{每 token 字节数}=2\cdot L_{\text{layers}}\cdot H_{\text{kv}}\cdot d_{\text{head}}\cdot b.$$[F1]
    • $2$：K 与 V 各一份；
    • $L_{\text{layers}}$：Transformer 层数，每层各存一套；
    • $H_{\text{kv}}$：KV 头（组）数——每个注意力头的 $q$ 都要与各 KV 头的 $k,v$ 交互；
    • $d_{\text{head}}$：每个头的向量维度；
    • $b$：每个元素的存储字节数，bf16/FP16 为 2，FP8 为 1。

    本页 KB/GB 按存储行业惯例换算：$1\,\text{KB}=1{,}024$ 字节、$1\,\text{GB}=2^{30}$ 字节。按此口径 128 KB/token 下，20,000 token 手册约 2.44 GB，128K 窗口单请求恰为 16 GB。

    $H_{\text{kv}}$ 的取值区分两种注意力结构。MHA（多头注意力）中 KV 头数等于查询头数，$H_{\text{kv}}=H_q$；GQA（分组查询注意力）中多组查询头共享一组 KV 头，$H_{\text{kv}}<H_q$——KV cache 直接缩小为 MHA 的 $H_{\text{kv}}/H_q$。多数现代开源模型（Llama 3、Qwen2.5 等）采用 GQA 省下的正是这份显存。

    两个算例对照。构造示例。Llama-3.1-8B（GQA）：32 层、$H_{\text{kv}}=8$、$d_{\text{head}}=128$、bf16（bfloat16，每元素 2 字节）[N2]，代入公式 $2\times 32\times 8\times 128\times 2=131{,}072$ 字节 = 128 KB/token。20,000 token 的手册共 $20{,}000\times 131{,}072\,\text{B}\approx 2.44\,\text{GB}$。文献算例。OPT-13B（MHA）：40 层、隐藏维 5120（即 $H_{\text{kv}}\cdot d_{\text{head}}=5120$）、FP16，得 $2\times 5120\times 40\times 2=800$ KB/token[N1]，单请求最长（2048 token）达 1.6 GB——这是 vLLM 论文给出的原始数字。GQA 的效果直接可见：Llama-3.1-8B 的 $H_{\text{kv}}/H_q=8/32=1/4$，若它是 MHA 结构，每 token 将是 512 KB。

    展开：128 KB/token 的完整代入与两个检查

    代入链：$2\ (\text{K 与 V})\times 32\ (\text{层})\times 8\ (\text{KV 头})\times 128\ (\text{每头维度})\times 2\ (\text{bf16 字节})=131{,}072$ 字节，除以 $1024^2$ 得 0.125 MB 即 128 KB。检查一（线性性）：token 数翻倍则总量翻倍——40,000 token 手册即约 4.88 GB（$2.44\times 2$），说明"上下文越长缓存越大"是线性关系而非别的曲线。检查二（GQA 比例）：把 $H_{\text{kv}}$ 从 8 换成 32（MHA），公式其余不变，结果变为 512 KB/token，恰为 4 倍——KV cache 缩小比例就是 KV 头数比例。128K 上下文窗口的单请求缓存即 $131{,}072\times 128\,\text{KB}=16\,\text{GB}$[N5]。

    本章问题

    1. Llama-3.1-8B 每个 token 的 KV cache 是多少字节？20,000 token 的手册呢？

      解答：128 KB/token，手册约 2.44 GB

      按公式 $2\cdot L\cdot H_{\text{kv}}\cdot d_{\text{head}}\cdot b$，Llama-3.1-8B 的参数为 32 层、8 个 KV 头（GQA，查询头 32 个）、每头维度 128、bf16 每元素 2 字节：$2\times 32\times 8\times 128\times 2=131{,}072$ 字节 = 128 KB/token。20,000 token 手册共 $20{,}000\times 131{,}072\,\text{B}\approx 2.44\,\text{GB}$。成立条件：标准 GQA 注意力结构、bf16 存储、无 KV 量化。

    2. GQA 如何改变缓存大小？

      解答：KV 头数直接进入公式，缩小比例 = 头数比

      GQA 把查询头分成 $H_{\text{kv}}$ 组、每组共享同一个 KV 头，公式中 $H_{\text{kv}}$ 相应变小。Llama-3.1-8B 的 $H_{\text{kv}}=8$ 而查询头 $H_q=32$，KV cache 是同结构 MHA 的 $1/4$（128 KB 对 512 KB）。OPT-13B 是 MHA（$H_{\text{kv}}\cdot d_{\text{head}}=d_{\text{hidden}}=5120$），故 800 KB/token。GQA 改变的是存储与 KV 侧计算，注意力的查询侧仍按 32 头进行。

    4. 为什么显存成为瓶颈——动态缓存与权重的争夺

    单看 128 KB/token 似乎不大，瓶颈来自三个因素的相乘。第一，缓存随 token 数线性增长：20,000 token 手册约 2.44 GB，128K 窗口单请求就要 16 GB[N5]。第二，并发请求数相乘：10 个客服同时各自带一份不同文档，就是 10 份 2.44 GB。第三，KV cache 与模型权重共用同一块显存，此消彼长：13B 参数模型在 40GB A100 上，约 65% 显存是静态权重，留给 KV cache 的只有近 30%[C4, N3]。

    量级判断：40 GB HBM（GPU 高带宽显存）对 Llama-3.1-8B 大约只够缓存 0.3M token[N4]——按每 token 128 KB 换算 $40\times 2^{30}\,\text{B}/131{,}072\,\text{B}\approx 0.33\text{M}$，与 Strata 论文的"约 0.3M"口径一致。0.3M token 听起来多，但一份手册就 0.02M，几十份文档或几百轮对话就会耗尽，而生产服务往往同时服务成百上千个会话。OPT-13B 时代单请求最长 1.6 GB 已被视为"大"（vLLM 论文原话）[N1]，上下文窗口扩张到 128K–1M 后，单请求缓存就到了 16–128 GB 量级。

    三处常见误解需要在此澄清。其一，KV cache 不是模型自带的固定组件：它是每个请求动态产生的中间数据，系统消耗多少显存放缓存取决于负载（并发 $\times$ 上下文长度），部署时的"显存规划"规划的就是权重与缓存份额的切分。其二，上下文窗口 128K 是模型可接受的长度上限，不是显存保证：128K token 需要 16 GB 缓存，与"放不放得下"无关。其三，缓存只省计算、不省存储——显存不够时系统只有两条路：逐出（丢掉缓存、下次重算）或分层（把不常用的缓存搬到 CPU 内存或 SSD，用时再搬回）。既有系统在请求完成即丢弃缓存[C5]，这让后续请求无法复用，也引出了两个后续问题：如何在显存内高效组织这些页（见 PagedAttention 分页管理），以及哪些前缀值得跨请求留着复用（见 前缀缓存）。当缓存分层后，"搬回 GPU 的速度"会成为新的瓶颈——那是 Strata 一文要解决的问题。

    本章问题

    1. 为什么说 KV cache 会"挤爆"显存？三个因素是什么？

      解答：线性增长 $\times$ 并发数 $\times$ 与权重共用显存

      第一，缓存随 token 数线性增长：128 KB/token 下 20,000 token 手册约 2.44 GB、128K 窗口单请求 16 GB。第二，并发请求各自持有独立上下文的缓存，总量相乘。第三，显存里静态权重先占大头（13B 模型在 40GB A100 上约 65%），KV cache 只能争夺剩余份额（近 30%）。三因素叠加的结果：40 GB HBM 只够 Llama-3.1-8B 缓存约 0.3M token，几十份长文档即耗尽。

    2. "上下文窗口 128K"和"显存放得下 128K"是一回事吗？

      解答：不是，窗口是长度上限，容量由显存决定

      128K 是模型结构（位置编码等）允许的最大输入长度；128K token 的 KV cache 在 Llama-3.1-8B 下需要 16 GB，是否放得下由显存大小、权重占用与其他并发请求共同决定。显存不足时系统只能逐出缓存或分层存储，与模型"支持"多长窗口无关。

    3. 缓存了 KV cache 之后，显存问题解决了吗？

      解答：没有，缓存只省计算不省存储

      KV cache 消除的是重复计算（把 $O(n^2)$ 量级的重算变成读取），但每 token 128 KB 的存储一点没省。显存不够时只有两条路：逐出（丢缓存、下次命中不了就重算）或分层（搬到 CPU 内存/SSD、用时搬回）。这两种方案的机制分别是后续页面（分页管理、前缀缓存）与 Strata 一文（分层传输）的主题。

    来源与范围说明

    核心论断与来源

    C1/C3（KV cache 定义与 K/V 来源）：Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention", SOSP 2023（arXiv:2309.06180）§1；C2（两阶段）：Xie et al., "Strata", OSDI 2026（arXiv:2508.18572v2）§2.1；C4（显存分布）、C5（完成后丢弃缓存，SGLang §1/§3、vLLM §4.2）：vLLM 论文 §1 与 SGLang 论文（Zheng et al., NeurIPS 2024, arXiv:2312.07104）§3.2。"K/V 与查询无关"（C3 标注推断）由注意力公式结构直接得出：$k_i=x_i W_K$ 只依赖第 $i$ 个 token 的输入与参数。$O(n^2)$ 重算量标注为推断（自回归结构直接推论）。

    核心公式与来源

    F1（每 token 字节数 $2\cdot L_{\text{layers}}\cdot H_{\text{kv}}\cdot d_{\text{head}}\cdot b$）：MHA 形式与 vLLM 论文 §3 的 OPT-13B 算式（$2\times 5120\times 40\times 2=800$ KB）一致；GQA 推广形式（用 $H_{\text{kv}}\cdot d_{\text{head}}$ 替代 $d_{\text{hidden}}$）为对多头结构的直接推广，标注推断，经 Llama-3.1-8B 算例复算验证。

    外部数字与实验条件

    N1（OPT-13B 800 KB/token、单请求 1.6 GB）：vLLM 论文 §3。N2（Llama-3.1-8B 配置 32 层/8 KV 头/head_dim 128/128K 窗口/bf16）：HuggingFace 模型配置（meta-llama/Llama-3.1-8B-Instruct config.json）。N3（65%/30% 显存分布）：vLLM 论文 §1 Figure 1（13B 模型、A100 40GB）。N4（40GB $\approx$ 0.3M token）：Strata 论文 §1（Llama-8B 口径，与本页 F1 复算一致）。N5（128K $\to$ 16 GB）：F1$\times$N2 推算。

    构造示例

    「今天/天气/很/好」4 token 序列（第 1、2 章）：展示每步新算与复用的 K/V 组数，便于手算，不代表真实负载。20,000 token 手册（第 2–4 章）：规模算例，数字为构造选择（与长上下文评测负载的平均规模同量级，见 Strata 一文实验部分），计算本身可复算。

    辅助解释与类比边界

    本文未使用类比解释机制；"纯读取"表述指不再执行矩阵乘、只访存，不暗示读取零成本（decode 每步读全部缓存正是访存瓶颈的来源，见第 2 章）。

    简化条件及其限制

    其一，公式假设标准 MHA/GQA 注意力与逐层独立 K/V；sliding window、层内稀疏注意力或 MLA（latent 压缩）等结构不适用，本文未覆盖。其二，$b$ 按存储精度取值（bf16/FP16=2、FP8=1），KV 量化只改 $b$ 不改公式结构，量化方法本身未展开。其三，示例忽略 batching 对显存占用的次要影响（激活值），不影响量级结论。其四，GQA 只给最小定义（多组查询头共享一组 KV 头），其训练动机与收敛性影响不在本文范围。
