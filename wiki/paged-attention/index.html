    PagedAttention（分页注意力）：把 KV cache 切成页，消掉显存浪费

    主要依据：Kwon et al., "Efficient Memory Management for Large Language Model Serving with PagedAttention"（SOSP 2023, arXiv:2309.06180）§1–§4；页大小取值与传输后果另引 Xie et al., "Strata"（OSDI 2026, arXiv:2508.18572v2）§2.2、§3.1。

    KV cache 动态增长、与权重争夺显存（见 KV cache），那么显存按什么规则分给各个请求？vLLM 之前的做法：每个请求到达时，按其最大可能长度一次性预留一段连续显存。一个上限 2048 token 的请求只实际用到 100 token，其余 1948 个槽位从头到尾空着；更糟的是这些大小不一的空洞彼此错开，新的请求反而放不进去。vLLM 的答案借自操作系统：把 KV cache 切成固定大小的页，页放在哪里都行，用一张页表记住顺序。本文讲清三件事：连续预留到底浪费在哪、分页怎么把这些浪费消掉、以及分页为显存效率付出的代价——跨内存层搬运时的小传输问题。

    核心问题

    1. 连续预留为什么浪费？三类浪费各是什么，实测有多大？

      解答：预留、内部碎片、外部碎片，有效利用仅两到四成

      按最大长度预分配连续显存产生三类浪费：为未来 token 保留的预留槽、实际长度小于最大长度造成的内部碎片、大小不一的预留块之间分配器切出的外部碎片。vLLM 实测既有系统只有 20.4%–38.2% 的 KV cache 显存真正存了 token 状态，其余全部浪费；浪费直接压低可并发的批大小。见「连续预留的三类浪费」一章。

    2. 分页机制怎么做？块、块表、按需分配如何消掉这些浪费？

      解答：固定大小页 + 页表映射 + 按需分配

      KV cache 切成固定 token 数的页，逻辑上序列顺序连续、物理上页放在显存任意空闲位置，页表记录逻辑页号到物理页号的映射，注意力 kernel 按页表取数。token 写满当前页才申请新页（按需分配），内部碎片被压到每请求最后一页；所有页同大小，任何空闲页都能用，外部碎片消失。注意力的数学计算不变，变的只是存储布局。见「分页机制」一章。

    3. 为显存设计的分页在什么场景下变成缺点？

      解答：跨内存层搬运时的小传输

      服务显存效率的页很小（TensorRT-LLM 32、vLLM 16、SGLang 1 token），一个序列的 KV cache 因此散布在大量互不相邻的页中。GPU 内计算无碍（kernel 按页表逐页取），但把缓存从 CPU 内存搬回 GPU 时每次只能按页传，KB 级小传输打不满 PCIe 带宽（实测 8192 token 加载仅约 22% 利用率）。另注意分页提高利用率但不增加容量。见「页间不连续」一章。

    4. 页大小怎么选？为什么没有普适最优？

      解答：显存效率与缓存粒度对传输效率与管理开销的权衡

      小页内部碎片小、按页匹配的前缀缓存粒度细（命中率高）；大页页表短、间接寻址开销低、跨层传输单位大。三个引擎默认值不同（32/16/1）本身就是权衡的证据。页大小是部署时要选的旋钮，没有普适最优；Strata 的 GPU-assisted I/O 让传输效率对页大小不再敏感，从而免去这个调参。见「页大小怎么选」一章。

    1. 连续预留的三类浪费

    分页之前的主流方案是连续预分配：请求到达时，按其最大可能序列长度（如 2048 token）一次性划出一段连续显存存放它的 KV cache[C1]。这个方案的问题按浪费类型分三类：

    • 预留槽（reserved slots）：为该请求未来将生成的 token 保留的位置。请求进行中这些槽必然存在，但生成结束前大部分时间空着。
    • 内部碎片（internal fragmentation）：按最大长度分配、按实际长度使用，两者之差是请求内部永远用不到的部分。实际长度只有生成结束才知道，但分配在开始就得做。
    • 外部碎片（external fragmentation）：不同请求预留的段大小不一，请求结束后释放的空洞尺寸各异，分配器（如 buddy allocator）拼不出新的连续段，总显存够、连续段不够。

    构造示例。请求 A 上限 2048 token、实际生成到第 100 token 结束；请求 B 上限 512 token、实际用到 500。连续预留下：A 实际获得 2048 槽、用了 100，浪费 1948 槽（生成结束后才确认是内部碎片；进行中主体是预留槽）；B 获得 512 槽、用 500，浪费 12 槽。A 结束后释放一段 2048 槽的连续空间——如果下一个请求上限是 3000，这段放不下，碎片出现。更重要的是总量：A+B 占了 2560 槽，真实数据只有 600 槽。

    这不是构造出来的极端例子。vLLM 论文对既有系统的 profiling 显示，KV cache 显存中只有 20.4%–38.2% 真正存了 token 状态，其余是预留、内部碎片、外部碎片等浪费（论文图例为 External frag. & Others，含少量未归类项）[C2, N1]。浪费的后果不是"显存难看"，而是直接限制并发：显存能放下的请求数就是批大小的上限，浪费六到八成显存等于把可服务的并发砍掉同样的比例。

    本章问题

    1. 三类浪费各自的产生机制是什么？

      解答：预留看未来、内部看差值、外部看空洞

      预留槽：按最大长度分配后为未来 token 保留的位置，请求进行中必然存在。内部碎片：分配按最大长度、使用按实际长度，差值在生成结束后确认为纯浪费。外部碎片：各请求预留段大小不一，释放后的空洞尺寸不齐，分配器拼不出新的连续段——总显存足够时新请求仍可能放不进。三者都源于"连续 + 按最大长度预分配"这一个决定。

    2. 浪费的实际规模和对服务的直接影响是什么？

      解答：有效利用仅 20.4%–38.2%，直接压低并发批大小

      vLLM 论文实测既有系统 KV cache 显存的有效利用率只有 20.4%–38.2%（即六到八成浪费）。显存能容纳的请求数就是批大小上限，浪费显存等于等比例减少可并发服务的请求数，吞吐与延迟随之受损。A/B 构造示例中 2560 槽只装了 600 槽的真实数据，有效利用率约 23%，正落在实测区间的低端。

    2. 分页机制——块、页表与按需分配

    操作系统遇到过同样的问题，答案是把物理内存切成固定大小的页、用页表把进程的连续虚拟地址映射到任意物理页。vLLM 把这套思想搬到 KV cache 上[C3]，论文给的对应关系是：页（block）对应 OS 的页，token 对应字节，请求对应进程。具体机制：

    • 固定大小页：每个页存放固定数量 token 的 K/V（页大小以 token 数计，见第 4 章）。
    • 逻辑连续、物理任意：序列中第 $i$ 个逻辑页可以放在显存任何空闲物理页上，页与页不必相邻。
    • 页表（block table）：每个请求一张表，记录它的逻辑页号到物理页号的映射；注意力 kernel 沿页表逐页取数，对上层而言序列仍是连续的。
    • 按需分配：token 写满当前页才申请新页[C5]——A 请求实际只用 100 token，页大小 16 时只占 7 页。

    三类浪费逐一对照：按需分配消掉了预留槽（未来 token 的页还没发生就不占）；内部碎片只剩最后一页的空余部分——每请求至多浪费一页[C6]，页大小 16 时 A 只浪费 12 个槽（对照连续预留的 1948）；所有页同大小，任何空闲页都能装任何逻辑页，外部碎片随之消失[C4]。附带收益是页级共享：两个序列若共享某段前缀，可以让它们的页表指向同一物理页——这是跨请求复用 KV cache 的实现基础，机制见 前缀缓存。

    需要澄清一个容易误解的点：PagedAttention 没有改变注意力的数学。缩放点积、softmax、加权求值一步不少，变的是 KV cache 的存储布局，以及 kernel 按页表在非连续页上取数的方式。"PagedAttention 是新注意力算法"的说法容易让人去找公式上的创新，实际创新全在内存管理。

    展开：A/B 例子在页 16 下的完整账目

    构造示例。页大小取 16 token。$\lceil\cdot\rceil$ 为向上取整（不足一页按一页计）。请求 A（实际 100 token）：需要 $\lceil 100/16\rceil=7$ 页 = 112 槽，内部碎片 $112-100=12$ 槽；请求 B（实际 500 token）：$\lceil 500/16\rceil=32$ 页 = 512 槽，碎片 12 槽。两请求合计占 624 槽，真实数据 600 槽，有效利用率 $600/624\approx 96\%$——对照连续预留的约 23%。外部碎片为零：A 结束释放的 7 页可以被任何后续请求的任何逻辑页使用。若 A 的生成还没结束（当前写到第 100 token），已分配仍是 7 页，没有为"可能写满 2048"预留任何东西——预留槽在按需分配下不存在。

    本章问题

    1. 页表怎么让"物理不连续"对注意力计算透明？

      解答：逻辑页号查表得物理页号，kernel 逐页取数

      每个请求的 KV cache 在逻辑上仍是连续序列（token 0..n），但被切成固定大小的页，页表记录每个逻辑页放在哪个物理页。注意力 kernel 计算 $q$ 与全部历史 K/V 的交互时，沿页表把各物理页的 K/V 逐页取出使用——取数多了一步查表，序列的逻辑顺序与注意力的数学完全不变。生成新 token 时若当前页未满直接写入，满了才查空闲池分配新物理页并追加页表行。

    2. 分页后三类浪费各剩多少？

      解答：预留槽清零、外部碎片清零、内部碎片每请求至多一页

      按需分配下未来 token 不占任何空间，预留槽消失。所有页同大小，任何空闲物理页可用于任何逻辑页，外部碎片消失。内部碎片只剩每请求最后一页的空余：实际 token 数未必是页大小整数倍，最后一页平均浪费半页（推断：均匀假设下的期望；论文口径为"至多一页"）。页大小 16 的 A/B 例子中总利用率约 96%，对照连续预留的 23%。

    3. 页间不连续——为显存设计，被传输惩罚

    分页为显存效率选择的页很小。三个引擎的取值：TensorRT-LLM 32 token、vLLM 16 token、SGLang 1 token；每 token 的 KV cache 从几十 KB 到几 MB[C7, N2]。小页服务两个显存侧目标：内部碎片与预留浪费小（利用率高）、按页匹配的前缀缓存粒度细（第 4 章）。

    但同一设计在另一个场景下变成负担。把 20,000 token 手册的缓存从 CPU 内存搬回 GPU 时（显存放不下、分层存储的常规操作，见 KV cache 第 4 章），按页大小 32 切分：手册占 625 页，每页 $32\times 128\,\text{KB}=4\,\text{MB}$（Llama-3.1-8B 口径）[N3]。这 625 页在 CPU 内存里互不相邻，传输只能逐页发起——4 MB 一次、发 625 次。页与页之间的不连续让"整份手册"永远无法作为一次连续大传输搬运[C8]。实测：8192 token（页 32）从 CPU 加载到 GPU 只达到 PCIe 5.0 理论带宽的约 22%；互联带宽更高的平台（如 NVLink 替代 PCIe 的 GH200）上利用率反而跌到约 5%[N4]。

    两个维度需要分开看：不连续性来自布局（页散布在内存各处），传输单元来自页大小（每次传一页）。增大页能扩大传输单元，但会同时放大内部碎片、并让按页匹配的前缀缓存粒度变粗——这正是第 4 章的权衡。另有一个边界必须澄清：分页提高的是显存利用率，不是容量。40 GB 显存的利用率从 30% 提到 96%，可用缓存约为原来的 3.2 倍，但 20,000 token 手册的缓存仍是约 2.44 GB；装不下的部分照样要逐出（丢缓存重算）或分层（搬到 CPU/SSD、用时搬回）。分层之后的"搬回速度"问题——小页传输打不满带宽——正是 Strata 一文的出发点。

    补充：页大小上限与可配置性

    vLLM 在 CUDA GPU 上的页大小上限是 32 token（Strata 论文 §3.1 引 vLLM 文档口径）[C7]；页大小是引擎的部署配置项，三个引擎的默认值不同即证明它是可调的。Strata 论文的分层缓存基线统一取页 32，是"先前分层 KV cache 工作的推荐值"（MemServe、CachedAttention、FlashGen、Pensieve）并恰为 vLLM 的上限值；Strata 自身与 SGLang 基线用默认页 1（§5.1）。页大小对传输效率与缓存命中率的双向影响在第 4 章与 前缀缓存第 4 章展开。

    本章问题

    1. 为什么页间不连续会拖慢跨内存层的搬运？

      解答：传输只能按页发起，小传输打不满带宽

      一个序列的各页在内存中互不相邻，搬运时只能逐页发起传输。页大小 32、Llama-3.1-8B 下每页仅 4 MB，20,000 token 手册要发起 625 次独立传输；带宽利用率受单次传输大小限制（大传输才能打满 PCIe，机理与数字见 Strata 一文），实测 8192 token 加载只达理论带宽约 22%，高带宽平台（GH200）上低至约 5%。GPU 内部计算不受影响——kernel 本来就按页表逐页取数。

    2. 分页解决了显存容量问题吗？

      解答：没有，解决的是利用率

      分页把 KV cache 显存的有效利用率从两三成提到接近全量（消掉预留、外部碎片、大部分内部碎片），相当于同样的显存能服务多得多的并发。但每 token 128 KB 的存储需求一点没变：装不下的缓存仍然要逐出（重算）或分层（搬到 CPU/SSD）。分层是容量的解法，分页是利用率的解法，两者解决的问题不同。

    4. 页大小怎么选——一个没有免费午餐的旋钮

    页大小同时压在四个目标上，且方向不一致：

    维度页小（如 1–32 token）页大（如 256–1024 token）
    内部碎片与预留浪费小（至多一页；平均约半页为推断）浪费大（平均半页的绝对值随页大小放大）
    前缀缓存命中粒度细：共享前缀几乎全部命中粗：非整页的共享尾部全部落空（见 前缀缓存）
    页表与寻址开销页表长、间接寻址多页表短、开销低
    跨层传输单元KB–MB 级小传输，打不满带宽单次传输大，带宽利用率高

    三个引擎的默认值——TensorRT-LLM 32、vLLM 16、SGLang 1[N2]——本身就说明这是一个工程权衡而非算法结论（各引擎的具体动机论文未记载；从取值推断，SGLang 取 1 可能为了前缀匹配粒度最细，TensorRT-LLM 取 32 可能兼顾传输单元——此为推断，非来源结论）。部署者面对长上下文分层缓存时，页大小是要试的旋钮：调大缓解传输、调小保命中率。Strata 的 GPU-assisted I/O 之所以值得单独讲，正因为它把第四行（传输单元）从权衡中摘了出去——传输效率不再依赖页大小，页大小可以回到"只为显存效率与缓存粒度而选"（该文 §5.3.2 的页大小扫描实验显示：基线系统把页调到最优值 512 仍只有 Strata-IO 93% 的吞吐，命中率低 2.4%）[N5]。

    本章问题

    1. 页大小影响哪四个目标？方向为什么不一致？

      解答：碎片、缓存粒度、管理开销、传输单元四向拉扯

      小页让内部碎片与预留浪费小、让按页匹配的前缀缓存粒度细（命中率高），但页表变长、间接寻址开销变大，且跨内存层传输单元小、打不满带宽；大页恰好全部反过来。四个目标没有同向的解，页大小只能在具体负载下调权。三个引擎默认值 32/16/1 的差异即权衡证据。

    2. 有没有办法让"传输效率"退出这个权衡？

      解答：有，Strata 的 GPU-assisted I/O

      Strata 用 GPU kernel（而非 DMA 拷贝 API）搬数据，高效传输粒度低至 128 字节（Strata §4.2），小页传输也能保持高 I/O 效率（原文口径 "consistently high I/O efficiency"），传输效率因此不再依赖页大小——页大小回到只为显存效率与缓存粒度而选的状态。其页大小扫描实验（§5.3.2）显示：基线系统把页调到自身最优值 512，吞吐仍只有 Strata-IO 的 93%（命中率低 2.4%），说明摘掉传输约束后小页方案整体占优。机制见 Strata 一文。

    外部数字与实验条件

    辅助解释与类比边界

    OS 分页类比（块-页、token-字节、请求-进程）为 vLLM 论文原文类比，仅帮助建立直觉；KV cache 页与 OS 页在"固定大小、页表映射、按需分配"三点上对应，在淘汰算法、页错误处理、硬件支持上均不对应，不展开。

    简化条件及其限制

    其一，账目计算只算 KV cache 部分的显存（不含权重与激活），与 vLLM 论文口径一致。其二，"平均半页"内部碎片为均匀假设下的推断，实际负载的长度分布会偏离。其三，页级共享只给结论（可行性与粒度），匹配、逐出与命中机制归前缀缓存一文。其四，注意力 kernel 在非连续页上的实现（如分块取数与融合）未展开，不影响本页目标。
