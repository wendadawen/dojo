    多模态图片的两阶段处理

    前端 render 链路用 HF image_processor 完成图片加载与 smart_resize，产出 pixel_values 与 image_grid_thw 随请求发送；EngineCore 的 _execute_mm_encoder 调用 embed_multimodal 跑视觉编码器，结果按图片哈希缓存在 encoder_cache 供 decode 复用。合批时字段类型决定合并方式，拆批仅由 modality、字段集合与 SharedField 数据决定。

    更新于 2026-08-21 · 类型：源码走读结论（vLLM 0.22.2.dev，Qwen3.5，TP=1）

    1. 分界在哪里：两段各自做什么

    一张图片从进入 vLLM 到产生图像特征，被拆成两段，分属两个进程：

    阶段进程做的事产出
    预处理 APIServer 加载图片、smart_resize、归一化（纯 CPU） MultiModalKwargsItem：pixel_values + image_grid_thw，附带哈希与占位符位置
    视觉编码 EngineCore 跑视觉编码器 ViT 的 forward（GPU） 图像特征 embedding，按 mm_hash 缓存

    这一分界与源码位置一致：预处理函数（fetch_image、multimodal/processing/processor.py 的 apply、renderers/ 中的调用）都位于 APIServer 侧的 render 链路，不含视觉编码器的 forward；视觉编码函数（_execute_mm_encoder、_process_image_input、embed_multimodal）都位于 gpu_model_runner 与模型类中，运行在 EngineCore 进程。APIServer 内部把图片文件的加载 IO（load_file、rgba_to_rgb）与多模态处理（HF processor 调用）放在不同线程上、与主线程的请求接发并行——这一线程划分为按代码结构的推断，未经运行期验证。

    2. 前端段：HTTP 请求到 pixel_values

    请求进入 OpenAI 入口后，图片沿一条链路被处理：render_chat_request（chat completion serving）→ render_messages_async（HfRenderer）→ parse_chat_messages_async 识别消息中的图片并经连接器的 fetch_image_async 加载 → _process_multimodal → mm_processor.apply → _apply_hf_processor_mm_only → call_hf_processor → 最终由 HF 的 image_processor 完成 resize 与归一化。产出的 MultiModalKwargsItem 含两个字段：pixel_values（归一化后的像素张量）与 image_grid_thw（分块网格），随请求一同序列化发送。

    image_grid_thw 由 HF image processor 基于 smart_resize 的输出计算：smart_resize 把图片高宽各自取整到 factor=32 的倍数（factor = patch_size(16) × merge_size(2)，是 patch 切分与合并的取整粒度）、总像素限制在 min/max 范围内、尽量保持宽高比。缩放后的高宽再除以 patch_size（Qwen3.5 为 16）即得网格数，网格的分块数即 patch 数。Qwen3.5 沿用 Qwen2-VL 的 image processor 类，但该模型配置为 patch_size=16、merge_size=2，min_pixels=65536、max_pixels=16777216。两个实例：980×986 的图片被缩放到 992×992，切为 grid [1, 62, 62]（62 = 992 ÷ 16，共 3844 个 patch）；480×640 的图片本就满足整除与像素范围，切为 grid [1, 30, 40]（1200 个 patch）。视觉 token 数再由 patch 数按 merge_size²=4 合并得到——前者 961、后者 300，即图片的 token 占位数量。

    3. 后端段：_execute_mm_encoder 的视觉编码

    收集

    调度器产出的 SchedulerOutput.scheduled_encoder_inputs 记录本步需要编码的项，结构为 {请求ID: 图片下标列表}。存下标而不存数据：数据可能已在编码缓存中或可从远端获取，调度器只决定"哪些项需要编码"。_batch_mm_inputs_from_scheduler 按下标从各请求的 mm_features 取出数据，整理为三个平行列表：图片哈希、图片数据、以及 (请求ID, 占位符位置) 引用——后者用于把图片映射回所属请求，从而查到该请求使用的 LoRA 适配器。占位符位置即 PlaceholderRange（offset + length），标记图片在 token 序列中的插入点。

    合批机制

    group_and_batch_mm_kwargs 把收集到的项组织成一批批可整体送入编码器的数据。机制分两层：怎么合并与什么时候拆批。

    每个字段（FieldElem）携带一个 field 对象，决定合批时数据的合并方式（reduce_data）：

    字段类型合并方式语义
    MultiModalBatchedField各 item 数据形状相同 → torch.stack 成一个张量；形状不同 → 以列表返回每个 item 拥有独立的一份张量（如 pixel_values）
    MultiModalSharedField取第一个 item 的数据（batch[0]）同一份数据复制给 batch 内所有 item（如跨 patch 共享的配置），合并时留一份即可

    拆批判定由每项的 group id 决定：把 item 的所有字段按名排序，每个字段记为 (字段名, 哈希)，其中只有 SharedField 字段参与哈希计算，BatchedField 字段哈希恒为空。相邻项的 group id 相同才落入同批。因此拆批当且仅当三种情况：modality 不同（外层按 modality 分组）；字段名集合不同（group id 的键不一致）；SharedField 字段的数据不同（哈希不一致）。BatchedField 的数据——包括图片大小、网格形状——完全不参与拆批判定：形状不同的图片留在同一批，只是合并时 pixel_values 退化为列表而非堆叠成张量。社区的单元测试（tests/multimodal/test_utils.py 的 test_group_and_batch_mm_items_split_by_fieldset 与 test_group_and_batch_mm_items_split_by_shared_data）覆盖了后两种拆批条件：字段集合不同拆批、SharedField 值不同拆批。

    编码

    每批数据以关键字参数展开传入 model.embed_multimodal，其内部对 image modality 调 _process_image_input 跑视觉编码器 forward，产出每个图片项的特征张量。这些特征张量随后沿统一输入路径并入模型输入：整个 batch 的全部 token 先过 embedding 层，图片位置再以 is_multimodal 掩码被覆写为 ViT 特征（多模态统一输入与 cudagraph）。调用处把模型对象当作 SupportsMultiModal 协议使用——协议只要求对象具有这些多模态方法，不依赖具体模型类，实现该组方法的模型即可复用同一编码调用路径（本页以 Qwen3.5 走读验证）。

    缓存

    编码结果按图片哈希写入 encoder_cache。视觉编码只在图片首次被调度的 prefill 回合执行；decode 回合需要图片特征时直接读缓存（_gather_mm_embeddings 按 PlaceholderRange 取对应片段），不再跑 ViT。同一图片被多个请求使用时也命中同一缓存条目。

    4. 为什么这样分

    预处理是纯 CPU 工作——图片解码、缩放、归一化，放在 APIServer 可以用独立线程做，不占用引擎进程；视觉编码需要 GPU 与模型权重，必须靠近模型所在进程，且编码结果要立即进入缓存供后续回合使用。把重活留在离 GPU 最近的 EngineCore、轻活留在离请求最近的 APIServer，是这条分界线的一种解读：依据是上述两段的功能分布（CPU 预处理 / GPU 编码），属推断，官方设计文档未直接陈述该动机。这条分界线对应的进程职责划分见V1 两进程架构。

    来源与范围说明

    源码定位

    • 前端链路：vllm/entrypoints/chat_utils.py（parse_chat_messages_async；经连接器 fetch_image_async 加载图片）、vllm/renderers/hf.py（render_messages_async）、vllm/renderers/base.py（_process_multimodal）、vllm/multimodal/processing/processor.py（apply；_apply_hf_processor_mm_only）、vllm/multimodal/processing/context.py（call_hf_processor）、vllm/multimodal/media/connector.py（fetch_image / fetch_image_async）
    • smart_resize：transformers/models/qwen2_vl/image_processing_qwen2_vl.py（smart_resize 定义在第 54 行，其 factor 入参默认 28；Qwen3.5 沿用该 image processor 类，但按模型配置 patch_size=16、merge_size=2，实际取整因子 factor=32）
    • 后端链路：vllm/v1/worker/gpu_model_runner.py（_preprocess；_execute_mm_encoder；_batch_mm_inputs_from_scheduler；_gather_mm_embeddings；encoder_cache 写入）
    • 合批机制：vllm/multimodal/utils.py（_get_group_hash；_batch_mm_items；group_and_batch_mm_items；group_and_batch_mm_kwargs）、vllm/multimodal/inputs.py（MultiModalBatchedField；MultiModalSharedField）
    • 编码：vllm/model_executor/models/qwen3_vl.py（embed_multimodal；_process_image_input）
    • 占位符：vllm/multimodal/inputs.py（PlaceholderRange）

    验证数据

    • smart_resize 数值：用 Qwen3.5 所用 HF image processor 的配置（patch_size=16、merge_size=2、min_pixels=65536、max_pixels=16777216；transformers 4.57.6）对 980×986 与 480×640 两张图片实跑，网格分别为 [1, 62, 62]（3844 个 patch）与 [1, 30, 40]（1200 个 patch）
    • 合批行为：按真实 processor 输出的字段构造输入，对 group_and_batch_mm_kwargs 运行——两张网格不同的图片合为一批（pixel_values 以列表返回）、图片与音频拆为两批、字段集合不同的两张图拆为两批；后两种拆批条件另有社区单元测试覆盖
    • 进程归属：预处理函数位于 APIServer 侧 render 链路、编码函数位于 EngineCore 的 gpu_model_runner 与模型类，均由源码位置判定（第 1 章）；APIServer 内部 IO 与多模态处理的线程划分为推断，未经运行期验证
    • 单元测试：社区仓库 tests/multimodal/test_utils.py（test_group_and_batch_mm_items_split_by_fieldset、test_group_and_batch_mm_items_split_by_shared_data；本地安装包未含 tests，依据仓库路径与测试内容核对）
    • 环境：vLLM 0.22.2.dev、Qwen3.5-0.8B（Qwen3_5ForConditionalGeneration）、TP=1 单机

    边界

    • 合批验证使用的输入由本地脚本构造（字段与真实 processor 输出一致），覆盖 modality 拆批、字段集合拆批、大小不拆三种情形；SharedField 数据不同的拆批情形依据源码与单元测试，未在本地复现
    • 跨进程的编码缓存传输（ec_connector）不在其中
