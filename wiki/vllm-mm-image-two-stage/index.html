多模态图片的两阶段处理

前端 render 链路用 HF image_processor 完成图片加载与 smart_resize，产出 pixel_values 与 image_grid_thw 随请求发送；EngineCore 的 _execute_mm_encoder 调用 embed_multimodal 跑视觉编码器，结果按图片哈希缓存在 encoder_cache 供 decode 复用。合批时字段类型决定合并方式，拆批仅由 modality、字段集合与 SharedField 数据决定。

更新于 2026-08-21 · 类型：源码走读结论（vLLM 0.22.2.dev，Qwen3.5，TP=1）

1. 分界在哪里：两段各自做什么

一张图片从进入 vLLM 到产生图像特征，被拆成两段，分属两个进程：

阶段进程做的事产出
预处理 APIServer 加载图片、smart_resize、归一化（纯 CPU） MultiModalKwargsItem：pixel_values + image_grid_thw，附带哈希与占位符位置
视觉编码 EngineCore 跑视觉编码器 ViT 的 forward（GPU） 图像特征 embedding，按 mm_hash 缓存

这一分界可用 profiler 的两份 trace 验证。APIServer 进程的 trace 出现的是 fetch_image、multimodal/processing/processor.py、renderers/ 等预处理函数，没有视觉编码器的 forward；EngineCore 进程的 trace 出现 _execute_mm_encoder、_process_image_input、embed_multimodal 等编码函数。APIServer 进程内部还进一步分线程：图片文件的加载 IO（load_file、rgba_to_rgb）与多模态处理（HF processor 调用）分布在不同线程上，与主线程的请求接发并行。

2. 前端段：HTTP 请求到 pixel_values

请求进入 OpenAI 入口后，图片沿一条链路被处理：render_chat_request（chat completion serving）→ render_messages_async（HfRenderer）→ parse_chat_messages_async 识别消息中的图片并调 fetch_image 加载 → _process_multimodal → mm_processor.apply → call_hf_processor_mm_only → 最终由 HF 的 image_processor 完成 resize 与归一化。产出的 MultiModalKwargsItem 含两个字段：pixel_values（归一化后的像素张量）与 image_grid_thw（分块网格），随请求一同序列化发送。

image_grid_thw 由 transformers 的 smart_resize 计算：把图片高宽各自取整到 factor=28 的倍数、总像素限制在 min/max 范围内、尽量保持宽高比，再除以 28 得到网格数。两个真实例子：980×986 的图片被缩放后切为 grid [1, 62, 62]，对应 3844 个 patch；2310×2310 的图片切为 grid [1, 144, 144]，对应 20736 个 patch。图片的 token 占位数量即由网格推出。

3. 后端段：_execute_mm_encoder 的视觉编码

收集

调度器产出的 SchedulerOutput.scheduled_encoder_inputs 记录本步需要编码的项，结构为 {请求ID: 图片下标列表}。存下标而不存数据：数据可能已在编码缓存中或可从远端获取，调度器只决定"哪些项需要编码"。_batch_mm_inputs_from_scheduler 按下标从各请求的 mm_features 取出数据，整理为三个平行列表：图片哈希、图片数据、以及 (请求ID, 占位符位置) 引用——后者用于把图片映射回所属请求，从而查到该请求使用的 LoRA 适配器。占位符位置即 PlaceholderRange（offset + length），标记图片在 token 序列中的插入点。

合批机制

group_and_batch_mm_kwargs 把收集到的项组织成一批批可整体送入编码器的数据。机制分两层：怎么合并与什么时候拆批。

每个字段（FieldElem）携带一个 field 对象，决定合批时数据的合并方式（reduce_data）：

字段类型合并方式语义
MultiModalBatchedField各 item 数据形状相同 → torch.stack 成一个张量；形状不同 → 以列表返回每个 item 拥有独立的一份张量（如 pixel_values）
MultiModalSharedField取第一个 item 的数据（batch[0]）同一份数据复制给 batch 内所有 item（如跨 patch 共享的配置），合并时留一份即可

拆批判定由每项的 group id 决定：把 item 的所有字段按名排序，每个字段记为 (字段名, 哈希)，其中只有 SharedField 字段参与哈希计算，BatchedField 字段哈希恒为空。相邻项的 group id 相同才落入同批。因此拆批当且仅当三种情况：modality 不同（外层按 modality 分组）；字段名集合不同（group id 的键不一致）；SharedField 字段的数据不同（哈希不一致）。BatchedField 的数据——包括图片大小、网格形状——完全不参与拆批判定：形状不同的图片留在同一批，只是合并时 pixel_values 退化为列表而非堆叠成张量。社区的单元测试（tests/multimodal/test_utils.py 的 TestGroupAndBatchMmItems）覆盖了后两种拆批条件：字段集合不同拆批、SharedField 值不同拆批。

编码

每批数据以关键字参数展开传入 model.embed_multimodal，其内部对 image modality 调 _process_image_input 跑视觉编码器 forward，产出每个图片项的特征张量。调用处把模型对象当作 SupportsMultiModal 协议使用——协议只要求对象具有这些多模态方法，不依赖具体模型类，因此任何实现了该组方法的视觉语言模型都能走同一条编码路径。

缓存

编码结果按图片哈希写入 encoder_cache。视觉编码只在图片首次被调度的 prefill 回合执行；decode 回合需要图片特征时直接读缓存（_gather_mm_embeddings 按 PlaceholderRange 取对应片段），不再跑 ViT。同一图片被多个请求使用时也命中同一缓存条目。

4. 为什么这样分

预处理是纯 CPU 工作——图片解码、缩放、归一化，放在 APIServer 可以用独立线程做，不占用引擎进程；视觉编码需要 GPU 与模型权重，必须靠近模型所在进程，且编码结果要立即进入缓存供后续回合使用。把重活留在离 GPU 最近的地方、轻活留在离请求最近的地方，是这条分界线的动机。

来源与范围说明

源码定位

  • 前端链路：vllm/entrypoints/chat_utils.py（parse_chat_messages_async）、vllm/renderers/hf.py（render_messages_async）、vllm/renderers/base.py（_process_multimodal）、vllm/multimodal/processing/processor.py（apply）、vllm/transformers_utils/processor.py（call_hf_processor_mm_only）、vllm/multimodal/utils.py（fetch_image）
  • smart_resize：transformers/models/qwen2_vl/image_processing_qwen2_vl.py（62）
  • 后端链路：vllm/v1/worker/gpu_model_runner.py（_preprocess；_execute_mm_encoder；_batch_mm_inputs_from_scheduler；_gather_mm_embeddings；encoder_cache 写入）
  • 合批机制：vllm/multimodal/utils.py（_get_group_hash；_batch_mm_items；group_and_batch_mm_items；group_and_batch_mm_kwargs）、vllm/multimodal/inputs.py（MultiModalBatchedField；MultiModalSharedField）
  • 编码：vllm/model_executor/models/qwen3_vl.py（embed_multimodal；_process_image_input）
  • 占位符：vllm/multimodal/inputs.py（PlaceholderRange）

验证数据

  • smart_resize 数值：对 testdata 真实图片（980×986 与 2310×2310）用模型自带的 HF processor 实际运行得到
  • 合批行为：对 group_and_batch_mm_kwargs 用真实 processor 输出实际运行——两张网格不同的图片合为一批（pixel_values 以列表返回），图片与音频拆为两批，字段集合不同的两张图拆为两批
  • trace 证据：APIServer 进程 trace（预处理函数分布）与 EngineCore 进程 trace（编码函数分布）
  • 单元测试：社区仓库 tests/multimodal/test_utils.py（TestGroupAndBatchMmItems，本地安装包未含 tests，依据仓库路径与测试内容核对）
  • 环境：vLLM 0.22.2.dev、Qwen3.5-0.8B（Qwen3_5ForConditionalGeneration）、TP=1 单机

边界

  • 合批验证使用的输入由本地脚本构造（字段与真实 processor 输出一致），覆盖 modality 拆批、字段集合拆批、大小不拆三种情形；SharedField 数据不同的拆批情形依据源码与单元测试，未在本地复现
  • 跨进程的编码缓存传输（ec_connector）不在其中
