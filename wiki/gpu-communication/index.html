    GPU 通信

    通信原语只有搬、算、换三类动作；跨机传输快慢的分界在于 CPU 是否参与搬运——socket/TCP 路径 CPU 全程参与，RDMA 路径绕过 CPU，GPUDirect 连主机内存都跳过。

    更新于 2026-08-07 · 类型：学习笔记

    分层与主线：谁调度、谁搬运

    GPU 之间传数据，从发出请求到数据落位，经过三个层次，各司其职：

    • 应用层：框架发起通信请求（"我要 all-reduce"）。应用不关心通信细节，只描述意图。
    • 通信库：枢纽。探测硬件拓扑（哪些卡之间有 NVLink、跨机走哪条网络）、选择算法（环形、树形）、管理通信组、决定数据走哪条物理通道。
    • 硬件层：物理通道执行搬运——机内的 PCIe/NVLink、跨机的网卡与网络。

    贯穿全部层次的加速主线只有一条：CPU 是否参与数据搬运。CPU 参与每一次拷贝与协议处理，传输就慢；网卡等硬件直接搬运、CPU 只下指令，传输就快。后文所有术语都围绕这条主线展开。

    通信原语：搬、算、换三类动作

    集合通信原语是通信库提供的最小操作，全部可归为三类动作，前缀 all 统一表示「结果人人有份」：

    • 搬：数据移位，值不变。broadcast、scatter、gather、all-gather。
    • 算：数据归约，值改变。reduce、all-reduce、reduce_scatter。
    • 换：数据交换主人。all-to-all。

    八个原语的完整定义

    描述每个原语只需回答两个问题：操作前每张卡各持有什么，操作后每张卡各持有什么。以 2 张卡 A、B 为例：

    原语操作前操作后典型用途
    broadcast 广播只有 A 有完整数据 [1,2,3]A、B 都有同一份 [1,2,3]分发公共参数、配置
    scatter 散播只有 A 有 [1,2,3,4]A 拿 [1,2]，B 拿 [3,4]（每人不同份）把任务/数据切分下发
    gather 收集A 有 [1,2]，B 有 [3,4]拼到 A：A 有 [1,2,3,4]，B 无结果汇集到主卡
    all-gather 全收集A 有 [1,2]，B 有 [3,4]每张卡都有拼接结果 [1,2,3,4]张量并行输出拼列
    reduce 归约A 有 [1,2]，B 有 [3,4]归约（求和）到 A：A 有 [4,6]梯度汇总到根卡
    all-reduce 全归约A 有 [1,2]，B 有 [3,4]每张卡都有 [4,6]（1+3，2+4）梯度同步、张量并行求和
    reduce_scatter 归约散播A 有 [1,2]，B 有 [3,4]先求和得 [4,6] 再切开：A 拿 [4]，B 拿 [6]序列并行中的归约切分
    all-to-all 全交换A 有 [a1,a2]，B 有 [b1,b2]A 拿 [a1,b1]，B 拿 [a2,b2]（数据换主人）MoE 专家路由、维度互换

    三类动作的边界：搬只改变数据的位置与排列，元素值全部保留；算把多张卡的数合并成新值（求和、求最大等归约操作）；换让每张卡收到其他卡各自给它的一份，是唯一能实现「维度互换」的原语。

    两个容易混淆的对比：broadcast 与 scatter 都是「一个源发给大家」，区别是发同一份（broadcast）还是切开每人一份（scatter）；gather 与 all-gather 都是「把分片拼起来」，区别是拼到一张卡（gather）还是每张卡（all-gather）。reduce_scatter 是归约与切分的组合，先算后切——它的两个阶段分别对应 all-reduce 的前半段。

    原语在张量并行中的对应：列切法（权重沿输出维切）每卡算出不同输出列，输出端需要 all-gather 拼列；行切法（权重沿输入维切）每卡算出部分和，输出端需要 all-reduce 求和。

    环形 all-reduce：带宽最优的两阶段算法

    all-reduce（求全局和）是训练与推理中最频繁的通信，最常见的实现是环形算法（ring all-reduce），由通信库在内部执行。以 4 张卡、每卡数据切成 4 块为例，分两个阶段：

    阶段一：reduce-scatter（边传边加）

    每张卡把自己的数据切成 N 块（N=卡数）。沿环传 N-1 步：每步把一块传给下一卡，收到后与自己同位置的块相加。3 步后，每张卡各持有「某一块」的全局和（卡 0 持有 A 块的和、卡 1 持有 B 块的和……）。

    阶段二：all-gather（边传边存）

    把已算好的块沿环再传 N-1 步，收到直接存储、不再相加。3 步后，每张卡都持有 A+B+C+D 的完整全局和。

    通信量：为什么环形算法带宽最优

    通信量按「每张卡发送的数据总量」计算。以每卡初始 1MB 数据为例：

    卡数 N环形算法（每卡发送）朴素方案（每卡发送）
    4 卡两个阶段各 3 步、每步传 1/4，共 1.5MB = 1.5 倍把自己的 1MB 复制给其余 3 卡 = 3MB = 3 倍
    8 卡约 1.75 倍7 倍
    128 卡约 1.98 倍127 倍

    环形算法的总通信量为 $\frac{2(N-1)}{N}$ × 数据量，卡数增大时趋近 2 倍、不超过 2 倍；朴素方案（每卡把自己的完整数据复制给其余所有卡）通信量为 N-1 倍，卡数越多越昂贵。这就是「带宽最优」的含义：任意卡数下通信量最多翻一倍。代价是延迟随卡数线性增长（步数 N-1），因此小消息场景环形算法表现一般。

    其他算法与选择

    树形算法（tree）在卡数多的集群中延迟更低（步数约 $2\log_2 N$，聚合 + 广播各 log 步），适合小消息与大集群；NVLS 利用 NVLink 硬件多播加速；PAT 等混合算法用于特定规模。通信库默认自动选择，也可通过环境变量指定算法与协议。

    机内互联：总线、直连与中心交换

    单台机器内的 GPU 之间有三条通道，速度与专用程度递增：

    通道定位连接范围特性
    PCIe公共总线CPU 与所有外设（GPU、网卡、硬盘）共享带宽；数据出网必经此路（网卡插在 PCIe 总线上，NVLink 不连网卡）
    NVLinkGPU 专用直连GPU 与 GPU（或 GPU 与 NVSwitch）点对点、不经 CPU，带宽数倍于 PCIe；不连网卡、不连硬盘
    NVSwitch中心交换芯片多张 GPU 汇聚到它，任意两卡互通8 卡两两直连需 28 条线，中心交换用 8 条线实现全互联

    三条通道各自存在的理由：PCIe 是外设与 CPU 之间的通用数据通路，任何外设都要靠它接入机器；NVLink 针对 GPU 间通信极其频繁的场景（张量并行每步都要通信），公共总线会成为瓶颈，需要专用快道；NVSwitch 解决全互联的物理难题——两两直连的线缆数量按组合数增长（8 卡需要 28 条），中心交换用少量线缆换回任意两卡互通。

    由此推出数据路径的约束：GPU 与 GPU 之间优先走 NVLink；数据要出机器（到网卡）则必经 PCIe——因为网卡挂在 PCIe 总线上，NVLink 不连接网卡。这也是「出网必经 PCIe」的由来。

    跨机传输：CPU 参与与绕过 CPU 两条路径

    路径一：socket / TCP / IP / 以太网，CPU 全程参与

    这一路径由四层协作，数据发出时从上往下逐层打包，接收时反向逐层拆包：

    • socket：编程接口（API），程序打开它建立连接点、收发数据。不是协议，是「开口」。
    • TCP（Transmission Control Protocol）：传输控制协议，保证数据可靠有序到达——丢包重传、乱序排好。
    • IP（Internet Protocol）：互联网协议，给每台机器分配门牌号（如 192.168.x.x），数据包靠它跨网络找到目标。
    • 以太网（IEEE 802.3）：物理层与链路层的统一标准，规定帧格式、速率等级，用 MAC 地址在交换机覆盖的网段内寻址。名字借自 19 世纪假想的传光介质「以太（Ether）」，寓意无处不在的传输媒介。

    MAC 与 IP 的分工：MAC 地址是网卡出厂固化的 48 位编号（如 08:00:27:b9:88:74），是以太网层「这一跳」的本地地址，交换机靠它把帧转给正确端口（交换机内部维护 MAC↔端口表）；IP 是网络层「全程」的全局地址。数据先靠 IP 知道要去哪台机器，到达所在网段后再靠 MAC 找到具体端口。

    为什么慢：数据每过一层，CPU 都要参与处理（封包、校验、拷贝），加上用户态与内核态之间、内核与网卡之间的多次拷贝，延迟高且占 CPU。作为代价，这一路径通用——任何机器、任何网络都能用，不需要专门硬件。

    路径二：RDMA 家族，绕过 CPU

    RDMA（Remote Direct Memory Access，远程直接内存访问）让网卡直接读写远端内存：应用先向网卡注册内存区域，网卡用 DMA 从源内存读出、经网络直达目标内存写入，绕过 CPU 与操作系统协议栈，零拷贝。三个关键词：远程（跨机器）、直接（不经 CPU）、内存访问（直接读写内存）。

    RDMA 是技术思想，需要硬件支持，有两条落地路线：

    IB（InfiniBand）RoCE（RDMA over Converged Ethernet）
    本质专为 RDMA 设计的独立网络（Infini 无限 + Band 带宽）把 RDMA 封装进以太网帧，跑在现成以太网上
    硬件自有交换机、网卡（HCA）、线缆，需单独布线复用现有以太网交换机与线缆
    无损保障链路层内置信用流控，天生无损需在交换机配置 PFC/ECN 制造「无损」，配置复杂且易错
    取舍性能最好、延迟最低，但设备昂贵成本低、融入以太网生态，但性能依赖配置

    配套术语：HCA（Host Channel Adapter）是 IB 网络里对网卡（NIC）的称呼——同一个硬件角色在不同网络世界的名字，HCA 里的 Adapter 指「转接两种规格」：主机内部总线与 IB 网络；GID（Global Identifier）是 IB/RoCE 网络的全局寻址，相当于 IB 世界的 IP（IB 独立设计，没有 IP 体系）；mlx5 是 Mellanox（已被 NVIDIA 收购）网卡在 Linux 里的设备名（如 mlx5_0），通信库找 RDMA 设备时找的就是它。

    GPUDirect 更进一步：普通 RDMA 网卡读写的是主机内存，数据路径是「GPU 显存 → 主机内存 → 网卡」，主机内存仍当中转；GPUDirect 让网卡直接读写 GPU 显存，连主机内存都跳过（NVIDIA 官方表述：CPU 与主机内存完全不在数据路径上）。对数据常驻显存的 AI 场景，这一跳的节省直接进入通信时间。

    两条路径并存的原因：TCP 路径通用、任何环境可用；RDMA 需要支持 RDMA 的网卡（如 Mellanox ConnectX 系列）与匹配的网络，只有高性能集群才配置。通信库会探测可用硬件，优先 RDMA，退化到 TCP。

    网卡：一个角色，多个名字与用法

    网卡是「机器出网的门」这个硬件角色，围绕它有一组容易混淆的术语，分属三个层面：

    • 称呼层：NIC（Network Interface Card，网络接口卡）是它在以太网世界的叫法；HCA（Host Channel Adapter）是它在 IB 世界的叫法。同一个角色，两个艺名，不是两种硬件。
    • 系统层：网卡装进 Linux 系统后不止一个名字，同一块物理网卡有两个身份——网络接口名 eth0（Ethernet 0，以太网接口 0 号，传统按发现顺序编号；现代系统也有按硬件位置编码的可预测命名，如板载网卡 eno1、PCIe 槽位网卡 ens1f0）走 IP/TCP 慢路径；RDMA 设备名 mlx5_0（Mellanox 第 5 代驱动）走 RDMA 快路径。通信库找快路径设备时找的是 mlx5_0 而不是 eth0。
    • 用法层：bond（绑定）不是新网卡，而是「把多块物理网卡绑成一块逻辑网卡 bond0」的使用方式，动机有两个——带宽叠加（链路聚合，如两块 25G 绑成 50G，需交换机配合 LACP）与故障冗余（主备模式，一块坏了另一块秒切）。

    为什么需要网卡这个设备而不是让 CPU 直接处理网络：一是信号转换，机器内部是 PCIe 总线信号（短距离、并行），外部是线缆信号（长距离、串行、带协议），两套规格需要硬件转接；二是协议处理卸载，封帧、寻址、校验是高频固定活，用专门硬件做比 CPU 软件做快得多、不占 CPU。

    通信库：集合通信库与传输库的分工

    通信库分两类，职责不同：集合通信库实现原语与算法、管理通信组；传输库封装底层传输通道、提供统一接口。

    库类别定位关键特征
    NCCL集合通信库NVIDIA 的标准 GPU 通信库GPU 通信事实标准，探测拓扑、选算法、管理通信组
    TCCL集合通信库腾讯针对自研高性能网络定制的版本接口与 NCCL 完全一致、替换即用，懂自研网络的拓扑与路由（官方披露常用通信模式性能提升约 40%）
    gloo集合通信库PyTorch 自带支持 CPU 张量与跨平台（macOS/Windows），定位 CPU 训练或作为后备
    UCX传输库开源统一通信框架把 RDMA、TCP 等封装成统一 API，自动探测可用传输并选最优路径
    NIXL传输库NVIDIA 面向推理的传输库（Xfer = Transfer）插件化支持 UCX、GDS 等后端；面向 KV 缓存跨节点传输、内存注册、异步零拷贝等推理场景

    两组容易混淆的对比：NCCL 与 gloo 都是集合通信库，一个 GPU 专用（CUDA），一个覆盖 CPU 与跨平台——官方选择规则是 GPU 训练用 NCCL、CPU 训练用 gloo；UCX 与 NIXL 都是传输库，UCX 面向通用高性能计算（HPC），NIXL 面向 AI 推理场景，UCX 只是 NIXL 的可选后端之一。TCCL 存在的理由是 NCCL 为通用硬件优化、不认识自研网络的特殊拓扑与协议，定制版按相同接口重写后无需改应用代码。
