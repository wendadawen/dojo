    MoonViT-V2：K3 从零训练的视觉编码器

    主要依据：Kimi K3 技术报告 §2.4 Native Vision（方案与架构）、§3.1 预训练数据、§3.3 训练配方、§5.2.3 多模态编码器优化；HuggingFace 官方 config.json（moonshotai/Kimi-K3，vision_config 字段）。可核对数字均与 config.json 与报告 Table 1 逐一对照。

    MoonViT-V2 是 Kimi K3 的视觉编码器，负责把图像和视频的像素变成 LLM 能读的视觉 token[C8]。它的核心选择是：不用 SigLIP 这类对比预训练模型做初始化，而是完全从零、用与 LLM 相同的 next-token prediction 目标训练[C1]。K3 报告显示，这样训练的编码器梯度更稳[C2]，且在视觉评测上匹配 SigLIP 初始化的对照——说明对比预训练作为多模态大模型视觉编码器的初始化，在规模上并非必要[C7]。

    核心问题

    1. 为什么 MoonViT-V2 选择从零训练视觉编码器，而不是像主流做法那样用 SigLIP 等对比预训练模型初始化？

      解答：梯度稳定性与目标对齐两个动机

      原因有二——报告以训练稳定性为主要动机，目标对齐为其后的附带动因。其一，训练稳定性：SigLIP 初始化的编码器接入 LLM 联合优化时，vision-tower 梯度范数持续更高且尖峰频繁，而从零训练的 MoonViT-V2 全程更低更平（K3 报告 Fig.6）。其二，目标对齐：对比损失偏向全局语义，next-token prediction 让表征直接被语言建模目标塑造，与编码器的最终用途一致。完整论证见「主流做法遇到什么问题」与「从零训练的方案」两章。

    2. MoonViT-V2 的架构由哪些组件构成，RMSNorm、去除 bias 等设计如何服务"从零训练更稳定"这一目标？

      解答：27 层 ViT 配置，RMSNorm 与去 bias 是稳定性配套设计

      架构是 27 层 ViT：隐藏维 1024、Q/K/V 投影维 1536、MLP 中间维 4096、patch 14，核心 27 层参数约 0.4B（可由 config.json 手算核对）。报告明确把 RMSNorm 与去除所有 bias 定位为"进一步稳定从零优化"的配套设计，不是独立风格选择。见「服务稳定性的架构」一章。

    3. MoonViT-V2 的训练具体是怎么进行的——是先单独训好编码器再接入，还是与 LLM 一起训练？

      解答：从预训练第一步起接入 LLM 联合优化，无事后对齐阶段

      K3 的训练策略是语言与视觉从一开始就联合优化：视觉与文本 token 交织在同一条序列里，共享单一的 next-token prediction 损失；从零初始化的 MoonViT-V2 经 MLP 投影器接在 LLM 前端，与主干一起更新。预训练视觉语料覆盖图注、图文交织文档、OCR、感知、视频、视觉编程六类数据。见「训练是怎么进行的」一章。

    4. 它如何用同一套参数同时处理图像和视频，并在 1M token 上下文内支持 3584×3584 像素的高分辨率输入？

      解答：共享参数 + 分解注意力与时间池化 + pixel-shuffle 压缩

      图像与视频共享全部参数；视频注意力分解为帧内空间、帧间时间两趟并加时间池化，避免全对全开销；投影前 pixel-shuffle 2×2 把 token 数除以 4，使 3584×3584 输入从 65536 个 patch token 压到 16384 个，在 1M 上下文内可负担。见「图像/视频共享与高分辨率」一章。

    5. 从零训练的 MoonViT-V2 与 SigLIP 初始化的 baseline 相比结果如何，这说明了什么、边界在哪？

      解答：匹配 baseline，对比预训练初始化在规模上非必要，但有两条边界

      MoonViT-V2 在视觉评测上匹配 SigLIP 初始化的 baseline，报告据此得出：对比预训练作为多模态大模型视觉编码器的初始化，在规模上并非必要。边界一限定场景——结论只针对"要不要用对比预训练权重做初始化"，不评价 SigLIP 方法自身的性能，不等于"SigLIP 没用"；边界二限定规模——结论只在 K3 的训练规模下成立，其主干是约 2.78T 参数的 MoE（混合专家）。见「结果与结论」一章。

    1. 主流做法遇到什么问题——SigLIP 初始化为何不稳

    一个多模态大模型要让 LLM 读取图像内容，得先把像素变成 token。主流做法分两步：先用对比预训练把视觉编码器训练好，再把它的权重作为初始化接入 LLM 联合训练——前提是预训练得到的视觉知识能让模型有个好的起点。K3 报告把这个前提的稳定性问题摆了出来。

    主流用的对比预训练模型代表是 SigLIP：把图像和文本编码进同一个嵌入空间，训练目标是让配对的图文靠近、不配对的远离。这种对比损失偏向学习"全局语义"——一张图整体在讲什么——而对细粒度的文本与结构线索关注不足。

    当 SigLIP 初始化的视觉编码器接入 LLM 联合优化时，报告观察到不稳定。具体到 MoonViT-3D——报告里用作对照的视觉编码器变体，用 SigLIP 初始化——它的 vision-tower 梯度范数持续更高，且频繁出现尖峰[C2, N1]。

    梯度范数是所有参数梯度组成向量的长度，是一个标量。它持续偏高、反复尖峰，意味着每步更新的方向和幅度在剧烈波动——这是训练不稳定的典型征兆。下图是 K3 报告 Fig.6 的简化对照，只表达两条曲线的相对高低与尖峰密度，不给出具体数值：

    这条对照把问题指向了初始化方式本身：报告观察到，接入 SigLIP 初始化的视觉编码器后联合优化不稳定。如果初始化是不稳定的来源，那换一种初始化方式——或者干脆不用这个预训练初始化——能否让训练稳下来？这正是 MoonViT-V2 要回答的。

    SigLIP 初始化在联合优化中梯度不稳定，这一现象已经明确。报告选择的应对是放弃这种初始化——从零训练就是它的替代方案。

    本章问题

    1. 用一句话说出主流做法的"两步"是什么。

      解答：先对比预训练，再作初始化接入 LLM 联合训练

      第一步用对比预训练把视觉编码器训练好，第二步把得到的权重作为初始化接入 LLM 联合训练。前提是预训练的视觉知识能提供稳定起点，而 Fig.6 显示这一前提在联合优化时不稳定[C2, N1]。

    2. Fig.6 中两条曲线在"高低"和"尖峰密度"上的相对差异是什么，这种差异对应哪种训练问题。

      解答：SigLIP 初始化曲线更高、尖峰更密，对应训练不稳定

      SigLIP 初始化的 MoonViT-3D 梯度范数持续更高且尖峰频繁，从零训练的 MoonViT-V2 全程更低更平。梯度范数持续偏高、反复尖峰，意味着每步更新的方向和幅度在剧烈波动，是训练不稳定的典型征兆。

    2. 从零训练的方案——next-token prediction 如何替代对比预训练

    MoonViT-V2 的方案两步：(1) 完全从零初始化——不加载任何预训练视觉权重；(2) 训练目标是 next-token prediction，即与 LLM 主干同一个语言建模目标：给定已观察的 token 序列，预测下一个 token 是什么[C1]。

    next-token prediction 是语言建模的标准目标——模型读一段 token 序列，逐位预测下一个 token。用符号写：记已观察的 token 序列为 $x_{\le t}$，被预测的下一个 token 为 $x_{t+1}$，则该位置的语言建模损失为 $\mathcal{L}=-\log p(x_{t+1}\mid x_{\le t})$（第 3 章训练通路图中出现的正是此式）。视觉编码器被这个目标训练，意味着它的表征是"为了帮 LLM 预测下一个词"而被塑造的，而不是"为了和某段文本配对"被塑造的。这是它和 SigLIP 对比损失在目标层面的根本区别。

    方案有两个动机——报告以训练稳定性为主要动机，目标对齐为其后的附带动因。

    动机一（主要）：训练稳定性。报告以从零训练作为对这一问题的回应——接入预训练编码器时联合优化不稳定，从零训练则全程稳定。Fig.6 的对照显示，从零训练的 MoonViT-V2 全程梯度范数更低、尖峰更少[C2]。

    动机二（附带）：目标对齐。报告原文——next-token prediction 让编码器表征直接被语言建模目标塑造，而对比损失偏向全局语义、不利于细粒度文本和结构线索[C3]。换句话说，SigLIP 优化的是"图和文整体配不配"，而 LLM 真正需要的是"图里每个细节如何帮它预测下一个词"。用同一个目标训练编码器，让表征从一开始就对齐它最终的用途。

    把两个方案在三维度上并排看差异：

    维度SigLIP 初始化（MoonViT-3D）从零 + NTP（MoonViT-V2）
    初始化来源对比预训练好的视觉权重从零（无预训练视觉权重）
    训练目标先对比损失、后接入 LM 联合始终是 next-token prediction（与 LLM 同目标）
    表征偏向全局语义细粒度文本与结构线索（被 LM 目标塑造）

    方案定了，但还差一环：训练本身怎么进行——在哪个阶段训、跟谁一起训、用什么数据？

    从零训练的方案与两个动机至此交代完毕，剩下的问题是如何把它落进真实的训练流程。

    本章问题

    1. MoonViT-V2 方案的"两步"分别是什么。

      解答：从零初始化 + 用 next-token prediction 训练

      第一步完全从零初始化，不加载任何预训练视觉权重；第二步用与 LLM 主干相同的 next-token prediction 目标训练——给定已观察的 token 序列，预测下一个 token[C1]。

    2. 报告给出从零训练的两个动机，分别是什么。其中"目标对齐"动机里，对比损失偏向什么、next-token prediction 偏向什么。

      解答：稳定性与目标对齐；全局语义 vs 细粒度线索

      动机一是训练稳定性：接入预训练编码器时联合优化不稳定，从零训练则全程稳定，Fig.6 显示从零训练全程梯度范数更低、尖峰更少[C2]。动机二是目标对齐：对比损失偏向全局语义，next-token prediction 让表征直接被语言建模目标塑造、偏向细粒度文本与结构线索[C3]。

    3. 训练是怎么进行的——接入 LLM 的联合预训练

    "从零训练 + next-token prediction"是方案，还不是训练流程。落到流程上，关键事实是：MoonViT-V2 不是先单独训好、再接入 LLM 的独立模型。K3 采用原生多模态训练策略——语言和视觉从训练一开始就联合优化，不存在"先把 LLM 训完、再把视觉编码器嫁接上去对齐"的事后阶段[C9]。

    这个形态可以分三层说清。数据层面，视觉与文本 token 交织排列在同一条序列里；目标层面，整条通路共享同一个 next-token prediction 损失；参数层面，从零初始化的 MoonViT-V2 经轻量 MLP 投影器接在 LLM 前端，与 LLM 主干在同一个优化循环里更新[C9, C8]。下图给出这条训练通路：

    这个形态直接解释了第 1 章 Fig.6 的实验设定：梯度对照发生在 K3 的预训练消融里——SigLIP 初始化的 MoonViT-3D 与从零的 MoonViT-V2 在同一种联合预训练下训练，监控的是 vision-tower 的梯度范数[C2, N1]。对照比较的是同一训练过程里的两种初始化，不是两种孤立的训练方案。

    3.1 训练用什么数据

    K3 的预训练语料由四大文本域——网页文本、代码、数学、知识——加一个大规模视觉语料构成[C10]。视觉语料沿用 Kimi K2.5 的数据分类体系，结合开源集合与内部流水线完成过滤、合成与去重，覆盖六类数据：

    • 图注（captions）
    • 图文交织文档（interleaved image–text documents）
    • OCR（图中文字识别）
    • 感知（perception）
    • 视频（video）
    • 视觉编程数据（visual coding data）

    数据构造上有两个细节值得点出。其一是坐标监督：定位类标注同时提供绝对坐标与归一化 $[0,1]$ 两种格式，让定位对分辨率变化更鲁棒[C10]。其二是程序化多模态数据（programmatic multimodal data）的扩展：把代码片段与它们的渲染结果配对，格式覆盖 SVG、3D 资产、网页、游戏与 CAD 图纸——"代码与渲染结果同处一个 token 流"正是 K3 原生多模态的输入形态[C10, C9]。

    3.2 训练配置：整个模型统一一套

    优化配置是整个模型统一的：Per-Head Muon 优化器（K3 的矩阵参数优化器，对注意力投影沿头维切分、逐头做正交化）配合 Kimi K2 引入的权重裁剪（对权重幅度设上限的稳定化机制），MoE（mixture-of-experts，混合专家）负载均衡用分位数均衡（把各专家的路由偏差直接设到目标负载对应的分数分位点），学习率为带 1% 线性预热的余弦调度，权重衰减全程 0.1[N3]。这套配置作用于整个 K3 模型；vision tower 是否另有单独超参，报告未披露。

    3.3 系统层面怎么跑得动

    从零联合训练意味着视觉编码器全程参与预训练，而大图与长视频会显著拉长 vision encoder 的计算时间，并造成跨设备负载不均[C11]。K3 用两个训练基础设施设计应对：

    • 动态上下文并行（context parallelism，把序列切分段分布到多设备并行处理）：单张大图沿 patch 维切分到多个设备，注意力通过跨设备聚合 KV（gather-KV）计算；每个 CP 组再分成若干子组，多张大图在子组间负载均衡分布，控制通信占比不随规模增长[C11]。
    • 把 ViT 计算藏进流水线气泡（pipeline parallelism，把模型按层切分到多设备流水执行；"气泡"指流水线中设备等待上下游时的空闲时段）：在 Kimi K2.5 解耦编码器进程（DEP，把 ViT 与文本训练切分为不同阶段）的基础上，K3 把 ViT 计算进一步分解——第一个流水线微批的 ViT 前向提前同步执行，其余前向与反向调度进流水线气泡；大部分 ViT 计算被隐藏，视觉编码器的有效开销大幅消除[C11]。

    至此，训练流程的三个问题都有了着落：在哪个阶段训——从预训练第一步起；跟谁一起训——接入 LLM、与主干联合优化；用什么数据——六类视觉语料与四大文本域交织。省去了预训练权重兜底，架构若不合理，从零训练更容易发散；稳定这套优化的架构设计单独展开。

    本章问题

    1. MoonViT-V2 是先单独训练好、再接入 LLM 的吗？训练从什么时候开始？

      解答：不是——从预训练第一步起接入 LLM 联合优化

      K3 采用原生多模态训练策略：语言和视觉从训练一开始就联合优化，不存在"先训 LLM、再嫁接视觉编码器对齐"的事后阶段。视觉与文本 token 交织在同一条序列里，共享单一的 next-token prediction 损失；从零初始化的 MoonViT-V2 经 MLP 投影器接在 LLM 前端，与主干一起更新[C9]。

    2. 预训练的视觉语料覆盖哪六类数据？程序化多模态数据配对的是什么？

      解答：图注、图文交织、OCR、感知、视频、视觉编程；代码与渲染视觉配对

      六类：图注（captions）、图文交织文档、OCR、感知（perception）、视频、视觉编程数据；语料沿用 Kimi K2.5 分类体系，结合开源集合与内部过滤/合成/去重流水线[C10]。程序化多模态数据把代码片段与它们的渲染结果配对，格式覆盖 SVG、3D 资产、网页、游戏、CAD 图纸[C10]。

    3. 第 1 章 Fig.6 的梯度对照是在什么实验条件下做的？这说明它比较的是什么？

      解答：预训练消融——同一联合训练下的两种初始化

      Fig.6 来自 K3 的预训练消融：SigLIP 初始化的 MoonViT-3D 与从零的 MoonViT-V2 在同一种联合预训练下训练，监控 vision-tower 梯度范数[C2, N1]。所以对照比较的是同一训练过程里的两种初始化，不是两种孤立的训练方案。

    4. 大图和长视频为什么给训练系统带来压力？两个对应设计分别是什么？

      解答：编码器计算时间大增且跨设备负载不均；动态 CP 与流水线气泡

      大图与长视频显著拉长 vision encoder 的计算时间，并造成跨设备负载不均[C11]。设计一：动态上下文并行——大图沿 patch 维切分到多设备、跨设备聚合 KV 算注意力、CP 组分子组均衡分布多张大图；设计二：把 ViT 前向与反向调度进流水线气泡，大部分编码器计算被隐藏，有效开销大幅消除[C11]。

    4. 服务稳定性的架构——27 层 ViT、RMSNorm、去 bias

    MoonViT-V2 的架构基础是 ViT（Vision Transformer）：把图像切成 patch、每个 patch 线性投影成一个向量、送入 transformer 层堆叠。MoonViT-V2 是 ViT 家族的一个具体实例，下面每个数字都来自 HuggingFace 官方 config.json 的 vision_config 字段，可逐项核对[C4]。

    config.json 字段值口语名
    vt_num_hidden_layers27层数
    vt_hidden_size1024隐藏维
    qkv_hidden_size1536Q/K/V 投影维
    vt_intermediate_size4096MLP 中间维
    vt_num_attention_heads12注意力头数
    patch_size14patch 像素
    norm_typermsnorm归一化类型
    attn_bias / linear_bias / patch_embed_proj_bias均为 false全部去 bias

    报告说 MoonViT-V2 "roughly 0.4B parameters"。这个数字可以用上面的配置手算核对。每层（无 bias）含 Q、K、V、O 四个注意力投影、两层 MLP、两个 RMSNorm：

    注意力投影（每个 $1024 \times 1536$ 或 $1536 \times 1024$）：

    $$\text{attn} = 4 \times (1024 \times 1536) = 6{,}291{,}456$$

    MLP（fc1 $1024 \times 4096$、fc2 $4096 \times 1024$）：

    $$\text{mlp} = 2 \times (1024 \times 4096) = 8{,}388{,}608$$

    两个 RMSNorm（各仅 $1024$ 个增益、无 bias）：

    $$\text{norms} = 2 \times 1024 = 2{,}048$$

    每层合计：

    $$\text{per layer} = 6{,}291{,}456 + 8{,}388{,}608 + 2{,}048 = 14{,}682{,}112$$

    27 层总计：

    $$27 \times 14{,}682{,}112 = 396{,}417{,}024 \approx 0.40\text{B}$$

    与报告"roughly 0.4B"一致[F1]。报告 Table 1 给出的 ViT 总参数是 401M，与核心 27 层手算的 396,417,024 相符。401M 的确切构成报告未披露：与手算的差值约 4.6M，和 patch embedding、位置嵌入这类核心层外小量同量级；MLP 投影器不小——pixel-shuffle 后通道维为 $1024\times 4=4096$，仅一层到 LLM 隐藏维 7168 的映射就要约 $29\mathrm{M}$ 参数，是否计入 401M 报告未说明。这些都不影响"核心 27 层约 0.4B"的结论。

    补充：用 config.json 数值运行核对参数量与 token 数

    以下代码可独立运行，输入为 config.json 的 vision_config 数值，输出每层分项、27 层总计，以及 3584×3584 输入的 token 变化。它验证的是上文的两个手算。

    # 从 Kimi-K3 官方 config.json vision_config 读取的 MoonViT-V2 参数
hidden = 1024        # vt_hidden_size
qkv = 1536           # qkv_hidden_size (Q/K/V 各投影到此维)
inter = 4096         # vt_intermediate_size (MLP 中间维)
layers = 27          # vt_num_hidden_layers
patch = 14           # patch_size
merge = 2            # merge_kernel_size [2,2]
image_px = 3584

# 每层参数（无 bias：attn_bias/linear_bias/patch_embed_proj_bias 均为 false）
q = hidden * qkv
k = hidden * qkv
v = hidden * qkv
o = qkv * hidden
attn = q + k + v + o

mlp = hidden * inter + inter * hidden  # fc1 + fc2
norms = 2 * hidden  # 两个 RMSNorm，各仅 1024 个增益

per_layer = attn + mlp + norms
total = per_layer * layers

print(f"Q = {q:,}")
print(f"K = {k:,}")
print(f"V = {v:,}")
print(f"O = {o:,}")
print(f"attn/layer = {attn:,}")
print(f"mlp/layer  = {mlp:,}")
print(f"norms/layer= {norms:,}")
print(f"per_layer  = {per_layer:,}")
print(f"total 27L  = {total:,}  (~{total/1e9:.2f}B)")

# token 数
patches_per_side = image_px // patch
tokens = patches_per_side * patches_per_side
after_shuffle = tokens // (merge * merge)
print(f"\n{image_px}x{image_px} / patch {patch} -> {tokens} tokens")

    验证的机制：attn/layer、mlp/layer、norms/layer 三项相加得 per_layer，$\times 27$ 得 total；patches_per_side 平方得 tokens，$\div 4$ 得 after_shuffle。对应正文 F1 与 F2 两个手算。

    观察重点：total 的 0.40B 与报告"roughly 0.4B"一致；after_shuffle 的 16384 远小于 1M 上下文，这是下一章高分辨率可行的前提。

    简化说明：只计核心 27 层（Q/K/V/O + 2 层 MLP + 2 RMSNorm），未计 patch embedding、位置嵌入（divided_fixed，按 height/width/time 分解）、MLP 投影器（patchmergerv2）与最终归一化；这些不在核心 27 层的计数范围内，不计入"约 0.4B"核心量级（其中 MLP 投影器并不小，是否计入 401M 报告未说明）。真实工程实现还含 flash-attention 等优化，不影响参数计数。

    架构里有两个设计需要单独点出，因为报告明确把它们定位为"服务从零训练稳定性"——不是任意工程惯例。

    第一是 RMSNorm：按均方根归一化、仅缩放增益、无 bias。它和 LayerNorm 的差别在于去掉了均值减法和 bias 项，计算更简、参数更少。

    第二是去除所有 bias：linear 和 attention 投影里的可学习加性偏置全部去掉（config 的 attn_bias、linear_bias、patch_embed_proj_bias 均为 false）。

    报告原文把这两条和"从零训练"绑在一起——"a design that further stabilizes the from-scratch optimization above"。也就是说，RMSNorm 和去 bias 不是独立风格选择，而是为了让从零训练更稳而配套的设计[C4, F3]。报告给了明确的目的定位，不是在陈述一般 ViT 惯例。

    架构配置与稳定性设计讲完了，但编码本身不回答另一个问题：一套参数如何同时处理图像与视频，又怎样在高分辨率下不撑爆上下文。

    本章问题

    1. 不查表，说出 MoonViT-V2 的层数、隐藏维、patch 大小三个数字。

      解答：27 层、隐藏维 1024、patch 14

      对应 config.json 的 vt_num_hidden_layers=27、vt_hidden_size=1024、patch_size=14；这三个数字也是参数量与 token 数两个手算的输入[C4]。

    2. 手算：每层注意力投影（4 个）共多少参数。27 层总计约多少。

      解答：每层 $6{,}291{,}456$，27 层共约 $0.40\mathrm{B}$

      每个投影是 $1024\times1536$ 或 $1536\times1024$，4 个共 $4\times(1024\times1536)=6{,}291{,}456$。加上 MLP 与两个 RMSNorm，每层合计 $14{,}682{,}112$；27 层总计 $396{,}417{,}024\approx 0.40\mathrm{B}$，与报告"roughly 0.4B"一致[F1]。

    3. 报告把 RMSNorm 和去 bias 定位成服务什么目标。

      解答：进一步稳定从零优化，是配套设计而非惯例

      报告原文把它们与从零训练绑定——"a design that further stabilizes the from-scratch optimization above"。即 RMSNorm 与全去 bias 不是独立的风格选择，而是让从零训练更稳的配套设计[C4, F3]。

    5. 图像/视频共享与高分辨率——分解注意力、时间池化、pixel-shuffle

    架构稳了，但 K3 要的是"原生多模态 + 长上下文"——一套参数同时吃图像和视频，还要在 1M token 上下文内塞下高分辨率。MoonViT-V2 用三个机制回答这个问题。

    机制一：图像与视频共享全部参数。同一套权重处理两种模态，不分成两个编码器。这是沿用 MoonViT-3D 的设计[C5]。

    机制二：分解注意力。处理视频时，注意力被拆成两趟（token 间相互加权聚合，见 标准 Transformer 注意力）：

    把空间和时间拆开，避免了"所有帧所有 patch 两两 attend"那种 $O(T^2 \cdot H^2 \cdot W^2)$（$T$ 为帧数，$H\times W$ 为每帧的 patch 网格）的爆炸式开销。时间池化进一步沿时间维压缩 token，把多帧信息压成更短的序列[C5]。

    机制三：pixel-shuffle 2×2 下采样。投影前，把 2×2 的空间邻域搬进通道维：

    这是无损重排——它压缩的是序列长度（token 数除以 4），不是信息量；四个邻域 token 的内容被完整保留在通道维里，后续投影再决定如何把它们降维成 LLM 嵌入。它不是"丢信息的有损压缩"——压缩的是序列长度，信息量由后续投影降维那一步决定。

    把这三个机制放到 3584×3584 这张图上算一遍 token 账。patch 大小为 14：

    $$\frac{3584}{14} = 256 \quad\Rightarrow\quad 256 \times 256 = 65{,}536 \text{ 个 patch token}$$

    pixel-shuffle 2×2 把它压成：

    $$\frac{65{,}536}{4} = 16{,}384 \text{ 个 token}$$

    16,384 远小于 K3 的 1M token 上下文——这就是"3584×3584 在 1M 上下文内可负担"的算术依据[C6, F2]。如果没有 pixel-shuffle 这一步压缩，65,536 个 token 会占用很大一部分上下文预算，原生多模态的长上下文就难以成立。

    token 算术已经算清，可行性有了依据，但这只是前提；从零训练在效果上够不够用，要靠实验结果回答。

    本章问题

    1. 手算：3584×3584 的图在 patch=14 下产生多少 token。pixel-shuffle 2×2 后剩多少。

      解答：$65{,}536$ 个，压缩后 $16{,}384$ 个

      每边 $3584/14=256$ 个 patch，共 $256^2=65{,}536$ 个 patch token；pixel-shuffle 2×2 把 token 数除以 4，得 $65{,}536/4=16{,}384$ 个，远小于 1M 上下文[C6, F2]。

    2. 分解注意力把视频注意力拆成哪两趟。为什么要拆。

      解答：帧内空间 + 帧间时间两趟，避免全对全开销

      拆成帧内空间注意力（一帧内 patch 之间）与帧间时间注意力（跨帧、对应空间位置之间）两趟，另用时间池化沿时间维进一步压缩。拆开避免了所有帧所有 patch 两两 attend 的 $O(T^2 \cdot H^2 \cdot W^2)$ 爆炸式开销[C5]。

    3. pixel-shuffle 压缩的是"信息量"还是"序列长度"。为什么。

      解答：压缩序列长度，是无损重排

      pixel-shuffle 只是把 2×2 空间邻域搬进通道维：token 数除以 4，四个邻域 token 的内容完整保留在通道维里，由后续投影决定如何降维。信息压缩发生在投影降维那一步，不属于 pixel-shuffle 本身。

    6. 结果与结论——对比预训练初始化是否必要

    方案、架构、token 预算都讲了，最后一个问题：从零训练到底够不够用？

    报告给的答案是：MoonViT-V2 在视觉评测上匹配 SigLIP 初始化的 baseline[C7, N2]。原文——"we find MoonViT-V2 matches the SigLIP-initialized baseline across vision evaluations"。报告没有给出逐项分数表，只给了这个定性结论，所以本文不构造任何具体分数数字。

    由此得出报告的核心结论：对比预训练作为多模态大模型视觉编码器的初始化，在规模上并非必要[C7]。

    维度SigLIP 初始化（baseline）从零 + NTP（MoonViT-V2）
    训练方式对比预训练 init + LM 联合完全从零、始终 NTP
    训练稳定性梯度范数高、尖峰频繁梯度范数低、更稳
    视觉评测结果baseline匹配 baseline
    结论—对比预训练 init 非必要

    这个结论有明确的边界，不能无限推广。

    边界一：限定场景。结论是"作为多模态大模型视觉编码器的初始化非必要"。它只评价"要不要用对比预训练权重做初始化"这一适用性，不评价 SigLIP 方法自身的性能。把"初始化非必要"扩大成"SigLIP 没用"是常见误读。

    边界二：限定规模。报告结论在 K3 的训练规模下成立——主干是约 2.78T 参数的 MoE（混合专家）[N4]。在更小规模、或不同主干下，从零训练是否仍能匹配对比初始化，报告没有给出保证。把规模结论外推到任意规模是不成立的。

    实证结论与适用边界都已给出，最后一部分交代各论断的出处与简化条件。

    本章问题

    1. MoonViT-V2 与 SigLIP 初始化 baseline 在视觉评测上的相对结果是什么。报告给了具体分数吗。

      解答：匹配 baseline，报告只有定性结论

      MoonViT-V2 在视觉评测上匹配 SigLIP 初始化的 baseline（"matches across vision evaluations"）。报告没有给出逐项分数表，只给了这个定性结论，因此本文不构造任何具体分数数字[C7, N2]。

    2. 报告的核心结论是什么。它的两个适用边界分别是什么。

      解答：对比预训练初始化在规模上非必要，边界在场景与规模

      核心结论：对比预训练作为多模态大模型视觉编码器的初始化，在规模上并非必要[C7]。边界一限定场景——"初始化非必要"只评价初始化的适用性，不等于"SigLIP 没用"，不评价 SigLIP 自身的性能；边界二限定规模——结论只在 K3 的训练规模下成立（主干约 2.78T 参数的 MoE）[N4]，更小规模或不同主干下没有保证。

    辅助解释与类比边界

    • 把"接入预训练编码器后联合优化不稳定"解读为"预训练视觉权重与 LM 目标之间的更新冲突"，是本页的推断而非报告结论。报告只陈述不稳定的现象（§2.4 "joint optimization becomes unstable"），未给出成因；正文不采用这一机制表述。
    • "梯度范数持续高且尖峰 = 训练不稳定"是辅助解释，只帮助理解 Fig.6 为何被当作稳定性证据。它不覆盖动量优化器、梯度裁剪等工程干预；严格判断仍以优化轨迹与损失曲线为准。
    • "pixel-shuffle 把空间搬进通道、是无损重排"是辅助解释，只描述张量重排这一局部操作。它不保证后续投影降维不丢失信息——降维那一步是有损的，但不属于 pixel-shuffle 本身。

    简化条件及其限制

    • 参数量只计核心 27 层（Q/K/V/O + 2 层 MLP + 2 RMSNorm/层），未计 patch embedding、divided_fixed 位置嵌入（按 height/width/time 分解）、MLP 投影器（patchmergerv2）与最终归一化。可推出：报告"约 0.4B"与核心层计算一致，且与 Table 1 的 ViT 总参数 401M 相符（401M 的确切构成报告未披露）。不可推出：MoonViT-V2 的总参数精确等于 396,417,024。
    • SigLIP 只取"对比预训练、图文对齐、偏向全局语义"这一核心特征，不展开 sigmoid 损失推导与 batch 构造。可推出：为何它是"全局语义偏向"的初始化来源。不可推出：SigLIP 的完整训练机制。
    • 分解注意力只讲"拆成帧内空间 + 帧间时间两趟"，不展开两趟的注意力掩码、实现顺序与计算复杂度推导。可推出：为何能避免全对全开销。不可推出：精确的 FLOPs 节省量。
    • 训练流程只讲"联合优化形态 + 视觉语料构成 + 两个系统设计"，不展开上下文并行的通信细节、1F1B 流水线调度、DEP 完整机制与训练数据配比数字（配比报告未披露）。可推出：训练在哪个阶段进行、跟谁一起、用什么数据、系统瓶颈如何应对。不可推出：vision tower 的单独超参与视觉 token 在语料中的占比。

    全文总结：MoonViT-V2 选择从零训练而非 SigLIP 初始化，原因是对比预训练权重在接入 LLM 联合优化时梯度不稳定（Fig.6 对照），且对比损失偏向全局语义、与 LM 目标不对齐。训练上，它从预训练第一步起接入 LLM 联合优化——视觉与文本 token 交织在同一条序列、共享单一的 next-token prediction 损失，训练语料覆盖六类视觉数据，大图与长视频的系统压力由动态上下文并行与流水线气泡调度应对。架构上采用 27 层 ViT、RMSNorm、全去 bias，这些设计被报告明确定位为服务从零训练稳定性。图像与视频共享全部参数，通过分解注意力、时间池化、pixel-shuffle 2×2 压缩 token，使 3584×3584 输入在 1M 上下文内可负担。结果上，MoonViT-V2 在视觉评测匹配 SigLIP 初始化 baseline，说明对比预训练作为视觉编码器初始化在规模上并非必要——但这一结论限定于多模态 LM 编码器初始化场景与 K3 规模。回扣开篇的核心问题：为什么从零训练、训练如何进行、架构如何服务稳定、如何共享参数与压缩 token、结果与边界——五个问题至此全部回答。
