    滑动窗口注意力（SWA）：把每个 query 的可见范围限制在最近 $W$ 个位置

    主要依据：Mistral 7B（Jiang et al., arXiv:2310.06825）§2「Architectural details」；StreamingLLM（Xiao et al., arXiv:2309.17453）§1、§3.1；DeepSeek-V4.1-Flash 官方推理配置与参考实现（inference/config.json、inference/model.py，官方发布物、非本仓库镜像）。字节账与索引规则的复算记录见文末来源说明。

    本页的「窗口」指单层的可见距离上限：位置 $i$ 只能看到上一层最近的 $W$ 个位置。窗口之外的位置要么靠层堆叠间接看到，要么由另一路全局可见性补足；后者不在本页展开，只在使用处指出。本页依赖 标准注意力（打分与加权的基线）、因果掩码（禁止看未来）、KV cache（缓存哪些张量、为什么随长度增长）与 RoPE（位置如何进入注意力相位）四个前置概念；窗口只改可见集，打分方式与它们一致。

    核心问题

    1. 滑动窗口注意力把 query 的可见集限制成了什么？

      解答：只保留上一层最近 $W$ 个位置，更远的位置单层内不可见

      位置 $i$ 在第 $k$ 层的隐状态只关注上一层最近的 $W$ 个位置，即 $[i-W+1, i]$（来源论文写作 $[i-W, i]$，实现取最近 $W$ 个）；序列开头不足 $W$ 个时只看到已存在的部分，实现上用 $-1$ 槽位占位、不参与打分。因果掩码管的是「不看未来」，窗口进一步管「不看太远」，两者叠加才是完整的可见集。完整定义与对照见第 1 章。

    2. 它省下多少计算与显存？

      解答：打分次数从 $N^2$ 降到 $N\cdot W$，缓存固定为 $W$ 条

      每层注意力打分次数从与序列长度平方成正比降为线性：$N=1048576$、$W=128$ 时少 8192 倍。KV cache 变成固定 $W$ 条的环形缓冲：$W=128$、$512$ 维、FP8 存储时每层 64 KiB，主干 40 层共 2.50 MiB，与序列长度无关（相对 1M 位置的全缓存是 $1/8192$）。完整账目见第 2 章。

    3. 层堆叠能补回多少「看得远」的能力？什么时候不够？

      解答：感受野约 $k\times W$，40 层只有 5120 个 token

      信息每层最多前移 $W$，$k$ 层后 $h_i$ 可间接访问输入层距离至多 $k\times W$ 的位置。DeepSeek-V4.1-Flash 主干 40 层、$W=128$，感受野 5120 个 token，只占 1M 上下文的 0.49%，因此长上下文必须在窗口之外另加全局可见性。另一个边界是：只保留窗口、丢弃序列开头的位置会让模型崩溃，因为开头的位置承担了注意力汇聚点的角色。完整推导与实测数字见第 3 章。

    4. 环形缓冲怎么做到缓存不随长度增长？位置编码怎么处理？

      解答：槽位取 $i \bmod W$，位置用原序列下标

      位置 $i$ 的键值写入槽位 $i \bmod W$，位置超过 $W$ 后覆盖最旧的一条，缓存大小恒为 $W$ 条。前向分两种索引形态：prefill 时每个 query 各得一行可见槽位（含 $-1$ 占位），decode 时唯一的 query 看到整个环、槽位按最旧到最新列出；两者映射回的位置集合实测完全一致。DeepSeek-V4.1-Flash 给窗口 KV 施加 RoPE 时用原序列位置，因此窗口内相对距离不超过 $W$。完整规则与可运行复算见第 4 章。

    常见误解

    • 「窗口注意力等于把长文本截断成 $W$ 个 token」——每个 query 的窗口不同且随位置滑动，位置 $i$ 仍能通过层堆叠间接访问 $i-kW$ 处的信息，只是保真度随层数衰减。
    • 「窗口注意力可以替代全局注意力做长上下文」——感受野只有 $k\times W$，DeepSeek-V4.1-Flash 的 40 层是 5120 个 token，仅占 1M 上下文的 0.49%。
    • 「环形缓冲会丢信息，所以不可靠」——被覆盖的是已经滑出窗口的最旧位置，它们本来就不在可见集内；真正会导致崩溃的是把序列开头的汇聚点位置一起覆盖掉。
    • 「decode 与 prefill 列出的槽位顺序不同，结果就会不同」——槽位顺序不同但集合相同，稀疏注意力对每个槽位独立处理，顺序不影响结果；实测 300 步位置集合完全一致。

    1. 窗口把可见集切成「最近 $W$ 个位置」

    全注意力里，位置 $i$ 的 query 可以看到从序列开头到 $i$ 的全部位置；滑动窗口注意力把上界砍到 $W$：只保留上一层最近的 $W$ 个位置，即 $[i-W+1, i]$ 的隐状态。来源论文把这一区间写作 $[i-W, i]$，而实现与图注都取最近 $W$ 个，本页统一按 $[i-W+1, i]$ 表述[C1]。这里的 $W$ 是窗口大小，DeepSeek-V4.1-Flash 取 128[C4]。

    每个位置的窗口都不同，随位置滑动：位置 4999 的窗口是 4872–4999，位置 5000 的窗口是 4873–5000，这也是「滑动窗口」这个名字的来源。

    1.1 因果掩码管方向，窗口管距离

    两个限制是叠加的，不是替代关系。因果掩码禁止 query 关注未来位置，把可见集限制在 $[0, i]$；窗口再把它收缩到 $[i-W+1, i]$。因此单层的可见槽位数是 $\min(i+1, W)$：序列短于窗口时窗口不起作用（与全注意力等价），序列长于窗口时被截断。

    实现上，窗口槽位与另一路「压缩全局 KV」的槽位拼进同一次注意力调用[C4]，所以「可见集」在代码里是一张索引表：窗口部分按位置索引，压缩部分按压缩条目编号索引。本页只讨论窗口部分。

    对比项全注意力滑动窗口注意力
    位置 $i$ 的可见集$[0, i]$$[i-W+1, i]$
    单层可见槽位数$i+1$$\min(i+1, W)$
    每层打分次数（$N$ 个 query）约 $N^2$约 $N\cdot W$
    KV cache 大小随 $N$ 线性增长恒为 $W$ 条
    远处信息直接可见只能经层堆叠间接获得（第 3 章）
    补充：$-1$ 槽位表示什么

    prefill 时位置靠前的 query 凑不满 $W$ 个可见位置，索引表里这些空位用 $-1$ 标记。注意力实现遇到 $-1$ 槽位时既不取值、也不参与 softmax 的分母，效果等同于该槽位不存在。若不做这个标记而把「空位」当成位置 0，位置 0 会被重复计入并放大它的权重。

    本章问题

    1. 窗口大小 $W=128$ 时，位置 4999 的 query 在某一层能看到哪些位置？

      解答：上一层的位置 4872 到 4999，共 128 个

      可见区间是 $[i-W+1, i] = [4999-128+1, 4999] = [4872, 4999]$，恰好 $128$ 个位置。来源论文把同一区间写作 $[i-W, i] = [4871, 4999]$，共 $W+1=129$ 个位置，但同节的图注写明「每个 token 最多关注上一层的 $W$ 个 token」；实现取最近 $W$ 个，即 4872–4999。位置 4871 及更早的位置在该层不可见；它们只能通过层堆叠间接影响位置 4999（第 3 章）。

    2. 窗口限制与因果掩码是什么关系？只加窗口能保证不看到未来吗？

      解答：不能，两者独立，必须同时使用

      窗口只限制「看多远」，不限制方向：区间 $[i-W+1, i]$ 已经天然不含未来位置，但这是因为它以 $i$ 为右端点。若实现时把窗口写成 $[i-W, i+W]$ 或按缓存槽位顺序取最近 $W$ 条而不带方向判断，就会把未来位置纳进来。因果掩码负责禁止 $>i$ 的位置，窗口负责禁止 $< i-W+1$ 的位置，两者叠加才是 $[i-W+1, i]$。

    2. 省下的是打分次数与缓存字节——以及精度取舍

    第 1 章确定了「每个 query 只看 $W$ 个位置」。这个限制换来两笔收益：计算量从平方变线性，缓存从「随长度增长」变成常量。

    2.1 每层打分次数从 $N^2$ 降到 $N\cdot W$

    注意力对每个 query 都要与可见槽位做一次点积，所以每层的打分次数就是「query 数 × 每个 query 的可见槽位数」[F3]：

    $$n_{\text{score}}(N) = \underbrace{N}_{\text{query 数}} \times \underbrace{W}_{\text{每个 query 可见槽位数}} \quad\text{（窗口）}\qquad\text{vs}\qquad N^2 \quad\text{（全注意力）}$$
    • $N$：序列长度，即 query 个数；
    • $W$：窗口大小，即单个 query 的可见槽位数上限；
    • $n_{\text{score}}$：每层需要计算的注意力分数个数，不含 softmax、值加权与投影的开销。
    序列长度 $N$全注意力打分次数窗口打分次数（$W=128$）倍数
    4 09616 777 216524 28832×
    131 07217 179 869 18416 777 2161 024×
    1 048 5761 099 511 627 776134 217 7288 192×

    倍数等于 $N/W$，因为全注意力与窗口的打分次数之比是 $N^2/(N\cdot W) = N/W$。这里全注意力按非因果的 $N^2$ 计（所有 query-key 对），窗口按因果的 $N\cdot W$ 计（每个 query 最多 $W$ 个可见槽位）；两者都按因果口径计的话，全注意力是 $N(N+1)/2$，比值约 $N/(2W)$，仍是线性增长。序列越长，窗口的收益越大[N5]。

    2.2 环形缓冲让缓存不随长度增长

    缓存侧的收益更直接：既然每个 query 只需要最近 $W$ 个位置的键值（键值见 KV cache），就不必保存全部历史。Mistral 7B 把这写成固定大小 $W$ 的滚动缓冲：位置 $i$ 的键值写入槽位 $i \bmod W$，位置超过 $W$ 后旧值被覆盖，缓存大小停止增长[C2, N2]。

    DeepSeek-V4.1-Flash 的窗口取值与精度给出了具体数字[C4, N5]：$W=128$、单头 512 维、窗口 KV 以 FP8 存储（每元素 1 字节），因此

    $$\text{每层窗口缓存} = 128 \times 512 \times 1\ \text{B} = 65\,536\ \text{B} = 64\ \text{KiB}$$
    • $128$：槽位数，等于窗口大小；
    • $512$：单个 KV 头的 latent 维（该模型只有 1 个 KV 头）；
    • $1\ \text{B}$：FP8 每元素字节数。
    展开：40 层窗口缓存的总量与「不随长度增长」的含义

    构造示例（数字取自官方配置，非实测运行）。主干 40 层各有一份窗口缓存：$40 \times 64\ \text{KiB} = 2560\ \text{KiB} = 2.50\ \text{MiB}$。除这 40 层外，模型还有 3 个 DSpark 草稿层各自注册一份同尺寸的窗口缓存，合计约 $3 \times 64\ \text{KiB} = 0.19\ \text{MiB}$；本页的「整个模型」账目只统计主干 40 层。这一项与序列长度无关：序列从 4K 涨到 1M，窗口缓存始终是 2.50 MiB。作为对照，若把 1M 个位置的窗口 KV 全部留下，单层就是 $1\,048\,576 \times 512 \times 1\ \text{B} = 512\ \text{MiB}$，40 层为 20 GiB；固定窗口相对它是 $1/8192$。这里的字节账只算窗口 KV，不含另一路压缩全局 KV 与索引器缓存——那两项才是长上下文缓存的主要部分。

    2.3 窗口 KV 为什么保持 FP8

    同一份模型里，压缩后的全局 KV 被量化到 FP4，而窗口 KV 保持 FP8。技术报告给出的理由是窗口 KV 对量化更敏感[C4]。两路 KV 角色不同：窗口 KV 直接保存最近 $W$ 个位置的键值并以 FP8 存储，不经压缩全局 KV 的池化与 FP4 量化这两步，每个 query 都必然读到；压缩全局 KV 是远距离的粗粒度摘要，本身已经过池化。

    本章问题

    1. 为什么窗口化对长序列的收益比短序列大？

      解答：因为收益倍数等于 $N/W$，随序列长度线性增长

      全注意力的打分次数是 $N^2$，窗口是 $N\cdot W$，比值 $N/W$。序列越短这个比值越接近 1（序列长度等于窗口时两者完全一样）；序列越长收益越大：$N=1\,048\,576$、$W=128$ 时是 8192 倍。反过来说，短序列上引入窗口不会带来计算收益，只会损失可见范围。

    2. 窗口缓存 64 KiB 是「每层」还是「整个模型」？为什么它可以与序列长度无关？

      解答：每层 64 KiB，主干 40 层合计 2.50 MiB；因为缓存只存最近 $W$ 个位置

      64 KiB = 128 槽 × 512 维 × 1 字节，是单层的量；主干 40 层合计 2.50 MiB。3 个 DSpark 草稿层另各有一份同尺寸缓存，加入后约 2.69 MiB。它与序列长度无关的原因是：写入按 $i \bmod W$ 循环覆盖，超过 $W$ 的位置直接覆盖最旧的一条，缓存条数恒为 $W$，不随 $i$ 增长。代价是位置 $i$ 只能看到最近 $W$ 个位置，超出部分不再保存在缓存里。

    3. 层堆叠接力：感受野 $k\times W$ 与它的天花板

    窗口砍掉了可见范围，但模型并没有因此「只记得最近 128 个 token」——因为层与层是串联的：第 1 层把远处信息搬到近处，第 2 层再搬一次。接力能走多远由每层前移量与层数共同决定，走到头之后窗口就不再够用。

    3.1 信息每层前移 $W$

    第 $k$ 层位置 $i$ 的隐状态关注上一层 $[i-W+1, i]$ 的隐状态，而上一层那些位置各自又关注了更早的 $W$ 个位置。递归展开，$k$ 层之后 $h_i$ 可以间接访问输入层距离至多 $k\times W$ 的位置[C1, F1]：

    $$\text{span}(k) = k \times W$$
    • $k$：层数（从输入层算起的注意力层数）；
    • $W$：窗口大小；
    • $\text{span}(k)$：第 $k$ 层可以间接访问的输入层最大距离，单位是 token。

    用 Mistral 7B 的公开数字可以对照这个公式：$W=4096$、32 层，理论上限注意力跨度约 $4096 \times 32 = 131\,072$ 个 token[N1]。数字与公式吻合。

    3.2 5120 对 1M：窗口之外需要另一路可见性

    把公式套到 DeepSeek-V4.1-Flash 上[N6]：$W=128$、主干 40 层，

    $$\text{span}(40) = 40 \times 128 = 5120\ \text{token}$$

    而该模型支持的上下文是 $1\,048\,576$ 个 token，5120 只占 $0.49\%$。也就是说：位置 999 999 的 query 单靠窗口只能间接看到 994 879 之后的内容，更早的 99.5% 上下文它「够不着」。这正是长上下文模型需要第二路可见性的原因——DeepSeek-V4.1-Flash 的做法是给除最前两层外的层再挂一路压缩后的全局 KV（把远距离的每 $r$ 个 token 池化成一条），由索引器为每个 query 挑出其中最重要的若干个位置[C4]。那一路的压缩比、选择规则与缓存账不属于本页范围；这些内容在 DeepSeek-V4.1-Flash 的完整说明页 中逐项展开，本页只用到「窗口之外另有全局可见性」这个结论。

    3.3 只用窗口会崩：注意力汇聚点

    窗口还有一个反直觉的失效模式。StreamingLLM 的实测显示：如果只保留最近窗口的 KV、把序列开头的位置全部丢弃，模型在序列长度超过缓存后会崩溃（困惑度从个位数涨到数千），而只要把最前面的 4 个位置留下就能恢复[C3]。原因是开头的位置承担了注意力汇聚点的角色——大量注意力分数被分配给它们，而它们一旦被移除，softmax 的分母会缺掉一大块，注意力分布随之偏移[C3]。这与语义无关：StreamingLLM 把开头 4 个 token 全部换成换行符，模型仍会显著地关注这些初始换行符；把它们作为初始位置保留时，困惑度恢复到与保留原始 4 个 token 相当的水平（5.60 对 5.40）[C3, N3]。

    补充：StreamingLLM 给出的对照数字

    Llama-2-13B 在 PG19 首本书（65K token）上：只用窗口（0 个初始位置 + 1024 个近期位置）困惑度 5158.07；保留 4 个初始位置（4+1020）后降到 5.40[N3]。另一个对照是 160M 参数模型：用可学习 sink token 训练的模型在「1 个 sink + 1023 个近期位置」下困惑度 18.01，而未做该训练的模型即使保留 2 个初始位置也只有 18.05——差别在于前者只需要 1 个 sink 就够[N4]。这两组数字说明「窗口 + 汇聚点」才是可用组合，也解释了为什么后续模型会把汇聚点做成一个可学习参数。

    本章问题

    1. 40 层、$W=128$ 的模型，感受野是 5120 个 token，这个数字怎么来的？它意味着什么？

      解答：$40 \times 128$，意味着窗口只能覆盖 1M 上下文的 0.49%

      每层把可见范围向前推 $W=128$ 个位置，40 层累计 $40 \times 128 = 5120$。它意味着：只有落在最近 5120 个 token 内的信息能通过层堆叠间接到达当前 query，更早的内容必须由另一路全局可见性提供。$k\times W$ 是上限而非保真范围——间接路径要经过多层混合，实际可利用性会随距离下降。

    2. 为什么「只保留最近窗口」会让模型崩溃？留下序列开头的位置解决了什么？

      解答：开头位置是注意力汇聚点，移除它们会抽掉 softmax 分母的一大块

      自回归模型里，序列开头的位置对所有后续位置都可见，训练时容易演变成「注意力汇聚点」：即使语义上不重要，也会被分配大量注意力。softmax 要求权重非零，模型需要一个「倾倒」注意力的去处，开头位置正好充当这个角色。把它们从缓存里移除后，分母缺少这一块，注意力分布显著偏移，模型输出崩溃；保留少量（4 个）开头位置即可锚定注意力计算。

    4. 环形缓冲：槽位、覆盖与位置编码

    前两章把「缓存固定为 $W$ 条」当作结论使用，其实现归结为两处最容易出错的地方：索引与位置。

    4.1 槽位 = 位置对窗口取模

    规则只有一条[C2, F2]：

    $$\text{slot}(i) = i \bmod W$$
    • $i$：token 在序列中的位置（0 起）；
    • $W$：窗口大小；
    • $\text{slot}(i)$：该位置在缓存数组中的下标，取值 $0 \sim W-1$。

    写入是循环覆盖：位置 $W$ 写进槽位 0，覆盖位置 0；位置 $W+1$ 覆盖位置 1，依此类推。因此缓存里始终是最新 $W$ 个位置，且数组长度不变。

    代码：环形缓冲的写入与索引是否一致 
    W = 8          # 窗口大小（示意用的小值）
seq_len = 20   # 序列长度

ring = {}      # 槽位 -> 它当前保存的位置
for p in range(seq_len):
    ring[p % W] = p                       # 写入：位置 p 进入槽位 p mod W
    # decode 时唯一的 query 看到整个环：槽位从"最旧"开始绕一圈
    oldest = p % W + 1
    slots = [s for s in list(range(oldest, W)) + list(range(oldest)) if s <= p]
    positions = sorted(ring[s] for s in slots)
    expect = list(range(max(0, p - W + 1), p + 1))
    assert positions == expect, (p, positions, expect)

print("W =", W, " 序列长度 =", seq_len, " 全程一致")
print("最后一步 p =", seq_len - 1)
print("  槽位序列   :", slots)
print("  映射回位置 :", positions)
print("  期望因果窗 :", expect)
print("  位置 % W   :", [p % W for p in positions])

    预期输出：

    W = 8  序列长度 = 20  全程一致
最后一步 p = 19
  槽位序列   : [4, 5, 6, 7, 0, 1, 2, 3]
  映射回位置 : [12, 13, 14, 15, 16, 17, 18, 19]
  期望因果窗 : [12, 13, 14, 15, 16, 17, 18, 19]
  位置 % W   : [4, 5, 6, 7, 0, 1, 2, 3]

    验证的机制：第 4.1 节的槽位映射与第 4.2 节的 decode 索引规则。每次写入后检查「按槽位读回的位置集合」是否等于期望的因果窗口 $[\max(0, p-W+1), p]$。

    观察重点：槽位序列是 $[4,5,6,7,0,1,2,3]$——它并不按位置递增排列，因为环形缓冲的物理顺序是「最旧到最新绕一圈」；但映射回位置后与期望窗口逐项相等。这说明槽位顺序与可见集是两件事。

    简化条件：单序列、单层、纯 Python 字典模拟；未涉及批量、chunked prefill 的分块边界，也未涉及缓存中的实际张量布局与精度。

    4.2 prefill 逐行、decode 整环

    同一份缓存，两种前向形态的索引方式不同[C4]：

    • prefill：一次处理 $N$ 个位置，每个 query 各需要一行可见槽位。实现按「位置减窗口再加偏移」算出每行的槽位下标，超出序列开头的部分填 $-1$。
    • decode：一次只有 1 个 query，它需要看到整个环。实现把槽位从「最旧」开始绕一圈列出，再对「位置还没写到」的槽位填 $-1$。

    两种形态列出的槽位顺序不同（prefill 每行按位置递增，decode 从最旧槽位绕一圈），但映射回位置后集合相同。实测：$W=128$、序列长 300 时逐位置比对，decode 槽位映射回的位置集合与 prefill 的因果窗口在全部 300 步一致；换成 $W=8$、序列长 20 的官方函数对照同样成立[N7]。顺序不影响结果，因为注意力实现把每个槽位独立处理（softmax 在同一组值上求和，与顺序无关）。

    4.3 位置编码用原序列位置

    最后一处易错点是位置。RoPE 的相位由位置决定，而环形缓冲里的槽位下标会重复使用，因此不能用槽位下标当位置。DeepSeek-V4.1-Flash 的做法是用原序列位置：实现统一取切片 freqs_cis[start_pos : start_pos + seqlen]——prefill 时 seqlen 等于本次处理的长度，decode 时 seqlen = 1，同一表达式自然取到 freqs_cis[start_pos : start_pos + 1][C5]。由于缓存里只有最近 $W$ 个位置，窗口内任意两个位置的相对距离不超过 $W$。

    作为对照，StreamingLLM 为了让「序列开头的汇聚点」与「最近的窗口」共处一个缓存，改用缓存内位置：把缓存里的位置重新编号成 $0,1,2,\dots$，而不是用它们在原文中的下标[C5]。两种口径的差别在需要跨越很远距离时显现：用原位置时，开头位置的相位差随序列增长而增大；用缓存内位置时，汇聚点被「拉近」到缓存开头。选择哪种取决于是否要把远处的汇聚点与近期窗口拼在同一个缓存里。

    本章问题

    1. 为什么 decode 时列出的槽位顺序与 prefill 不同，却不会影响结果？

      解答：集合相同且每个槽位独立处理，顺序只影响累加次序

      prefill 每行按位置递增列出可见槽位；decode 只有一行，按「最旧到最新」绕环列出。两者覆盖的位置集合相同（实测 300 步一致）。注意力对每个槽位算出分数后做 softmax 再加权求和，这个过程对槽位顺序不敏感：交换两个槽位只会改变浮点加法的次序，不会改变数学结果。真正会出错的是把「槽位下标」当成「位置」使用，那会改变 RoPE 相位与可见性判断。

    2. 如果窗口 KV 用槽位下标而不是原序列位置来加 RoPE，会发生什么？

      解答：相位会周期性重复，相同槽位的键在不同轮次被赋予同一位置

      槽位下标只有 $W$ 个取值，位置 $i$ 与 $i+W$ 会落在同一槽位、被赋予同一相位。于是模型无法区分「最近的第 $W$ 个位置」与「$2W$ 之前的那个位置」，相对距离信息被破坏，注意力的距离分辨能力退化成周期性的。因此实现必须用原序列位置（或用缓存内位置并接受相应的语义变化，如 StreamingLLM 为汇聚点所做的处理）。

    来源与范围说明

    论断与来源（C）

    [C1] Mistral 7B（Jiang et al., arXiv:2310.06825）§2「Sliding Window Attention」：「the hidden state in position i of the layer k, h_i, attends to all hidden states from the previous layer with positions between i−W and i. Recursively, h_i can access tokens from the input layer at a distance of up to W×k tokens」；「At each attention layer, information can move forward by W tokens. Hence, after k attention layers, information can move forward by up to k×W tokens.」

    [C2] 同上 §2「Rolling Buffer Cache」：「The cache has a fixed size of W, and the keys and values for the timestep i are stored in position i mod W of the cache. As a result, when the position i is larger than W, past values in the cache are overwritten, and the size of the cache stops increasing.」

    [C3] StreamingLLM（Xiao et al., arXiv:2309.17453）§1、Table 2 与 §3.1：§1「StreamingLLM simply keeps the attention sink tokens' KV (with just 4 initial tokens sufficing) together with the sliding window's KV」；Table 2 caption「(1) Window attention (0+y) has a drastic increase in perplexity.」（§3.1 对应表述为「it results in an exceedingly high language modeling perplexity」）与 §3.1「removing these initial tokens' KV will remove a considerable portion of the denominator in the SoftMax function in attention computation.」

    辅助解释与类比边界

    「层堆叠接力」是辅助解释：它说明信息每层前移 $W$、累计 $k\times W$，但不代表间接可见的信息保真度与直接可见相同——每层都要经过 softmax 加权混合，距离越远、路径越长，可恢复性越低。本页不量化这个衰减，只在使用 $k\times W$ 作为上限时说明它是上限。

    简化条件及其限制

    • 字节账只算窗口 KV（单序列、单层），不含压缩全局 KV、索引器缓存与压缩器跨步残态；这些项随 batch 与实现变化，不影响「窗口缓存与序列长度无关」这个结论。「40 层 2.50 MiB」指主干层，不含 3 个 DSpark 草稿层。
    • 1 B/元素取自技术报告 §2.4.4 的部署口径（「We retain FP8 for the SWA KV cache」）；参考实现里 act_quant(kv, fp8_block_size, scale_fmt, scale_dtype, True) 的 inplace=True 按 kernel 文档是 quant+dequant 回 BF16，其缓冲区实际占 2 B/元素（128 KiB/层），与本页按部署口径算出的 64 KiB 不同。本页描述的是部署时的 FP8 存储形态。
    • 复杂度按注意力打分次数计数，不含 softmax、值加权与投影开销；因此「少 8192 倍」指打分次数，不等于端到端延迟的倍数。全注意力一项按非因果 $N^2$ 计（与窗口的 $N\cdot W$ 不同口径），若改按因果全对计则为 $N(N+1)/2$。
    • 索引一致性复算覆盖 $W=8$ 与 $W=128$ 两种规模、单序列；未覆盖多 batch、chunked prefill 分块边界与张量并行切分。
    • 窗口取值的对照（Mistral 的 4096 与 DeepSeek-V4.1-Flash 的 128）只说明两者取值不同，不构成优劣判断——窗口大小与是否需要全局 KV、模型深度共同决定。
