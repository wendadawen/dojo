异构 PD 分离全链路

P 侧 NVIDIA 与 D 侧 AMD 的 attention backend、专家并行、网卡全不一样，KV 却能直接 RDMA 对拷。原因有两个：入口由 proxy 双投递、三层握手只交换元数据不动数据；传输层字节原样搬运，唯一硬条件是两侧 KV cache 布局逐字节相同。实测 KV 传输仅占端到端 0.12%，瓶颈在 decode。

更新于 2026-08-22 · 类型：部署实测归档

PD 分离（prefill/decode disaggregation，背景见另一篇笔记）把一次生成拆到两台机器：P 节点算完 prompt 的 KV cache 就交棒，D 节点拿着 KV 逐 token decode。实测环境两侧完全异构：

P（prefill）D（decode）
GPU8× NVIDIA RTX PRO 5000 72GB（Blackwell）8× AMD MI300X 192GB（ROCm）
attention backendHPC_ATTNHYVL_INT8_ATTN
专家并行 / 序列并发EP=2 / max-num-seqs=32EP=8 / max-num-seqs=64
RoCE 网卡命名mlx5_bond_*bnxt_re_bond*
connector / 角色MultiConnector(Flexible+Offloading)，kv_bothFlexibleConnector，kv_consumer

模型是 20B 级 MoE-VL（w8a8c8 量化），测试用例为一张 500×625 的 webp 图 + 「详细描述一下图像中的内容」，得到 362 个 prompt token（其中 340 个图像 token），生成 64 个 output token。传输组件为 FlexibleConnector + NIXL + Mooncake + RoCE。

1. 入口分发：proxy 按 request_id 双投递

请求入口不是任何一台 vLLM，而是跑在 P 节点上、独立于 vLLM 的 proxy（8000 端口）。proxy 把同一个 request_id 拆成两个请求投出去：给 P 的 max_tokens=1——只做 prefill、产出第一个 token；给 D 的 max_tokens=真实值，并在 kv_transfer_params 里带上 P 的控制面地址，D 由此知道去哪里等 KV。

必须打 proxy 8000，不能直接打 8021。打错的表现完全不同，而且都很隐蔽：

错误入口实际发生什么表现
直接打 P:8021P 单机跑完全部 token，PD 完全没参与request_decode_time_seconds=0、kv_transfer_e2e_time_ms=0、kv_transfer_params=null；返回结果完全正常，极易误判为 PD 已生效
直接打 D:8021 并手动塞 kv_transfer_paramsD 挂起等 KV，但没有 proxy 通知 P 做 prefill等满 120 s（VLLM_TRANSFER_TIME_OUT）后 KV transfer timeout，finish_reason=abort，只吐 1 个 token

2. 建连：三层握手

请求到来之前，两侧要把 RDMA 通路建好。整个过程没有中心注册（无 etcd/redis）——P 的地址由 proxy 在请求里带给 D；也没有心跳，靠 TCP 长连接保活。

第 1 层：Scheduler 间的 TCP 控制面

P 启动时在 VLLM_KV_META_BASE_PORT + dp_rank 上监听（实测端口 33981），登记为 kv_meta_addr。D 主动连过来，双方互发 (node_info, workers_info)，并校验 TP 兼容性、计算 compute_target_rank()。

node_info 是一个 15 字段的自我描述，其中三份信息分工明确：

信息内容是否参与 compat_hash
compat_manifest影响正确性的字段：dtype、kv_cache_dtype、block_size、head_size、num_hidden_layers、attn_quant_config 等是
capabilities异构字段：attention_backend、moe_backend、gpu_name、ep_size、max_num_seqs 等否（故意排除）
寻址与并行度kv_meta_addr、http_port、tp_size、total_num_kv_heads 等部分

设计意图：正确性必须一致（manifest 参与哈希），性能实现可以各异（capabilities 不参与）。正因为后者不入哈希，P 用 HPC_ATTN/EP=2、D 用 HYVL_INT8_ATTN/EP=8 才能共存。tp_size 与 total_num_kv_heads 另有用途：两侧 TP 不等时，靠它们把远程 block id 重映射（tp_ratio / head_offset）。

隐患在于 compat_hash 只收集、不强制。类注释明写「This method only gathers information; it does NOT enforce any validation」——哈希不匹配时只是可被观测，不会拦住启动。

第 2 层：NIXL agent 元数据交换（每个 TP rank 一对）

每个 worker 调 export_local_agent() 导出一个二元组，经第 1 层的 TCP 通道转发给对端，对端 import_remote_agent() 消化。TP=8，所以共 8 对 agent。scheduler 只做转发与配对，真正的 RDMA 握手发生在 worker 之间。

导出物内容性质
agent_metadataRDMA 建连凭证，不透明二进制 blob内部结构在 NIXL 库里，vLLM 只搬运不解析；按 RDMA 通用要素推测含 GID/QP/rkey（推断，未实证）
kv_mem_info显存位置清单，每条四元组：(起始地址, 总字节数, GPU 序号, layer_name)完全可实证；layer_name 只有 "ALL_LAYERS"（80 层打包成一块）

kv_mem_info 是同一个对象干两件事：交给 register_memory(..., "VRAM") 把显存注册给网卡（允许远程直接读写），同时发给对端声明「我的 KV cache 在哪、多大」。对端拿到后展开成 descriptor 列表：addr[i] = base_addr + i × 1351680。这就是 P 能算出「D 的第 N 个 block 落在哪个显存地址」的依据，建链时一次算好，请求时不再询问。

第 3 层：RoCE 网卡自动选路（异构的关键）

NIXL 走 Mooncake 后端时，创建 agent 前自动扫 /sys/class/infiniband，只保留满足三个条件的网卡：RoCE v2、IPv4 映射 GID、网卡 IP 不等于管控 IP（管理网卡没有到对端的 RoCE 通路）。筛选结果写进 MC_TE_FILTERS。两侧各筛出 8 张数据面网卡，正好对应 8 个 TP rank——尽管两边网卡命名体系完全不同（NVIDIA 的 mlx5_bond_* 与 AMD 的 bnxt_re_bond*）。

没有这份白名单时，Mooncake 会退化去用管理网卡，报 Process failed for slice；一张可用网卡都找不到时直接抛异常，代码注释的原话是「Failing loudly here beats a silent KV transfer timeout later」——宁可启动就响，不要事后静默超时。

3. 一次请求的完整时序

建连完成后，一次请求在数据面走五步：

  1. 双投递：proxy 把同一 request_id 分别发给 P（max_tokens=1）和 D（max_tokens=64）。
  2. D 分配 block 并告知 P：362 个 token 需要 6 个 block（每 block 64 slot，$6\times64=384 \geq 362$），D 把 block_ids 经控制面发给 P——相当于告诉 P「写到我的哪几个块」。
  3. P prefill：ViT 把图像编码为 [340, 4096]，拼进文本得到 [362, 4096]，过 80 层语言骨干，每层把 K/V 写进 KV cache，实测 ttft 约 150 ms。
  4. 入队发送：save_kv_layer() 把 block 放进发送队列。实测走 unified 模式——最后一层算完后一次发全部 block；layerwise 模式（设 VLLM_PD_LAYERWISE_THRESHOLD）可边算边传以隐藏延迟，未启用。
  5. RDMA WRITE + decode：P 主动把 6 个 block 写进 D 的显存（descriptor 建链时已预建，请求时只做索引，这是传输能压到毫秒级的原因之一），D 收到完成通知后开始 decode。

一组实测时序（前缀缓存命中，P 的 prefill 被部分跳过；关闭缓存的数据见第 7 节）：

时刻事件
15:54:03.902proxy → D 收到请求（max_tokens=64）
15:54:03.904proxy → P 收到同一 request_id（max_tokens=1）
15:54:04.017P prefill 完成，ttft=0.126 s，image_tokens=340
15:54:04.024D 侧日志 [Decode Worker] KV recv done

4. KV 的字节构成：1351680 是怎么来的

传输的最小单元是 block，一个 block 打包全部 80 层（cross-layer 模式，layer_name 只有 ALL_LAYERS 一个 key）。每个 block 恰好 1351680 字节，可由模型参数直接推导：

$$1351680 = \underbrace{2}_{K,V} \times \underbrace{64}_{\text{block\_size}} \times \underbrace{1}_{\text{KV head/rank}} \times \underbrace{132}_{128\ \text{head\_size} + 4} \times \underbrace{80}_{\text{层数}} = 16896\ \text{B/层} \times 80\ \text{层}$$
  • KV head 每 rank 1 个：模型 GQA 共 8 个 KV head（64 个 Q head 共享 8 个 KV head，8:1），TP=8 切下来每 rank 恰好 1 个。
  • 132 = 128 + 4：每行 128 字节数据加 4 个元素的 scale 尾部。K 的 scale 是动态值（per-token-per-head 量化，每 32 个 token 一组 fp32），必须随数据走，内嵌在 block 尾部；V 的 scale 是静态 per-head 值，直接从 checkpoint 的 _v_scale 读，不进 cache，槽位空置（约 3% 浪费）。
  • D 侧读取用零拷贝视图：split_hyvl_kv_cache() 把 (64, 132) reshape 成 (66, 128)——前 64 行是 KV 数据，后 2 行是 scale（64/32=2 组），不搬数据。

实测速率：关闭前缀缓存后单 rank 传输 8110080 B 用时 4.4 ms（约 1.70 GB/s，热路径）；冷路径 17.8 ms（约 0.42 GB/s）。日志中 GB/s 按 $10^9$ 基数计算。

5. 异构可行的条件与脆弱性

传输层不做任何格式转换——字节原样 RDMA WRITE，D 侧按自己的 backend 解释。所以两个不同的 backend 能直接对拷，不是碰巧，而是两侧独立算出了逐字节相同的 KV 布局：

P 侧 HPC_ATTND 侧 HYVL_INT8_ATTN
get_kv_cache_shape()(nb, 2, block_size, num_kv_heads, head_size + padded)(nb, 2, block_size, num_kv_heads, head_size + K_SCALE_BYTES)
尾部字节数动态算（见下）固定 4（K_SCALE_BYTES）
代入结果(nb, 2, 64, 1, 132)(nb, 2, 64, 1, 132) — 相同

P 侧的尾部字节数由 _fp8_per_head_scale_elems_padded() 计算：

$$\text{raw} = 4,\qquad \text{unit} = \frac{\text{head\_size}}{\gcd(\text{block\_size},\ \text{head\_size})},\qquad \text{elems} = \left\lceil \frac{\text{raw}}{\text{unit}} \right\rceil \times \text{unit}$$

约束来自零拷贝 reshape：cache 按 (block_size, head_size+elems) 分配、运行时 reshape 成 (pad_total_rows, head_size)，元素总数必须守恒，所以 elems × block_size 必须能被 head_size 整除。代入 block_size=64、head_size=128：$\gcd(64,128)=64$，unit = 2，elems = 4——与 D 侧固定值恰好一致，两侧每层每 block 同为 16896 B。

这个一致是脆弱的、靠参数组合碰上的。反例：head_size=192、block_size=64 时 $\gcd=64$、unit=3、elems=6 $\neq$ 4，两侧布局就不再匹配；而第 2 节说过 compat_hash 只报告不阻止——布局错配会变成静默的数据损坏风险，只能在观测侧发现。

另有两处「允许不同」：一是 block_stride，P 若走 cross-layer split KV 则 stride=2，D 的 backend 不 split 则 stride=1，两侧各用各自的 stride 计算索引（descriptor 长度建链时已按对端参数算好）；二是 D 侧代码注释明确 HYVL_INT8_ATTN 不能加进 K/V-outer 布局的 backend 集合——它是 NHD 序且 scale 内嵌在每个 head 尾部，属于另一套布局约定。

6. 失败路径与可观测点

场景行为
NIXL 传输失败check_xfer_state(handle) != "DONE" → 记 error、加入 failed_agents、尝试 reconnect_remote_agent()；重连失败则该 agent 置 None 后续跳过
D 收不到 KVscheduler 检查 VLLM_TRANSFER_TIME_OUT（默认 120 s）超时 → 广播 kv_timeout → worker 清理待发送块 → 请求 abort
P 侧 prefill 失败主动发 prefill_failed 通知 D，D 立即释放请求，不用等满 120 s
kv_load_failure_policy 不一致P 配了 recompute 但 D 启动命令没给该参数、实际生效 fail → D 没有 recompute 兜底，拿不到 KV 只能超时 abort

7. 实测结论：传输不是瓶颈

关掉前缀缓存后的干净数据（cached_tokens=0，362 prompt / 64 output）：

阶段耗时占比
proxy 分发 + P prefill约 150 ms4%
KV RDMA 传输4.4 ms0.12%
D decode（64 token @ 17.3 tok/s）3.48 s96%

两个佐证：前缀缓存命中与关闭两次请求的 KV 字节数完全相同（都是 8110080 B）——block 数只取决于 token 数（362 → 6 blocks），缓存只省 P 的计算，不改变传什么；单请求吞吐上，走 PD（20.3 tok/s）比 D 本机跑全程（23.5 tok/s）略慢，因为 PD 模式下 D 每步只算 1 个 token 的 decode，固定开销占比更高。

所以这套架构的收益不在省传输，而在让 P 和 D 各自跑满：P 用大批量（max-num-batched-tokens=32768）做计算密集的 prefill，D 用大并发（max-num-seqs=64）做访存密集的 decode，两者互不干扰，消除 prefill 长 forward 阻塞 decode token 流的问题（TTFT 与 TPOT 不再互相拖累）。多请求并发下的整体吞吐才是 PD 的收益所在，单请求对比体现不出来。

复现要点

  • 入口必须走 proxy 的 8000 端口，不要直连任一侧的 8021。
  • 关前缀缓存两侧注入方式不同：一侧写系统 environment 文件即可生效（启动脚本经 ssh bash -l 拉起、只透传白名单变量，但 ssh 层会 source 它）；另一侧的启动脚本 source 的平台环境文件里硬编码 VLLM_ENABLE_PREFIX_CACHING="1" 且只读，只能在 source 之后再 export 覆盖。
  • 验证 PD 生效：两侧分别 grep KV send done / KV recv done。
  • 重启前确认显存归零（NVIDIA 侧 nvidia-smi --query-gpu=memory.used，AMD 侧 rocm-smi），否则 OOM；清残留进程时不要用 pkill -f "VLLM::" 全局名字匹配——会误伤平台管控进程（实测曾把一台节点打成不可达），应先定位 vllm serve 主进程再按进程树 kill。
