KV cache 布局（NHD/HND）

同一份 KV cache 的两种显存排法：NHD 让写入零转置，HND 让单头整页连续——写读诉求相反，布局选择跟随瓶颈。

更新于 2026-09-03

定位摘要

KV cache 布局（NHD 与 HND）描述的是同一份缓存数据在显存里的排列顺序，不是新的数据格式。KV cache 的三个维度——token 数、KV 头数、每头维度——谁排在外层、谁排在内层，就是布局的全部内容：NHD 按 (token, 头, 维) 排，同一 token 的所有头连续；HND 按 (头, token, 维) 排，同一头的整页 token 连续。

问题背景

写路径和读路径对“谁应该连续”的诉求相反：注意力的投影输出天然是 NHD（写入零转置），而 attention 读取时按（头， 全部历史 token）取数——HND 让单头整页连成一段。两种布局因此并存，选择跟随瓶颈在哪一侧。

核心机制

  • 三个维度：$N$（token 数）、$H_{\mathrm{kv}}$（KV 头数，GQA 下少于查询头数）、$d$（每头维度）。分页形式下 NHD 形状为 $(n_{\text{page}}, p, H_{\mathrm{kv}}, d)$，HND 为 $(n_{\text{page}}, H_{\mathrm{kv}}, p, d)$。
  • 写入偏好 NHD：投影输出 $XW_K$ 的形状是 $(N, H_{\mathrm{kv}} \cdot d)$，行主序下每行恰为一个 token 的全部头数据，reshape 即 NHD、零转置；decode 追加写落进一段连续槽位。
  • 读取偏好 HND（特定场景）：单头取一页的传输单元从 NHD 的 $d$ 个元素（fp16、$d=128$ 时 256 B）变成 HND 的一整段 $p \cdot d$ 个元素（$p=32$ 时 8 KB）。收益集中在低精度（fp8/nvfp4）的 trtllm-gen kernel——其 API 默认 kv_layout="HND"、NHD 会触发转置拷贝——以及页级大块搬运（offload、换入换出）。FreeKV 甚至两侧各用一种：GPU 用 NHD、CPU 用 HND，只在 offload 一页时转置一次。
  • vLLM 的实现：布局是同一块显存的视图属性——逻辑形状恒为 $[L, B, H, N, C]$，KVCacheLayout 枚举值是 stride 置换（LBNHC 即 NHD、LBHNC 即 HND），切换不复制数据。布局在 engine core 解析一次：各注意力后端声明偏好列表取交集，环境变量 VLLM_KV_CACHE_LAYOUT 可显式指定；默认偏好 NHD 排第一。
  • SM100（Blackwell）强制 head-major：trtllm-gen kernel 只消费 head-major（头维排在外层，即 HND 类）的块内布局，FlashInfer 后端因此只声明 (LBHNC, BLHNC)——SM100 上布局必然解析为 HND 类即来源于此。

关键结论与边界

  • fp16 常规推理下两种布局性能差异不显著（FlashInfer 实践表述），默认选择仍是 NHD；HND 不是普遍升级，是被低精度 kernel 与页级搬运选中的排法。
  • 切换布局不复制数据：它只是同一 storage 配不同 stride 的两个视图，写入 kernel 内部用视图 transpose 适配。
  • “HDN”不是标准命名，业界只有 NHD 与 HND，字母顺序即维度顺序。
  • 碎片要分两层：分配碎片由分页解决，布局只决定页内访问的碎片；vLLM 细节基于 2026-09-03 的 main 分支（RFC #42082 形状体系），更早版本（如 v0.13.0）用每层独立 buffer 加 permute 置换，机制同源。
