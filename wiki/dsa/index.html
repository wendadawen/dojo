    DeepSeek Sparse Attention（DSA）：只读最相关的 k 个位置

    主要依据：arXiv:2512.02556《DeepSeek-V3.2: Pushing the Frontier of Open Large Language Models》（2025-12-02 提交版 LaTeX 源码）、DeepSeek-V3.2-Exp 官方开源推理实现（HuggingFace，commit 194c67e）、vLLM 实现（commit 5ac2684）

    一个模型已经读进 128K token 的上下文，现在要生成第 128001 个 token。这一步里，注意力要把新 token 的查询与前面 128000 个位置逐一比对，算出 128000 个分数，再按分数加权求和。下一个 token 到来时，这件事从头再做一遍——而且这次是 128001 个位置。

    问题不在于这些计算做错了什么，而在于其中绝大部分位置对当前这一步几乎没有贡献。DeepSeek Sparse Attention（DSA）针对的正是这件事：先用一个成本极低的打分器给历史中每个位置评一个相关性分数，只让分数最高的 $k$ 个位置参与完整的注意力计算。主注意力的代价因此从"与序列长度平方成正比"变成"与序列长度成正比"。

    读完你能回答

    • 长上下文为什么必须动注意力，滑动窗口和线性注意力为什么不是同一条路？

    • top-k 选择如何接回主注意力，为什么所有注意力头必须读同一批位置？
    • indexer 的打分能力从哪来，为什么需要两个阶段的续训？
    • DSA 省下了什么、没省下什么，什么情况下它完全不起作用？

    进入本页前需要的基础：注意力机制中 query（查询向量，代表"当前位置想找什么"）、key（键向量，代表"每个历史位置提供什么"）、value（值向量，代表"取用时实际读到的内容"）三者的分工，以及"多头"的含义（同一层里并行跑多套 query/key/value 投影，各自关注不同模式）。这些在标准注意力概念页有完整讲解，不熟悉的话建议先读那一页。

    下面先把代价的结构说清楚——只有知道钱花在哪里，才能判断该砍哪一刀。

    长上下文里，注意力的代价长在哪里

    标准的稠密注意力规定：每个位置的查询要和它之前的每一个位置比对一次。序列里第 1 个位置只有 1 个对象可比，第 2 个有 2 个，第 8 个有 8 个。把 8 个位置的比对次数加起来是 $1+2+\cdots+8 = 36$ 次。

    把序列翻倍到 16 个位置，比对次数变成 $1+2+\cdots+16 = 136$ 次。长度翻了 1 倍，工作量涨了将近 4 倍。写成一般形式，长度 $L$ 的序列需要 $L(L+1)/2$ 次配对，量级是 $O(L^2)$。这就是"平方"的含义：序列每长一点，代价涨得比长度本身快得多。

    推理时这件事还有第二层。生成阶段每次只产生一个新 token，它的查询要和全部历史位置比对，因此每生成一个 token 都要把整个 KV cache（缓存下来的历史 key/value 条目）从显存里读一遍。128K 上下文下这是每步都要搬动的大块数据，瓶颈往往不在算得快不快，而在数据搬不搬得过来。

    这里要区分两种"让注意力更快"。FlashAttention 一类的工作改的是怎么算——通过分块和减少显存往返，让同一批计算跑得更快，算出的结果与朴素实现完全一致，读的仍是全部位置。本页讨论的是另一件事：能不能少读。两者互不冲突，可以叠加。

    两条减负路线，以及 DSA 选的那条

    既然要少读，就得决定读哪些。这里有两条方向完全不同的路。

    路线一：按位置固定地砍。最典型的是滑动窗口——只看最近的若干个位置，更早的一律不看。它便宜且实现简单，但代价直接：窗口之外的信息不是被降权，是被彻底丢掉。如果关键信息恰好在很远的位置（长文档问答里这是常态），窗口方案就失效了。

    路线二：换掉注意力本身的形式。线性注意力及其现代变体（如 KDA）不再为每个位置保留一份 KV 条目，而是把历史压进一个固定大小的状态里递推。代价随长度线性增长，KV cache 也不再随长度膨胀，但换来的是精确检索能力的损失——固定大小的状态无法无损保留任意长历史里的任意细节。

    DSA 走的是第三条：保留 softmax 注意力的完整形式，只减少每个查询实际读取的位置数，并且让"读哪些"由内容决定而不是由位置决定。被选中的位置照旧做完整的注意力计算，因此精确检索能力保留；没被选中的位置这一步不参与，因此代价下降；而选择依据是学出来的相关性分数，所以很远处的关键位置照样能被选中。

    在贯穿例子上看这个差别。假设 8 个位置里，与当前查询真正相关的是第 2 和第 7 个位置（分数的具体算法下一章给出）：

    方案第 8 个位置读取的位置读取数量关键信息是否保留
    稠密注意力1, 2, 3, 4, 5, 6, 7, 88全部保留
    滑动窗口（最近 3 个）6, 7, 83第 2 个位置丢失
    DSA（$k=3$）2, 7, 83保留，代价是放弃了低分的第 6 个位置

    三种方案的读取数量对比说明了 DSA 的取向：读取量与滑动窗口相同，但选中的是"分数高的"而非"位置近的"。滑动窗口丢掉了远处的第 2 个位置，DSA 保留了它，代价是放弃了近处但低分的第 6 个位置。

    "由内容决定"是 DSA 与固定模式稀疏的分界线，也是它的成本所在：必须先给每个位置算出一个分数，才知道该选谁。这个打分器本身若不够便宜，省下的计算就被它自己吃掉了。

    lightning indexer 如何用极低成本给每个位置打分

    打分器的任务比主注意力轻得多。主注意力算出的分数要直接用作加权系数，参与最终输出的构造，因此精度要求高。打分器只需要给出一个排序：谁比谁更值得读。排序对数值误差的容忍度远高于加权求和，这就是它能被大幅简化的空间。

    DSA 的打分器叫 lightning indexer（闪电索引器）。它给查询 token $\mathbf{h}_t$ 与它之前的 token $\mathbf{h}_s$ 算一个 index score：

    $$I_{t, s} = \sum_{j=1}^{H^I} w_{t, j}^I \cdot \mathrm{ReLU}\left(\mathbf{q}^{I}_{t, j} \cdot \mathbf{k}^{I}_{s}\right)$$
    • $t$：当前查询 token 的位置；$s$：被打分的历史位置。论文的表述是"在 $t$ 之前的 token"；官方实现的因果掩码用 triu_(1) 从对角线上方开始屏蔽，对角线本身不屏蔽，因此 $s$ 实际取遍 $t$ 之前的位置以及 $t$ 自身。本页按实现口径处理，贯穿例子中当前位置 8 也参与打分。
    • $H^I$：indexer 的头数。这是 indexer 自己的头，与主注意力的头无关。
    • $j$：indexer 头的索引，从 1 取到 $H^I$。
    • $\mathbf{q}^I_{t,j} \in \mathbb{R}^{d^I}$：indexer 第 $j$ 头在位置 $t$ 的 query 向量，由 $\mathbf{h}_t$ 导出，$d^I$ 是 indexer 每头的维度。
    • $\mathbf{k}^I_s \in \mathbb{R}^{d^I}$：位置 $s$ 的 indexer key，由 $\mathbf{h}_s$ 导出。注意它不带头下标——全部 indexer 头共用同一个 $\mathbf{k}^I_s$。
    • $w^I_{t,j} \in \mathbb{R}$：第 $j$ 头的标量权重，也由 $\mathbf{h}_t$ 导出，决定这个头的意见在总分里占多少比重。
    • $\mathrm{ReLU}(x) = \max(x, 0)$：把负的点积截成 0。

    这个式子是定义式，不是推导结论，因此不展开推导。理解它的方式是代入算一遍：每个 indexer 头拿自己的 query 与该位置的 key 做点积，负值截成 0，再按各头的权重加权求和，得到这个位置的总分。

    在贯穿例子上手算

    教学示例。取 $H^I = 2$、$d^I = 2$，当前查询在位置 8。indexer 的两个 query 向量与两个头权重是

    $$\mathbf{q}^I_{8,1} = (1, 0),\quad \mathbf{q}^I_{8,2} = (0, 1),\quad w^I_{8,1} = 1.0,\quad w^I_{8,2} = 0.5$$

    这样取是为了让点积一眼可算：头 1 只看 key 的第一维，头 2 只看第二维。8 个位置的 indexer key 与算出的分数：

    $s$$\mathbf{k}^I_s$头 1 点积ReLU 后头 2 点积ReLU 后$I_{8,s}$
    1$(2, 0)$$+2.00$2.00$0.00$0.002.00
    2$(1, 3)$$+1.00$1.00$+3.00$3.002.50
    3$(-1, 0.5)$$-1.00$0.00$+0.50$0.500.25
    4$(0.5, -2)$$+0.50$0.50$-2.00$0.000.50
    5$(0, 0)$$0.00$0.00$0.00$0.000.00
    6$(0.5, 0.5)$$+0.50$0.50$+0.50$0.500.75
    7$(2, 4)$$+2.00$2.00$+4.00$4.004.00
    8$(1, 4)$$+1.00$1.00$+4.00$4.003.00

    以 $s=2$ 为例代入：头 1 得 $(1,0)\cdot(1,3) = 1$，头 2 得 $(0,1)\cdot(1,3) = 3$，两者都为正无需截断，加权得 $1.0 \times 1 + 0.5 \times 3 = 2.5$。

    位置 3 和位置 4 展示了 ReLU 的作用。$s=3$ 在头 1 上点积为 $-1$，被截成 0，最终分数只由头 2 贡献；$s=4$ 反过来。ReLU 的效果是：某个头认为该位置"负相关"时，这个头不会把总分往下拉，只是不投赞成票。

    剩余六个位置的完整代入过程

    教学示例，全部数字人为构造。

    $s=1$：头 1 $(1,0)\cdot(2,0) = 2$，ReLU 后 2；头 2 $(0,1)\cdot(2,0) = 0$，ReLU 后 0。总分 $1.0\times 2 + 0.5\times 0 = 2.00$。

    $s=3$：头 1 $(1,0)\cdot(-1,0.5) = -1$，ReLU 截成 0；头 2 $(0,1)\cdot(-1,0.5) = 0.5$，ReLU 后 0.5。总分 $1.0\times 0 + 0.5\times 0.5 = 0.25$。

    $s=4$：头 1 $(1,0)\cdot(0.5,-2) = 0.5$，ReLU 后 0.5；头 2 $(0,1)\cdot(0.5,-2) = -2$，ReLU 截成 0。总分 $1.0\times 0.5 + 0.5\times 0 = 0.50$。

    $s=5$：两个头点积都是 0。总分 0.00。这个位置对当前查询没有任何相关性信号。

    $s=6$：头 1 $(1,0)\cdot(0.5,0.5) = 0.5$；头 2 $(0,1)\cdot(0.5,0.5) = 0.5$。总分 $1.0\times 0.5 + 0.5\times 0.5 = 0.75$。

    $s=7$：头 1 $(1,0)\cdot(2,4) = 2$；头 2 $(0,1)\cdot(2,4) = 4$。总分 $1.0\times 2 + 0.5\times 4 = 4.00$，是全部位置中最高的。

    $s=8$：当前 token 对自身打分。头 1 得 1，头 2 得 4，总分 $1.0\times 1 + 0.5\times 4 = 3.00$。

    便宜来自五处

    论文明确指出，由于 lightning indexer 头数少且可以在 FP8 下实现，其计算效率非常突出（C6）。把便宜的来源拆开看，一共五处：

    来源indexerV3.2 的主注意力
    头数$H^I = 64$128 个注意力头
    每头维度$d^I = 128$latent 512 维 + rope 64 维
    激活函数 / 归一化方式ReLU（逐元素，无需跨序列归一化）softmax（需沿序列维归一化）
    精度可在 FP8 下计算论文只声称 indexer 可 FP8 实现，未给出主注意力的精度对照
    输出每对 token 一个标量分数还要用分数去加权聚合 value

    关于 ReLU，论文给出的理由是"出于吞吐考虑"（C5），没有进一步展开。教学解释：softmax 需要先在整行上求指数和才能得出任何一个归一化结果，是一个跨全序列的规约操作；ReLU 逐元素独立，不需要这类规约。这一解释只用于说明两种运算在实现结构上的差别，论文本身未给出这个论证。

    便宜不等于复杂度降低。indexer 仍然要给每个查询扫过全部历史位置，复杂度依旧是 $O(L^2)$。它改变的是每一对 token 的单价，不是配对的数量。这一点在最后一章会重新算账。

    top-k 选择，以及候选集为什么必须跨头共享

    有了每个位置的分数，选择这一步很直接：取分数最高的 $k$ 个位置，只让这些位置的 key-value 条目参与注意力。论文把这个组件称为 fine-grained token selection mechanism（细粒度 token 选择），本页在提到它时也会用"top-k 选择"这个更短的说法，两者指同一件事：

    $$\mathbf{u}_t = \mathrm{Attn}\left(\mathbf{h}_t, \left\{ \mathbf{c}_s \mid I_{t, s} \in \mathrm{Top\text{-}k}\left(I_{t, :}\right) \right\}\right)$$
    • $\mathbf{c}_s$：位置 $s$ 的 key-value 条目。在 V3.2 中它是 MLA 的 latent 向量。
    • $\mathrm{Top\text{-}k}(I_{t,:})$：$I_{t,:}$ 这一行分数里最大的 $k$ 个。
    • $\mathbf{u}_t$：位置 $t$ 的注意力输出。
    • $k$：选取的位置数。V3.2 中 $k = 2048$。注意区分：这个斜体 $k$ 表示数量，而 key 向量一律写作 $\mathbf{k}^I_s$。

    接回贯穿例子。上一章算出的 8 个分数按降序是 $s=7$（4.00）、$s=8$（3.00）、$s=2$（2.50）、$s=1$（2.00）、$s=6$（0.75）、$s=4$（0.50）、$s=3$（0.25）、$s=5$（0.00）。取 $k=3$ 得到选中集合 $\{2, 7, 8\}$——这正是第二章表格里 DSA 那一行的来源。

    实现上，这个"只对选中位置做注意力"通常通过掩码达成：官方推理实现构造一个掩码张量，把未选中位置置为 $-\infty$，加到注意力分数上再做 softmax（$e^{-\infty} = 0$，这些位置的权重变成 0）。数学结果与"只对 $k$ 个位置计算"一致，但要注意这只是参考实现的表达方式——掩码版本仍然把全部位置算了一遍，真正的性能收益要靠专门的稀疏注意力 kernel 才能拿到。

    为什么所有头读同一批位置

    按"多头注意力各头关注不同模式"的直觉，似乎应该让每个头各选自己的 top-k。DSA 没有这么做：该 token 的全部 query 头共享同一个候选集。

    原因是 kernel 效率。论文引用 NSA 指出，在 kernel 层面每个 key-value 条目必须被多个 query 共享才能保证计算效率（C4）。如果每个头独立选择，一个 token 就会产生多套互不相同的不规则位置列表，显存访问模式随之碎片化——而稀疏计算的收益本来就依赖于把分散的读取整理成规整的批量访问。

    每头独立选择（DSA 没有采用）
  头 1 ──► 读位置 {2, 7, 8}   ┐
  头 2 ──► 读位置 {1, 3, 7}   ├─ 每头一套不同的访存模式
  头 3 ──► 读位置 {2, 5, 6}   ┘   同一位置被反复零散读取

共享候选集（DSA 的做法）
  indexer ──► 一套位置 {2, 7, 8}
                    │
        ┌───────────┼───────────┐
      头 1        头 2        头 3   ── 全部头读同一批条目
                                        一次读取，多个 query 复用

    论文把这两件事分成两层来讲。选择 MLA 作为承载 DSA 的注意力，理由是续训——V3.2 是从 V3.1-Terminus 继续训练而来，沿用原有的 MLA 是前提。而在 MLA 内部选用 MQA 模式，理由才是上面说的 kernel 层约束：MQA 模式下一个 latent 向量本就被该 token 的全部 query 头共享，与"共享候选集"的要求天然吻合。

    这是一处算法设计被硬件约束反向决定的例子。"每头独立选择"在表达能力上不会更差，但它在 kernel 上跑不快，因此没有被采用。

    indexer 的打分能力是训出来的

    前面一直假设 indexer 能打出有意义的分数。但 indexer 是新增的参数模块——$\mathbf{q}^I$、$\mathbf{k}^I$、$w^I$ 的投影矩阵都是新权重。随机初始化时它打出的分数与相关性毫无关系，此时做 top-k 等于随机丢掉大部分历史位置。

    所以 DSA 不能直接加到一个训练好的稠密模型上。DeepSeek 的做法是从 V3.1-Terminus 的一个已扩展到 128K 上下文的 base checkpoint 出发，做两个阶段的续训。

    阶段一：dense warm-up，让 indexer 学会模仿主注意力

    这一阶段的思路是：主注意力已经训练好了，它对每个位置的注意力分数本身就代表了"哪些位置重要"这一判断。让 indexer 去拟合这个已有的判断，就得到了一个有意义的初始打分器。

    具体做法是保持稠密注意力不变，冻结除 lightning indexer 外的全部模型参数。目标分布这样构造：对第 $t$ 个查询 token，先把主注意力分数跨全部注意力头求和，再沿序列维度做 L1 归一化，得到 $p_{t,:} \in \mathbb{R}^{t}$。然后用 KL 散度作为 indexer 的训练目标：

    $$\mathcal{L}^{I} = \sum_t D_{\mathrm{KL}}\left(p_{t,:} \,\|\, \mathrm{Softmax}\left(I_{t,:}\right)\right)$$

    KL 散度衡量两个概率分布的差异，此处的作用是把 indexer 分数经 softmax 后的分布拉向目标分布 $p_{t,:}$。注意 indexer 在推理时用 ReLU 而不用 softmax；softmax 只出现在训练损失里，用于把分数转成可与 $p_{t,:}$ 比较的分布。

    目标分布 $p_{t,:}$ 的构造过程（教学示例数字）

    教学示例，主注意力分数为人为构造。假设主注意力有 4 个头，对 8 个位置的注意力分数分别为：

    头 1：$(0.30, 0.05, 0.02, 0.03, 0.05, 0.10, 0.25, 0.20)$
    头 2：$(0.10, 0.30, 0.05, 0.02, 0.03, 0.05, 0.25, 0.20)$
    头 3：$(0.05, 0.25, 0.05, 0.05, 0.05, 0.10, 0.25, 0.20)$
    头 4：$(0.15, 0.20, 0.03, 0.02, 0.05, 0.05, 0.30, 0.20)$

    第一步，跨头逐位置求和。位置 1 得 $0.30+0.10+0.05+0.15 = 0.60$，位置 2 得 $0.05+0.30+0.25+0.20 = 0.80$，依此类推，8 个位置的和为

    $(0.60,\ 0.80,\ 0.15,\ 0.12,\ 0.18,\ 0.30,\ 1.05,\ 0.80)$

    第二步，沿序列维做 L1 归一化。总和为 $0.60+0.80+0.15+0.12+0.18+0.30+1.05+0.80 = 4.00$，逐项除以 4.00 得目标分布

    $p_{8,:} = (0.1500,\ 0.2000,\ 0.0375,\ 0.0300,\ 0.0450,\ 0.0750,\ 0.2625,\ 0.2000)$

    各项之和为 1.0，是一个合法的概率分布。位置 7 的目标概率最高（0.2625），位置 4 最低（0.0300）——KL 损失要让 indexer 的分布呈现同样的相对高低关系。

    阶段二：sparse training，让整个模型适应稀疏

    indexer 有了初始能力后，引入细粒度 token 选择，并放开全部模型参数一起优化，让模型适应 DSA 的稀疏模式。indexer 仍继续对齐主注意力分布，但这次只在被选中的集合上计算：

    $$\mathcal{L}^{I} = \sum_t D_{\mathrm{KL}}\left(p_{t,\mathcal{S}_t} \,\|\, \mathrm{Softmax}\left(I_{t,\mathcal{S}_t}\right)\right), \quad \mathcal{S}_t = \left\{ s \mid I_{t,s} \in \mathrm{Top\text{-}k}\left(I_{t,:}\right) \right\}$$

    其中 $\mathcal{S}_t$ 是位置 $t$ 选中的位置集合。KL 的作用域从"全部位置"收窄到"选中的位置"，因为未被选中的位置不参与注意力，它们的相对排序不再影响输出。

    这一阶段还有一处关键安排：indexer 的输入从计算图上 detach，以便独立优化。indexer 的训练信号只来自 $\mathcal{L}^I$，主模型的优化只依据语言建模损失（C10）。两条梯度路径互不干扰。

    工程落地：从 hidden state 到稀疏注意力的完整链路

    前面讲的是机制。这一章看它在真实推理实现中由哪些部件构成。本章内容以 DeepSeek 官方开源推理实现与 vLLM 实现为依据，属于实现层事实，论文正文未涉及这些细节。

    前向链路

    从 hidden state 出发，先分出三条投影：

    hidden state h
  │
  ├─ wq_a + q_norm ──► qr（query 低秩 latent）
  │                     │
  │                     ├──► 主注意力自己的 q 投影 ──► q
  │                     │
  │                     └──► wq_b(qr) ──► q^I（64 头 × 128 维）
  │
  ├─ wk(h) + k_norm ──► k^I（不分头，128 维）
  │
  └─ wkv_a ──► KV latent ──► 主 KV cache

    其中 q 与主 KV cache 归主注意力，q^I 与 k^I 归 indexer。indexer 拿到这两样后的处理是一条直线：

    q^I, k^I
  │
  ▼
RoPE（只对前 64 维施加，非 interleaved）
  │
  ▼
Hadamard 变换（rotate_activation）
  │
  ▼
量化到 FP8 ──► k^I 写入 indexer 自己的 k_cache（FP8 值 + scale）
  │
  ▼
FP8 index kernel ──► index score I（每个位置一个标量）
  │
  ▼
top-k 选择 ──► topk_indices（选中的位置）

    最后两路汇合，主注意力只按 indexer 给出的位置去读自己的 KV cache：

    q + 主 KV cache + topk_indices
  │
  ▼
稀疏 MLA
  │
  ▼
注意力输出 u

    图中各节点的含义：wq_a 与 q_norm 产出 query 的低秩 latent qr，主注意力和 indexer 都从它出发再各投影一层（前者用自己的 q 投影，后者用 wq_b）；wk 是 indexer 专有的 key 投影，k_norm 是作用在 indexer key 上的 LayerNorm；wkv_a 产出主注意力的 KV latent。竖线与箭头表示前向传播方向。要注意的是 indexer 一路最终只输出一件东西——选中的位置；它不参与输出的加权计算。

    链路中有三处值得单独说明。

    indexer 使用独立的 RoPE 通道与独立的 key。indexer 的 key 由 hidden state 重新投影得到（wk(x) 再经 k_norm），与主注意力的 key 无关；indexer 的 query 则由主注意力的 query 低秩 latent qr 再投影一层（wq_b(qr)）得到，这一段与主注意力共用。两者随后各自施加 RoPE，且官方实现中有两处注释明确写着 indexer 的 rope 不是 interleaved 的，与主注意力的应用方式不同（C12）；vLLM 同样为 indexer 单独构造了一份 rope 模块。也就是说，indexer 的独立性体现在 key 投影、RoPE 通道与 key cache 三处，query 一侧则复用了主注意力已经算出的低秩 latent。

    量化前做一次 Hadamard 变换。官方实现在把 q、k 量化到 FP8 之前调用 rotate_activation，即一次带 $1/\sqrt{d}$ 缩放的 Hadamard 变换（C13）。教学解释：这类变换会把向量中的异常大值能量摊到各维度上，减少低精度量化的误差——这是低精度计算中的常见预处理。需要说明的是，这个动机是推断，官方代码只给出了实现，没有说明理由。

    indexer 有自己的一份 key cache。官方实现为 indexer 注册了独立的 k_cache（FP8）与 k_scale_cache；vLLM 中对应一个独立的 DeepseekV32IndexerCache。它与主 KV cache 并存，两者互不复用。

    FP8 index kernel 的四步

    index score 的实际计算由一个专用 FP8 kernel 完成。官方实现的 docstring 把计算链写成四步（C6）：

    index kernel 的四步计算链（伪代码） 
    以下是伪代码，不是 Python。对应官方 fp8_index 的计算链。

输入：q（FP8，形状 [batch, m, h, d]）        —— indexer query，h 个头、d 维
      q_s（FP32，形状 [batch, m, h]）        —— 已折叠了 w^I 与缩放因子的每头权重
      k（FP8，形状 [batch, n, d]）           —— indexer key，不分头
      k_s（FP32，形状 [batch, n]）           —— key 侧的量化 scale
状态：logits（FP32，形状 [n_block, h]）
输出：index_score（FP32，形状 [batch, m, n]）

步骤 1：FP8 矩阵乘
    logits ← q @ kᵀ                      对应公式中的 q^I_{t,j} · k^I_s

步骤 2：ReLU 后乘 query 侧权重
    对每个 (头 j, 位置 s)：
        logits[s, j] ← max(logits[s, j], 0) × q_s[j]
                                         对应 w^I_{t,j} · ReLU(·)

步骤 3：沿头维求和
    logits_sum[s] ← Σ_j logits[s, j]     对应公式中的 Σ_{j=1}^{H^I}

步骤 4：乘 key 侧量化 scale
    index_score[s] ← logits_sum[s] × k_s[s]
                                         把 FP8 量化的比例还原回真实数值

    四步与公式的对应关系是直接的：步骤 1 是点积，步骤 2 是 ReLU 与加权，步骤 3 是对头求和。步骤 4 没有出现在公式里——它属于 FP8 量化的还原，把量化时除掉的比例乘回来。另一处实现与公式的差别是：$w^I_{t,j}$ 在实现中被额外乘上了 $1/\sqrt{H^I}$ 与 softmax 缩放因子，然后合进 q_s，这属于实现层的缩放约定。

    用 numpy 复现 index score 与 top-k（验证前面的手算） 
    import numpy as np

# 教学示例：8 个位置的序列，第 8 个位置是当前 query。
# H_I = 2 个 indexer 头，d_I = 2 维，k = 3。

# q^I_{8,j}：indexer 第 j 头在位置 8 的 query 向量（由 h_8 导出）
q_indexer = np.array([
    [1.0, 0.0],   # j = 1
    [0.0, 1.0],   # j = 2
])

# w^I_{8,j}：第 j 头的标量权重（同样由 h_8 导出）
w_indexer = np.array([1.0, 0.5])

# k^I_s：位置 s 的 indexer key，全部 indexer 头共用同一个 k^I_s
k_indexer = np.array([
    [2.0,  0.0],   # s = 1
    [1.0,  3.0],   # s = 2
    [-1.0, 0.5],   # s = 3
    [0.5, -2.0],   # s = 4
    [0.0,  0.0],   # s = 5
    [0.5,  0.5],   # s = 6
    [2.0,  4.0],   # s = 7
    [1.0,  4.0],   # s = 8
])

# 按 F1 逐位置计算 index score
index_scores = []
for s in range(8):
    per_head = []
    for j in range(2):
        dot = float(q_indexer[j] @ k_indexer[s])
        relu = max(dot, 0.0)
        per_head.append((dot, relu))
    score = sum(w_indexer[j] * per_head[j][1] for j in range(2))
    index_scores.append(score)
    print(
        f"s={s + 1}  "
        f"head1: dot={per_head[0][0]:+.2f} relu={per_head[0][1]:.2f}  "
        f"head2: dot={per_head[1][0]:+.2f} relu={per_head[1][1]:.2f}  "
        f"I_8,{s + 1}={score:.2f}"
    )

index_scores = np.array(index_scores)

# 细粒度 token 选择：取 index score 最大的 k 个位置
top_k = 3
selected = np.sort(np.argsort(-index_scores, kind="stable")[:top_k]) + 1
print(f"\nk={top_k} 时选中的位置: {selected.tolist()}")

# k >= L 时选择不产生任何裁剪
top_k_large = 8
selected_large = np.sort(np.argsort(-index_scores, kind="stable")[:top_k_large]) + 1
print(f"k={top_k_large} 时选中的位置: {selected_large.tolist()}（序列长 8，未裁剪）")

    观察重点：$s=3$ 与 $s=4$ 的输出中各有一个头的点积为负、ReLU 后变成 0，这两个位置的最终分数只由另一个头贡献。以及最后两行的对比：$k=3$ 时选中 3 个位置，$k=8$ 时全部 8 个位置都被选中——此时 top-k 不产生任何裁剪。

    教学简化：这段代码用 FP64 逐元素循环计算，真实实现是 FP8 矩阵乘 + 融合 kernel，且量化前还有 Hadamard 变换与 RoPE。代码只验证 index score 的算术定义与选择逻辑，不反映真实的数值精度与性能特征。

    KV cache 被切分时，top-k 如何保持精确

    服务端常把 KV cache 按 rank 切分到多张卡上（vLLM 中称 decode context parallel，DCP）。此时每张卡只持有全部历史位置的一部分，各自只能算出自己那部分的局部 top-k。要得到全局 top-k，是否必须把整行分数都传一遍？

    不必。vLLM 的实现给出了论证：如果某个 token 属于全局 top-k，那么全局范围内至多有 $k-1$ 个 token 排在它前面；它所在的那张卡上排在它前面的 token 只会更少，因此它必然也在本卡的局部 top-k 内。于是只交换各卡的局部 top-k 候选就足够，结果与把整行分数全部聚合完全等价，而传输量从整行分数降到 $\text{卡数} \times k$ 个候选（C14，来源为 vLLM 实现，非论文内容）。

    这个论证为什么是精确的而非近似

    反证。设 token $x$ 属于全局 top-k，但不属于它所在卡的局部 top-k。不属于局部 top-k 意味着该卡上至少有 $k$ 个 token 的分数排在 $x$ 之前。这 $k$ 个 token 也都在全局范围内，因此全局至少有 $k$ 个 token 排在 $x$ 之前，即 $x$ 的全局排名至少是第 $k+1$ 位，与 $x$ 属于全局 top-k 矛盾。

    因此"全局 top-k 的成员必定出现在其所属卡的局部 top-k 中"成立，收集全部卡的局部 top-k 候选不会漏掉任何全局 top-k 成员。这是精确算法，不是近似。

    需要注意的是，vLLM 中这条合并路径有实现约束：要求 CuteDSL，且 index_topk 取值为 512、1024 或 2048 之一。这些是实现层限制，与上面的正确性论证无关。

    省了什么、没省什么、什么时候不该用

    把账算清楚。

    项DSA 带来的变化依据
    主注意力计算复杂度从 $O(L^2)$ 降到 $O(Lk)$论文明确声称
    lightning indexer 复杂度仍是 $O(L^2)$，未降低论文明确声称
    indexer 每对 token 的单价远低于 V3.1-Terminus 中的 MLA论文明确声称
    KV cache 显存不减少从实现推出
    额外显存增加一份 indexer 的 key cache从实现推出
    模型效果未观察到明显回退论文明确声称，有条件
    短序列（$L \le k$）无收益，应走稠密路径论文与实现一致

    DSA 没有把注意力变成线性

    $O(Lk)$ 在 $k$ 固定时对 $L$ 是线性的，容易让人得出"DSA 把注意力复杂度降到线性"的结论。这个结论不成立：indexer 仍要给每个查询扫过全部历史位置，复杂度依旧是 $O(L^2)$。论文对此的处理是明确承认这一点，并给出论证——indexer 相比 V3.1-Terminus 中的 MLA 需要的计算量少得多。

    准确的说法是：DSA 把主项从平方变成线性，同时把残留的平方项的系数压得很低。整体不是线性。

    DSA 不省 KV cache

    "只读 $k$ 个位置，那是不是只需要存这 $k$ 个位置"——不是。每个查询选出的 $k$ 个位置各不相同，后续 token 可能选到任何历史位置，因此全部历史位置的 KV 条目都必须完整保留。

    这一点在两套实现中都能直接看到：主 KV cache 按最大序列长度分配，不随 $k$ 缩减；而 indexer 还额外需要自己的一份 key cache。所以 DSA 在显存上是略有增加而非减少。这条结论是从实现推出的，论文没有以否定句的形式声称它。

    容易与 MLA 的效果混淆。MLA 通过低秩压缩减少每个位置存多少，这确实省 KV cache；DSA 改变的是每次读哪些位置。V3.2 同时具备两者，但省显存的功劳属于 MLA，不属于 DSA。

    短序列下 DSA 不起作用

    当序列长度不超过 $k$ 时，top-k 会把全部位置都选进来——选择不产生任何裁剪，但 indexer 的计算照样发生，成为纯开销。贯穿例子的最后一行验证了这一点：8 个位置、$k=8$ 时，选中集合就是全部 8 个位置。

    真实模型中 $k = 2048$，因此这个失效区间是序列长度不足约 2048 的场景。两套实现对此都有专门处理：论文说明官方为短序列 prefill 特别实现了一个 masked MHA 模式来模拟 DSA，它在短上下文条件下效率更高；vLLM 的判据是当该批 prefill 请求的最大序列长度不超过 index_topk、且未强制走 MQA 时，置 use_dense_mha=True 走稠密路径（消费侧还有进一步的条件判断）。两者方向一致，但这个具体判据来自 vLLM 实现，不是论文给出的数字。

    效果上的代价

    论文报告，V3.2-Exp 在显著提升长序列计算效率的同时，与 V3.1-Terminus 相比在短上下文和长上下文任务上均未观察到明显的性能下降。这条结论的成立条件需要一并记住：标准 benchmark 的评测时间为 2025 年 9 月，对比对象是 V3.1-Terminus，且两者的训练设置被严格对齐——正是这种对齐才让"性能差异来自稀疏注意力"这一归因成立。

    论文的 parity 论证还包含另外两组独立证据。一是人类偏好侧：以 ChatbotArena 作为间接评估，V3.1-Terminus 与 V3.2-Exp 在 2025 年 11 月 10 日取得的 Elo 分数相近，而两者的后训练策略相同。二是长上下文侧：V3.2-Exp 发布后有若干独立评测使用了此前未见过的测试集，其中 AA-LCR 上 V3.2-Exp 在 reasoning 模式下比 V3.1-Terminus 高 4 分，Fiction.liveBench 上多项指标持续更优。三组证据的时间点与测试集各不相同，这是"不回退"这一结论的完整依据。

    论文另给出 H800 集群上的推理成本曲线，按 2 USD/GPU 小时估算，展示 token 成本随序列位置的变化。本页只取其定性结论（长上下文下端到端显著加速），不复述曲线读数。

    适用边界小结

    • 解决：长上下文下主注意力的计算量与访存量，使长序列训练与推理成本显著下降。
    • 不解决：KV cache 显存占用；短序列场景的效率；不改变注意力的数学形式，因此不带来线性注意力那类的常数状态优势。
    • 成立条件：序列长度显著大于 $k$；模型已完成 DSA 续训；有配套的 FP8 index kernel 与稀疏注意力 kernel；KV 条目跨 query 头共享。
    • 条件不满足时：$L \le k$ 时 indexer 成为纯开销；未经续训直接开启 top-k 会显著掉点；缺少共享候选集时 kernel 无法高效实现。

    与相邻方法的定位

    DSA 常与几类方法混在一起讨论。用前面几章建立的判据把它们分开。

    方法改变什么KV cache 是否减少是否需要专门训练
    DSA每个查询读哪些位置（内容决定）不减少，略增需要，两阶段续训
    滑动窗口每个查询读哪些位置（位置决定）可减少（窗口外可丢弃）视方案而定
    线性注意力 / KDA注意力的数学形式减少，替换为固定大小状态需要，从头设计与训练
    FlashAttention稠密注意力怎么算（分块、访存）不变不需要，结果等价
    MLA每个位置存什么（低秩压缩）减少需要，架构层设计

    与 NSA（Native Sparse Attention）的关系需要单独说明。两者同属可训练稀疏注意力，DSA 论文引用 NSA 来支撑"kernel 层面每个 key-value 条目必须被多个 query 共享"这一约束。但 NSA 是另一篇论文的另一套设计，DSA 不是它的重命名或简化版；本页只用到 NSA 支撑的那一条约束，不展开其机制。

    名称歧义：DSA 在本页特指 DeepSeek Sparse Attention。它不是"动态稀疏注意力"（dynamic sparse attention）这一类方法的统称，也与计算机基础课程里的 Data Structures and Algorithms、密码学里的 Digital Signature Algorithm 无关。

    教学解释与类比边界

    "ReLU 逐元素独立、softmax 需要跨序列规约"是对 C5 的教学解释。论文只说选 ReLU 出于吞吐考虑，未给出这一论证；该解释仅用于说明两种运算在实现结构上的差别，不可当作论文结论，也不能据此推断二者在效果上的优劣。

    "Hadamard 变换把异常大值能量摊到各维度以减少低精度量化误差"是对 C13 的教学解释。S2 只给出了实现，未说明动机；这一动机属于推断。

    "打分器只需给出排序，因此对数值误差的容忍度高于加权求和"是教学解释，用于说明 indexer 可被简化的空间。它解释的是设计动机的方向，不是论文给出的论证，也不构成对具体精度可降到何种程度的判断。

    教学简化及其限制

    贯穿例子把 128K 序列缩到 8 个位置、64 头缩到 2 头、128 维缩到 2 维。这一简化保留了 index score 的算术定义、ReLU 的作用与 top-k 的选择逻辑，可支持"公式如何代入计算""ReLU 何时截断""$k \ge L$ 时不产生裁剪"这三类结论；不可用于推断真实模型的分数分布形态、稀疏模式的实际稠密度，或任何性能数字。

    正文用掩码（未选中位置置 $-\infty$）说明 top-k 如何接回注意力，这与官方参考实现的做法一致，但掩码版本仍把全部位置算了一遍。它在数学上等价于只对 $k$ 个位置计算，不等价于性能上的收益——真实收益依赖专门的稀疏注意力 kernel。这一点已在正文标明，不可据此认为掩码实现即可获得论文报告的加速。

    可运行代码用 FP64 逐元素循环实现，真实实现是 FP8 矩阵乘加融合 kernel，且量化前还有 RoPE 与 Hadamard 变换。代码只验证算术定义与选择逻辑，不反映真实的数值精度、访存行为与性能特征。
