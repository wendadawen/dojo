# 增量 KV 传输——内容范围

## 1. 概念含义

### 概念名称与语境

- 概念名称：增量 KV 传输（任务发起人称呼「Increase KV」，指只传输「增加部分」的 KV）
- 语境：PD 分离（prefill/decode disaggregation）推理架构中的一项 KV 传输优化。机制由任务发起人于 2026-09-03 以工程描述形式给出，本页机制部分的唯一权威依据是该描述。
- 歧义处理状态：已裁定（依据：任务发起人给出的机制定义；公开资料中无「Increase KV」专有名词，2026-09-03 检索确认）。

### 机制事实（任务发起人描述的忠实转述，本页一切机制论断的基准）

1. 背景：PD 分离下，decode（D）节点自己也开了 prefix cache。
2. 问题：一个请求的前 $N$ 个 token 在 D 侧本地命中时，这部分 KV 已经躺在 D 侧显存里；但 prefill（P）侧此前仍然把整条 prompt 的 KV 全量 RDMA 过来，把命中的块又覆写一遍。
3. 机制：D 侧算出一个 `num_skip_blocks`，随 `block_ids` 消息传给 P 侧；P worker 发送前把 local/remote 两条 block id 列表在同一 skip 偏移处切掉同样长度的头部。
4. 效果：少发字节，且不破坏两条列表的配对。

### 简要定义

在 PD 分离推理系统中，D 侧本地前缀缓存命中的块不再由 P 侧重传：D 侧把命中块数编码为 skip 偏移传给 P 侧，P 侧在发送前从待传块序列的头部切掉这部分，只传输 D 侧没有的增量。

### 本文采用的语境

单机或多机的 PD 分离部署，KV 从 P 到 D 经 RDMA 传输，块粒度管理（PagedAttention 式 block）。不预设具体 connector 实现；字段名以任务发起人描述为准。

### 包括什么

| 内容 | 为什么属于本概念 |
|---|---|
| PD 分离的最小事实：P 做 prefill、D 做 decode、KV 必须从 P 搬到 D | 问题成立的前提，开头内联最小含义 |
| D 侧 prefix cache 命中：哪些块已在 D 侧显存 | skip 的判定来源（前置：prefix-caching 页） |
| 全量传输的覆写浪费：传输量与命中率的错配 | 本概念要消除的问题 |
| `num_skip_blocks` 协议：D 侧计算、`block_ids` 消息携带、P 侧切头 | 机制主体 |
| local/remote 两条列表与配对不变量：同偏移、等长切头 | 机制的正确性论证核心 |
| 传输量收益模型：节省正比于命中长度 | 机制的效果 |

## 2. 学习目标

### Q1：PD 分离下 KV 为什么必须从 P 传到 D？D 侧前缀命中时，旧的全量传输浪费在哪里？

- 完成答案：PD 分离让 P 专注 prefill、D 专注 decode，prefill 产出的整条 prompt KV 必须搬进 D 侧显存才能继续逐 token 解码；D 侧自己也运行 prefix cache，请求前 $N$ 个 token 命中时这部分 KV 已在 D 侧显存；旧逻辑下 P 侧不掌握命中信息，仍把整条 prompt 的 KV 全量 RDMA 过来，命中块被内容相同的块覆写一遍——多付的传输字节与时间没有任何收益
- 为什么是核心目标：不看清「命中却全量重传」这个错配，就无法理解 skip 机制要解决什么
- 依赖内容：PD 分离最小事实、prefix cache 命中（前置页）、覆写冗余

### Q2：`num_skip_blocks` 协议怎么运作——D 侧怎么算、随哪条消息传、P worker 收到后做什么？

- 完成答案：D 侧在处理请求时查本地 prefix cache，把命中前缀对应的块数算出来作为 `num_skip_blocks`，随发给 P 侧的 `block_ids` 消息一起传递；P worker 在发送 KV 前把 local/remote 两条 block id 列表在同一 skip 偏移处切掉同样长度的头部，然后只发送剩余部分
- 为什么是核心目标：这是本页的机制主体
- 依赖内容：Q1 的问题背景、block 组织（前置页）

### Q3：为什么 local/remote 两条列表必须同一偏移、切同样长度？配对被破坏会怎样？

- 完成答案：两条列表按位置配对、对应同一逻辑块序列（同一条 prompt 的块），P worker 发送时依赖这种按位对应关系组织传输；只在一条列表上切、或两条切得不一样长，剩余部分的按位关系就错位，配对被破坏，P 侧的发送组织会指向错误的块；在同一偏移处切掉同样长度的头部，剩余部分从头对齐，配对原样保留
- 为什么是核心目标：「不破坏配对」是该 commit 的关键设计约束，也是理解「为什么切头要同步」的唯一途径
- 依赖内容：Q2 的协议、block id 列表的配对语义

### Q4：这个优化的收益怎么量化？成立条件和边界是什么？

- 完成答案：传输量从「整条 prompt 的块数」降到「未命中的块数」，节省正比于命中长度；成立条件：D 侧命中块的内容与 P 侧将传输的内容一致（同一 prompt 前缀、同一模型、确定性计算），且命中边界与块边界对齐；边界：命中率越高省得越多、完全不命中时不省（还多了一条消息字段的开销）；本机制只省传输，不省 P 侧 prefill 计算
- 为什么是核心目标：防止把机制用到边界外（如以为它也省计算、或以为跳过有精度损失）
- 依赖内容：Q1–Q3 全部、每 token 占用公式（贯穿示例用）

## 6. 常见误解和适用边界

### 常见误解

1. 误解「跳过传输会丢数据/降精度」——正确：D 侧命中块的内容与 P 侧将要覆写的内容一致（同一 prompt 前缀、同一模型的确定性 prefill 输出），覆写本来就是把相同内容写一遍；跳过是无损的。
2. 误解「这个优化让 P 侧 prefill 变快」——正确：本机制只作用于传输环节；P 侧要 prefill 多少、要不要重算，是 P 侧自己的 prefix cache（lookup）那条线的事。
3. 误解「切哪条列表、切多长是自由实现细节」——正确：local/remote 两条列表按位置配对，切头必须同偏移等长，否则剩余部分错位、配对被破坏。
4. 误解「只要 D 侧有缓存就一定省」——正确：只有前缀从第 0 个 token 起连续命中的块才能 skip（skip 是从头部切）；命中率为零时不仅不省，还多传了一个字段。

### 适用边界

- 概念解决的问题是「命中块的重复传输」，不解决：D 侧缓存容量不足、P 侧重复计算、网络带宽绝对不足。
- 正确性依赖三个条件：命中块内容与 P 侧输出一致（同模型同前缀）、命中发生在 prompt 头部且与块边界对齐、skip 数与实际命中块数相等。任一不满足时必须回退到全量传输。
- 收益上限：传输量最低降到「未命中部分」，不为零；节省比例等于头部命中块数占总块数的比例。
- 本页机制描述为行为级（字段名 `num_skip_blocks`、`block_ids`、local/remote 列表），以任务发起人的工程描述为准，不对应公开论文或上游实现的具体版本。
