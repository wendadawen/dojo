# 增量 KV 传输——文章大纲

## 1. 页面开头

开头场景（贯穿问题）：PD 分离部署里，一条 8192 token 的 prompt 完成 prefill 后，P 侧要把整条 prompt 的 KV 通过 RDMA 传给 D 侧。但这条 prompt 的前 4096 token 是各请求共享的系统提示词和对话历史——它们在 D 侧的 prefix cache 里已经命中，KV 早就躺在 D 侧显存里。P 侧并不知道这件事：它照样把 512 个块共 1 GiB 全量传过来，其中前 256 个块被内容完全相同的块覆写一遍，多传的 512 MiB 没有换来任何东西。

随后简要解释：问题的本质是「D 侧知道命中、P 侧不知道」，解法是把 D 侧的命中信息逆着请求方向传回去——D 侧算出命中块数 `num_skip_blocks`，P 侧发送前从块序列头部切掉这一段，只传增量。本文的机制依据为工程实践描述（无公开论文定位），文末来源章节如实标注。

学习目标（核心问题块）：Q1–Q4，见 scope.md §2。

首个示例：开头场景即贯穿示例的首次亮相（8192 token、512 块、前 256 块命中、1 GiB → 512 MiB），完整手算在第 3 章展开。

与第 1 章的过渡：先把「谁在什么位置已经有什么」摆清楚。

前置 section 顺序：reading-time → blockquote.meta（主要依据：工程描述 + 前置页）→ 引言（上述场景）→ learning-goals（核心问题）→ misconceptions（3 条：跳过会丢数据 / 让 prefill 变快 / 切头是自由实现细节）→ 正文。

## 2. 章节设计

### 第 1 章 命中却全量重传——问题的构成

- 章节问题：PD 分离下 KV 为什么必须传到 D 侧？D 侧命中时，全量传输的浪费具体是什么？
- 答案要点：PD 分离最小事实（P 做 prefill、D 做 decode、KV 必须搬到 D 才能逐 token 解码，经 RDMA）；D 侧自己也运行 prefix cache，头部命中的块 KV 已在 D 侧显存；旧逻辑 P 侧不掌握命中信息，全量传输，命中块被相同内容覆写——多付的字节与时间零收益。
- 对应范围：Q1；C1、C2、C3、C8、C9。
- 正文要点：
  1. PD 分离与 RDMA 的最小含义（各一段，内联；延伸阅读链接 hetero-pd、beyond-buzz-disaggregation）
  2. D 侧 prefix cache 命中：链接 prefix-caching 页（命中条件：从第 0 个 token 起逐 token 精确匹配；块粒度复用）
  3. 块组织：链接 paged-attention 页（block、block id）
  4. 浪费的刻画：覆写的内容与已驻留内容相同（K/V 只依赖前缀与模型，链接 kv-cache 页第 1 章结论）——覆写即纯冗余
  5. 贯穿示例登场：512 块条带图（前 256 已命中 + 后 256 缺失；旧传输范围盖住全部）
- 表达材料及职责：
  - 块条带 SVG：展示「D 侧已有 / D 侧没有」与「旧传输范围」的错配——问题一图可见
  - 无公式（本章定性）
- 前置知识安排：prefix-caching、paged-attention、kv-cache 页链接（各自首次依赖处）。
- 本章问题：2 题（KV 为什么必须传？浪费具体指什么、为什么说覆写是纯冗余？）。

### 第 2 章 把命中信息传回去——skip 协议与同步切头

- 章节问题：`num_skip_blocks` 怎么算、怎么传、P worker 收到后做什么？为什么两条列表必须同偏移等长切？
- 答案要点：D 侧在本地匹配请求前缀，头部连续命中的块数即 `num_skip_blocks`，随 D→P 的 `block_ids` 消息传给 P 侧；P worker 发送前把 local/remote 两条 block id 列表在同一 skip 偏移处切掉同样长度的头部，只发送剩余部分。配对不变量：两条列表按位置对应同一条 prompt 的块序列，P worker 的发送组织依赖按位配对；只在一条上切或切得不等长，剩余部分错位、配对被破坏；同偏移等长切头使剩余部分从头保持按位对应。
- 对应范围：Q2、Q3；C4、C5、C6、C7。
- 正文要点：
  1. 协议总览消息流（图）：请求到 D → D 查命中算 skip 数 → `block_ids` 消息携带 → P worker 切头 → 只传剩余 → D 侧续接
  2. D 侧的计算：命中从第 0 块起连续（前缀语义），skip 数 = 头部连续命中块数；与 prefix-caching 页的匹配条件衔接
  3. P worker 的动作：两条列表（描述称 local 与 remote）按位配对、对应同一逻辑块序列；具体取数来源是实现细节，本页只需要配对行为（表述边界，yellow callout 标注）
  4. 为什么必须同步切（Q3 核心）：反推论证——若配对不被依赖，「同一偏移、同样长度」的约束就无必要；错位后果：P 侧发送组织指向错误块。标注为「由设计约束反推的论证」
  5. 贯穿示例推进：skip=256，P 侧切掉前 256 块，剩余 256 块按位配对原样保留
- 表达材料及职责：
  - 消息流图（dg-flow）：协议三方行为与时序
  - 配对切头 SVG（本页核心图）：两条平行列表、skip 偏移线贯穿两行、头部灰色（切掉）、尾部按位连线（配对保留）
  - yellow callout ×2：表述边界（列表语义止于配对行为）；反推论证的标注
- 前置知识安排：本章不新增前置。
- 本章问题：2 题（协议三方各做什么？为什么必须同偏移等长、破坏配对会怎样？）。

### 第 3 章 传输账与成立条件——省多少、何时灵

- 章节问题：收益怎么量化？正确性靠什么保证、边界在哪？
- 答案要点：传输量 $T_{new}=(B_{total}-n_{skip})\cdot m\cdot s_{blk}$，节省率 $=n_{skip}/B_{total}$；成立条件三条：命中块内容与 P 侧将传内容一致（同前缀同模型，K/V 确定性）、命中发生在头部且与块边界对齐、skip 数恰为命中块数；边界：命中率越高省得越多，零命中时不省（多一个字段开销）；只省传输不省 P 侧 prefill 计算。
- 对应范围：Q4；C3（推理部分）、C10；F1、F2；N1、N2。
- 正文要点：
  1. 手算展开：每 token 128 KB（引 kv-cache 页 Llama-3.1-8B 算例）→ 每块 2 MiB → 旧 1 GiB 新 512 MiB（折叠块放完整过程）
  2. 命中率扫描表：0/128/256/384/512 块命中 → 传输量与节省率，展示线性关系
  3. 正确性三条件逐一说明：内容一致（链接 kv-cache 页 K/V 确定性）、头部对齐（前缀命中天然从头连续，但边界必须落在块边界）、skip 数准确
  4. 与「省计算线」的区分：本机制只动传输；P 侧是否重算是 P 侧 lookup 的事（误解 2 的正面展开）
  5. 适用边界正文化：不解决 D 侧容量不足、P 侧重复计算、绝对带宽不足
- 表达材料及职责：
  - 公式 F2：传输量变量关系
  - 命中率扫描表格：线性关系一表可见
  - 数值折叠块：完整手算
- 前置知识安排：本章不新增前置。
- 本章问题：2 题（收益怎么算、上限在哪？正确性靠什么保证、不满足时怎么办？）。
