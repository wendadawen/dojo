    增量 KV 传输（increase KV）：PD 分离下 D 侧命中的块不再从 P 侧重传

    主要依据：机制行为定义来自工程实践描述（PD 分离推理系统，2026-09，行为级，无公开论文定位，性质见文末来源说明）；前置概念依据：前缀缓存（prefix-caching）、PagedAttention 分块（paged-attention）、KV cache 占用公式（kv-cache）。

    一条 8192 token 的 prompt 在 P 侧（prefill 节点）算完，它的全部 KV cache——512 个块、以 8B 级模型计约 1 GiB——需要经 RDMA 送进 D 侧（decode 节点）显存，解码才能开始。但这条 prompt 的前 4096 token 是各请求共享的系统提示词和对话历史，它们在 D 侧的 prefix cache 里已经命中：这 256 个块的 KV 早就躺在 D 侧显存里。P 侧并不知道这件事。它照样把 512 个块全部传过来，前 256 个块被内容完全相同的块覆写一遍——多传的 512 MiB 没有换来任何新信息。

    浪费的根源是一个信息不对称：D 侧知道自己命中了什么，P 侧不知道。解法因此直接：把命中信息逆着请求的方向传回去。D 侧把头部连续命中的块数算出来，作为一个 skip 偏移随 block_ids 消息——D 侧发往 P 侧、携带块编号的消息——发给 P 侧；P worker（P 侧执行发送的工作进程）在发送前把两条 block id 列表的头部切掉这一段，只传输 D 侧没有的增量。这就是本文讲的增量 KV 传输（任务语境中称 increase KV：只传输「增加部分」的 KV）。

    本文先拆问题的构成（第 1 章「命中却全量重传」），再讲协议与它必须保持的不变量（第 2 章「把命中信息传回去」），最后算传输账、划成立条件（第 3 章「传输账与成立条件」）。机制的依据是工程实践中的行为级描述，不是公开论文；文中论证的性质——描述基准还是标注推理——逐处标明。

    核心问题

    1. PD 分离下 prompt 的 KV 为什么必须从 P 侧传到 D 侧？D 侧前缀命中时，旧的全量传输浪费在哪里？

      解答：KV 必须进 D 显存才能解码；命中块被相同内容覆写

      P 侧做 prefill、D 侧做 decode：prefill 结束时整条 prompt 的 KV 在 P 侧显存，而 D 侧每一步解码的注意力都需要它们，KV 必须经 RDMA 搬进 D 侧。D 侧自己也运行 prefix cache，头部命中的块 KV 已在 D 侧显存；旧逻辑下 P 侧不掌握命中信息，仍全量传输，命中块被内容完全相同的块覆写——多付的字节与传输时间没有任何收益。完整论证见「命中却全量重传」一章。

    2. num_skip_blocks 协议怎么运作——D 侧怎么算、随哪条消息传、P worker 收到后做什么？

      解答：D 侧算命中块数，随 block_ids 消息传回，P 侧切头发增量

      D 侧在本地 prefix cache 中匹配请求前缀，头部连续命中的块数即 num_skip_blocks，随 D 发往 P 的 block_ids 消息传递。P worker 发送前把 local/remote 两条 block id 列表在同一 skip 偏移处切掉同样长度的头部，只发送剩余部分；D 侧把收到的增量接在已命中块之后。贯穿示例：512 块的 prompt 命中 256 块，切掉 256 项、只传 256 块。完整论证见「把命中信息传回去」一章。

    3. 为什么 local/remote 两条列表必须在同一偏移处切、且切同样长度？配对被破坏会发生什么？

      解答：两条列表按位配对，同步切头才能保持对齐

      两条列表按位置配对、对应同一条 prompt 的块序列（描述基准）；发送组织对这种按位对应的依赖，由「同一偏移、同样长度」的约束反推得出（标注推理）。只在一条列表上切、或两条切得不等长，剩余部分的起点错开，本应同位的表项不再对应，配对被破坏，发送组织指向错误的块。在同一偏移处切掉同样长度，剩余部分从头保持按位对应，配对原样保留。完整论证见「把命中信息传回去」一章的配对不变量一节。

    4. 这个优化的收益怎么量化？正确性靠什么保证、边界在哪里？

      解答：节省比例等于头部命中率；三条件保证正确性；只省传输

      传输量从 $B_{total}$ 块降到 $B_{total}-n_{skip}$ 块，节省比例为 $n_{skip}/B_{total}$，恰等于头部命中率（示例：1 GiB 降到 512 MiB，省 50%）。正确性依赖三条件：命中块内容与 P 侧将传内容一致（同前缀同模型）、命中在头部且对齐块边界、num_skip_blocks 准确；任一不满足须回退全量传输。边界：零命中时不省（多一个消息字段）；本机制只省传输，不省 P 侧 prefill 计算。完整论证见「传输账与成立条件」一章。

    常见误解

    • 「跳过传输会丢数据或降精度」——命中块的内容与 P 侧将要覆写的内容完全相同（同一 prompt 前缀、同一模型的确定性输出），覆写本来就是重写相同内容；跳过不缺任何状态，是无损的。
    • 「这个优化让 P 侧 prefill 变快」——它只作用于 P 到 D 的传输环节；P 侧要算多少、要不要查自己的 prefix cache 避免 prefill 重算，是省计算那条线（lookup）的事，与本机制互补。
    • 「切哪条列表、切多长是实现自由」——local/remote 两条列表按位置配对，切头必须同偏移、等长；否则剩余部分错位，P worker 的发送组织指向错误的块。

    1. 命中却全量重传——问题的构成

    要看清浪费，先把三个事实摆正：KV 为什么必须搬家、D 侧手里已经有什么、全量传输盖住了什么。

    1.1 PD 分离的最小事实——KV 必须从 P 搬到 D

    PD 分离把 prefill 与 decode 放到不同节点：P 侧做 prefill，把整条 prompt 一次并行算完；D 侧做 decode，逐 token 生成。架构的完整权衡与调度不在本文范围（延伸阅读见 异构 PD 分离全链路 与 Beyond the Buzz），本文只需要一个事实：prefill 结束时，整条 prompt 的 KV cache 在 P 侧显存里；而 D 侧接着解码时，每一步注意力都要用到这些 K/V。KV 因此必须从 P 搬到 D，搬运走 RDMA——远程直接内存访问，一种绕过两端 CPU 的网络内存读写。[C1]

    1.2 D 侧自己也开着 prefix cache

    D 侧不是一张白纸。它运行着自己的 prefix cache：跨请求复用相同前缀的 KV。匹配从第 0 个 token 起逐 token 精确、以块为粒度命中与复用，机制见 前缀缓存。[C2][C9] 系统提示词、多轮对话历史、共享文档前缀——每个请求的开头往往相同，D 侧的命中可以覆盖 prompt 的头部一段。

    命中意味着：这部分 token 的 KV 已经在 D 侧显存里，D 侧解码时直接可用，不需要任何人再提供。[C2]

    块是两侧的共同语言。KV cache 按固定 token 数分块管理（见 PagedAttention），每个块有 block id，一条 prompt 的块序列用一列 block id 指代。[C8] block_ids 消息能在两侧之间传递这些编号，前提正是两侧用同一种编号指认同一个块——这由消息传递行为直接推出，属标注推理。[C4]

    1.3 命中块被覆写一遍——纯冗余的传输

    旧逻辑下，P 侧不掌握 D 侧的命中信息。发送时它按整条 prompt 的块序列全量传输：512 个块全部 RDMA 到 D 侧，D 侧全部写入显存——包括那 256 个已经命中的块，被内容相同的块覆写一遍。[C3]

    覆写为什么是纯冗余：K/V 只依赖前缀 token 与模型参数，历史不变则 K/V 不变（见 KV cache 第 1 章的依赖关系分析）。D 侧命中的块与 P 侧将要写入的块来自同一 prompt 前缀、同一模型，内容完全相同——这一致性由 K/V 对前缀与参数的确定性推出，属标注推理。把相同内容写一遍，不产生任何新状态。[C3]

    错配清晰可见：D 侧显存的前半段已经就位，旧逻辑的传输范围却盖住整条 prompt。要消除浪费，P 侧需要知道那条分界线的位置——这正是「把命中信息传回去」一章的协议要做的事。

    本章问题

    1. PD 分离下，为什么 prompt 的 KV 必须从 P 侧传到 D 侧？D 侧命中时，全量传输浪费的具体是什么？

      解答：解码每步都要用整条 prompt 的 K/V；浪费是命中块被相同内容覆写

      P 侧做 prefill、D 侧做 decode：prefill 结束时全部 prompt 的 KV 在 P 侧显存，而 D 侧逐 token 解码时每一步注意力都需要这些 K/V，因此 KV 必须经 RDMA 搬进 D 侧显存。D 侧 prefix cache 头部命中的块已在 D 侧显存；旧逻辑下 P 侧不掌握命中信息，把整条 prompt 全量传过来，命中块被内容完全相同的块覆写——这部分传输的字节与时间没有任何收益。示例中 512 块全传 1 GiB，其中 256 块（512 MiB）是白传的。

    2. 为什么说覆写是纯冗余、跳过它不会丢任何信息？

      解答：K/V 由前缀与模型确定，覆写只是重写相同内容

      K/V 只依赖前缀 token 与模型参数，历史不变则 K/V 不变。D 侧命中的块与 P 侧将要写入的块来自同一 prompt 前缀、同一模型，内容完全相同；覆写只是把相同内容重写一遍，不产生新状态。跳过覆写，D 侧显存里的内容与覆写后的内容一字不差，不缺任何信息。

    2. 把命中信息传回去——skip 协议与同步切头

    第 1 章的浪费来自信息不对称：分界线的位置只有 D 侧知道。消除它只需要一个动作——让这条信息逆着请求流回到 P 侧，再让 P 侧据此少发。

    2.1 协议总览：一条消息与一次切头

    协议三方行为可以一句话说完：D 侧算出头部连续命中的块数 num_skip_blocks，随发给 P 侧的 block_ids 消息传递；P worker 发送前，把 local/remote 两条 block id 列表在同一 skip 偏移处切掉同样长度的头部，然后只发送剩余部分。[C4][C5]

    D 侧把收到的增量接在已命中块之后，凑成完整的块序列——拼接位置由「命中块已在 D 侧」[C2]与「切头只发送序列后缀」[C5]直接推出，属标注推理。

    2.2 D 侧的计算：头部连续命中块数

    num_skip_blocks 的计算就是一次前缀匹配。D 侧在本地 prefix cache 里匹配请求前缀：匹配从第 0 个 token 起、逐 token 精确、以块为粒度（见 前缀缓存）。因此命中段天然是头部连续段——命中了多少个完整的块，num_skip_blocks 就是多少。[C4][C9]

    构造数据。prompt 8192 token、块大小 16（构造参数），共 512 块；头部 4096 token 命中，即 256 个完整块——num_skip_blocks 为 256。[N2]

    两个极端方向都值得看清。命中 0 块时 num_skip_blocks 为 0，切头退化为不切，机制无损但也无收益；命中全部 512 块时切完为空——此时请求是否还需要 P 侧介入，属于调度层的决策，超出本页机制（见「边界：它不解决什么」一节）。

    2.3 P worker 的动作：同偏移切头

    P worker 为本次发送维护两条 block id 列表——描述中称 local 与 remote。本页依据的行为级描述只保证一点：这两条列表按位置配对，第 $i$ 个位置的表项对应同一条 prompt 的第 $i$ 个逻辑块（这是对描述中「配对」一词按块序的字面展开）。发送组织为什么依赖这种按位对应、切头为什么必须同步——这由设计约束反推得出，见「为什么必须同偏移、等长——配对不变量」一节的分析。两条列表各自的取数来源（哪些块记入哪条）是实现细节，不影响本页要讲的不变量。[C5]

    表述边界。local/remote 两条列表「各自记什么」超出本页依据的范围；本页只需要并只使用其行为约定：两条列表按位配对，切头必须同步进行。

    动作本身：在 skip 偏移处——第 $n_{skip}$ 块与第 $n_{skip}+1$ 块之间——把两条列表各切掉头部 $n_{skip}$ 项。切完之后，剩余部分的第 0 项对应原来的第 $n_{skip}$ 块，两条列表的按位关系原样保留；实际发送的只有剩余部分。[C5][C6]

    2.4 为什么必须同偏移、等长——配对不变量

    为什么强调「同一偏移、同样长度」？这一约束的存在理由就是配对必须保持。反过来想：如果两条列表的按位关系不被发送组织依赖，同步切头就根本没有必要写进机制——两条列表各切各的即可。约束本身说明按位配对是被依赖的。[C7]

    错位的具体画面分两种情形。情形一：只在 local 列表上切——local 切掉头部 256 项，它的第 0 项对应原来的第 256 块；remote 一项未切，第 0 项仍对应原来的第 0 块。两条列表的剩余部分起点相差整整 256 块。情形二：两条切得不等长——local 切掉 300 项、remote 切掉 256 项，local 的第 0 项对应原来的第 300 块，remote 的第 0 项对应原来的第 256 块。两种情形下，P worker 按位组织发送时，本应对应同一逻辑块的表项不再对应，配对被破坏，发送组织指向错误的块。

    在同一偏移处切掉同样长度，剩余部分从头对齐，按位关系与切头前完全一致。这就是「少发字节且不破坏配对」中「不破坏配对」的准确含义。[C6][C7]

    论证性质。切头动作与「少发字节且不破坏配对」的效果是描述基准；本节的必要性论证（若配对不被依赖、同步切头即无必要）由设计约束反推得出，是标注推理而非描述原文。

    本章问题

    1. 协议中 D 侧、block_ids 消息、P worker 三方各做什么？

      解答：D 算命中块数，消息携带传回，P 侧切头只发剩余

      D 侧在本地 prefix cache 匹配请求前缀，把头部连续命中的块数算为 num_skip_blocks（示例：512 块的 prompt 头部命中 256 块，值为 256），随 D 发往 P 的 block_ids 消息传递。P worker 收到后在 skip 偏移处把 local/remote 两条 block id 列表各切掉头部同样长度（256 项），只发送剩余部分（256 块）；D 侧把收到的增量接在已命中块之后。命中 0 块时值为 0，切头退化为不切。

    2. 为什么两条列表必须同一偏移、切同样长度？配对被破坏会发生什么？

      解答：按位配对被发送组织依赖，错位即指向错误块

      local/remote 两条列表按位置配对，第 $i$ 位表项对应同一条 prompt 的第 $i$ 个逻辑块（描述基准）；发送组织对这种按位对应的依赖由「同步切头」约束反推得出——若配对不被依赖，该约束即无存在的必要（标注推理）。若只在一条列表上切、或两条切得不等长，剩余部分的起点错开——local 第 0 项与 remote 第 0 项不再对应同一逻辑块，P worker 按位组织发送时指向错误的块，配对被破坏。在同一偏移处切掉同样长度，剩余部分从头对齐，按位关系与切头前完全一致。

    3. 传输账与成立条件——省多少、何时灵

    协议定了，切头保住了配对。剩下两件事：把账算清——省多少；把边界划清——什么时候灵、正确性靠什么。

    3.1 传输账：从整条到增量

    传输的字节数由三个量决定：块数、每 token 占用、每块 token 数。每 token 占用沿用 KV cache 页的公式 $m = 2 \cdot L_{\text{layers}} \cdot H_{\text{kv}} \cdot d_{\text{head}} \cdot b$（各符号见下方列表）；以 Llama-3.1-8B 计（32 层、8 个 KV 头、头维 128、bf16），每 token 128 KB。[F1][N1]

    旧逻辑与新机制的传输量为：

    $$T_{old} = B_{total} \cdot m \cdot s_{blk}, \qquad T_{new} = (B_{total} - n_{skip}) \cdot m \cdot s_{blk}.$$[F2]

    • $B_{total}$：prompt 的总块数（贯穿示例 512）。
    • $n_{skip}$：头部连续命中的块数，即 num_skip_blocks 的值（贯穿示例 256）。
    • $s_{blk}$：每块 token 数（构造参数，取 16）。
    • $m$：每 token 的 KV 字节数，$m = 2 \cdot L_{\text{layers}} \cdot H_{\text{kv}} \cdot d_{\text{head}} \cdot b$（Llama-3.1-8B 为 128 KB）。
    • $L_{\text{layers}}$：Transformer 层数（Llama-3.1-8B 为 32）。
    • $H_{\text{kv}}$：每层 KV 头数（Llama-3.1-8B 为 8）。
    • $d_{\text{head}}$：每个注意力头的维度（Llama-3.1-8B 为 128）。
    • $b$：每个缓存元素的字节数（bf16 为 2）。

    传输节省的比例为两式之差与旧传输量之比：$(T_{old}-T_{new})/T_{old} = n_{skip}/B_{total}$——恰好等于头部命中率。构造数据的手算：每块 $16 \times 128\ \text{KB} = 2\ \text{MiB}$；旧 $T_{old} = 512 \times 2\ \text{MiB} = 1\ \text{GiB}$；新 $T_{new} = 256 \times 2\ \text{MiB} = 512\ \text{MiB}$，节省一半。[N2]

    展开：贯穿示例的完整手算

    输入：Llama-3.1-8B，$L_{\text{layers}}=32$、$H_{\text{kv}}=8$、$d_{\text{head}}=128$、$b=2$（bf16）；prompt 8192 token；块大小 $s_{blk}=16$（构造）；头部命中 4096 token。

    每 token 占用：$m = 2 \times 32 \times 8 \times 128 \times 2 = 131{,}072$ 字节 $= 128$ KB。[F1][N1]

    总块数：$B_{total} = 8192 / 16 = 512$ 块。命中块数：$n_{skip} = 4096 / 16 = 256$ 块。

    每块 KV：$16 \times 128\ \text{KB} = 2{,}048$ KB $= 2$ MiB。

    旧传输量：$T_{old} = 512 \times 2\ \text{MiB} = 1{,}024$ MiB $= 1$ GiB。

    新传输量：$T_{new} = (512-256) \times 2\ \text{MiB} = 256 \times 2\ \text{MiB} = 512$ MiB。

    节省比例：$n_{skip}/B_{total} = 256/512 = 50\%$。数字全部为 2 的幂，可逐步复算。

    同一构造数据下改命中率，节省随命中块数线性增长：

    命中块数 $n_{skip}$传输块数传输量节省
    05121 GiB0%（多一个消息字段）
    128384768 MiB25%
    256256512 MiB50%
    384128256 MiB75%
    51200100%（是否仍需 P 侧介入属调度层）

    同一条链路、同样带宽下，传输时间的节省比例与字节数一致——少传一半字节，就少花一半传输时间。[F2]

    3.2 正确性靠什么保证：三个条件

    跳过传输不是碰运气，它成立依赖三个条件，缺一就必须回退全量传输。

    条件一：命中块的内容与 P 侧将传的内容一致。K/V 只依赖前缀 token 与模型参数（见 KV cache 第 1 章），同一前缀、同一模型之下，D 侧命中的 KV 与 P 侧算出的完全相同——跳过不丢任何状态。[C3] 反过来，若两侧模型或权重不一致，覆写反而是必要的，skip 会把错误内容留在 D 侧。

    条件二：命中发生在头部，且对齐块边界。skip 是从头切：偏移之前的块被跳过、之后的全部传输。前缀匹配天然从第 0 个 token 开始、按块粒度命中，条件二由 prefix cache 的匹配方式保证（见 前缀缓存）；中间段的相同内容——例如 prompt 中部嵌入一段与缓存相同的文档——不能用于 skip。[C9]

    条件三：num_skip_blocks 恰等于实际命中块数。传大了，P 侧切得过多，D 侧没有的块没有被传输，解码缺状态（错误）；传小了，多传几块、覆写部分命中块，正确性无损但收益打折。这两个方向由切头动作直接得出，属标注推理。[C4][C5]

    3.3 边界：它不解决什么

    这条机制的作用面很窄，窄正是它可靠的原因。

    它只省传输，不省 prefill 计算。P 侧要不要重算前缀、要不要查自己的 prefix cache（lookup），是省计算那条线的事；两条线作用于不同环节，互补而不互相替代。[C10]

    它不解决 D 侧缓存容量问题：命中块若已被逐出，skip 无从谈起（容量与逐出见 前缀缓存）。它不解决绝对带宽不足：字节少传了，链路速率没有变。它也不决定哪些请求去哪个 P——那是调度层的事。

    零命中时 num_skip_blocks 为 0，切头退化为不切；机制不亏不赚，只多了一个消息字段的开销。

    本章问题

    1. 传输量与节省怎么算？收益的上限在哪里？

      解答：节省比例等于头部命中率，上限是传输量归零

      $T_{new} = (B_{total} - n_{skip}) \cdot m \cdot s_{blk}$，节省比例为 $n_{skip}/B_{total}$，恰等于头部命中率。贯穿示例：512 块、每块 2 MiB，旧传 1 GiB；命中 256 块后只传 256 块 512 MiB，省 50%。上限是头部全部命中（$n_{skip} = B_{total}$），传输量降到 0——此时请求是否仍需 P 侧介入属于调度层决策，超出本页机制。同链路同带宽下，时间节省比例与字节一致。

    2. 正确性靠什么保证？条件不满足时怎么办？

      解答：内容一致、头部对齐、skip 数准确；不满足则回退全量

      三个条件：一，命中块内容与 P 侧将传内容一致——由同一前缀、同一模型下 K/V 的确定性保证，若两侧模型不一致则覆写反而必要，skip 会留下错误内容；二，命中发生在头部且对齐块边界——由前缀匹配从第 0 个 token 起、按块粒度命中的方式保证，中间段相同内容不能 skip；三，num_skip_blocks 恰等于实际命中块数——传大会漏传、解码缺状态（错误），传小则多传几块、正确性无损但收益打折。任一条件不满足时回退全量传输。
