# UltraEP 文章大纲

## 页面开头

- 定位摘要（lead）：大规模专家并行下，按历史负载周期性搬专家已经跟不上真实的负载漂移。UltraEP 把均衡搬到 gating 之后的关键路径上，每个 microbatch、每一层都用精确负载重新规划一次；能这么做的前提是机架级节点把 scale-up 域扩到了整机架。
- 论文解决的具体问题：拿到精确负载的唯一时机在 gating 之后，此时规划与专家状态搬运必然进入关键路径；要让均衡收益大于这份开销。
- 论文元信息（组件 02）：标题、作者与单位、arXiv v3、链接；无公开代码仓库，删除代码行。
- 核心问题块（组件 03）：scope.md 的 Q1–Q4，每题配解答折叠块。
- 术语速查表（组件 04）：EP、large-EP、RSN、scale-up/scale-out、逻辑专家/物理专家、主槽/冗余槽、配额、reroute、精确负载、热路径、不均衡度、EPLB/EPLB+/LPLB、强制均衡 ideal。
- 首个具体场景：EP=4、8 个逻辑专家、每 rank 1 个冗余槽的最小例子。给出负载矩阵，rank 0 初始负载 12、rank 3 只有 2，rank 级不均衡 2.0。这个例子贯穿第 3、4 章。
- 与第 1 章的过渡：先看清「负载到底怎么变」，才能判断历史统计为什么不够用。

## 章节设计

### 1. 专家热度在层与批次之间快速漂移，历史统计撑不住

职责：回答 Q1。建立「非平稳」这个事实，并说明它在大 EP 下如何放大成 rank 级问题。

内容：
- 先讲 serving prefill 为何是均衡目标而不是 decode（C38）。这一段同时消掉「UltraEP 能给整条推理链路加速」的误解。
- prefill 的三个漂移维度：跨 forward step、跨数据域、跨层（C3、N46）。
- 训练的两种动态：初期路由未特化、后期辅助损失负反馈持续重调，DeepSeek 式补偿降低整体不均衡但放大短期摆动；microbatch 间还有采样抖动（C4、N47）。
- 大 EP 的放大机制：每 rank 主专家只剩 2 或 4 个，专家级抖动直接变成 rank 级倾斜（C5）。
- 原图 G3（Figure 6）：EPLB 前后的 rank 级不均衡曲线，EPLB 出现高于 no-balancing 的尖峰（C5、N48）。
- 一句边界：系统侧均衡不替代辅助损失，两者目标不同（C34）。这里链接 `../aux-loss-free-routing/`。
- 前置知识引用：`../moe-serving/`（MoE、router、top-k、EP、all-to-all、prefill/decode、TTFT、TPOT）在本章第一次依赖时给出。

本章问题：
1. 为什么论文把均衡目标限定在训练与 serving prefill，不管 decode？——答：decode 是 memory-bound，计算侧不均衡被访存延迟稀释；靠增大 batch 提高计算强度又与 decode 的 TPOT SLO 冲突。prefill 追求吞吐以降 TTFT，是实际可优化的对象（C38）。
2. 同样是「负载不均衡」，为什么 EP 从 8 路提到 64 路会让问题质变？——答：每 rank 承载的主专家数随 EP 增大而变少（论文说常 2 或 4），一个专家变热就没有同 rank 的其他专家来摊薄，专家级抖动直接成为 rank 级倾斜；rank 是同步单位，最慢的那个决定整步耗时（C5、C1）。
3. EPLB 已经在做冗余专家复制，为什么还会「变得更差」？——答：EPLB 本身与负载估计无关，但常见部署用近期路由历史、周期性重均衡以摊薄开销。当实际负载偏离用来算布局的统计时，按旧热度建的副本收不到流量、而新热专家没有副本，于是产生新的尖峰与 straggler（C2、C5，Figure 6 可见 EPLB 曲线的尖峰超过 no-balancing）。

### 2. 精确负载只能在 gating 之后拿到，机架级节点让这件事第一次划得来

职责：回答 Q2 的前半（为什么是 RSN），并交代两个挑战。

内容：
- 时序约束：精确负载在 gating 后产生，于是规划与搬运落在关键路径上；前向搬权重，训练还要搬梯度或优化器状态（C6）。
- 标准 RDMA 集群的限制：scale-up 只覆盖单台 4/8 卡，跨机走 scale-out；大 EP 下跨机搬专家状态在热路径上不现实（C7）。这里链接 `../gpu-communication/`。
- RSN 是什么：scale-up 域扩到整机架 64+ 卡，机架内跨服务器仍直连；带宽与语义对比（C8）。原图 G2（Figure 2）。
- 原图 G1（Figure 1）：三个维度的差异——负载保真度（stale vs exact）、决策时机（global batch 边界 vs 层内热路径）、均衡频率。图中标注 hot-path balancing 的暴露开销约 0.3 ms，这个数字在第 6 章由 Figure 13 精确到 0.33 ms。
- 必要不充分：控制面的决策窗口、数据面的不规则搬运（C9）。这两条直接对应第 4、5 章。
- 每个 EP 组装在一个 RSN 内，跨机架靠 PP 和 DP（§4 开头）。链接 `../model-parallelism/`。

本章问题：
1. 「精确负载」和「历史负载」差在哪一个时间点上？——答：差在 gating。gating 算完就知道本次每个 token 选了哪些专家，这是精确负载；历史负载是上几个 batch 的统计，用它可以提前规划、把开销摊薄，但它对本次的真实分布只是一个预测（C6、C2）。
2. 为什么同一套算法在普通 8 卡机集群上不可行？——答：不是算法不可行，是搬运代价不可行。普通集群的高带宽 scale-up 只覆盖单机 4/8 卡，EP64 必然跨机，专家权重要走每卡数十 GB/s 的 scale-out；在 gating 到 dispatch 之间的窗口里搬不完（C7、C8）。
3. 有了 RSN 就够了吗？——答：不够。论文明确 RSN 是必要不充分。还剩两个问题：控制面要在 gating 与 dispatch 之间的短窗口里出高质量决策；数据面要跑静态集合通信支撑不好的不规则、易变搬运，否则吃不满 RSN 带宽，开销可能把均衡收益抹掉（C9）。

### 3. 只复制不重排：把冗余槽做成跨层复用的临时缓冲

职责：回答 Q4 的内存部分，并交代问题形式化。这是理解第 4、5 章的结构基础。

内容：
- 逻辑专家 vs 物理专家、主槽 vs 冗余槽、一对多映射（C10）。原图 G4（Figure 7）。
- 为什么只复制不重排（C11、A14）。这里回答「EPLB 会重排，为什么 UltraEP 不」。
- 跨层 buffer 复用：冗余槽不存优化器状态、权重/梯度 buffer 跨层共享；Qwen3-235B-A22B（94 层、128 专家）单槽从 3.3 GB + 6.6 GB 降到每 rank 36 MB + 72 MB（C12、N39）。代价是前向关键路径上的逐层权重实体化紧期限。
- 前向流水线：notify-dispatch 复用、每 rank 确定性算出同一份计划无需额外同步、reroute 与权重分发可重叠但 dispatch 必须等权重分发结束（C13）。原图 G5（Figure 8）。
- 反向流水线：权重重实体化与 Wgrad 重叠、到 Dgrad 前为止；梯度归约保持与无副本形式的等价性、必须在下一层前完成；反向不重新求解（C14）。这一段回答「训练语义会不会被改变」。
- 问题形式化：输入输出、Eq.(1)（F1）与 Eq.(2)（F2）目标，Eq.(3)–(5)（F3–F5）代价模型，四条约束（C15）。每个公式说明它要解决的问题与首次出现符号。
- 折叠块：Eq.(3)–(5) 为什么都取 max——同步执行下最慢的 rank 决定整步耗时，因此代价模型都写成对 rank 取最大。附一个用贯穿示例的代入检查。

本章问题：
1. 为什么冗余槽敢不存优化器状态？——答：因为优化器更新只作用于主专家。反向结束后每个主专家把所有远端副本的梯度聚合回主梯度 buffer，该归约保持与「没有副本」时完全等价的结果，优化器只需在主专家上更新（C12、C14）。这也是训练语义不变的原因。
2. 跨层复用省了多少，代价是什么？——答：Qwen3-235B-A22B 有 94 个 MoE 层，若每层每槽都留一份权重与梯度，单个冗余槽需要 3.3 GB 权重 + 6.6 GB 梯度；跨层共享一份后降到每 rank 36 MB + 72 MB（$3.3\times1024/94\approx36$，$6.6\times1024/94\approx72$）。代价是这份 buffer 每层都要重新装载，前向关键路径上出现逐层的权重实体化紧期限（C12、N39）。
3. 为什么 Eq.(3)、Eq.(4)、Eq.(5) 都是对 rank 取 max？——答：一个 EP 组内的 rank 在每层都要同步（all-to-all 与后续计算），整步耗时由最慢的 rank 决定。MoE 计算取 reroute 后负载最大的 rank；token all-to-all 取「发送量或接收量」较大者中的最大 rank；权重分发取承载最热主专家、要发出最多副本份数的 rank（F3–F5）。

### 4. 配额把「建不建副本」和「接多少 token」并成一个变量

职责：回答 Q3。这是控制面的核心。

内容：
- 先说清 EPLB 家族的做法与它的缺口：先定副本再用独立启发式（如 round-robin）分流，优化的是 reroute 前的热度（C2、C29）。
- 配额是什么、为什么它是耦合变量（C17、A7）。
- 阈值形式化：Eq.(6)（F6）的 $\mathrm{exc}_r$ 与 $\mathrm{slk}_r$，可行性的定义。
- 二分 + 贪心 oracle 的完整流程（C16），配 F7、F8。
- 贯穿示例推进：用开头的 EP=4 例子走完整个二分过程（$\tau=9$ 可行 → $\tau=7$ 可行 → $\tau=6$ 可行，最终 $\tau=6$，四个 rank 各 6，不均衡 1.0，只用了 2 个冗余槽中的 2 个）。
- 可运行代码折叠块：Algorithm 1 的完整实现，输出二分过程、最终配额、reroute 拆分，以及两个对照——同一副本集合下 round-robin 得到 1.1667，关闭本地优先后跨 rank 流量从 41.7% 升到 62.5%。代码已实际运行。
- reroute：本地优先为什么不破坏已解阈值（C18、A9），比例分摊与确定性取整（F9、F10）。
- token 级分配：累积配额 + 前缀扫描 + 上界查找（C19）。
- GPU 原生求解：为什么不是简单数据并行、单 SM 上一个 cooperative thread block 的做法（C20）。链接 `../gpu-execution-model/`。
- 消融结果：Table 3 的五项对照（N25–N29）与 Figure 15（G9，N30）。表格用组件 14，基线行完整。
- 一句推断标注：二分 + 贪心 oracle 不保证全局最优（C39、A15）。

本章问题：
1. 「先定副本再 round-robin 分流」到底差在哪？——答：差在优化目标错位。round-robin 让某个专家的 token 在其副本间均分，但各副本所在 rank 上还有别的专家，均分后各 rank 的总负载并不相等。用页面的 EP=4 例子：同一副本集合下配额求解得到四个 rank 各 6（不均衡 1.0），round-robin 得到 6/6/7/5（不均衡 1.1667）。论文的说法是 UltraEP 直接优化 reroute 后的负载上界，EPLB+ 优化的是 reroute 前的热度（C29、代码输出）。
2. 为什么要设 $u_{\min}=1024$ 这个下限？——答：为了不建无效副本。建一个副本要付出权重搬运（前向）与梯度归约（反向）的代价，若它只承接几十个 token，收益抵不上开销。算法里表现为 $\delta<u_{\min}$ 时直接 break，不接受这次转移（C15、F8）。Table 3 中 UltraEP 消耗的实例总数 45 对 EPLB+ 的 107，少 57.9%，主要来自这类剪枝（N27、C29）。
3. 本地优先为什么不会破坏已经解出的阈值？——答：因为它只改「哪个源 rank 消费某个配额」，不改配额本身。阈值是由配额表 $U$ 决定的（每 rank 的 reroute 后负载 $\sum_e u_{e,r}$），而本地优先只是在满足 $\sum_r q_{r,e,t}=u_{e,t}$ 的前提下重排源侧归属，所以每个实例接到的总量不变（C18、F10）。收益是跨 rank 流量下降：页面示例中从 62.5% 降到 41.7%，论文模拟均值是在飞 token 占比从 98.4% 降到 96.0%（N29）。
4. 二分搜索找到的 $\tau$ 是最优解吗？——答：不是全局最优。每次探测用的是贪心可行性 oracle（按残余超额降序取 rank、按 $\lambda_e$ 降序取专家、送给空闲最大的目标），贪心判定为不可行的阈值未必真的不可行。论文全篇用的词是 near-optimal，没有给最优性证明。这一条属于本页的推断（C39）。

### 5. 把不规则的专家搬运做成 tile 流水线与 chunk 中继

职责：回答 Q4 的通信部分。这是数据面的核心。

内容：
- 均衡流量的性质：运行期自适应的稀疏传输图，不是规则集合通信；两条路径（前向权重分发/反向重分发、反向梯度归约）；目标是有效带宽而非峰值链路速率（C21）。
- 瓶颈一：非载荷开销被放大——任务切分与流水、数据暂存、动态寻址；盲目加并行度浪费且与重叠的反向计算争资源（§4.4）。
- persistent tile streaming（C22）：tile 单元、常驻任务流、共享内存双缓冲、权重分发的「一次暂存多处写出」与梯度归约的「累加后就地清零」。链接 `../gpu-execution-model/`。
- overlap-aware footprint（C23）：前向多给 block 打满带宽，反向限制 SM 占用与共享内存以留余量。
- 瓶颈二：热专家 fan-out——发送侧受限（每 rank 最多 $N_{\text{slot}}$ 个入站副本，但可能要推多个热专家给很多目的地）；RSN 的交换机组播假设预设通信组，而专家复制的组稀疏且逐层逐 microbatch 变化（§4.4）。
- chunk streaming relay（C24）：阈值 4、前沿 $\sqrt{\lvert\mathcal{H}(e)\rvert-1}$（F11）、chunk 级 ready flag 与无全局屏障。原图 G6（Figure 10），三种方案的对照正是这一机制的直接呈现。
- load-aware relay scheduling（C25）：按已分配发送字节量选中继与挂叶子。
- 通信实测：Figure 16（G10，N31–N36），表格给五档完整数据。这里说明 Ours 随 fan-out 增长维持约 0.28 ms、no-relay 线性增长，低倾斜时 relay 不激活。
- 折叠块：实现层面的 RSN 内存语义（C27）与端到端集成含 virtual layer ID（C28、C26）。

本章问题：
1. 为什么用 persistent kernel 而不是「每个副本发一次传输」？——答：因为瓶颈不在链路带宽而在控制路径。每副本一次传输意味着每次都要做任务查表、地址翻译与同步，这些非载荷开销在不规则搬运下被放大。persistent kernel 一次启动后常驻，thread block 反复从设备上的任务流取下一个 tile，并对共享内存 tile 双缓冲（tile $i$ 写出时已开始载入 tile $i+1$），于是控制开销被折进流水线、被数据搬运掩盖（C22）。
2. 两级中继为什么能降低瓶颈，代价是什么？——答：瓶颈是发送侧的 fan-out。一个热专家有 $\lvert\mathcal{H}(e)\rvert-1$ 个远端副本时，源 rank 要发这么多份；改成两级后源只发给约 $\sqrt{\lvert\mathcal{H}(e)\rvert-1}$ 个中继，中继各自转发给自己的叶子，两级宽度近似平衡。代价是多了一跳延迟，所以只对副本数超过 4 的专家启用；低倾斜时策略不激活 relay，只有可忽略的控制开销（C24、N36）。
3. 为什么中继要按 chunk 而不是按整个专家转发？——答：按整个专家转发意味着中继必须收完全部 tile 才能开始发，两级串行；论文图中的同步两级方案还需要一个全局 Barrier。按 chunk（若干连续 tile）转发时，一个 chunk 的所有 tile 到达后 kernel 写下该 chunk 的 ready flag，二阶段等这个 flag 就立刻从本地中继缓冲发出，两级因此流水线化，不必等整个专家、也不引入全局跨阶段屏障（C24，Figure 10 的 (b) 与 (c) 对照）。

### 6. 实验结果：均衡后逼近强制均衡上界，剩余差距来自路由本身

职责：给出端到端与分解结果，说明「实时均衡划不划算」的最终答案，并交代所有关键数字的实验条件。

内容：

- 训练端到端：Figure 11（G7）与完整对照表（N10–N14）。明确 94.6% 是三模型均值，单模型 96.4% / 91.2% / 96.1%。DeepSeek-V3 上 EPLB 与 LPLB 与 Megatron-LM 相当甚至更差的原因（N15、C4）。
- serving 端到端：数字表（N16–N18）与回放 trace 的对照方法（N19）。
- 延迟分解：Figure 13（G8）与 N20–N23。这里给出热路径开销的精确值 0.33 ms / 1.8%，以及 token all-to-all 前向 +33% 的归因（C31）。
- 关键结论的正确读法：剩余差距主要来自真实路由的不均匀，不是残余不均衡也不是热路径开销（C30）。这一段同时消掉「不均衡 1.01 就意味着只差 1%」的误解。
- 活跃内存：N24 与 C32。
- 生产训练：Figure 17（G12）、N37、N38、C33。
- 摘要数字的基线澄清：1.49× 相对 no-balancing，1.42×/1.56× 相对 Megatron-LM/SGLang；94.3% 是训练与 serving 总平均（N1–N7）。

本章问题：
1. 摘要的 1.49$\times$ 和正文的 1.42$\times$、1.56$\times$ 是什么关系？——答：基线不同。1.49$\times$ 是训练与 serving 平均、相对「完全不做均衡」；1.42$\times$ 是训练相对 Megatron-LM 的平均，1.56$\times$ 是 prefill 相对 SGLang。三个数都出自论文，读的时候必须带上基线（N4–N6）。
2. 均衡后不均衡度已经 1.01–1.03，为什么吞吐还差 ideal 约 5%？——答：残余不均衡不是唯一损耗。Figure 13 显示与 ideal 相比，UltraEP 的非 MoE 部分前向多 0.33 ms（占总延迟 1.8%），MoE 计算因冗余物理专家带来轻微控制开销，token all-to-all 前向高 33%、反向高 10%——后者来自真实路由的不均匀（ideal 用的是合成的均匀 dispatch），对 DeepEP 表现为其内部 dispatch 流水线的轻微 stall。论文明确剩余差距主要来自真实路由本身，不是残余不均衡或热路径开销（N22、N23、C30、C31）。
3. 均衡除了提吞吐还带来什么？——答：压平了接收侧的活跃内存热点。不做均衡时 MoE 活跃内存峰值是 ideal 的 2 倍（训练）与 11 倍（serving），UltraEP 把它降到接近 ideal，直接降低 OOM 风险、提升模型扩展余量，并可避免为省内存而启用 activation checkpointing 所付的额外计算（N24、C32）。训练侧这个数字是在关闭 activation checkpointing、取初期高倾斜阶段的峰值下测得的。
4. 生产训练的结论强度如何？——答：RefMoE-288B-A16B 在 EP32 下维持 >92% ideal，相对 no-balancing 平均提升 9.6%，loss 曲线符合预期预训练轨迹。但这只是一个内部模型、一个并行配置；ideal 取的是实测强制均衡的最好值以剔除环境波动，no-balancing 从关闭 UltraEP 的续跑区间采样（N37、N38、C33）。

### 7. 方法评价（组件 17，分析性判断）

优点：
- 把「均衡质量」的优化目标改对了：从 reroute 前的热度改成 reroute 后的负载上界，同一副本集合下就能拿到更好的均衡（页面示例 1.0 vs 1.1667），并顺带省资源（Table 3：实例总数 45 vs 107）。
- 配额作为耦合变量避开了组合爆炸：不枚举副本集合、不做 token 级路由，二分 + 贪心把决策压到 0.111 ms 量级。
- 内存与通信的协同：跨层复用把冗余槽压到 36 MB/72 MB 量级，才让「每层重搬」在预算上成立；tile streaming 与 relay 把搬运压到亚毫秒，才让它在时间上成立。任一环缺失，实时均衡都不成立。
- 训练语义可论证地不变：梯度归约回主专家、优化器只更新主专家，加上 virtual layer ID 让反向取回匹配的前向计划，PP/virtual PP 下也成立。

局限：
- 硬件前提强：结论建立在「EP 组装得进一个 RSN 的 scale-up 域」上。论文自己指出跨多机搬专家状态在热路径上不可行，因此这套方法在普通 8 卡机集群上不适用。
- 覆盖面窄于「MoE 推理优化」：不管 decode，不管 token all-to-all 内核，不管专家内部计算。
- 最优性只是经验的：二分的每次探测用贪心 oracle，论文用 near-optimal 而非 optimal，未给最优性或近似比证明（推断）。
- 生产证据单薄：只有一个内部模型 RefMoE-288B-A16B、一个 EP32 配置；serving 只在单机架验证。
- 与预算的关系需要注意：Figure 15 显示 $N_{\text{slot}}=1$ 且初始不均衡 6.0/8.0 时，UltraEP 也升到 1.07/1.09；预算变紧时两者都变差，只是 UltraEP 退化得慢。

适用场景与位置：
- 适用：RSN 上的大 EP MoE 训练与 prefill，且负载非平稳、$N_{\text{slot}}$ 有 2 个以上余量。
- 与 EPLB / LPLB 的关系：同一问题的不同时机与不同保真度——EPLB 是历史+周期，LPLB 是 EPLB 加每 microbatch 的 reroute 微调且限一个副本，UltraEP 是精确+每层每 microbatch。
- 与 MoonEP（`../moonep/index.html`）的关系：MoonEP 追求每个 rank 恰好收到 $S\times K$ 个 token 的完美均衡，靠固定大小 buffer 与静态形状消 host 同步；UltraEP 追求的是配额意义下的近最优并把决策放上热路径。两者都属于「用冗余专家在线纠正」这条路线，具体目标函数与工程约束不同。
- 与 DeepEP 的关系：不是竞品。UltraEP 用它做 token dispatch/combine，论文也把它适配来作专家权重搬运的通信基线；论文明确这类通信与计算优化与 UltraEP 正交可叠加（C36）。
- 论文展望：因为同时覆盖训练与推理，同一抽象可延伸到交替这两个过程的 RL pipeline（C37，标注为论文展望、未做实验）。
