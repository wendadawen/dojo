# HiSparse 文章大纲

## 1. 页面开头

- 标题（h1）：HiSparse：把稀疏注意力解码从显存容量墙里解放出来
- 定位摘要（lead 段）：一句话——top-$k$ 稀疏注意力把每步读的 KV 降到 $k$ 个，但 serving 系统仍为"可能被读"而全量驻留 HBM；HiSparse 把完整 KV 放 host、GPU 只留每请求每层 $B$ 格缓存，用 LRU 把选择局部性变成约 87% 命中率、单个融合 kernel 解析剩余 miss、共享选择模型上的精确预取藏掉一半 IO，输出逐位不变，长上下文峰值吞吐最高 4.7×。
- 论文元信息（组件 02）：标题、作者与单位、arXiv:2608.07009v1（NeurIPS 2026 投稿预印本）、链接、代码（并入上游 SGLang）。
- 术语速查表（组件 04）：KV cache、HBM、top-$k$ 稀疏注意力、indexer、TTFT、TPOT、PD-colocated/PD-disaggregated、pinned host memory、anchor/shared 层、LRU、Bélady、（CUDA graph 链接已有页）。
- 核心问题块（组件 03）：Q1–Q5，每题配解答折叠块（结论 + 关键机制 + 成立条件 + 指明完整论证章节）。
- 首个具体场景：GLM-5.1 一个 128K 请求的账单——13.09 GB BF16 KV，而 8×H200 权重驻留后每卡只余有限 HBM；过渡到第 1 章问"为什么稀疏了还是装不下"。

## 2. 章节设计

每章一个主要职责；标题直接给出本章解决的问题或结论。编号 h2 从 1 连续递增，h3 为 X.Y。

### 第 1 章 容量墙：稀疏注意力省了读，没省驻留（id: capacity-wall）

- 职责：完整回答 Q1。
- 内容：top-$k$ 稀疏注意力接口回顾（链接 wiki/dsa/；一个 decode 步、indexer 发出 $\mathcal{S}_t^{(\ell)}$、注意力只读 $k$ 条）→ 选择集漂移（现在跳过的之后可能被选中）→ 全量驻留的 admission 约束 C1/C2 → GLM-5.1 数字链 N4/N5（128K=13.09 GB、1M>100 GB、32K≈60 并发、128K≈15 请求、777 tokens/s decode-only）→ 两种部署模式（分离：容量封顶 decode 池；混布：TTFT 陡增）→ 原图 IMG-1（Figure 1）→ 贯穿示例引入。
- 贯穿示例（第一次出现，输入完整说明）：构造示例——单请求、单层序列简化模型，历史 $L_{\text{ctx}}{=}8$ 个逻辑位置，indexer 每步选 $k{=}2$ 个位置；给出 3 步选择序列展示漂移（如 $S_1{=}\{2,5\}$、$S_2{=}\{2,6\}$、$S_3{=}\{3,6\}$），说明"位置 5 在第 2 步没被选但第 3 步又回来"式的漂移为什么逼迫全量驻留。明确标注构造示例。
- 误解处理：误解 1（省读=省显存）在本章正面拆解（引用 §1 原句）。
- 本章问题（2 题）：为什么每步只读 $k$ 条却要全量驻留；容量墙在两种部署模式下各表现为什么。

### 第 2 章 解耦可用与驻留：host 存全量，GPU 留 B 格（id: hierarchy）

- 职责：完整回答 Q2。
- 内容：核心洞察（模型需要每个位置逻辑可用，GPU 只需要本步实际读的）→ naive offload 不行（F3 带宽估算：200 MB/token、7 GB/s、十几个并发饱和 PCIe Gen5）→ 局部性是缺口关闭者（步间重叠 + 层间相关/共享）→ 四条设计目标与不变量 C3–C6 → footprint 公式 F1/F2 + GLM-5.1 换算 N4（13.09→0.4 GB）→ 两层结构与元数据（host KV pool / GPU cache / 页表 / LRU 元数据）→ 选择状态不迁移 C7/N15 → 生命周期四阶段 C9（含 write-through 事件排序）→ 原图 IMG-2（Figure 2）。
- 图示（自绘，结构 B dg-stack）：三层堆叠——host KV pool（权威全量）、GPU cache（每请求每层 B 格 + 页表 + LRU）、常驻选择状态（indexer key 等不迁移）；图注定义各层职责。
- 贯穿示例推进：8 位置例子的 host pool 有 8 条记录；GPU cache 分 $B{=}4$ 格；给出第 3 步之后的一个页表快照（位置→槽位/host-only）与新 token 出生进 reserved slot + write-through 的路径。
- 本章问题（2 题）：为什么不能每步都从 host 取（F3）；HiSparse 用什么结构保证输出不变的同时 footprint 有界。

### 第 3 章 LRU：把选择局部性变成 87% 命中率（id: lru-cache）

- 职责：完整回答 Q3。
- 内容：$B{=}k$ 只暂存 top-k 为什么 miss 30%（选择集漂移的直接代价，引 N6）→ LRU 管理（hit 提升 refinement C8）→ 原图 IMG-5（Figure 6）+ 策略对比表（组件 14：Swap-vanilla 30%、LRU 13.4%、random 16.1%、FIFO 17.2%、Bélady 8.2%、B=8192 LRU 6.7%，含 trace 条件）→ Bélady 的含义（离线最优、可达上限的度量）→ $B$ 的选择 $[2k,4k]$ 与容量/扫描/命中率的三角权衡 C23/N10 → 链路越快最优 B 越小的伏笔（N9 的 112→29 μs 在第 6 章展开，这里只留钩子）。
- 贯穿示例推进：8 位置例子从第 1 步走 4 步 LRU 演化表（每步：选择集、hit/miss、LRU 序、页表）；对照 $B{=}2$（等价 $B{=}k$）同 trace 的 miss 计数，展示多出来的 2 格把一次 miss 变 hit。
- 可运行代码（组件 12，折叠）：Python 模拟——构造带时间局部性的选择 trace（热点集缓慢漂移），实现 $B{=}k$ 全换策略与 $B{=}2k$ LRU+hit 提升，输出两者 miss 率；标注构造示例，说明验证的机制（LRU 把步间局部性变成命中率）、观察重点（B 加倍 miss 下降的幅度）、简化条件（单层、无层间共享、均匀记录大小）。
- 误解处理：误解 7（miss 数字普适）随 N6 实验条件说明。
- 本章问题（2 题）：为什么只存当前 top-k 不够、LRU 的 hit 提升改变什么；B 加倍的收益与代价各是什么、Bélady 对照说明什么。

### 第 4 章 Resolve：一次 kernel 解决一层的全部 miss 解析（id: resolve-kernel）

- 职责：回答 Q4 前半（解析本身为什么便宜、怎么进 CUDA graph）。
- 内容：解析在每稀疏层每步的关键路径位置 → 为什么融合（C10：多 launch 物化中间态 + launch 延延；中间状态耦合）→ 五阶段逐段展开 C11（配原图 IMG-3/Figure 3）：哈希表（成员测试免重复读 top-k 向量）、并行探测标记、并行 scan 选 victim + LRU 更新、GPU-assisted IO fetch（C12，链接 wiki/strata/；`ld.global.nc.v2.b64` 向量化非一致加载、块大小调优）、发布 top_k_device_locs → CUDA graph 捕获的含义（链接 wiki/vllm-cudagraph/；重放无需 host 分支）→ "逻辑索引进、物理槽位出"的 TLB 类比（论文原句，标明为论文所用类比）。
- 伪代码（组件 11，折叠）：Resolve 的五阶段伪代码（输入：选择集、页表、LRU 状态、host pool 指针；状态：B 格 cache；输出：top_k_device_locs、更新后的元数据；循环范围与停止条件写明）。
- 贯穿示例推进（本章高潮，正文完整走一遍）：8 位置例子在第 5 步的 resolve——选择集 1 hit 1 miss、哈希表内容、探测标记结果、victim 选择（LRU 尾）、fetch、输出向量；每格数字手算可验。
- 本章问题（2 题）：为什么必须是单个融合 kernel 且捕获进 CUDA graph；五个阶段各自解决什么、输出给注意力后端什么。

### 第 5 章 精确预取：anchor 一发声，shared 层提前搬（id: prefetch）

- 职责：回答 Q4 后半（剩余 IO 延迟怎么藏）。
- 内容：miss 仍在关键路径（即使融合 kernel 也只是让解析便宜，IO 延迟还在）→ anchor/shared 层结构 C13（IndexCache 分层；GLM-5.2 IndexShare 每 4 层一组、78=21+57）→ plan-then-IO C14（anchor 记录 miss plan → side stream copy-only kernel 重放 → shared 层等事件、复用 slot 表、完全跳过 resolve）→ 为什么是"精确"（选择已知而非预测；无浪费流量）→ 推测式变体的负结果 C15/N15 层数（hint 大多已驻留、新进入位置预测不了）→ no-IO oracle 的角色 C16（输出无效但时序是上界；机制零成本 + IO 是唯一代价）→ 原图 IMG-6（Figure 8）+ N8 关键数字（1727/2034、85%、TPOT -13~15%、IO 暴露 7.7→3.0 ms）→ 结构性下界 N13（21/78 anchor 层 ≈ 27% IO 无法预取）。
- 图示（自绘，内联 SVG 时间线）：4 层一组的层序列横轴 + 计算流/host 链路两条泳道——anchor 层 resolve（含同步 miss fetch）→ 其后 side stream 上为 shared 层搬运的块与中间层计算重叠 → shared 层等事件后直接跑注意力；SVG 内标签用 foreignObject 承载（$B$、$\ell$ 等符号）。坐标先脚本算好。
- 本章问题（2 题）：为什么共享选择让预取从预测变已知、plan-then-IO 每一步做什么；推测式预取为什么失败、oracle 说明什么。

### 第 6 章 收益与代价：最高 4.7 倍吞吐，TPOT 多付几毫秒（id: results-tradeoffs）

- 职责：完整回答 Q5。
- 内容：实验设置表（模型×selector×平台×k，N12 baseline 定义）→ 端到端数字表（组件 14，完整基线不删减：N1/N2/N3 的各输入长度对比）→ 原图 IMG-4（Figure 5）→ 收益机制（batch-size effect，decode-only 对 PD 分离的含义与 proxy 证据等级）→ TTFT 改善 N7/N8 → TPOT 代价与预取缓解（同步 7.7/22.0 → 预取 3.0/11.2 ms）→ kernel 分解数字 N9（112→29 μs、probe&scan 平台无关、60 μs/层量级对照）→ 容量红利的两种兑现（更多并发 N14 或更少硬件/更长上下文，上限变 host 容量 C22/N17）→ 禁用条件（非容量 bound 时无收益抵开销）。
- 误解处理：误解 3（4.7× 普遍）、误解 4（单步变快）、误解 6（host 无限）集中在本章与评价章拆解。
- 贯穿示例：本章不推进（实验数字章）。
- 本章问题（2–3 题）：收益从哪来、在什么条件下成立；TPOT 代价多大、预取能藏多少；什么时候应该禁用 HiSparse。

### 第 7 章 方法评价（id: evaluation，必有，组件 17）

- 开头 callout：本章为分析性判断。
- 优点：接口切入点的选择（只消费逻辑位置 → indexer 无关、精确性白拿）；三大挑战各有明确对应机制且实验逐一隔离验证（cache 策略、kernel、prefetch 三组消融）；oracle 方法论（把"机制成本"与"IO 成本"分离）；负结果（推测式预取）如实报告；工程落地真实（上游 SGLang）。
- 局限：host 容量成为新上限（GB200/GB300 乘数缩小）；TPOT 正代价在非容量 bound 场景无法摊销；PD 分离结论依赖 decode-only proxy；B 静态、依赖离线 profiling；miss 率证据来自单一 trace 家族；共享选择的预取依赖模型 co-design（存量模型享受不到）。
- 适用场景与位置：长上下文 + 高并发 + host DRAM 充裕的部署；与 HiCache（prefill 侧前缀复用）组成对偶；与 KV 压缩/量化正交可叠加（分析性判断，标注）；对比 ESS/ECHO 一句话定位（依据 §4.1/§6）。
