HiSparse: Scaling Sparse-Attention Decoding with Hierarchical KV Cache Management

top-$k$ 稀疏注意力让每步注意力只读 $k$ 条 KV，但 serving 系统仍须把完整 KV 常驻 HBM，解码先撞容量墙。HiSparse 把完整 KV 放进 host pinned 内存、GPU 每层只留固定大小的 LRU 缓存，用融合 kernel 解析 miss、用精确预取隐藏 IO，输出逐位不变，长上下文峰值吞吐最高 4.7 倍。

arXiv:2608.07009v1 · Zhiqiang Xie 等（Stanford、Meta、Alibaba 等） · NeurIPS 2026 投稿预印本 · 更新于 2026-09-03

解决的问题

top-$k$ 稀疏注意力把每步读的 KV 降到 $k$ 条，但选择集随步与层漂移：这一步跳过的位置，下一步可能被选中。serving 系统因此不敢丢任何 KV，完整 KV 仍须常驻 HBM——decode batch 的准入卡在「$N_{\text{batch}} \times L_{\text{ctx}}$ 条 KV」上，算力还没用满，显存先撞墙，上下文越长、并发越高吞吐越早走平。朴素的解法是把 KV 全放 host、每步按选择取回，但论文估算 GLM-5.1 这样每 token 需移动约 200 MB KV，十几路并发就打满 PCIe Gen5 $\times$16——解耦本身不够，必须利用选择的局部性。

主要贡献

  • 把瓶颈从读带宽改判为驻留容量：模型侧的稀疏注意力工作解决「读什么」，不解决「什么必须驻留」；论文量化指出 top-$k$ 解码的 serving 瓶颈是防备未来任意选择的全量驻留，并用 naive offload 的带宽反设论证「必须靠局部性」。
  • indexer 无关且精确：相对并发的 ESS（DeepSeek-V3.2 专用、仿真评估）与 ECHO（NSA 专用、以预测式预取为中心），HiSparse 用统一接口消费任意选择器的逻辑位置（DSA、NSA、Quest 均接入），只改 KV 的驻留位置，输出与全驻留逐位相同。
  • 局部性优先的融合解析：LRU 管理的 GPU cache 让多数选择驻留、把 IO 负载本身降下来而非只靠重叠隐藏；hit 检测、victim 选择、host 拷贝、页表更新压进单个融合 kernel，并被捕获进 decode CUDA graph，不付逐层 launch 与中间态落 HBM 的代价。
  • 选择可先知时的精确预取：对显式共享选择的模型（IndexShare：少数 anchor 层跑 indexer、多数 shared 层复用其选择），anchor 层的 miss 计划被重放进 shared 层缓存，传输与计算重叠；推测式预取实测无端到端收益，被论文否定。

方法概述

HiSparse 解耦「逻辑可用」与「物理驻留」：host pinned DRAM 维护每请求完整 KV 的权威副本；GPU 侧每请求每层预留固定 $B$ 格缓存（$B \ge k$，实用范围 $[2k, 4k]$），页表记录逻辑位置到槽位（或 host-only 哨兵），每层独立 LRU 决定谁留下。解码 KV footprint 从随上下文线性增长的 $N_{\text{batch}} N_{\ell} L_{\text{ctx}} W_{\text{KV}} s$ 变为常数 $N_{\text{batch}} N_{\ell} B W_{\text{KV}} s$；模型选择状态（indexer key 等）始终留在 GPU 不分页。

解码每步每层先跑 Resolve kernel：选择集装进共享内存哈希表，并行探测 $B$ 个槽位标记 hit 与可逐出者，scan 压缩后更新 LRU 并选出 victim，负责 miss 的线程用 GPU-assisted IO 从 pinned host 内存直接向量化拷贝，最后发布与逻辑位置对齐的物理槽位表；此后注意力只读 GPU 槽位。新产生的 KV 写入预留槽位并异步写回 host。实现合并进上游 SGLang，约 2200 行 Python 加一个 CUDA kernel 头文件（Resolve 的两种布局变体与 copy-only kernel），--enable-hisparse 启用。

关键结论

  • 长上下文峰值吞吐最高 4.7 倍：Qwen3+Quest 在 GH200 上 200K 输入从 111 提到 520 tokens/s；GLM-5.1（DSA）32K 为 3.1 倍；短上下文（4K）与基线相当（GLM-5.1：2288$\to$2280）。条件：未修改 SGLang v0.5.11 全 KV 基线、峰值吞吐口径、$k = 2048$。
  • 容量与上下文长度解耦：GLM-5.1 一个 128K 请求的 KV 从约 13 GB 降到 $B = 4096$ 时约 0.4 GB（约 30 倍）；约 60 请求 batch 的解码 KV 预算从约 240 GB 降到约 25 GB，容量红利可兑换为更高并发或更便宜的部件。
  • LRU 把选择局部性变成约 87% 命中：$B = 2k$ 时 miss 13.4%，对比只存 top-$k$ 的 30% 与 Bélady 理想下界 8.2%。条件：GLM-5.1 服务 100K token prompt 的单 trace 前 1000 步统计。
  • 精确预取隐藏约一半 IO，代价可控：GLM-5.2（IndexShare，78 层 = 21 anchor + 57 shared）上 TPOT 的 IO 暴露从 7.7 降到 3.0 ms/token（并发 8），预取吞吐达 no-IO oracle 的 85%。剩余代价：TPOT 仍高于全 KV 基线，容量上限从 HBM 换成 host DRAM（Grace 平台 LPDRAM 约 480 GB，与 HBM 相当时优势缩小），$B$ 为部署时静态配置。
