# DeepSeekMoE 教学大纲

## 1. 页面开头

### 钩子问题
"一个 MoE 层有 16 个专家、每 token 选 2 个，能组合出 120 种搭配；把每个专家切成 4 份、变成 64 个小专家、每 token 选 8 个，组合数跳到 44 亿种——而每个 token 的计算量一分没涨。这是怎么做到的，又为什么有用？"

### 一句话解释
DeepSeekMoE 是一种 MoE 架构，通过把每个专家切成更小的多个专家并隔离出对所有 token 恒激活的共享专家，在保持每 token 计算量不变的前提下让专家学得更专注、更不重叠。

### 要解决的具体问题
传统 top-K MoE 专家数量有限，存在知识混合（一个专家被迫塞多种知识）和知识冗余（多个专家各自重学同一份通用知识），导致专家无法获得"互不重叠且聚焦"的专门知识。

### 学习承诺（与 scope.md Q1–Q4 一致）
见 learning-goals 组件。

### 首个具体场景
用 16 专家 top-2 的标准 MoE 起手，指出它的两个毛病，再逐步引入细粒度分割与共享专家隔离。

### 与第一章的过渡
"先看清传统 MoE 到底有哪两个毛病，才知道 DeepSeekMoE 的两把刀分别砍向哪里。"

### 页面开头组件选择
- 01 callout（blue）：用一句话点出"两策略 + 计算量不变"的核心。
- 02 context-box：本页位置、读者设定、不讲什么。
- 03 learning-goals：Q1–Q4。
- 05 blockquote.meta：主要依据论文。

### S2：把专家切小——细粒度专家分割
- 主要教学问题：怎样在每 token 计算量不变的前提下让组合更灵活？
- 对应范围：Q2；C4、C5、C7；F3、F4、F7。
- 正文要点：
  - 机制（C4）：每个专家 FFN 中间隐藏维度 → 1/m，专家数 N → mN，激活数 K → mK。
  - 计算量守恒（C7、F7）：mK·(1/m) = K，与原来相同；专家参数总量 mN·(1/m) = N，也不变。
  - 贯穿手算例子（教学示例）：4 专家 top-1，m=2 → 8 小专家 top-2。参数量：4·1 = 4 单位 → 8·0.5 = 4 单位；计算量：1·1 = 1 → 2·0.5 = 1。组合数：C(4,1)=4 → C(8,2)=28。
  - 论文真实数字（N8）：N=16, K=2, m=4 → C(16,2)=120 → C(64,8)=4,426,165,368。
  - 为什么组合灵活有助于专门化：每个专家更小、更专注一种知识，token 可以同时从多个小专家那里"挑"不同知识，而非被塞进一个大专家。
- 讲解材料及职责：
  - 公式 F3/F4：表达细粒度 MoE 层与门控。
  - 手算例子（教学示例，便于手算）：4 专家 split 2。
  - 对照表格：分割前后的参数量、计算量、组合数。
- 前置知识安排：FFN 中间隐藏维度决定参数量（前置页已讲，引用）。
- 完成检查：(1) 手算 4 专家 top-1 在 m=2 下的参数量与每 token 计算量，说明二者均不变；(2) 说出组合数从 C(4,1) 变为 C(8,2) 的值；(3) 说明为什么"专家更小、激活更多"能让知识更专注。
- 过渡："切小解决了'一个专家塞太多'。但'通用知识被每个专家各学一份'还没解决——那是第二把刀的事。"

### S3：把通用知识拎出来——共享专家隔离
- 主要教学问题：共享专家如何消除冗余，与路由专家如何分工？
- 对应范围：Q3；C6、C7；F5、F6、F7。
- 正文要点：
  - 机制（C6）：隔离 K_s 个共享专家，对所有 token 恒激活、不参与 router 打分与 top-k，承载通用知识；路由专家数 mN → mN-K_s、激活路由专家数 mK → mK-K_s，维持计算量守恒。
  - 完整公式（F5）：h = Σ_{i=1}^{K_s} FFN_i(u) + Σ_{i=K_s+1}^{mN} (g_{i,t} FFN_i(u)) + u。第一项无 g（恒激活），第二项有 g（稀疏）。
  - 门控（F6）：路由只在 K_s+1..mN 范围内选 mK-K_s 个；加 K_s 个共享，总激活仍为 mK。
  - 计算量守恒（F7）：K_s·(1/m) + (mK-K_s)·(1/m) = mK·(1/m) = K，与细粒度一致。
  - 贯穿手算例子推进：在 S2 的 8 小专家（m=2）基础上加 1 个共享专家（K_s=1），路由专家 8→7、激活路由 2→1，加共享总激活仍 2。参数量：7·0.5 + 1·0.5 = 4，不变；计算量：1·0.5 + 1·0.5 = 1，不变。
  - 为什么共享专家不参与路由：通用知识每个 token 都要用，让 router 反复"选中"它反而重新引入冗余；恒激活等于把通用知识压缩到一份。
  - 论文真实配置（N3、N5）：2B 模型 1 shared + 63 routed，激活 1+7=8；16B 模型 2 shared + 64 routed，激活 2+6=8。
- 讲解材料及职责：
  - 公式 F5/F6：表达共享 + 路由 + 残差与路由范围。
  - 贯穿手算例子推进：在 S2 基础上加共享专家。
  - ASCII 图示：展示 shared（恒激活）与 routed（稀疏）的分工。
- 前置知识安排：shared/routed expert 基本区分（前置页 C4，引用）。
- 完成检查：(1) 写出完整 DeepSeekMoE 层公式并说明哪部分恒激活、哪部分稀疏；(2) 在 S2 的 8 小专家基础上加 1 共享专家，手算路由专家数、激活数、参数量、计算量；(3) 说明共享专家为什么不参与路由。
- 过渡："两把刀都到位了。但'计算量不变、组合更灵活、冗余更少'听起来只是合理——它真的换来更好的性能吗？要看实验。"

### S4：相同算力下真的更好——2B、16B 与 145B 的证据
- 主要教学问题：在相同计算预算下，DeepSeekMoE 相对 GShard 的优势体现在哪些数字上？
- 对应范围：Q4；C7；N1、N2、N4、N6、N7。
- 正文要点：
  - 三架构计算量恒定（C7）是所有对比的前提：标准、细粒度、完整 DeepSeekMoE 专家参数与每 token 计算成本相同。
  - 2B 对比（N1、N2）：DeepSeekMoE 2B 与 GShard 2.9B（1.5× 专家参数与计算）性能相当；并接近同总参数的稠密模型（MoE 的上界）。
  - 16B 对比（N4、N6）：DeepSeekMoE 16B 与 LLaMA2 7B 性能相当，仅需约 39.6% 计算；可在 40GB 显存单卡部署，推理约 2.5× 7B 稠密速度。
  - 145B 对比（N7）：DeepSeekMoE 145B 与 DeepSeek 67B 性能相当，仅需 28.5%（可能 18.2%）计算。
  - 强调：性能结论依赖论文实验配置，不可外推到任意规模（M4 边界）。
- 讲解材料及职责：
  - 对照表格：三组对比的参数量、激活参数、计算量、性能结论。
- 前置知识安排：无新前置。
- 完成检查：(1) 说出三组对比的"谁 vs 谁、计算比例、性能结论"；(2) 说明三架构计算量恒定为什么是这些对比的前提；(3) 指出性能结论不可外推到任意规模。
- 过渡："两策略在 2B、16B、145B 三个规模上都成立。最后看一下它对后续架构的影响。"

### S5：影响与继承——Stable LatentMoE 等

  - 边界：本页只讲继承关系，不展开 Stable LatentMoE 的机制。

## 3. 讲解顺序

S1（问题）→ S2（第一把刀：切小）→ S3（第二把刀：共享）→ S4（证据）→ S5（继承）。先讲为什么需要它（S1 的两个毛病），再讲是什么（S2/S3 两策略），再讲证据（S4），最后讲影响（S5）。一次只引入一个新变量：S2 引入 m，S3 引入 K_s。

## 4. 贯穿例子

用"4 专家 top-1，m=2"作为贯穿手算例子：
- S2 首次出现：4 专家 top-1 → 8 小专家 top-2，参数量 4→4、计算量 1→1、组合数 4→28。
- S3 推进：在 8 小专家基础上加 1 共享专家，路由 8→7、激活路由 2→1、总激活 2、参数量 4→4、计算量 1→1。
单一例子自然覆盖 S2/S3 的核心计算。S4 用论文真实数字（2B/16B/145B）作为外部证据，不复用教学例子。
