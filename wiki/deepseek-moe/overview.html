DeepSeekMoE

DeepSeekMoE 把每个专家切成更小的多个专家、再隔离出对所有 token 恒激活的共享专家，在不涨每 token 计算量的前提下让专家学得更专注、更不重叠。

更新于 2026-08-09 · 依据 Dai et al. 2024 (arXiv:2401.06066)

为什么需要它

传统 top-K MoE（背景见 MoE 大模型推理与服务基础）专家数量有限，有两个毛病：

  • 知识混合：一个专家收到的 token 涵盖多种知识，被迫把截然不同的东西塞进同一份参数，难以同时利用。
  • 知识冗余：不同专家都可能需要通用知识（如基本语法），于是各自学一份，参数重复。

两者共同妨碍"专家专门化"——让每个专家获得互不重叠且聚焦的知识。

核心直觉

  • 把专家切小：每个专家 FFN 中间维度缩为 $1/m$，专家数从 $N$ 变 $mN$、每 token 激活数从 $K$ 变 $mK$。每 token 计算量 $= mK \times (1/m) = K$，一分没涨；但组合数从 $\binom{N}{K}$ 涨到 $\binom{mN}{mK}$（论文例子：120 → 44 亿）。
  • 隔离共享专家：$K_s$ 个专家对所有 token 恒激活、不参与 router 打分，专门承载通用知识；路由专家只承载专门知识，不必再各学一份通用知识。
  • 连带调整维持守恒：引入 $K_s$ 个共享专家后，路由专家总数从 $mN$ 降为 $mN - K_s$、每 token 激活路由专家从 $mK$ 降为 $mK - K_s$；总激活仍是 $mK$，计算量仍守恒。
  • 共享专家不参与路由的原因：通用知识每个 token 都要用，让它参与 router 竞争要么占 top-k 名额、要么偶尔落选，两种都会重新引入冗余或缺失。

关键结论与边界

  • 三架构计算量恒定：标准 top-K、细粒度分割、完整 DeepSeekMoE 的专家参数与每 token 计算成本相同——这是所有性能对比的前提。
  • 实证：DeepSeekMoE 2B 与 GShard 2.9B（1.5× 专家参数与计算）性能相当；16B 与 LLaMA2 7B 性能相当，仅需约 39.6% 计算；145B 与 DeepSeek 67B 性能相当，仅需 28.5%（可能 18.2%）计算。
  • 边界：性能结论依赖论文实验配置（2B/16B/145B），不可外推到任意规模；组合数变多是机制潜力，性能提升靠实验验证，不能单从机制断言。
  • 后续继承：DeepSeek-V3 继承 shared+routed 组织但改了路由打分（sigmoid + 偏置）；Stable LatentMoE 也继承了这一组织，在其上做隐空间路由与稳定化。
