PP 负载均衡

让流水线各 stage 环环等长：推理 PP 的忙闲不均从哪来，token 切分与 batch 配平怎么做。

更新于 2026-09-03

它是什么

PP 负载均衡是推理系统中让流水线各 stage 的执行时间保持相近、减少气泡的切分与调度机制。流水线并行把模型按层切给不同节点、只在 stage 边界通信；代价是后级要等前级、流水线填不满时产生气泡，而一次迭代的节拍由最慢的 stage 决定。

问题从哪来

推理场景有两个放大器。一是单条长请求整体进入流水线：128K 到 1M token 的 prompt 让下游 GPU 长时间空等。二是注意力的增量特性：位置越靠后要交互的历史越多，同样大小的 chunk 越跑越慢，各 stage 的步长随进度漂移。高并发下还有第三层：每个调度步的 micro-batch 计算量忽大忽小。

核心机制

  • token 维度切分：因果注意力保证位置只依赖历史，因此同一条请求的不同 token 段可以同时在不同 stage 上计算。切点前长后短——前面交互少多装 token、后面交互多少装，让各片段成本接近相等。
  • 动态时间对齐：把累计运行时间拟合为前缀长度的二次函数，解增量时间方程确定下一个 chunk 的大小，后段 chunk 逐步缩小，对齐各 stage 的节拍。
  • batch 维度配平：解耦 prefill 与 decode 的调度——decode token 均摊到全部在飞 micro-batch；prefill 按积压量与 KV cache 空闲率动态定 batch 大小，水位过低时暂停 prefill 防止 decode 被抢占重算。
  • 两个维度可组合：联合优化先按每个候选 batch size 求序列切分，再解背包问题定 batch 切分。

关键结论与边界

  • 均衡的对象是执行时间，不是元素个数：均分 token 数或请求数都不等于均衡，优化目标是压最慢片段。
  • 切分不是越细越好：片段太小吃不满 GPU（单 token 与 256 token 的前向时间可以相同），chunk 尺寸有利用率下限。
  • token 维切分依赖因果注意力，双向注意力模型不适用；短上下文下无显著额外开销，收益场景是长上下文。
  • 性能数字都绑定条件：本页引用的加速比（如 prefill 吞吐 3.31 倍、吞吐提升 11% 到 398%）各自对应特定的模型、硬件与基线配置，见完整说明页的来源与范围说明。

代表系统：TeraPipe（机制源头，训练场景）、Mooncake CPP（推理 prefill 落地）、SGLang 动态 chunk（时间对齐）、gLLM token throttling（batch 配平）。机制细节、手算示例与来源定位见完整说明页。
