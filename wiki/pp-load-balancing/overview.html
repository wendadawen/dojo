PP Load Balancing

大语言模型（LLM）按已有内容逐个生成文本时用流水线并行（PP）部署，把流水线每一级（stage）每一步的执行时间拉齐、压小设备空等（气泡）的 token（词元）切分与 batch（一次处理的一组请求）配平做法。

把各 stage 每步执行时间拉齐

PP（pipeline parallelism，流水线并行）把模型的层按顺序切成若干段，每段放在一组设备上，这一组叫一个 stage，前一个 stage 算完把中间结果传给下一个。一条请求的输入先被切成 token（词元，模型处理文本的最小单位）串，逐段流过流水线。流水线里各段设备等输入、等下游的空档叫气泡。PP 负载均衡就是让各 stage 每一步的执行时间保持相近、把气泡压小的切分与调度做法。它不改变模型本身的计算，只改请求怎么切、每一步各排多少。

节拍由最慢的 stage 决定

一次前向（模型从输入算到输出的一遍计算）的总时间由最慢的 stage 决定，只要一个 stage 比别人久，其余 stage 就在等它，气泡由此出现。推理把这种空等放大两次：单条很长的请求整体进入流水线时，输入到 128K 甚至 1M token，第一个 stage 要算很久，后面的 stage 长时间空等；注意力的计算量还随位置变化，位置越靠后要与越多的历史 token 交互（见 标准注意力），同样大小的片段越往后越慢，各 stage 的步长（每一步的执行时间）越拉越开。并发请求多时，每一步里各 micro-batch（微批次，一次迭代中并行推进的最小批次部分）的计算量又会有波动。

按执行时间对齐，不是按条数

均衡的对象是各 stage 的执行时间，不是 token 的条数。token 维度：把一条请求的输入序列切成若干片段分给不同 stage，切点前长后短，靠后的片段装更少 token，以抵消它更重的注意力。chunk（切成一段的 token 块，见 chunked prefill）若取固定大小，会随前缀（已处理的历史 token）变慢，各 stage 的步长越差越多；改用随前缀缩小的 chunk，就能让各 stage 的节拍对齐。batch 维度：把并发的 decode token（生成阶段每一步新产出的 token）按 token 数均摊到各 micro-batch，让每一步的计算量接近。
