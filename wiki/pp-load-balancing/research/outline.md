# 文章大纲：PP 负载均衡

贯穿示例（全文共用）：构造一条 12 token 的请求和 $K=3$ 个 stage 的流水线。成本代理：位置 $t$ 的注意力交互次数为 $t$（与之前每个 token 各交互一次），片段成本取其位置和；标注为构造示例，省略项在「简化条件」中说明。各章复用时只增加新概念：

- Ch1：整条请求不切分进入流水线 → stage 2/3 长时间空等（空等全景图）。
- Ch2：切成片段后三个 stage 同时忙碌；手算均分 $4{+}4{+}4$ 得片段成本 $(10,26,42)$、$\max=42$，前长后短 $7{+}3{+}2$ 得 $(28,27,23)$、$\max=28$，按目标函数 $T=\sum t_i+(K-1)\max t_j$ 得 $162 \to 134$（约 $1.21\times$）。
- Ch3：同一流水线连续处理等大 chunk，chunk 时间随前缀增长的漂移使后级等待逐步累积（时间表手算）。
- Ch4：引入并发——8 条 decode 请求与积压 prefill 的 $\#D$、$\#P$ 配平手算。

## 页面开头

1. 最小场景：跨机部署的大模型用 PP（前置引用模型并行页），一条 128K token 的请求到达——第一个 stage 要算很久，后面的 stage 只能等；反过来高并发时每一步 micro-batch 的计算量忽大忽小。提出问题：流水线的节拍由最慢的一环决定，怎么让它环环等长。
2. 简要解释：PP 负载均衡 = 让各 stage 每一步的执行时间相近的切分与调度机制；公开文献没有统一名称（内部叫 PPLB），相关机制散见于 pipeline stage balancing、token-level pipeline parallelism、balanced pipeline parallelism 等名义下；两条主线：把一条请求沿 token 维度切开（空间上补齐），把并发请求的计算量在 micro-batch 间配平（时间上补齐）。
3. 前置知识引用段：模型并行（PP 定义与气泡公式）、chunked prefill（chunk 与 token budget）、KV cache、causal attention，各给概念页链接，声明只使用结论。
4. 核心问题（= scope 的 Q1–Q5）。
5. 首个示例预告 + 过渡到第 1 章。

## 1. GPU 为什么空转：两类等待与两个放大器

- 章节问题：
  1. PP 推理中 GPU 空闲来自哪两类依赖？
  2. 为什么长上下文和注意力的增量特性让失衡更严重？
- 答案要点：inter-stage 依赖（后级等前级）与 inter-batch 依赖（并发 micro-batch 数受流水线深度限制）[C1]；失衡也分 inter-stage 与 inter-batch 两类 [C2 前半]；放大器一是单条长请求整体进入流水线时下游长时间空闲、且单次前向要保存整条序列的中间状态 [C3]；放大器二是同尺寸 chunk 的处理时间随前缀增长非线性增加 [C4 前半]；代价引用气泡公式 $\frac{K-1}{K-1+M}$（记号映射：模型并行页的 $p,m$ 对应本文 $K,M$）[F1]。
- 正文要点与材料：
  - 贯穿示例 v1 + SVG 网格时间线图（stage × 时间，整条请求竖条 + 大片空白），图职责：让"空等"直接可见。
  - 两类依赖/两类失衡的命名表（gLLM 的二分法），表职责：给全文提供统一词汇。
  - 范围：Q1；C1、C2 前半、C3、C4 前半、F1；B（贯穿示例）。
- 过渡：空等有两个来源——单条请求太粗切不开、多个 micro-batch 忽胖忽瘦；下一章先解决前者。

## 2. token 维度切分：把一条请求拆进流水线

- 章节问题：
  1. 自回归性质为什么允许在单条序列内部做流水线？
  2. 均分序列为什么计算量递增，最优切分为什么前长后短？
  3. TeraPipe 目标函数的两项分别是什么？
  4. CPP 在 Mooncake 的 prefill 池里怎么组织节点与 chunk？
- 答案要点：位置 $t$ 只依赖 $\le t$ 的 token，当前片段在 stage $k$ 计算时，更早的片段可同时在 stage $k+1$ [C5，引用 causal attention 前置页]；位置越靠后交互越多，片段成本依赖自身长度与全部前缀 [C6、F3]，均分使成本递增；流水线总时延由最慢 stage 决定，最优切分前长后短 [C6]；目标 $T^*=\min\{\sum_i t_i+(K-1)\max_j t_j\}$，第一项是单 stage 总前向时间、第二项是流水线开销 [F2]；DP 求解（递推折叠块）[辅助材料]；训练场景数字 [N1、N2]；Mooncake CPP：每 $X$ 节点一组流水线、chunk $\le$ `prefill_chunk`、同请求不同 chunk 同时处理、边界通信可与计算重叠、短上下文无显著开销 [C7]，动机是跨节点 TP 的 per-layer all-reduce 与 SP 的利用率问题 [C8、N3]。
- 正文要点与材料：
  - 贯穿示例 v2 手算表：均分 $(10,26,42)$ vs 前长后短 $(28,27,23)$，$T=162\to134$；表职责：把「均衡的是时间不是个数」变成可复算的数字。
  - SVG 网格图（与 Ch1 同构）：切分后片段斜向填充流水线；图职责：展示序列内流水的时空模式。
  - 折叠块：DP 递推与复杂度（补充：）；含线性项的二次成本模型讨论（补充：——说明成本模型选择会影响最优切分、工程用实测拟合，呼应 M1）；DP 最小可运行代码（代码：，验证 $7{+}3{+}2$ 最优）；Mooncake 与 TeraPipe 的场景差异（补充：训练含反向 vs 推理 forward-only，工程取舍见 M5）。
  - 正文明确：TeraPipe 面向同步训练，推理取其 forward 机制（M5）。
  - 范围：Q2；C5–C8、F2、F3、N1–N3、B。
- 过渡：切点定好后还有时间维度的坑——同样大小的 chunk，处理时间并不一样长。

## 3. 时间对齐：固定 chunk 的漂移与动态 chunk

- 章节问题：
  1. 固定大小的 chunk 为什么在更高的 PP rank 上错配更严重？
  2. 动态 chunk 怎么确定下一个 chunk 的大小？
- 答案要点：增量注意力使同尺寸 chunk 时间随前缀 $L$ 非线性增加，错配沿流水线传播、在更高 rank 复合放大，实际气泡比率超过理论值 [C4 完整]；SGLang 把累计运行时间建模为 $L$ 的二次函数，解 $\mathrm{Runtime}(L+\Delta L)-\mathrm{Runtime}(L)=\mathrm{Runtime}(\text{初始 chunk})$ 得 $\Delta L$，随 $L$ 增长逐步缩小以对齐各 stage 执行时间 [F4]；预测值向下对齐到 $\max(\text{page size},64)$ 倍数；smooth factor 默认 0.75、推荐 0.6–0.85 [N4]。
- 正文要点与材料：
  - 贯穿示例 v3 漂移时间表（4 个等大 chunk 在两个 stage 的开始/结束时刻手算），表职责：让"级联放大"从一句结论变成可追踪的数字。
  - SVG 漂移累积甘特图：固定 chunk（等待逐步拉大）vs 动态 chunk（后段缩小、节奏对齐）；图职责：两种策略的对照。
  - 折叠块：SGLang 三步调参法与异步 P2P/事件循环工程细节（补充：）。
  - 数字：DeepSeek-V3.1 3.31×/30.5%、TTFT 67.9%/81.1%、82.8% 扩展效率 [N4，带条件]。
  - 范围：Q3；C4、F4、N4。
- 过渡：单条请求内部的时间对齐解决不了另一件事——并发请求拼 batch 时每步计算量依然忽大忽小。

## 4. batch 维度均衡：配平 micro-batch 之间的计算量

- 章节问题：
  1. 固定 token budget 为什么会波动？
  2. gLLM 怎么分别调节 decode 和 prefill 的 token 数量？
- 答案要点：Sarathi-Serve 固定预算混排 chunked prefill 与 decode，波动来自错过混批机会与 decode token 分布不均，缩小预算会惩罚 prefill 速率 [C9，引用 chunked-prefill 页作背景]；gLLM 解耦并引入全局反馈：decode 按 $\#D=\#RD/\#PP_{\text{depth}}$ 均摊 [C10、F5]；prefill 合并 $\#P=\max(\min(\#WP/\#T,\#MaxP\times\frac{KV_{\text{free}}-KV_{\text{thresh}}}{1-KV_{\text{thresh}}}),\#MinP)$，KV 空闲率低于阈值时暂停 prefill 防止 decode 被抢占重算 [C11、F5]。
- 正文要点与材料：
  - 贯穿示例 v4 手算：$\#RD=96$、$\#PP_{\text{depth}}=4$ → $\#D=24$；$\#WP=6144$、$\#T=8$ → $768$；$KV_{\text{free}}=0.6$、$KV_{\text{thresh}}=0.05$、$\#MaxP=2048$ → $1189$；$\#P=768$；表职责：把两个公式变成可代入的数字。
  - gLLM 调度决策伪代码（折叠块，代码：，基于论文描述的构造简化版）。
  - 数字与佐证：11%–398%、拐点 2–6× [N5，带条件]；一念多阶段流水线 + batch 间均衡、5K→9K [N6，折叠块]。
  - 范围：Q4；C9–C11、F5、N5、N6。
- 过渡：两类做法分别补空间和时间，它们能不能一起用、什么时候不该用。

## 5. 组合与边界：什么时候用哪条路

- 章节问题：
  1. token 维度与 batch 维度能否同时使用？
  2. 哪些场景不适合这两类做法？
- 答案要点：TeraPipe 对两维度联合优化——每个候选 batch size 跑 token 维 DP 得 $T_b$，再解一维背包定 batch 切分 [C12]；batch 足够大时退化为只切 batch 维 [C13]；SGLang PP 兼容其他并行、PD 分离与 HiCache [C15]。边界：切分过细 GPU 利用率下降（单 token 与 256 token 前向时间相同）[C14]；短上下文 CPP 无显著开销也无收益 [C7 限定语]；token 维切分依赖单向自回归，双向注意力不适用 [C5 条件]；gLLM 只解决 inter-batch 失衡 [C2 后半]；所有性能数字必须带条件引用。
- 正文要点与材料：
  - 两类做法对照表：解决哪类失衡 / 代价 / 代表系统 / 关键参数（表职责：收束全文）。
  - 范围：Q5；C2 后半、C12–C15、各 N 的条件。
