    MoonEP 完美均衡专家并行：让每个 EP rank 恰好收到 S×K token

    MoE 训练里，每个 EP rank 收到多少 token 完全由 router 决定，而 router 偏好随每个 micro-batch、每一层都在变。结果有的 rank 收到 10 倍于其他 rank 的 token，有的几乎空转；通信 buffer 的形状每次都不一样，每层都得让 CPU 跟 GPU 同步一次才能确定本层到底算多少。MoonEP 解决的就是这件事——让每个 rank 每层都恰好收到 $S\times K$ 个 token，把"动态形状"彻底改成"静态形状"。

    MoonEP 是 Moonshot AI 在 K3 训练系统里提出的 MoE 训练专家并行方案：在保留 DeepEP 等传统 EP 总体计算流的前提下，通过在线规划和迁移"冗余专家"让每个 EP rank 恰好收到 $S\times K$ 个 token，从而把负载、通信 buffer 形状和每层计算形状都变成静态已知（论断 C2）。本文依据 K3 技术报告 §5.2.1 与 §E 附录，不引用未公开的源码。

    MoE 与 EP

    本文语境
    $S$ = 每 rank 本地序列长度；$K$ = 每 token 选的专家数；$E$ = 专家总数；$R$ = EP size（EP rank 数）。只讲训练场景。

    主要依据：Kimi K3 Technical Report §5.2.1（Perfectly Balanced Expert-Parallel MoE Training）与 §E（MoonEP General Upper Bound Proof）。MoonEP 开源仓库 github.com/MoonshotAI/MoonEP；本页不引用其源码。

    下面先用一个最小例子把"不均衡"具体化。教学示例。 设 $E=4$ 个专家、$R=2$ 个 EP rank、每 rank 本地 $S=4$ 个 token、每 token 选 $K=1$ 个专家。每 rank 持有 $E/R=2$ 个本地专家：rank 0 持专家 $\{0,1\}$，rank 1 持专家 $\{2,3\}$。每 rank 发出 $S\times K=4$ 个 token-expert pair，全网络总 pair 数 $S\times K\times R=8$。完美均衡时每 rank 收到 $S\times K=4$ 个 pair。

    传统 EP 为什么让 rank 间负载不均衡？MoonEP 的核心思路是什么？

    先回顾 EP 的基础数据流（详细见 MoE 大模型推理与服务基础的 EP 章节）：每个 token 选 $K$ 个专家，专家被均匀分片到 $R$ 个 rank 上、每个 rank 持有 $E/R$ 个本地专家。一个 token 想算某个专家，就得把它的激活送到那个专家所在的 rank（home rank）上算，算完再送回原 rank。一次 forward 由两段 all-to-all 组成：dispatch 把 token-expert pair 送到 home rank，combine 把专家输出送回原 rank。

    关键问题在于：每 rank 收到多少 pair 完全取决于"我持有的 $E/R$ 个专家被全网 token 选了多少次"。这个数由 router 的偏好决定，而 router 偏好随每个 micro-batch、每一层都在变。报告原文（论断 C1）给出两个直接后果：计算不均衡降低训练吞吐，routed-expert 激活形状动态变化导致显存碎片。

    用贯穿例子把不均衡具体化。教学示例。 设 router 输出极端不均衡——8 个 token 的选择全部落到专家 0（在 rank 0 上）。那么 rank 0 收到全部 8 个 pair（过载 2 倍），rank 1 收到 0 个（完全空转）。总量守恒（公式 F4）仍成立：$8+0=8=S\times K\times R$，但每 rank 收到的数远偏离平衡值 $S\times K=4$。

    传统 EP dispatch（router 极端偏好专家 0 时）

rank 0 持专家 {0,1}    rank 1 持专家 {2,3}
   8 个 pair ──dispatch──►  [rank 0: 收 8 个 pair]   过载 2×
                           [rank 1: 收 0 个 pair]  完全空转

  每 rank 平衡值 = S×K = 4；实际 {8, 0} → 不均衡
  每层 token 数变化 → 每层都要 host-device 同步拿形状

    MoonEP 的核心新对象是冗余专家：把某个 home rank 上的专家临时复制到另一个 rank 上，让那个 rank 在本地处理原本要发出去的 token。这不是常驻副本——forward 阶段从当前 micro-batch、当前层 router 输出在线规划需要哪些冗余专家并预取，backward 阶段把冗余专家的梯度暂存到本地 reduce buffer、计算完成后再归约回 home rank。整个流程保留了 DeepEP 等传统方案的总体计算流，只是在 dispatch 之前多了一步在线规划（论断 C2）。

    有了冗余专家，MoonEP 把目标定为完美均衡：每 rank 恰好收到 $S\times K$ 个 token（论断 C3）。总量守恒保证这总是可能——$R$ 个 rank 各收 $S\times K$，总和 $S\times K\times R$ 恰好等于全网发出的 pair 总数。回到上面的例子：rank 0 过载 8 个、rank 1 空转 0 个，要把 rank 0 上的 4 个 pair 迁到 rank 1 上算。这 4 个 pair 都想算专家 0，所以 rank 1 需要专家 0 的一个副本——这就是一个冗余专家。

    维度传统 EP（如 DeepEP）MoonEP 完美均衡
    每 rank 收到 token 数由 router 偏好决定，随层和 micro-batch 变化恒等于 $S\times K$
    计算形状每层动态变化所有层静态已知
    是否引入新对象否冗余专家（forward 预取、backward 归还）

    本章回答了 Q1：传统 EP 不均衡的根源是 router 偏好动态、rank 收到 pair 数完全被动；MoonEP 引入冗余专家作为负载载体，把过载 rank 的 token 迁到空转 rank 上本地计算，从而让每 rank 恰好收到 $S\times K$。但这里马上出现下一个问题：要迁多少个冗余专家才够？

    冗余专家要多少个才够？$E/R$ 上界与"基本紧"

    现在把"要多少冗余专家"形式化。给定一个 router 输出 $I$，规划 $P$ 决定哪些专家被复制到哪些 rank。记 $m_r(P)$ 为规划 $P$ 下 rank $r$ 上的冗余专家数。MoonEP 的规划目标是

    $$M(I)=\min_P\max_r\{m_r(P)\}.\quad\text{(F1)}$$

    这是个 min-max 目标——最小化"任意 rank 上冗余数的最大值"。注意它不要求每 rank 冗余数相等，只要求最坏那个 rank 别太离谱。这个目标的选择直接对应工程预留：每 rank 预留 $M(I)$ 个冗余槽位即可保证该 router 输出下有可行规划。

    报告 §E 证明了两个定理。第一个是一般上界（论断 F2）：

    Theorem 1：对任意 router 输出 $I$，$M(I)\le E/R$。

    证明的核心是一条关键引理：存在一种规划 $P^*$，使每 rank 的远端 token 全部来自同一个 home rank。构造过程是迭代的填充：初始每 rank 只有本地 token，按是否达到 $S\times K$ 分为 underloaded 和 overloaded；每次取一个 underloaded rank 和一个 overloaded rank，把 overloaded rank 上的 token 迁过来填满 underloaded rank 到 $S\times K$；overloaded rank 可能仍过载、可能恰好平衡、可能变 underloaded，放回对应集合。重复直到全部平衡。

    这个填充过程有两个关键性质。第一，每次 fill 让一个 underloaded rank 达到 $S\times K$ 且此后不再变化，所以至多 $R-1$ 次 fill 就终止。第二，每个 rank 至多被 fill 一次，所以它的远端 token 全部来自同一个 home rank。既然远端 token 同源 rank $s$，而这些 token 想算的都是 rank $s$ 上的本地专家，而 rank $s$ 至多有 $E/R$ 个本地专家（专家均匀分片），所以 rank $r$ 上的冗余专家数 $m_r(P^*)\le E/R$。这就推出 $M(I)\le E/R$。

    工程含义：每 rank 预留 $E/R$ 个冗余槽位就保证总有可行规划，训练不会因为"找不到满足条件的规划"而中断。

    补充：Theorem 1 构造性证明的完整复述与终止性论证

    报告 §E 原文（约 2947–2962 行）的完整论证：

    目标：证明对任意 router 输出 $I$，$M(I)\le E/R$。

    关键引理：存在规划 $P^*$ 使每 EP rank 收到恰好 $S\times K$ 个 token，且每 rank 的远端 token 全来自同一个 EP rank。

    构造：初始每 rank 只有本地 token，按是否达到 $S\times K$ 分为 underloaded / overloaded 两集合。重复以下操作：取一个 underloaded rank $u$ 和一个 overloaded rank $o$；把 $o$ 上的 token 迁到 $u$ 直到 $u$ 达到 $S\times K$；$o$ 可能仍过载、可能恰好平衡、可能变 underloaded，放回对应集合；$u$ 已平衡，移出 underloaded 集合。

    终止性：每次 fill 让一个 underloaded rank 达到 $S\times K$ 且此后不再变化（后续 fill 只往其他 underloaded rank 迁 token，不会动已平衡的 rank），所以至多 $R-1$ 次 fill 后所有 rank 平衡，过程终止。

    同源性：每个 rank 至多被 fill 一次（一旦平衡就移出 underloaded 集合，不会再被选为填充目标），所以它的远端 token 全部来自同一个 home rank。引理证毕。

    推出上界：rank $r$ 的远端 token 全来自 rank $s$，这些 token 想算的都是 rank $s$ 上的本地专家；rank $s$ 至多 $E/R$ 个本地专家（专家均匀分片），所以 $m_r(P^*)\le E/R$。故 $M(I)=\min_P\max_r m_r(P)\le\max_r m_r(P^*)\le E/R$。即公式 (28)。

    第二个定理给出界的基本紧性（论断 F3）：

    Theorem 2：存在 router 输出 $I^*$ 使 $M(I^*)=\lceil E(R-1)/R^2\rceil\approx E/R$（大 $R$）。

    最坏构造：让 rank 0 上的 $E/R$ 个专家收到 0 个 token，其余 $R-1$ 个 rank 上的 $E(R-1)/R$ 个专家均分全部 $S\times K\times R$ 个 pair。每个被使用的专家收到 $SKR^2/(E(R-1))$ 个 pair。rank 0 必须从远端收 $S\times K$ 个 pair，这些 pair 至少涉及 $\lceil S K / (S K R^2/(E(R-1)))\rceil=\lceil E(R-1)/R^2\rceil$ 个不同专家，所以 rank 0 至少需要这么多冗余专家。反向用填充过程构造规划可以把每 rank 冗余数控制在这个值，故等号成立。

    大 $R$ 时 $\lceil E(R-1)/R^2\rceil\approx E/R$，所以不可能有显著小于 $E/R$ 的通用上界——这就是"基本紧"。MoonEP 预留 $E/R$ 槽位不是工程经验值，而是有证明的最优预留。

    数字例子：在 $E=4,R=2$ 的贯穿例子里手算 $E/R$ 与最坏构造

    教学示例。 沿用 $E=4, R=2, S=4, K=1$，rank 0 持专家 $\{0,1\}$，rank 1 持专家 $\{2,3\}$。$E/R=4/2=2$，所以每 rank 预留 2 个冗余槽位即保证可行。

    情形 A（一般不均衡，用界但不达上界）：8 个 pair 全部落到专家 0（在 rank 0 上）。rank 0 过载（收到 8）、rank 1 空转（收到 0）。填充：把 4 个 pair 从 rank 0 迁到 rank 1。这 4 个 pair 都想算专家 0，所以 rank 1 需要专家 0 的副本——1 个冗余专家。验证 $1\le E/R=2$，未达上界。

    情形 B（最坏构造，界达到）：rank 0 上的专家 $\{0,1\}$ 收到 0 个 pair，rank 1 上的专家 $\{2,3\}$ 均分全部 8 个 pair（每个专家收 4 个）。rank 0 必须从远端收 $S\times K=4$ 个 pair。最优规划让 rank 0 取同一专家的全部 4 个 pair（如全取专家 2），只需 1 个冗余专家。验证 $M(I^*)=1=\lceil E(R-1)/R^2\rceil=\lceil 4\times 1/4\rceil=1<E/R=2$。此例展示小 $R$ 下 $\lceil E(R-1)/R^2\rceil$ 严格小于 $E/R$，$E/R$ 仅大 $R$ 渐近紧。

    本章回答了 Q2：$E/R$ 上界来自构造性证明的关键引理（远端 token 同源 → home rank 至多 $E/R$ 本地专家 → 冗余数 $\le E/R$）；基本紧来自最坏构造（rank 0 空载、其余均分）使冗余数达到 $\lceil E(R-1)/R^2\rceil\approx E/R$。预留 $E/R$ 槽位即保证总有可行解，且不可能显著更小。

    完美均衡怎样让 buffer 降到 $S\times K$、消除 host 同步？forward/backward 怎样跑？

    有了 $E/R$ 上界保证可行解，接下来看完美均衡带来的三个工程收益怎样落地，以及 MoonEP 的 forward/backward 与传统 EP 有什么不同。

    通信 buffer 从 $S\times K\times R$ 降到 $S\times K$

    传统 EP（如 DeepEP）在最坏不均衡下要支持 zero-copy 数据路径，需要 $S\times K\times R$ 的通信 buffer（论断 C7）——因为任何一个 rank 都可能收到接近全网总量的 pair，buffer 必须按最坏情况预留。注意这里的 $S\times K\times R$ 是最坏不均衡下的预留，不是 DeepEP 的常态开销；非最坏情况下 DeepEP 可以用更小 buffer。

    MoonEP 因为保证每 rank 恰好收到 $S\times K$ 个 pair，buffer 形状恒定为 $S\times K$，与 router 输出无关。$R$ 倍的节省在最坏情况下是直接的显存收益。

    静态形状消除每层 host 同步

    传统 EP 实现里，per-expert token 数随 step 和层变化，host 必须在每一层与 device 同步一次拿到真实计算形状，才能 launch 该层的 expert 计算 kernel（论断 C8）。这个同步点会 stall 流水线、放大 host-side kernel-launch overhead。

    MoonEP 让每 rank 每层都收 $S\times K$，所有层的计算形状静态已知——这意味着形状在 launch 前就确定，不需要 host 在每层等 device 报数。报告原文（论断 C8）说这"消除每层 MoE host 同步、缓解 host-side kernel-launch overhead"。

    forward：planning kernel + 零拷贝 dispatch

    MoonEP 的 forward 在传统 dispatch 之前多一步在线规划（论断 C4、C6）：

    1. planning kernel：从当前 micro-batch、当前层的 router 输出，在线计算哪些专家要复制到哪些 rank 上。报告明确说每步求精确最优代价过高（"prohibitively expensive"），所以 GPU planning kernel 只求近最优——开销可忽略、且总尊重 $E/R$ 上界。离线用 ILP 求代表性 case 的精确解作为 GPU kernel 的参考。
    2. 预取冗余专家：把要用的冗余专家权重拉到本地，在 routed-expert 计算之前完成。
    3. fused permute/unpermute dispatch：planning kernel 已经预计算了每个 token 的目的地，所以 token 直接被发到远端 rank 上expert-grouped 位置（同一专家的所有 token 连续存放，便于后续 GEMM），并直接返回通信 buffer 的 view 给计算 kernel，免中间拷贝（论断 C6）。

    backward：梯度暂存 + reduce 回 home rank

    backward 阶段冗余专家也要算梯度，但这些梯度属于 home rank 而非本地。MoonEP 的处理（论断 C5）：

    1. 暂存本地 reduce buffer：冗余专家的梯度先写到本地一个 reduce buffer，不直接写回原梯度 buffer。
    2. reduce 回 home rank：该 rank 上所有冗余专家计算完成后，把暂存的梯度归约回它们各自 home rank 的梯度 buffer。这里的 "reduce" 是跨 rank 归约到 home rank（结果只 home rank 得到，不是 all-reduce 让所有 rank 都得到），只针对冗余专家的梯度，不是全量梯度。

    这个流程保证冗余专家只是临时副本：forward 预取、用完即弃；backward 算完梯度归还原 rank。下一层、下一个 micro-batch 会重新规划。

    MoonEP forward 与 backward 数据流（vs 传统 EP 多了 planning 与 reduce-back）

[forward]
  router 输出 ──► planning kernel（在线规划冗余专家，近最优、尊重 E/R）
              │
              ├─► 预取冗余专家权重到本地
              │
              └─► fused permute：token 直接发到远端 expert-grouped 位置
                                 返回 buffer view，免中间拷贝
                                 每个收到 S×K 个 pair（完美均衡）

[backward]
  冗余专家梯度 ──► 本地 reduce buffer（暂存，不直接写回）
                │
                └─► 计算完成后 reduce 回 home rank 的梯度 buffer
                    （只针对冗余专家梯度，不是全量 all-reduce）
    伪代码：MoonEP forward 的 planning + dispatch（不是 Python） 
    输入：
  router 输出 I（当前 micro-batch、当前层的 top-k 选择）
  每个专家的 home rank 表 home[e] ∈ {0,…,R-1}
  每 rank 本地 token 数 S、每 token 选 K 个专家、专家总数 E、EP size R
  每 rank 预留的冗余槽位 E/R
状态：
  本地 token 池 local_tokens（每 rank S 个）
  通信 buffer recv_buf[S×K]（固定大小，形状静态）
  冗余专家权重缓存 redund_w[E/R]（最多 E/R 个槽位）
核心步骤：
  # 1. planning：在线决定哪些专家要复制到哪些 rank
  plan = planning_kernel(I, home, S, K, E, R)   # 近最优，m_r ≤ E/R
  
  # 2. 预取冗余专家权重
  for (expert e, target_rank r) in plan.redundant_copies:
      redund_w[r].pull(home[e], e)   # 从 home rank 拉专家 e 的权重
  
  # 3. fused permute dispatch：每 token 直接发到远端 expert-grouped 位置
  for token t in local_tokens:
      for expert e in t.selected_experts:
          dest_rank = plan.destination(t, e)   # 已预计算
          # token 直接写到 dest_rank 的 recv_buf 中 expert-grouped 位置
          # 不经过中间 buffer
  # 返回 recv_buf 的 view 给本地计算 kernel
  return recv_buf.view()

    本章回答了 Q3：完美均衡让 buffer 从 $S\times K\times R$ 降到 $S\times K$（因每 rank 恒收 $S\times K$）、让形状静态化消除每层 host 同步（因形状 launch 前就已知）；forward 在 dispatch 前加 planning + 预取，并用 fused permute 把 token 直接发到 expert-grouped 位置免中间拷贝；backward 把冗余专家梯度暂存本地 reduce buffer 再 reduce 回 home rank，使冗余专家成为临时副本。本章讲了三个工程收益，但 MoonEP 的边界在哪里？

    MoonEP 解决什么、不解决什么？与 ECHO、UltraEP、DeepEP 的区别

    MoonEP 解决的三个问题

    前三章已得结论，这里汇总：MoonEP 解决训练时 EP 的 rank 间负载不均衡（S1）、通信 buffer 形状动态（S3）、每层 host 同步开销（S3）。三个问题都源自同一个根因——router 偏好动态导致每 rank 收到 token 数动态——所以同一个机制（完美均衡）一次性解决。

    MoonEP 不解决的三个问题

    报告 §5.2.1 最后一段（论断 C9）明确指出：即使 rank 间总量完美均衡，每 rank 内部 per-expert token 数仍可能偏斜，固定顺序、workload-oblivious 的调度会让这种偏斜变成跨 SM 的 makespan 不均。这是 MoonEP 不解决的问题，由独立的 Expert-GEMM workload-aware scheduler 处理：launch 前根据当前 token 分布调参、launch 后固定；系数通过离线 autotuning 标定（具体算法报告未公开，本页不展开）。同时，shared expert 的 GEMM 分到独立 stream 与其他 kernel 重叠。

    另外两个 MoonEP 不解决的问题：router 本身的训练——router 是否均衡训练由辅助损失负责，MoonEP 只在 router 输出给定后做规划，不修改 router（这是常见误解，见下方边界）；内存碎片——由 §5.2.2 memory-efficient training 独立处理（如 unified activation manager、memory-efficient MoE），与完美均衡无关。

    与 ECHO、UltraEP 的区别

    报告 §5.2.1（论断 C10）明确对比：ECHO 和 UltraEP 预设冗余专家数或施加 per-rank token cap，训练在找不到满足 cap 的可行规划时会被迫中断，且 cap 本身需要手动调参、仍留残余不均衡。MoonEP 用 $E/R$ 这个有证明的、基本紧的上界预留槽位，保证总有可行解、不需手动调参。这是 MoonEP 区别于 ECHO/UltraEP 的核心：把"经验值"换成"有证明的界"。

    与 DeepEP 的区别

    MoonEP 保留 DeepEP 的总体计算流（论断 C2），只是在其上增加了在线规划与冗余专家迁移。所以 MoonEP 不是 DeepEP 的替代，而是 DeepEP 之上的一层扩展：DeepEP 提供 dispatch/combine 的基础数据路径，MoonEP 决定哪些 token 走冗余专家这条路。最坏 buffer 从 $S\times K\times R$ 降到 $S\times K$ 是这一扩展带来的直接收益。

    方案是否有界保证是否需手动调 cap最坏通信 buffer训练是否会因无解中断
    MoonEP是，$E/R$（Theorem 1）否$S\times K$不会
    DeepEP否（传统方案）—$S\times K\times R$（最坏）不会（但不保证均衡）
    ECHO否，预设冗余数是—会（无解时）
    UltraEP否，施加 token cap是—会（无解时）

    本章回答了 Q4：MoonEP 解决负载、buffer、host 同步三个问题；不解决 per-expert 偏斜（由 Expert-GEMM scheduler 处理）、router 训练（由辅助损失负责）、内存碎片（由 §5.2.2 处理）；与 ECHO/UltraEP 区别在"有界保证"对"预设 cap"，与 DeepEP 关系是"保留计算流 + 增加规划"。

    $E=4, R=2, S=4, K=1$ 的贯穿例子及其两种 router 输出（情形 A 一般不均衡、情形 B 最坏构造）是教学构造，目的在于让 $E/R$ 上界、最坏构造、forward/backward 流程在 $\le 4$ 的数字上可手算复算。不来自 K3 报告，不代表真实训练配置。报告未公开 K3 训练 2.8T MoE 的具体 $E, R, K, S$ 取值。

    教学解释与类比边界

    • "冗余专家 = 临时副本"：用于强调 forward 预取、backward 归还的特性。失效边界：若 router 极端偏好长期不变，冗余专家可能在多个 micro-batch 间复用副本，但 MoonEP 仍按每 micro-batch、每层重新规划，不假设长期复用。
    • "reduce-back 与 all-reduce 同语义但只针对冗余专家梯度"：用于帮助理解 reduce-back 的归约语义。失效边界：reduce-back 不是全量梯度 all-reduce，只涉及当前层、当前 micro-batch 用到的冗余专家梯度。

    教学简化及其限制

    • 伪代码省略了 combine、router 训练、辅助损失、optimizer step 等通用 MoE 步骤，只展示 planning、预取、dispatch 三个 MoonEP 特有步骤。真实工程还包括 stream 调度、内存池管理等。简化不改变 MoonEP 机制的关键构成（planning、冗余专家、零拷贝 dispatch、reduce-back）。
    • Theorem 1 构造性证明的复述省略了原证明中"overloaded rank 在 fill 后可能仍过载、可能恰好平衡、可能变 underloaded"的状态转移细节对算法复杂度的分析，只保留终止性与同源性两个关键性质。完整证明见补充折叠块与报告 §E。
    • Theorem 2 最坏构造的下界公式 $\lceil E(R-1)/R^2\rceil$ 在小 $R$ 下严格小于 $E/R$，界仅大 $R$ 渐近紧；数字例子折叠块手算验证 $E=4,R=2$ 时 $M(I^*)=1<E/R=2$。
    • DeepEP 的 $S\times K\times R$ 是最坏不均衡下的 buffer 预留，不是 DeepEP 常态开销；本页在正文与表格中均标明这一限定。
