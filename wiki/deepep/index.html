    DeepEP：MoE 专家并行的 dispatch 与 combine 通信库

    主要依据：DeepEP 仓库 README 与 docs/legacy.md（main 分支 commit 01dc3aa，2026-08-04）、V1 初始源码 docstring（commit ebfe47e，2025-02-24）、DeepSeek-V3 技术报告（arXiv:2412.19437v2）§2.1.2、§3.2、§3.4、§3.5.1。论断、公式与数字的编号（C/F/N）与文末来源与范围说明逐条对应。

    MoE 模型的每一层都把 token 发往专家所在的 GPU：门控网络为每个 token 选出若干专家，这些专家分布在专家并行（EP）的不同 rank 上；专家算完后，输出还要送回 token 的出发地加权合并。这两个方向的搬运分别叫 dispatch 与 combine，形态上是 all-to-all——每个 rank 都可能向其他所有 rank 发送数据。规模上来之后，这一来一回成为系统的主要通信开销：DeepSeek-V3 的 decode 部署用 320 块 GPU 组织 EP320，每块 GPU 只放 1 个路由专家，每生成一个 token 都要完成一次全集群的 dispatch 与 combine[C28, N6]。

    一个自然的想法是用现成的集合通信库（如 NCCL）发这些数据。但 MoE 的 dispatch/combine 对通信库提出了四点结构性要求——通信不能抢计算的 SM（streaming multiprocessor，GPU 上执行 kernel 的基本单元，通信与计算都要占用它）、接收数据要按专家分组排布、dispatch 载荷要用 FP8、decode 的每步小 batch 通信要低延迟且兼容 CUDA graph——这些是通用集合通信原语不提供的接口语义。DeepEP 是 DeepSeek 为此开源的通信库：当前聚焦专家并行，核心只做 token 搬运，两套内核分别对准训练/prefill 的高吞吐与 decode 的低延迟，不做路由决策、专家计算与调度重叠[C1]。

    本文的讲解主线：第 1 章「专家并行的 all-to-all 卡在哪」算清通信量、指出通用库的四个不适配点；第 2 章「高吞吐内核」与第 3 章「低延迟内核」分别拆开两套内核；第 4 章「V2 重构」讲工程重构；第 5 章「DeepEP 不解决什么」划清与相邻系统的责任边界。机制叙述以 V1 的两套内核为主线，V2 的接口与工程变化集中在第 4 章「V2 重构」。

    本文依赖的前置概念：top-$K$ 路由与门控见 DeepSeekMoE 结构；专家并行、all-to-all 与 prefill/decode 两阶段见 MoE 推理与服务基础；NVLink、RDMA/IB 等互连硬件见 GPU 通信；CUDA graph 见 torch.compile 图捕获与 CUDA Graph；FP8（E4M3）见 FP8 块量化。本文只使用这些页面的结论，不重复推导。

    核心问题

    1. MoE 专家并行的 dispatch/combine 通信有什么特殊要求，为什么通用集合通信库不够用？

      解答：四个结构性不适配

      dispatch 按 top-$K$ 路由把每个 token 复制 $K$ 份发往专家所在 rank，combine 把各副本按门控值加权求和送回原 rank。通用库不适配的四点：SM 争抢（V3 训练用 20/132 个 SM 专职通信、tensor core 闲置）、接收侧无按专家分组的布局契约（grouped GEMM 无法直接消费）、FP8 dispatch 非标准需求、decode 小 batch 的延迟与 CUDA graph 兼容。背景是跨节点 EP 的计算通信比约为 1:1，通信是必须正面优化的对象。完整论证见第 1 章「专家并行的 all-to-all 卡在哪」。

    2. 高吞吐内核如何利用 NVLink 与 RDMA 两种带宽，把跨节点 dispatch/combine 跑满？

      解答：两段转发让两种网络完全重叠

      token 先经 IB 到目标节点上与发送 rank 同 in-node index 的 GPU，落地后经 NVLink 转发给持有目标专家的 GPU，不被后到 token 阻塞——IB 与 NVLink 完全重叠。配合 node-limited routing（每 token 至多 4 个目标节点）限制 IB 流量，20 个 SM 分成 10 个通信通道即可跑满两种网络。实测节点内 153/158 GB/s 逼近 160 GB/s 的 NVLink 峰值，跨节点 43-58 GB/s 逼近 50 GB/s 的 RDMA 峰值。完整论证见第 2 章「高吞吐内核」。

    3. decode 场景为什么需要另一套低延迟内核，纯 RDMA、固定槽位与 hook 各解决什么问题？

      解答：用带宽换延迟的三个取舍

      decode 每步都发生通信、batch 小、TPOT 敏感，且 CUDA graph 要求无隐式 CPU 同步。低延迟内核放弃 NVLink 走纯 RDMA（所有 rank 经 RDMA 可见，点对点直达去掉两段转发的中转与同步）；接收张量按最坏情况预留固定槽位，不做 CPU 接收计数同步从而兼容 CUDA graph；hook 让 dispatch 只发 RDMA 请求不等待，等待期 GPU 去算另一个 micro-batch，不占任何 SM。代价是 RDMA 带宽利用率显著低于高吞吐模式。完整论证见第 3 章「低延迟内核」。

    4. V2 重构改变了什么——为什么换掉 NVSHMEM，统一接口与解析式调参解决什么问题？

      解答：后端、接口与调参的三处工程重做

      V2 把通信后端从 NVSHMEM 换成 NCCL Gin（header-only、可复用现有 NCCL communicator），高吞吐与低延迟 API 统一进单一 ElasticBuffer 接口并支持到 EP2048，SM 与 QP 数量改为按带宽建模解析计算、不再 auto-tuning；内核全部 JIT 编译，安装期无需 CUDA 编译。V3 式训练的通信 SM 从 24 降到 4-6，峰值性能最高 1.3 倍。代价是 buffer 消耗更大、0 SM RDMA 低延迟 EP 不再支持。完整论证见第 4 章「V2 重构」。

    5. DeepEP 解决什么、不解决什么，与相邻系统如何分工？

      解答：只搬 token，不决定去向、不算专家、不排调度

      DeepEP 只负责 dispatch/combine 的传输与接收布局；token 去向由模型 gating 决定，负载均衡靠 gating 算法、部署层冗余专家或专门系统（UltraEP、MoonEP），专家计算由 grouped GEMM 库完成，计算通信重叠调度（DualPipe、TBO）由框架层编排。硬件门槛：Hopper（SM90）及以上、节点内 NVLink、跨节点 RDMA 网络；IB 全测试，RoCE 理论兼容。完整论证见第 5 章「DeepEP 不解决什么」。

    1. 专家并行的 all-to-all 卡在哪——为什么不是再写一个 NCCL 调用

    1.1 dispatch 与 combine 在搬什么

    门控网络为 token $t$ 选出 $K$ 个路由专家并给出门控值后，MoE 层的输出是各路由专家输出的加权和。DeepSeek-V3 的形式为[F1]

    $$\mathbf{h}_{t}^{\prime} =\mathbf{u}_{t}+\sum_{i=1}^{N_{s}}\operatorname{FFN}^{(s)}_{i}\left(\mathbf{u}_{t}\right)+\sum_{i=1}^{N_{r}}g_{i,t}\operatorname{FFN}^{(r)}_{i}\left(\mathbf{u}_{t}\right)$$
    • $\mathbf{u}_t$：第 $t$ 个 token 的隐藏状态向量，维度为 $h$（hidden size）。
    • $N_s$、$N_r$：共享专家数与路由专家数，V3 取 $N_s=1$、$N_r=256$，每 token 激活 $K_r=8$ 个路由专家[N7]。
    • $g_{i,t}$：token $t$ 对选中专家 $i$ 的归一化门控值，未选中的专家为 0。
    • $\operatorname{FFN}^{(s)}_i$、$\operatorname{FFN}^{(r)}_i$：第 $i$ 个共享专家与第 $i$ 个路由专家的前馈网络。

    式中共享专家项不含门控值：共享专家对每个 token 都生效，留在本 rank 计算不参与通信，dispatch/combine 只搬运路由专家的副本（共享专家的设计见 DeepSeekMoE 结构）。dispatch 搬的就是式中的 $\mathbf{u}_t$：按路由结果把每个 token 复制 $K$ 份发往各专家所在的 rank。combine 搬的是反方向：各专家的输出副本送回原 rank，按 $g_{i,t}$ 加权求和——上式最后一项就是 combine 的通信语义。通信量可以直接算出来：一个 token 被路由到 $K$ 个专家即复制 $K$ 份，每份载荷 $h$ 个元素；BF16 每元素 2 字节，dispatch 每 token 发送 $2Kh$ 字节；FP8 每元素 1 字节，为 $Kh$ 字节[F2]。

    构造示例（全文贯穿）。取 2 节点、每节点 4 GPU 的 EP 系统：rank 0-3 在节点 A，rank 4-7 在节点 B；8 个路由专家，专家 $E_e$ 放在 rank $e$ 上（每 rank 恰好 1 个本地专家）；hidden 取 $h=2$，top-$K$ 取 $K=2$。所有数字便于手算，不代表真实部署规模。rank 0 持有两个 token：$t_0=(1.0,2.0)$ 路由到 $(E_1,E_5)$、权重 $(0.6,0.4)$；$t_1=(1.0,3.0)$ 路由到 $(E_2,E_6)$、权重 $(0.5,0.5)$。发送计划为

    token目标专家目标 rank路径类型
    $t_0$ 第 1 份$E_1$1节点内（NVLink）
    $t_0$ 第 2 份$E_5$5跨节点（IB 后 NVLink）
    $t_1$ 第 1 份$E_2$2节点内（NVLink）
    $t_1$ 第 2 份$E_6$6跨节点（IB 后 NVLink）

    FP8 下 rank 0 这一步 dispatch 共发出 4 份副本、每份 $h=2$ 个元素、每元素 1 字节，合计 8 字节。这个例子在第 2 章「高吞吐内核」用来追踪两段转发的具体路径，在第 3 章「低延迟内核」切到 decode 场景展示固定槽位，在第 5 章「DeepEP 不解决什么」改路由制造不均衡。

    1.2 通用集合通信库的四个不适配

    跨节点 EP 的通信量级可以从一个数字感受：DeepSeek-V3 训练中，跨节点专家并行引入的通信使计算通信比约为 1:1——一半时间在算、一半时间在搬[C29]。通信因此是必须正面优化的对象，而把通用 all-to-all 原语直接拿来用，会在四个点上不适配。

    第一，SM 争抢。用通用库做通信，搬运由 SM 上的 kernel 执行，抢的是计算的 SM：V3 训练用 20/132 个 H800 SM 专职通信，且这些 SM 上 tensor core 完全闲置[C9, N5]。通信内核必须把 SM 用量做成可控制的参数，而不是任由库的默认配置占用。

    第二，接收侧布局契约。all-to-all 原语只按 rank 搬数据，不知道"按专家分组连续排布"这回事；而接收侧的计算是 grouped GEMM——对按来源分组的多段矩阵连续做乘法，要求数据落进 buffer 时就按专家分组排好。DeepEP 的接收布局就是为配套 GEMM 库设计的[C31]，这是通用原语不提供的接口语义。

    第三，FP8 dispatch。V3 把 MoE up 投影前的激活量化为 FP8 再 dispatch，反向的激活梯度同样处理；前后向 combine 保留 BF16 以保住训练关键路径的精度[C30]。dispatch 载荷的 FP8（连同样因子的布局约定）不是通用库的标准需求。

    第四，decode 的延迟与 CUDA graph。decode 的通信每步都发生、batch 小（低延迟内核的实测条件为每 batch 128 tokens，即 V3/R1 的典型生产设置[N3]）、直接计入 TPOT（每输出一个 token 的耗时）；且推理引擎用 CUDA graph 消除 kernel 启动开销，要求 GPU 工作形状固定、无隐式 CPU 同步。而"发送侧事先不知道本 rank 会收到多少 token"的动态 all-to-all 天然带同步点——即使 DeepEP 自己的 V1 高吞吐 dispatch 内核，内部也包含等待 GPU 接收计数信号的隐式 CPU 等待，与 CUDA graph 不兼容[C11]。decode 需要另一套内核（第 3 章「低延迟内核」）。

    常见误解：NCCL 也有 all-to-all，DeepEP 只是快一点。差异是结构性的：按专家分组的接收布局、FP8 dispatch、SM 用量控制、CUDA graph 兼容与零 SM 等待的 hook，都是接口语义层面的差别，带宽数字只是这些设计的结果之一。

    1.3 DeepEP 是什么，负责哪一段

    DeepEP 是 DeepSeek 开源的高性能通信库，当前聚焦专家并行：提供高吞吐与低延迟两套 all-to-all GPU 内核（即 MoE dispatch 与 combine），支持包括 FP8 在内的低精度，另提供流水线并行（PP）、上下文并行（CP）、远程内存访问（Engram）的实验性原语，全部按零或最小 SM 占用设计[C1]。V1 于 2025-02-24 发布，V2 于 2026-04-30 公开[C2]。

    两套内核对应两个场景[C4]：高吞吐内核（normal）面向训练与推理 prefill，针对非对称域带宽转发优化——把数据从 NVLink 域搬进 RDMA 域（或反向），与 DeepSeek-V3 的 node-limited（group-limited）gating 算法对齐，支持 SM 数量控制；低延迟内核（low-latency）面向延迟敏感的推理 decode，用纯 RDMA 压延迟，配合不占 SM 的 hook 做通信计算重叠。这套设计与 DeepSeek-V3 论文的描述同源，但实现细节略有差异[C3]。

    责任边界一句话预览（第 5 章「DeepEP 不解决什么」展开）：DeepEP 只搬 token、只保证接收布局；token 去向由 gating 决定，专家计算由 grouped GEMM 完成，重叠调度由框架编排。

    本章问题

    1. dispatch/combine 到底在搬什么、量有多大？

      解答：按路由复制 $K$ 份发出去，算完加权送回来

      dispatch 搬 token 的隐藏状态 $\mathbf{u}_t$：按 top-$K$ 路由把每个 token 复制 $K$ 份发往各专家所在 rank，BF16 每 token 发送 $2Kh$ 字节、FP8 发送 $Kh$ 字节。combine 搬专家输出：各副本送回原 rank 按 $g_{i,t}$ 加权求和，即 V3 式（12）最后一项的通信侧。构造示例里 rank 0 的两个 token 各复制 2 份，FP8 下 dispatch 共发出 8 字节。

    2. 通用集合通信库哪里不够用？

      解答：四个结构性不适配

      一是 SM 争抢，通信 kernel 抢计算的 SM（V3 用 20/132 个 SM 专职通信、tensor core 闲置）；二是接收侧无按专家分组的布局契约，grouped GEMM 无法直接消费；三是 FP8 dispatch（含 scale 布局）非标准需求；四是 decode 小 batch 要低延迟且兼容 CUDA graph，动态 all-to-all 的接收计数同步与 CUDA graph 冲突。背景是跨节点 EP 计算通信比约 1:1，通信量级决定了它必须被专门优化。

    3. DeepEP 是什么，它在整条链路里负责哪一段？

      解答：只负责 dispatch 与 combine 两段的通信库

      DeepEP 是 DeepSeek 开源的专家并行通信库（V1 2025-02-24 发布、V2 2026-04-30 公开），两套内核分别对准训练/prefill 的高吞吐与 decode 的低延迟，另有 PP/CP/Engram 实验性原语。在 MoE 层链路里它只负责 dispatch 与 combine 两个搬运段（以及接收侧布局契约）；gating 决定去向、grouped GEMM 做计算、框架做调度，这些都不在库内。

    2. 高吞吐内核——两种网络的两段转发

    2.1 两种网络的带宽差

    DeepSeek-V3 的 H800 集群里，节点内 GPU 经 NVLink 互联，最大带宽约 160 GB/s；跨节点经 IB 全互联，每 GPU 接一块 CX7 400 Gb/s 网卡，RDMA 最大带宽约 50 GB/s——NVLink 约是 IB 的 3.2 倍[N1]。两种网络相互独立：一块 GPU 上的数据要到达另一节点的 GPU，必须先经 IB 再经 NVLink（或反向），中间必须有人搬运。DeepEP 把这类搬运称为非对称域带宽转发[C4]。V3 论文列举的 SM 通信任务里，第一项就是在 IB 与 NVLink 域之间转发数据，并把发往同节点多块 GPU 的 IB 流量在单块 GPU 上聚合[C9]。

    2.2 两段转发：IB 落地即 NVLink 转发

    高吞吐内核的核心机制是两段转发[C5]：token 的路由决定后，先经 IB 传到目标节点上与发送 rank 同 in-node index 的 GPU；到达目标节点后，即经 NVLink 转发给持有目标专家的 GPU，不被后到的 token 阻塞——论文把"瞬时转发"表述为设计目标（力求确保），而非协议层面的保证。这样 IB 传输与 NVLink 转发完全重叠——前一个 token 还在 NVLink 上走时，后一个 token 的 IB 传输已经在进行。

    in-node index 指 rank 在自己节点内的序号：构造示例里 rank 0-3 的 in-node index 为 0-3，rank 4-7 的也是 0-3。追踪 $t_0$ 的 $E_5$ 副本：rank 0 的 in-node index 是 0，$E_5$ 在节点 B 的 rank 5 上，于是这份副本先经 IB 到节点 B 上 in-node index 同为 0 的 rank 4，落地后立即经 NVLink 转发给 rank 5。$E_1$ 副本则不必过 IB——$E_1$ 就在本节点的 rank 1 上，直接走 NVLink。

    流量可以逐段手算（FP8 下每份副本 $h=2$ 个元素、共 2 字节）：$E_1$ 副本走 NVLink 一段，流动 2 字节；$E_5$ 副本走 IB 一段加 NVLink 一段，各流动 2 字节。同一份数据在两段链路上各流动一次，这是两段转发付出的搬运代价，换来的是两种网络的完全重叠。combine 沿相反方向走同样的两段路径，且转发途中完成归约累加[C8]。

    展开：$t_0$ 全部链路流量的完整手算

    dispatch 方向（FP8，每元素 1 字节，每份副本 $h=2$ 个元素即 2 字节）：

    • $E_1$ 副本（节点内）：rank 0 经 NVLink 到 rank 1，流动 2 字节。
    • $E_5$ 副本（跨节点）：rank 0 经 IB 到 rank 4，流动 2 字节；rank 4 经 NVLink 到 rank 5，再流动 2 字节。
    • 链路合计流动 $2+2+2=6$ 字节；发出的副本载荷是 2 份共 4 字节——跨节点那份在两段链路上被各搬运一次。

    combine 方向（BF16，每元素 2 字节，每份副本 4 字节；V3 的精度策略是 combine 保留 BF16[C30]）：

    • $E_1$ 输出：rank 1 经 NVLink 回 rank 0，流动 4 字节。
    • $E_5$ 输出：rank 5 经 NVLink 到 rank 4，流动 4 字节；rank 4 经 IB 回 rank 0，再流动 4 字节；转发途中完成归约累加[C8]。
    • 链路合计流动 $4+4+4=12$ 字节。

    $t_1$ 同理：$E_2$ 走节点内一段，$E_6$ 走跨节点两段。

    2.3 路由算法的配合：node-limited routing

    IB 是两种网络里窄的那条，控制 IB 流量的办法是限制 token 的目标节点数。V3 的 node-limited routing 保证每个 token 至多发送到 $M=4$ 个节点，节点按各节点上分数最高的 $K_r/M$ 个专家的亲和分数之和选择[C6]。在这条约束下，每 token 平均可选 3.2 个专家/节点而不产生额外 NVLink 开销；V3 实际激活 8 个路由专家，通信成本不变的前提下最多可扩到 13 个[C7]。路由怎么选是 gating 算法的事（第 5 章「DeepEP 不解决什么」的分工），但高吞吐内核与这条约束是共同设计的[C4]——内核为它优化转发，它为内核省 IB 流量。

    补充：等效 13 个专家的由来

    node-limited routing 把每 token 的目标节点数限制在 $M=4$ 个以内，以此减少 IB 流量；在此约束下每 token 平均可选 3.2 个专家/节点而不产生额外 NVLink 开销[C7]。通信成本不变时的等效专家数上限为 $4\times 3.2=12.8\approx 13$[F3]；V3 实际激活 $K_r=8$ 个路由专家，尚未用满这个余量。

    2.4 20 个 SM 与 10 个通信通道

    两段转发由通信 kernel 里的 SM 执行。V3 的内核设计只需 20 个 SM 即可跑满 IB 与 NVLink 带宽，并用 warp specialization——让 warp（SM 内的线程调度单元）各自专职一类任务——把 20 个 SM 分成 10 个通信通道[C8]。dispatch 侧三类任务由各自的 warp 专职负责：(1) IB 发送，(2) IB 到 NVLink 的转发，(3) NVLink 接收；combine 侧反向：(1) NVLink 发送，(2) NVLink 到 IB 的转发与累加，(3) IB 接收与累加。各任务分到的 warp 数量按实际负载动态调整[C8]。SM 的其余通信任务还包括 RDMA buffer 与输入输出 buffer 之间的搬运、combine 的归约运算、分块传输时的细粒度内存布局管理[C9]。

    SM 用量是可控参数：V1 的 normal 内核提供 SM 数量控制（示例代码里 Buffer.set_num_sms(24)），并配合定制的 PTX 指令与 auto-tune 的通信分块大小，降低 L2 缓存占用和对其他 SM 计算的干扰[C8, C10]。V2 进一步把 SM 数量改为解析式计算（第 4 章「V2 重构」）。

    2.5 实测带宽

    V1 normal 内核在 H800 上的实测，测试条件为 V3/R1 预训练设置：每 batch 4096 tokens、hidden 7168、top-4 组、top-8 专家、FP8 dispatch + BF16 combine[N2]：

    部署#EPdispatch 瓶颈带宽combine 瓶颈带宽
    节点内8153 GB/s（NVLink）158 GB/s（NVLink）
    跨节点1643 GB/s（RDMA）43 GB/s（RDMA）
    跨节点3258 GB/s（RDMA）57 GB/s（RDMA）
    跨节点6451 GB/s（RDMA）50 GB/s（RDMA）

    节点内 153/158 GB/s 逼近 160 GB/s 的 NVLink 峰值，跨节点 43-58 GB/s 逼近 50 GB/s 的 RDMA 峰值——高吞吐内核的设计目标就是把两种网络都跑满。表中带宽为瓶颈带宽口径：按最慢一段网络折算。V2 的实测（每 batch 8K tokens、hidden 7168、top-8 专家、FP8 dispatch + BF16 combine，逻辑带宽含本 rank 流量）在 EP 8×2 拓扑用 12 个 SM 达到 90/81 GB/s[N4]，见第 4 章「V2 重构」。

    高吞吐内核用两段转发换带宽，代价是路径长、同步点多：V1 的 normal dispatch 内部还有等待接收计数的隐式 CPU 同步，与 CUDA graph 不兼容[C11]。prefill 与训练的大 batch 扛得住这些代价，decode 的每步小 batch 通信等不起——需要一套设计点完全不同的内核。

    本章问题

    1. NVLink 和 RDMA 带宽差多少，为什么不能各自直接用？

      解答：160 对 50 GB/s，跨域必须有人搬运

      H800 节点内 NVLink 最大带宽约 160 GB/s，每 GPU 的 CX7 IB 网卡 RDMA 最大带宽约 50 GB/s，约 3.2 倍之差。两种网络相互独立：数据从一块 GPU 到另一节点的 GPU 必须先经 IB 再经 NVLink（或反向），中间的搬运由通信内核的 SM 承担（非对称域带宽转发）。没有这层搬运，两种网络各自再快也用不上。

    2. 两段转发怎么走，为什么两种网络能完全重叠？

      解答：IB 到同 in-node index 的 GPU，落地即 NVLink 转发

      token 先经 IB 到目标节点上与发送 rank 同 in-node index 的 GPU，到达后即经 NVLink 转发给持有目标专家的 GPU，不被后到 token 阻塞（论文把瞬时转发表述为设计目标）。因此一个 token 在 NVLink 上转发时，下一个 token 的 IB 传输已在进行，两种网络的时间线互相填满。构造示例中 $t_0$ 的 $E_5$ 副本路径为 rank 0 经 IB 到 rank 4、再经 NVLink 到 rank 5；$E_1$ 副本直接 NVLink 到 rank 1。

    3. 路由算法要配合做什么？

      解答：限制每 token 的目标节点数

      node-limited routing 保证每 token 至多发送到 $M=4$ 个节点（按各节点上分数最高的 $K_r/M$ 个专家的亲和分数之和选节点），以此限制 IB 流量；IB 是两种网络中窄的一条。该约束下每 token 平均可选 3.2 个专家/节点且不产生额外 NVLink 开销，通信成本不变时等效专家数上限约 13 个。

    4. 20 个 SM 怎么把两种网络都跑满？

      解答：warp 专职分工加动态调整

      用 warp specialization 把 20 个 SM 分成 10 个通信通道。dispatch 侧 IB 发送、IB 到 NVLink 转发、NVLink 接收由各自的 warp 专职负责；combine 侧 NVLink 发送、NVLink 到 IB 转发与累加、IB 接收与累加同样专职，warp 数量按实际负载动态调整。SM 用量本身是可控参数（V1 示例设 24 个），V2 改为解析式计算。

    5. 实测带宽到什么水平？

      解答：节点内与跨节点都逼近各自峰值

      V1 normal 实测（H800、每 batch 4096 tokens、hidden 7168、top-4 组 top-8 专家、FP8 dispatch + BF16 combine）：节点内 EP8 dispatch/combine 为 153/158 GB/s，逼近 160 GB/s 的 NVLink 峰值；跨节点 EP16/32/64 为 43-58 GB/s，逼近 50 GB/s 的 RDMA 峰值。口径为瓶颈带宽（按最慢一段网络折算）。

    3. 低延迟内核——decode 的纯 RDMA 与固定槽位

    3.1 decode 的通信需求

    prefill 一次处理整段输入，batch 大，通信分摊在大量 token 上；decode 逐 token 生成，每一步都要完成一次 dispatch/combine，且 batch 小——低延迟内核的实测条件是每 batch 128 tokens（V3/R1 的典型生产设置）[N3]。通信延迟直接计入 TPOT，没有计算可以掩盖它。部署形态也不同：V3 decode 用 40 节点 320 GPU 组织 EP320，每 GPU 恰好 1 个专家，dispatch/combine 的 all-to-all 用 IB 直接点对点传输换低延迟，并用 IBGDA（InfiniBand GPUDirect Async，IB 的异步 GPUDirect 扩展）进一步降延迟[C28, N6]。decode 阶段每个专家的 batch 通常在 256 tokens 以内，瓶颈是访存而非计算——只给 dispatch+MoE+combine 分配少量 SM 不会显著影响整体性能[C28]。

    3.2 纯 RDMA：放弃 NVLink

    低延迟内核基于 IBGDA 的纯 RDMA 实现：要求所有 rank——无论节点内还是跨节点——都经 RDMA 可见；为简化设计，连节点内也完全禁用 NVLink[C12]。V1 源码把低延迟模式的 IBGDA 释义为"不在 NVLink 与 RDMA 之间做包转发"，并把 NIC handler 设到 GPU 侧[C12]。每个 token 副本从原 rank 直接点对点写入目标专家 rank 的接收 buffer，没有两段转发的中转 GPU，也没有转发引入的同步点——路径短，延迟就低。

    常见误解：低延迟内核就是高吞吐内核的小 batch 版。两者是不同的设计点：高吞吐内核用两段转发最大化带宽利用率（节点内 153/158 GB/s），低延迟内核放弃 NVLink、用固定槽位与纯 RDMA 把延迟压到百微秒级，但 RDMA 带宽利用率显著低于高吞吐模式（3.5 节「低延迟的代价」的数字对比）。都叫 dispatch/combine，优化的目标函数不同。

    3.3 固定槽位布局：接收侧不做 CPU 同步

    低延迟 dispatch 返回的接收张量形状为[C13, F4]

    $$[\,\text{num\_local\_experts},\quad \text{num\_max\_dispatch\_tokens\_per\_rank}\times\text{num\_ranks},\quad h\,]$$
    • num_local_experts：本 rank 持有的专家数（构造示例里每 rank 1 个）。
    • num_max_dispatch_tokens_per_rank：每 rank 最多发出的 token 数，全组统一取值。
    • 第二个维度按来源 rank 分段预留：每个来源 rank 固定占 num_max_dispatch_tokens_per_rank 个槽，构造示例取 2，于是每行 16 个槽。
    • $h$：hidden，数据为 FP8 e4m3，附带每 128 元素一组的缩放因子（列主序排布以兼容 TMA）[C13]。

    关键设计在第二个维度：接收行按来源 rank 分段，段基址由来源 rank 决定，段内下标按该 rank 发往此专家的 token 依次递增——V1 源码的偏移计算即"来源 rank × num_max + 段内序号"，序号是发送 rank 内按专家计数的到达顺序[C13]。确定一个副本落在哪个槽只需要发送 rank 自己的路由信息，不需要任何跨 rank 同步；接收侧也不需要预先知道"实际会收到多少 token"——所有 rank 都按最坏情况（每个来源 rank 的全部 token 都可能发来）预留空间，不做 CPU 接收计数同步。这带来两个直接后果：其一，内核与 CUDA graph 兼容（replay 时需恢复部分 buffer 状态），dispatch 还隐式完成 FP8 转换[C14]；其二，槽位不全部有效，recv_count 给出每个本地专家的实际接收数，计算侧据此只处理有效槽位[C13]。

    构造示例切到 decode 场景：每 rank 2 个 token（即 num_max_dispatch_tokens_per_rank 取 2），16 个 token 按一张显式路由表分发，构造原则是均衡——每个专家恰好收到 4 个 token。专家 $E_5$ 的接收行共 16 槽（表中 $t_{r,j}$ 表示来源 rank $r$ 的第 $j$ 个 token）：

    来源 rank槽位区间$E_5$ 接收行的内容有效槽位
    00-1槽 0 收到 $t_{0,0}$1 / 2
    12-3空0 / 2
    24-5槽 4 收到 $t_{2,0}$1 / 2
    36-7空0 / 2
    48-9槽 8 收到 $t_{4,1}$1 / 2
    510-11空0 / 2
    612-13槽 12 收到 $t_{6,0}$1 / 2
    714-15空0 / 2

    16 个槽里只有 4 个有效——这就是按最坏情况预留的直观代价。buffer 的大小由 num_max_dispatch_tokens_per_rank（解码引擎的实际 batch size）决定，官方建议该值小于 256；低延迟模式消耗的显存远大于 normal 模式。为了最佳性能，QP（RDMA 队列对）数应与本地专家数一致[C17]。

    补充：双缓冲限制——同时最多持有 2 个结果张量

    低延迟模式的内部只有两个 buffer，返回的张量复用 buffer，因此同一时刻最多持有 2 个低延迟内核的结果张量，持有第 3 个会覆盖尚未消费的数据[C16]。

    代码：固定槽位布局与 combine 带权归约的最小模拟 
    """DeepEP 低延迟内核固定槽位布局的最小模拟（构造示例）。

模拟对象：
- 8 个 rank（rank 0-3 在节点 A，rank 4-7 在节点 B），每 rank 2 个 token；
- 8 个路由专家，专家 E_e 放在 rank e 上（每 rank 恰好 1 个本地专家）；
- hidden h = 2，top-2 路由。

本代码只模拟「槽位布局 + 带权归约」的数据结构逻辑，不含真实通信：
token 的搬运用数组读写代替 RDMA，专家计算用逐元素加法的 mock FFN 代替 grouped GEMM。
"""

NUM_RANKS = 8
NUM_EXPERTS = 8
HIDDEN = 2
MAX_TOKENS_PER_RANK = 2  # num_max_dispatch_tokens_per_rank
SLOTS_PER_EXPERT = MAX_TOKENS_PER_RANK * NUM_RANKS  # 每个本地专家一行的槽位数


# 槽位规则：段基址由来源 rank 决定（rank * MAX），
# 段内下标按该 rank 发往此专家的 token 顺序递增
# （对应 V1 源码的偏移计算 rank * num_max + slot_idx，
#   slot_idx 为发送 rank 内按专家计数的到达序号）
def segment_base(source_rank):
    return source_rank * MAX_TOKENS_PER_RANK


# ---- 1. 构造路由表与 token 值（显式给出，便于逐条核对） ----
# 原则：rank 0 的两个 token 分别给出「节点内 + 跨节点」各一条路径；
# 每个专家恰好收到 4 个 token（均衡）；无 token 路由到本 rank 的专家。
# token 值 t_{r,j} = (1+r, 2+j)
ROUTES = {
    # (rank, token 序号): [(专家, 权重), ...]
    (0, 0): [(1, 0.6), (5, 0.4)],
    (0, 1): [(2, 0.5), (6, 0.5)],
    (1, 0): [(3, 0.6), (7, 0.4)],
    (1, 1): [(4, 0.5), (0, 0.5)],
    (2, 0): [(5, 0.6), (1, 0.4)],
    (2, 1): [(6, 0.5), (0, 0.5)],
    (3, 0): [(0, 0.6), (4, 0.4)],
    (3, 1): [(7, 0.5), (1, 0.5)],
    (4, 0): [(3, 0.6), (0, 0.4)],
    (4, 1): [(7, 0.5), (5, 0.5)],
    (5, 0): [(2, 0.6), (6, 0.4)],
    (5, 1): [(3, 0.5), (7, 0.5)],
    (6, 0): [(1, 0.6), (5, 0.4)],
    (6, 1): [(2, 0.5), (4, 0.5)],
    (7, 0): [(3, 0.6), (4, 0.4)],
    (7, 1): [(2, 0.5), (6, 0.5)],
}

tokens = {(r, j): (1.0 + r, 2.0 + j) for (r, j) in ROUTES}

print("rank 0 的发送计划：")
for j in range(MAX_TOKENS_PER_RANK):
    plan = ", ".join(f"E{e}(rank {e}, w={w})" for e, w in ROUTES[(0, j)])
    print(f"  t_{j} = {tokens[(0, j)]} -> {plan}")

# ---- 2. dispatch：按固定槽位写入每个专家的接收行 ----
# recv_slots[e][s] 的取值：None 表示空槽，(来源 rank, token 序号) 表示有效槽
recv_slots = {e: [None] * SLOTS_PER_EXPERT for e in range(NUM_EXPERTS)}
copy_slot = {}     # (来源 rank, token 序号, 专家) -> 该副本的槽位下标
segment_used = {}  # (来源 rank, 专家) -> 段内已占槽数
for (r, j), route in ROUTES.items():
    for e, _w in route:
        k = segment_used.get((r, e), 0)
        segment_used[(r, e)] = k + 1
        slot = segment_base(r) + k
        recv_slots[e][slot] = (r, j)
        copy_slot[(r, j, e)] = slot

recv_count = {e: sum(1 for s in recv_slots[e] if s is not None)
              for e in range(NUM_EXPERTS)}

print(f"\n专家 E5 的接收槽位行（共 {SLOTS_PER_EXPERT} 槽，"
      f"有效 {recv_count[5]} 槽）：")
for s in range(SLOTS_PER_EXPERT):
    if recv_slots[5][s] is not None:
        r, j = recv_slots[5][s]
        print(f"  slot {s:2d} <- rank {r} 的 t_{j}")
print(f"recv_count（各专家实际接收数）= {[recv_count[e] for e in range(NUM_EXPERTS)]}")

# ---- 3. 专家计算（mock：FFN_e(x) = (x0 + e, x1 + e)），只读有效槽位 ----
def mock_ffn(expert_id, x):
    return (x[0] + expert_id, x[1] + expert_id)

expert_out = {e: [None] * SLOTS_PER_EXPERT for e in range(NUM_EXPERTS)}
for e in range(NUM_EXPERTS):
    for s in range(SLOTS_PER_EXPERT):
        if recv_slots[e][s] is not None:
            r, j = recv_slots[e][s]
            expert_out[e][s] = mock_ffn(e, tokens[(r, j)])

# ---- 4. combine：专家输出送回原 rank，按门控值加权求和 ----
combined = {}
for (r, j), route in ROUTES.items():
    acc = [0.0] * HIDDEN
    for e, w in route:
        out = expert_out[e][copy_slot[(r, j, e)]]  # 从该副本的槽位取回输出
        for k in range(HIDDEN):
            acc[k] += w * out[k]
    combined[(r, j)] = tuple(acc)

print("\nrank 0 两个 token 的 combine 结果：")
for j in range(MAX_TOKENS_PER_RANK):
    print(f"  t_{j}: ({combined[(0, j)][0]:.4f}, {combined[(0, j)][1]:.4f})")

# ---- 5. 参照：不经槽位直接计算，验证 round-trip 一致 ----
mismatch = 0
for (r, j), route in ROUTES.items():
    direct = [0.0] * HIDDEN
    for e, w in route:
        out = mock_ffn(e, tokens[(r, j)])
        for k in range(HIDDEN):
            direct[k] += w * out[k]
    if any(abs(direct[k] - combined[(r, j)][k]) > 1e-9 for k in range(HIDDEN)):
        mismatch += 1
        print(f"  不一致: rank {r} 的 t_{j}")

print(f"\n槽位路径与直接计算的逐 token 比对："
      f"{len(ROUTES) - mismatch}/{len(ROUTES)} 一致")

# ---- 6. 最坏情况预留的显存代价 ----
valid_total = sum(recv_count.values())
print(f"\n槽位利用率：全库有效槽位 {valid_total} / 预留 {NUM_EXPERTS * SLOTS_PER_EXPERT}"
      f"（每专家一行 {SLOTS_PER_EXPERT} 槽，共 {NUM_EXPERTS} 行）")

    预期输出：

    rank 0 的发送计划：
  t_0 = (1.0, 2.0) -> E1(rank 1, w=0.6), E5(rank 5, w=0.4)
  t_1 = (1.0, 3.0) -> E2(rank 2, w=0.5), E6(rank 6, w=0.5)

专家 E5 的接收槽位行（共 16 槽，有效 4 槽）：
  slot  0 <- rank 0 的 t_0
  slot  4 <- rank 2 的 t_0
  slot  8 <- rank 4 的 t_1
  slot 12 <- rank 6 的 t_0

槽位利用率：全库有效槽位 32 / 预留 128（每专家一行 16 槽，共 8 行）

    验证的机制：dispatch 把每个 token 副本写入目标专家接收行的固定槽位（segment_base 与段内计数对应正文"来源 rank × num_max + 段内序号"的规则）；专家计算只读有效槽位；combine 从同一槽位取回输出、按门控值加权求和（对应式（12）最后一项）。第 5 步逐 token 比对槽位路径与直接计算，验证布局与归约的一致性。

    观察重点：专家 $E_5$ 的接收行 16 槽中只有槽 0、4、8、12 有效，recv_count 全部为 4；combine 后 $t_0$ 得到 $(3.6,4.6)$，正是 $0.6\cdot\operatorname{FFN}_1(t_0)+0.4\cdot\operatorname{FFN}_5(t_0)$ 的手算结果。

    简化条件：用数组读写代替 RDMA 传输、用逐元素加法的 mock FFN 代替 grouped GEMM、不做 FP8 量化（真实内核隐式完成 FP8 转换）、不含 hook 与双缓冲逻辑。构造中每个来源 rank 至多一个 token 发往同一专家，段内序号均为 0；真实内核中同一 rank 的多个 token 可发往同一专家，段内序号依次递增。本代码验证的是布局与归约的数据结构逻辑，不是 DeepEP 的通信实现。

    3.4 接收 hook：等待不占 SM

    低延迟内核还提供 return_recv_hook 接口：设为 true 时，dispatch/combine 内核只发出 RDMA 请求而不实际等待数据到达；调用返回的 hook 之后，才保证数据就位[C15]。等待期间 GPU 去做什么由调用方决定——V3 用两个 micro-batch 交错（two-batch overlap，TBO）填这个窗口：prefill 侧同时处理两个 micro-batch，把一个的 attention/MoE 与另一个的 dispatch/combine 重叠[C27]；decode 侧同样在探索这一交错（论文表述为 also exploring）——让一个 micro-batch 的 attention 与另一个的 dispatch+MoE+combine 重叠[C28]。这种基于 hook 的通信计算重叠不占用任何 SM 资源[C15]——不同于第 2 章「高吞吐内核」的 normal 内核"用 SM 上的 warp 做通信"的重叠方式。

    3.5 低延迟的代价

    用带宽换延迟。V1 低延迟内核在 H800 上的实测，条件为 V3/R1 生产设置：每 batch 128 tokens、hidden 7168、top-8 专家、FP8 dispatch + BF16 combine[N3]：

    #EPdispatch 延迟dispatch RDMA 带宽combine 延迟combine RDMA 带宽
    877 µs98 GB/s114 µs127 GB/s
    16118 µs63 GB/s195 µs74 GB/s
    32155 µs48 GB/s273 µs53 GB/s
    64173 µs43 GB/s314 µs46 GB/s
    128192 µs39 GB/s369 µs39 GB/s
    256194 µs39 GB/s360 µs40 GB/s

    dispatch 延迟从 EP8 的 77 µs 涨到 EP128 的 192 µs 后趋于平坦，但折算带宽从 98 GB/s 掉到 39 GB/s——对比 normal 内核跨节点的 43-58 GB/s（节点内 153/158 GB/s），纯 RDMA 的带宽利用率明显更低。小 batch 的 decode 关心的是延迟而非带宽，这个交换才划算；低延迟内核的定位本来就是延迟敏感的 decode——与 high-throughput 内核面向训练/prefill 的分工相对（见第 1 章「专家并行的 all-to-all 卡在哪」）。另一个代价是显存：固定槽位按最坏情况预留，低延迟模式的 buffer 消耗远大于 normal 模式[C17]。

    两套内核讲完，剩下的是工程面：V1 的接口是两套、通信后端是 NVSHMEM、SM 数量靠 auto-tuning——V2 把这些统一重做，引出第 4 章「V2 重构」。

    本章问题

    1. decode 的通信需求跟 prefill 差在哪？

      解答：每步都发生、batch 小、延迟直接进 TPOT

      prefill 的 batch 大，通信分摊在大量 token 上；decode 每生成一个 token 都要完成一次 dispatch/combine，batch 小（实测条件为每 batch 128 tokens），通信延迟直接计入 TPOT，且推理引擎的 CUDA graph 要求无隐式 CPU 同步。V3 decode 部署 EP320、每 GPU 1 个专家、IB 点对点传输加 IBGDA；每专家 batch 通常不超过 256 tokens、瓶颈是访存，少量 SM 即可。

    2. 为什么放弃 NVLink 与两段转发，全部走 RDMA？

      解答：点对点直达去掉中转与同步

      低延迟内核要求所有 rank（含节点内）经 RDMA 可见、NVLink 完全禁用。每个 token 副本从原 rank 直接点对点写入目标专家 rank 的接收 buffer，没有两段转发的中转 GPU 与转发同步点，路径短延迟低。代价是放弃 NVLink 的高带宽，带宽利用率明显低于高吞吐内核。

    3. 固定槽位布局怎么让接收侧不做 CPU 同步、兼容 CUDA graph？

      解答：按最坏预留，槽位地址只由来源决定

      接收张量形状为 $[\text{本地专家数},\ \text{每 rank 最大 token 数}\times\text{rank 数},\ h]$，第二维按来源 rank 分段，段基址由来源决定、段内序号只依赖该 rank 自己发往此专家的 token 数——确定槽位不需要跨 rank 同步。因此不需要预先知道"实际收到多少 token"——按最坏情况预留空间即可，CUDA graph 要求的固定形状得到满足；recv_count 标记每个本地专家的实际接收数，计算侧只处理有效槽位；dispatch 隐式完成 FP8 转换。

    4. hook 怎么让通信等待不占 SM？

      解答：只发请求不等待，调用方填窗口

      return_recv_hook=True 时内核只发出 RDMA 请求、不等待数据到达，返回一个 hook；调用 hook 后才保证数据就位。等待期间 GPU 转去做其他计算（V3 的 TBO：算另一个 micro-batch 的 attention），等待本身不占用任何 SM——与 normal 内核用 SM warp 做通信的方式不同。不重叠的调用方可设 return_recv_hook=False，由内核确保数据到达。

    5. 低延迟的代价是什么？

      解答：带宽利用率与显存

      带宽：纯 RDMA 的折算带宽在 EP128 时为 39 GB/s（dispatch），明显低于 normal 内核跨节点的 43-58 GB/s 与节点内的 153/158 GB/s。显存：固定槽位按最坏情况预留（槽位总数为 $\text{本地专家数}\times\text{每 rank 最大 token 数}\times\text{rank 数}\times h$），消耗远大于 normal 模式，官方建议每 rank 最大 token 数小于 256；另有双缓冲限制（同时最多持有 2 个结果张量）与"QP 数与本地专家数一致"的性能建议。

    4. V2 重构——统一接口与解析式调参

    第 2、3 章的两套内核是 V1 的形态：两套接口、NVSHMEM 后端、SM 数量靠 auto-tuning。V2（2026-04-30 公开）把这些工程面重做，机制内核同源延续。

    4.1 换后端：NVSHMEM 到 NCCL Gin

    V2 从 NVSHMEM 后端切换到 NCCL Gin 后端：header-only、轻量，能复用已有的 NCCL communicator[C18]——EPv2 的通信路径建立在集群通常已部署的 NCCL 之上。注意这不是彻底移除 NVSHMEM：V2 安装仍依赖 NVSHMEM 以支持 legacy 方法（V1 路径）[C18]。全部内核经轻量 JIT 模块在运行时编译，安装时无需 CUDA 编译[C22]。

    4.2 ElasticBuffer：统一接口与更大规模

    高吞吐与低延迟两套 API 统一进单一的 ElasticBuffer 接口，带新的 GEMM 布局；scale-up 与 scale-out 域的支持扩大到 EP2048[C19]。hybrid（分层 RDMA+NVLink，对 multi-plane/multi-rail 网络更友好）与 direct（不分层直达）两种模式都保留[C23]——两段转发的分层思想在 V2 里延续。decode 侧新增 handle 缓存：gating 决策不变时复用缓存 handle 的布局，跳过布局重算与 CPU 同步[C24]。

    4.3 解析式 SM/QP 计算：不再 auto-tuning

    V1 的配置靠 auto-tuning：默认配置在 DeepSeek 内部集群上调优，其他集群建议跑全部测试选最优[C10]。V2 用 ElasticBuffer.get_theoretical_num_sms 按带宽建模直接算出最优 SM 数：输入 RDMA 带宽、NVLink 带宽、单 SM 的 HBM 读/写带宽，假设均衡的 gate 分布[C10]——源码注释明确该函数只针对均衡 gate，V3.0 的 group-limited gate 暂不适用（标记为待支持）。调参从"跑测试扫描"变成"代入参数求解"，代价是建模假设偏离实际负载时结果也会偏离（见文末简化条件）。

    4.4 收益与代价

    收益[C20, N4, N5]：对 V3 式传统训练，通信 SM 从 24 降到 4-6 且性能相当或更好；对比 V1 峰值性能最高 1.3 倍、SM 数最多省 4 倍。V2 实测（每 batch 8K tokens、hidden 7168、top-8 专家、FP8 dispatch + BF16 combine；带宽为逻辑带宽，含本 rank 流量）[N4]：

    架构网卡拓扑dispatch 瓶颈带宽combine 瓶颈带宽SM 数
    SM90CX7EP 8×290 GB/s（RDMA）81 GB/s（RDMA）12
    SM90CX7EP 8×461 GB/s（RDMA）61 GB/s（RDMA）6
    SM100CX7EP 8×290 GB/s（RDMA）91 GB/s（RDMA）12
    SM100无（单节点）EP 8726 GB/s（NVLink）740 GB/s（NVLink）64（最大性能）

    拓扑列记法的含义 README 未定义，本文解读为：EP 8×2 指 8 块 GPU 分布于 2 个节点、EP 8×4 指分布于 4 个节点——依据是这两种拓扑的瓶颈带宽都标注为 RDMA，与跨节点部署一致。官方未公布更大 EP 配置的数字，本表不外推。代价[C21]：buffer 消耗大于 V1；0 SM RDMA 低延迟 EP 不再支持——第 3 章「低延迟内核」hook 形式的"等待不占 SM"在 V2 中移除；Engram（RDMA 远程内存访问）、0 SM PP、0 SM CP 均为实验特性[C32]。

    常见误解：V2 把 V1 的机制全部推翻了。hybrid（分层 NVLink+RDMA）与 direct 两种模式都保留，两段转发的分层思想延续；变化集中在后端、接口、调参方式与规模，个别能力被移除（0 SM RDMA 低延迟 EP）[C19, C21, C23]。

    机制与版本讲完，剩下的问题是边界：哪些 MoE 的麻烦事 DeepEP 不管、由谁管——第 5 章「DeepEP 不解决什么」。

    本章问题

    1. V2 换掉 NVSHMEM 的理由是什么？

      解答：NCCL Gin 更轻且能复用现有 communicator

      NCCL Gin 后端 header-only、轻量，能复用集群上已有的 NCCL communicator，不必为 EP 通信单独维护一套 NVSHMEM 栈。同时全部内核改为运行时 JIT 编译，安装期不再需要 CUDA 编译，部署门槛随之降低。

    2. ElasticBuffer 统一了什么，规模扩到多大？

      解答：两套 API 并一，支持到 EP2048

      高吞吐与低延迟两套 API 统一进单一 ElasticBuffer 接口，带新的 GEMM 布局；scale-up/scale-out 域支持扩大到 EP2048。hybrid（分层 RDMA+NVLink）与 direct 两种模式保留；decode 侧支持 handle 缓存，gating 不变时跳过布局重算与 CPU 同步。

    3. 解析式 SM/QP 计算取代了什么？

      解答：取代 auto-tuning

      V1 靠 auto-tuning 选配置，默认值只在 DeepSeek 内部集群上调优，其他集群要跑全部测试。V2 的 get_theoretical_num_sms 以 RDMA 带宽、NVLink 带宽、单 SM HBM 读写带宽为输入解析求解最优 SM 数（假设均衡 gate 分布），不再需要扫描测试。

    4. V2 的收益与代价各是什么？

      解答：SM 省 4 倍、峰值 1.3 倍；buffer 更大且 0 SM 低延迟移除

      收益：V3 式训练通信 SM 从 24 降到 4-6 且性能相当或更好；对比 V1 峰值最高 1.3 倍、SM 最多省 4 倍；SM100 单节点 EP8 实测 726/740 GB/s。代价：buffer 消耗大于 V1；0 SM RDMA 低延迟 EP（第 3 章「低延迟内核」hook 形式）不再支持；Engram/PP/CP 原语仍是实验特性。

    5. DeepEP 不解决什么——与相邻系统的分工

    5.1 路由与负载均衡不在这里

    DeepEP 只搬不改：dispatch 的输入就是 gating 算出的 topk_idx 与 topk_weights，token 去向完全由模型的路由决定，库内没有改写路由的逻辑。路由不均衡时会发生什么，用构造示例改一下路由就能看清：让 rank 0、1、2 的全部 6 个 token 都把 $E_5$ 列为选择（各自另一个选择分散到别的专家），$E_5$ 的接收行变成 6 个有效槽（槽 0-5，全部来自 rank 0-2），其余专家行的空槽更多。固定槽位按最坏情况预留，6 个 token 不至于溢出——每 rank 至多 2 个 token、8 个 rank 至多 16 份副本，恰好是预留上限；但若按均衡时的平均值（每专家 4 个）预留 buffer，$E_5$ 就装不下了。预留越保守越安全、显存越浪费，这对反向约束就是固定槽位的成本结构。

    均衡问题在 DeepEP 之外分三层解决：gating 算法层（如 V3 的无辅助损失路由，用 bias 调节专家选择，见 辅助损失无关路由）；部署层（复制高负载专家——V3 prefill 设 32 个冗余专家、decode 用 64 块 GPU 承载冗余与共享专家[C27, C28]）；专门系统层（UltraEP 用配额驱动的实时规划与重路由做负载感知均衡，token 搬运基于 DeepEP 的 hybrid-ep 分支；MoonEP 做冗余专家在线规划，保留 DeepEP 的 dispatch/combine 数据路径并以静态形状消除 host 同步）。

    5.2 计算与调度归谁

    计算：接收侧的 grouped GEMM 由配套计算库完成——DeepEP 只保证接收布局按专家分组连续排布，V1 示例注释明说接收格式是给配套 GEMM 库用的，V2 的 handle 还提供 num_recv_tokens_per_expert_list 供 GEMM 使用[C31]。调度：训练侧 DualPipe 把每个 chunk 拆成 attention、dispatch、MLP、combine 四个组件，在前后向 chunk 对内部重排组件并手工调整通信/计算的 SM 配比；论文的表述是，在该重叠策略下 all-to-all 与 PP 通信可以在执行中被完全隐藏[C29]。decode 侧 TBO 交错两个 micro-batch（第 3 章「低延迟内核」）。DeepEP 提供内核，重叠编排是框架的事。

    职责谁负责说明

    token 搬运（dispatch/combine）DeepEP两套内核与接收布局契约
    接收侧专家计算grouped GEMM 计算库消费 DeepEP 的分组布局
    计算通信重叠调度训练/推理框架DualPipe（训练）、TBO（decode）
    负载均衡gating 算法、冗余专家部署、专门系统UltraEP、MoonEP 等

    常见误解：DeepEP 是一个 MoE 推理框架。它是通信库：只提供 dispatch/combine 内核、接收布局与少量实验性通信原语；专家计算、路由、调度、负载均衡都不在库内——上表就是完整的责任划分。

    5.3 使用门槛

    硬件与依赖[C26]：V2 要求 Hopper（SM90）或支持 SM90 PTX ISA 的架构、PyTorch 2.10+、NCCL 2.30.4+、节点内 NVLink、跨节点 RDMA 网络；V1 曾支持 Ampere（SM80，仅节点内）。网络配置[C25]：DeepEP 在 IB 上完整测试，理论上兼容 RoCE；建议用虚拟路（VL）隔离不同类型的流量；V2 建议在所有网络负载条件下开启自适应路由（虽引入额外延迟）；拥塞控制被禁用（损害最大带宽）。

    本章问题

    1. 路由与负载均衡为什么不在 DeepEP 里，不均衡时会发生什么？

      解答：库只搬不改，不均衡由外部分层解决

      dispatch 的输入就是 gating 的输出，DeepEP 不决定 token 去向。不均衡时接收槽位照样空置或拥挤：构造示例里 6 个 token 涌向 $E_5$，其接收行 6/16 槽有效、其余行更空；按最坏预留不会溢出，但按平均预留就会。均衡靠三层：gating 算法（无辅助损失路由）、部署层冗余专家（V3 prefill 32 个、decode 64 块 GPU）、专门系统（UltraEP 的配额重路由、MoonEP 的冗余规划与静态形状）。

    2. 计算与重叠调度分别由谁做？

      解答：grouped GEMM 与框架层

      计算由配套 grouped GEMM 库完成，DeepEP 只保证按专家分组的接收布局（V2 handle 还提供每专家接收数）。调度由框架层做：训练侧 DualPipe 把 chunk 拆成 attention/dispatch/MLP/combine 四组件重排，论文表述为在该重叠策略下 all-to-all 与 PP 通信可在执行中被完全隐藏；decode 侧 TBO 交错两个 micro-batch。DeepEP 提供内核与 hook 这类重叠原语，编排逻辑在框架。

    3. 用 DeepEP 有哪些硬性门槛？

      解答：Hopper 与双网络，IB 全测试

      V2 要求 Hopper（SM90）或支持 SM90 PTX ISA 的架构、PyTorch 2.10+、NCCL 2.30.4+、节点内 NVLink、跨节点 RDMA 网络（V1 曾支持 Ampere SM80 节点内）。网络侧在 IB 上完整测试、RoCE 理论兼容需自行验证；建议 VL 隔离流量、V2 全负载开启自适应路由、禁用拥塞控制。低延迟模式还要求所有 rank 经 RDMA 可见。

    构造示例

    2 节点 8 GPU、8 专家每 rank 1 个、$h=2$、$K=2$、每 rank 2 token 的 EP 系统，以及全部路由表、token 值（$t_{r,j}=(1+r,\ 2+j)$）、权重与 mock 专家 $\operatorname{FFN}_e(x)=(x_0+e,\ x_1+e)$，均为构造数据，目的是让 dispatch/combine 语义、两段转发路径、槽位布局与带权归约可手算复算。第 3 章「低延迟内核」的显式路由表构造原则：rank 0 的两个 token 分别给出节点内与跨节点路径、每专家恰好 4 个 token、无自路由。第 5 章「DeepEP 不解决什么」中"6 个 token 涌向 $E_5$"是改路由后的对照构造。均不代表真实部署规模与数据。

    简化条件及其限制

    • 槽位模拟代码：用数组读写代替 RDMA、mock FFN 代替 grouped GEMM、不做 FP8 量化、不含 hook 与双缓冲。它验证槽位下标规则与带权归约的一致性，不能推出真实内核的延迟、带宽与显存占用。
    • V2 解析式 SM 计算的"假设均衡 gate 分布"是官方建模假设，实际负载不均衡时解析结果会偏离最优；且源码注释明确该函数只针对均衡 gate，V3.0 的 group-limited gate 暂不适用（官方标记为待支持），使用前需确认路由形态。
    • 两段转发的流量手算只计链路流动字节，不含协议开销与元数据；据此只能比较路径长短与网络占用结构，不能推出实测带宽。
    • 贯穿示例的 8 专家、$h=2$ 规模是为了手算方便；真实系统的专家数（如 V3 的 256 个路由专家）、hidden（7168）与 rank 数都大得多，但 dispatch/combine 的语义与槽位规则同构。
