概念概览 · MoE 专家并行通信

DeepEP

DeepSeek 开源的专家并行通信库：为 MoE 的 token 搬运（dispatch 与 combine）提供高吞吐与低延迟两套 all-to-all 内核，只做通信，不做路由、计算与调度。

更新于 2026-09-03

MoE 模型的每一层都要把 token 发给专家所在的 GPU（dispatch），算完再送回来加权合并（combine），形态是 all-to-all。DeepSeek-V3 的 decode 部署在 320 块 GPU 上每块只放 1 个专家，每生成一个 token 都要完成一次全集群的来回搬运。

问题背景

通用集合通信库（如 NCCL）的 all-to-all 原语不适配这个场景的四个结构性要求：通信不能抢计算的 SM（V3 训练用 20/132 个 SM 专职通信）；接收数据要按专家分组排布、供 grouped GEMM 直接消费；dispatch 载荷要用 FP8；decode 的每步小 batch 通信要低延迟且兼容 CUDA graph。跨节点专家并行的计算通信比约为 1:1，通信本身就是要正面优化的对象。

核心机制

  • 高吞吐内核（训练/prefill）：两段转发——token 先经 IB 到目标节点上与发送 rank 同 in-node index 的 GPU，落地后经 NVLink 转发给持有目标专家的 GPU，不被后到 token 阻塞，IB 与 NVLink 完全重叠；20 个 SM 分 10 个通道、warp 专职分工即可跑满两种网络。
  • 低延迟内核（decode）：纯 RDMA——所有 rank（含节点内）经 RDMA 可见、NVLink 完全禁用，点对点直达去掉中转与同步；接收张量按最坏情况预留固定槽位，不做 CPU 接收计数同步从而兼容 CUDA graph；接收 hook 让 dispatch 只发请求不等待，等待期 GPU 计算另一个 micro-batch，不占任何 SM。
  • 路由配合：node-limited routing 限制每 token 至多 4 个目标节点以省 IB 流量；平均 3.2 专家/节点、等效最多 13 个专家。
  • V2 重构：NCCL Gin 后端替换 NVSHMEM、ElasticBuffer 统一两套 API、SM/QP 数解析式计算取代 auto-tuning、支持到 EP2048、全 JIT 编译。

关键结论与边界

  • 实测带宽逼近硬件峰值：V1 节点内 153/158 GB/s（NVLink 峰值约 160）、跨节点 43-58 GB/s（RDMA 峰值约 50）；V2 对 V3 式训练把通信 SM 从 24 降到 4-6 且性能相当或更好，峰值最高 1.3 倍。
  • 低延迟是用带宽换的：纯 RDMA 的折算带宽在 EP128 时只有 39 GB/s，明显低于高吞吐内核；固定槽位按最坏预留，显存消耗远大于 normal 模式。
  • DeepEP 只搬 token：路由决策、专家计算（grouped GEMM）、负载均衡（冗余专家、UltraEP/MoonEP 等系统）、重叠调度（DualPipe/TBO）都在库外。
  • 硬性门槛：Hopper（SM90）及以上、节点内 NVLink、跨节点 RDMA 网络；IB 全测试、RoCE 理论兼容；V2 的 buffer 消耗大于 V1、0 SM RDMA 低延迟 EP 不再支持。
