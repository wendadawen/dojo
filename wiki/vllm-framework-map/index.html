    vLLM 框架全景

    vLLM 的进程按 API Server、EngineCore、GPU Worker、DP Coordinator 四类划分；代码按入口、引擎、执行、模型、编译五层组织，外加采样、推测解码、结构化输出、KV 传输等跨层子系统。

    更新于 2026-08-21 · 类型：框架总览（检出 v0.23.1rc0-1383-g95e073e17）

    1. 进程架构

    一个部署中的进程数量由并行度决定：API Server 默认与数据并行数相同；EngineCore 每个数据并行 rank 一个；GPU Worker 每张卡一个；数据并行大于 1 时额外有一个 DP Coordinator 做负载均衡与 MoE 同步。

    进程类型数量职责
    API Server默认 = DP（可配）HTTP 请求、tokenize、多模态预处理、流式返回；与所有 EngineCore 经 ZMQ 多对多连接
    EngineCore= DP调度器、KV cache 管理、忙等循环、向 worker 派发
    GPU Worker= DP × PP × TP（即卡数）加载权重、执行 forward、管理显存
    DP CoordinatorDP>1 时 1 个跨 DP rank 负载均衡、MoE 同步

    单机 4 卡 TP=4 共 6 个进程（1 API + 1 EngineCore + 4 Worker）；8 卡 TP=2 DP=4 共 17 个进程。进程间通信三类：请求与结果走 ZMQ（单机 ipc、跨机 tcp）；EngineCore 到 worker 的调用广播走共享内存环形缓冲 + ZMQ 发布订阅；GPU 之间走 NCCL。API Server 与 EngineCore 两个进程各自的代码边界、忙等循环与 Executor→Worker→Runner 三层调用链，另见 vLLM V1 框架总览。

    4. 关键设计决策

    官方架构总览给出三个贯穿全部代码的决策：

    1. VllmConfig 全局配置对象：所有类接收同一个完整配置对象而非逐项参数；新增功能只需在 VllmConfig 增加字段，任何层直接读取，无需层层修改构造函数。
    2. 统一模型构造签名：所有模型构造函数统一为 __init__(*, vllm_config, prefix="")。ModelRunner 不必知道模型类型即可创建模型；视觉语言模型可由子模型组合而成。prefix 用于非均匀量化（模型不同部分用不同量化）。
    3. 分片与量化在初始化时完成：不在加载后处理。以 405B 模型跑 16 卡为例，若先加载全部再分片，每卡都要装下 810GB；初始化时分片则每层只创建自己需要的分片，显存开销显著更小。量化同理。

    6. 请求生命周期

    一次生成请求依次经过九个环节：① 请求进来（前端预处理）→ ② ZMQ 交给 EngineCore → ③ 主循环收请求进调度器 → ④ 调度选批 → ⑤ 模型 forward → ⑥ 采样出新 token → ⑦ 更新 KV cache → ⑧ 新 token 回下一轮 → ⑨ 结果回 API Server。

    链路三段各归其位：前端预处理在 API Server 的 renderers 链路（tokenize、多模态图片加载与 smart_resize）；模型输入准备在 worker，由 v1/worker/gpu_model_runner.py 的 _preprocess 完成（含 _gather_mm_embeddings、_prepare_mm_inputs 等函数，并调用模型对象的 embed_input_ids）；采样由 v1/sample/ 的采样器完成。三段原理见关联笔记多模态图片的两阶段处理与多模态统一输入与 cudagraph。
