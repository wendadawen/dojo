vLLM 框架全景

vLLM 的进程按 API Server、EngineCore、GPU Worker、DP Coordinator 四类划分；代码按入口、引擎、执行、模型、编译五层组织，外加采样、推测解码、结构化输出、KV 传输等跨层子系统。

更新于 2026-08-21 · 类型：框架总览（vLLM 0.22.2.dev）

1. 进程架构

一个部署中的进程数量由并行度决定：API Server 默认与数据并行数相同；EngineCore 每个数据并行 rank 一个；GPU Worker 每张卡一个；数据并行大于 1 时额外有一个 DP Coordinator 做负载均衡与 MoE 同步。

进程类型数量职责
API Server默认 = DP（可配）HTTP 请求、tokenize、多模态预处理、流式返回；与所有 EngineCore 经 ZMQ 多对多连接
EngineCore= DP调度器、KV cache 管理、忙等循环、向 worker 派发
GPU Worker= DP × PP × TP（即卡数）加载权重、执行 forward、管理显存
DP CoordinatorDP>1 时 1 个跨 DP rank 负载均衡、MoE 同步

单机 4 卡 TP=4 共 6 个进程（1 API + 1 EngineCore + 4 Worker）；8 卡 TP=2 DP=4 共 17 个进程。进程间通信三类：请求与结果走 ZMQ（单机 ipc、跨机 tcp）；EngineCore 到 worker 的调用广播走共享内存环形缓冲 + ZMQ 发布订阅；GPU 之间走 NCCL。

4. 关键设计决策

官方架构总览给出三个贯穿全部代码的决策：

  1. VllmConfig 全局配置对象：所有类接收同一个完整配置对象而非散装参数。新增功能只需在 VllmConfig 加字段，任何层直接读取，不用层层改构造函数——这是应对快速演进的扩展性设计。
  2. 统一模型构造签名：所有模型构造函数统一为 __init__(*, vllm_config, prefix="")。ModelRunner 不必知道模型类型即可创建模型；视觉语言模型可由子模型组合而成。prefix 用于非均匀量化（模型不同部分用不同量化）。
  3. 分片与量化在初始化时完成：不在加载后处理。以 405B 模型跑 16 卡为例，若先加载全部再分片，每卡都要装下 810GB；初始化时分片则每层只创建自己需要的分片，显存开销最小。量化同理。

6. 走读路线与进度基准

生命周期主线

① 请求进来（前端预处理）→ ② ZMQ 交给 EngineCore → ③ 主循环收请求进调度器 → ④ 调度选批 → ⑤ 模型 forward → ⑥ 采样出新 token → ⑦ 更新 KV cache → ⑧ 新 token 回下一轮 → ⑨ 结果回 API Server。

三段式路线

段内容目的
第一段 走完生命周期主线：_preprocess 剩余三函数 → _model_forward → postprocess → 采样（v1/sample）→ KV cache 管理（block_pool / kv_cache_manager）→ 循环收尾 打通一次请求的完整闭环
第二段 框架支柱：attention 后端选择器（v1/attention/selector + platforms 联动）→ 编译层全流程（torch_compile 设计文档对照）→ 模型层骨架（公共层体系、量化初始化介入、加载器） 理解框架的三大支柱机制
第三段 按兴趣选：推测解码（eagle）/ 结构化输出 / KV 跨机传输（PD 分离）/ LoRA / pooling 扩展视野
