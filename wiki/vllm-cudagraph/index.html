    torch.compile 图捕获与 CUDA Graph

    torch.compile 通过 TorchDynamo 将前向计算捕获为计算图、再由 Inductor 编译为 GPU kernel 以提升推理性能；图捕获阶段的约束决定了哪些代码可被编译，解码阶段则由 CUDA Graph 录制一次、逐批重放。

    更新于 2026-09-13 · 类型：学习笔记

    1. torch.compile 的两阶段流程

    PyTorch 默认的 forward() 以逐行解释方式执行：每条 Python 语句通常对应一次或多次算子（kernel）提交，中间结果写入显存、再由后续算子读回，解释器与 kernel 启动存在固定开销。torch.compile 通过将计算整体化为可复用编译产物来大幅降低这部分开销，分为两个阶段：

    1. 图捕获（graph capture）：由 TorchDynamo 在运行前向时，将 Python 层调用逐条转换为一张计算图（graph），图中节点对应算子。
    2. 图编译（graph compilation）：由后端将计算图翻译为可执行的 GPU kernel。torch.compile 的默认后端为 Inductor（PyTorch 官方内置），其通过代码生成以 Triton 语言产出 kernel，再编译为 CUDA 机器码。产物除 kernel 外，还包括调用它们的执行计划，整体封装为可复用的编译函数，此后推理直接执行该产物、不再逐行解释。

    2. Dynamo 图捕获的处理边界

    图捕获要求计算中的每个可追踪节点都能映射为图算子，或可被安全地 graph break（跳出图、回落到 Python 执行）。Dynamo 对代码类型的处理方式如下：

    代码类型Dynamo 处理方式结果
    张量运算（torch.add、torch.matmul）映射为图节点正常编译
    可静态展开的控制流（for 循环、len）展开或追踪为图节点正常编译
    数据相关的控制流（分支/循环条件依赖张量取值，如 if x.sum() > 0）graph break，回落到 Python 执行可继续，性能下降
    C 扩展（如 hashlib.sha1）无追踪规则，标记为 skipped 并 graph break可继续（fullgraph=True 时以 Unsupported 失败）

    graph break 是软性失效：图在该位置断开、控制流回落 Python，执行仍可继续。被标记为 skipped 的 C 扩展同样走这条路径，Dynamo 按 graph break 处理（并给出一次警告），编译继续；只有在 fullgraph=True（或 nopython）模式下，这类 graph break 才被当作硬错误，抛出 Unsupported 终止捕获。

    C 扩展指通过 CPython C API 编译为共享库（.so）供 Python 调用的函数。这类函数对 Dynamo 而言是黑盒，无法映射为图节点，默认模式下 Dynamo 在此 graph break 并给出警告、执行继续。警告文本形如：Dynamo does not know how to trace the builtin `_hashlib.openssl_sha1.`

    3. CUDA Graph 的录制与重放

    即便 kernel 已编译完成，每次推理仍由 CPU 逐个向 GPU 提交 kernel，每次提交存在固定延迟（CPU 到 GPU 的命令下发开销）。CUDA Graph 将完整的 GPU 执行序列——包括 kernel 顺序、各 kernel 参数、输入输出内存地址及数据搬运操作——一次性录制（capture）为一张图，此后 CPU 仅需一次命令即可整张重放（replay），从而消除逐个下发的开销。

    • 适用阶段：主要用于解码（decode）阶段。decode 每步仅生成一个 token，kernel 单次计算量小但数量多，CPU 逐个下发开销占比较高，且计算形状相对稳定，适合以 FULL（整图）模式录制重放；预填充（prefill）单次处理的 token 数变化大、计算形状动态，整图重放不适用，vLLM 对其通常采用 PIECEWISE 分段录制或直接落到 eager 执行。每步是否重放捕获图由 GPUModelRunner 查表决定，这一层在引擎进程中的位置见 vLLM V1 框架总览。
    • 开销特征：录制开销较大（需逐次执行、记录地址与依赖、分配内存池），因此只执行一次并复用；重放开销极小。
    • 显存代价：录制须预留固定地址的内存池（memory pool），池中空间存放被固化的输入输出与中间张量，不随重放释放。vLLM 为全部捕获图共用同一个全局 cudagraph 内存池（get_global_graph_pool 返回类级单例），录制时以该池提交，故显存占用由最大捕获尺寸所对应的工作集决定，而非随捕获图数量线性增长；图本身另占每张数十至数百 MB 量级（此量级为推断）。捕获尺寸上限默认不超过 512：在紧凑显存场景下避免 OOM，并避免为收益有限的大批量捕获大量图而大幅拉长启动时间（compilation.py 注释）。
    • 核心约束：录制时地址被固化，重放阶段输入输出内存地址不可改变，故数据须存放于预分配的固定内存池中（如 vLLM 的 KV cache 缓冲区即为此设计）。

    4. 捕获尺寸的确定

    CUDA Graph 捕获的尺寸以解码阶段的总 token 数为单位。decode 中每个请求每步仅产生一个 token（无投机解码时），故单步总 token 数等于并发请求数（num_seqs，即 batch size）。上下文长度（seq_len）不进入尺寸组合：注意力经分页 KV cache 与 block table 读取，与上下文长度解耦。

    默认捕获尺寸按 [1, 2, 4] + list(range(8, 256, 8)) + list(range(256, max_cudagraph_capture_size + 1, 16)) 生成，末元素即最大捕获尺寸 max_cudagraph_capture_size。未显式指定时，该上限默认取 min(max_num_seqs × decode_query_len × 2, 512)，再与 max_num_batched_tokens 取较小值；其中 decode_query_len = 1 + num_speculative_tokens（无投机解码时为 1）。实际总 token 数不落在合法捕获尺寸上时，按邻近的合法尺寸向上补齐（padding）。尺寸超出捕获上限或未命中捕获记录时退回 eager 执行；据多模态统一输入与 cudagraph的走读数据，decode 命中 FULL 重放，而单批 token 数超出捕获尺寸上限的大 prefill 落到 eager。
