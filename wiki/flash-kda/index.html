    FlashKDA 与 KDA Context Parallelism：让 KDA 的串行状态在 GPU 上高效跑起来

    主要依据：Kimi K3 Technical Report §5.1.1（FlashKDA、设备内 CP）、§5.1.2（KCP，Eq.17）、§5.4.2（KDA 解码 kernel）。KDA 递归公式 Eq.1 见 §2.1.1，完整机制见 KDA 概念页。

    Kimi K3 用 69 层 KDA 替换 softmax 注意力，把随序列增长的 KV cache 压成固定大小的递归状态——省了显存，但状态必须串行更新。一块 H100 有 132 块 SM 靠宽并行隐藏延迟，串行依赖却让多数 SM 排队等状态。这个冲突在四个执行 regime 下表现成不同瓶颈。K3 为每个 regime 设计了专门方案。本文讲解这四套方案——FlashKDA、设备内 CP、KCP、投影输入缓存——各自解决什么瓶颈，核心机制是什么。

    核心问题

    1. KDA 的串行状态更新为什么与 GPU 并行偏好冲突，为什么这个冲突在不同执行 regime 表现成不同瓶颈。

      解答：串行依赖与宽并行的对立，四 regime 各有瓶颈

      KDA 的递归 $S_t = M_t S_{t-1} + \beta_t k_t v_t^\top$ 要求状态一步一步串行更新，而 GPU 靠宽而均匀的并行隐藏延迟，两者对立。冲突在训练/prefill、长 prefill、跨设备、解码四个 regime 下分别表现为 chunkwise 两阶段交替导致 SM 空转、纯 TP 填不满 SM、各 rank 状态不能直接求和、投机解码拒绝 draft token 后状态无法回滚。完整论证见「1. 串行状态 vs GPU 并行」章。

    2. FlashKDA 如何把 intra-chunk 计算与 cross-chunk 状态传播重叠起来。

      解答：token-parallel 与 head-parallel 独立调度

      FlashKDA 把工作分解为 chunk 内 token 维度并行的 token-parallel stages 和 head 维度递归的 head-parallel recurrence，各自独立调度。不同 head 的状态递归互相独立，因此算一个 chunk 的 intra-chunk 计算时可以同时传另一些 head 的状态，两阶段流水线重叠而非交替等待。见「2. FlashKDA」章。

    3. 设备内 context parallelism 如何在单 rank 上并行一条长序列，且不产生跨设备通信。

      解答：SM 级切序列，段转移独立计算后精确合并

      关键观察是 KDA 状态转移为线性：一段 token 的转移效果可分解成作用于入状态的部分和从零生成的部分，独立于入状态预先算好。SM 级 CP planner 据此把序列切到单 rank 的多块 SM 上并行算段转移，再合并恢复每段精确初始状态；SM 之间通过 shared memory / L2 协作，完全不走跨设备通信。见「3. 设备内 context parallelism」章。

    4. KCP 为什么不能像 vanilla 线性注意力那样直接求和本地状态，它的 $M+\tilde S$ 分解如何让通信量与序列长度无关。

      解答：$M_t$ 作用于入状态，需分解后 all-gather 固定大小片段

      vanilla 线性注意力递归是纯加性，本地状态可直接求和；KDA 的 delta rule 先用 token-dependent 矩阵 $M_t$ 作用于入状态再加写入，本地段效果依赖入状态，直接求和会漏掉累积转移。KCP 把每段效果分解为累积转移 $M_{t\leftarrow 1}$（本地 token 的 $M$ 连乘）与从零生成的状态 $\tilde S$，两者都可在入状态可用前本地算出；各 rank 一次 all-gather 交换这两个固定大小的片段，再用 prefix scan 重组入状态，通信量与序列长度无关。见「4. KCP」章。

    5. KDA 解码如何处理投机解码拒绝 draft token 时的状态回滚，又不让状态流量爆炸。

      解答：缓存投影输入，片上重跑递归重建状态

      为每个 draft 位置存状态快照会把状态流量乘上 draft 长度，大 batch 在线服务下不可接受。K3 的方案是只缓存 draft token 的投影输入（几个 $d_k$ 维向量，比 $d_k\times d_v$ 的状态矩阵小得多）：任意接受前缀后的状态由投影输入完全决定，验证后在片上重跑 KDA 递归即可重建接受 token 的状态并写回。投影缓存不离开 decode 阶段，不污染上层服务架构。见「5. KDA 解码」章。

    最容易误解

    • "FlashKDA 就是把 chunkwise 形式实现一遍" —— chunkwise 形式 chunk 内并行、chunk 间串行，朴素实现两者交替会让 SM 在传播时空转；FlashKDA 的关键是把 intra-chunk 计算与 cross-chunk 状态传播重叠，不是简单实现。
    • "设备内 CP 和 KCP 是同一回事，都是跨设备" —— 设备内 CP 完全在单 rank 的 SMs 上切序列、无跨设备通信；KCP 是跨 device rank、需要一次 all-gather。
    • "KCP 只是把线性注意力的 CP 搬到 KDA" —— vanilla 线性注意力递归是纯加性，各 rank 本地状态可直接求和；KDA 的 delta rule 有 token-dependent $M_t$ 作用于入状态，本地段效果依赖入状态，不能直接求和——必须分解成 $M+\tilde S$。
    • "KDA 解码的回滚就是存状态快照" —— 状态快照能支持回滚但流量在大 batch 下占主导；方案是缓存更小的投影输入、片上重建。

    1. 串行状态 vs GPU 并行——为什么 KDA 在四个 regime 瓶颈不同

    KDA 把 softmax 注意力随序列长度增长的 KV cache 压成了一个固定大小的递归状态 $S_t \in \mathbb{R}^{d_k \times d_v}$（K3 config.json 中 $d_k=d_v=128$，约 32KB[N1]）。省了显存，但代价是状态必须一步一步串行更新。K3 报告 §2.1.1 的 Eq.1[F1]给出单步更新：

    $$S_t = M_t S_{t-1} + \beta_t k_t v_t^\top,\qquad M_t := I - \beta_t k_t k_t^\top \mathrm{Diag}(\alpha_t).$$

    关键在右边：$S_t$ 依赖 $S_{t-1}$。要算第 $t$ 步的状态，必须先有第 $t-1$ 步的状态。这是一个串行依赖。KDA 的机制、$M_t$ 的含义、channel-wise forget gate 的作用由 KDA 概念页完整讲解，本页只引用 Eq.1 与 $M_t$ 的结论。

    串行依赖和 GPU 的天性对立。一块 GPU（以 H100 为例）有 132 块 SM[N3]，每块 SM 内还有多个 warp 轮流占用计算单元——GPU 靠宽而均匀的并行隐藏延迟、撑满算力，详见 GPU 执行模型页。当一个计算必须一步步串行时，同一时刻只有少数 SM 在干活，其余的排队等状态。

    这个冲突不是抽象的——它在 KDA 的四个执行 regime 下表现成不同的瓶颈。K3 报告 §5.1.1 开门见山："The serial dependence of the KDA state is at odds with the GPU's preference for wide, uniform parallelism, and it manifests as a different bottleneck in each execution regime."[C1]所以 K3 为每个 regime 设计了专门的方案：

    执行 regime串行依赖表现为K3 的方案对应章节
    训练 / prefillchunkwise 形式里 intra-chunk 计算与 cross-chunk 状态传播交替，SM 在传播时空转FlashKDA：重叠两阶段FlashKDA
    长 prefill（纯 TP 部署）每个 rank 只持少量 head，132 块 SM 大部分闲设备内 CP：SM 级切序列设备内 CP
    跨设备（序列超单卡）线性注意力的"各 rank 求和"对 KDA 不成立KCP：$M+\tilde S$ 分解 + prefix scanKCP
    解码（MTP 投机）瓶颈从"利用并行"转为"管理原地更新的状态"投影输入缓存 + 片上重建KDA 解码

    先看 chunkwise 形式（KDA 页已完整讲过）留下的空隙。chunkwise 把序列切成大小 $C$ 的 chunk：chunk 内并行 matmul（intra-chunk，所有位置同时算），chunk 间串行传 $S$（cross-chunk，$S[t]\to S[t+1]$）。朴素执行里这两阶段交替：

    朴素 chunkwise 的时间线（chunk 间有空隙）：

  时间 -->
  chunk 1: [算 intra] [传 S→]            chunk 2: [算 intra] [传 S→]
           ^满载 SM    ^少数 SM 推状态      ^满载 SM    ^少数 SM 推状态
                       +-- 空隙：多数 SM 闲                  +-- 空隙

  intra-chunk 计算和 cross-chunk 状态传播交替进行，传播时多数 SM 空转

    这个空隙就是 FlashKDA 要解的第一个瓶颈。本章先建立"冲突根源 + 四 regime 定位"的框架，后续四章各解一个 regime。

    本章建立了冲突根源与四 regime 定位的框架。但框架只是开始，每个 regime 还需要专门方案——下一章讲 FlashKDA 如何重叠 chunk 内计算与 chunk 间状态传播。

    本章问题

    1. KDA 串行状态与 GPU 并行偏好冲突的根源是什么，Eq.1 的哪个符号体现了这个根源。

      解答：$S_{t-1}$ 的串行依赖

      根源在 Eq.1 右边的 $S_{t-1}$：$S_t = M_t S_{t-1} + \beta_t k_t v_t^\top$ 使得第 $t$ 步必须先有第 $t-1$ 步的状态，状态只能一步一步串行更新。GPU 靠宽而均匀的并行隐藏延迟、撑满算力（H100 有 132 块 SM），串行依赖让同一时刻只有少数 SM 在干活，其余排队等状态。

    2. 对照四个 regime 的表，指出各自瓶颈的定位。

      解答：空转、填不满、求和失效、回滚受阻

      训练/prefill：chunkwise 形式里 intra-chunk 计算与 cross-chunk 状态传播交替，SM 在传播时空转。长 prefill（纯 TP）：TP 切 head 不缩短递归，每 rank 只持少量 head，SM 大部分闲。跨设备：线性注意力"各 rank 求和"对 KDA 不成立。解码：瓶颈从利用并行转为管理原地更新的状态。

    3. chunkwise 形式为何"比纯串行快但仍有空隙"，空隙出在哪两个阶段之间。

      解答：chunk 内可并行，传播期空转

      chunkwise 把序列切成大小 $C$ 的 chunk：chunk 内的 matmul 可在 token 维度铺开到多块 SM 同时算，所以比逐步串行快；但 chunk 间传 $S[t]\to S[t+1]$ 只由少数 SM 推进，intra 的 SM 此时无事可做。空隙出在 intra-chunk 计算与 cross-chunk 状态传播两阶段的交替处——传播期间多数 SM 空转。

    2. FlashKDA——把 chunk 内计算与 chunk 间状态传播重叠

    上一章看到 chunkwise 形式里 intra-chunk 计算和 cross-chunk 状态传播交替、SM 在传播时空转。朴素实现的根源是：算 chunk $t$ 的 intra-chunk 时，cross-chunk 的 $S[t]\to S[t+1]$ 没法开始（要等 intra 算完才有 $S[t]$）；传 $S$ 时，intra 的 SM 又无事可做。两个阶段互相等待。

    FlashKDA[C2]是 K3 为此开发的 CUTLASS-based chunkwise kernel。它的核心动作是一个词：重叠。具体做法是把工作分解成两个独立调度的部分：

    • token-parallel stages：chunk 内的 token 维度并行。一个 chunk 有 $C$ 个 token，intra-chunk 的位置-位置 attention 可以在 token 维度上铺开到多块 SM 同时算。
    • head-parallel recurrence：chunk 间的 head 维度递归。KDA 有多个 head（K3 配置 96 个 head[N2]），不同 head 的状态递归互相独立——算 head $h$ 的 $S[t]\to S[t+1]$ 不需要等 head $h'$ 的 intra-chunk。

    各自独立调度后，chunk $t$ 的 intra-chunk 计算就能和 chunk $t-1 \to t$ 的状态传播同时进行：当 token-parallel 阶段在算 chunk $t$ 的 intra 时，head-parallel 阶段在传另一些 head 的状态。两阶段不再交替等待，而是流水线重叠。

    FlashKDA 的重叠时间线（对比上一章的朴素版本）：

  时间 -->
  head A: [算 intra t] [传 S] [算 intra t+1] [传 S]
  head B:    [传 S] [算 intra t] [传 S] [算 intra t+1]
  head C:       [传 S] [算 intra t] [传 S] [算 intra t+1]
                 +-- 两阶段重叠，SM 持续有活干 --+

  token-parallel（chunk 内 token 维度）和 head-parallel（head 维度递归）独立调度
  intra-chunk 计算与 cross-chunk 状态传播重叠，消除上一章的空隙
    分解的部分并行维度职责
    token-parallel stageschunk 内 token算 intra-chunk 的位置-位置 attention
    head-parallel recurrencehead（96 个互相独立）传 cross-chunk 状态 $S[t]\to S[t+1]$

    工程定位：FlashKDA 是 CUTLASS-based（NVIDIA 的高性能 kernel 模板库），同时服务训练和推理 prefill两个场景，并作为 flash-linear-attention 框架的一个后端自动分发——这意味着上层调用方不需要手写 dispatch，框架会自动选用 FlashKDA[C2]。CUTLASS 模板编程和 Tensor Core 的具体调度细节超出本页职责，GPU 执行模型页已讲 SM/CTA/warp 层面足够支撑这里的理解。

    本章讲了 FlashKDA 通过重叠消除 chunk 间空隙。但 FlashKDA 仍假设序列在一个 rank 上跑完，长 prefill 下纯 TP 填不满 SM——下一章讲设备内 CP 如何在单 rank 的 SM 级切序列。

    本章问题

    1. 朴素 chunkwise 实现里，SM 空转发生在哪个阶段。

      解答：cross-chunk 状态传播期

      空转发生在 cross-chunk 的传播期。算 chunk $t$ 的 intra-chunk 时，$S[t]\to S[t+1]$ 的传播没法开始（要等 intra 算完才有 $S[t]$）；传 $S$ 时又只有少数 SM 推状态，intra 的 SM 无事可做。两个阶段互相等待、交替空转。

    2. token-parallel 与 head-parallel 各自并行什么维度，为什么 head 之间可以独立递归。

      解答：token 维度与 head 维度，head 递归互不依赖

      token-parallel stages 并行 chunk 内的 token 维度，算 intra-chunk 的位置-位置 attention；head-parallel recurrence 并行 head 维度，传 cross-chunk 状态 $S[t]\to S[t+1]$。K3 配置 96 个 head，不同 head 的状态递归互相独立——算 head $h$ 的传播不需要等 head $h'$ 的 intra-chunk，因此两部分可各自独立调度、重叠执行。

    3. FlashKDA 服务的两个场景是什么，它的后端宿主框架是哪个。

      解答：训练与推理 prefill，flash-linear-attention

      FlashKDA 同时服务训练和推理 prefill 两个场景，并作为 flash-linear-attention 框架的一个后端自动分发——上层调用方不需要手写 dispatch，框架会自动选用 FlashKDA。

    3. 设备内 context parallelism——单 rank 的 SM 级切序列

    FlashKDA 让 chunk 内外重叠，但它仍然假设"序列在一个 rank 上跑完"。当 prefill 一条超长序列时，新的瓶颈出现：Tensor Parallelism（TP）的局限。

    TP 是把 attention 的不同 head 切到不同设备——设备 A 算 head 1–24，设备 B 算 head 25–48，以此类推。但 TP 切的是 head 维度，不缩短序列方向的递归步数。K3 报告 §5.1.1 原文："Tensor parallelism partitions heads across devices but never shortens the recurrence"[C3]。后果是：纯 TP 部署下 prefill 一条超长序列时，每个 rank 只持少量 head，132 块 SM 大部分闲着——递归还得一步步走，只是走的 head 少了。

    TP 切 head vs 设备内 CP 切序列（单 rank 内）：

  纯 TP（head 切到多卡，序列不切）：
    rank 0: head 1-24 --> 序列 1→N 一步步走（只有 24 个 head，SM 大量空闲）
    rank 1: head 25-48 --> 序列 1→N 一步步走
    递归步数没缩短，每 rank 的 SM 没填满

  设备内 CP（序列切到单 rank 的多块 SM）：
    rank 0 的 SM 0: 序列段 1     +
    rank 0 的 SM 1: 序列段 2     | 各 SM 并行算段转移
    rank 0 的 SM 2: 序列段 3     | 之后合并恢复每段入状态
    ...                          +
    序列方向被切短，SM 填满，且无跨设备通信

    设备内 CP 能成立，靠的是一个关键观察：KDA 的状态转移 $S_t = M_t S_{t-1} + \beta_t k_t v_t^\top$ 是线性的——一段 token 的转移效果可以分解成"作用于入状态的部分"和"从零生成的部分"，独立于入状态预先算好，之后精确合并[C3]。这个性质是 KCP 的前置，也是设备内 CP 的基础。具体怎么分解是 KCP 章的核心，这里先用结论：每段的 segment transition 可以独立计算。

    有了这个观察，SM 级 CP planner把序列切到单 rank 的多块 SM：每块 SM 算一段的 segment transition（独立于入状态），算完后合并恢复每段的精确初始状态[C3]。关键区别在通信：

    • 设备内 CP：完全在一个 rank 的 SMs 之间，无跨设备通信。SM 之间通过 shared memory / L2 协作，不走网络。
    • KCP（下一章）：跨 device rank，需要一次 all-gather。

    这个区别是设备内 CP 和 KCP 最容易混淆的点（见页首误解提示）。设备内 CP 解决的是"单 rank SM 没填满"，KCP 解决的是"序列超单卡"——两者层次不同。

    本章讲了设备内 CP 在单 rank 内切序列、无跨设备通信。但序列长到一台设备装不下时需要跨 device rank——下一章讲 KCP 为什么不能直接求和以及 $M+\tilde S$ 分解。

    本章问题

    1. TP 切的是哪个维度，为什么它不缩短序列方向的递归。

      解答：切 head 维度，递归步数不变

      TP 把 attention 的不同 head 切到不同设备——设备 A 算 head 1–24、设备 B 算 head 25–48，以此类推。head 维度的切分不缩短序列方向的递归步数：纯 TP 部署下 prefill 超长序列时，每个 rank 只持少量 head，132 块 SM 大部分闲着，递归还得一步步走，只是走的 head 少了。

    2. "段转移可独立于入状态计算"依赖 KDA 递归的什么性质（提示：看 Eq.1 里 $M_t$ 和加性项的关系）。

      解答：状态转移的线性性

      依赖 KDA 状态转移的线性性：$S_t = M_t S_{t-1} + \beta_t k_t v_t^\top$ 中 $M_t$ 与加性项可分离，一段 token 的转移效果可以分解成"作用于入状态的部分"和"从零生成的部分"，两者都独立于入状态预先算好，之后精确合并。若递归非线性使段转移不可分离，这个性质不成立。

    3. 设备内 CP 与 KCP 在通信上的根本区别是什么。

      解答：SM 间协作 vs 跨设备 all-gather

      设备内 CP 完全在一个 rank 的 SMs 之间，SM 通过 shared memory / L2 协作，无跨设备通信；KCP 是跨 device rank 的方案，需要一次 all-gather 交换状态片段。两者解决的问题层次也不同：设备内 CP 解决"单 rank SM 没填满"，KCP 解决"序列超单卡"。

    4. KCP——为什么不能直接求和，以及 $M+\tilde S$ 分解

    跨设备时，最自然的想法是借鉴 vanilla 线性注意力的 context parallelism。但它对 KDA 不成立——这一章讲清楚为什么，以及 K3 的 KCP 怎么解决。

    4.1 先看 vanilla 线性注意力为什么能直接求和

    线性注意力页讲过，vanilla 线性注意力的因果递归是纯加性的[F3]：

    $$s_i = s_{i-1} + \phi(k_i) v_i^\top.$$

    其中 $\phi$ 是 key 的特征映射（feature map），详见线性注意力页；本页只需用"纯加性、无矩阵作用于入状态"这一性质。

    注意右边没有任何矩阵作用于 $s_{i-1}$——新状态就是旧状态直接加一个外积。这意味着：如果把序列切成多段分给多个 rank，每个 rank 从 $s=0$ 起算本地段的累加，然后把前序 rank 的本地状态直接求和，就恢复了入状态[C4]。K3 报告 §5.1.2 原文："Prior context-parallel methods exploit the additive recurrence of vanilla linear attention by computing, on each rank, the state that the local tokens generate from S = 0 and summing these local states over the preceding ranks to recover the incoming state."

    vanilla 线性注意力的跨设备 CP（可直接求和）：

  rank 0: s̃_0 = φ(k1)v1^T + φ(k2)v2^T   （从 s=0 起）
  rank 1: s̃_1 = φ(k3)v3^T + φ(k4)v4^T   （从 s=0 起）
  rank 2: s̃_2 = φ(k5)v5^T + φ(k6)v6^T   （从 s=0 起）

  rank 2 的入状态 = s̃_0 + s̃_1  （直接求和前序 rank）
  原因：递归纯加性，没有矩阵作用于入状态

    4.2 KDA 为什么不能：$M_t$ 作用于入状态

    对比 KDA 的 Eq.1[F1]：

    $$S_t = M_t S_{t-1} + \beta_t k_t v_t^\top,\qquad M_t := I - \beta_t k_t k_t^\top \mathrm{Diag}(\alpha_t).$$

    右边有一个 token-dependent 矩阵 $M_t$ 作用于入状态 $S_{t-1}$，然后才加写入 $\beta_t k_t v_t^\top$。这就是 delta rule 的"先擦后写"——先用 $M_t$ 擦除/衰减旧状态，再加新内容。KDA 页讲过这个几何，这里只用结论。

    后果：一段 token 对状态的效果依赖进入该段的状态。rank $i+1$ 从 $S=0$ 起算的本地状态 $\tilde S$，和它真正以 $S_T^{[i]}$ 为入状态算出的状态不一样——因为中间每步的 $M_t$ 作用于不同的 $S_{t-1}$。所以不能像 vanilla 线性注意力那样直接把各 rank 的 $\tilde S$ 求和[C4]。K3 报告原文："This direct summation, however, is insufficient for KDA. ... KDA's delta rule applies the token-dependent matrix $M_t$ to the incoming state before adding the current write. Consequently, the effect of a local sequence segment depends on the state entering that segment and cannot be determined from the state computed with S = 0 alone."

    4.3 KCP 的分解：累积转移 $M$ + 从零生成 $\tilde S$

    KCP 的核心是把这个依赖显式分解出来[C4, F2]。考虑进入第 $(i+1)$ 个 context-parallel rank 的入状态 $S_T^{[i]}$，经 rank $i+1$ 内 $t$ 个本地 token 后的状态 $S_t^{[i+1]}$。K3 报告 Eq.17 给出：

    $$\boxed{\,S_t^{[i+1]} = \tilde S_t^{[i+1]} + M_{t\leftarrow 1}^{[i+1]}\, S_T^{[i]},\,}$$

    其中：

    • $M_{t\leftarrow 1}^{[i+1]} := \prod_{r\leftarrow 1}^{t} M_r \in \mathbb{R}^{d_k \times d_k}$ 是 rank $i+1$ 内前 $t$ 个本地 token 的 $M$ 连乘（累积转移）。
    • $\tilde S_t^{[i+1]}$ 是同一个递归从 $S=0$ 起跑出的状态（从零生成）。

    两项的职责完全分开：$\tilde S$ 是"本地 token 自己生成的状态"，与入状态无关；$M_{t\leftarrow 1}$ 是"入状态要经过的累积变换"。关键是两项都可在入状态 $S_T^{[i]}$ 可用前本地算出——$\tilde S$ 从 0 起算，$M_{t\leftarrow 1}$ 是本地 token 的 $M$ 连乘，都不需要入状态[F2]。这就是各 rank 要交换的两个片段。

    把这个分解递推到所有 rank，$t=T_{i+1}$ 时离开 rank $i$ 的状态可以展开成所有前序 rank 的片段组合（Eq.17 的求和形式）：

    $$S_T^{[i]} = \tilde S_T^{[i]} + \sum_{j=1}^{i-1}\left(\prod_{l=j+1}^{i} M_{T\leftarrow 1}^{[l]}\right) \tilde S_T^{[j]}.$$

    每一项都是某个 rank 的本地片段（$\tilde S_T^{[j]}$）经过后续 rank 的累积转移（$M$ 连乘）传播过来。因为这些 rank 级更新满足结合律，入状态可以用 prefix scan（前缀扫描，一种并行算法）从 $S=0$ 起依次重组[C4]。

    4.4 一次 all-gather + prefix scan，通信量固定

    整个 KCP 的流程是[C4]：

    1. 每个 rank 本地算自己的 $(M_{T\leftarrow 1}^{[i]},\, \tilde S_T^{[i]})$ 两个片段（在入状态可用前就能算）。
    2. 一次 all-gather：所有 rank 把自己的两个片段广播给其他所有 rank。交换的是固定大小的状态（$S\in\mathbb{R}^{d_k\times d_v}$ 及同形状的 $M$）。
    3. 每个 rank 用收到的所有片段做 prefix scan：从 $S=0$ 起，按文档顺序依次应用 $S \leftarrow M_{T\leftarrow 1}^{[j]} S + \tilde S_T^{[j]}$，重组出本 rank 的入状态。
    KCP 的数据流（2 个 rank 示意）：

  rank 1 本地算: (M累积_1, S̃_1) --+
                                   |  一次 all-gather
  rank 2 本地算: (M累积_2, S̃_2) --+  交换固定大小的状态片段

  收到后 prefix scan（每个 rank 自己重组入状态）：
    S_T^[0] = 0
    S_T^[1] = S̃_1 + M累积_1 · S_T^[0] = S̃_1
    S_T^[2] = S̃_2 + M累积_2 · S_T^[1]   ← rank 2 的入状态

  通信量 = 固定大小的状态，与序列长度无关

    通信量固定是 KCP 相对 softmax CP 的核心优势。softmax 注意力的 context parallelism（如 Ring Attention）要交换随序列长度增长的 KV block——序列越长，通信越多[C4]。KCP 只 all-gather 固定大小的状态（config.json 中约 32KB[N1]），与序列长度无关，并达成线性计算扩展。

    方案递归形式本地段能否独立确定跨设备通信量
    vanilla 线性注意力 CP$s_i = s_{i-1} + \phi(k_i)v_i^\top$（纯加性）能（直接求和）固定（状态大小）
    KDA KCP$S_t = M_t S_{t-1} + \beta_t k_t v_t^\top$（有 $M_t$）不能（需 $M+\tilde S$ 分解）固定（状态大小）
    softmax CP（Ring Attention）—（KV cache 随长增长）—随序列长度增长

    4.5 手算验证：2 rank × 2 token 的 KDA 递归

    构造示例。取 $d_k=d_v=2$，教学构造 $\alpha=0.5$（标量，$\mathrm{Diag}(\alpha)=0.5I$）、$\beta=1$、单位向量 $k$。于是 $M_t = I - 0.5\,k_t k_t^\top$。序列 4 个 token 分给 2 个 rank，每 rank 2 个：

    • rank 1（token 1,2）：$k_1=(1,0), v_1=(1,2)$；$k_2=(0,1), v_2=(3,4)$。
    • rank 2（token 3,4）：$k_3=(1,0), v_3=(5,6)$；$k_4=(0,1), v_4=(7,8)$。

    对应的 $M$：$M_1=M_3=\begin{pmatrix}0.5&0\\0&1\end{pmatrix}$，$M_2=M_4=\begin{pmatrix}1&0\\0&0.5\end{pmatrix}$。

    顺序计算的 ground truth（从 $S_0=0$ 起一步步算）结果是 $S_4=\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$。下面用 KCP 分解重组，看能否得到同样的值。

    各 rank 本地算两个片段：

    • $M累积_1 = M_2 M_1 = \begin{pmatrix}0.5&0\\0&0.5\end{pmatrix}=0.5I$；$\tilde S_1$ 从 $0$ 起算两步 $=\begin{pmatrix}1&2\\3&4\end{pmatrix}$。
    • $M累积_2 = M_4 M_3 = \begin{pmatrix}0.5&0\\0&0.5\end{pmatrix}=0.5I$；$\tilde S_2$ 从 $0$ 起算两步 $=\begin{pmatrix}5&6\\7&8\end{pmatrix}$。

    一次 all-gather 后，prefix scan 重组入状态：

    • $S_T^{[0]}=0$。
    • $S_T^{[1]}=\tilde S_1 + M累积_1\cdot 0=\begin{pmatrix}1&2\\3&4\end{pmatrix}$。
    • $S_T^{[2]}=\tilde S_2 + M累积_2\cdot S_T^{[1]}=\begin{pmatrix}5&6\\7&8\end{pmatrix}+0.5I\cdot\begin{pmatrix}1&2\\3&4\end{pmatrix}=\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$。

    $S_T^{[2]}=\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$，与顺序计算的 $S_4$ 完全一致。分解成立。

    展开：ground truth 4 步 + KCP 分解 3 步的逐矩阵代入

    顺序计算 ground truth（$S_0=0$）：

    $S_1 = M_1\cdot 0 + k_1 v_1^\top = 0 + \begin{pmatrix}1\\0\end{pmatrix}\begin{pmatrix}1&2\end{pmatrix} = \begin{pmatrix}1&2\\0&0\end{pmatrix}$。

    $S_2 = M_2 S_1 + k_2 v_2^\top = \begin{pmatrix}1&0\\0&0.5\end{pmatrix}\begin{pmatrix}1&2\\0&0\end{pmatrix} + \begin{pmatrix}0&0\\3&4\end{pmatrix} = \begin{pmatrix}1&2\\0&0\end{pmatrix}+\begin{pmatrix}0&0\\3&4\end{pmatrix}=\begin{pmatrix}1&2\\3&4\end{pmatrix}$。

    $S_3 = M_3 S_2 + k_3 v_3^\top = \begin{pmatrix}0.5&0\\0&1\end{pmatrix}\begin{pmatrix}1&2\\3&4\end{pmatrix} + \begin{pmatrix}5&6\\0&0\end{pmatrix} = \begin{pmatrix}0.5&1\\3&4\end{pmatrix}+\begin{pmatrix}5&6\\0&0\end{pmatrix}=\begin{pmatrix}5.5&7\\3&4\end{pmatrix}$。

    $S_4 = M_4 S_3 + k_4 v_4^\top = \begin{pmatrix}1&0\\0&0.5\end{pmatrix}\begin{pmatrix}5.5&7\\3&4\end{pmatrix} + \begin{pmatrix}0&0\\7&8\end{pmatrix} = \begin{pmatrix}5.5&7\\1.5&2\end{pmatrix}+\begin{pmatrix}0&0\\7&8\end{pmatrix}=\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$。

    KCP 分解的本地片段：

    rank 1：$M累积_1=M_2 M_1=\begin{pmatrix}1&0\\0&0.5\end{pmatrix}\begin{pmatrix}0.5&0\\0&1\end{pmatrix}=\begin{pmatrix}0.5&0\\0&0.5\end{pmatrix}=0.5I$。$\tilde S_1$ 从 $0$ 起：第一步 $\tilde S_1^{(1)}=M_1\cdot 0+k_1 v_1^\top=\begin{pmatrix}1&2\\0&0\end{pmatrix}$；第二步 $\tilde S_1^{(2)}=M_2\tilde S_1^{(1)}+k_2 v_2^\top=\begin{pmatrix}1&2\\0&0\end{pmatrix}+\begin{pmatrix}0&0\\3&4\end{pmatrix}=\begin{pmatrix}1&2\\3&4\end{pmatrix}$。故 $\tilde S_1=\begin{pmatrix}1&2\\3&4\end{pmatrix}$（与 $S_2$ 一致，因 $S_0=0$）。

    rank 2：$M累积_2=M_4 M_3=\begin{pmatrix}1&0\\0&0.5\end{pmatrix}\begin{pmatrix}0.5&0\\0&1\end{pmatrix}=\begin{pmatrix}0.5&0\\0&0.5\end{pmatrix}=0.5I$。$\tilde S_2$ 从 $0$ 起：第一步 $\tilde S_2^{(1)}=M_3\cdot 0+k_3 v_3^\top=\begin{pmatrix}5&6\\0&0\end{pmatrix}$；第二步 $\tilde S_2^{(2)}=M_4\tilde S_2^{(1)}+k_4 v_4^\top=\begin{pmatrix}5&6\\0&0\end{pmatrix}+\begin{pmatrix}0&0\\7&8\end{pmatrix}=\begin{pmatrix}5&6\\7&8\end{pmatrix}$。故 $\tilde S_2=\begin{pmatrix}5&6\\7&8\end{pmatrix}$。

    prefix scan 重组：$S_T^{[0]}=0$；$S_T^{[1]}=\tilde S_1+M累积_1\cdot 0=\begin{pmatrix}1&2\\3&4\end{pmatrix}$；$S_T^{[2]}=\tilde S_2+M累积_2\cdot S_T^{[1]}=\begin{pmatrix}5&6\\7&8\end{pmatrix}+0.5I\cdot\begin{pmatrix}1&2\\3&4\end{pmatrix}=\begin{pmatrix}5&6\\7&8\end{pmatrix}+\begin{pmatrix}0.5&1\\1.5&2\end{pmatrix}=\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$。与 $S_4$ 一致，分解成立。

    对照：若误用 vanilla 线性注意力的直接求和（错误做法）：$S_T^{[2]}\stackrel{?}{=}\tilde S_2+\tilde S_1=\begin{pmatrix}5&6\\7&8\end{pmatrix}+\begin{pmatrix}1&2\\3&4\end{pmatrix}=\begin{pmatrix}6&8\\10&12\end{pmatrix}\neq\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$。直接求和会得到错误结果，因为漏掉了 $M累积_2$ 对入状态的衰减作用。这就是"direct summation is insufficient for KDA"的数值体现。

    这个例子把 KCP 的两个关键点都展示了：$\tilde S$ 是本地从零算的状态片段，$M累积$ 是入状态要经过的衰减变换。两者分开计算、一次 all-gather 交换、prefix scan 重组，就能在不串行走完整序列的前提下恢复每段入状态。

    本章讲了 KCP 的 $M+\tilde S$ 分解与固定通信量。但前三章的瓶颈都是利用并行，解码的瓶颈转为管理状态——下一章讲投影输入缓存如何支持投机解码的状态回滚。

    本章问题

    1. vanilla 线性注意力的递归[F3]和 KDA 的递归[F1]在"作用于入状态"上有什么本质区别，这个区别为什么让直接求和对 KDA 失效。

      解答：纯加性 vs $M_t$ 先作用于入状态

      vanilla 线性注意力的因果递归 $s_i = s_{i-1} + \phi(k_i) v_i^\top$ 是纯加性的，右边没有任何矩阵作用于 $s_{i-1}$，因此各 rank 从 $s=0$ 起算的本地状态可直接求和恢复入状态。KDA 的递归右边有 token-dependent 矩阵 $M_t$ 先作用于入状态 $S_{t-1}$ 再加写入，一段 token 对状态的效果依赖进入该段的状态——从 $S=0$ 起算的 $\tilde S$ 与真实入状态下的结果不一样，直接求和会漏掉累积转移的作用。

    2. KCP 分解的两项（$M_{t\leftarrow 1}$ 和 $\tilde S$）各自代表什么，为什么都可在入状态可用前本地算出。

      解答：累积转移与从零生成，均不依赖入状态

      $M_{t\leftarrow 1}^{[i+1]} := \prod_{r\leftarrow 1}^{t} M_r$ 是 rank 内前 $t$ 个本地 token 的 $M$ 连乘，代表入状态要经过的累积变换；$\tilde S_t^{[i+1]}$ 是同一个递归从 $S=0$ 起跑出的状态，代表本地 token 自己生成的内容。前者只需本地 token 的 $M$，后者从零起算，两者都不需要入状态，因此可在入状态 $S_T^{[i]}$ 可用前本地算出。

    3. KCP 通信量为何与序列长度无关，与 softmax CP 对比；在手算例子中误用直接求和会得到什么结果。

      解答：固定大小片段一次 all-gather，直接求和数值错误

      KCP 只在一次 all-gather 中交换固定大小的状态片段（$S\in\mathbb{R}^{d_k\times d_v}$ 及同形状的 $M$，config.json 中约 32KB），与序列长度无关；softmax 注意力的 CP（如 Ring Attention）要交换随序列长度增长的 KV block。手算例子中误用直接求和得 $\tilde S_2+\tilde S_1=\begin{pmatrix}6&8\\10&12\end{pmatrix}$，而正确结果是 $\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$——错误在于漏掉了 $M累积_2$ 对入状态的衰减作用，正确做法多了 prefix scan 中应用累积转移这一步。

    5. KDA 解码——投影输入缓存与状态重建

    前面三章的瓶颈都是"利用并行"。解码的瓶颈不一样：它是管理原地更新的状态。K3 报告 §5.4.2 原文："the primary bottleneck shifts from exploiting parallelism to efficiently managing the evolving recurrent state, which is updated in place at every decoding step."[C5]

    解码每生成一个 token，就原地更新一次状态 $S$。这在普通自回归解码里没问题。但 K3 用 MTP（multi-token prediction）投机解码：一次猜测多个 draft token，然后验证接受或拒绝。最小解释 MTP 的词汇：draft token 是猜测的待验证 token；verify 是检查；accept 是通过验证保留；reject 是未通过丢弃；bonus token 是验证后额外生成的确认 token。

    问题出在拒绝。K3 报告原文："if verification rejects a subset of the drafted tokens, the state has already advanced beyond the last accepted token and cannot be trivially rolled back."[C5] 状态已经按全部 draft token 更新过去了，但部分 draft token 被拒绝——状态停在了一个"不该停"的位置，无法平凡回滚到最后接受 token。

    投机解码的状态回滚问题：

  draft: [t1] [t2] [t3] [t4]      ← 一次猜 4 个 draft token
  状态:  S→a  S→b  S→c  S→d       ← 状态已经按 4 个 token 一路更新到 S_d
  verify:  ✓    ✗    ✓    ?        ← 验证：t2 被拒绝
  需要:   状态回滚到 t1 之后（即 S→a 之后的位置），再继续

  问题: 状态是原地更新的，已经推进到 S_d，没有"回到 S_a"的快照

    5.1 朴素方案与代价

    最直接的回滚办法是为每个 draft 位置存一个状态快照——算完 $S_a$ 存一份，算完 $S_b$ 存一份，依此类推。拒绝时回到对应快照。但这有个致命代价：状态流量被乘上了 draft 长度[C5]。K3 报告原文："Maintaining a state snapshot for each draft position would enable rollback, but would also multiply state traffic — a cost that dominates at the large batch sizes typical of online serving." 在线服务的大 batch 下，这个流量占主导，不可接受。

    5.2 投影输入缓存：更小的载荷

    K3 的关键观察是：任意接受前缀后的状态，由 draft token 的投影输入完全决定，而投影输入比状态小得多[C5]。这里的"投影输入"指 draft token 经过 $W_{q/k/v/\beta/\alpha}$ 投影后的 $q,k,v,\beta,\alpha$——它们是 KDA 前向的全部投影输入（$k,v,\beta,\alpha$ 用于状态更新 Eq.1，$q$ 用于输出计算 $o_t = S_t^\top q_t$）。KDA 更新是确定性的：给定相同输入序列，状态唯一。所以只要缓存了投影输入，就能在任何时候重新跑一遍递归，重建出任意接受前缀的状态。

    方案是[C5]：

    1. 只缓存 draft token 的投影输入（不存状态快照）。投影输入比状态小——状态是 $d_k\times d_v$ 的矩阵，投影输入是几个 $d_k$ 维向量。
    2. 验证后，在片上（on-chip，SM 内）重建接受 token 的状态：用缓存的投影输入重跑 KDA 递归，从最后一个确定状态算到接受前缀的末尾。
    3. 写回已验证 token 和 bonus token 的状态，继续后续解码。
    状态快照（大流量）vs 投影输入缓存（小流量）：

  状态快照方案（朴素，流量大）：
    draft: [t1] [t2] [t3] [t4]
    快照:  S_a   S_b   S_c   S_d    ← 每个 draft 位置存一份状态（d_k×d_v 矩阵）
    流量 = draft 长度 × 状态大小（大 batch 下占主导）

  投影输入缓存（K3 方案，流量小）：
    draft: [t1] [t2] [t3] [t4]
    缓存:  proj proj proj proj      ← 只存投影输入（几个 d_k 维向量）
    拒绝 t2 后: 用 proj 在片上重跑递归，重建 S_a（接受前缀的状态）
    流量 = draft 长度 × 投影输入大小（远小于状态）

    这个方案由 K3 与并发工作 ReplaySSM 独立提出[C5]。"replay"正是这个机制的名字——把接受的 token 的状态"重放"出来。重建在一个融合 kernel里完成，覆盖短卷积、输入归一化、门控、KDA 递归、输出归一化。K3 报告称验证延迟随验证 token 数亚线性增长，且低于状态缓存基线[C5]。

    5.3 一个重要的工程后果：载荷不变

    投影缓存不离开 decode 阶段[C5]。这意味着前缀缓存和 prefill–decode 分离（PD 分离，把 prefill 和 decode 分到不同设备的部署方式）与非投机服务使用相同的载荷——K3 报告原文："Because the projection caches never leave the decode stage, prefix caching and prefill–decode disaggregation operate on the same payload as in non-speculative serving." 投机解码的回滚机制被完全封装在 decode kernel 内部，不污染上层服务架构。

    本章讲了投影输入缓存与片上重建。四套方案至此解完——下一章是来源与范围说明。

    本章问题

    1. 解码的瓶颈和训练/prefill 的瓶颈有何不同，用"利用并行"和"管理状态"回答。

      解答：从利用并行转为管理原地更新的状态

      训练/prefill 的瓶颈是利用并行——串行依赖与 GPU 宽并行的冲突让 SM 空转或填不满。解码的瓶颈是高效管理每步原地更新的递归状态：普通自回归解码没问题，但 MTP 投机解码拒绝部分 draft token 后，状态已越过最后接受 token，无法平凡回滚。

    2. 状态快照方案为什么在大 batch 下不可接受，投影输入缓存为什么可行。

      解答：快照放大状态流量，投影输入小且可重建状态

      为每个 draft 位置存状态快照会把状态流量乘上 draft 长度，这一代价在在线服务的大 batch 下占主导。可行的替代：任意接受前缀后的状态由 draft token 的投影输入完全决定（KDA 更新是确定性的），而投影输入（$q,k,v,\beta,\alpha$ 等几个 $d_k$ 维向量）比 $d_k\times d_v$ 的状态矩阵小得多——只缓存投影输入，验证后在片上重跑递归即可重建接受 token 的状态并写回。

    3. 投影缓存不离开 decode 阶段，对前缀缓存和 PD 分离有什么意义。

      解答：与非投机服务相同载荷，不污染上层架构

      投影缓存不离开 decode 阶段意味着投机解码的回滚机制被完全封装在 decode kernel 内部：前缀缓存和 prefill–decode 分离（PD 分离）与非投机服务使用相同的载荷，上层服务架构不需要为投机解码做任何改动。

FlashKDA serves both training and inference prefill and is auto-dispatched as a backend of flash-linear-attention [141]."
    [C3] 设备内 CP 的段转移可独立于入状态计算、SM 级切序列、无跨设备通信：K3 报告 §5.1.1，原文 "Tensor parallelism partitions heads across devices but never shortens the recurrence... The key observation is that the state transition of each segment can be evaluated independently of the incoming state and composed exactly afterward. An automatic SM-level context-parallel (CP) planner... partitions the sequence across the SMs of a single rank, evaluates the segment transitions in parallel, and merges them to recover each segment's exact initial state. Recall from Eq. 1 that KDA updates its state as $S_t = M_t S_{t-1} + \beta_t k_t v_t^\top$, where $M_t := I - \beta_t k_t k_t^\top \mathrm{Diag}(\alpha_t)$. KDA's delta rule applies the token-dependent matrix $M_t$ to the incoming state before adding the current write. Consequently, the effect of a local sequence segment depends on the state entering that segment..." 与 "we introduce KDA Context Parallelism (KCP), which decomposes the effect of each segment into two locally computable quantities, a cumulative transition acting on the incoming state and a state generated locally from zero" 与 "KCP requires only a fixed-size all-gather for recurrent-state synchronization and achieves linear compute scaling."

This in-place update becomes problematic in MTP-based speculative decoding: if verification rejects a subset of the drafted tokens, the state has already advanced beyond the last accepted token and cannot be trivially rolled back. Maintaining a state snapshot for each draft position would enable rollback, but would also multiply state traffic... The state after any accepted draft prefix, however, is fully determined by the projected inputs of the draft tokens, which are far smaller than the state itself. We therefore cache only these projected inputs, rebuild the states of accepted tokens on-chip, and write back the states of the verified and bonus tokens, a design independently proposed in the concurrent work ReplaySSM [25]." 与 "Because the projection caches never leave the decode stage, prefix caching and prefill–decode disaggregation operate on the same payload as in non-speculative serving."

    构造示例

    KCP 章的 2 rank × 2 token KDA 递归：$d_k=d_v=2$，教学构造 $\alpha=0.5$（标量，$\mathrm{Diag}(\alpha)=0.5I$）、$\beta=1$、单位向量 $k$。rank 1（token 1,2）：$k_1=(1,0),v_1=(1,2)$；$k_2=(0,1),v_2=(3,4)$。rank 2（token 3,4）：$k_3=(1,0),v_3=(5,6)$；$k_4=(0,1),v_4=(7,8)$。构造目的：让"不能直接求和"和"$M+\tilde S$ 分解"在 2×2 矩阵上手算可见，$M累积=0.5I$ 干净。不代表真实 K3 数值（K3 的 $\alpha$ 由 scaled sigmoid 产出、范围 $(e^{-5},1)$、$d_k=128$、96 head）。ground truth $S_4=\begin{pmatrix}5.5&7\\8.5&10\end{pmatrix}$，KCP 分解重组后一致；误用直接求和得 $\begin{pmatrix}6&8\\10&12\end{pmatrix}$（错误）。

    辅助解释与类比边界

    (1) "KDA 串行状态与 GPU 并行偏好冲突"是机制解释，服务"串行状态 vs GPU 并行"章。失效边界：冲突的前提是 KDA 用递归状态（$S_t$ 依赖 $S_{t-1}$）；若用 softmax 的 KV cache（无递归依赖），瓶颈形态完全不同。
    (2) "FlashKDA 重叠两阶段"是工程解释，服务 FlashKDA 章。失效边界：重叠的前提是 chunkwise 形式成立（chunk 内并行、chunk 间递归）且 head 间递归独立；若递归本身不可分块或 head 间有依赖，重叠无从谈起。
    (3) "段转移可独立于入状态计算"是机制解释，服务设备内 CP 与 KCP 章。失效边界：依赖 KDA 状态转移的线性性（$M_t$ 和加性项可分离）；若递归非线性使段转移不可分离，设备内 CP 和 KCP 的分解都不成立。
    (4) "投影输入比状态小"是量级解释，服务 KDA 解码章。失效边界：投影输入是 $q,k,v,\beta,\alpha$ 等几个 $d_k$ 维向量，状态是 $d_k\times d_v$ 矩阵；具体比例依赖模型配置，本页只陈述"小得多"的定性结论，不引入未经证实的精确比例数字。

    简化条件及其限制

    (1) 手算例子参数简化：取 $d_k=d_v=2$、标量 $\alpha$、单位 $k$，让矩阵运算手算可见。可推出：KCP 的 $M+\tilde S$ 分解在数值上成立、直接求和会得到错误结果。不可推出：真实 K3 数值（$d_k=128$、$\alpha$ 由 scaled sigmoid 产出、$k$ 经 L2Norm 单位化但非坐标轴向量）。
    (2) 无伪代码与可运行代码：四套方案均以图示表达流程。可推出：每套方案的数据流与通信模式。不可推出：CUTLASS/分布式框架（flash-linear-attention、NCCL）层面的工程实现。
    (3) CUTLASS/TMA/warp specialization 细节未展开：只点名 FlashKDA 是 CUTLASS-based。可推出：FlashKDA 通过 token-parallel 与 head-parallel 重叠两阶段。不可推出：tile 调度、warp 分工、TMA 异步搬运等 GPU 编程实现细节（GPU 执行模型页已讲 SM/CTA/warp 层面）。
    (4) MTP 投机解码最小解释：只用到 draft/verify/accept/reject/bonus 五个词汇。可推出：拒绝 draft token 时状态需要回滚、投影输入缓存如何支持回滚。不可推出：draft 模型架构、接受策略、bonus 生成的完整算法。
    (5) 无外部性能数字：K3 报告 §5.1/§5.4.2 未给出可定位的加速比/带宽基准表。可推出："substantially outperforms the Triton reference implementation"（C2）与"verification latency grows sub-linearly"（C5）为报告原文定性结论。不可推出：具体加速比或带宽基准数值。

    全文总结：KDA 的串行状态更新与 GPU 并行偏好的冲突，在四个执行 regime 下表现成不同瓶颈——训练/prefill 里 SM 空转（FlashKDA 用 token-parallel 与 head-parallel 重叠解决）、长 prefill 下纯 TP 填不满 SM（设备内 CP 在 SM 级切序列、无跨设备通信）、跨设备时直接求和失效（KCP 的 $M+\tilde S$ 分解让通信量与序列长度无关）、投机解码拒绝 draft token 时状态无法回滚（投影输入缓存 + 片上重建，不污染上层服务架构）。四套方案共同让 KDA 的递归状态在 GPU 和多设备上高效运行。
