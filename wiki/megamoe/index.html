    MegaMoE：把 MoE 一层塞进一个持久 kernel，让通信与计算同时进行

    主要依据：DeepGEMM 官方仓库（GitHub deepseek-ai/DeepGEMM，main 分支 commit 559d79f，2026-07-15）的 README、PR #304（2026-04-17 引入 Mega MoE）、PR #316（2026-04-24 基准数据）与 kernel 源码 sm100_fp8_fp4_mega_moe.cuh 等；机制描述另引第三方论文 X-Stage（arXiv:2607.23264）。来源均存档于本页 research/sources/。

    一块 GPU 在跑 MoE 模型的一层时，token 要发给别的卡上的专家去算，算完还要送回来。传统做法把这件事拆成五个独立 kernel 依次执行：先发数据、等着，再算、等着，最后收回结果、等着。发送和收回的时候，负责计算的单元停着；计算的时候，负责传输的互联线路闲着。Mega MoE 是 DeepSeek 开源在 DeepGEMM 里的 kernel 家族（官方写法 Mega MoE，2026 年 4 月随 PR #304 公开[C1, N6]），它把这五段工作融合成一个占满整块 GPU、从头跑到尾的持久 kernel，让 NVLink 传输与 Tensor Core 计算同时进行——通信量没有减少，但通信造成的空闲被计算填满了。后文约定几个用词：一块 GPU 上参与通信的一个进程称为一个 rank；SM 是 GPU 的计算单元；warp 是 32 线程为一组的执行单位；TMA 是异步批量搬运数据的单元。它们在首次正式使用的章节还有更完整的说明与概念页链接。

    本文按以下问题展开：先看清楚传统执行到底慢在哪（第 1 章），再看融合后的 kernel 如何分工（第 2 章）、支撑跨 rank 读写的地基是什么（第 3 章）、一个 token 在 kernel 里走完整条路的每个站点（第 4 章），最后核对官方基准数字与适用边界（第 5 章）。阅读需要 MoE 路由、专家并行（EP）、SwiGLU 与 GPU 执行模型的背景，相关概念页在首次依赖处给出。

    核心问题

    1. MoE 一层在专家并行下要执行哪五段工作，为什么通信会让计算单元空转？

      解答：五段是 dispatch、Linear-1、SwiGLU、Linear-2、combine，串行执行时通信与计算互相等待

      token 先按路由结果被送往各专家所在的 rank（dispatch），每个专家做两层线性变换夹一个 SwiGLU 激活（Linear-1 把 hidden 维升到中间维的 gate/up 两半，SwiGLU 相乘后减半，Linear-2 投回 hidden 维），最后各专家输出按路由权重加权求和送回源 rank（combine）。传统实现里五段是独立 kernel 串行：dispatch/combine 期间 Tensor Core 没有有效计算，GEMM 期间 NVLink 没有流量，且每段之间数据要落回显存。完整论证见「MoE 一层的五段执行」一章。

    2. Mega MoE 把五段融合成一个持久 kernel 后，靠什么让 NVLink 传输与 Tensor Core 计算同时进行？

      解答：持久 kernel 占满全部 SM，warp 专用化让不同线程组同时推进通信与计算

      kernel 以 grid 恰好等于 SM 数的方式启动并一直运行到整层结束，任务由 kernel 内部调度器分发。block 内的线程分成三组：dispatch 线程组负责跨 rank 的计数、源索引与数据拉取，TMA 生产者 warp 负责加载矩阵分块，MMA warp 发射 Tensor Core 指令，epilogue 线程组做激活、量化与结果写回。通信动作由 dispatch 组与 epilogue 组发起，与 GEMM 计算在不同 warp 上并行推进。完整论证见「一个持久 kernel 里的分工」一章。

    3. 对称内存为什么是单 kernel 跨 rank 读写的前提？它是怎么工作的？

      解答：所有 rank 以相同布局分配缓冲，地址差为固定偏移，一次加法即可定位远端地址

      多进程以相同布局在各自 GPU 上分配缓冲区后，任意 rank 内的地址加上固定偏移就是目标 rank 的对应地址。kernel 侧的 SymBuffer 保存本 rank 基址与全部 rank 的偏移表，map(ptr, dst_rank) = ptr + offsets[dst_rank] 一步完成翻译，线程因此能在 kernel 执行中途直接对远端发起读写。独立通信库由框架在 kernel 之间编排 all-to-all、kernel 本身只见本地指针，不需要这个约束。完整论证见「对称内存」一章。

    4. 一个 token 的数据在融合 kernel 里走完整条路要经过哪些站点？各站点如何衔接？

      解答：元数据先行、数据分块拉取进环形缓冲，两层 GEMM 后按源元数据远程写回，最后归约

      dispatch 线程组先把每专家计数与源索引发往专家所在 rank（元数据小、先行推送），接收侧再按专家分组、轮转选源，用 TMA 把 token 数据按不超过 4096 字节的块拉进本地环形缓冲。调度器把两层 GEMM 切成 task（Linear1/Linear2/共享专家四相），L1 预热后交替发布，环形缓冲的 full/empty 计数器衔接生产与消费。L1 epilogue 在片上完成 SwiGLU 并量化回 FP8，L2 epilogue 按源元数据把 BF16 结果远程写入源 rank 的 combine 缓冲对应槽位；全部写回后源 rank 对 top-k 槽做浮点累加、写出结果。完整论证见「一个 token 的完整旅程」一章。

    5. Mega MoE 实测收益是多少，在什么条件下成立、什么条件下用不了？

      解答：EP8 下相对非重叠基线 1.50–1.96 倍，但仅限 Blackwell（sm100）与 FP8xFP4 等条件

      官方基准在 DeepSeek-V4-Flash 与 V4-Pro 两档规格、8 路专家并行下测得相对非重叠基线（DeepEP 通信 + 分组 GEMM + SwiGLU）加速 1.50–1.96 倍，batch 为每 rank 1 个 token 时收益最大。边界：发布版仅 sm100（Blackwell）实现并依赖 TMEM/tcgen05，发布声明仅支持 FP8xFP4，要求 PyTorch 不低于 2.9 与多进程对称内存，top-k 不超过 32；Hopper 上官方无收益数据（第三方评论称无 TMEM 时不显著）。正确性以与基线逐位一致（无共享专家）验证。完整论证见「收益与边界」一章。

    常见误解

    • 「融合 kernel 把通信消掉了」——通信的数据量一点没少：dispatch 仍要把每 token 的激活送到各专家所在 rank，combine 仍要把结果送回；Mega MoE 消除的是通信造成的空闲时间，方式是让传输与计算同时进行，而不是删除传输本身。
    • 「Mega MoE 是新通信库，用来替代 DeepEP」——它是 DeepGEMM 里的计算 kernel 家族，只是把通信动作融合了进来；DeepEP 是独立通信库，两者层级不同。官方基准的对照基线恰好是用 DeepEP 做通信的非重叠流水线。

    1. MoE 一层的五段执行——通信为什么让 GPU 空转

    MoE 模型把一个大的前馈网络拆成许多小专家，路由网络为每个 token 只选其中几个[C1]。专家数一多，一块 GPU 放不下全部专家权重，于是把不同专家放到不同 GPU 上——这就是专家并行（EP），一块 GPU（一个进程、一个 rank）持有全部专家中的一小部分。路由结果与专家摆放一旦不同 rank，token 就必须在 rank 之间旅行：这是 MoE 与稠密模型推理最本质的执行差异。专家切分与共享专家的背景见DeepSeekMoE，EP 下的服务形态见MoE serving 基础。

    先约定一个小到可以手算的贯穿示例，后文各章反复使用、逐层加深。

    1.1 五段各自做什么

    一个 token 穿过 EP 下的 MoE 层，要经过五段执行[C1]：

    用公式写一层的输出。设 token 的输入为 $x\in\mathbb{R}^{h}$（$h$ 为 hidden 维），路由选中专家集合为 $\mathcal{S}$（$|\mathcal{S}|=k$），每个专家 $e\in\mathcal{S}$ 的路由权重为 $g_{e}$、两层变换为 $W_1^{(e)}$、$W_2^{(e)}$，则

    $$y=\sum_{e\in\mathcal{S}} g_{e}\cdot W_2^{(e)}\,\mathrm{SwiGLU}\!\left(W_1^{(e)}x\right),\qquad \mathrm{SwiGLU}(u,v)=\mathrm{silu}(u)\odot v.$$

    其中 $W_1^{(e)}\in\mathbb{R}^{2d\times h}$ 的两半分别是 gate 与 up（$d$ 为中间维），$\mathrm{silu}(u)=u\cdot\sigma(u)$，$\odot$ 为逐元素乘；combine 段完成的就是这个按 $g_{e}$ 的加权求和[F1]。SwiGLU 的完整讲解见SwiGLU，这里只需要它的形状事实：输出宽度是输入 gate/up 拼接宽度的一半。

    在贯穿示例里走一遍 $t_0$ 的路径：$t_0$ 在 rank0，被路由到 $E_0$（rank0）和 $E_3$（rank1）。dispatch 段，$t_0$ 的一份副本留在 rank0 给 $E_0$，另一份发往 rank1 给 $E_3$。计算段，rank0 上 $E_0$ 对 $t_0$ 做 Linear-1 → SwiGLU → Linear-2，同时 rank1 上 $E_3$ 也对 $t_0$ 的副本做同样三段。combine 段，$E_3$ 的输出要送回 rank0，与 $E_0$ 的输出按各自路由权重相加，得到 $t_0$ 的层输出。注意两件事：$t_0$ 一共被两个专家处理，dispatch 要发出 $k=2$ 份副本；其中一份根本不出本 rank（$E_0$ 也在 rank0），另一份要跨 rank 往返。四个 token 的全部 8 个专家-路由对里，6 个（$t_0$→$E_3$、$t_1$→$E_2$ 与 $t_1$→$E_3$、$t_2$→$E_1$、$t_3$→$E_0$ 与 $t_3$→$E_1$）需要跨 rank 传输，只有 $t_0$→$E_0$ 与 $t_2$→$E_2$ 留在本地——四分之三的专家计算要等远端数据。

    dispatch 与 combine 这两个方向合起来就是 all-to-all 通信的形态——每个 rank 都既向别的 rank 发数据、也从别的 rank 收数据，这种集合通信的背景见GPU 通信。DeepSeek 的专用通信库 DeepEP 提供的就是这两段的高吞吐/低延迟实现（其概念页见DeepEP）；本文只需要 dispatch/combine 的方向语义。

    1.2 串行执行的两种空闲

    传统实现里，五段由独立 kernel 依次完成[C1]：框架先调用通信库的 dispatch kernel，等它返回；再调用分组 GEMM kernel 算 Linear-1，等它返回；然后 SwiGLU kernel、第二个分组 GEMM kernel，最后 combine kernel。串行带来两种浪费：dispatch/combine 运行时，SM 上没有有效计算，Tensor Core 空转；GEMM 运行时，互联线路上没有数据流，NVLink 空转。每段结束到下一段开始之间，中间结果还要写回显存再读出。SM、kernel 启动与占用的背景见GPU 执行模型。

    通信本身也不是小数目。用基准里的 DeepSeek-V4-Pro 规格（hidden $h=7168$、top-$k=6$）[N3]算一笔账：激活按 FP8 存储时每元素 1 字节，一个 token 的 dispatch 发送量约为 $k\times h\times 1\,\mathrm{B}=6\times 7168=43008\,\mathrm{B}\approx 43\,\mathrm{KB}$；combine 回传的是 BF16 结果，约 $86\,\mathrm{KB}$。每 rank 512 个 token 时，仅 dispatch 方向就要发出约 $22\,\mathrm{MB}$（$43008\times 512=22{,}020{,}096$ 字节，十进制口径）——这还是每层、每 rank 反复发生的量。这笔账只算数据本体，是按公式 $k\times h\times b_{\mathrm{act}}$ 直接推出的量级估算[F3]，不是实测流量；官方基准表中互联带宽一列（batch 512 时 266/182 GB/s[N2, N4]）就是这些流量的实测体现。

    既然通信量删不掉，唯一出路就是让它与计算同时发生。这要求"发数据的人"和"算数的人"住在同一个 kernel 里——这正是 Mega MoE 的做法，下一章看它如何组织。

    本章问题

    1. 专家并行下，一个 token 穿过 MoE 层要经过哪五段？每段数据在哪里？

      解答：dispatch、Linear-1、SwiGLU、Linear-2、combine；数据在源 rank、专家 rank 与源 rank 之间往返

      五段依次是：dispatch（token 副本按路由从源 rank 发往各专家所在 rank）、Linear-1（每个专家把 token 从 $h$ 维投影到 $2d$ 维的 gate/up 拼接）、SwiGLU（silu(gate) 乘 up，宽度减半为 $d$ 维）、Linear-2（投回 $h$ 维）、combine（各专家输出按路由权重 $g_{e}$ 加权求和送回源 rank）。以贯穿示例的 $t_0$ 为例：数据从 rank0 出发，一份留在 rank0 给 $E_0$、一份到 rank1 给 $E_3$，两边各自完成三段计算后，$E_3$ 的结果回传 rank0 与 $E_0$ 的结果相加。计算段在专家所在的 rank 上本地完成，通信段只在 dispatch 前向与 combine 回向发生。成立条件：专家分布在多个 rank 上（EP）；若全部专家在同一 rank，退化为纯本地计算。

    2. 为什么说传统实现里"通信时计算空闲、计算时互联空闲"？

      解答：五段由独立 kernel 串行执行，任一时刻只有通信或只有计算在推进

      传统实现按 dispatch kernel → 分组 GEMM → SwiGLU kernel → 分组 GEMM → combine kernel 的顺序串行调用，每段都要等前一段完全结束。dispatch/combine 运行期间 SM 没有可做的计算，Tensor Core 空转；三段计算运行期间互联上没有数据流，NVLink 空闲。此外 kernel 之间中间结果要落回显存再读出，带来额外访存。在 V4-Pro 规格、每 rank 512 token 的量级下，仅 dispatch 方向每 rank 每层就要发出约 22 MB（$6\times 7168\times 512\approx 2.2\times 10^{7}$ 字节，FP8、top-$k$ 6、hidden 7168 的构造估算），这些传输在串行时间里全部是纯开销。要消除空闲，需要通信与计算同时推进——这正是 Mega MoE 改变的执行方式。

    2. 一个持久 kernel 里的分工——融合与重叠如何成立

    官方对 Mega MoE 的一句话定义拆开是两件事[C1]：融合（fuse）——dispatch、Linear-1、SwiGLU、Linear-2、combine 五段不再各自启动 kernel，中间状态不回到框架手里；重叠（overlap）——通信动作与 Tensor Core 计算同时推进。融合是重叠的前提：只有当发数据的人和算数的人住在同一个 kernel 里，一方的等待才能被另一方的工作填满。这也回应了开头的误解澄清——通信量没有变少，变的是它发生的时间安排。

    2.1 持久 kernel：一个启动，跑到整层结束

    Mega MoE 的启动形态是持久 kernel（persistent kernel）：grid 维度恰好等于 SM 数量，每 SM 一个 block，kernel 从 MoE 层开始一直运行到层内全部工作完成才退出[C8]。这和常规 kernel 形成对照——常规做法是把工作切成许多小块、每块启动一次 kernel，由 GPU 的硬件调度器把 block 摊到 SM 上。持久形态的好处是：全部工作在 kernel 内部自组织，可以按数据就绪情况安排顺序，通信与计算的交错不再受 kernel 边界约束；代价则是 kernel 必须自己完成调度——谁先算哪块、谁等谁，都由 kernel 内的调度器决定（见第 4 章）。

    启动时每个 block 里居住着三组线程，共 384–512 线程：dispatch 线程组 128 线程、非 epilogue 组 128 线程、epilogue 组 128–256 线程（按负载分档选择）[C9]。三组线程之间还有一次寄存器再分配：dispatch 组与非 epilogue 组主动释放寄存器，epilogue 组领取更多（最多每线程 208 个），因为 SwiGLU、量化与写回的中间值都在寄存器里[C30]。

    分工表里所有跨 rank 的动作——写计数、写源索引、拉取数据、远程写回——都要落到一个共同前提上：kernel 里的普通线程必须能直接定位远端 rank 的内存。这个前提由对称内存提供，下一章专门讲它。

    本章问题

    1. "融合成一个 kernel"和"重叠通信与计算"分别指什么？持久 kernel 是什么形态？

      解答：融合指五段不再各自启动 kernel，重叠指通信与计算同时推进；持久 kernel 是 grid 等于 SM 数、跑到整层结束的单次启动

      融合是结构变化：dispatch、Linear-1、SwiGLU、Linear-2、combine 五段在同一个 kernel 里完成，中间结果在片上与环形缓冲之间流转，不回到框架；重叠是时间安排变化：通信动作（远端读写、数据拉取）由 dispatch 线程组与 epilogue 线程组发起，与 MMA warp 的 Tensor Core 计算在不同 warp 上同时推进。持久 kernel 指 grid 维度恰好等于 SM 数量、每 SM 一个 block、kernel 从层开始运行到全部工作完成才退出的启动形态（源码中以 __launch_bounds__(kNumThreads, 1) 与 grid=num_sms 启动）。任务分配由 kernel 内部调度器完成而非硬件调度器。成立条件：单层的工作量足以占满全部 SM；收益来自消除 kernel 间的等待与通信空闲，不是来自减少任何一方的总量。

    2. kernel 内部有哪些角色，各自负责什么？

      解答：三组线程六个角色——dispatch 组管通信输入侧，TMA A/B、MMA、调度 warp 管计算，epilogue 组管激活、量化与通信输出侧

      一个 block 内三组线程：dispatch 线程组（4 warp、128 线程）读本地路由、统计每专家 token 数、把计数与源索引写往专家所在 rank、按块拉取 token 数据；非 epilogue 组（4 warp、128 线程）中 TMA A warp 加载激活分块（含缩放因子）、TMA B warp 加载权重分块、MMA warp 发射 Tensor Core 指令（仅 leader CTA）、调度 warp 发布计算任务；epilogue 线程组（4–8 warp、128–256 线程）做 SwiGLU、FP8 重量化、远程写回与 combine 归约。三组之间有一次寄存器再分配（epilogue 组最多每线程 208 个寄存器）。计算以 2-SM cluster 配对执行，累加器在 TMEM。通信分散在 dispatch 组（输入侧）与 epilogue 组（输出侧），因此与计算天然并行。

    3. 对称内存——kernel 内跨 rank 读写的地基

    分工表里的每个跨 rank 动作，最终都变成一次普通的内存读写——只是地址在别的 rank 上。让这件事成为可能的机制是对称内存：多进程在各自 GPU 上以完全相同的布局分配各自的缓冲区，于是同一逻辑位置在两个 rank 的地址差是一个固定常数。Mega MoE 要求多进程启动与对称内存，PyTorch 版本不低于 2.9[C1, C3]。

    3.1 布局约定与地址翻译

    kernel 侧的视图叫 SymBuffer：保存本 rank 缓冲区基址，以及一张覆盖全部 rank 的偏移表（最多 72 个 rank）[C10]。把本 rank 地址 $a$ 翻译成目标 rank $r_1$ 的等价地址只需一次加法：

    $$\mathrm{map}(a,\,r_1) = a + \Delta_{r_1},\qquad \Delta_{r_1} = B_{r_1} - B_{r_0},$$

    其中 $B_{r_0}$、$B_{r_1}$ 分别是两个 rank 缓冲区的基址[C10]。源码实现就是一张偏移数组加一次指针加法，没有任何运行时查找。

    构造示例（沿用贯穿配置）。rank0 与 rank1 各分配一块同布局缓冲：rank0 基址 $B_0$、rank1 基址 $B_1$，$\Delta = B_1 - B_0$。看 dispatch 拉取的一个瞬间：rank0 上的专家 $E_1$ 需要 $t_2$，而 $t_2$ 存放在 rank1 的 input 缓冲里、恰好与 rank0 本地 0 号槽（存放 $t_0$ 的那个位置）是同一逻辑槽位。rank0 的线程手里有这个槽位在本地视角下的地址 $a$，访问 $a + \Delta$ 就直接落到 rank1 上存放 $t_2$ 的槽——一次加法完成跨 rank 定位。

    3.2 为什么融合 kernel 必须要它

    独立通信库不需要这个约束：框架在 kernel 之间调用它的 dispatch/combine，每个通信 kernel 启动时框架已经把源和目的缓冲的指针都准备好了，kernel 只管搬数据。融合 kernel 相反——它在执行计算的中途就要发起跨 rank 读写，而 kernel 参数里不可能为每次读写都预先传好远端指针；唯一可行的办法是让每个线程都能自己算出远端地址，这正是"同布局 + 固定偏移"提供的能力[C10]。

    跨 rank 读写还带来顺序问题：dispatch 侧必须确认所有 rank 的计数都已写好，才能开始拉数据；combine 侧必须确认所有结果都已写回，才能开始归约。这些确认由 kernel 内的 NVLink barrier 完成——本质上是一组放在对称内存里的跨 rank 计数信号，配合 grid 内同步构成屏障；kernel 在拉取前、归约前、收尾清理后各用它同步一次[C29]。

    使用形态上，这一切被封装成三步：先为进程组分配对称缓冲，再把权重变换到所需布局，然后拷入输入、调用 kernel[C22]。多进程一侧，官方测试默认为每个 rank 启动一个进程（8 进程）[C23]。完整调用序列来自官方 README：

    本章问题

    1. 对称内存的布局约定是什么？地址是怎么"翻译"到远端的？

      解答：所有 rank 以相同布局分配缓冲，SymBuffer 存基址与偏移表，map 就是一次加法

      约定：参与通信的每个进程在各自 GPU 上按完全相同的布局分配缓冲区（PyTorch 2.9 起的对称内存机制，多进程启动）。kernel 侧的 SymBuffer 结构保存本 rank 基址 $B_{r_0}$ 与一张全部 rank 的偏移表；对任意本 rank 地址 $a$ 与目标 rank $r_1$，$\mathrm{map}(a, r_1) = a + \Delta_{r_1}$，其中 $\Delta_{r_1} = B_{r_1} - B_{r_0}$ 为固定常数。偏移表最多覆盖 72 个 rank，rank 数直接内嵌在缓冲地址表的长度里。实现上没有查找表或运行时服务，就是数组索引加指针加法。成立条件：所有 rank 的缓冲布局严格一致——这正是官方 API 要求先统一分配对称缓冲、再把输入拷进去的原因。

    2. 为什么融合 kernel 必须要对称内存，而独立通信库不需要？

      解答：融合 kernel 在执行中途发起远端读写，每个线程必须能自己算出远端地址

      独立通信库的 dispatch/combine 由框架在 kernel 之间调用，每次通信 kernel 启动时框架已经传好源与目的缓冲的指针，kernel 本身只见本地指针，因此不需要跨 rank 的地址约定。融合 kernel 把通信动作散布在计算过程中：dispatch 线程组要写远端计数、读远端 token；epilogue 线程组要把结果写到远端 combine 缓冲——这些读写发生在 kernel 执行中途，不可能由参数表预先提供全部远端指针，唯一可行方案是让每个线程按"同布局 + 固定偏移"自行换算地址。此外 kernel 内的跨 rank 时序（拉取前确认计数就绪、归约前确认写回完成）由 NVLink barrier——放在对称内存里的跨 rank 计数信号——完成，共在拉取前、归约前、清理后三处使用。

    4. 一个 token 的完整旅程——拉取、两层 GEMM、远程写回与归约

    本章把第 2 章的角色和第 3 章的地址翻译拼成一条完整数据流。先声明精度方案：路由专家的激活是 FP8 E4M3、权重是 FP4 E2M1（缩放因子粒度 32、格式 UE8M0），共享专家权重是 FP8，combine 回传与最终输出是 BF16[C7]。格式本身见FP8 块量化与MXFP4 量化，本章只需要"激活 1 字节、权重半字节、输出 2 字节"这个事实。

    4.1 dispatch 侧：元数据先行，数据分块拉取

    dispatch 线程组的工作分三步[C11]。第一步，每个 rank 读自己 token 的路由结果，统计每个专家分到多少 token，并通过 NVLink 把计数原子累加到专家所属 rank 的 workspace 里。第二步，把每个"token-专家"对的源索引（哪个 rank 的哪个 token 的第几个 top-k 槽）也写往专家所在 rank。这两步传的元数据非常小——每专家一个 8 字节计数、每个 token-专家对一个 4 字节源索引——先于大数据出发。第三步，经 NVLink barrier 确认所有 rank 的元数据就位后，接收侧开始拉数据：按专家分组遍历本 rank 的专家，对每个槽位用轮转策略（按各源 rank 的计数逐轮取最小值交错选取）决定从哪个源 rank 拉，然后用 TMA 把 token 数据从远端对称缓冲搬进本地的 L1 环形缓冲——一个 token 的 hidden 维被切成若干块，每块不超过 4096 字节[C12]。

    为什么元数据用推送、数据用拉取？元数据小、且发送方天然知道全部内容，直接写过去最快；数据大，而"什么时候有空闲缓冲来接"只有接收侧知道——接收侧按自己的消费节奏分块拉取，正好把传输塞进计算的空隙里。

    注意方向的不对称：dispatch 侧是"元数据推送 + 数据拉取"（接收侧主动来拉），combine 侧是"远程写入"（专家侧把结果直接 push 到源 rank 的槽位）。两个方向并不对称，把两者都理解成"把数据推过去"会错判缓冲压力的承担方——dispatch 的接收节奏由本 rank 控制，combine 的写入节奏由对端控制[C11, C15]。

    在贯穿示例里代入：rank1 的 dispatch 线程组统计后发现，本 rank 的 $E_2$ 要处理 $t_1$（在 rank0）和 $t_2$（本地），$E_3$ 要处理 $t_0$、$t_1$（都在 rank0）。前两步它把"来自 rank0 的 token 计数"写进自己 workspace 的同时，rank0 也把"我贡献了哪些 token-专家对"的源索引写了过来；第三步 rank1 从 rank0 的 input 缓冲里把 $t_0$、$t_1$ 的数据拉进自己的 L1 缓冲，按 $E_2$、$E_3$ 分组摆放——$t_2$ 本来就在本地，直接归组。

    4.2 两层 GEMM：task 调度与环形缓冲

    拉进来的数据由调度器安排计算。调度单元叫 task：一个 task 说明"哪个专家的第几个 M 块（行块）、在第几个 N 簇（列块）上、处于哪个相位"——相位有四个值：Linear1、Linear2、SharedLinear1、SharedLinear2[C18]。调度 warp 先发布若干批 Linear-1 任务作为预热（保证后续 Linear-2 依赖的数据已经开动，避免死锁），之后 L1 与 L2 任务交替发布；每个 2-SM cluster 的 leader CTA 上运行一个调度 warp，通过 workspace 里的原子计数器动态认领 task 并发布给 cluster 内的两个 CTA，快的 cluster 多干活[C18]。共享专家的任务不依赖 dispatch，可以在等路由统计的同时先行[C17]。

    数据缓冲是环形的：L1/L2 的输入输出都在一个固定容量的缓冲里循环复用，每块配一对 full/empty 计数器——生产者写完加 full，消费者用完加 empty，下一轮使用者自旋等待计数到位[C19]。一个值得注意的省内存设计：L1 的输出缓冲和 L2 的输入缓冲是同一块内存——SwiGLU 把宽度从 $2d$ 减半到 $d$，正好原地容纳[C13]。

    tile 大小不是拍脑袋定的。配置启发式按"每专家期望 token 数"分档选择 block_m：

    $$N_{\mathrm{exp}} = \frac{n_{\mathrm{tokens}}\times n_{\mathrm{ranks}}\times k}{E},$$

    其中 $n_{\mathrm{tokens}}$ 是本 rank 的 token 数、$E$ 是全局专家数[F2]。代入官方基准的 V4-Pro 规格手算：

    场景（V4-Pro：$E=384$，$k=6$，EP8）计算$N_{\mathrm{exp}}$落入档位与 block_m
    batch 512 / rank$512\times 8\times 6/384$$64$大批解码档，block_m = 96
    batch 8192 / rank$8192\times 8\times 6/384$$1024$prefill / 大 EP 档，block_m = 192
    batch 1 / rank$1\times 8\times 6/384$$0.125$RL 长尾档，block_m = 16

    batch 越小、每专家的 token 越少，tile 就切得越小——batch 为 1 时一个专家平均连一个 token 都摊不到，小 tile 才不至于浪费算力，这正是延迟敏感场景（如强化学习采样）的形态[C24]。

    4.3 epilogue：SwiGLU 重量化、远程写回与归约

    GEMM 的两端各有一段收尾工作，都由 epilogue 线程组完成。L1 相位：从 TMEM 读出 Linear-1 输出的 gate 与 up 两半，gate 只按上限截断、up 上下限都截断（防止激活爆炸），算 $\mathrm{silu}(\mathrm{gate})\times\mathrm{up}$，乘上该 token-专家对的路由权重 $g_{e}$，统计绝对值最大值后量化回 FP8 E4M3（缩放因子 UE8M0），写进 L2 的输入缓冲[C14]。这里出现了一个容易忽视的事实：F1 公式里 combine 段的加权求和，权重 $g_{e}$ 的乘法其实在这里就完成了——写回源 rank 的是已经乘过权重的专家输出，最后的归约是纯加法[F1]。

    L2 相位：结果从 TMEM 读出转成 BF16 后，每个 token 行查一下 dispatch 阶段记录的源元数据——它来自哪个 rank、是哪个 token 的第几个 top-k 槽——然后通过对称地址直接远程写入源 rank 的 combine 缓冲对应槽位[C15]。全部写回经 NVLink barrier 确认后，combine 阶段开始：源 rank 的 epilogue 线程按 token 遍历自己的 $k$ 个槽（有共享专家时再加第 $k+1$ 个槽，共享专家结果不经 dispatch、本地算完直接入槽），在浮点寄存器里累加，转 BF16 写出 $y$[C16, C17]。

    补充：X-Stage 论文对调度的再分析与"expert wave"术语

    第三方论文 X-Stage（arXiv:2607.23264）分析 Mega MoE 时把"本地专家按组分批执行"的组织方式称为 expert wave（专家波）：一个波先做它的 Linear-1，再做激活与 Linear-2，然后进入下一波；不同波的 Linear-1 之间没有神经网络依赖，理论上前一波的远程写回没完成时，后一波的 Linear-1 就可以开始[C20, C25]。需要说明：官方源码里没有"expert wave"这个词，调度单元是 task（四相 BlockPhase）与 L1 预热/交替发布，"wave"是论文对这种分批结构的描述用语[C20]。该论文还发现：把发布的时间线当作"Combine 是一段完整通信"会低估加速（保守估计上限约 1.5 倍，低于实测 1.56 倍），因为发出远程写后发送方可以继续干活；据此它提出跨波交错 Linear-1 与 Linear-2 的改法，在自己的 84 组配置上比原调度再快 1.18 倍（几何均值）、最高 1.62 倍[C25]——这是论文实验修改版的结果，未进入 DeepGEMM 主线。

    1. dispatch 侧怎么把 token 集合到专家手里？

      解答：元数据（计数、源索引）先推送，数据由接收侧按专家分组、轮转选源、分块拉取

      三步：① 每个 rank 读本地路由并统计每专家 token 数，通过 NVLink 把计数原子累加到专家所属 rank 的 workspace；② 把每个 (token, topk) 的源索引写往专家所在 rank；③ 经 NVLink barrier 确认后，接收侧按本 rank 专家分组、用轮转策略（按各源 rank 计数逐轮取最小值交错）为每个槽位选定源 rank，用 TMA 把 token 数据按不超过 4096 字节的块从远端对称缓冲拉进本地 L1 环形缓冲。元数据小且发送方全知，直接推送；数据大且接收时机只有接收侧知道，由接收侧按消费节奏拉取。在贯穿示例中，rank1 为 $E_2$ 从 rank0 拉 $t_1$、为 $E_3$ 拉 $t_0$ 与 $t_1$，本地 token $t_2$ 直接归组。

    2. 两层 GEMM 的任务怎么组织？环形缓冲怎么衔接生产与消费？

      解答：task 为单元、四相 BlockPhase、L1 预热后交替发布、原子认领；环形缓冲配 full/empty 计数器

      调度单元是 task（相位取值 $\{$Linear1、Linear2、SharedLinear1、SharedLinear2$\}$ 四种，加上专家号、M 块、N 簇）。调度 warp 先发布若干 L1 预热波避免依赖死锁，之后 L1/L2 交替发布；每个 cluster 的 leader CTA 上的调度 warp 通过原子计数器认领任务并发布给 cluster 内两个 CTA，负载不均时快的 cluster 多做。数据缓冲按固定容量循环复用，每块配 full/empty 计数器，生产者写完加 full、消费者用完加 empty、下轮使用者自旋等到位。L1 输出与 L2 输入共用同一缓冲（SwiGLU 后宽度减半，原地容纳）。共享专家任务不依赖 dispatch，可先行。tile 大小按每专家期望 token 数 $N_{\mathrm{exp}} = n_{\mathrm{tokens}}\times n_{\mathrm{ranks}}\times k / E$ 分六档选 block_m（16–192）：V4-Pro batch 512/rank 时 $N_{\mathrm{exp}}=64$，选 block_m=96。

    3. L1 epilogue 做了什么？L2 结果怎么回到源 rank、最后怎么归约成 y？

      解答：SwiGLU 后乘路由权重并量化 FP8；L2 结果查源元数据远程写回；源 rank 对 k 个槽浮点累加

      L1 epilogue 从 TMEM 读出 Linear-1 输出的 gate 与 up 两半，按界限截断（gate 上限、up 上下限）后算 $\mathrm{silu}(\mathrm{gate})\times\mathrm{up}$，乘上路由权重 $g_e$，按绝对值最大值量化回 FP8 E4M3（SF 为 UE8M0），写入 L2 输入缓冲——注意 F1 公式里 combine 的加权，乘法在这一步就完成了。L2 epilogue 把结果转 BF16，逐 token 行查 dispatch 阶段记录的源元数据（源 rank、token 号、top-k 槽位），通过对称地址直接远程写入源 rank 的 combine 缓冲。全部写回经 NVLink barrier 确认后，源 rank 遍历每个 token 的 $k$ 个槽（共享专家占第 $k+1$ 槽），浮点累加、转 BF16 写出 $y$。贯穿示例里 $E_3$（rank1）对 $t_0$ 的已加权结果写进 rank0 的 $t_0$ 槽位之一，与本地 $E_0$ 的结果相加即为 $t_0$ 的输出。

    5. 收益与边界——基准数字、正确性与适用条件

    机制说完，回到最实际的问题：值多少、什么时候用得上。DeepGEMM 把自己定位为统一的高性能 Tensor Core kernel 库，Mega MoE 是其中"带通信重叠的融合 MoE"组件[C2]；它由 DeepSeek 的八位贡献者开发，官方声明仍在持续优化中，且发布与内部模型无关[C27, C28]。

    5.1 官方基准：测了什么、快了多少

    官方基准（PR #316）在 DeepSeek-V4 两档规格上测试：V4-Flash（256 专家、top-$k$ 6、hidden 4096、中间维 2048）与 V4-Pro（384 专家、top-$k$ 6、hidden 7168、中间维 3072），均为 8 路专家并行（EP8）、单节点，batch size 指每 rank 的 token 数（官方在评论中确认口径，EP8 下 512/rank 即全节点 4096），全部数值为 8 个 rank 的平均[N1, N3, N5]。加速的对照对象（"legacy"）是 DeepEP dispatch/combine + DeepGEMM 分组 GEMM + TileLang SwiGLU 的非重叠流水线——即第 1 章描述的传统执行方式的具体实现[C21]。

    5.2 正确性验证

    融合 kernel 的输出靠与基线逐字对比验证：无共享专家时，融合实现与 DeepEP 基线的输出逐位一致（torch.equal）；有共享专家时数值差异小于 $10^{-8}$；每专家的接收统计同样逐位一致[C21]。官方测试还支持随机化 token 数与路由掩码，在多组随机输入下重复这一对比[N7]。

    5.3 适用边界

    把这些条件列全，任何一条不满足都要重新评估：

    • 硬件：发布版仅 sm100（Blackwell）实现——代码以 __CUDA_ARCH__ >= 1000 守卫，其他架构上直接断言不支持；矩阵计算依赖 TMEM 与 2-SM cluster 的 tcgen05 指令[C5, C6]。Hopper（sm90）上官方没有收益数据；第三方评论（非官方声明）称没有 TMEM 时性能提升不显著，Hopper 上可用"FP4 EP v2 + FP8 DeepGEMM + PDL（Programmatic Dependent Launch，程序化依赖启动——让后一个 kernel 在前一个结束前就开始的调度机制）"的组合替代，sm90 移植在推进中[N9]。
    • 精度：PR #304 发布时仅支持 FP8xFP4 组合（激活 FP8 E4M3、权重 FP4 E2M1）[C3]；当前主线的源码与测试中已出现 bf16 变体（sm100_bf16_mega_moe、--mma-type bf16xbf16）[C4]，属于后续加入的路径。
    • 软件与形态：要求 PyTorch 不低于 2.9、多进程启动与对称内存；FP8 路径要求 hidden 与中间维被 128 整除[C1, C3, N7]。测试覆盖的默认配置是 384 专家、top-$k$ 6、hidden 7168、1 个共享专家、每 rank 最多 8192 token[N7]。
    • 结构约束：top-$k$ 不超过 32；有共享专家时 top-$k$ 加共享专家数不超过 32（combine 归约由单个 warp 逐槽遍历的约束）；专家数必须被 rank 数整除[N8]。
    • 拓扑：官方基准为单节点 EP8；跨机（RDMA 域）行为没有公布数据。SymBuffer 偏移表最多 72 个 rank[N11]。
    • 成熟度：官方声明仍在开发与优化中（"still under development and optimizations"）[C27]。调试上提供环境变量 DG_COMM_KERNEL_DEBUG，每次调用前清零对称缓冲以定位问题[C26]。

    「融合 kernel 在任何 GPU 上都更快」不成立。加速的成立条件是：Blackwell 硬件（TMEM/tcgen05）、匹配的精度组合（FP8xFP4，或后续的 bf16 路径）、多进程对称内存环境、单节点 NVLink 域。条件不满足时（如 Hopper），收益没有官方数据支撑，替代方案是传统流水线或官方后续的移植版本。

    回看全文的五问：MoE 一层的五段执行与通信空转是问题（第 1 章）；融合进一个持久 kernel、warp 专用化分工是方案（第 2 章）；对称内存的地址平移是地基（第 3 章）；元数据先行、分块拉取、交替调度、远程写回与归约是数据流（第 4 章）；1.50–1.96 倍的加速与一列硬边界是它今天的样子（本章）。Mega MoE 的价值不在发明新的通信算法，而在于把已有的一段执行重新安排了时间与空间——让通信与计算在同一个 kernel 里互为对方的填充物。

    本章问题

    1. 官方基准测了什么、加速多少？对照的基线是什么？

      解答：V4-Flash 与 V4-Pro 规格、EP8、四档 batch，加速 1.50–1.96 倍；基线是 DeepEP+分组 GEMM+SwiGLU 非重叠流水线

      两组配置：V4-Flash（256 专家、top-$k$ 6、hidden 4096、中间维 2048）与 V4-Pro（384 专家、top-$k$ 6、hidden 7168、中间维 3072），EP8 单节点，batch 为每 rank token 数（1/512/8192/32768），数值为 8 rank 平均。加速相对"legacy"基线——DeepEP dispatch/combine + DeepGEMM 分组 GEMM + TileLang SwiGLU 的非重叠流水线。结果：V4-Flash 加速 1.96/1.73/1.56/1.62 倍，V4-Pro 加速 1.61/1.54/1.50/1.54 倍（按 batch 从小到大）。规律：batch=1 时收益最大（通信占比最高），大 batch 收敛到约 1.5 倍。正确性以与基线逐位一致（无共享专家）或差异小于 $10^{-8}$（有共享专家）验证。

    2. 哪些条件下 Mega MoE 用不了或收益存疑？

      解答：非 Blackwell 硬件、精度不符、缺对称内存环境、top-k 超限、跨机场景，均不适用或无数据

      硬件上仅 sm100（Blackwell）实现，代码以 __CUDA_ARCH__ >= 1000 守卫并依赖 TMEM/tcgen05；Hopper 无官方收益数据，第三方评论称无 TMEM 时不显著（可改用 FP4 EP v2 + FP8 DeepGEMM + PDL）。精度上发布版仅 FP8xFP4（后续主线加入 bf16 变体）。软件上要求 PyTorch 2.9 以上、多进程对称内存，FP8 路径要求 hidden 与中间维被 128 整除。结构上 top-$k\le 32$、top-$k$ 加共享专家数 $\le 32$、专家数被 rank 数整除。拓扑上官方仅发布单节点 EP8 数据，跨机行为未公布。成熟度上官方声明仍在开发中。任何一条不满足时，应退回传统流水线或等待官方对应支持。
