# EPLB 内容范围

## 1. 概念含义

- 概念名称：EPLB，Expert Parallelism Load Balancer，专家并行负载均衡器。
- 简要定义：给定每个逻辑专家的估计负载，计算一份「复制哪些专家（冗余专家）+ 每个物理专家放在哪张 GPU」的排布方案，使各 GPU 负载尽量均衡；在线部署中按统计周期性重算该方案。
- 正式定义：
  - EPLB 仓库（deepseek-ai/EPLB，main 分支）README：专家并行下不同专家分到不同 GPU，专家负载随 workload 变化，需要保持各 GPU 负载均衡；DeepSeek 采用冗余专家策略复制高负载专家，再启发式地把复制后的专家打包到 GPU；算法开源为 `eplb.py`，入口函数 `rebalance_experts`。
  - vLLM 文档（Expert Parallel Deployment 页）：vLLM 提供内置的 Expert Parallelism Load Balancer，用 `--enable-eplb` 启用，每次前向收集负载统计并周期性重排专家分布。
  - vLLM 源码 `vllm/distributed/eplb/policy/default.py` 模块 docstring：重排算法改编自 DeepSeek EPLB。
- 本文采用的语境：MoE 大模型在专家并行部署下的负载均衡；以 DeepSeek-V3 部署为实例、以 EPLB 仓库与 vLLM 为两个具体实现。
- 概念歧义处理：已裁定。LLM 推理语境中 EPLB 即 DeepSeek 的 Expert Parallelism Load Balancer（开源库），vLLM 内置功能与其同名同源（default 策略直接改编自该仓库），无其他主流含义。

## 包括什么

- 专家并行负载不均的机制与代价量化（最慢卡决定整层时间）——这是 EPLB 存在的理由。
- 逻辑专家与物理专家的区分、冗余专家的两个作用（分摊热专家负载；让物理槽位数被 GPU 数整除以对齐显存）。
- `replicate_experts` 贪心复制算法（每次给单副本负载最大的专家加一副本）。
- `balanced_packing` 均衡打包贪心（负载降序、放入仍有容量的最轻包、每包恰好 n/m 个）。
- 层次策略三步（组→节点、节点内复制、物理→GPU）与全局策略的触发条件、各自适用阶段。
- 官方 README 示例（12 逻辑专家、16 副本、2 节点 8 GPU）的完整手算与官方输出核对。
- 动态重平衡闭环：统计收集 → 周期性重算 → 权重搬运与路由表更新；V3 prefill/decode 部署数字。
- vLLM 集成：启用方式、参数（window_size、step_interval、num_redundant_experts 等）、每 rank 专家数公式、内存开销公式、preserve_intragpu_slots。

## 不包括什么

- 专家负载预测方法（README 明示 out of scope，仅提到移动平均是常见做法）——排除理由：官方明确划出范围。
- 路由层负载均衡（V3 的 aux-loss-free bias 机制）——已有概念页《辅助损失无关路由》，本文只引用其结论说明两层互补。
- 专家并行与 all-to-all 通信机制本身——已有概念页《MoE 大模型推理与服务基础》，本文只引用。
- DeepEP 通信库、all-to-all kernel 优化、IBGDA——独立主题，与排布算法无关。
- UltraEP、MoonEP 的算法细节——各有页面，本文仅在边界处一句话对比并链接。
- vLLM 异步 EPLB 执行细节（async_worker、communicator 后端选择）——工程细节，不影响概念理解。
- 权重搬运的具体实现（DeepSeek 训练/服务框架侧未开源；vLLM 侧仅说明有通信后端与槽位保持机制）。

## 相邻概念

- 辅助损失无关路由（aux-loss-free routing）：同属「MoE 负载均衡」，但作用层不同——bias 调「token 选谁」，训练期生效；EPLB 调「专家放在哪、复制几份」，部署期生效。两者互补，不混淆。不纳入本页正文展开（有页面）。
- 静态摆放策略（如 vLLM 的 expert_placement_strategy linear/round_robin）：不依赖负载统计的初始摆放。vLLM 配置中存在，与 EPLB（动态、带冗余）是不同选项。仅一句话提及，不展开。
- UltraEP：把「建不建副本」与「接多少 token」并成配额、实时规划，改进 EPLB 周期性重排跟不上漂移的问题。有页面，链接。
- MoonEP：让每个 EP rank 恰好收到固定数量 token 的完美均衡方案。有页面，链接。

## 2. 学习目标

### Q1：专家并行下 GPU 负载为什么不均，代价如何量化？

- 完成答案：EP 中每张 GPU 只持有部分专家，token 由路由发往专家所在卡；一张卡的负载 ≈ 发到它所持专家的 token 数。dispatch/combine 之后各卡独立计算，但整层在 all-to-all 同步点等所有卡完成，层时间由负载最大的卡决定；理想均分下的利用率可用 平均负载/最大负载 量化（构造两卡 800/200 例：62.5%）。训练期 bias 均衡只在训练步末更新，推理期路由规则固定，而线上 token 分布随 workload 高度倾斜，因此推理部署需要独立于路由的均衡手段；V3 以不丢 token 为前提，选择部署层排布。
- 为什么是核心目标：不理解「最慢卡决定整层时间」与「推理期为何仍不均」，就无法区分 EPLB 与路由层均衡的职责。
- 依赖内容：EP 与 all-to-all（moe-serving 页）、V3 bias 均衡机制（aux-loss-free-routing 页）、木桶效应量化（本页构造）。

### Q2：冗余专家如何在不增加每 token 计算的前提下分摊热专家负载，为什么还顺带解决显存槽位对齐？

- 完成答案：逻辑专家（模型定义中的专家）可拥有多个物理副本，发往该逻辑专家的 token 被分摊到各副本，单副本负载 = 逻辑负载 / 副本数；每个 token 激活的专家数不变（仍是 top-k），代价是多出的副本参数占显存。同时，物理专家总数必须被 GPU 数整除（每卡固定槽位、显存均匀），逻辑专家数不整除时冗余副本恰好补齐槽位（12 逻辑专家 + 4 冗余 = 16 = 8 卡 × 2 槽）。贪心复制：每次给 逻辑负载/副本数 最大的专家加一副本，逐步压低最大副本负载。
- 为什么是核心目标：这是 EPLB 与「无冗余摆放」的本质差异，是算法两块基石之一。
- 依赖内容：逻辑/物理专家定义、均摊公式、贪心复制、Q1 的负载概念。

### Q3：rebalance_experts 的三步层次策略每步做什么、如何手算？全局策略何时启用、有何取舍？

- 完成答案：层次策略适用于节点数整除组数时（prefill 阶段较小 EP）：第一步把专家组均衡打包到节点（组不跨节点，配合组受限路由减少跨节点流量）；第二步在每个节点内对本地专家做贪心复制；第三步把物理专家（负载 = 逻辑负载/副本数）均衡打包到节点内 GPU。全局策略（组数不整除节点数、decode 大 EP）：忽略分组全局复制再全局打包，均衡度更好但失去组局部性。官方示例手算：组负载 262/330/116/325 → 节点 446/587；节点内复制 e5,e4 与 e10,e1；最终 GPU 负载 86.5–156（max/mean≈1.21），与官方输出 tensor 逐槽一致；同例全局策略 max/mean≈1.07。
- 为什么是核心目标：这是 EPLB 的核心算法，可手算可复算，是页面主体。
- 依赖内容：Q2 的复制贪心、balanced_packing 打包贪心、组与组受限路由。

### Q4：重平衡如何在线上周期性执行？vLLM 中如何启用、参数与内存开销是什么？

- 完成答案：闭环 = 每次前向收集负载统计 → 周期性重算排布（V3 线上约每 10 分钟；vLLM 默认每 3000 步，用最近 1000 步窗口统计）→ 搬运专家权重、更新物理映射与路由表。V3 prefill：4 节点 32 GPU、EP32、32 个冗余专家（每卡 8 原 + 1 冗余）；decode：40 节点 320 GPU、EP320、每卡 1 专家（64 卡承载冗余与共享专家，无需重排，共享专家视为必选路由专家）。vLLM：--enable-eplb 启用；每 rank 专家数 = (专家总数 + 冗余数) / EP rank 数；内存开销 = MoE 层数 × 每专家字节数 × 冗余专家数 / EP rank 数（V3 每 rank 1 个冗余 ≈ 2.4 GB）；preserve_intragpu_slots 让留在本卡的专家保持原槽位以减少搬运。
- 为什么是核心目标：算法若不落地为周期性闭环，就无法应对负载漂移；vLLM 集成是读者最可能接触的形态。
- 依赖内容：Q2/Q3 的排布方案、统计来源说明。

### Q5：EPLB 不解决什么？成立的约束条件是什么？

- 完成答案：不解决负载预测（常用历史统计移动平均，官方划出范围）；不做路由层均衡（与 V3 bias 互补）；不保证最优（贪心 + 整除与分组约束，构造例中层次策略均衡度低于全局）；冗余副本占显存（内存公式）；重排有搬运成本（周期性而非实时，UltraEP/MoonEP 是改进方向）。约束：物理专家数被 GPU 数整除、逻辑专家数被组数整除、（层次路径）组数被节点数整除；均摊假设要求分发层把同逻辑专家 token 均摊到副本。
- 为什么是核心目标：划定概念边界，防止把 EPLB 当万能均衡器。
- 依赖内容：Q2/Q3/Q4 全部结论。

## 6. 常见误解和适用边界

### 误解

1. 错误：EPLB 是一种训练技术/损失函数，会改变路由。正确：EPLB 是部署层的排布算法，输入是负载统计、输出是「复制谁、放哪里」，路由规则原封不动；调「token 选谁」的是训练期的 bias 均衡（另一层，见 aux-loss-free-routing）。形成原因：两者都叫「负载均衡」。影响 Q1、Q5。
2. 错误：冗余专家让每个 token 多算几个专家。正确：每 token 激活的专家数不变（V3 每 token 8 个路由专家）；副本只改变「发往同一逻辑专家的 token 由几个物理副本分摊」，代价是显存而非每 token 计算。形成原因：「冗余」一词像增加计算。影响 Q2。
3. 错误：EPLB 一次排布就永久均衡。正确：线上负载随 workload 漂移，方案要周期性重算（V3 线上约每 10 分钟、vLLB 默认每 3000 步）；重排跟不上实时漂移正是后续工作（UltraEP）的动机。形成原因：把「均衡」理解为一次性状态。影响 Q4、Q5。
4. 错误：均衡之后每张卡负载相等。正确：贪心启发式 + 组/节点/整除约束下只能「尽量」均衡；构造例中层次策略 max/mean≈1.21，并非 1.0。影响 Q3、Q5。

### 适用边界

- 解决的问题：专家并行部署中由路由偏好与 workload 漂移造成的 GPU 忙闲不均。
- 不解决的问题：负载预测本身；路由层均衡；通信 kernel 效率。
- 成立条件：物理专家数被 GPU 数整除（每卡槽位固定）；层次路径还要求逻辑专家数被组数整除、组数被节点数整除；副本均摊要求分发层把同逻辑专家的 token 均摊到各物理副本。
- 条件不满足时：整除断言失败（算法拒绝运行）；均摊不成立时实际负载偏离计算值；不重排则负载漂移逐渐放大不均衡。
