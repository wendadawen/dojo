    专家并行负载均衡（EPLB）：复制热专家、均衡摆放，拉平忙闲不均

    主要依据：deepseek-ai/EPLB 仓库（README 与 eplb.py，main 分支）；DeepSeek-V3 技术报告（arXiv:2412.19437）；vLLM 文档「Expert Parallel Deployment」与源码 vllm/distributed/eplb/policy/default.py。

    一个 8 卡的专家并行部署上放着 12 个逻辑专家。一段服务时间过后，统计给出每个专家收到的 token 数：

    专家e0e1e2e3e4e5e6e7e8e9e10e11合计
    token 负载9013240611041653947356183861033

    这组数字来自 EPLB 仓库 README 的示例，用来演示算法输入，不是线上实测。两个观察先摆在这里：第一，12 个专家的槽位没法均分到 8 张卡上；第二，最热的专家 e10 一家就吃掉 183 个 token，而 8 卡均摊的预算只有 $1033/8 = 129.125$。不做处理的话，e10 所在的卡必然超载，并拖慢整层计算。

    EPLB（Expert Parallelism Load Balancer，专家并行负载均衡器）是 DeepSeek 开源的排布算法，也是 vLLM 的内置功能：给定每个逻辑专家的估计负载，它计算一份「复制哪些专家、每个物理副本放在哪张卡」的方案，使各卡负载尽量均衡；线上部署再按统计周期性重算这份方案[C1, C2, C13]。本页用上面的示例把算法完整手算一遍，并对照 DeepSeek-V3 的部署事实与 vLLM 的集成方式。

    核心问题

    1. 专家并行下 GPU 负载为什么不均？代价如何量化？

      解答：负载由路由结果决定，整层时间由最慢的卡决定

      专家并行把不同专家分到不同 GPU，一张卡的负载约等于发往它所持专家的 token 数；dispatch 之后各卡独立计算，整层在同步点等最慢的卡，层时间由负载最大的卡决定。理想均分下的利用率可以用「平均负载 ÷ 最大负载」量化——构造一个两卡 800/200 的例子，利用率只有 62.5%。训练期的 bias 均衡只在训练步末更新，推理期路由规则固定，而线上 token 分布随 workload 变化，所以推理部署需要独立于路由的均衡手段。完整论证见「1. 专家并行的木桶效应」。

    2. 冗余专家如何在不增加每 token 计算的前提下分摊热专家负载？为什么还顺带解决显存槽位对齐？

      解答：副本均摊单副本负载 $w_e/c_e$，多出的槽位补齐整除

      逻辑专家可以拥有多个物理副本，发往它的 token 被各副本均摊，单副本负载为 $w_e/c_e$；每个 token 激活的专家数不变（仍是 top-k），代价是副本参数多占显存。物理专家总数必须被 GPU 数整除（每卡槽位固定），逻辑专家数不整除时，冗余副本恰好补齐槽位：12 个逻辑专家补 4 个冗余得 16 = 8 卡每卡 2 槽。复制谁由贪心决定：每次给 $w_e/c_e$ 最大的专家加一副本。完整论证见「2. 冗余专家」。

    3. 层次策略的三步各做什么？如何在官方示例上完整手算？

      解答：组进节点、节点内复制、再均衡装进 GPU，手算结果与官方输出逐槽一致

      第一步把专家组均衡打包到节点（组不跨节点，减少跨节点流量）；第二步在每个节点内对本地专家贪心复制；第三步把物理专家（打包负载 = 逻辑负载 ÷ 副本数）均衡打包到节点内 GPU。官方示例上：组负载 262/330/116/325 打包成节点 446/587，节点内分别复制 e5、e4 与 e10、e1，最终 8 卡负载落在 86.5–156，输出映射与官方 tensor 逐槽一致。全局策略忽略分组，同例均衡度更好（max/mean 约 1.07 对 1.21）但失去组局部性。完整手算见「3. 三步排布」。

    4. 重平衡闭环如何在线上运转？DeepSeek-V3 与 vLLM 各怎么落地？

      解答：统计、重算、搬运、继续服务；V3 约每 10 分钟，vLLM 默认每 3000 步

      每次前向收集负载统计，周期性重算排布（V3 线上约每 10 分钟；vLLM 默认每 3000 个引擎步、用最近 1000 步的窗口统计），然后搬运权重、更新物理映射与路由表。V3 prefill 用 4 节点 32 卡、每卡 8+1 个专家；decode 用 40 节点 320 卡、每卡 1 个专家、共享专家视为必选路由专家。vLLM 用 --enable-eplb 启用，每卡专家数按 (专家总数 + 冗余数) ÷ EP rank 数计算，内存开销有对应公式。完整论证见「4. 周期性重平衡」。

    5. EPLB 不解决什么？

      解答：负载预测、路由层均衡、通信 kernel 效率、重排间隙的漂移都不在其范围

      负载预测方法被官方明确划出范围（常见做法是历史统计的移动平均）；「token 选谁」的路由层均衡由训练期 bias 承担，与 EPLB 是互补的两层；贪心加整除约束不保证最优——构造例中层次策略 max/mean 约 1.21 而非 1.0；周期性重排跟不上实时漂移，UltraEP、MoonEP 是后续改进方向。完整论证见「5. 边界」。

    常见误解

    • EPLB 改变路由，让 token 换个选法——不改。EPLB 调节「专家放哪、复制几份」，路由规则原封不动；调节「token 选谁」的是训练期的 bias 均衡，两层互补。
    • 冗余专家让每个 token 多算几个专家——不多算。每 token 激活的专家数不变（仍是 top-k），副本只分摊发往同一逻辑专家的 token，代价是多占显存而非多算。
    • 一次排布就永久均衡——线上负载随 workload 漂移，方案要周期性重算（V3 线上约每 10 分钟，vLLM 默认每 3000 步）。

    先弄清楚「为什么慢」：不均的代价有多大、训练期已经做过的均衡为什么到推理期会失效。

    1. 专家并行的木桶效应——最慢的卡决定整层时间

    1.1 一张卡的负载由什么决定

    专家并行（EP）把 MoE 层的不同专家分片到不同 GPU，每张卡只持有部分专家。每个 token 由 router 选出 top-k 个专家后，它的激活被 dispatch（一次 all-to-all 通信）送到这些专家所在的卡；专家算完，输出再经 combine（又一次 all-to-all）送回原卡加权合并。这套数据流的细节见MoE 大模型推理与服务基础。

    于是一张卡的负载约等于「发往它所持专家的 token 数」。这个量由两件事共同决定：token 的路由结果（选了哪些专家），以及专家摆在了哪些卡上。路由结果随 workload 变化——不同业务、不同时间段，热门专家不同[C1]；摆放如果固定不变，忙闲不均就只是时间问题。

    代价在同步点兑现。dispatch 之后各卡独立计算，但 combine 之前整层必须等所有卡到齐：快卡算完也得等慢卡。整层时间由负载最大的卡决定，其余卡的空闲都是浪费。构造一个最小的量化工具（本页构造，非来源公式）：层利用率 = 平均负载 ÷ 最大负载[F2]。两卡各承载 800 与 200 个 token 时，利用率 = $500/800 = 62.5\%$——一半算力在等。该比值越大越接近 1（完全均衡），实际中总是 $\le 1$。

    回到开头的 12 专家示例。总负载 1033，8 卡均值 129.125；而 e10 一家的负载就有 183，超出预算 42%。若不复制 e10：e10 独占一卡时该卡最大负载 183（最好情况；最大与均值之比至少 $183/129.125 \approx 1.42$，层利用率至多约 70.6%）；若 e10 与另一个专家共卡，最好的搭配是 e10 与最冷的 e7 共卡，该卡最大负载 187（max/mean 至少 $\approx 1.45$，层利用率至多约 69%）[N2]。不论哪种摆放，单 e10 一项就足以让最慢卡把整层时间拉到比理想均分高出 40% 以上。「12 个槽分给 8 张卡」这个整除问题，也会在「2. 冗余专家」一并解决。

    1.2 训练时已经均衡了，为什么推理还会不均

    DeepSeek-V3 训练时用辅助损失无关策略做均衡：一个 bias 项加在专家亲和分数上，只影响 top-K 选择；每个训练步的末尾，过载专家的 bias 减 $\gamma$、欠载的加 $\gamma$，逐步把负载拉平。机制的完整拆解见辅助损失无关路由。由于均衡策略有效，V3 训练全程不丢 token[C12]。

    问题在于这套更新挂在训练步上。报告原文写的是「每个训练步末」更新 bias[C12]；推理没有训练步，bias 不再更新，路由规则（含 bias）原封不动——这是从更新机制直接得出的推断（报告未逐字陈述推理期行为）。与此同时，线上 token 分布随 workload 变化[C1]：换个业务、换个时间段，热门专家就换一批。训练期学到的均衡只覆盖训练分布，推理期的漂移要靠部署层自己吸收。

    V3 还给了一个硬约束：推理也不丢 token[C12]。丢 token（溢出即丢弃）是路由层的暴力均衡手段，V3 不用；剩下的手段就是部署层的排布——这正是 EPLB 所在的层。两层均衡各管一件事：

    训练期 bias 均衡推理期 EPLB
    作用层路由层（token 选谁）部署层（专家放哪、复制几份）
    调节对象加在亲和分数上的 bias物理专家的副本数与位置
    生效时机每个训练步末更新按统计周期性重算排布
    路由规则随 bias 变化原封不动

    本章问题

    1. 一张 GPU 的负载由什么决定？整层计算时间由什么决定？

      解答：负载约等于发往该卡所持专家的 token 数，层时间由负载最大的卡决定

      负载 = 路由结果（token 选了哪些专家）与专家摆放（专家在哪些卡上）的乘积效应，约等于发往该卡所持专家的 token 数。dispatch 之后各卡独立计算，combine 之前整层在同步点等所有卡到齐，层时间由负载最大的卡决定，层利用率可用平均负载 $\div$ 最大负载量化。构造示例：12 专家总负载 1033、8 卡均值 129.125，e10 负载 183 已超预算；不复制 e10 时，e10 独占一卡最大负载 183（max/mean $\approx 1.42$、利用率 $\le 70.6\%$），与 e7 共卡最大负载 187（max/mean $\approx 1.45$、利用率 $\le 69\%$）。

    2. 训练时已经用 bias 均衡了，为什么推理部署还会不均？

      解答：bias 更新挂在训练步末，推理期路由固定而 token 分布仍在漂移

      V3 报告写明 bias 的增减发生在每个训练步末；推理没有训练步，bias 固定、路由规则不变（由更新机制直接推出的推断，报告未逐字陈述）。线上 token 分布随 workload 变化，训练期的均衡不覆盖推理期的分布。V3 承诺训练与推理都不丢 token——丢 token 是路由层的暴力均衡手段，不用它，就用部署层排布（EPLB）：调「专家放哪、复制几份」，路由规则不动。

    2. 冗余专家——用参数副本分摊计算，顺带对齐显存槽位

    2.1 逻辑专家与物理专家

    把两个词分开：逻辑专家是模型定义中的专家，router 的候选单位，数量记为 num_log；物理专家是显存里实际存放的一份专家参数，总数记为 num_phy。一个逻辑专家 $e$ 可以拥有 $c_e$ 个物理副本——它们参数相同、各占一份显存，对路由来说仍是同一个候选。

    副本的作用是分摊。设逻辑专家 $e$ 的估计负载为 $w_e$（一段时间内发往它的 token 数），副本数为 $c_e$，则每个副本承载的打包负载为：

    $$\ell_e = \frac{w_e}{c_e}$$

    • $w_e$：逻辑专家 $e$ 的估计负载，单位为一段时间内发往它的 token 数。
    • $c_e$：逻辑专家 $e$ 的物理副本数。
    • $\ell_e$：每个物理副本承载的打包负载（用于后续均衡打包计算）。

    这个式子背后是一个显式假设：发往同一逻辑专家的 token 被各副本均摊[C8, F1]。EPLB 的打包计算建立在该假设上，把它变成现实是分发层的职责——dispatch 时需要在各副本之间分散发往该逻辑专家的 token。具体的分发机制不在 EPLB 仓库范围内（README 只对负载预测点过「移动平均」一种常见做法），本页亦无法验证「轮流分发」是否就是常见实现，故此处的具体表述仅为辅助解释，与 EPLB 自身的约束保持独立；若分发不均，实际负载会偏离计算值。

    注意每 token 的计算量没有变：token 仍按 top-k 选逻辑专家，每个被选中的逻辑专家在其中一份副本上算一次。副本改变的是「谁来算」，不是「算多少」；代价是显存——多一个副本就是多一份完整的专家参数，量化公式放在「4. 周期性重平衡」的 4.3 节。

    2.2 槽位整除——冗余的第二个作用

    显存均匀地分配给每张卡，每卡的专家槽位数固定，因此物理专家总数必须被 GPU 数整除——这是 EPLB 接口的硬约束（num_replicas 必须是 num_gpus 的倍数[C9]）。12 个逻辑专家放进 8 张卡，12 不被 8 整除，怎么摆都不齐。

    冗余专家把两个问题一起解决：12 个逻辑专家补 4 个冗余副本，得 16 个物理专家，$16 = 8 \times 2$，每卡恰好 2 槽。从补齐整除的角度看，多出来的 4 个槽放谁都行——复制最冷的专家也能凑数；但对均衡无益，因为热门专家的负载没有被分摊。对照：若 4 个名额给了冷专家（如 e7，负载 4），槽位齐了，最大单副本负载仍是 e10 的 183。放热专家的副本，才能同时分摊计算[C2]。这就是「复制高负载专家」策略的完整动机。

    层次策略路径上还有一条整除链：逻辑专家数要整除组数、组数要整除节点数、GPU 数要整除节点数[C9]。「组」是什么、为什么要整除，第 3 章展开。

    2.3 复制哪些专家——贪心规则

    复制谁由一个贪心决定：目标是使「所有副本的最大负载」尽量小，实现为每次给 $w_e/c_e$ 最大的逻辑专家增加一个副本[C6]。直觉很直接：每一步都把当前最高的单副本负载压到 $w_e/(c_e+1)$，冷专家永远不会成为最大值，名额不会被浪费。

    在示例上从全局视角手算（12 → 16，4 个冗余名额，暂不管节点与分组）：

    步加副本给加之前 $w_e/c_e$加之后 $w_e/c_e$当前最大单副本负载
    1e1018391.5165（e5）
    2e516582.5132（e1）
    3e113266104（e4）
    4e41045291.5（e10）

    四步之后，最大单副本负载是 91.5（e10 的两份副本），已低于 129.125 的预算；对照不复制时 e10 所在卡的至少 187，热专家的负载被切实分摊了。贪心每一步都选当前最大，这保证了名额永远花在刀刃上。

    展开：贪心复制 12→16 的逐步验证

    逐步列出每次加副本后全部专家的 $w_e/c_e$（只写变化项与最大值）。初始（全部 $c_e = 1$）：最大值 = e10 的 183。

    第 1 步后：e10 = 91.5；其余不变。最大值 = e5 的 165。第 2 步后：e5 = 82.5。最大值 = e1 的 132。第 3 步后：e1 = 66。此时剩余候选中的最大值：e4 = 104（e10 = 91.5、e0 = 90、e11 = 86 都更小）。第 4 步后：e4 = 52。最终各专家 $w_e/c_e$：e0=90、e1=66、e2=40、e3=61、e4=52、e5=82.5、e6=39、e7=4、e8=73、e9=56、e10=91.5、e11=86；最大值 91.5。若还有第 5 个名额，会再次给 e10（91.5 最大，压到 61）——名额用完即停。

    这一节的手算是「全局视角」：只回答复制谁，不管放哪。真实算法里，层次策略的复制发生在每个节点内部（「3. 三步排布」的 3.2 节第二步），节点内有哪些专家取决于组先装到了哪个节点；全局策略则直接采用本节视角。两种策略的差异见 3.3 节「全局策略——何时启用、得失如何」。

    本章问题

    1. 逻辑专家和物理专家是什么关系？副本如何分摊负载？

      解答：物理专家是逻辑专家在显存中的参数副本，各副本均摊 $w_e/c_e$

      逻辑专家是模型定义的路由候选单位（num_log 个）；物理专家是显存里的一份参数副本（共 num_phy 个）。逻辑专家 $e$ 有 $c_e$ 个副本时，每个副本承载 $w_e/c_e$——前提是分发层把发往 $e$ 的 token 均摊到各副本（EPLB 打包计算的显式假设）。每 token 激活的专家数不变（仍 top-k，每个被选中的逻辑专家算一次），代价是副本参数多占显存。

    2. 为什么冗余专家同时解决了「槽位数不整除」的问题？

      解答：每卡槽位固定要求物理专家数被 GPU 数整除，冗余副本补齐缺口

      显存均匀分配给每张卡、每卡槽位数固定，物理专家总数必须被 GPU 数整除（接口硬约束）。12 个逻辑专家补 4 个冗余得 16 = 8×2，每卡恰好 2 槽。凑数的槽放谁都行，但放热专家的副本才能同时分摊计算：复制冷专家（如负载 4 的 e7）只凑数，最大单副本负载仍是 e10 的 183。

    3. 复制哪些专家？贪心规则是什么、为什么有效？

      解答：每次给 $w_e/c_e$ 最大的专家加一副本，逐步压低最大单副本负载

      贪心规则：每一步给 $w_e/c_e$ 最大的逻辑专家加一个副本，把它压到 $w_e/(c_e+1)$。示例的 4 个名额依次给 e10（183→91.5）、e5（165→82.5）、e1（132→66）、e4（104→52），结果最大单副本负载 91.5，低于预算 129.125。有效的原因：每一步都作用于当前最大值，冷专家永远不会成为 $w_e/c_e$ 的最大者，名额不会浪费在无助于均衡的复制上。

    3. 三步排布——组进节点、节点内复制、再均衡装进 GPU

    3.1 组与节点受限路由

    「组」是逻辑专家按连续编号划分的固定分组，数量由 EPLB 的 num_groups 参数指定。示例的 12 个专家分 4 组：G0 = {e0, e1, e2}、G1 = {e3, e4, e5}、G2 = {e6, e7, e8}、G3 = {e9, e10, e11}。

    按组组织排布，是为了配合 DeepSeek-V3 的节点受限路由：每个 token 至多发给 $M$ 个节点，节点按「该节点上专家的最高 $K_r/M$ 个亲和分数之和」选出[C3]。EPLB 的 README 把这一机制称为 group-limited expert routing。若一个组的专家全部落在同一节点上，发往该组的 token 就不必出节点。

    组局部性值钱的原因是带宽差：节点内 NVLink 带宽 160 GB/s，跨节点 InfiniBand 50 GB/s，约 3.2 倍[C19]。V3 正是靠限制每 token 至多 4 个节点来压住 IB 流量[C19]。所以 EPLB 在打包时「尽量把同组专家放进同一节点」[C2]——层次策略的第一步由此而来。

    3.2 层次策略的三步

    当节点数整除组数时，EPLB 走层次策略（示例：4 组、2 节点，组数恰为节点数的两倍）[C5]。三步依次是：组打包到节点、节点内复制、物理专家打包到 GPU。

    第一步：组均衡打包到节点。先算组负载：G0 = 90+132+40 = 262，G1 = 61+104+165 = 330，G2 = 39+4+73 = 116，G3 = 56+183+86 = 325。用均衡打包贪心（负载降序遍历，每个对象放进仍有容量且当前最轻的包，每包恰好装 2 组[C7]）：G1（330）进节点 0，G3（325）进节点 1，G0（262）进当时更轻的节点 1，G2（116）进更轻的节点 0。结果：节点 0 = {G1, G2}，负载 446；节点 1 = {G0, G3}，负载 587。

    第二步：节点内贪心复制。每个节点分到 6 个逻辑专家，要扩成 8 个物理专家（2 个冗余名额），复制只在节点内部进行。节点 0 持有 {e3, e4, e5, e6, e7, e8}（负载 61, 104, 165, 39, 4, 73），按第 2 章的贪心：名额给 e5（165→82.5）、再给 e4（104→52）。节点 1 持有 {e0, e1, e2, e9, e10, e11}（负载 90, 132, 40, 56, 183, 86），名额给 e10（183→91.5）、再给 e1（132→66）。注意复制结果依赖于第一步：e10 在节点 1，所以节点 1 的名额给了 e10；若分组换了方向，复制对象就不同。

    第三步：物理专家均衡打包到 GPU。每个物理槽位的打包负载 = 所持逻辑专家负载 ÷ 该专家副本数——每一份副本（包括未标「副本」的那份）都记均摊值[C8]。节点 0 的 8 个物理负载为 82.5（e5）、82.5（e5 副本）、73（e8）、61（e3）、52（e4）、52（e4 副本）、39（e6）、4（e7），降序打包进 4 张卡（每卡 2 槽），得到四卡负载 121.5 / 86.5 / 125 / 113；节点 1 同法得 147.5 / 131.5 / 156 / 152。

def balanced_packing(weight, num_packs):
    """Greedy: descending load; each item into the lightest pack with capacity."""
    n = len(weight)
    per_pack = n // num_packs
    order = sorted(range(n), key=lambda i: -weight[i])
    pack_index, rank_in_pack = [-1] * n, [-1] * n
    pack_load = [0.0] * num_packs
    pack_count = [0] * num_packs
    for i in order:
        p = min((q for q in range(num_packs) if pack_count[q] < per_pack),
                key=lambda q: pack_load[q])
        pack_index[i], rank_in_pack[i] = p, pack_count[p]
        pack_load[p] += weight[i]
        pack_count[p] += 1
    return pack_index, rank_in_pack


def replicate_experts(weight, num_phy):
    """Greedy: each new replica goes to the expert with max load per replica."""
    num_log = len(weight)
    phy2log = list(range(num_phy))
    logcnt = [1] * num_log
    for i in range(num_log, num_phy):
        best = max(range(num_log), key=lambda e: weight[e] / logcnt[e])
        phy2log[i] = best
        logcnt[best] += 1
    return phy2log, logcnt

    3.3 全局策略——何时启用、得失如何

    当组数不被节点数整除时，EPLB 改走全局策略：忽略分组，全局贪心复制、全局打包到 GPU[C5]。README 对应的使用建议是：层次策略适用于 prefill 阶段较小的 EP，全局策略适用于 decode 阶段较大的 EP[C5]（两类部署的实际差别见「4. 周期性重平衡」）。

    同一个示例用全局策略重算：复制采用第 2 章的全局视角手算（名额给 e10、e5、e1、e4），再把 16 个物理负载直接打包进 8 张卡。8 卡负载变为 130.5 / 95.5 / 130 / 138 / 138.5 / 134.5 / 134 / 132，落在 95.5–138.5 之间，最大值与均值之比约 1.07——均衡度好于层次策略的 1.21[N2]。原因不难理解：全局打包的搜索空间不受「组不跨节点、节点内复制」约束，负载配对的自由度更大。

    代价是组局部性。全局打包后同组专家可能散到不同节点：本例中 G0 = {e0, e1, e2} 的专家分别落在 GPU 2 与 GPU 7 上——若这两张卡分属不同节点，发往 G0 的 token 就要跨节点。还有一个值得注意的细节：贪心只以负载为目标，全局打包甚至会把同一专家的两个副本放进同一张卡（本例 GPU 7 的两个槽都是 e1，合计 132）。对负载无害，但这份副本没有起到分散的作用——「复制几份、放在哪」全由负载贪心决定，算法没有「副本必须分散」的约束。

    1. 为什么要先把「组」装进节点？组是什么？

      触发条件是组数不被节点数整除（eplb.py 的分支判断）；README 建议 decode 大 EP 用全局、prefill 小 EP 用层次。同一示例下全局策略复制 e10、e5、e1、e4，8 卡负载 95.5–138.5，max/mean 约 1.07，优于层次的 1.21——全局打包不受组与节点约束，配对自由度更大。代价：同组专家（如 G0 = {e0, e1, e2}）可能散到不同节点（例中 e0、e2 落在 GPU 2、e1 两副本落在 GPU 7），跨节点流量回来；且贪心只管负载，可能把同一专家的两副本放进同一张卡（GPU 7 = e1 + e1），副本没有起到分散作用。

    4. 周期性重平衡——从线上统计到权重搬运

    4.1 重平衡闭环

    排布方案不是一次性的。「1. 专家并行的木桶效应」已经看到，线上 token 分布随 workload 漂移，今天的均衡摆放明天就可能失衡，所以方案要周期性重算。完整闭环是：

    两个环节值得展开。其一是「估计负载从哪来」：EPLB 算法吃的是估计值，怎么从统计得到估计不在它的范围内——README 明示这是使用方的职责，常见做法是历史统计的移动平均[C4]。vLLM 把这部分做成了现成能力：按窗口聚合最近若干步的统计，窗口与步数都可配置[C14]。

    其二是应用方案的成本。重算部分是排序与贪心打包，开销远小于搬运；贵的是搬运权重：整份专家参数在 GPU 间拷贝。vLLM 用 preserve_intragpu_slots 压这部分开销：GPU 数与每卡槽位数不变时，重排后让留在本卡的专家保持原槽位、新来的专家填空槽，避免不必要的权重拷贝[C16]。

    4.2 DeepSeek-V3 的 prefill 与 decode 部署

    V3 报告给出了两个阶段各自怎么用冗余专家。prefill 的最小部署单元是 4 节点 32 GPU：attention 部分用 TP4+SP、DP8（术语见模型并行页），MoE 部分用 EP32；引入 32 个冗余专家，每张 GPU 除原有 8 个专家外多持有 1 个（8+1）。高负载专家由线上部署收集的统计检测、周期性调整（如每 10 分钟）；确定冗余集合后，在节点内 GPU 间精心重排——不增加跨节点 all-toall 通信开销的前提下尽量均衡[C10, N4]。8+1 的数字可以用第 4.3 节的公式验证：$(256 + 32)/32 = 9$[C15, C17]。

    decode 的做法更极端，先改了语义：把共享专家当作路由专家对待——每 token 路由时选 9 个专家，共享专家被视为始终被选中的高负载专家[C11]。最小部署单元 40 节点 320 GPU：attention TP4+SP、DP80，MoE EP320；每张 GPU 只持有 1 个专家，64 张 GPU 承载冗余专家与共享专家。因为每卡只有 1 个专家，重排无从谈起——冗余集合换了，只是换哪些卡放冗余副本，不存在「卡内重新摆放」[C11, N5]。

    4.3 vLLM 中的 EPLB

    vLLM 内置了同名的 EPLB 功能，用 --enable-eplb 启用；启用后每次前向收集负载统计并周期性重排专家分布，默认策略的重排算法改编自 DeepSeek EPLB[C13]。文档示例用 Qwen/Qwen3-30B-A3B 与 deepseek-ai/DeepSeek-V3-0324 演示启用 EPLB 的 serving 配置[N6]。

    主要参数[C14]：

    参数默认含义
    window_size1000重平衡决策追踪的最近引擎步数
    step_interval3000每 N 个引擎步执行一次重排；大于窗口时只用最近窗口的统计
    num_redundant_experts0冗余专家数
    log_balancedness关记录均衡度指标：平均每专家 token 数 ÷ 最大每专家 token 数
    policydefault重排策略（default 即改编自 DeepSeek EPLB 的算法）

    两个公式决定部署形态[C15]。每 rank 专家数：

    $$\text{每 rank 专家数} = \frac{\text{专家总数} + \text{冗余专家数}}{\text{EP rank 数}}$$

    不带冗余时退化为专家总数除以 rank 数。用 V3 prefill 验证：$(256 + 32)/32 = 9$，即报告所说的每卡 8+1[C15, C17]。文档字面给出的「内存开销」公式为：

    $$\text{每 rank 总专家存储} = \frac{\text{MoE 层数} \times \text{每专家字节数} \times (\text{专家总数} + \text{冗余专家数})}{\text{EP rank 数}}$$

    DeepSeek-V3 在每 rank 1 个冗余专家的设置下，由冗余带来的增量开销约 2.4 GB（用上述公式减去无冗余时的项，等价于 $\text{MoE 层数} \times \text{每专家字节数} \times \text{冗余专家数} / \text{EP rank 数}$）；文档建议大规模部署把 num_redundant_experts 设为 32[C15, N6]。另外，vLLM 的配置里还有不依赖统计的静态摆放（expert_placement_strategy，如 linear、round_robin[C18a]），那是初始摆放选项，与按统计动态重排的 EPLB 是两回事。

    本章问题

    1. 重平衡的完整闭环是什么？各环节多久一次？

      解答：统计、重算、搬运、继续服务四环节循环；V3 约每 10 分钟，vLLM 默认每 3000 步

      每次前向收集负载统计；周期性重算复制与排布方案（V3 线上约每 10 分钟；vLLM 默认每 3000 个引擎步，用最近 1000 步的窗口统计）；然后搬运专家权重、更新物理映射与路由表；继续服务产生新统计，进入下一轮。负载预测本身不在 EPLB 范围内（README 明示），常见做法是历史统计的移动平均；vLLM 把窗口统计做成了内置参数。

    2. V3 的 prefill 与 decode 分别怎么用冗余专家？

      解答：prefill 每卡 8+1、节点内重排；decode 每卡 1 个专家、无需重排

      prefill 最小单元 4 节点 32 GPU、EP32，设 32 个冗余专家，每卡 8 原有 + 1 冗余；确定冗余集合后在节点内 GPU 间重排，不增加跨节点 all-toall 开销；周期约每 10 分钟。decode 最小单元 40 节点 320 GPU、EP320，共享专家被当作路由专家（每 token 选 9 个专家），每卡只持 1 个专家，64 张卡承载冗余与共享专家；每卡单专家所以无需重排。

    3. vLLM 里怎么启用 EPLB？每卡专家数与内存开销怎么算？

      解答：--enable-eplb；每卡专家数 = (总数+冗余)/EP rank 数，内存按层数均摊

      用 --enable-eplb 启用，可配 window_size（默认 1000）、step_interval（默认 3000）、num_redundant_experts（默认 0）等。每 rank 专家数 = (专家总数 + 冗余专家数) ÷ EP rank 数——V3 prefill 验证：(256+32)/32 = 9 = 8+1。内存开销 = MoE 层数 × 每专家字节数 × 冗余专家数 ÷ EP rank 数；V3 每 rank 1 个冗余约 2.4 GB。preserve_intragpu_slots 让留在本卡的专家保持原槽位、新专家填空槽，减少权重搬运。

    5. 边界——EPLB 不解决什么

    四条边界，每条给出「不解决什么、谁来管」。

    负载预测。算法吃的是估计负载，估计怎么来不在范围内——README 明示 out of scope，只提到移动平均是常见做法[C4]。这一环节由部署方的统计管线承担；vLLM 把窗口统计（window_size）做成了现成能力，算是给了个默认答案。

    路由层均衡。「token 选谁」的均衡是训练期 bias 的职责（见辅助损失无关路由），EPLB 调「放哪、复制几份」，两层互补不互相替代。V3 两层都用：训练期 bias 拉平，推理期部署排布兜住漂移，且全程不丢 token[C12]。

    通信 kernel 效率。dispatch/combine 的 all-toall 怎么跑得快是另一题（DeepEP 等通信库的领域）。EPLB 只保证「要送的数据尽量不出节点」（组局部性），不优化「怎么送」。

    最优性与实时性。贪心不保证最优——构造例中层次策略 max/mean 约 1.21、全局约 1.07，全局也不是最优解；整除约束限制了可用配置（物理专家数被 GPU 数整除、层次路径还有组数链[C9]）；冗余副本占显存（内存公式见「4. 周期性重平衡」的 4.3 节[C15]）；周期性重排有滞后，两次重排之间的漂移无人处理。后续工作正是冲着这些来的：UltraEP 把「建不建副本」与「接多少 token」并成配额、实时规划，改进周期性重排跟不上漂移的问题；MoonEP 追求每个 EP rank 恰好收到固定数量 token 的完美均衡。

    问题EPLB 是否管谁管
    负载怎么预测不管（官方明确划出范围）部署方统计管线；vLLM 的窗口统计
    token 选谁（路由均衡）不管训练期 bias（辅助损失无关路由）
    all-toall kernel 效率不管通信库（DeepEP 等）

    排布是否最优不保证（贪心 + 整除与分组约束）换策略或加大冗余预算的搜索

    本章问题

    1. 哪些问题被官方明确划出范围？

      解答：负载预测；路由层均衡与通信 kernel 也各属其他层

      负载预测被 README 明确划出（out of scope，移动平均是常见做法）——算法只吃估计值。路由层的「token 选谁」均衡由训练期 bias 承担，与 EPLB 的「放哪、复制几份」是互补两层，V3 两个都用且都不丢 token。通信 kernel 效率属于通信库（DeepEP 等）的领域，EPLB 只通过组局部性减少「要跨节点送的数据量」。

    2. EPLB 的贪心与约束意味着什么做不到的事？后续工作往哪走？

      解答：非最优、受整除约束、占显存、重排有滞后；UltraEP 与 MoonEP 是改进方向

      贪心非最优：构造例中层次策略 max/mean 约 1.21、全局约 1.07，全局也非最优解。整除约束限制配置：GPU 数须整除物理专家数，层次路径还要求节点数整除组数、节点数整除 GPU 数[C9]。冗余副本占显存，开销按 MoE 层数 × 每专家字节数 × 冗余数 ÷ EP rank 数累积。周期性重排有滞后，两次重排之间的漂移无人处理。后续工作：UltraEP 用配额实时规划，MoonEP 追求每个 EP rank 恰好收到固定数量 token 的完美均衡[C5]。

    辅助解释与类比边界

    「补位/凑数」的类比只用于解释槽位整除（冗余副本补齐物理专家数对 GPU 数的整除缺口）；失效边界：副本同时承担分摊计算的职责，不只是占位——放进冷专家同样能凑数但无益于均衡。「木桶效应」描述 dispatch/combine 同步点上的等待现象，不涉及流水线重叠等更细的执行模型。

    简化条件及其限制

    单层视角：多层 MoE 各自独立计算排布（官方接口本就逐层输入负载），页面只手算层 0。负载即 token 数：假定专家同构（V3 细粒度专家满足此条件），忽略专家参数量与计算强度差异；专家不同构时负载应加权。可运行代码为算法复刻而非生产实现：无分布式、无并发、单层数据，不含统计收集、权重搬运与槽位保持；这些属于部署侧（vLLM 模块）的工程内容。忽略 attention 部分的并行与负载：EPLB 只作用于 MoE 专家。
