# 投机解码（Speculative Decoding）· 内容范围

## 1. 概念歧义处理

- 名称：投机解码（Speculative Decoding），又称 Speculative Sampling、推测采样。
- 英文与缩写：Speculative Decoding / Speculative Sampling；社区常缩写为 SpecDec。
- 歧义来源：两篇奠基论文用不同术语——Leviathan et al. 2023 用 "Speculative Decoding"，Chen et al. 2023 用 "Speculative Sampling"；后续工程实现（vLLM、TGI）多采用前者。
- 裁定：本页统一采用「投机解码」（Speculative Decoding）作为主术语，首次出现时注明「Chen et al. 称之为 Speculative Sampling」。两篇论文机制本质相同（独立提出），不并列呈现两种含义。
- 状态：已裁定。

## 2.1 概念含义

- 一句话定义：投机解码是一种推理加速方法，用一个小而快的 draft 模型自回归地生成若干候选 token，再让大 target 模型一次性并行验证，通过修改版拒绝采样接受匹配的 token、拒绝并修正不匹配的 token，从而在不改变输出分布的前提下减少大模型的串行调用次数。
- 正式定义：与 Leviathan et al. 2023 §3 一致——给定 target 分布 $p$ 与 draft 分布 $q$，draft 自回归采样 $\gamma$ 个 token；target 单次前向传播对 $\gamma+1$ 个位置打分；对每个 draft token $x$ 以概率 $\min(1, p(x)/q(x))$ 接受，首个被拒绝处从 $\mathrm{norm}(\max(0, p-q))$ 重采样一个 token 并终止本轮；若全部接受则从 $p_{\gamma+1}$ 免费采样一个 bonus token。
- 本文采用语境：聚焦「为什么这样设计能既快又不改变分布」，不展开具体 draft 模型训练方法、不展开分布式部署细节。
- 包括：
  - 自回归解码的串行瓶颈与「内存带宽受限」前提（说明验证为何几乎免费）
  - Draft-then-Verify 两阶段流程
  - 修改版拒绝采样规则（接受概率 + 残差分布）
  - 输出分布不变性的证明（核心数学结论）
  - 期望 token 数与加速比公式
  - 贪心解码的退化情形
  - K3 用 EAGLE-3 作为 draft 模型的工程引用（占位）
- 不包括：
  - Draft 模型的具体训练或蒸馏方法（独立主题，本页只假设 draft 已存在且分布 $q$ 可计算）
  - 自回归 Transformer 的内部结构（前置概念 standard-attention 已覆盖注意力机制）
  - 分布式推理的拓扑与通信（独立主题，本页只在引用 Chen et al. 分布式结果时一句话提及）
  - 量化、剪枝等正交加速技术（与投机解码不冲突但独立，本页只在边界处用一句话区分）
  - Beam search 等改变输出分布的解码策略（相邻概念，本页只在「不改变分布」边界处对照）
- 相邻概念：
  - Beam search：保留多条候选序列并选最优，改变输出分布；投机解码保留单一序列且分布不变。本页不展开 beam search。
  - 量化：降低权重精度以减少显存和带宽占用；与投机解码正交，可叠加。本页不展开。
  - KV cache：缓存已计算的注意力键值，避免重复计算；投机解码假设 KV cache 已存在。本页不展开 KV cache 的实现，但会说明 draft 与 target 各自维护自己的 KV cache。

## 2.2 学习目标

### Q1：自回归解码慢在哪里，为什么「并行验证多个 token」几乎不增加成本？

- 完成答案：读者应能说明单 token 解码是内存带宽受限的（每次都要把全部权重从 HBM 读到 SM），所以单 token 前向传播和「一次性给 $\gamma+1$ 个位置打分」的前向传播墙钟时间几乎相同；多余的算术运算落在原本空闲的计算单元上。
- 为什么是核心目标：不理解这一点就无法理解「验证为何几乎免费」，整个方法的动机站不住脚。
- 依赖内容：GPU 执行模型（HBM 带宽、SM 计算单元）、自回归解码的串行性。

### Q2：Draft-then-Verify 一轮做了什么，每个 token 在什么条件下被接受或拒绝？

- 完成答案：读者应能描述一轮的输入（当前前缀、draft 模型、target 模型、草稿长度 $\gamma$）、五个步骤（draft 自回归采样 $\gamma$ 个 token、target 单次前向打分、逐位计算接受概率 $\min(1, p/q)$、首个拒绝处从残差分布重采样、若全接受则采样 bonus token）、以及每一步的输入和输出。
- 为什么是核心目标：这是机制的核心，回答不了就无法手算任何例子或理解证明。
- 依赖内容：$p$ 与 $q$ 的定义、接受概率公式、残差分布公式、bonus token 来源。

### Q3：为什么这个接受/拒绝规则能保证输出分布与纯 target 采样完全相同？

- 完成答案：读者应能写出单位置上「被采出」的概率分解：$\Pr[\text{emit }x]=\min(q(x),p(x))+\max(0,p(x)-q(x))=p(x)$，并说明两项分别对应「draft 采样到 $x$ 且被接受」与「某个 token 被拒后从残差重采样到 $x$」两条互斥路径；由此推出全文逐位置、逐轮等价于纯 $p$ 采样。
- 为什么是核心目标：这是投机解码「无损」性质的全部依据，是它区别于近似加速方法的核心。
- 依赖内容：接受概率公式、残差分布的定义与归一化常数、概率的互斥分解。

### Q4：接受率 $\alpha$ 和草稿长度 $\gamma$ 如何决定加速比，什么时候反而更慢？

- 完成答案：读者应能写出期望 token 数 $\mathbb{E}[L]=(1-\alpha^{\gamma+1})/(1-\alpha)$ 与加速比 $S=(1-\alpha^{\gamma+1})/[(1-\alpha)(1+\gamma c)]$，手算给定 $\alpha,\gamma,c$ 时的加速比；说明 $\alpha$ 太低或 $c$ 太大时 $S<1$（反而变慢），以及高负载批处理下「空闲计算」消失时的退化。
- 为什么是核心目标：决定何时该用、何时不该用、如何选 $\gamma$。
- 依赖内容：几何级数、接受率定义、draft 成本比 $c$ 的定义。

### Q5：贪心解码下规则如何退化，与采样情形的关系是什么？

- 完成答案：读者应能说明当 $p,q$ 退化为点质量分布（argmax）时，$\min(1,p/q)$ 退化为「draft 的 argmax 是否等于 target 的 argmax」的二元判断，残差重采样退化为直接取 target 的 argmax；输出与纯 target 贪心解码逐 token 一致。
- 为什么是核心目标：贪心情形是最易懂的入口，且工程中常用；明确退化关系避免读者误以为采样与贪心是两套机制。
- 依赖内容：点质量分布、argmax、贪心解码定义。

## 2.6 常见误解和适用边界

误解 M1：
- 错误理解：「投机解码是一种近似加速，会略微降低输出质量以换取速度。」
- 正确结论：投机解码是精确的（lossless），输出分布与纯 target 采样在数学上完全相同（仅受硬件数值精度影响）；draft 模型只影响速度，不影响可能的输出集合。
- 形成原因：与量化、剪枝、蒸馏等近似加速方法归为一类；未注意修改版拒绝采样的设计目的正是保分布。
- 影响目标：Q3。

误解 M2：
- 错误理解：「draft 模型猜得越准越好，所以应该用尽可能大的 draft 模型。」
- 正确结论：加速比 $S=(1-\alpha^{\gamma+1})/[(1-\alpha)(1+\gamma c)]$ 同时依赖 $\alpha$（越大越好）和 $c=T_{\text{draft}}/T_{\text{target}}$（越小越好）。增大 draft 会提升 $\alpha$ 但同时提升 $c$；Leviathan et al. 指出 $c$ 上升往往比 $\alpha$ 上升更快，存在最优 draft 规模。
- 形成原因：只关注接受率、忽略 draft 自身的串行成本。
- 影响目标：Q4。

误解 M3：
- 错误理解：「拒绝时直接从 target 分布 $p$ 重新采样一个 token 即可。」
- 正确结论：直接从 $p$ 重采样会破坏分布——因为「被采到且被接受」已经偏向 $q$ 高的 token，必须从残差 $\mathrm{norm}(\max(0, p-q))$ 重采样才能补回被低估的部分，使总分布回到 $p$。
- 形成原因：直觉认为「拒绝就重来」；未注意接受步骤已对分布做了筛选。
- 影响目标：Q3。

误解 M4：
- 错误理解：「只要有空闲算力，投机解码总是加速。」
- 正确结论：单流低负载下加速；高负载批处理下「空闲算力」消失，验证的 $\gamma+1$ 个位置会挤占本可服务其他请求的算力，vLLM 实测在高查询率下出现 1.4-1.8× 减速。是否加速取决于负载。
- 形成原因：只看单流加速比公式，忽略共享集群的吞吐代价。
- 影响目标：Q4。

适用边界：
- 解决：单流自回归解码的延迟（wall-clock latency per token）。
- 不解决：吞吐（throughput）——高并发批处理下可能反而降低总吞吐。
- 不需要：target 模型重训练或架构修改（Leviathan et al. 与 Chen et al. 均强调「off-the-shelf」）。
- 需要：target 与 draft 共享 tokenizer（词表对齐，否则 $p/q$ 无意义）；draft 单步成本远小于 target（$c \ll 1$）；批处理规模足够小使验证的额外位置不挤占他人算力（或专用低负载场景）。
- 条件不满足时：词表不齐则无法应用；$c$ 接近 1 则加速消失甚至变慢；高负载批处理则减速。
