    Mooncake：把 KVCache 提升为调度中心的分离式 LLM 服务架构

    主要依据：Ruoyu Qin, Zheming Li, Weiran He, Mingxing Zhang, Yongwei Wu, Weimin Zheng, Xinran Xu. Mooncake: A KVCache-centric Disaggregated Architecture for LLM Serving. FAST '25 / arXiv:2407.00079v4（3 Sep 2025），23 页 13 图。

    开源仓库：kvcache-ai/Mooncake（论文 §1 仅声明 trace 仓库地址，本文不展开仓库内部组件命名）。

    长上下文请求涌入时，prefill 阶段要把数万 token 一次性送进模型——这在常规推理集群里常常把同 batch 上所有 decode 序列的 TBT 拉高一个或更多 step。MaaS（Model as a Service，模型即服务）的用户既看首字延迟 TTFT（time to first token）也看连续解码延迟 TBT（time between tokens），两个 SLO 同时被破坏。Mooncake 围绕 KVCache 重构了整套推理架构：把 prefill 与 decode 拆到不同集群，把 GPU 集群里长期闲置的 CPU/DRAM/SSD/RDMA 资源组织成分布式 KVCache 池，再用一个全局调度器把请求路由到「缓存复用最多」与「负载最轻」同时成立的实例。当 GPU 供给受限出现过载时，它按预测的解码负载决定是否提前拒绝请求，避免算力浪费。本页解释这套架构为什么这样设计、它怎么工作、在哪些条件下收益最大。

    本页范围：论文（arXiv:2407.00079v4）所述的整体架构设计——两阶段分离动机、组件与四步工作流、cache-aware 调度算法、长上下文 prefill 的 CPP 与 layer-wise 重叠、过载早拒绝与预测。Transfer Engine 的内部实现、开源仓库的组件生态、异构加速器等不展开。

    核心问题

    1. Mooncake 为什么要把 prefill 与 decode 拆到不同集群？合在一起服务时会出现什么问题？

      解答：两阶段计算特性截然不同，对应两个互不妥协的延迟 SLO，耦合时会互相破坏

      prefill 把全部输入一次性并行处理，是计算密集型——注意力随输入长度平方增长、MLP 线性增长，整体超线性于输入长度；decode 每批每请求只能前进 1 个 token，是内存带宽受限型，时间次线性于 batch 大小。MaaS 把这两个阶段绑在同一集群里时，长 prefill 会抬高同 batch 中所有 decode 序列的 TBT，把 TTFT 与 TBT 两个独立 SLO 同时击穿。Mooncake 选择把两阶段彻底分离到不同集群，仅允许「不分块且不破坏 TBT SLO」的小请求 inline。完整论证在第 1 章。

    2. Mooncake 的整体架构由哪些组件构成，一个请求经过哪几步？

      解答：五大组件 + 四步工作流，KVCache 跨阶段共享

      五大组件：Conductor（全局调度器）、prefill 实例池、decode 实例池、分布式 KVCache 池（CPU DRAM + SSD + RDMA）、Messenger（GPUDirect RDMA 跨节点传输）。每个请求经过四步：① KVCache 复用（把可复用前缀从远端 CPU 内存载入 GPU 显存）；② 增量 prefill（新产生的 KVCache 写回 CPU，必要时切块流水线）；③ KVCache 传输（Messenger 逐层流式传到 decode 节点，与 prefill 重叠）；④ 解码（收齐后加入连续批处理，本地调度器复核 TBT）。完整描述在第 2 章。

    3. Mooncake「以 KVCache 为中心」的调度具体怎么运作？为什么不能只按负载均衡或只按缓存最长调度？

      解答：用 prefix 匹配 + 传输代价估计选最小 TTFT，热点缓存自动复制

      对每个请求，先按块哈希链算出它在每个 prefill 实例可复用的前缀长度 prefix_len，然后估计 TTFT——若本地足够（best/prefix < 阈值）则用本地 prefix，否则传输差额并假设传输后复用最佳 prefix。选 TTFT 最短的实例；若超出 SLO 直接 HTTP 429 拒绝。当所选实例的 prefix 远小于全局最佳时，自动把热点缓存迁到所选实例。单纯负载均衡会把请求路由到无缓存实例（重算），单纯缓存优先会让热门实例过载；cache-aware + balance-aware 组合同时最优。完整算法 + 贯穿示例在第 3 章。

    4. Mooncake 在 prefill 池里如何把长上下文 prefill 跨节点加速，又如何在传输 KVCache 时不拖慢 GPU？

      解答：CPP 把输入切成块流水到不同节点，layer-wise prefill 把 KVCache 传输藏进计算

      Mooncake 不直接跨节点做张量并行（每层 2 次 RDMA all-reduce 会显著降低 MFU），也不直接做序列并行（每层至少 1 次跨节点通信），而是用 CPP（chunked pipeline parallelism）：把每请求输入切成 $≤$ prefill_chunk 的块，不同块由不同节点流水线同时处理，跨节点通信只在阶段边界并可与计算重叠。再用 layer-wise prefill 把每层 KVCache 的 load/store 异步化与计算重叠，使 prefill 实例的执行时间 $≈$ max(载入时间, 标准 prefill 时间)——调度只需考虑 DRAM 而不必考虑 VRAM。完整对比与时序在第 4 章。

    5. 过载时 Mooncake 怎么决定拒绝哪些请求？为什么朴素早拒绝会引发负载震荡，又如何用预测解决？

      解答：在 prefill 前按池中较高负载拒绝；按预测的 decode 负载而非当前负载

      Mooncake 的目标是 goodput（只计完整完成的请求），因此 decode 阶段拒收会导致 prefill 算力浪费——必须在 prefill 前决定是否接受。朴素做法按当前 decode 负载调度，但 decode 负载在 prefill 完成时才显现，存在时滞，引发 prefill/decode 反相震荡的四阶段循环。Mooncake 用基于系统级预测的早拒绝：假设每请求 decode 时长均匀 $t_d$，预测 $t$ 时刻 decode 负载（按平均 TBT 比值）。实验显示 8P+8D $2\times$ 重放下，拒绝数 Baseline 4183 → ER 3771 → ERP 3589。完整机制在第 5 章。

    常见误解

    • 「Mooncake 等于开源的 Mooncake Transfer Engine」：本页采用的 Mooncake 指 FAST'25 论文（arXiv:2407.00079v4）描述的 Kimi 服务平台整体设计；同名开源仓库（论文 §1 仅声明 trace 仓库地址，组件生态与开源版本不在本文范围）。两者相关但不同，本文以论文含义为准。
    • 「PD 分离就是 Mooncake 的核心创新」：PD 分离此前已有 Splitwise、DistServe、TetriInfer 等并行工作。Mooncake 的核心是把 KVCache 提升为调度中心——全局 KVCache 池、cache-aware 调度、热点自动迁移、过载下的预测早拒绝。PD 分离是基础而非全部。
    • 「朴素早拒绝就是常规限流」：常规做法按当前 decode 负载调度，但 prefill 与 decode 之间存在时滞，按当前负载决策会引发反相震荡。Mooncake 用基于系统级预测的早拒绝（假设均匀 decode 时长 $t_d$，预测 $t$ 时刻 decode 负载）来缓解。

    1. 为什么把 prefill 与 decode 拆开

    prefill 与 decode 在硬件偏好和 SLO 上彼此独立；把它们绑在同一集群里会互相破坏对方的延迟。

    1.1 两阶段的计算特性与 SLO

    一次 LLM 请求在概念上分两段：prefill 把全部输入 token 一次性并行处理，同时生成第一个输出 token 并把每层的 K/V 写入 KVCache；decode 每次前进一步，把新 token 与 KVCache 一起读出，再把新生成的 K/V 追加到 KVCache。[C6, C7]

    两段对硬件的偏好相反。注意力计算量随输入长度平方增长、MLP 线性增长，整体 prefill 时间随输入长度超线性增长（论文图 2 左侧）；它把整个 GPU 的算力铺满，是计算密集型。decode 每批每请求只能前进 1 个 token，是访存密集型：计算时间随 batch 大小只次线性增长（计算量本身随 batch 线性），而每步要把不断增长的 KVCache 从 HBM 读出、写入，时间主要花在内存带宽而不是算力上（图 2 右侧）。

    MaaS 给两段定义了不同的 SLO（Service Level Objective，服务级别目标）：prefill 阶段关心的是 TTFT（time to first token，请求到达 → 第一个 token），decode 阶段关心的是 TBT（time between tokens，同一请求连续 token 间的间隔）。[C9] 在论文实验中，TTFT 与 TBT 的 SLO 阈值定义为「无干扰单请求的相应延迟的倍数」，常用 TTFTP90 = 10×、TBTP90 = $5\times$ 来约束（下标 P90 表示第 90 百分位，即 90% 的请求需满足）。[N10]

    两段对硬件与延迟的不同偏好意味着：让它们共享同一 GPU 集群会互相伤害。一个长 prefill 占满算力的整个期间，集群无法及时推进已有 decode 序列的步进，这些序列的 TBT 会一起被拉高；反过来，一个超大 decode batch 把所有 KVCache 塞进 HBM 时，新到请求的 prefill 也要等 decode 释放资源才能启动，TTFT 变差。

    1.2 连续批处理不能消除两阶段耦合

    vLLM 等系统引入的 连续批处理（continuous batching，每步迭代检查所有请求状态并加入新请求、移除已完成请求）确实显著提高了吞吐，但它作用在 同一 阶段内部：它让 decode 的 batch 不断刷新，但 prefill 与 decode 仍在同一硬件上竞争。[C8]

    一种常见替代方案是 chunked prefill：把长 prefill 切成多个小块，让 decode 搭便车分摊 prefill 的算力开销，从而避免「一整段 prefill 阻塞同 batch decode」的现象。[C15] 但 chunked prefill 不能解决根本问题——它只把 prefill 切碎，没把两阶段对硬件的不同偏好分到不同硬件上。Mooncake 在论文 §5 中明确指出两个理由要把两阶段彻底分离到不同集群：

    1. 长上下文 prefill 需要不同的跨节点并行策略（仅靠 chunked prefill 无法满足 TTFT SLO，详见第 4 章）；
    2. 分离后能节省 VRAM——prefill 实例的 VRAM 只需容纳单请求（配合 layer-wise prefill，详见第 4 章），decode 实例的 VRAM 不再被 prefill 抢占，可全部用于聚合 decode batch（§1 已指出 decode 侧本就受聚合 KVCache VRAM 容量约束）。

    因此 Mooncake 的取舍是：彻底分离 prefill 与 decode 集群，仅允许「不分块且不破坏 TBT SLO」的小请求 inline 到 decode batch。[C15] 这把 TTFT 与 TBT 的优化目标分别交给两个独立资源池，避免互相破坏。

    本章问题

    1. 为什么把 prefill 与 decode 放在同一集群会同时破坏 TTFT 与 TBT？

      解答：长 prefill 抬高 decode 的 TBT，超大 decode batch 拖慢新请求的 TTFT

      prefill 是计算密集、随输入长度超线性增长；decode 是访存密集、随 batch 大小次线性增长。把它们放在同一集群里：长 prefill 占满算力的整个期间，所有 decode 序列的步进被推迟，TBT 一起被拉高；反过来当 decode batch 把所有 HBM 都用于 KVCache，新到请求的 prefill 要等 decode 释放资源，TTFT 变差。Mooncake 用彻底分离两阶段到不同集群来让两个 SLO 各自被独立满足。

    2. chunked prefill 为什么不能替代 PD 分离？

      解答：它只解决同 batch 的阻塞，不解决两阶段对硬件的不同偏好

      chunked prefill 把长 prefill 切成多个小块，让 decode 搭便车分摊算力，缓解 generation stall，但它仍把两阶段放在同一硬件上竞争。两阶段对硬件的偏好相反：prefill 要算力，decode 要带宽；把它们绑在一起，任何阶段的突发都会伤害另一阶段。Mooncake 在论文 §5 中给出两条理由：(1) 长上下文 prefill 需要不同的跨节点并行策略（chunked prefill 解决不了）；(2) 彻底分离后 prefill 实例只需装下单请求，VRAM 可以留给 decode 装尽可能大的 batch。

    2. Mooncake 架构总览：组件、KVCache 池与四步工作流

    五大组件 + 一条四步工作流，KVCache 在 CPU/DRAM 上以分页块存储并通过 Messenger 跨节点传输。

    2.1 五大组件

    Mooncake 由五类组件组成（论文图 1）：

    • Conductor：全局调度器。它负责选择 prefill 与 decode 实例对、估计请求 TTFT 与 TBT、判断是否接受或拒绝请求、执行 KVCache 的 swapping 与 replication（把最热的块复制到多个节点避免 fetch 拥塞，把最冷的块换出）。[C11]

    • prefill 实例池：只跑 prefill 的 GPU 集群；每实例内部有本地 chunked prefill 调度器与按 PagedAttention 风格管理的 KVCache（prefill 期间临时驻留 GPU 显存）。
    • decode 实例池：只跑 decode 的 GPU 集群；每实例内部维护连续批处理的调度器，VRAM 用于装下聚合 batch 的 KVCache。
    • 分布式 KVCache 池：GPU 集群内每节点 CPU DRAM（必要时扩展到 SSD）共同组成的 KVCache 存储层，按分页块（默认 $B=512$ tokens）管理，跨节点通过 RDMA 互联。[C3, N3]

    • Messenger：基于 GPUDirect RDMA 的跨节点 KVCache 传输组件，作为独立进程部署在每个节点，接收信号执行高速 KVCache 传输。[§3]（v4 论文中此组件命名为 Messenger；本文不展开开源仓库中的 Transfer Engine 内部实现。）

    2.2 分布式 KVCache 池：分页块、哈希链、Messenger 传输

    KVCache 池的存在方式有两点关键设计：

    1. 分页块（paged blocks）：KVCache 以固定 $B=512$ tokens 的块为最小单位存放在 CPU 内存，与 PagedAttention 的分页思想一致。分页让分配/淘汰与传输都以等大块为单位（推断：避免外部碎片与不规则拷贝；论文 §3 仅指出 CPU 内存按分页块管理并使用 LRU/LFU 等淘汰策略）。[C3, N3]

    2. 块哈希链（hash chain）去重：每个块的 key = Hash(本块 tokens, 前一块 key)。等价 ID 同时意味着「块内容相同 + 此前所有块都相同」，因此能安全地把整个前缀复用到任何请求。这一实现与 vLLM 的本地缓存复用一致，Mooncake 把它的范围从单节点扩展为全局池。[C33, §3 Figure 3]

    淘汰策略可选 LRU、LFU 或 LengthAwareCache 等。论文在公开 trace 上的实验表明 LRU 在该 trace 表现最优；trace 上 50,000 块容量对应的命中率约 50%（1,000 块容量仅 30%）。[N4, N5] 同时 trace 显示超过 50% 的块从未被访问，部分块被访问数万次——这要求系统显式做热点复制，否则热门前缀会反复因 fetch 拥塞而拖慢。[N6, C11]

    Messenger 是 GPUDirect RDMA 跨节点传输组件，独立进程部署在每节点；它是基于 RDMA 的组件，跨节点直接读写对端 KVCache 块。论文 v4 仅描述其接口与位置；RDMA 一般特性下的对端 CPU 占用与拷贝路径不在论文范围内。[§3]

    2.3 请求四步工作流

    对每个请求，Conductor 先选一对 prefill 与 decode 实例，然后按四步推进（论文图 4）：

    每一步的输入/输出与传输组件：

    步骤输入输出传输组件
    ① KVCache 复用远端 CPU 上的可复用前缀块载入 GPU 显存的 KVCacheMessenger（GPUDirect RDMA）
    ② 增量 prefill已加载前缀 + 剩余输入新生成的 KVCache（写回 CPU）本地 GPU/CPU 异步 store
    ③ KVCache 传输增量 prefill 新产生的逐层 KVCache（论文 §3 step 3：streaming the KVCache generated by each model layer）decode 节点 CPU DRAM 中的副本Messenger（GPUDirect RDMA）
    ④ 解码decode 节点 CPU DRAM 中的全量 KVCache连续批处理中的解码步进本地 GPU 读取

    几个值得记下的工程要点：

    • 步骤 ② 的切块阈值 prefill_chunk 典型 > 1,000 tokens；剩余输入 $≤$ 阈值时不分块，避免流水线填充开销。[N7]
    • 步骤 ③ 与 ② 重叠——prefill 算到第 $L$ 层时，第 $L$ 层的 KVCache 已经在传给 decode；不等全部 prefill 完成。[C20]
    • 步骤 ④ 在 Conductor 预先选定 decode 实例后，仍由本地调度器复核 TBT SLO；若不通过则拒收——此时 prefill 算力已经浪费。[§3 step 4]
    辅助解释：为什么把 KVCache 放在 CPU DRAM 而不是 GPU VRAM？

    GPU VRAM 同时要装模型权重、当前请求的 KVCache、聚合 decode batch 的 KVCache。一条 12,288 token 的请求 KVCache，以 KV cache 页面的公式 $B_{\text{kv}}=2\cdot L\cdot H_{\text{kv}}\cdot d_{\text{head}}\cdot b$ 估算：取 LLaMA2-70B 配置 $L=80,\ H_{\text{kv}}=8,\ d_{\text{head}}=128,\ b=2$（fp16），$B_{\text{kv}}\approx 320\ \text{KiB/token}$，12,288 tokens 约 3.75 GiB。128k 上下文的请求就接近 40 GiB——单一请求的 KVCache 已经占满单卡 VRAM 的一半。把 KVCache 池放到 CPU DRAM/SSD 相当于把 GPU 集群里长期闲置的「邻居」容量（不仅是便宜）纳为己用；同时 RDMA 互联为 KVCache 搬运提供了独立于 GPU 算力的高带宽通路。[C3]

    本章问题

    1. Mooncake 的分布式 KVCache 池与本地 KVCache 缓存（如 vLLM 的实现）相比，关键差异是什么？

      解答：把块哈希链与 LRU 复用从单节点扩展为跨节点全局池 + Messenger 跨节点传输

      本地 KVCache 缓存（如 vLLM 的实现）只在一台 GPU 服务器内做块哈希链与 LRU 复用，缓存容量受单节点 VRAM 限制；命中只能帮同节点上的请求。Mooncake 的池把块哈希链与 LRU 扩展到 GPU 集群里每节点的 CPU DRAM（必要时 SSD），通过 Messenger（GPUDirect RDMA）在节点间搬运。关键差异有三：(1) 容量大幅增加（CPU DRAM 容量与带宽显著高于单卡 VRAM（推断，论文未给出具体数值））；(2) 命中能帮到任何节点上的请求，Conductor 可以把请求路由到缓存最多的节点；(3) 跨节点传输必须考虑网络拥塞，因此调度同时考虑 prefix 长度与传输代价（详见第 3 章）。

    2. 为什么 Mooncake 在请求完成前就已经开始把 KVCache 传给 decode 节点，而不是等 prefill 全部完成？

      解答：让传输与 prefill 计算在时间上重叠，减少端到端 TTFT

      把步骤 ②（增量 prefill）与步骤 ③（KVCache 传输）重叠：prefill 节点算到第 $L$ 层时，第 $L$ 层的 KVCache 已经由 Messenger 流式传到 decode 节点的 CPU DRAM。这样等 prefill 全部完成时，decode 节点已经在 GPU 上加载好了全量 KVCache，可以立即加入连续批处理；如果等 prefill 完成再开始传输，decode 节点的等待时间等于传输时间，会被白白浪费。这与 layer-wise prefill 的「计算与传输重叠」是同一种思路。

    3. KVCache-centric 调度算法

    Algorithm 1 在每个请求上算 prefix 匹配与传输代价，选 TTFT 最短的实例，并在必要时自动迁移热点缓存。

    3.1 块哈希链与 prefix 匹配

    对每个到达的请求 $R$，Mooncake 的 Conductor 第一步是算它能命中多少 KVCache：[C10]

    1. 把 $R$ 的 prompt tokens 按 $B=512$ tokens 切块，得到 $n=\lceil\text{prompt\_len}/B\rceil$ 块；
    2. 对每块算 key = Hash(本块 tokens, 前一块 key)（链式哈希），得 block_keys = $(k_1, k_2, \ldots, k_n)$；
    3. 对池中每个 prefill 实例 $p_i$ 比较 block_keys 与其本地缓存键，找出最长公共前缀 prefix_len$_i$（tokens 数），并记全局最佳 best_prefix_len 与 best_matched_instance = $p_{\text{best}}$。

    链式哈希保证等价 ID 同时意味着「块内容相同 + 前缀完全相同」，所以 prefix_len$_i$ 是可以原样复用的安全长度。[C33, §3 Figure 3]

    3.2 Algorithm 1 的两条分支

    对每个 prefill 实例 $p_i$，Conductor 按 Algorithm 1 估计 TTFT：

    展开：Algorithm 1 完整伪代码 
    输入：prefill 实例池 P，decode 实例池 D，请求 R，块大小 B
输出：处理 R 的 (p, d)（prefill 实例，decode 实例）

block_keys ← PrefixHash(R.prompt_tokens, B)
TTFT ← ∞
p ← ∅
best_prefix_len, best_matched_instance ← FindBestPrefixMatch(P, block_keys)

for instance ∈ P do
    prefix_len ← instance.prefix_len
    T_queue ← EstimatePrefillQueueTime(instance)
    if best_prefix_len / prefix_len < kvcache_balancing_threshold then       # Cache-aware 分支
        T_prefill ← EstimatePrefillExecutionTime(len(R.prompt_tokens), prefix_len)
        if TTFT > T_queue + T_prefill then
            TTFT ← T_queue + T_prefill
            p ← instance
        end if
    else                                                # Cache-aware + balance 分支
        transfer_len ← best_prefix_len - prefix_len
        T_transfer ← EstimateKVCacheTransferTime(instance, best_matched_instance, transfer_len)
        T_prefill ← EstimatePrefillExecutionTime(len(R.prompt_tokens), best_prefix_len)
        if TTFT > T_transfer + T_queue + T_prefill then
            TTFT ← T_transfer + T_queue + T_prefill
            p ← instance
        end if
    end if
end for

d, TBT ← SelectDecodingInstance(D)                                 # 负载均衡选 decode
if TTFT > TTFT_SLO or TBT > TBT_SLO then
    reject R; return                                             
end if
if best_prefix_len / p.prefix_len > kvcache_balancing_threshold then
    TransferKVCache(best_matched_instance, p)                            # 热点迁移
end if
return (p, d)

    两条分支的语义是：

    • 分支 1（cache-aware）：如果实例 $p_i$ 的本地前缀与全局最佳差距不大（best/prefix$_i$ < threshold），就直接用本地 prefix_len 计算 T_prefill，不传输。[C22]
    • 分支 2（cache-aware and -balancing）：如果 $p_i$ 的本地前缀远逊于全局最佳（best/prefix$_i$ $≥$ threshold），计算把差额部分（transfer_len = best_prefix_len - prefix_len）从 $p_{\text{best}}$ 经 Messenger 拉过来；T_prefill 用 best_prefix_len 计算（假设传输后复用全部最佳前缀）。[C22]

    T_prefill 由离线测试数据拟合的预测模型估计（依请求长度与 prefix_len），T_queue 由已排队请求的 prefill 时间累加得到。[C24]

    3.3 热点自动迁移

    Algorithm 1 末尾还有一步容易被忽略：当选定 $p$ 之后，若 best_prefix_len / $p$.prefix_len > threshold，则触发 TransferKVCache(best_matched_instance, p)——把 $p_{\text{best}}$ 上的热点缓存块迁到 $p$。[C23]

    这一步看似只是「搬运」，但它的实际作用是热点缓存的 自动复制：当一个无缓存/低缓存的轻负载实例因为传输后 TTFT 最短被选中，下一次再来的同前缀请求就不需要再走远端传输了。同时由于热点块被复制到多节点，原本集中在 $p_{\text{best}}$ 上的 fetch 拥塞被分散。[§6.2] Algorithm 1 的两条分支（cache-aware 与 cache-aware and -balancing）与这一热点迁移机制共同实现缓存复用与负载均衡的折中，整个过程不依赖对未来 KVCache 使用频率的精确预测——这是论文 §6.2 中以启发式（heuristic）替代预测模型的工程取舍。

    本章问题

    1. Algorithm 1 的两条分支分别适用于哪种 prefix 匹配情况？为什么需要这两条分支？

      解答：分支 1 处理「本地够用」、分支 2 处理「本地远不够、需要从最佳实例拉」

      两条分支对应不同的 prefix 匹配差距。分支 1（cache-aware）：当 best_prefix_len/prefix_len$_i$ < threshold，$p_i$ 的本地前缀与全局最佳差距不大（与全局最佳差距在阈值倍数以内）成本可控，直接用本地 prefix_len 计算 T_prefill，不传输；分支 2（cache-aware + balance）：当差距过大，$p_i$ 的本地 prefix 远逊于 best，从 $p_{\text{best}}$ 拉差额（transfer_len = best − prefix$_i$），并按传输后复用 best_prefix_len 估计 T_prefill。两条分支都需要：分支 1 避免无意义的传输浪费、分支 2 防止因「本地远不够」而把请求拒掉——同时后者也是热点自动迁移的前置条件。

    2. 为什么 Mooncake 不能只按负载均衡（最闲的实例）调度？

      解答：可能把请求路由到无缓存实例，导致全量重算；cache 复用率直接受路由影响

      单纯负载均衡选 T_queue 最小的实例——但 T_queue 小的实例其缓存可能并未集中（推断：trace 显示请求前缀复用集中于少量热点块，热点块所在实例更易进入队列）。把请求路由到无缓存实例意味着全量 prefill，TTFT 显著恶化（构造示例里纯 LB = 4.072s，比 KVCache-centric 3.036s 高 ~1s；真实回放实验 60.41s vs 6.26s）。同时 cache 命中率与路由策略强耦合：路由决策决定下次请求能命中多少。Mooncake 的解法是把 prefix 长度纳入调度（Algorithm 1），让 T_queue 与 prefix_len 共同决定 TTFT，而非只看 T_queue。

    4. 长上下文 prefill 的多节点与传输重叠

    Mooncake 用 CPP 把长上下文 prefill 切成流水线跨节点处理，用 layer-wise prefill 把 KVCache 传输藏进 GPU 计算。

    4.1 三种跨节点方案的通信代价对比

    近期 LLM 可用上下文长度迅速增长（论文 §5.1 提到 8k → 128K → 1M，引自论文参考文献 [16]）。单 8×GPU 节点的 TP 在 128K+ 上下文上很难满足 TTFT SLO，需要把单个请求的 prefill 拆分到多个节点并行。但跨节点并行的通信代价差别极大：

    方案每层跨节点通信MFU 影响动态调整
    跨节点 TP2 次 RDMA all-reduce显著降低 MFU不需要
    跨节点 SP（Ring/Striped）$≥$ 1 次跨节点仍差于单节点 TP通常需要静态分两组
    chunked pipeline parallelism（CPP）仅阶段边界通信少且可重叠（论文 §5.1 仅给「更好 MFU」的定性表述，未与单节点 TP 做直接对比）无需频繁重划分

    每层 2 次 all-reduce 的 TP 跨节点方案在长 prefill 上 MFU（Model FLOPs Utilization）掉得很厉害；SP（Ring Attention、Striped Attention 等）每层至少 1 次跨节点通信，MFU 仍比单节点 TP 差。[C16, C17] Mooncake 的解法不是 SP，而是 CPP。

    4.2 CPP：chunked pipeline parallelism

    CPP 的核心思想来自训练中的流水线并行（PP），但把切分维度反过来——不是按层切节点，而是把 请求的输入序列 切成 microbatch（Mooncake 称为 chunk），不同 chunk 流过同一组模型层（每节点持有一部分层）。[C18, C19]

    具体做法：把每 $X$ 个节点组成一个 pipelined prefill node group；对每请求，输入 tokens 被切成 $≤$ prefill_chunk 的 chunk，不同 chunk 由不同节点同时处理（在流水线相邻 stage 上并发），跨节点通信只在 stage 边界传递 activation，且可与计算重叠。CPP 与 chunked prefill（Chunked Prefill）天然契合——chunked prefill 已经按多个小块切分，CPP 把这些块在不同 stage 上流水线推进。

    CPP 的两点关键收益：

    1. 通信少且可重叠：只在 stage 边界通信，与 stage 内计算重叠，因此 通信少且可重叠，MFU 优于跨节点 TP 与 SP（论文未给与单节点 TP 的直接对比）；同时跨节点通信不与 KVCache 跨节点传输抢网络资源。[C19]
    2. 同时适合短/长上下文：短请求可以走单节点 PP 不切块，长请求切块流水线；不需要根据负载动态调整节点划分（避免复杂的弹性 SP 机制）。[C19]

    4.3 Layer-wise prefill：把 KVCache 传输藏进计算

    CPP 解决了 prefill 的并行加速，但还有一个独立的工程问题：长上下文请求的 KVCache 远大于 GPU 显存容量。论文定义占用代价 $S\cdot T$（$S$ 为 KVCache 大小，$T$ 为该请求在 GPU 上的驻留时间）。[F2] 把请求 inline 到 decode batch 会让 $T$ 变大；彻底分离 + 立即搬走则让 $S\cdot T$ 变小。

    Mooncake 用 layer-wise prefill 把 KVCache 传输与计算重叠：prefill 按层逐层进行；每层开始 attention 之前，等该层 KVCache 异步载入完成，并触发下一层 KVCache 的异步载入；attention 计算完成后立即启动该层 KVCache 的异步 store（写回 CPU DRAM）。[C20]

    效果：prefill 实例的执行时间 $≈$ max(KVCache 载入时间, 标准 prefill 计算时间)——两者中较慢的那个决定总时间。[C20] 这使得 prefill 调度只需考虑 DRAM 容量（装得下单请求）而无需考虑 VRAM——VRAM 中可同时驻留正在载入的层与正在计算的层（推断，论文 §5.2 未直接描述此细节）。这与上一节 CPP 一起，把 Mooncake 的 prefill 池做到了「VRAM 不再是 prefill 调度的约束」的程度。

    本章问题

    1. Mooncake 为什么不直接用跨节点张量并行（TP）或序列并行（SP）来加速长上下文 prefill？

      解答：TP 每层 2 次 RDMA all-reduce、SP 每层至少 1 次跨节点通信，MFU 都低于单节点 TP

      跨节点 TP 在每层要做 2 次 RDMA all-reduce，长 prefill 时这部分通信开销显著降低 MFU。SP（Ring/Striped Attention）把请求输入序列切到多节点，每层至少 1 次跨节点通信，MFU 仍差于单节点 TP。Mooncake 的替代方案是 CPP：把每请求输入切成 $≤$ prefill_chunk 的块，不同块由不同节点流水线处理，跨节点通信只在 stage 边界传递 activation，可与计算重叠——通信少且可重叠，MFU 优于跨节点 TP 与 SP（论文未给与单节点 TP 的直接对比），同时不需要根据负载频繁动态调整节点划分。

    2. layer-wise prefill 为什么能让 prefill 调度忽略 VRAM 容量？

      解答：每层 KVCache 在该层 attention 算完后立即异步 store，下一层的 KVCache 在上一层算时已异步载入

      layer-wise prefill 把 KVCache 的 load/store 异步化与每层 attention 计算重叠。每层开始前等待该层 KVCache 载入完成（由上一层 attention 期间触发的异步 store/load 提供数据），attention 完成后立即启动该层异步 store。结果：prefill 实例的执行时间 $≈$ max(载入时间, 计算时间)——两者中较慢的支配总时间。VRAM 中同时驻留的是「正在载入的一层 + 正在算的一层」（推断），占用代价 $S \cdot T$ 大幅缩小，因此调度只需考虑 DRAM 容量（装得下单请求）而不用考虑 VRAM。

    5. 过载场景下的早拒绝与预测

    Mooncake 的目标是 goodput；朴素早拒绝按当前负载调度会引发反相震荡，Mooncake 用基于系统级预测的早拒绝解决。

    5.1 Goodput 与 Early Rejection

    Mooncake 把优化目标定义为 goodput：在满足 SLO 的前提下完整完成的请求数。[C27] 只完成了一半就 decode 拒收的请求，之前消耗的 prefill 算力全部浪费，且不算入 goodput。

    在传统耦合系统里，prefill 与 decode 互相干扰、TTFT/TBT 难以精确预测，因此负载常用「请求数/最大容量」这个简单单一度量近似衡量；Mooncake 分离后两阶段独立，负载 可以直接用 SLO 满足度衡量——把请求路由到一个实例上，预测其 TTFT 是否超 TTFT SLO、TBT 是否超 TBT SLO。[§7.1]

    Early Rejection：在 prefill 开始前就按 prefill 与 decode 池中较高负载决定是否接受请求。[C28] 这样 decode 后续拒收不会浪费 prefill 算力。

    5.2 朴素早拒绝的负载震荡

    朴素 Early Rejection 按「当前」decode 负载调度——但 decode 负载是 prefill 完成后的结果，存在时滞。这导致 prefill 与 decode 负载反相震荡（论文图 10a）：

    这种反相震荡让集群利用率严重下降。[C25, §7.3]

    5.3 基于系统级预测的早拒绝

    Mooncake 用 Early Rejection Based on Prediction：在决定是否接受请求时，不看「当前」decode 负载，而是预测请求 完成 prefill 后 的 decode 负载。[C26] 预测有两种粒度：

    • 请求级：预测每请求的输出长度。难度高（LLM 输出长度难以精确预测），过载场景下更难。
    • 系统级：估计未来一段时间的整 batch 数或 TBT 状态。要求低，适合过载场景。

    Mooncake 采用系统级：假设每请求 decode 时长均匀 $t_d$，在 $t$ 时刻计算 decode 负载 = avg(TBT ratio to $l_{\text{tbt}}$)，即：

    1. 把将在 $t$ 时刻完成 prefill 的请求加入 decode 池；
    2. 把将在 $t$ 时刻之前完成 decode 的请求移出 decode 池；
    3. 计算所有 decode 实例的平均 TBT 比值作为预测负载，与 SLO 阈值 $l_{\text{tbt}}$ 对比。

    实验结果（8P+8D、$2\times$ 重放 23,000 条真实请求）：拒绝数 Baseline 4183 → Early Rejection 3771 → Early Rejection+Prediction 3589。[N9] 基于预测的早拒绝比朴素早拒绝再减少 ~5% 的拒绝数，对应的有效利用率提升来自反相震荡的缓解。

    其中长上下文场景（16k–128k）下 Mooncake 优势最显著（50%–525%），与「分离 + cache-aware 调度 + CPP + layer-wise prefill」面向此类场景的设计意图一致。短上下文、低复用场景（ArXiv cache ratio $≈$ 0%）增益相对小（仅 +20%），但仍有收益——分离架构本身的收益并不完全依赖缓存复用。[C29–C32, N11–N13]

    vLLM 在真实回放下 TBT SLO 满足率仅 57%（vLLM 的耦合设计在长上下文 prefill 涌入时被扰动），Mooncake 接近 100%。[N13] 这印证了第 1 章提出的「分离两阶段避免互相破坏 SLO」的设计动机。

    本章问题

    1. Mooncake 的优化目标是 goodput 而不是 throughput；为什么 goodput 意味着必须在 prefill 前就做接受决定？

      解答：decode 阶段拒收会让已消耗的 prefill 算力浪费，不计 goodput

      goodput 只计完整完成的请求。如果在 prefill 完成后才发现 decode 已经过载而拒收，之前消耗的 prefill 算力全部浪费，且这部分请求不计入 goodput。因此必须在 prefill 开始前就根据当前/预测的负载决定是否接受——这就是 Early Rejection 的动机。

    2. 朴素 Early Rejection 为什么会引发 prefill 与 decode 的反相震荡？Mooncake 如何用基于系统级预测的早拒绝解决？

      解答：按当前 decode 负载决策有时滞；按预测的「prefill 完成时」decode 负载决策

      朴素 Early Rejection 按「当前」decode 负载调度，但 decode 负载是 prefill 完成后的结果，存在时滞：(1) prefill 与 decode 都轻 → 大量接受 → prefill 满载；(2) prefill 完成涌入 decode → decode 满载 → 开始拒收 → prefill 空载；(3) 无新请求进 decode → decode 减载 → 又开始接受；(4) decode 又满载 → 拒收。prefill 与 decode 负载反相震荡，集群利用率低。Mooncake 用系统级预测：假设每请求 decode 时长均匀 $t_d$，在 $t$ 时刻预测 decode 负载 = avg(TBT ratio to $l_{\text{tbt}}$)——把 prefill 完成时间纳入预测窗口。实验显示 8P+8D $2\times$ 重放下拒绝数 4183 → 3771 → 3589。

    构造示例

    • 贯穿示例（第 3 章）：3 个 prefill 实例、块大小 512、请求 12,288 tokens、阈值 = 2。$T_{\text{prefill}}(p) = 0.5 + (12288 - p)/4000$ s、$T_{\text{transfer}}(t) = t/10000$ s。用于演示 Algorithm 1 两条分支与策略对比。数字均为便于手算的构造值，非论文实测。
    • KVCache 大小估算：12,288 tokens × 320 KiB/token $≈$ 3.84 GiB。以 LLaMA2-70B 配置（80 层 / 8 KV 头 / 128 head dim / fp16）估算，仅作辅助说明。

    简化条件及其限制

    • 贯穿示例的时间模型：$T_{\text{prefill}}$ 与 $T_{\text{transfer}}$ 为构造模型。论文实验中 prefill 时间由 §6.1 的离线数据拟合模型估计，受实际硬件、并行策略、prefix 复用、网络拥塞等多重因素影响。正文只用构造模型演示算法流程，不可外推为 Mooncake 实际 TTFT。
    • 回放 trace 与 dummy 模型：论文所有实验结果基于回放 trace + dummy LLaMA2-70B 架构（保护商业信息），trace 不含真实用户内容。[C35] 数字为该实验条件下的测量，不外推到所有 LLM 服务场景。
    • 缓存复用率上界：trace 内 KVCache 理论最多约 50% 可复用（容量与 TTFT SLO 无限时）；papers.cool 场景约 90%。[C34, N16] 实际复用率随应用而显著变化。
    • KVCache 大小估算：以 LLaMA2-70B 配置估算的 320 KiB/token 不直接适用于其他模型（GQA 配置、head dim、量化精度都会改变每 token 字节数）。
