Mooncake

Moonshot AI 为 Kimi 在线服务打造的分离式推理架构：把 prefill 与 decode 拆到不同集群，把 GPU 集群闲置的 CPU/DRAM/SSD/RDMA 组成全局 KVCache 池，由 Conductor 按缓存复用与负载同时最优路由请求。

更新于 2026-09-03

问题背景

在线 LLM 服务需要同时满足两个延迟 SLO：TTFT（首字延迟，对应 prefill 阶段）与 TBT（连续 token 间延迟，对应 decode 阶段）。然而 prefill 是计算密集、超线性于输入长度；decode 是访存密集、次线性于 batch 大小。把两个阶段放在同一 GPU 集群里服务时，长 prefill 会抬高同 batch 中所有 decode 序列的延迟，超大 decode batch 又会拖慢新请求的 prefill——两个 SLO 同时被破坏。Mooncake 把两阶段彻底分离到不同集群来解决这一矛盾。

核心机制

  • PD 分离 + 分布式 KVCache 池：GPU 集群里每节点的 CPU DRAM（必要时 SSD）共同组成全局 KVCache 池，跨节点由 Messenger（GPUDirect RDMA）传输。这把传统本地 KVCache 缓存（如 vLLM 的 PagedAttention）从单节点扩展到全集群，并利用 GPU 服务器里长期闲置的邻居容量。
  • Conductor + cache-aware 调度（Algorithm 1）：对每请求按块哈希链（见 Prefix caching）算出在每个 prefill 实例可复用的前缀长度，估计 TTFT（本地够用则不传、否则从最佳实例拉差额并按传输后复用最佳前缀计算），选 TTFT 最短者；超过 SLO 直接 HTTP 429 拒绝；所选实例的 prefix 远低于全局最佳时，自动把热点缓存迁过来——这是 cache-aware + 负载均衡同时最优的解。
  • CPP（chunked pipeline parallelism）：长上下文 prefill 把每请求输入切成 $≤$ prefill_chunk 的块，不同块由不同节点流水线同时处理，跨节点通信只在 stage 边界传递 activation 且可与计算重叠。比跨节点 TP（每层 2 次 RDMA all-reduce）和 SP（每层至少 1 次跨节点通信）的 MFU（Model FLOPs Utilization）都高。
  • Layer-wise prefill：prefill 按层逐层进行，每层 KVCache 在该层 attention 算完后立即异步 store 到 CPU DRAM，下一层 KVCache 在上一层算时已异步载入。prefill 实例执行时间 $≈$ max(载入时间, 标准 prefill 时间)——调度只需考虑 DRAM 容量而无需考虑 VRAM。
  • 基于预测的早拒绝：当 GPU 供给受限出现过载时，朴素早拒绝按当前 decode 负载调度会引发 prefill/decode 反相震荡的四阶段循环；Mooncake 用系统级预测——假设每请求 decode 时长均匀 $t_d$，预测请求完成 prefill 时的 decode 负载，再决定是否接受。

关键结论与边界

  • PD 分离对长上下文场景显著有益：在 16k/32k/64k/128k 上下文模拟数据上，Mooncake 相比 vLLM 提升 50%–525% 吞吐；在真实 Kimi 回放负载下多处理约 75% 请求，且 TBT SLO 满足率 ~100%（vLLM 仅 57%）。该结论在 cache ratio > 0% 的多轮/系统提示词场景下成立。
  • cache-aware 调度的收益主要来自 cache 复用，不是单纯靠负载均衡：8 prefill + 8 decode 实例重放实验中，KVCache-centric 调度把平均 TTFT从 random 92.07s 降到 6.26s，把 cache-aware（14.36s）和 load-balancing（60.41s）也都优于随机；cache-aware 与 KVCache-centric 均满足 SLO 线。
  • 该设计针对在线 MaaS（Model as a Service，模型即服务）场景优化：长上下文为主、输入远超输出、多轮前缀复用、过载常态化。在短输入/低复用场景（如 ArXiv Summarization，cache ratio $≈$ 0%）Mooncake 仅比 vLLM 多 20% 吞吐——收益仍存在但不显著。所有实验基于回放 trace + dummy LLaMA2-70B 架构（论文保护商业信息）。
  • 本页面不展开：Transfer Engine / Messenger 的内部实现（RDMA 编程、拓扑探测——论文 v4 仅描述接口与位置）、同名开源仓库的组件生态（论文 §1 仅声明 trace 仓库地址，组件扩展不在本文范围）、异构加速器/PIM 等未来方向（论文 §10 提及）。这些是相关但独立的内容。
