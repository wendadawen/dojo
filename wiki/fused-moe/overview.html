FusedMoE

vLLM 的融合 MoE 算子：把一层里全部专家参与的矩阵乘合并成分块 GEMM 内核调用，调用次数不再随专家数增长。

更新于 2026-09-03

这是什么

MoE 层的 router 为每个 token 选出少数专家，剩下的计算是若干次"token 乘专家权重"的矩阵乘。朴素做法按专家循环，每个专家一次小 GEMM；FusedMoE 把这些矩阵乘组织成统一的分块 GEMM：先按专家把 token 槽位排序、填充到块边界，再一次内核调用算完全部专家的份额。本文以 vLLM v0.28.0 源码为参考实现。

为什么需要它

decode 批量小时，token 行被大量专家切得极稀：每个专家只分到零星一两行，小 GEMM 铺不满 GPU 的计算单元；内核启动次数随专家数线性增长；逐专家 gather/scatter 还带来额外数据搬运。把全部专家的 tile 放进同一个网格，三个来源同时消除。这一"按块组织 MoE 计算"的思路由 MoE 层与路由的稀疏性决定，思想先例是 MegaBlocks 的块稀疏表述。

核心机制

  • 槽位展开：把 $M\cdot k$ 个 (token, 专家选择) 对展开成槽位序列，作为计算的组织单位。
  • 分块对齐：moe_align_block_size 把槽位按专家排序、每段填充到 block_size 的倍数，产出 sorted_token_ids、expert_ids（每个块的专家号）与 num_tokens_post_padded（有效总长）三个数组；填充槽用掩码跳过，不会算错值。
  • 融合内核：fused_moe_kernel 的网格覆盖全部专家的 tile；每个 tile 由块号选定专家权重切片、由槽位编号定位 token 行（第一次 GEMM 中槽位除以 $k$ 还原 token 行，第二次直接作行号）。
  • 两次 GEMM 与激活：先乘 gate+up 拼接的 w13 得 $2I$ 维，门控激活收缩到 $I$ 维，再乘 w2 投影回 $H$ 维并在内核内乘路由权重，最后沿 top-k 求和。

关键结论与边界

  • 融合是重组计算而不是新算子语义：对同一输入，融合路径与逐专家循环的输出逐元素一致（完整说明页附纯 Python 双实现验证）。
  • "融合"的对象是全部专家的 GEMM；整层仍是路由、对齐、两次 GEMM、激活、求和多个内核接力，调用次数固定为个位数。
  • 它只负责单 rank 内的计算组织：专家并行的 dispatch/combine 通信由独立组件承担（内核对非本 rank 专家写零兜底），负载均衡属于 EPLB，量化路径复用同一内核框架。
  • 批量极小时（未启用专家并行且 $M\cdot k\times 4\le E$）跳过对齐直通计算，decode 单请求正落在这一档；tile 参数按形状从调优配置查找，不写死。
