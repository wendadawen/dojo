    FusedMoE：把全部专家的 GEMM 合并进一次内核调用

    主要依据：vLLM v0.28.0 源码（commit 2cf0a69，vllm/model_executor/layers/fused_moe/）；MegaBlocks 论文（Gale 等，arXiv:2211.15841）。

    设想一张有 256 个专家的 MoE 模型正在做 decode：批里只有 8 个 token，每个 token 由 router 挑出 8 个专家，一共 64 次"token 乘专家权重"的矩阵计算，散布在 256 份专家权重上，平均每份摊不到一行。如果按直觉把这一层写成"每个专家收集自己的 token、做一次矩阵乘、再把结果放回去"，这 64 次计算会变成上百个只处理一两行的小内核调用，GPU 的大量计算单元在等活。FusedMoE 是 vLLM 对这个问题的回答：先把 token 按专家排好队、对齐到块边界，再让一次分块 GEMM 内核调用覆盖所有专家的份额——w13 与 w2 两份权重各调用一次（每次内核都把全部专家的对应权重切片读进来），调用次数固定为个位数、不再随专家数增长。本文的学习目标包括：说明逐专家循环的浪费来源；手算分块对齐产生的三个数组；说明内核如何用这三个数组完成索引；走通一个 token 的完整前向；划清 FusedMoE 层的职责边界。

    本文讨论 vLLM 的融合 MoE 算子。它依赖两个前置概念：MoE 层的 router、top-k 路由与专家并行见 MoE 大模型推理与服务基础；GEMM 的 tile 划分与 GPU 内核执行模型见 GPU 执行模型与 kernel 调度。本文只使用这两个概念的结论，不重复推导。

    核心问题

    1. MoE 层的专家计算为什么不能靠"每个专家一次普通 GEMM"的循环来做？

      解答：三重浪费——小 GEMM 铺不满、调度边界多、数据搬运多

      逐专家循环把本该一起调度的计算切成 $E$ 份独立的小 GEMM：每份的 token 行数极少，tile 的行维利用率低、单个专家的 tile 数常常少于 SM 数；专家之间的活被内核边界隔开，启动次数随专家数线性增长；gather 与 scatter 还带来额外的数据搬运。decode 批量越小、专家数越多，三重浪费越大。融合路径把全部专家的 tile 放进同一个网格，三个来源同时消除。完整论证见「1. 朴素实现的问题」一章。

    2. moe_align_block_size 如何把"哪个槽位归哪个专家"编码成三个数组？

      解答：排序、按段填充到块边界、逐块登记专家号

      把 $M\cdot k$ 个 (token, 选择) 槽位按所属专家分段排序得到 sorted_token_ids；每个专家的段补齐到 block_size 的倍数，填充槽的值等于有效槽位数；每个块登记一个专家号得到 expert_ids；填充后的总长记入 num_tokens_post_padded。给定 topk_ids 与 block_size，三个数组可以逐步手算。机制与手算见「2. 按专家分块对齐」一章。

    3. fused_moe_kernel 如何用这三个数组算出正确的"token 乘对应专家权重"？

      解答：槽位除以 $k$ 还原 token 行，按块号偏移专家权重

      网格沿填充后的槽位维和输出维划分，每个 program 负责一个 tile；tile 的块号 $b$ 决定专家（expert_ids[$b$]，据此偏移 B 矩阵到该专家的权重切片），槽位编号除以 $k$ 还原 token 在输入矩阵中的行；填充槽与越界块用掩码和提前返回跳过。索引公式与手算见「3. 一次内核调用算完所有专家」一章。

    4. 一个 token 从进入 MoE 层到输出，完整经过哪些计算？

      解答：路由、对齐、两次 GEMM、门控激活、加权求和

      router 打分后经 topk_softmax 得到专家与路由权重（即门控权重，对应 topk_weights）；对齐产生三个索引数组；第一次 GEMM（gate 与 up 拼接的 w13）输出 $2I$ 维；门控激活 silu 乘 up 收缩到 $I$ 维；第二次 GEMM（w2）投影回 $H$ 维并在内核内乘路由权重；最后沿 top-k 求和。合成公式为 $y_t=\sum_j g_{t,j}\,W_2^{(e_{t,j})}(\operatorname{silu}(a_{t,j})\odot u_{t,j})$，其中 $g_{t,j}$ 为路由权重，$(a_{t,j},u_{t,j})$ 为 $W_{13}^{(e_{t,j})}x_t$ 的前后两半。数据流、张量形状与手算见「4. 一个 token 的完整路径」一章。

    5. FusedMoE 层在 vLLM 中管什么、不管什么？

      解答：管单 rank 内的专家计算组织，不管通信与负载均衡

      它承担路由执行、按 TP 切分存放专家权重（w13 列切、w2 行切）、组织融合内核计算；专家并行的 dispatch/combine 通信由独立组件承担（内核只对非本 rank 专家写零兜底），负载均衡属于 EPLB，权重量化由量化方法在同一个内核框架内扩展。批量极小时还有跳过对齐的低延迟路径。边界与依据见「5. FusedMoE 层的职责边界」一章。

    常见误解

    • "FusedMoE 把 router、GEMM 和求和全部融进一个内核"——融合的对象是"全部专家的 GEMM 合并为一次调用"：整层仍由路由、对齐、两次 GEMM、激活、求和多个内核接力完成，调用次数固定为个位数但不是 1。
    • "不丢 token 是因为没有填充"——每个专家段都补齐到 block_size 的倍数，填充槽位用掩码跳过；"不丢"指每个 (token, 专家) 对都被计算，与按容量截断丢弃 token 的路由方式相对。
    • "FusedMoE 包含专家并行的 all-to-all 通信"——它只负责本 rank 内的计算组织；跨 rank 的 dispatch/combine 通信由独立组件承担，内核对非本 rank 的专家写零兜底。
    • "BLOCK_SIZE_M 越小越好，可以少填充"——tile 尺寸影响张量核效率与 SM 占用，由调优配置按批量选取；填充浪费有上界 $E\times(B_M-1)$ 且被掩码，不进入输出。

    1. 朴素实现的问题——逐专家小 GEMM 喂不饱 GPU

    MoE 层把 Transformer 的前馈网络换成一组专家：router 为每个 token 对全体专家打分，选出 $k$ 个并给出路由权重（即 topk_weights，本页也称门控权重），token 的输出是这 $k$ 个专家输出的加权和；层结构、路由与稀疏激活的完整讲解见 MoE 大模型推理与服务基础。本页从路由结果出发：每个 token 已经拿到 $k$ 个 (专家, 权重) 对，剩下的问题是，这些"token 乘专家权重"的矩阵计算在 GPU 上怎么组织。

    最直接的写法是一个按专家的循环。以下伪代码展示其结构（展开本节要讨论的机制，省略数值细节）：

    代码：朴素逐专家循环的伪代码 
    输入：M 个 token 的隐藏态 x（每行 H 维）、topk_ids（M×k）、topk_weights（M×k）、
     专家权重 w13（E 份，每份 2I×H）、w2（E 份，每份 H×I）
输出：M 个 token 的层输出 y（每行 H 维）

    若 rows 为空：继续下一个专家
    X_e ← 按 rows 取出对应 token 的行                # gather：一次数据搬运
    G_e ← X_e × w13[e]                              # GEMM 1
    A_e ← silu(G_e 前半) 逐元素乘 G_e 后半           # 门控激活
    Y_e ← A_e × w2[e]                               # GEMM 2
    把 Y_e 乘门控权重后按行累加回 y                  # scatter：一次数据搬运

    这个循环在数学上完全正确，问题出在它交给 GPU 的任务形状上。浪费来自三个相互叠加的来源。

    第一个来源：小 GEMM 喂不满计算单元。GEMM 把输出矩阵切成 tile，由 SM 并行计算，tile 的行数（BLOCK_SIZE_M）是任务并行度与张量核效率的来源之一，见 GPU 执行模型与 kernel 调度。逐专家循环把 $M\cdot k$ 行切到 $E$ 个专家头上：开头场景里 64 行摊给 256 个专家，多数专家拿到零或一行。行数为一两行的矩阵乘退化成 GEMV，一个按 16 行设计的 tile 只装着 2 行有效数据，其余行的算力被白白烧掉；而且单个专家的那份 GEMM 的 tile 总数常常不足 SM 数量，调用期间部分 SM 从头到尾空闲——它们本可以去算别的专家的活，但那些活在下一个内核里。

    第二个来源：调度边界随专家数线性增多。循环体里每个专家要经历 gather、两次 GEMM、激活、scatter 多次内核启动，次数随 $E$ 线性增长；$E$ 为 256 时一个 MoE 层一次前向就要发起上千次调用。每次启动有固定的提交与同步开销，decode 每个 step、每层都要重复一遍。融合路径把这些步骤收敛为固定个位数次调用：路由一次、对齐一次、两次 GEMM、激活一次、求和一次，不再随专家数变化[C5, C13]。

    第三个来源：数据搬运。gather 先把散落的 token 行复制成每个专家自己的连续输入，scatter 再把各专家的结果写回原位；每个专家的中间结果也要先落到自己的缓冲再被读出。融合路径里 token 行不搬家——内核通过索引数组直接定位到原始 hidden_states 的行；中间结果按槽位写入一块统一缓冲，紧接着被第二次 GEMM 按同样的槽位读走。

    三个来源在 decode 批量小时同时出现：批量越小，行被专家切得越稀，浪费越明显；prefill 大批量时每个专家能分到成片的行，朴素实现的形状问题会缓解，调度与搬运开销仍在。这正是 MoE 推理"存得多、算得少"特性的另一面：激活的行数天生就少，组织方式必须适应稀疏。历史上，把 MoE 计算重新表述为分块/块稀疏运算、用定制 GPU 内核处理动态分组的思路由 MegaBlocks 系统化提出——当时的框架为迁就硬件约束，被迫在"丢弃 token"与"为填充浪费计算和内存"之间取舍，MegaBlocks 用块稀疏内核做到不丢 token[C16]，其训练端到端加速最高 40%（对比 Tutel）[N4]。vLLM 的融合算子走的是同一条路：按专家分组、以块为单位组织 GEMM，但用"块内掩码"而不是"容量截断"来处理不均匀。

    本章已经说明了浪费的来源：问题不在 GEMM 本身，而在组织方式。要消除它，需要先回答一个前置问题——分块 GEMM 的一个 tile 里，所有行必须乘同一个专家的权重切片，而 token 到专家的归属是动态的。下一章说明 vLLM 如何把这个动态归属预先编码成三个数组。

    本章问题

    1. 朴素逐专家循环的三个浪费来源分别是什么？各自与 GPU 执行模型的哪个事实相关？

      解答：形状退化、调度边界、数据搬运

      来源一是形状退化：行数被切到每个专家头上后极少，tile 行维利用率低，且单个专家 GEMM 的 tile 数常少于 SM 数，调用期间部分 SM 空闲——对应"GEMM 按 tile 由 SM 并行计算"的事实。来源二是调度边界：每个专家多次内核启动，次数随 $E$ 线性增长，启动开销串行累积——对应"内核启动有固定开销"的事实。来源三是数据搬运：gather/scatter 与逐专家中间缓冲带来额外访存——token 行本可以直接由索引定位。三者叠加，decode 批量越小浪费越大。

    2. 为什么 decode 批量小时浪费被放大，prefill 大批量时相对不严重？

      解答：行的稀疏程度由"行数除以专家数"决定

      每个专家平均分到 $M\cdot k/E$ 行。decode 时 $M$ 小（如 8），$M\cdot k/E$ 远小于 1，多数专家拿到零或一行，tile 严重空转；prefill 时 $M$ 可达数千，每专家分到成片行，单个 GEMM 形状恢复正常，形状退化基本消失。但调度边界与数据搬运两个来源只与组织方式相关，批量再大也仍在——所以融合在两种阶段都受益，只是 decode 收益更极端。

    softmax 打分与 top-k 选择的机制属于路由话题，见 MoE 大模型推理与服务基础；本页从这份结果出发。手算三个数组分三步：

    第一步，展开槽位并数出每个专家的段长。槽位 $s=t\cdot k+j$ 依次为：$s_0$($t_0$,$e_0$)、$s_1$($t_0$,$e_1$)、$s_2$($t_1$,$e_1$)、$s_3$($t_1$,$e_3$)、$s_4$($t_2$,$e_0$)、$s_5$($t_2$,$e_3$)、$s_6$($t_3$,$e_1$)、$s_7$($t_3$,$e_2$)。按专家归堆：$e_0$ 得 $s_0,s_4$（2 个），$e_1$ 得 $s_1,s_2,s_6$（3 个），$e_2$ 得 $s_7$（1 个），$e_3$ 得 $s_3,s_5$（2 个）。

    第二步，每段补齐到 $B_M=2$ 的倍数：$e_1$ 补 1 个槽、$e_2$ 补 1 个槽，总长从 8 变为 10。填充槽的值一律用有效槽位数 8——任何不小于 8 的编号都不对应真实槽位，内核据此识别并屏蔽[C3]。

    第三步，按专家序拼接并逐块登记专家号。排序后的槽位序列是

    sorted_token_ids $=[\,0,\,4\,|\,1,\,2,\,6,\,\text{pad}\,|\,7,\,\text{pad}\,|\,3,\,5\,]$，共 10 个有效槽；5 个块的专家号依次为 expert_ids $=[0,1,1,2,3]$；num_tokens_post_padded $=10$。

    为什么必须填充？分块 GEMM 里，一个 tile 的 B 矩阵地址按块号一次性给出：内核读一次 expert_ids[$b$]，把 B 偏移到该专家的权重切片，整个 tile 都用这一份权重[C8]。如果某个块横跨两个专家的段，后一段的行就会乘错权重。排序让同专家的槽位连续，填充把每段长度补成 block_size 的倍数，块边界于是永远不会切开一个专家段——这正是内核文档对"排序与填充保证可被 BLOCK_SIZE_M 整除"的表述[C4]。

    填充的规模有上界。分配 sorted_token_ids 时按最坏情况预留：

    $$\text{max\_num\_tokens\_padded} \;=\; M\cdot k \;+\; E\times(B_M-1)$$

    其中 $B_M$ 是 block_size[F1]。每个专家的段长向上取整到 $B_M$ 的倍数，最坏时每段多出 $B_M-1$ 个槽。当槽位总数小于专家数时，实现会把分配长度截断到 $M\cdot k imes B_M$ 与该上界的较小值，以省下空段占用的空间；两种情形下有效内容的语义不变。

    补充：为什么每个专家最多只多补 $B_M-1$ 个槽

    设某专家分到 $c$ 个槽，补齐后的段长是 $\lceil c/B_M\rceil\cdot B_M$。把 $c$ 写成 $c=q\cdot B_M+r$（$0\le r<B_M$）：$r=0$ 时不需要补；$r>0$ 时补 $B_M-r$ 个，最多 $B_M-1$ 个。$E$ 个专家的填充量逐个不超过 $B_M-1$，相加得到上界。构造示例 A 里 $e_1$ 补 1 个、$e_2$ 补 1 个，共 2 个，小于上界 $4\times(2-1)=4$。

    三个数组就是第 1 章想要的"预编码的分组信息"：动态的归属变成静态的布局。但数组只是索引，真正的计算发生在 GEMM 内核里——下一章说明内核如何拿这三个数组，把"正确的 token 行"乘上"正确的专家权重"。

    本章问题

    1. 三个数组各存什么？分别被谁消费？

      解答：槽位布局、块到专家的映射、有效长度

      sorted_token_ids 存按专家分段排序并填充后的槽位序列，内核用它定位 A 的行与输出的写入位置；expert_ids 存每个块的专家编号，内核用它把 B 偏移到对应专家的权重切片；num_tokens_post_padded 存填充后的有效总槽数，内核用它让越界块提前返回。三者都由 moe_align_block_size 产生、由 fused_moe_kernel 消费。

    2. 给定 topk_ids 与 block_size，如何手算三个数组？

      解答：数段长、补齐到块边界、拼接登记

      三步：把 topk_ids 展开成 $M\cdot k$ 个槽位并按专家归堆，得到每段的槽位集合；把每段长度向上取整到 block_size 的倍数，不足处补入值为"有效槽位数"的填充槽；按专家序拼接得到 sorted_token_ids，每 block_size 个槽为一组登记专家号得到 expert_ids，总长记入 num_tokens_post_padded。以构造示例 A（$M=4$、$E=4$、$k=2$、$B_M=2$）为例，结果为 $[0,4,1,2,6,8,7,8,3,5]$、$[0,1,1,2,3]$、$10$。

    3. 为什么每个专家的段必须填充到 block_size 的倍数？

      解答：块的权重偏移是整块共享的常数

      内核为每个块读一次 expert_ids[$b$] 并据此偏移 B，块内所有行共用这一份权重切片。若块边界切开两个专家的段，段尾的行会乘上错误专家的权重。填充把每段长度变成 block_size 的倍数，保证任何完整的块都落在单一专家的段内；代价是最多 $E\times(B_M-1)$ 个填充槽，它们被掩码跳过，不影响输出。

    3. 一次内核调用算完所有专家——fused_moe_kernel 的索引方式

    vLLM 的融合 MoE 计算由 Triton 内核 fused_moe_kernel 完成[C1]。它的矩阵语义：输入 $A$ 是形状 $(*, K)$ 的 token 矩阵，$B$ 是形状 $(E, N, K)$ 的堆叠专家权重，输出 $C$ 形状 $(M, k, N)$；一次调用覆盖全部专家[C2]。理解它只需要"一个 program 负责一个 tile"的执行模型（见 GPU 执行模型与 kernel 调度）。

    网格沿两个维度展开：$\lceil EM/B_M\rceil\times\lceil N/B_N\rceil$，其中 $EM$ 取 sorted_token_ids 的分配长度（按 F1 上界预留，示例 A 为 12），$N$ 是本次 GEMM 的输出宽度[C7]。每个 program 负责一个 $(B_M, B_N)$ 的输出 tile；网格里相邻的 M 块按 GROUP_SIZE_M 分组排列，让同组的 program 尽量同时在跑，以提高权重 tile 在 L2 中的复用[C7]。$B_M$ 的取值由配置决定，默认随批量增大从 16 到 128[N1]。请注意 $EM$ 是分配长度而非 num_tokens_post_padded：构造示例 A 中前者 12、后者 10，网格据此覆盖 6 个 M 块，末尾块因超出有效长度被前序检查直接返回。

    program 内部的索引是本页的核心机制。对第 $b$ 个块（专家 $e=\text{expert\_ids}[b]$）中的第 $r$ 行，令槽位 $s=\text{sorted\_token\_ids}[b\cdot B_M+r]$，该 program 计算的输出元素是

    $$C[s,\,n]\;=\;\sum_{q=0}^{K-1} A\big[\,\lfloor s/k\rfloor,\;q\,\big]\cdot B[e,\,n,\,q]$$

    各符号与职责[C8, F2]：

    • $s$：槽位编号，来自 sorted_token_ids；它同时是 $C$ 的写入位置（按槽位展开的 $(M\cdot k, N)$ 视图）。
    • $\lfloor s/k\rfloor$：槽位整除 $k$ 还原 token 行号。第一次 GEMM 中 $A$ 是 $M\times H$ 的 hidden_states，必须除回原行；第二次 GEMM 中 $A$ 换成 $M\cdot k$ 行的中间缓存、$k$ 参数传 1，$s$ 直接就是行号。
    • $e$：块号查 expert_ids 得到的专家编号；$B$ 的地址加上 $e\times\text{stride}_{be}$ 就偏移到该专家的权重切片，整块共用。
    • $B[e,n,q]$：专家 $e$ 权重第 $n$ 行第 $q$ 列；$K$ 是本次 GEMM 的输入宽度（第一次为 $H$，第二次为 $I$）。

    用构造示例 A 手算一个块。取块 1：$b=1$，$e=\text{expert\_ids}[1]=1$，块内槽位 $s_1, s_2$，对应 token $\lfloor 1/2\rfloor=t_0$、$\lfloor 2/2\rfloor=t_1$。第一次 GEMM 里这个 program 要算的是 $t_0$、$t_1$ 两行各乘 $w_{13}[e_1]$。输入取 $t_0=(1,0)$、$t_1=(0,1)$（构造值，下一章给出完整权重），$w_{13}[e_1]$ 的 gate 行为 $(1,0)$、$(0,1)$，up 行为 $(1,1)$、$(1,0)$，于是

    $$C[s_1] = t_0\times w_{13}[e_1] = (1,\,0,\,1,\,1),\qquad C[s_2] = t_1\times w_{13}[e_1] = (0,\,1,\,1,\,0),$$

    两行乘的是同一个专家的权重，块号 $b=1$ 决定了这一点；槽位 $s_1,s_2$ 决定了结果写回哪里、输入行从哪里取。

    内核对无效位置有三处防御[C9]。其一，整块越界：块的起始位置不小于 num_tokens_post_padded 时 program 直接返回——构造示例 A 的分配长度是 12、有效长度是 10，网格会覆盖 6 个块，第 5 号块（槽位 10、11）启动后立即退出，右侧两个虚线槽从不被读取。其二，读掩码：填充槽的编号是 8，不小于有效槽位数 8，掩码 $s<8$ 为假，$A$ 的该行读入 0。其三，写掩码：输出只写掩码内的槽位，填充槽不产生写入。三处合起来，填充只浪费一点行宽，不会算错任何值。

    两次 GEMM 复用同一个内核，索引方式只有输入与参数不同：

    $A$（输入矩阵）$k$ 参数$B$（权重）输出乘路由权重
    第一次hidden_states，$(M, H)$$k$w13，$(E, 2I, H)$cache1，$(M\cdot k, 2I)$否
    第二次cache2（激活结果），$(M\cdot k, I)$1w2，$(E, H, I)$cache3，$(M\cdot k, H)$是，fp32

    两栏"乘路由权重"的取舍由参数 apply_router_weight_on_input 决定：默认 False 时权重在 GEMM2 乘入；某些模型置 True，把权重乘到 hidden_states 的输入侧再传入，两栏对调[C6]。

    专家并行时还有一个配合动作：对齐阶段会先按全局专家数对齐所有槽位，返回前把不在当前 rank 的专家在 expert_ids 里标成 $-1$；内核遇到 $-1$ 时不做乘法，直接把该块输出写零[C10]。这样每张卡都能独立跑完整个对齐序列，非本 rank 的块贡献零值，通信与合并由上层组件另行处理——边界细节见「5. FusedMoE 层的职责边界」一章。

    索引机制已经就位：块号选权重、槽位选行、掩码挡填充。但一个 token 的输出要经过两次 GEMM、一次激活、一次加权求和才最终成形。下一章把全部步骤串起来，并用构造示例 A 算出真实数值。

    本章问题

    1. 网格如何划分？一个 program 负责哪块输出？

      解答：块维与输出维两个方向上取整相乘

      网格大小为 $\lceil EM/B_M\rceil\times\lceil N/B_N\rceil$：$EM$ 取 sorted_token_ids 的分配长度（按 F1 上界预留，示例 A 为 12），沿它切出的每个 M 块由 expert_ids 指定专家；$N$ 是本次 GEMM 的输出宽度，沿它切成若干列块。一个 program 负责一个 $(B_M,B_N)$ 的输出 tile。相邻 M 块按 GROUP_SIZE_M 分组排列以提高 L2 复用。越界的块（起始位置不小于 num_tokens_post_padded）启动后直接返回。

    2. 为什么第一次 GEMM 要把槽位除以 $k$，第二次不用？

      解答：两次的 $A$ 行含义不同

      第一次的 $A$ 是 hidden_states，只有 $M$ 行，槽位必须整除 $k$ 才能还原 token 行号；第二次的 $A$ 是激活后的中间缓存，本身就是 $M\cdot k$ 行、按槽位排列，$k$ 参数传 1 后 $s\div 1=s$，槽位就是行号。输出侧两次都按槽位写入（cache1 与 cache3 都按 $(M\cdot k, \cdot)$ 组织），所以两次 GEMM 可以共用同一套 sorted_token_ids 与 expert_ids。

    3. 填充槽与越界块如何保证不产生错误输出？

      解答：掩码读零、掩码不写、整块提前返回

      填充槽的值等于有效槽位数，掩码 $s<\text{num\_valid}$ 为假：读 $A$ 时该行取 0，写 $C$ 时该槽被屏蔽，即使参与乘法也只影响被丢弃的结果。越界块的起始位置不小于 num_tokens_post_padded，program 在读取任何数据前直接返回。因此填充最多浪费行宽，不会污染任何有效槽位的输出。

    4. 一个 token 的完整路径——从 router 到加权求和

    把前两章的机制接进完整前向。融合算子的入口 fused_experts 接收 hidden_states、两份权重与路由结果（topk_weights、topk_ids）——路由在入口之前已经完成，其结果作为入参传入；入口内部按固定顺序执行五步[C5]。下图从路由开始展示整层数据流，共六个节点，后五个方块对应入口内的五步：

    路由这一步：gate 线性层输出每个 token 对 $E$ 个专家的分数，融合内核 topk_softmax 一次完成 softmax 与 top-k 选择，产出 topk_weights 与 topk_ids，不再分开调用 softmax、排序、取前 $k$[C13]。专家分配对齐即第 2 章的三个数组。

    两份权重的形状与命名沿自 Mixtral 的 w1/w2/w3 约定：w13 是 gate 与 up 两份投影沿输出维拼接的结果，形状 $(E,\,2I,\,H)$，gate 在前、up 在后；w2 是 down 投影，形状 $(E,\,H,\,I)$[C12]。因此 GEMM1 的输出是 $2I$ 维（gate 半与 up 半各 $I$ 维），门控激活 silu_and_mul 把 gate 半过 silu 后与 up 半逐元素相乘，$(\cdot, 2I)$ 收缩为 $(\cdot, I)$；这一步的激活语义即 SwiGLU 家族的门控乘，见 SwiGLU 门控激活。GEMM2 把 $I$ 维投影回 $H$ 维，并在内核内、以 fp32 精度乘上路由权重[C6]；最后 moe_sum 把 $(M, k, H)$ 沿 $k$ 维相加，得到每个 token 的输出。实现上 cache1 与 cache3 共享同一块缓冲——用到 cache3 时 cache1 已消费完毕[C15]。

    整条路径对单个 token 的语义可以合成一个公式。设 token $t$ 的输入为 $x_t$，其第 $j$ 个选择的专家为 $e_{t,j}$、路由权重为 $g_{t,j}$，则

    $$y_t\;=\;\sum_{j=1}^{k}\; g_{t,j}\cdot W_2^{(e_{t,j})}\Big(\operatorname{silu}(a_{t,j})\odot u_{t,j}\Big),\qquad (a_{t,j},\,u_{t,j})\,=\,W_{13}^{(e_{t,j})}x_t\text{ 拆为前 }I\text{ 维与后 }I\text{ 维}$$

    其中 $W_{13}^{(e)}$ 取专家 $e$ 的 gate+up 权重（输出 $2I$ 维，$a$ 为 gate 半、$u$ 为 up 半），$W_2^{(e)}$ 取其 down 权重，$\odot$ 为逐元素乘[C6, F3]。这就是"加权求和的 MoE 输出"在融合路径里的落点：加权和不是先算完再乘权重，而是权重在 GEMM2 内乘进每个槽位、求和只做纯加法。

    用构造示例 A 走通 $t_0$。输入 $x_{t_0}=(1,0)$，路由给 ($e_0$, 0.6) 与 ($e_1$, 0.4)，权重取下表构造值：

    专家w13（gate 两行、up 两行）w2
    $e_0$gate $(2,1),(0,1)$；up $(1,1),(1,0)$$(1,0),(0,1)$
    $e_1$gate $(1,0),(0,1)$；up $(1,1),(1,0)$$(1,1),(0,1)$
    $e_2$gate $(1,2),(1,1)$；up $(0,1),(1,1)$$(1,0),(1,1)$

    $t_0$ 的两个槽位是 $s_0$（$e_0$）与 $s_1$（$e_1$）。逐级计算：

    • GEMM1：$C[s_0]=x_{t_0}\times w_{13}[e_0]=(2,\,0,\,1,\,1)$，即 gate 半 $(2,0)$、up 半 $(1,1)$；$C[s_1]=x_{t_0}\times w_{13}[e_1]=(1,\,0,\,1,\,1)$，gate 半 $(1,0)$、up 半 $(1,1)$。
    • 门控激活：$\operatorname{silu}(2)\approx 1.7616$、$\operatorname{silu}(1)\approx 0.7311$、$\operatorname{silu}(0)=0$，得 cache2$[s_0]=(1.7616,\,0)$、cache2$[s_1]=(0.7311,\,0)$。
    • GEMM2 与权重：$w_2[e_0]$ 是单位阵，cache3$[s_0]=(1.7616,\,0)\times 0.6=(1.0570,\,0)$；$w_2[e_1]$ 给出 $(0.7311,\,0)$，乘 0.4 得 cache3$[s_1]=(0.2924,\,0)$。

    以下代码把两条路径写成可运行程序：moe_naive 是第 1 章的逐专家循环（按合成公式直接累加），moe_fused 复刻融合路径——先构造三个数组，再按块循环、逐槽掩码、在 GEMM2 内乘权重、最后沿 top-k 求和。两条路径的输出应逐元素一致，这正是"融合只是重组计算、不改变数学"的机械验证：

    代码：朴素实现与融合实现的等价性验证（纯 Python，无第三方依赖） 
    import math

# ---- 构造输入：4 个 token、4 个专家、top-2、块大小 2（全部数字为构造值） ----
M, E, TOPK, BLOCK = 4, 4, 2, 2
H, I = 2, 2                                    # 隐藏维 H，中间维 I
x = [[1.0, 0.0], [0.0, 1.0], [1.0, 1.0], [2.0, 0.0]]      # token 输入
w13 = [                                        # (E, 2I, H)：前 I 行 gate，后 I 行 up
    [[2, 1], [0, 1], [1, 1], [1, 0]],
    [[1, 0], [0, 1], [1, 1], [1, 0]],
    [[1, 2], [1, 1], [0, 1], [1, 1]],
    [[0, 1], [2, 0], [1, 1], [0, 2]],
]
w2 = [                                         # (E, H, I)：down 投影
    [[1, 0], [0, 1]],
    [[1, 1], [0, 1]],
    [[1, 0], [1, 1]],
    [[0, 1], [1, 0]],
]
topk_ids     = [[0, 1], [1, 3], [0, 3], [1, 2]]
topk_weights = [[0.6, 0.4], [0.5, 0.5], [0.7, 0.3], [0.8, 0.2]]
NUM_VALID = M * TOPK                           # 有效槽位数 = 8


def silu(v):
    return v / (1.0 + math.exp(-v))


def matvec(W, v):                              # W: (out, in)
    return [sum(W[n][k] * v[k] for k in range(len(v))) for n in range(len(W))]


# ---- 朴素参考实现：逐 token 逐选择，gather-GEMM-加回 ----
def moe_naive():
    out = [[0.0] * H for _ in range(M)]
    for t in range(M):
        for j in range(TOPK):
            e = topk_ids[t][j]
            gu = matvec(w13[e], x[t])                          # gate+up
            inter = [silu(gu[d]) * gu[I + d] for d in range(I)]  # 门控激活
            y_e = matvec(w2[e], inter)                         # down 投影
            for h in range(H):
                out[t][h] += topk_weights[t][j] * y_e[h]       # 加权累加
    return out


# ---- 对齐：构造 sorted_token_ids / expert_ids / num_tokens_post_padded ----
def moe_align(topk_ids, block, E):
    counts = [0] * E
    for row in topk_ids:
        for e in row:
            counts[e] += 1
    seg, acc = [0] * E, 0                      # 各专家段的起始偏移（对齐后）
    for e in range(E):
        seg[e] = acc
        acc += (counts[e] + block - 1) // block * block
    max_len = NUM_VALID + E * (block - 1)      # 分配上界
    sorted_ids = [NUM_VALID] * max_len         # 填充值 = num_valid
    fill = seg[:]
    for s in range(NUM_VALID):                 # 槽位按专家归位
        t, j = divmod(s, TOPK)
        e = topk_ids[t][j]
        sorted_ids[fill[e]] = s
        fill[e] += 1
    post = 0                                   # 填充后有效总长
    for e in range(E):
        if counts[e]:
            post = seg[e] + (counts[e] + block - 1) // block * block
    expert_ids = []
    for b in range((max_len + block - 1) // block):
        if b * block >= post:                  # 越界块：内核提前返回
            break
        base = b * block
        for e in range(E):
            end = seg[e] + (counts[e] + block - 1) // block * block
            if seg[e] <= base < end:
                expert_ids.append(e)
                break
    return sorted_ids, expert_ids, post, max_len


# ---- 融合路径：按块复刻 fused_moe_kernel 的索引方式 ----
def moe_fused():
    N1 = 2 * I
    cache1 = [[0.0] * N1 for _ in range(NUM_VALID)]   # (M*topk, 2I)
    cache2 = [[0.0] * I for _ in range(NUM_VALID)]    # (M*topk, I)
    cache3 = [[0.0] * H for _ in range(NUM_VALID)]    # (M*topk, H)
    sorted_ids, expert_ids, post, max_len = moe_align(topk_ids, BLOCK, E)

    # GEMM1：A 行 = 槽位 // TOPK 还原 token，B = w13[expert_ids[b]]，不乘权重
    for b, e in enumerate(expert_ids):
        for r in range(BLOCK):
            s = sorted_ids[b * BLOCK + r]
            if s >= NUM_VALID:                 # 填充槽：掩码跳过
                continue
            cache1[s] = matvec(w13[e], x[s // TOPK])

    # 激活：silu(gate) 逐元素乘 up
    for s in range(NUM_VALID):
        g, u = cache1[s][:I], cache1[s][I:]
        cache2[s] = [silu(g[d]) * u[d] for d in range(I)]

    # GEMM2：A 行 = 槽位本身（top_k=1），乘路由权重
    for b, e in enumerate(expert_ids):
        for r in range(BLOCK):
            s = sorted_ids[b * BLOCK + r]
            if s >= NUM_VALID:
                continue
            t, j = divmod(s, TOPK)
            y_e = matvec(w2[e], cache2[s])
            cache3[s] = [topk_weights[t][j] * v for v in y_e]

    # moe_sum：沿 topk 维求和
    out = [[0.0] * H for _ in range(M)]
    for s in range(NUM_VALID):
        t, _ = divmod(s, TOPK)
        for h in range(H):
            out[t][h] += cache3[s][h]
    return out, sorted_ids, expert_ids, post, max_len, cache1, cache2, cache3

    本章问题

    1. 五步数据流中各步的张量形状如何变化？为什么 GEMM1 输出 $2I$ 维、激活后变 $I$ 维？

      形状序列：hidden_states $(M, H) \to$ 路由结果 $(M, k)$ 与三数组 $\to$ cache1 $(M\cdot k, 2I) \to$ cache2 $(M\cdot k, I) \to$ cache3 $(M\cdot k, H) \to$ 输出 $(M, H)$。GEMM1 乘的 w13 是 gate 与 up 两份投影沿输出维的拼接（gate 在前 up 在后），所以输出 $2I$ 维；门控激活 silu_and_mul 对 gate 半过 silu 后与 up 半逐元素相乘，两半合成一份 $I$ 维；GEMM2 乘 w2 把 $I$ 维投影回 $H$ 维。

    2. 用构造示例 A 的数字，$t_0$ 的输出怎么一步步算出来？

      解答：两条支路各自过三步，再相加

      $x_{t_0}=(1,0)$，槽位 $s_0$（$e_0$, 0.6）与 $s_1$（$e_1$, 0.4）。支路 $s_0$：GEMM1 得 $(2,0,1,1)$（gate $(2,0)$、up $(1,1)$）；激活得 $(\operatorname{silu}(2)\cdot 1,\ \operatorname{silu}(0)\cdot 1)=(1.7616, 0)$；GEMM2 过单位阵 $w_2[e_0]$ 后乘 0.6 得 $(1.0570, 0)$。支路 $s_1$ 同法得 $(0.2924, 0)$。求和得 $y_{t_0}=(1.3494, 0)$。其余 token 见展开折叠块或运行代码复算。

    5. FusedMoE 层的职责边界——它管什么、不管什么

    机制之上是工程组织。在 vLLM 中，模型代码不直接调用内核，而是使用 MoE 层：早期版本（如 v0.10.2）是一个 FusedMoE 模块类；v0.28.0 改为由 FusedMoEFactory 组装三件套——Router 负责 token 到专家的分配（含 topk_softmax 等路由内核）、RoutedExperts 持有全部专家权重、MoERunner 编排前向[C12]。权重的并行切分沿用张量并行的标准做法：w13 是列切（MergedColumnParallel，各 rank 持有输出维的一段），w2 是行切（RowParallelLinear，各 rank 持有输入维的一段），两者配合使每层只需一次归约，见 模型并行。

    把本章的问题列成一张职责表：

    职责归属与融合算子的关系
    单 rank 内专家计算的组织FusedMoE（本文主题）对齐 + 两次 GEMM + 激活 + 求和
    路由打分与 top-k 选择Router（层内）产出 topk_ids 与 topk_weights；分组 top-k、sigmoid 打分等变体属模型结构话题
    TP 下专家权重切分RoutedExpertsw13 列切、w2 行切，切分后各 rank 独立跑融合内核
    EP 的 dispatch/combine 通信独立通信组件不属于 FusedMoE；内核只对非本 rank 专家写零兜底[C10]
    专家负载均衡EPLB调整专家摆放与冗余复制，见 EPLB 专家并行负载均衡
    权重量化与反量化量化方法层fp8、int4 等路径复用同一内核框架，在内核内做反量化；细节超出本页
    内核参数调优调优配置按 (专家数, 输出宽, 设备, 精度) 查 JSON 取 BLOCK_SIZE 等参数，未命中用默认阶梯[C11]

    专家并行值得单独说清。EP 模式下不同专家放在不同 rank，token 需要被送往持有其专家的卡、算完再送回——dispatch 与 combine 通信由独立的组件承担，其机制见 MoE 大模型推理与服务基础。融合算子在其中的角色是"每张卡各自把自己的那份算完"：对齐阶段按全局专家数对齐，expert_ids 里非本 rank 的专家标 $-1$，内核对这类块写零输出[C10]——零值不干扰后续合并。也就是说，第 2、3 章的机制在 EP 下原样运转，只是有效计算集中在属于本 rank 的块上。

    两个工程细节补全边界。其一，tile 参数不是写死的：内核启动前按专家数、输出宽度、设备与精度查找调优 JSON，取最接近当前批量的档位；查不到时用默认阶梯（如 bf16 路径 $B_M$ 从 16 到 128 随批量增大）并告警[C11, N1]。其二，极小批量有专门路径：在未启用专家并行（expert_map 为空）且 $M\cdot k\times 4$ 不超过全局专家数时，排序填充本身的开销都不划算，vLLM 跳过 moe_align_block_size，让每个块只装一个有效槽位直通计算[C14, N3]——decode 单请求场景（$M=1$）正落在这一档。

    最后是版本与生态边界。本页全部机制以 vLLM v0.28.0 的 Triton 未量化路径为基准描述；量化路径与 DeepGEMM、CUTLASS 等其他后端复用或替代同一套数据流，但内核内部实现不同，本页结论不直接迁移。SGLang 等系统有机制相近的融合 MoE 实现，亦不在本页核对范围内。

    本章问题

    1. FusedMoE 层由什么组成？TP 下专家权重怎么切？

      解答：Router、RoutedExperts、MoERunner 三件套；w13 列切 w2 行切

      v0.28.0 中 FusedMoEFactory 组装 Router（token 到专家分配，含路由内核）、RoutedExperts（专家权重）与 MoERunner（前向编排）；早期版本是单个 FusedMoE 模块类。TP 下 w13 沿输出维列切、w2 沿输入维行切，各 rank 对本地分片独立执行融合内核，配合标准的列切加行切归约结构。

    2. EP 通信为什么不属于 FusedMoE？内核如何配合 EP？

      解答：通信由独立组件承担，内核写零兜底

      FusedMoE 的语义边界是单 rank 内的计算组织：把本 rank 持有的 (token, 专家) 对算成分块 GEMM。跨 rank 的 dispatch/combine 由独立的通信组件承担。配合方式是对齐阶段按全局专家数处理所有槽位、把非本 rank 的专家在 expert_ids 标为 $-1$，内核对 $-1$ 块写零输出，零值不干扰上层合并。

    3. 批量极小时走什么特殊路径？为什么合理？

      解答：$M\cdot k\times 4\le E$ 时跳过对齐，逐槽直通

      当槽位数远小于专家数（vLLM 取四倍裕量判断）时，绝大多数专家一个槽都没有，排序与填充的准备工作比计算本身还重。此路径跳过 moe_align_block_size，sorted_token_ids 传空、每个块只装一个有效槽位，其余位置屏蔽。GEMM 语义不变，省掉的是对齐内核的启动与执行。decode 单请求（$M=1$）正落在这档。
