# FusedMoE 文章大纲

## 1. 页面开头

- 具体场景开头：一张 256 专家的 MoE 模型在 decode，批里 8 个 token、每个选 8 个专家——64 次 (token, 专家) 乘法散布在 256 个专家上，平均每个专家不足 1 行。按"每个专家一次 GEMM"的直觉组织，这 64 次乘法变成几十上百个小内核调用。
- 概念简要解释：FusedMoE 把这些乘法合并成分块 GEMM：先按专家排序对齐，再一次内核调用算完所有专家的份额。
- 来源摘要 blockquote：vLLM v0.28.0 源码 + MegaBlocks 论文。
- 学习目标（见 scope.md Q1–Q5）。
- 常见误解块（开头放置 4 条，来自 scope.md 第 7 节）。
- 过渡：先看朴素做法到底浪费在哪。

## 2. 章节设计

### 第 1 章 朴素实现的问题——逐专家小 GEMM 喂不饱 GPU（Q1）

- 章节问题：①朴素逐专家循环每步做什么、浪费来自哪里？②decode 批量下为什么浪费被放大？
- 完成答案要点：①对每个专家 gather 属于它的 token 行 → 两次小 GEMM + 激活 → scatter 加权回原位；浪费来自小 GEMM 形状（M 极小）、内核启动次数（随专家数与步骤数线性）、gather/scatter 额外访存。②decode 批量小时 (token,专家) 对数远小于专家数，多数专家拿到 0–2 行，GEMM 退化成 GEMV，SM 大量空闲；引用 N1 说明 tile 尺寸的意义。MegaBlocks 的 drop-vs-pad 权衡作为历史动机（C16、N4）。
- 正文要点：朴素实现的伪代码（折叠块）；浪费的三个来源逐一说明；"问题不在 GEMM 本身而在组织方式"的过渡结论。
- 表达材料：伪代码折叠块（朴素循环）；构造数字（8 token×8 专家/256）。
- 前置知识安排：MoE 层与 top-k 路由（moe-serving 链接）、GEMM tile 与 SM（gpu-execution-model 链接）在章首引用。
- 范围：C16、N4；构造示例 A（路由结果的构造数字）首次定义。

### 第 2 章 按专家分块对齐——moe_align_block_size 的三个数组（Q2）

- 章节问题：①三个数组各存什么？②给定 topk_ids 与 block_size 如何手算出它们？③为什么必须把每个专家的段填充到 block_size 的倍数？
- 完成答案要点：①sorted_token_ids=按专家排序的槽位序列（含填充）、expert_ids=每个 block 的专家、num_tokens_post_padded=有效总长。②构造示例 A 手算：T=4、E=4、topk=2、block=2 → 排序、逐专家补齐、读出三数组。③一个 tile 里所有行必须乘同一专家的权重切片，B 的偏移按 tile 常数给出；不填充就会出现跨专家的 tile（C4）。
- 正文要点：槽位（token×topk 展开）的定义；三数组语义表；填充上界 F1；padding 值 = num_valid 与掩码跳过（C3）。
- 表达材料：SVG 条带图（10 个槽按专家分段、填充槽高亮、block 分界）；三数组语义表；构造示例 A 的手算（正文给关键步骤，完整逐槽演算进折叠块）。
- 前置知识安排：无新增。
- 范围：C3、C4、F1；构造示例 A 展开。

### 第 3 章 一次内核调用算完所有专家——fused_moe_kernel 的索引方式（Q3）

- 章节问题：①网格怎么划、一个 program 算哪块？②怎么保证乘的是"这个 tile 的 token × 这个专家的权重"？③填充槽和无效块怎么不产生错误输出？
- 完成答案要点：①grid = cdiv(EM,BM)×cdiv(N,BN)，GROUP_SIZE_M 分组促 L2 复用（C7）。②A 行 = sorted_token_ids[j]//top_k（GEMM1；GEMM2 中 top_k=1 直通行号），B 偏移 = expert_ids[b]×stride_be，输出按槽位写回（F2、C8）。③token_mask 屏蔽填充槽的读写；超出 num_tokens_post_padded 的块提前返回（C9）；EP 下 -1 专家写零（C10，指向第 5 章）。
- 正文要点：从"tile 内单专家"到指针公式的推导；GEMM1 与 GEMM2 索引差异对照表；掩码三处（读 A、写 C、提前返回）。
- 表达材料：F2 公式及符号表；GEMM1/GEMM2 索引对照表；构造示例 A 的一个 tile 手算（block b=1，专家 e1 的 [s1,s2] 两行 × w13[1]）。
- 前置知识安排：GEMM 分块计算复用 gpu-execution-model。
- 范围：C7、C8、C9、C10（简）、F2。

### 第 4 章 一个 token 的完整路径——从 router 到加权求和（Q4）

- 章节问题：①完整数据流按序是哪几步、各步张量形状如何变化？②给定构造示例 A 的权重与输入，t0 的输出怎么算出来？
- 完成答案要点：①router 打分 → topk_softmax 得 topk_weights/topk_ids（C13）→ 对齐 → GEMM1(w13) → silu_and_mul → GEMM2(w2, 乘路由权重) → moe_sum（C5、C6）；w13 形状 (E, 2I, H)、w2 (E, H, I)、cache1 (M, topk, 2I)、cache2 (M·topk, I)、cache3 (M, topk, H)。②t0=(1,0) 经 e0 与 e1 两条支路：手算 gate/up、silu 门控乘、w2 投影、乘权重 0.6/0.4、求和得 y_0（F3）。
- 正文要点：数据流图；两次 GEMM 之间形状收缩（2I→I）的来源（激活语义）；权重在 GEMM2 乘且 fp32（C6）；moe_sum 求和；cache13 复用一句带过（C15）。
- 表达材料：结构 A 顺序流程图（五步）；贯穿手算（正文算 t0 全程 + t0×e0 支路逐步，其余槽位折叠块）；可运行代码折叠块（朴素参考实现 vs 分块对齐实现逐元素一致，纯 Python 无第三方库）。
- 前置知识安排：SwiGLU 门控激活（swiglu 链接）在激活步引用。
- 范围：C5、C6、C13、C15、F3；构造示例 A 数值层展开；可运行代码。

### 第 5 章 FusedMoE 层的职责边界——它管什么、不管什么（Q5）

- 章节问题：①FusedMoE 层在 vLLM 里由什么组成、TP 下专家权重怎么切？②EP 通信、负载均衡、量化为什么不属于它？③批量极小时有什么特殊路径？
- 完成答案要点：①v0.10.2 为 FusedMoE 类；v0.28.0 为 FusedMoEFactory 组装 Router+RoutedExperts+MoERunner；w13 列切、w2 行切（C12，model-parallelism 链接）。②EP 的 dispatch/combine 由独立组件承担，内核只对非本 rank 专家写零（C10）；EPLB 管负载均衡（链接概念页）；量化路径复用同一内核框架但内部多反量化步骤（范围外）。③num_tokens×top_k×4 ≤ E 时跳过对齐（C14、N3）；调优配置按形状查 JSON（C11、N1）。
- 正文要点：职责对照表（管/不管）；"融合 ≠ 整层一个内核"的澄清落点。
- 表达材料：职责边界表。
- 前置知识安排：TP 列切/行切（model-parallelism 链接）；EP 概念（moe-serving 链接）。
- 范围：C11、C12、C14、N1、N3。

## 4. 贯穿示例

构造示例 A（唯一贯穿例子，全部数字为构造，不代表真实模型）：

- 规模：T=4 个 token，E=4 个专家（id 0–3），topk=2，block_size=2，隐藏维 H=2，中间维 I=2。
- 路由结果（给定，作为融合算子的输入；softmax 打分属 moe-serving 范围）：
  - t0→(e0, 0.6), (e1, 0.4)；t1→(e1, 0.5), (e3, 0.5)；t2→(e0, 0.7), (e3, 0.3)；t3→(e1, 0.8), (e2, 0.2)
- 输入：t0=(1,0)，t1=(0,1)，t2=(1,1)，t3=(2,0)
- 权重（元素取 0/±1/2 便于手算）：w13[e] 为 4×2（gate 两行 + up 两行），w2[e] 为 2×2
- 推进：第 2 章用它手算三数组（整数层）；第 3 章用它手算一个 tile 的索引与乘法（数值层开始）；第 4 章完成 t0 的两条支路与最终输出，并给可运行代码算全部 4 个 token 与朴素实现对照。

每个局部材料的服务目标：三数组手算服务 Q2；tile 手算服务 Q3；全程手算与代码服务 Q4。
