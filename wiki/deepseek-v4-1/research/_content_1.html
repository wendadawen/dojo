主要依据：DeepSeek-V4.1-Flash 技术报告《DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression》（research/official/tech_report.txt）；官方推理配置 official/inference/config.json（HF 仓库版 official/config.json 为 transformers 格式；两版关键字段取值一致，个别字段名不同，本页按各自版本引用）；官方参考实现 official/inference/model.py、kernel.py；真实 checkpoint 分片头（HTTP Range 读取，research/ckpt/headers.json，96085 个张量）。全部数值来自这些材料的直接读取或本机实测，实测脚本与存档见文末。

一次 1M 上下文的长请求里，模型每生成一个 token，要为「它能回头看多远」在显存里留下 890 字节——不到一页纯文本的 ASCII 长度。这个数字不是某个单点技巧的结果：压缩把每 $r$ 个 token 池化成一条条目，跨层共享让多层共用同一份缓存，FP4 把每条条目的存储压到 4 位。本页要做的就是把 890 拆开，逐项对上这三个来源。页内所有字节数出自官方配置与参考实现的常量，不是估算；凡是为说明计算方法而人为设定的参数，都会标为构造示例。

核心问题

  1. 890 字节/token 是怎么算出来的？

    解答：主 KV 720 字节 + 索引器 K 170 字节，各自由压缩、共享、FP4 三项叠出来

    一条压缩条目在 512 维上以 FP4 存储占 256 字节，加上每 16 通道一个 E4M3 缩放因子（32 个，共 32 字节），合计 288 字节。压缩比为 2 的层每两条 token 才产生一条条目，折合 144 字节/token；压缩比为 1 的层不做跨 token 池化，折合 288 字节/token。全模型只有四个层真正生产主 KV（层 2、8、14、20），前三个压缩比为 2、第四个为 1，于是 $3\times144+288=720$ 字节；索引器键值按同一口径（每条目 68 字节）折合 $3\times34+68=170$ 字节。两项相加是 890 字节。完整账目见第 1 章。

  2. CED 为什么能让 prefill 只跑一半的层？

    解答：解码器的全局 KV 不来自本层隐状态，而由编码器末层投影而来

    主干 40 层被划成前 20 层因果编码器与后 20 层解码器。解码器各层的全局 KV 不由各自的隐状态 $H_l$ 算出，而是由编码器最后一层隐状态 $H_{L/2}$ 经投影得到。与跨层共享机制结合后，只有解码器中被指派为 Full 模式的层（层 20）真正执行这次投影，其余解码器层直接读它发布的缓存。既然解码器的全局 KV 在编码器跑完时就已经确定，prefill 阶段就只需要跑编码器半栈。滑动窗口注意力不适用这一点，它仍逐层从本层隐状态计算，因此服务端需要为它做有界重放。完整推导见第 2 章。

  3. 一个 query 到底能看到哪些位置？

    解答：本层窗口内最多 128 个原始位置 + 索引器选出的至多 512 个压缩条目

    可见集由两部分拼成。一部分是滑动窗口内的原始 KV，最多 $n_{\text{win}}=128$ 个；另一部分是该层所属压缩比组的压缩条目中被索引器选中的 Top-512 个。压缩条目按组编号，组 $j$ 覆盖 token $[jr,(j+1)r)$，其位置编码取 $j\cdot r$；尚未产生的条目（编号超出 $\lfloor(i+1)/r\rfloor$）在打分阶段就被置为 $-\infty$，不参与竞争。解码器还有一级候选池：建池层先用块级打分选出 2048 个块、每块 8 个位置，共 16384 个候选，后续层只在这个池内选 Top-512。两部分槽位拼进同一次稀疏注意力调用。完整规则与可运行复算见第 3 章。

  4. 8B 与 16B 的激活参数量是怎么加出来的？

    解答：单层约 377M，编码器半栈 7.89B、解码器半栈 7.58B

    单层每 token 激活的参数量约 377M：注意力 126.6M（层 20 因多出压缩器与索引器为 134.7M）、路由门控 1.97M、共享专家 35.4M、top-6 路由专家 212.3M、超连接模块 0.98M。编码器 20 层合计 7.8929B（其中层 1、14 各含约 157M 的 Engram 稠密投影），解码器 20 层合计 7.5758B。prefill 只跑编码器，对应 8B 口径；decode 跑满全栈，对应 15.5B，约 16B。完整加总见第 4 章。

  5. Engram 与 DSpark 各自补了什么？

    解答：Engram 补可寻址的条件记忆，DSpark 补解码吞吐

    Engram 是插在层 1 与层 14 的 n-gram 哈希查表：每 token 只查 24 行嵌入（阶数 2/3/4 乘 8 个哈希头），但把查到的向量写回残差流的投影矩阵是稠密的，因此它让每 token 多激活约 157M 参数，却不增加任何 KV 缓存。DSpark 是块式推测解码，用 3 个 MTP 块一次前向产出 5 个草稿位置，输入取自层 37、38、39 的注意力输入，末块用 Markov 头与置信头决定接受哪些草稿；它同样不改变主干缓存，只提高 decode 吞吐。完整机制见第 5 章。

常见误解

  • 「890 字节是每一层缓存相加的结果」——跨层共享后全模型只存 4 份主 KV 与 4 份索引器键值；若每层各存一份，主 KV 一项就是 8352 字节/token，是现在的 11.6 倍。
  • 「压缩比 2 就是每两个 token 平均成一个」——池化权重是组内 softmax 门控（每个通道一组可学习权重），不是算术平均；而且每条压缩条目在索引器里还另有一份 FP4 键。
  • 「Reuse 层复用了 Top-K 索引，所以它看到的和 Full 层一样」——复用索引的前提是同一份主 KV；不同压缩比组的条目编号与位置换算关系不同，跨组不能共用。
  • 「prefill 只要 8B，说明解码器不参与推理」——decode 阶段仍要跑满 40 层；8B 只是 prefill 阶段的计算量口径，不是结构裁剪。
  • 「报告的分层公式说明每个解码器层都有自己的全局 KV 投影」——那是设计的一般形式；与压缩共享机制结合后只有解码器的 Full 层（层 20）执行投影，其余层读它的缓存。

1. 890 字节的账——压缩、共享与 FP4 各贡献多少

先把问题收窄到一个可核算的对象：模型每处理一个 token，要为全局注意力在显存里多留多少字节？答案取决于三件事各自省下了什么，所以这一章不直接报数字，而是把条目大小、条目密度、条目份数依次算出来，最后相加。

1.1 压缩条目：把 $r$ 个 token 池化成一条 KV

若每个 token 都保留一份完整的键值（见 KV cache），缓存就会随序列长度线性增长，这正是长上下文最贵的一项。压缩注意力的做法是：让每 $r$ 个 token 共同产生一条键值条目，其中 $r$ 是该层的压缩比。于是缓存条目数变成序列长度的 $1/r$。

把 token 按 $r$ 个一组切开，第 $j$ 组覆盖位置区间 $[jr,(j+1)r-1]$。这一组 $r$ 个 token 的隐状态先各自投影出候选值向量与门控分数，再在组内做 softmax 加权求和——权重由数据决定，不是固定平均[F1]：

$$C_j = \mathrm{RMSNorm}\!\Big(\sum_{t=jr}^{(j+1)r-1} \mathrm{softmax}_{t'}\big(s_{t'}\big)\, v_t\Big)$$
  • $r$：该层的压缩比，本模型取 1 或 2；
  • $j$：压缩条目的编号，从 0 开始，第 $j$ 组覆盖 token $[jr,(j+1)r)$；
  • $v_t = W_{kv}h_t$：第 $t$ 个 token 的候选值向量；
  • $s_t = W_{gate}h_t$：第 $t$ 个 token 的门控分数，softmax 在这 $r$ 个分数上取；
  • $C_j$：该组的压缩条目，先池化再经过 RMSNorm。

这个式子有两个容易忽略的点。第一，池化权重是逐通道的门控，同一组里不同维度可以有不同权重组合，所以它不等于把 $r$ 个向量相加再除以 $r$。第二，条目需要自己的位置编码：压缩后的一条条目代表 $r$ 个原始位置，实现给它的位置取组起点 $j\cdot r$，而不是组内某个 token 的位置[F1]。

当 $r=1$ 时门控退化：每组只有一个 token，softmax 在单元素上恒为 1，条目就是 $\mathrm{RMSNorm}(W_{kv}h_t)$。也就是说压缩比为 1 的层不做跨 token 池化，每个 token 仍然产生一条条目——它的节省来自别处，不是压缩。这一点在第 1.3 节的份数账里会体现出来。

池化的数值路径也有一处实测细节：同一条池化在 fp32 层面对照时差异为 4.5e-6（相对 2.2e-6），转成 bf16 后 4096 个元素中有 5 个落在不同 ulp[N8]。也就是说压缩器内部用 fp32 计算、输出再转回 bf16 这一安排不是多余的——它把舍入推迟到最后一步。

补充：压缩发生在 token 方向，与 MLA 的压缩方向不同

低秩潜变量注意力（MLA）把每个 token 的键值从「多头乘头维」压成一条低维潜向量，削减的是每个 token 内部的宽度；压缩注意力的池化削减的是token 方向的条数。两者可以叠加，本模型也同时用了：压缩比决定条数，条目的 512 维宽度则沿用潜变量那一套。理解这一点可以避免把「压缩比 2」误读成「条目宽度减半」。

1.2 一条条目 288 字节：FP4 与逐通道缩放因子

条目数算完了，接下来算每条条目占多少字节。这由存储格式决定。主 KV 以 FP4 存储，具体格式是 MXFP4（见 MXFP4 量化 与 混合精度量化）：数值本身是 E2M1（1 位符号、2 位指数、1 位尾数，可表示 $\{0,0.5,1,1.5,2,3,4,6\}$ 及其相反数），每 16 个通道共享一个 E4M3 缩放因子，并且不带第二级全局缩放[C3]。

于是每条条目的字节数由两块组成。第一块是数值：512 维、每个数值 4 位，两个数值拼成一个字节，共 $512/2 = 256$ 字节。第二块是缩放因子：每 16 个通道一个，共 $512/16 = 32$ 个，每个 1 字节（E4M3），合计 32 字节。两块相加：

$$\underbrace{\frac{512}{2}}_{\text{FP4 数值}} + \underbrace{\frac{512}{16}}_{\text{E4M3 缩放因子}} = 256 + 32 = 288\ \text{字节}$$
  • $512$：主 KV 条目的通道数（即潜变量维度），该模型所有全局 KV 条目都是这个宽度；
  • $512/2$：每个数值占 4 位，因此每 2 个通道占 1 字节；
  • $512/16$：每 16 个通道共享一个缩放因子；
  • $288$：一条压缩条目（不含索引器键值）的字节数。

把 288 字节拆成「数值 256 + 缩放 32」而不是笼统记作 288，是因为后面两项都会用到：一旦通道数或缩放粒度变化，两个分量要分别重算。

低精度的代价可以直接量出来：在 512 维的归一化输出上，FP4 的相对误差为 9.5%，FP8 为 2.65%，前者是后者的 3.58 倍[N5]。报告称训练中观察到的最大幅值约为 10，而 E4M3 缩放因子能表示的上界是 $448\times6=2688$，尚有约 268 倍的余量。精度换来的空间收益是 4 位对 8 位——同样通道数下字节减半。这个取舍在后面的账里体现为：主 KV 用 FP4 而窗口 KV 保持 FP8。

补充：为什么缩放因子按 16 通道而不是整条条目

FP4 只有 4 位表示能力，若不分组缩放，一条条目内部数值的动态范围会被拉得很窄：整条用一个缩放因子时，某个特别大的通道会迫使其他通道全部落到低量级上。按 16 个通道分组后，每组各自有自己的尺度，组内的相对关系仍能保留。代价是每 16 个通道多 1 字节开销（$512/16=32$ 字节，约为数值部分的 12.5%）。分辨率与开销的折中就是这条 16 的粒度，它直接决定了 288 这个数：若把粒度放宽到 32，条目会变成 $256+16=272$ 字节。

1.3 只有四个层生产主 KV：份数账

有了「每条 288 字节」和「每 $r$ 个 token 一条」，还差最后一个因子：全模型一共要存多少条这样的条目。这一步的关键在于，并不是每一层都存自己的全局 KV。

跨层共享把主干切成若干组，组内只由第一个层（称为 source 层）生产一份主 KV，其余层读取同一份[C2]。实测的分组是层 2–7、8–13、14–19、20–39，对应的 source 层为 2、8、14、20。也就是说，整个 40 层主干只生产 4 份主 KV，而不是 40 份。判定哪个层是 source、哪一层复用的是 Full / Reindex / Reuse 三模式，属于第 3 章的内容；这一章只需要这个结论：生产份数是 4，压缩比分别是 2、2、2、1。

逐项折算到「每个 token 贡献多少字节」。压缩比为 2 的层每 2 个 token 产生一条 288 字节的条目，因此对序列里每个 token 平均贡献 $288/2 = 144$ 字节；压缩比为 1 的层不做池化，每个 token 一条，贡献 288 字节。实测配置里层 2、8、14 的压缩比为 2，层 20 的压缩比为 1[C2]：

项目每条条目压缩比 2 的 source 层（2、8、14）压缩比 1 的 source 层（20）
主 KV（512 维 FP4 + 逐 16 通道缩放因子）$256+32=288$ B每 2 token 一条，折合 144 B/token每 token 一条，288 B/token
索引器 K（128 维 FP4 + 逐 32 通道缩放因子）$64+4=68$ B每 2 token 一条，折合 34 B/token每 token 一条，68 B/token

表里第二行的索引器 K 是另一条旁路所需的键：稀疏注意力要用一个轻量索引器给压缩条目打分，才决定选哪些条目，所以每条压缩条目需要额外配一份供打分用的键。它同样是 FP4，但宽度是 128 维（索引头维）。数值部分的口径与主 KV 相同（两个数值一字节，$128/2=64$ 字节），缩放因子却是每 32 通道一个 E8M0——粒度与类型都与主 KV 的每 16 通道 E4M3 不同。因此每条 $128/2 + 128/32 = 64+4 = 68$ 字节[C3]。

把两行各自的四个 source 层加起来[N1]：

$$\underbrace{3\times144 + 288}_{\text{主 KV}} + \underbrace{3\times34 + 68}_{\text{索引器 K}} = 720 + 170 = 890\ \text{字节/token}$$
  • $3\times144$：三个压缩比为 2 的 source 层，各折合 144 B/token；
  • $288$：压缩比为 1 的 source 层 20，折合 288 B/token；
  • $3\times34 + 68$：索引器 K 按同一口径折算；
  • $890$：全模型每 token 的全局 KV 缓存（常驻显存）。

主 KV 的 720 与索引器 K 的 170 是两项独立开销，把 890 归到其中任何一项名下都不对：主 KV 占 81%，索引器 K 占 19%，两者都由「压缩 + 共享 + FP4」共同压出来——压缩决定条数、共享决定份数、FP4 决定每条大小，三者缺一不可。

报告称这个数字约为 DeepSeek-V4-Flash 对应开销的 1/4；报告另给出相对 DeepSeek-V1 的 1/437 与服务实现持久化的 1/8 两个倍数[N9]。这三个倍数都登记为报告宣称：本页缺对方模型的配置与缓存结构，无法独立推导，因此只陈述宣称本身，不据此比较架构优劣。

展开：890 的完整加总与「不共享会是多少」的反事实

构造示例（数值取自官方配置与参考实现的常量，非额外实跑）：把上式的每一项拆开写。

主 KV 一项：压缩比 2 的三个层，每 token 折合 $288 \div 2 = 144$ 字节；压缩比 1 的层 20，每 token 288 字节。合计 $144 \times 3 + 288 = 720$ 字节。

索引器 K 一项：每条 $128 \div 2 + 128 \div 32 = 68$ 字节（数值 $64$ 字节，加每 32 通道一个 E8M0 缩放因子 $4$ 字节）。压缩比 2 的三个层折合 $68 \div 2 = 34$ 字节/token；压缩比 1 的层 20 折合 68 字节/token。合计 $34 \times 3 + 68 = 170$ 字节。

两项相加 $720 + 170 = 890$ 字节/token。

反事实：假如不做跨层共享，每个 ratio 大于 0 的层都各存一份主 KV。压缩比 2 的层有 18 个（层 2–19），压缩比 1 的层有 20 个（层 20–39）。主 KV 一项就是 $18 \times 144 + 20 \times 288 = 2592 + 5760 = 8352$ 字节/token，是共享后 720 的 11.6 倍。这个对比说明：在 890 这个数字里，跨层共享贡献的是「份数」这一维度的压缩，与压缩比贡献的「条数」、FP4 贡献的「每条大小」是三件独立的事。

本章问题

  1. 890 字节由哪两项构成？各自是怎么算出来的？

    解答：主 KV 720 字节 + 索引器 K 170 字节，算法是「每条大小乘折算密度再乘份数」

    主 KV 一项：一条条目在 512 维上以 FP4 存储占 $512/2=256$ 字节，加 $512/16=32$ 个 E4M3 缩放因子共 32 字节，得 288 字节/条。三个压缩比为 2 的 source 层（层 2、8、14）每 2 个 token 产生一条，折合 144 字节/token；压缩比为 1 的层 20 每 token 一条，折合 288 字节/token。合计 $3\times144+288=720$ 字节。

    索引器 K 一项：供索引器打分用的键宽 128 维，同样 FP4，每条 $128/2+128/32=68$ 字节（缩放因子为每 32 通道一个 E8M0）；按同一折算口径得 $3\times34+68=170$ 字节。

    两项相加为 890 字节/token。需要强调「份数只有 4」这个前提：若每层各存一份，主 KV 一项就是 8352 字节/token。

  2. 为什么跨层共享能把主 KV 从 8352 字节压到 720 字节，而不是压到 1/40？

    解答：共享只减少份数，不改变条数与每条大小；剩下的是压缩比差异导致的必然开销

    跨层共享做的是把「40 个层各存一份」变成「4 个组各存一份」，份数从 40 降到 4，这是 10 倍。但 720 相对 8352 只有 11.6 倍，看起来接近但算法不同：8352 是按 38 个层各存一份算的（压缩比 2 的 18 层 + 压缩比 1 的 20 层），而 720 是 4 个 source 层按各自的压缩比折算后相加。两者的差别不只是份数，还包括被共享掉的那些层本来有不同的压缩比。

    换一种算法看得更直接：共享后保留的 4 个 source 层自身也要占位置，其中层 20 的压缩比是 1（每 token 一条 288 字节），这是四份里最贵的一份，占总量的 40%。共享能省掉的是「重复的份数」，省不掉「压缩比 1 那层必须逐 token 存」这件事——要再压这一项，只能改压缩比或改存储精度。完整的分组与模式判定见第 3 章。

2. prefill 为什么只跑一半——CED 把解码器的全局 KV 前移

第 1 章算清了「缓存里存多少」。但缓存的来源还没交代：这些条目由哪些层、用什么输入算出来？这个问题直接决定了 prefill 阶段需要跑多少层，因此先回答它。

2.1 主干被切成编码器与解码器两半

主干 40 层不是一条同质的栈。它被划成前 20 层（层 0–19）与后 20 层（层 20–39）两段，报告称前者为因果编码器、后者为解码器，合起来叫 CED（Causal Encoder–Decoder）[C1]。两段的差别不在层结构，而在全局 KV 从哪里来：编码器各层照常从自己的隐状态算全局 KV，解码器各层则不这样做。

层与层之间靠残差流串联（见 残差连接），所以「第 20 层拿到的输入」就是「第 19 层的输出」——这一点在下一节会直接用到。

2.2 解码器的全局 KV 由 $H_{L/2}$ 投影而来

报告给出的形式化描述很直接：对于上半段（解码器，$l > L/2$），键值条目不由各自的隐状态 $H_l$ 导出，而是直接从第 $L/2$ 层的隐状态 $H_{L/2}$ 投影，投影权重按层各自不同[C6, F7]：

$$C_l = H_{L/2}W_l^{KV},\qquad Z_l = H_{L/2}W_l^{Z},\qquad l > L/2$$
  • $L$：主干层数，$L=40$，因此 $L/2=20$；
  • $H_{L/2}$：编码器最后一层的隐状态，即第 20 层的输入（第 19 层的输出）；
  • $W_l^{KV}, W_l^{Z}$：第 $l$ 层的投影权重，逐层不同，不是全栈共享一组；
  • $C_l, Z_l$：第 $l$ 层要用的全局键值条目与配套表示。

因此「共享」这个词需要精确一点：共享的是输入 $H_{L/2}$，不是投影结果。每个解码器层照旧有自己的投影权重，只是喂进去的东西换成了同一个编码器输出。

与压缩共享机制结合后还有一层收窄：真正执行这次投影的只有解码器中被指派为 Full 模式的层。报告写明，结合之后由 Full 层从编码器末层隐状态计算全局 KV[C6]；在本模型的配置里这个层是层 20。其余解码器层读它发布的缓存，不再自己算。参考实现中的表现是「层 20 的压缩器读取它自己的注意力输入」，而该输入恰好就是层 19 的输出，与公式中的 $H_{L/2}$ 对上。

这就是 prefill 减半的来源：解码器所需的全局 KV 在编码器跑完时就已确定，所以 prefill 阶段可以只跑编码器半栈。需要区分的是，这条结论关于计算量，不是关于结构——decode 阶段仍要跑满 40 层。

补充：报告的设计描述与参考实现的分工

报告描述的是设计意图：解码器的全局 KV 由 $H_{L/2}$ 投影，因而具备提前退出的条件。参考实现里没有「prefill 只跑编码器」的分支——它对任何 prefill 都逐层跑满 40 层[C11]。也就是说，报告中的「接近减半的 prefill 计算」与「有界重放」属于服务端部署时的优化，参考实现是可读的模型定义，不是性能路径。本页把两者分开陈述：前者标为报告宣称，后者标为参考实现的实际行为。用一句话概括边界——本页能核对的是「解码器全局 KV 的输入是 $H_{L/2}$」，不能核对的是「服务端真的省掉了一半」。

2.3 滑动窗口 KV 不能一起省

既然解码器的全局 KV 可以前移，为什么不把滑动窗口的 KV 也一起前移，让 prefill 跑得更少？答案是两者的作用对象不同：全局 KV 是压缩后的远距离摘要，滑动窗口 KV 是最近位置的原始精度副本，每个 query 必然读到（见 滑动窗口注意力）。

关键在于滑动窗口 KV 依赖本层经过完整计算的隐状态，而第 $l$ 层的隐状态要等第 $l-1$ 层算完才能得到。这条依赖链无法用「读编码器输出」替代——编码器末层的隐状态不包含「解码器前一层如何重新混合过信息」的结果。因此服务端要省掉解码器的窗口重算，只能采用有界重放：重算最后 $n_{\text{win}}$ 个位置就够，因为再往前的窗口内容已经滑出可见范围。这一点属于服务实现，本页只登记其成立条件（见文末范围说明）。

两条路合起来可以看到设计的一致性：全局 KV 之所以能前移，是因为它本来就没打算记住细节——它已经是压缩摘要；窗口 KV 之所以不能前移，正是因为它要保留细节。省的对象不同，可省的程度也就不同。

本章问题

  1. 解码器的全局 KV 从哪里来？参考实现里对应哪个位置？

    解答：来自编码器末层隐状态 $H_{L/2}$ 的投影；参考实现中即层 20 的压缩器读取自己的注意力输入

    报告给出 $C_l = H_{L/2}W_l^{KV}$、$Z_l = H_{L/2}W_l^{Z}$（$l>L/2$），即解码器各层的键值条目由编码器最后一层的隐状态投影得到，投影权重逐层不同。与跨层共享结合后，只有解码器的 Full 层（本模型为层 20）执行这次投影，其余解码器层复用它发布的缓存。

    参考实现里的对应现象是：层 20 的压缩器不读自己的隐状态，而读它自己的注意力输入——而第 20 层的注意力输入就是第 19 层的输出，即 $H_{L/2}$。两处描述指向同一件事。需要注意「共享的是输入而非投影结果」：各解码器层仍有各自的投影权重。

  2. 既然解码器全局 KV 可以提前算出，为什么滑动窗口 KV 不能同样处理？

    解答：窗口 KV 依赖本层的完整隐状态，而该隐状态的依赖链无法用编码器输出替代

    全局 KV 是压缩摘要，允许由编码器末层一次性投影；窗口 KV 是最近位置的原始精度副本，必须由本层经过完整注意力和前馈计算后的隐状态生成。第 $l$ 层的窗口 KV 需要第 $l$ 层的隐状态，而第 $l$ 层的隐状态又要等第 $l-1$ 层算完，这条链不能跳过，因此窗口 KV 无法像全局 KV 那样「前移」到编码器末尾。

    服务端的替代办法是有界重放：只重算最后 $n_{\text{win}}$ 个位置即可，因为更早的位置已经滑出窗口、不在可见集内。这一优化属于服务实现，参考实现中不含该分支。
