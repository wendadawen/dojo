# DeepSeek-V4.1-Flash 文章大纲

## 4.1 页面开头

**具体问题**：一次 1M 上下文的长请求里，模型每生成一个 token，要在显存里为"它能回头看多远"留下多少缓存？技术报告给出的答案是 **890 字节**——不到一页文本的长度。这个数字不是单一技巧的结果，而是压缩、跨层共享与低精度存储三件事叠出来的。

**随后给出**：简要解释（V4.1-Flash 用 CSA2 管理全局 KV、用 CED 把 prefill 压到半栈、用 FP4 存主 KV）；本文学习目标（Q1–Q5）；第一个示例（构造示例：一个 token 的账本，用真实配置值）；过渡到第 1 章。

**组件**：`blockquote.meta`（主要依据）、`callout-blue`（范围与口径说明）、`learning-goals`（核心问题 5 条）、`misconceptions`（5 条常见误解）。

## 4.2 章节设计

### 第 1 章 890 字节的账——压缩、共享与 FP4 各贡献多少

- **章节问题**：890 B/token 由哪些项构成？跨层共享与 FP4 各贡献多少？
- **完成答案要点**：主 KV 条目 288 B（512 维 FP4 = 256 B + 32 个 E4M3 scale = 32 B）；压缩比 2 的三个 source 层各 144 B/token，压缩比 1 的层 20 为 288 B/token，主 KV 合计 720 B；索引器 K 条目 68 B，按同口径合计 170 B；总计 890 B。不共享时主 KV 一项就是 8352 B/token（11.6×）。
- **对应范围**：Q1；C2、C3；F1（压缩比与池化定义）；N1、N5
- **正文要点**：压缩条目是什么（组 $j$ 覆盖 token $[jr,(j+1)r)$）；池化权重是组内 softmax 门控（公式 F1 的用途与符号）；288 B 的两项来源；四个 source 层与它们覆盖的层区间；索引器 K 的存在理由（打分需要键）
- **材料**：公式 F1；对照表格（主 KV / 索引器 K × 压缩比 2 / 1 × 每 token 字节）；`details` 展开 890 的加总与 8352 的反事实
- **前置知识**：压缩发生在"跨 token 池化"、MLA 的压缩发生在"每 token 维内"（mla 页）；FP4/FP8 与 scale 的字节（mxfp4-qat 页、mixed-precision-quant 页）；KV cache 基本形态（kv-cache 页）
- **本章问题**：2 条（890 的两项构成；为什么共享能把主 KV 从 8352 压到 720）

### 第 2 章 prefill 为什么只跑一半——CED 把解码器的全局 KV 前移

- **章节问题**：解码器的全局 KV 从哪里来？为什么这样能让 prefill 少跑一半的层？
- **完成答案要点**：CED 让解码器层的全局 KV 由编码器最后一层隐状态 $H_{L/2}$ 投影得到（报告 Eq. 1）；与 CSA2 结合后只有解码器的 Full 层（层 20）执行这次投影，其余解码器层共用；参考实现中该投影就是"层 20 的压缩器读自己的注意力输入"；SWA 的 KV 仍逐层从本层隐状态算，故服务端需要 SWA 重放，报告给出有界重放只重算最后 $n_{\text{win}}$ 个 token。
- **对应范围**：Q2；C1、C6、C11；F7；F1（层 20 压缩器）
- **正文要点**：编码器/解码器的划分与"半栈"含义；Eq. 1 的符号与成立条件；报告与参考实现的分工（报告描述设计意图，参考实现只做单栈逐层执行）；SWA 为什么不能省
- **材料**：公式 F7；结构图（20+20 层、全局 KV 来源、SWA 逐层）；`details` 补充参考实现的对应位置（层 20 压缩器输入 = 层 19 输出）
- **前置知识**：滑动窗口注意力（**缺失，需递归生成**）；残差流与层间依赖（residual-connection 页）
- **本章问题**：2 条（全局 KV 的来源；为什么 SWA 不能一起省）

### 第 3 章 一个 query 看到哪些位置——窗口、压缩条目与两级筛选

- **章节问题**：给定层号与 query 位置，它能看到的 KV 槽位是怎么确定的？
- **完成答案要点**：可见集 = 本层窗口内最多 128 个原始位置 + 至多 512 个压缩条目；压缩条目按组编号、组 $j$ 的 RoPE 位置是 $j\cdot r$；可达条目数 $\lfloor (i+1)/r\rfloor$（prefill）与 $\lfloor (s+1)/r\rfloor$（decode）一致，不可达条目在打分前置 $-\infty$；Top-512 由索引器打分选出（$I=\sum_h w_h\,\mathrm{ReLU}(q_h\cdot k_j)$），选中的槽位与窗口槽位拼进同一次稀疏注意力调用，注意力汇聚点只进分母；解码器还有一级候选池：建池层选出 2048 个块（块分 = 块内最大索引分，最新块钉住）× 8 位置 = 16384 个候选，后续 Reindex 层只在该池内选 Top-512。
- **对应范围**：Q3；C2、C7、C10；F2、F3、F4、F9
- **正文要点**：可见性规则（哪些位置可见）与选择规则（选哪些）分开陈述；三模式对"谁算 Top-K、谁复用"的影响；实测边界——参考实现在 ratio>1 的 kv_source 层上，解码步中组未填满时会读到别的层的索引键（C10），因此 prefill 与 decode 的选择可以不同，但可见性规则本身一致
- **材料**：公式 F2/F3/F4/F9；结构图（两级筛选：全位置打分 → 块级候选 → 位置级 Top-512）；可运行代码（自包含复现可达性规则与 Top-K 语义，已在正文外实跑）；`details` 展开索引器打分与汇聚点语义
- **前置知识**：稀疏注意力与 indexer（dsa 页）；注意力汇聚点（**缺失，需递归生成**）；滑动窗口注意力（**缺失，需递归生成**）；RoPE（rope 页）
- **本章问题**：3 条（可见集的两部分；可达条目数怎么算；prefill 与 decode 的选择为什么可能不同）

### 第 4 章 8B 与 16B——激活参数的账怎么算

- **章节问题**：每 token 激活 8B（prefill）/16B（decode）是怎么加出来的？MoE 稀疏性与半栈各贡献多少？
- **完成答案要点**：单层每 token 激活约 377M：注意力 126.6M（层 20 为 134.7M）+ gate 1.97M + 共享专家 35.4M + top-6 路由专家 212.3M + mHC 0.98M + norm；编码器 20 层合计 7.8929B（含层 1、14 的 Engram 稠密投影各约 157M），解码器 20 层合计 7.5758B；prefill 只跑编码器 → 8B，decode 全栈 → 15.5B ≈ 16B。
- **对应范围**：Q4；C4、C8；F5、F6；N2、N3、N6
- **正文要点**：路由公式与"偏置只影响选择"；专家形状与 top-6 的折算；Engram 的稀疏查表（24 行）与稠密投影（每层 157M）为什么必须分开算；半栈加总
- **材料**：公式 F5；对照表格（单层各组件参数量、半栈合计）；`details` 展开 7.89B / 7.58B 的加总
- **前置知识**：MoE 路由与无辅助损失偏置（deepseek-moe、aux-loss-free-routing 页）；超连接与 Sinkhorn（hyper-connections 页）；n-gram 哈希查表（ngram 页）
- **本章问题**：2 条（单层 377M 的构成；为什么 Engram 的 98B 表不计入激活）

### 第 5 章 Engram 与 DSpark——两个不改缓存账的模块

- **章节问题**：这两个模块各解决什么问题？它们如何影响整机成本？
- **完成答案要点**：Engram 用 n-gram 哈希（阶 2/3/4 × 8 头 = 24 桶）查可学习嵌入表，把"条件记忆"写进残差流，门控是流与键的归一化点积的 sigmoid；它使每 token 多激活约 157M 稠密投影，但不增加 KV 缓存。DSpark 是块式推测解码：3 个 MTP 块、每块一次前向产出 5 个草稿位置，输入取自层 37/38/39 的注意力输入拼接，末块用 Markov 头（rank 256）与置信头决定接受；它不改变主干缓存，只提高 decode 吞吐。
- **对应范围**：Q5；C4、C5；N2
- **正文要点**：n-gram 哈希的输入输出与门控；为什么图像 token 被屏蔽；DSpark 的双流输入（草稿嵌入 + 主干隐状态）与草稿链；两个模块对"缓存账 / 激活账"的不同作用
- **材料**：结构图（DSpark 数据流：主干隐状态 → main_proj → 草稿块 → Markov 头 → 草稿 token）；`details` 补充 Engram 的哈希桶与乘子构造
- **前置知识**：n-gram 哈希查表（ngram 页）；推测解码与 MTP（speculative-decoding 页）
- **本章问题**：2 条（Engram 与 DSpark 各自的作用；它们为什么不改变 890 字节的账）

## 4.3 讲解顺序

依赖链：压缩条目与字节（第 1 章）→ 全局 KV 的来源（第 2 章，依赖第 1 章的"谁存 cache"）→ 可见性规则（第 3 章，依赖第 1 章的压缩条目与第 2 章的层划分）→ 激活参数（第 4 章，独立于前三章但复用"半栈"）→ 两个附加模块（第 5 章）。第 2 章开头用一句说明从"存多少"转到"谁来产生"，第 3 章开头从"缓存里有什么"转到"query 能拿到什么"。

## 4.4 贯穿示例

**场景**：在 1M 上下文里生成第 5000 个 token，追踪它在层 2 与层 20 上的开销与可见范围。各章推进：

1. 第 1 章：这一个 token 在层 2 贡献主 KV 144 B + 索引器 K 34 B；在层 20 贡献 288 B + 68 B
2. 第 2 章：它在层 2 的压缩条目由层 2 自己的压缩器产生；层 20 的全局 KV 则由层 19 的隐状态投影
3. 第 3 章：位置 4999 的 query 在层 2 可见 128 个窗口位置 + $\lfloor 5000/2\rfloor = 2500$ 个可达压缩条目中选出的 512 个
4. 第 4 章：处理这一个 token 在编码器半栈激活约 7.89B 参数中的一层份额
5. 第 5 章：DSpark 用层 37/38/39 的注意力输入为它生成 5 个草稿位置
