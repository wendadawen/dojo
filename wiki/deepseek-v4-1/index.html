    DeepSeek-V4.1-Flash：把每 token 全局 KV 缓存压到 890 字节的三项叠加

    主要依据（公开仓库 deepseek-ai/DeepSeek-V4.1-Flash）：DeepSeek-V4.1-Flash 技术报告《DeepSeek-V4.1-Flash: Pushing the Limits of KV Cache Compression》（DeepSeek_V41_Tech_Report.pdf）；官方推理配置 inference/config.json（HF 仓库版 config.json 为 transformers 格式；两版关键字段取值一致，个别字段名不同，本页按各自版本引用）；官方参考实现 inference/model.py、inference/kernel.py；真实 checkpoint 分片头（HTTP Range 读取，96085 个张量）。全部数值来自这些材料的直接读取或本机实测，实测脚本与运行输出不随仓库分发，实测清单见 research/measured.md。

    一次 1M 上下文的长请求里，模型每生成一个 token，要为「它能回头看多远」在显存里留下 890 字节——不到一页纯文本的 ASCII 长度。这个数字不是某个单点技巧的结果：压缩把每 $r$ 个 token 池化成一条条目，跨层共享让多层共用同一份缓存，FP4 把每条条目的存储压到 4 位。下文按压缩、共享、FP4 三项拆开 890 的构成。页内所有字节数出自官方配置与参考实现的常量，不是估算；凡是为说明计算方法而人为设定的参数，都会标为构造示例。各模块在完整前向中的先后顺序与张量形状，另见 DeepSeek-V4.1-Flash 前向数据流。

    核心问题

    1. 890 字节/token 是怎么算出来的？

      解答：主 KV 720 字节 + 索引器 K 170 字节，各自由压缩、共享、FP4 三项叠出来

      一条压缩条目在 512 维上以 FP4 存储占 256 字节，加上每 16 通道一个 E4M3 缩放因子（32 个，共 32 字节），合计 288 字节。压缩比为 2 的层每两条 token 才产生一条条目，折合 144 字节/token；压缩比为 1 的层不做跨 token 池化，折合 288 字节/token。全模型只有四个层真正生产主 KV（层 2、8、14、20），前三个压缩比为 2、第四个为 1，于是 $3\times144+288=720$ 字节；索引器键值按同一口径（每条目 68 字节）折合 $3\times34+68=170$ 字节。两项相加是 890 字节。完整账目见第 1 章。

    2. CED 为什么能让 prefill 只跑一半的层？

      解答：解码器的全局 KV 不来自本层隐状态，而由编码器末层投影而来

      主干 40 层被划成前 20 层因果编码器与后 20 层解码器。解码器各层的全局 KV 不由各自的隐状态 $H_l$ 算出，而是由编码器最后一层隐状态 $H_{L/2}$ 经投影得到。与跨层共享机制结合后，只有解码器中被指派为 Full 模式的层（层 20）真正执行这次投影，其余解码器层直接读它发布的缓存。既然解码器的全局 KV 在编码器跑完时就已经确定，prefill 阶段就只需要跑编码器半栈。滑动窗口注意力不适用这一点，它仍逐层从本层隐状态计算，因此服务端需要为它做有界重放。完整推导见第 2 章。

    3. 一个 query 到底能看到哪些位置？

      解答：本层窗口内最多 128 个原始位置 + 索引器选出的至多 512 个压缩条目

      可见集由两部分拼成。一部分是滑动窗口内的原始 KV，最多 $n_{\text{win}}=128$ 个；另一部分是该层所属压缩比组的压缩条目中被索引器选中的 Top-512 个。压缩条目按组编号，组 $j$ 覆盖 token $[jr,(j+1)r)$，其位置编码取 $j\cdot r$；尚未产生的条目（编号超出 $\lfloor(i+1)/r\rfloor$）在打分阶段就被置为 $-\infty$，不参与竞争。解码器还有一级候选池：建池层先用块级打分选出 2048 个块、每块 8 个位置，共 16384 个候选，后续层只在这个池内选 Top-512。两部分槽位拼进同一次稀疏注意力调用。完整规则与可运行复算见第 3 章。

    4. 8B 与 16B 的激活参数量是怎么加出来的？

      解答：单层约 377M，编码器半栈 7.89B、解码器半栈 7.58B

      单层每 token 激活的参数量约 377M：注意力 126.6M（层 20 因多出压缩器与索引器为 134.7M）、路由门控 1.97M、共享专家 35.4M、top-6 路由专家 212.3M、超连接模块 0.98M。编码器 20 层合计 7.8929B（其中层 1、14 各含约 157M 的 Engram 稠密投影），解码器 20 层合计 7.5758B。prefill 只跑编码器，对应 8B 口径；decode 跑满全栈，对应 15.5B，约 16B。完整加总见第 4 章。

    5. Engram 与 DSpark 各自补了什么？

      解答：Engram 补可寻址的条件记忆，DSpark 补解码吞吐

      Engram 是插在层 1 与层 14 的 n-gram 哈希查表：每 token 只查 24 行嵌入（阶数 2/3/4 乘 8 个哈希头），但把查到的向量写回残差流的投影矩阵是稠密的，因此它让每 token 多激活约 157M 参数，却不增加任何 KV 缓存。DSpark 是块式推测解码，用 3 个 MTP 块一次前向产出 5 个草稿位置，输入取自层 37、38、39 的注意力输入，末块用 Markov 头与置信头决定接受哪些草稿；它同样不改变主干缓存，只提高 decode 吞吐。完整机制见第 5 章。

    常见误解

    • 「890 字节是每一层缓存相加的结果」——跨层共享后全模型只存 4 份主 KV 与 4 份索引器键值；若每层各存一份，主 KV 一项就是 8352 字节/token，是现在的 11.6 倍。
    • 「压缩比 2 就是每两个 token 平均成一个」——池化权重是组内 softmax 门控（每个通道一组可学习权重），不是算术平均；而且每条压缩条目在索引器里还另有一份 FP4 键。
    • 「Reuse 层复用了 Top-K 索引，所以它看到的和 Full 层一样」——复用索引的前提是同一份主 KV；不同压缩比组的条目编号与位置换算关系不同，跨组不能共用。
    • 「prefill 只要 8B，说明解码器不参与推理」——decode 阶段仍要跑满 40 层；8B 只是 prefill 阶段的计算量口径，不是结构裁剪。
    • 「报告的分层公式说明每个解码器层都有自己的全局 KV 投影」——那是设计的一般形式；与压缩共享机制结合后只有解码器的 Full 层（层 20）执行投影，其余层读它的缓存。

    1. 890 字节的账——压缩、共享与 FP4 各贡献多少

    先把问题收窄到一个可核算的对象：模型每处理一个 token，要为全局注意力在显存里多留多少字节？答案取决于三件事各自省下了什么，所以这一章不直接报数字，而是把条目大小、条目密度、条目份数依次算出来，最后相加。

    1.1 压缩条目：把 $r$ 个 token 池化成一条 KV

    若每个 token 都保留一份完整的键值（见 KV cache），缓存就会随序列长度线性增长，这正是长上下文最贵的一项。压缩注意力的做法是：让每 $r$ 个 token 共同产生一条键值条目，其中 $r$ 是该层的压缩比。于是缓存条目数变成序列长度的 $1/r$。

    把 token 按 $r$ 个一组切开，第 $j$ 组覆盖位置区间 $[jr,(j+1)r-1]$。这一组 $r$ 个 token 的隐状态先各自投影出候选值向量与门控分数，再在组内做 softmax 加权求和——权重由数据决定，不是固定平均[F1]：

    $$C_j = \mathrm{RMSNorm}\!\Big(\sum_{t=jr}^{(j+1)r-1} \mathrm{softmax}_{t'}\big(s_{t'}\big)\, v_t\Big)$$
    • $r$：该层的压缩比，本模型取 1 或 2；
    • $j$：压缩条目的编号，从 0 开始，第 $j$ 组覆盖 token $[jr,(j+1)r)$；
    • $v_t = W_{kv}h_t$：第 $t$ 个 token 的候选值向量；
    • $s_t = W_{gate}h_t$：第 $t$ 个 token 的门控分数，softmax 在这 $r$ 个分数上取；
    • $C_j$：该组的压缩条目，先池化再经过 RMSNorm。

    这个式子有两个容易忽略的点。第一，池化权重是逐通道的门控，同一组里不同维度可以有不同权重组合，所以它不等于把 $r$ 个向量相加再除以 $r$。第二，条目需要自己的位置编码：压缩后的一条条目代表 $r$ 个原始位置，实现给它的位置取组起点 $j\cdot r$，而不是组内某个 token 的位置[F1]。

    当 $r=1$ 时门控退化：每组只有一个 token，softmax 在单元素上恒为 1，条目就是 $\mathrm{RMSNorm}(W_{kv}h_t)$。也就是说压缩比为 1 的层不做跨 token 池化，每个 token 仍然产生一条条目——它的节省来自别处，不是压缩。这一点在第 1.3 节的份数账里会体现出来。

    池化的数值路径也有一处实测细节：同一条池化在 fp32 层面对照时差异为 4.5e-6（相对 2.2e-6），转成 bf16 后 4096 个元素中有 5 个落在不同 ulp[N8]。也就是说压缩器内部用 fp32 计算、输出再转回 bf16 这一安排不是多余的——它把舍入推迟到最后一步。

    补充：压缩发生在 token 方向，与 MLA 的压缩方向不同

    低秩潜变量注意力（MLA）把每个 token 的键值从「多头乘头维」压成一条低维潜向量，削减的是每个 token 内部的宽度；压缩注意力的池化削减的是token 方向的条数。两者可以叠加，本模型也同时用了：压缩比决定条数，条目的 512 维宽度则沿用潜变量那一套。理解这一点可以避免把「压缩比 2」误读成「条目宽度减半」。

    1.2 一条条目 288 字节：FP4 与逐通道缩放因子

    每条条目的字节数由存储格式决定。主 KV 以 FP4 存储，具体格式是 MXFP4（见 MXFP4 量化 与 混合精度量化）：数值本身是 E2M1（1 位符号、2 位指数、1 位尾数，可表示 $\{0,0.5,1,1.5,2,3,4,6\}$ 及其相反数），每 16 个通道共享一个 E4M3 缩放因子，并且不带第二级全局缩放[C3]。

    于是每条条目的字节数由两块组成。第一块是数值：512 维、每个数值 4 位，两个数值拼成一个字节，共 $512/2 = 256$ 字节。第二块是缩放因子：每 16 个通道一个，共 $512/16 = 32$ 个，每个 1 字节（E4M3），合计 32 字节。两块相加：

    $$\underbrace{\frac{512}{2}}_{\text{FP4 数值}} + \underbrace{\frac{512}{16}}_{\text{E4M3 缩放因子}} = 256 + 32 = 288\ \text{字节}$$
    • $512$：主 KV 条目的通道数（即潜变量维度），该模型所有全局 KV 条目都是这个宽度；
    • $512/2$：每个数值占 4 位，因此每 2 个通道占 1 字节；
    • $512/16$：每 16 个通道共享一个缩放因子；
    • $288$：一条压缩条目（不含索引器键值）的字节数。

    把 288 字节拆成「数值 256 + 缩放 32」而不是笼统记作 288，是因为后面两项都会用到：一旦通道数或缩放粒度变化，两个分量要分别重算。

    低精度的代价可以直接量出来：在 512 维的归一化输出上，FP4 的相对误差为 9.5%，FP8 为 2.65%，前者是后者的 3.58 倍[N5]。报告称训练中观察到的最大幅值约为 10，而 E4M3 缩放因子能表示的上界是 $448\times6=2688$，尚有约 268 倍的余量。精度换来的空间收益是 4 位对 8 位——同样通道数下字节减半。这个取舍在后面的账里体现为：主 KV 用 FP4 而窗口 KV 保持 FP8。

    补充：为什么缩放因子按 16 通道而不是整条条目

    FP4 只有 4 位表示能力，若不分组缩放，一条条目内部数值的动态范围会被拉得很窄：整条用一个缩放因子时，某个特别大的通道会迫使其他通道全部落到低量级上。按 16 个通道分组后，每组各自有自己的尺度，组内的相对关系仍能保留。代价是每 16 个通道多 1 字节开销（$512/16=32$ 字节，约为数值部分的 12.5%）。分辨率与开销的折中就是这条 16 的粒度，它直接决定了 288 这个数：若把粒度放宽到 32，条目会变成 $256+16=272$ 字节。

    1.3 只有四个层生产主 KV：份数账

    有了「每条 288 字节」和「每 $r$ 个 token 一条」，还差最后一个因子：全模型一共要存多少条这样的条目。这一步的关键在于，并不是每一层都存自己的全局 KV。

    跨层共享把主干切成若干组，组内只由第一个层（称为 source 层）生产一份主 KV，其余层读取同一份[C2]。实测的分组是层 2–7、8–13、14–19、20–39，对应的 source 层为 2、8、14、20。也就是说，整个 40 层主干只生产 4 份主 KV，而不是 40 份。判定哪个层是 source、哪一层复用的是 Full / Reindex / Reuse 三模式，属于第 3 章的内容；这一章只需要这个结论：生产份数是 4，压缩比分别是 2、2、2、1。

    逐项折算到「每个 token 贡献多少字节」。压缩比为 2 的层每 2 个 token 产生一条 288 字节的条目，因此对序列里每个 token 平均贡献 $288/2 = 144$ 字节；压缩比为 1 的层不做池化，每个 token 一条，贡献 288 字节。实测配置里层 2、8、14 的压缩比为 2，层 20 的压缩比为 1[C2]：

    项目每条条目压缩比 2 的 source 层（2、8、14）压缩比 1 的 source 层（20）
    主 KV（512 维 FP4 + 逐 16 通道缩放因子）$256+32=288$ B每 2 token 一条，折合 144 B/token每 token 一条，288 B/token
    索引器 K（128 维 FP4 + 逐 32 通道缩放因子）$64+4=68$ B每 2 token 一条，折合 34 B/token每 token 一条，68 B/token

    表里第二行的索引器 K 是另一条旁路所需的键：稀疏注意力要用一个轻量索引器给压缩条目打分，才决定选哪些条目，所以每条压缩条目需要额外配一份供打分用的键。它同样是 FP4，但宽度是 128 维（索引头维）。数值部分的口径与主 KV 相同（两个数值一字节，$128/2=64$ 字节），缩放因子却是每 32 通道一个 E8M0——粒度与类型都与主 KV 的每 16 通道 E4M3 不同。因此每条 $128/2 + 128/32 = 64+4 = 68$ 字节[C3]。

    把两行各自的四个 source 层加起来[N1]：

    $$\underbrace{3\times144 + 288}_{\text{主 KV}} + \underbrace{3\times34 + 68}_{\text{索引器 K}} = 720 + 170 = 890\ \text{字节/token}$$
    • $3\times144$：三个压缩比为 2 的 source 层，各折合 144 B/token；
    • $288$：压缩比为 1 的 source 层 20，折合 288 B/token；
    • $3\times34 + 68$：索引器 K 按同一口径折算；
    • $890$：全模型每 token 的全局 KV 缓存（常驻显存）。

    主 KV 的 720 与索引器 K 的 170 是两项独立开销，把 890 归到其中任何一项名下都不对：主 KV 占 81%，索引器 K 占 19%，两者都由「压缩 + 共享 + FP4」共同压出来——压缩决定条数、共享决定份数、FP4 决定每条大小，三者缺一不可。

    报告称这个数字约为 DeepSeek-V4-Flash 对应开销的 1/4；报告另给出相对 DeepSeek-V1 的 1/437 与服务实现持久化的 1/8 两个倍数[N9]。这三个倍数都登记为报告宣称：本页缺对方模型的配置与缓存结构，无法独立推导，因此只陈述宣称本身，不据此比较架构优劣。

    展开：890 的完整加总与「不共享会是多少」的反事实

    构造示例（数值取自官方配置与参考实现的常量，非额外实跑）：把上式的每一项拆开写。

    主 KV 一项：压缩比 2 的三个层，每 token 折合 $288 \div 2 = 144$ 字节；压缩比 1 的层 20，每 token 288 字节。合计 $144 \times 3 + 288 = 720$ 字节。

    索引器 K 一项：每条 $128 \div 2 + 128 \div 32 = 68$ 字节（数值 $64$ 字节，加每 32 通道一个 E8M0 缩放因子 $4$ 字节）。压缩比 2 的三个层折合 $68 \div 2 = 34$ 字节/token；压缩比 1 的层 20 折合 68 字节/token。合计 $34 \times 3 + 68 = 170$ 字节。

    两项相加 $720 + 170 = 890$ 字节/token。

    反事实：假如不做跨层共享，每个 ratio 大于 0 的层都各存一份主 KV。压缩比 2 的层有 18 个（层 2–19），压缩比 1 的层有 20 个（层 20–39）。主 KV 一项就是 $18 \times 144 + 20 \times 288 = 2592 + 5760 = 8352$ 字节/token，是共享后 720 的 11.6 倍。这个对比说明：在 890 这个数字里，跨层共享贡献的是「份数」这一维度的压缩，与压缩比贡献的「条数」、FP4 贡献的「每条大小」是三件独立的事。

    本章问题

    1. 890 字节由哪两项构成？各自是怎么算出来的？

      解答：主 KV 720 字节 + 索引器 K 170 字节，算法是「每条大小乘折算密度再乘份数」

      主 KV 一项：一条条目在 512 维上以 FP4 存储占 $512/2=256$ 字节，加 $512/16=32$ 个 E4M3 缩放因子共 32 字节，得 288 字节/条。三个压缩比为 2 的 source 层（层 2、8、14）每 2 个 token 产生一条，折合 144 字节/token；压缩比为 1 的层 20 每 token 一条，折合 288 字节/token。合计 $3\times144+288=720$ 字节。

      索引器 K 一项：供索引器打分用的键宽 128 维，同样 FP4，每条 $128/2+128/32=68$ 字节（缩放因子为每 32 通道一个 E8M0）；按同一折算口径得 $3\times34+68=170$ 字节。

      两项相加为 890 字节/token。需要强调「份数只有 4」这个前提：若每层各存一份，主 KV 一项就是 8352 字节/token。

    2. 为什么跨层共享能把主 KV 从 8352 字节压到 720 字节，而不是压到 1/40？

      解答：共享只减少份数，不改变条数与每条大小；剩下的是压缩比差异导致的必然开销

      跨层共享做的是把「40 个层各存一份」变成「4 个组各存一份」，份数从 40 降到 4，这是 10 倍。但 720 相对 8352 只有 11.6 倍，看起来接近但算法不同：8352 是按 38 个层各存一份算的（压缩比 2 的 18 层 + 压缩比 1 的 20 层），而 720 是 4 个 source 层按各自的压缩比折算后相加。两者的差别不只是份数，还包括被共享掉的那些层本来有不同的压缩比。

      换一种算法看得更直接：共享后保留的 4 个 source 层自身也要占位置，其中层 20 的压缩比是 1（每 token 一条 288 字节），这是四份里最贵的一份，占总量的 40%。共享能省掉的是「重复的份数」，省不掉「压缩比 1 那层必须逐 token 存」这件事——要再压这一项，只能改压缩比或改存储精度。完整的分组与模式判定见第 3 章。

    2. prefill 为什么只跑一半——CED 把解码器的全局 KV 前移

    第 1 章算清了「缓存里存多少」。但缓存的来源还没交代：这些条目由哪些层、用什么输入算出来？这个问题直接决定了 prefill 阶段需要跑多少层，因此先回答它。

    2.1 主干被切成编码器与解码器两半

    主干 40 层不是一条同质的栈。它被划成前 20 层（层 0–19）与后 20 层（层 20–39）两段，报告称前者为因果编码器、后者为解码器，合起来叫 CED（Causal Encoder–Decoder）[C1]。两段的差别不在层结构，而在全局 KV 从哪里来：编码器中各组的 Full 层（层 2、8、14）从本层隐状态算出该组主 KV，组内其余层读取这一份；解码器各层则不由本层隐状态算，而由 $H_{L/2}$ 投影而来。

    层与层之间靠残差流串联（见 残差连接），所以「第 20 层拿到的输入」就是「第 19 层的输出」——这一点在下一节会直接用到。

    2.2 解码器的全局 KV 由 $H_{L/2}$ 投影而来

    报告给出的形式化描述很直接：对于上半段（解码器，$l > L/2$），键值条目不由各自的隐状态 $H_l$ 导出，而是直接从第 $L/2$ 层的隐状态 $H_{L/2}$ 投影，投影权重按层各自不同[C6, F7]：

    $$C_l = H_{L/2}W_l^{KV},\qquad Z_l = H_{L/2}W_l^{Z},\qquad l > L/2$$
    • $L$：主干层数，$L=40$，因此 $L/2=20$；
    • $H_{L/2}$：编码器最后一层的隐状态，即第 20 层的输入（第 19 层的输出）；
    • $W_l^{KV}, W_l^{Z}$：第 $l$ 层的投影权重，逐层不同，不是全栈共享一组；
    • $C_l, Z_l$：第 $l$ 层要用的全局键值条目与配套表示。

    因此「共享」这个词需要精确一点：共享的是输入 $H_{L/2}$，不是投影结果。每个解码器层照旧有自己的投影权重，只是喂进去的东西换成了同一个编码器输出。

    与压缩共享机制结合后还有一层收窄：真正执行这次投影的只有解码器中被指派为 Full 模式的层。报告写明，结合之后由 Full 层从编码器末层隐状态计算全局 KV[C6]；在本模型的配置里这个层是层 20。其余解码器层读它发布的缓存，不再自己算。参考实现中的表现是「层 20 的压缩器读取它自己的注意力输入」，而该输入恰好就是层 19 的输出，与公式中的 $H_{L/2}$ 对上。

    这就是 prefill 减半的来源：解码器所需的全局 KV 在编码器跑完时就已确定，所以 prefill 阶段可以只跑编码器半栈。需要区分的是，这条结论关于计算量，不是关于结构——decode 阶段仍要跑满 40 层。

    补充：报告的设计描述与参考实现的分工

    报告描述的是设计意图：解码器的全局 KV 由 $H_{L/2}$ 投影，因而具备提前退出的条件。参考实现里没有「prefill 只跑编码器」的分支——它对任何 prefill 都逐层跑满 40 层[C11]。也就是说，报告中的「接近减半的 prefill 计算」与「有界重放」属于服务端部署时的优化，参考实现是可读的模型定义，不是性能路径。本页把两者分开陈述：前者标为报告宣称，后者标为参考实现的实际行为。用一句话概括边界——本页能核对的是「解码器全局 KV 的输入是 $H_{L/2}$」，不能核对的是「服务端真的省掉了一半」。

    2.3 滑动窗口 KV 不能一起省

    既然解码器的全局 KV 可以前移，为什么不把滑动窗口的 KV 也一起前移，让 prefill 跑得更少？答案是两者的作用对象不同：全局 KV 是压缩后的远距离摘要，滑动窗口 KV 是最近位置的原始精度副本，每个 query 必然读到（见 滑动窗口注意力）。

    关键在于滑动窗口 KV 依赖本层经过完整计算的隐状态，而第 $l$ 层的隐状态要等第 $l-1$ 层算完才能得到。这条依赖链无法用「读编码器输出」替代——编码器末层的隐状态不包含「解码器前一层如何重新混合过信息」的结果。因此服务端要省掉解码器的窗口重算，只能采用有界重放：重算最后 $n_{\text{win}}$ 个位置就够，因为再往前的窗口内容已经滑出可见范围。这一点属于服务实现，本页只登记其成立条件（见文末范围说明）。

    两条路合起来可以看到设计的一致性：全局 KV 之所以能前移，是因为它本来就没打算记住细节——它已经是压缩摘要；窗口 KV 之所以不能前移，正是因为它要保留细节。省的对象不同，可省的程度也就不同。

    本章问题

    1. 解码器的全局 KV 从哪里来？参考实现里对应哪个位置？

      解答：来自编码器末层隐状态 $H_{L/2}$ 的投影；参考实现中即层 20 的压缩器读取自己的注意力输入

      报告给出 $C_l = H_{L/2}W_l^{KV}$、$Z_l = H_{L/2}W_l^{Z}$（$l>L/2$），即解码器各层的键值条目由编码器最后一层的隐状态投影得到，投影权重逐层不同。与跨层共享结合后，只有解码器的 Full 层（本模型为层 20）执行这次投影，其余解码器层复用它发布的缓存。

      参考实现里的对应现象是：层 20 的压缩器不读自己的隐状态，而读它自己的注意力输入——而第 20 层的注意力输入就是第 19 层的输出，即 $H_{L/2}$。两处描述指向同一件事：共享的是输入而非投影结果，各解码器层仍有各自的投影权重。

    2. 既然解码器全局 KV 可以提前算出，为什么滑动窗口 KV 不能同样处理？

      解答：窗口 KV 依赖本层的完整隐状态，而该隐状态的依赖链无法用编码器输出替代

      全局 KV 是压缩摘要，允许由编码器末层一次性投影；窗口 KV 是最近位置的原始精度副本，必须由本层经过完整注意力和前馈计算后的隐状态生成。第 $l$ 层的窗口 KV 需要第 $l$ 层的隐状态，而第 $l$ 层的隐状态又要等第 $l-1$ 层算完，这条链不能跳过，因此窗口 KV 无法像全局 KV 那样「前移」到编码器末尾。

      服务端的替代办法是有界重放：只重算最后 $n_{\text{win}}$ 个位置即可，因为更早的位置已经滑出窗口、不在可见集内。这一优化属于服务实现，参考实现中不含该分支。

    3. 一个 query 看到哪些位置——窗口、压缩条目与两级筛选

    第 1 章算出缓存里有什么，第 2 章说明这些条目由谁产生。两者都还没回答一个更直接的问题：给定层号和 query 位置，这次注意力到底把哪些键值取出来算？这一章把「哪些位置可见」与「可见的位置里选哪些」分开说——前者是规则，后者是打分结果。

    3.1 可见集由两部分拼成

    全局 KV 是压缩摘要，粒度粗；只靠它，模型对最近几个 token 的分辨能力会被池化抹平。所以每层的可见集由两部分拼成：

    • 窗口部分：本层滑动窗口内的原始 KV，最多 $n_{\text{win}}=128$ 个位置。这部分未压缩、保持 FP8，位置编码用原序列下标（见 滑动窗口注意力）。
    • 压缩部分：该层所属压缩比组的压缩条目中被索引器选中的 Top-$K$ 个，$K=512$。条目按组编号，第 $j$ 组覆盖 token $[jr,(j+1)r)$，位置编码取 $j\cdot r$（见 RoPE）。

    这些取值全部来自官方配置，并与真实张量头的形状一致：窗口 128、索引 Top-512、候选 $2048\times8=16384$、索引头 $32\times128$、KV 头 $1\times512$[N4]。

    两部分的槽位在下标空间里用同一个索引表表示：窗口部分按位置索引，压缩部分按条目编号索引。它们拼进同一次稀疏注意力调用，也就是说 softmax 在两部分槽位的并集上做一次归一化，而不是分别算两次再合并[C2]。这一点在 3.5 节的公式里会看得更清楚。

    3.2 可达条目数：整组出现过才算

    压缩条目不是想用就有。一个条目由 $r$ 个 token 池化而来，只有这 $r$ 个 token 都出现之后，条目才存在。于是「编号 $j$ 的条目是否可达」有明确判据：整组覆盖的最后一个位置 $(j+1)r-1$ 必须不超过当前 query 位置 $i$。

    把这条判据写成条目数[F3]：

    $$n_{\text{reach}}(i) = \left\lfloor \frac{i+1}{r}\right\rfloor \quad(\text{prefill}),\qquad n_{\text{reach}}(s) = \left\lfloor \frac{s+1}{r}\right\rfloor \quad(\text{decode})$$
    • $i$：query 在序列中的位置（0 起）；
    • $s$：解码步编号；
    • $r$：该层的压缩比；
    • $n_{\text{reach}}$：从条目 0 起连续可达的条目条数。编号不小于该值的条目在打分阶段被置为 $-\infty$，不参与竞争。

    用本页贯穿的算例核算。该算例追踪位置 $i=4999$ 的 query 在层 2 与层 20 上的开销与可见范围（下称穿越示例）：在压缩比 $r=2$ 的层上，它的可达条目数是 $\lfloor 5000/2\rfloor = 2500$ 条，覆盖 token $0$ 到 $4999$——正好是它能看到的全部历史。同一条 query 在压缩比 $r=1$ 的层上，可达 5000 条。这也解释了为什么压缩比 1 的层更贵：它保留的位置更细。

    可达性判据对 prefill 与 decode 两种形态都成立；实测在等比缩小模型上，修正后（fp32）两种形态逐位置一致[N7]。

    注意判据是「整组出现」而不是「组首出现」。位置 $i=4$、$r=2$ 时，组 2 覆盖 token $[4,5]$，它的组首 $4$ 已经出现，但组尾 $5$ 还没出现，因此该组尚不可达，可达数是 $\lfloor 5/2\rfloor = 2$ 而不是 3。把判据写成「组首出现」会把一条凭空多出的条目算进可见集。

    展开：可达条目数的枚举核对（构造示例）

    构造示例（用 $r=2$ 的小规模序列，便于手算）。逐位置列出「按整组出现」判据枚举到的条目数，与公式对比：

    query 位置 $i$已完成的组枚举条目数$\lfloor (i+1)/2\rfloor$
    0无（组 0 覆盖 0–1，组尾未出现）00
    1组 011

    公式与枚举逐行一致。位置 $i=0$ 时没有任何条目可达——它只能看窗口里的内容，这与「序列第一个 token 没有历史可压缩」的直觉吻合。第 3.4 节的代码会把这个核对扩展到更大的规模。

    3.3 两级筛选：先在块级别缩范围，再在位置级别选 Top-512

    可达条目随上下文线性增长：1M 上下文、压缩比 2 时约 50 万条，而 $K$ 只有 512。要选得准，直接对全部可达条目逐条打分当然可以，但解码时每个 query 都重算一遍代价不小。分层稀疏索引器的做法是把选择拆成两级[C7]。索引器本身是稀疏注意力的旁路打分模块，其中「用轻量打分选 Top-K 再算注意力」这一基本形态见 稀疏注意力与索引器；本页只讲这一模型在它之上加的两级筛选：

    1. 块级：把位置切成大小 8 的块，块分取块内最大的索引分[F4]。建池层为每个 query 选出 2048 个块。
    2. 位置级：这些块覆盖的位置构成候选池，$2048 \times 8 = 16384$ 个候选位置；后续层只在这个池内选 Top-512。

    在长上下文下，第二级的搜索范围从随上下文线性增长的「全部可达条目」变为固定的 16384 个候选位置，每次选择的代价因此与上下文长度无关。缩减倍数随上下文增长：1M 上下文、$r=2$ 时约为 30 倍。短上下文下可达条目本身少于 16384，候选池不起缩减作用。块级候选池由建池层用自身索引分选出并被后续层共享；位置级 Top-512 则由各 Reindex 层在池内用各自的索引分重算——打分公式相同（$\sum_h w_{q,h}\mathrm{ReLU}(q_h\cdot k_j)$[F2]），分数逐层不同，这也正是 Reindex 与 Reuse 的区别所在。

    有一个边界要单独说明：最新块通常只填了一部分（query 自己所在的位置还没凑满 8 个），若按常规打分，它的块分可能被更早的完整块压过而落选，从而让 query 看不到自己最近的历史。实现对此的处理是把最新块钉住：无论分数高低都保留在候选池内[C7]。

    3.4 三模式：谁算主 KV、谁算 Top-K

    到这里还有一个问题：如果每一层都要自己算主 KV、自己算索引分，第 1 章说的「只有 4 个层生产主 KV」就不成立了。实际上每个压缩比大于 0 的层静态属于三种模式之一，区别在于主 KV 与索引选择各由谁做[C2]：

    模式主 KV 与索引器 KTop-K 选择
    Full自己算自己算；建立候选池仅限建池层（本模型为层 20）
    Reindex复用最近一份自己算（在候选池内）
    Reuse复用最近一份复用最新的选择，不算索引分

    三种模式由配置静态决定，不是运行时按内容切换。实测得到的分工是 Full 层为 2、8、14、20，Reindex 层为 24、28、32、36，其余 30 个压缩层为 Reuse；层 0、1 没有全局 KV，属于纯滑动窗口层。Full 层恰好就是第 1 章说的四个 source 层——这不是巧合：只有自己算主 KV 的层才有索引器 K 可以发布，其余层的索引器只能读别人的[C2]。

    「Reuse」这个名字容易引起误解：它复用的是选择结果，不是可见集。不同压缩比组的主 KV 不同，条目编号与位置的换算关系也不同，跨组不能共用选择。因此复用的前提是同一份主 KV——这也是为什么共享发生在同压缩比的组内（见 跨层 KV 复用）。

    补充：参考实现在组未填满时的一个已实测行为

    参考实现里「发布索引器 K」这一步挂在「本层自己拥有主 KV 且本次前向产出了主 KV」的条件分支内，而「读取索引器 K」是无条件执行的。压缩比大于 1 的层在解码步中每隔 $r$ 步才产出一次主 KV，于是存在若干步它读到的是上一次的前向中最后发布者的缓存——在真实配置下是压缩比为 1 的层 20[C10]。

    本机实测在缩小模型上复现了这一点：偶数解码步层 2 读到的键与层 4 的缓存一致，奇数步读到自己的。这条记录只描述该参考实现的行为，用于说明「prefill 与 decode 的选择结果可以不同」，不外推到服务实现，也不影响可见性规则本身——可达性判据对两种形态都成立。

    3.5 选中的槽位怎么参与计算

    可见集和选择都定了，最后一步是注意力本身。稀疏注意力只对选中的槽位做加权求和，并把每头一个可学习的汇聚点标量加在分母上[F8]：

    $$o = \frac{\sum_{t\in\mathcal{T}} e^{\,q\cdot k_t/\sqrt{d}\,-\,m}\,v_t}{\sum_{t\in\mathcal{T}} e^{\,q\cdot k_t/\sqrt{d}\,-\,m} + e^{\,\text{sink}-m}},\qquad m = \max_{t\in\mathcal{T}}\frac{q\cdot k_t}{\sqrt{d}}$$
    • $\mathcal{T}$：本次选中的槽位集合，含窗口槽位与压缩条目槽位；
    • $q, k_t, v_t$：query、第 $t$ 个槽位的键与值；
    • $d$：注意力头维；
    • $\text{sink}$：该头可学习的汇聚点标量，作为 logit 使用；
    • $m$：选中槽位分数的行最大值，用于数值稳定；分子分母共享同一个 $m$；
    • $o$：该头的输出。

    第一，$m$ 只由选中槽位的分数取得，汇聚点不参与取最大值；分子分母同时乘 $e^{-m}$，所以 $m$ 的取值不改变结果，它只是数值稳定手段。第二，汇聚点只出现在分母：它提供一个「倾倒注意力」的去处，本身不携带任何值向量，因此不影响分子（详见 注意力汇聚点）。第三，索引为 $-1$ 的占位槽位在分子分母都不贡献——它们既不被取值，也不进入指数和。

    窗口槽位与压缩槽位在这里合流：$\mathcal{T}$ 是两者的并集，softmax 在并集上做一次归一化。这也意味着窗口位置与压缩条目在竞争同一份注意力预算，而窗口并没有被赋予额外权重——谁的分高谁拿得多。

    3.6 可达性与 Top-K 语义的复算

    该段代码验证两件事：可达条目数公式与「整组出现」的枚举判据一致；以及不可达条目被置为 $-\infty$ 之后，Top-$K$ 选择不会把它们选进来。

    代码：可达条目数与 Top-K 选择的语义复算 
    """复算两个机制：压缩条目可达数、Top-K 选择语义。纯 Python，无第三方依赖。"""


def reachable_formula(i, r):
    """F3 公式：floor((i+1)/r)"""
    return (i + 1) // r


def reachable_bruteforce(i, r):
    """按「整组出现」逐组枚举：组 j 覆盖 [jr, (j+1)r)，组尾 <= i 才算可达"""
    count = 0
    j = 0
    while (j + 1) * r - 1 <= i:
        count += 1
        j += 1
    return count

    本章问题

    1. 压缩比 2 的层上，位置 4999 的 query 能看到多少个压缩条目？公式里为什么是 $\lfloor(i+1)/r\rfloor$ 而不是 $\lfloor i/r\rfloor+1$？

      解答：2500 条；判据是「整组出现」，组尾不超过 query 位置才算可达

      位置 $i=4999$、$r=2$ 时 $\lfloor 5000/2\rfloor=2500$ 条，覆盖 token 0 到 4999，正好是全部历史。

      两个式子的差别在边界：$\lfloor i/r\rfloor+1$ 等价于「组首出现即可达」，而 $\lfloor(i+1)/r\rfloor$ 要求「组尾也出现」。用 $i=4$、$r=2$ 检验：组 2 覆盖 token 4–5，组首 4 已出现但组尾 5 是未来，因此该组尚未完成池化、条目不存在。前者给 3 条，后者给 2 条——正确答案是 2 条。只有当 $i$ 恰好是组尾（$i+1$ 被 $r$ 整除）时两个式子才相等，所以边界上的差别容易在实际使用中被忽略。

    2. 候选池起什么作用？为什么最新块要被「钉住」？

      解答：把 Top-512 的搜索范围从随上下文增长的条目数变为固定 16384 个候选；不钉住最新块会让 query 看不到自己最近的历史

      可达条目随上下文线性增长（1M 上下文、压缩比 2 时约 50 万条），而 $K$ 只有 512。分层索引器先用块级打分（块分取块内最大值）从建池层选出 2048 个块，块内 8 个位置构成 16384 个候选位置，后续层只在这个池内搜索 Top-512。这样每次选择不必重扫全部可达条目。

      最新块只有部分位置被填充，按常规打分它的块分（块内最大值）虽不至于为零，但若按平均或按「完整块才入选」处理，它很容易落选，导致 query 看不到紧邻自己的那几个位置。钉住最新块保证这部分历史一定进入候选池。这一机制只在解码器使用，编码器层不做候选限制。

    3. 为什么 prefill 和 decode 的选择结果可能不同，但可见性规则相同？

      解答：可见性由「组是否完成」决定，两种形态用同一判据；选择结果取决于索引分，而参考实现在某些解码步读到了别的层的索引键

      可达性判据是「整组覆盖的最后一个位置不超过当前 query」，prefill 的 $\lfloor(i+1)/r\rfloor$ 与 decode 的 $\lfloor(s+1)/r\rfloor$ 是同一判据在两种形态下的写法，实测逐位置一致。

      选择结果则取决于索引分，而索引分来自索引器。参考实现中「发布索引器 K」挂在条件分支内、「读取索引器 K」无条件执行，压缩比大于 1 的层在解码步的组未填满时读到的是上一次前向最后发布者的缓存（真实配置下为层 20），因此同一位置在 prefill 与 decode 下可能得到不同的 Top-K。这条差异是参考实现的已实测行为，只说明「选择结果不保证逐位一致」，不改变可见性规则，也不外推到服务实现。

    4. 8B 与 16B——激活参数的账怎么算

    前三章算的是「存多少」与「看哪些」。还有一笔独立的账：算的时候实际动用了多少参数？报告给出的口径是每 token 激活 8B（prefill）与 16B（decode）。这一章把这个数字从宣传口径拆成可复算的加法。

    4.1 单层 377M 的构成

    一层里的参数分两类。稠密的部分每个 token 都过一遍：注意力投影、路由门控、共享专家、超连接模块和归一化。MoE 的路由专家则是稀疏的：每层存 384 个专家，每个 token 只走其中 6 个。所以「激活参数」不是层参数总量，而是「稠密项全加 + 稀疏项按激活比例折算」[N6]。

    稀疏项的折算需要一个明确的选择规则。路由打分用平方根软加（$\sqrt{\mathrm{softplus}}$），选择时加上一个可学习的修正偏置（见 DeepSeek MoE 与 无辅助损失负载均衡）[C8, F5]：

    $$\text{score} = \sqrt{\mathrm{softplus}\big(xW^\top\big)},\qquad \text{idx} = \mathrm{topk}_{6}\big(\text{score}+b\big),\qquad w = \frac{\text{score}_{\text{idx}}}{\sum_{\text{idx}} \text{score}_{\text{idx}} + 10^{-20}}\times 1.5$$
    • $x$：进入 MoE 的隐状态；$W$：路由打分矩阵；
    • $\text{softplus}(z)=\ln(1+e^{z})$，先取平方根再排序；
    • $b$：每个专家的可学习修正偏置，只参与 ${\rm topk}$ 的选择；
    • $\text{idx}$：被选中的 6 个专家的下标；
    • $w$：这 6 个专家的混合权重，在选中的集合内归一化后再乘路由缩放系数 $1.5$；
    • $10^{-20}$：分母的数值稳定项，避免全零。

    公式里最关键的一点是偏置的作用范围：它进入 ${\rm topk}$ 的排序，但不进入权重计算——权重来自原始分数。所以调节偏置可以改变「哪些专家被选中」，不会改变「被选中的专家各占多少权重」。这个设计让负载均衡的调节不干扰前向输出的数值尺度（旁证见 4.2 节末）。

    超连接把残差流按 4 份并行携带，用三套系数（读前、写后、以及 4 份之间的混合）读写[F6]，其中混合矩阵经 20 轮行列交替归一化逼近双随机[C9]（见 超连接）。它的参数量来自一个从隐状态到系数的小投影：输入是展平后的 $4\times5120=20480$ 维残差流，输出是读前 4 维、写后 4 维与 4 份之间混合的 $4\times4=16$ 维，合计 $4+4+16=24$ 维系数，因此总参数为 $2\times24\times20480=983{,}040$，约 0.98M。这个模块的意义不在参数量，而在改变了信息流的结构——它让每层读写残差流的路径不止一条，从而分摊了单一路径上的干扰。它的参数量虽小，但每个 token 都要读入并写回全部 $4\times5120=20480$ 维残差流，影响不由参数量衡量。

    5. Engram 与 DSpark——两个不改缓存账的模块

    前面四笔账（缓存、prefill、可见集、激活参数）都围绕主干注意力与 MoE 展开。还有两个模块在配置里占着位置，却不改变其中任何一笔——弄清它们各自补什么，才算把整机成本看全。

    5.1 Engram：把「条件记忆」做成可寻址的查表

    语言模型把知识压进参数里，要用时靠注意力检索。这种检索是「按内容相似度找到相关位置」，当模型需要某个固定的事实片段时，它没有直接寻址的手段。Engram 补的正是这一点：用 n-gram 哈希把上下文里出现的连续片段映射成表下标，直接取出对应的嵌入向量[C4]。

    它的工作方式可以分成三步。第一步，从当前位置往前取长度为 2、3、4 的连续片段，各自用 8 个不同的哈希函数映射到表的下标，得到 $(4-1)\times8=24$ 个下标——这就是为什么说「每 token 查 24 行」。第二步，按这些下标从嵌入表里取出向量。第三步，把取出的向量经过一个稠密投影写回残差流，写入的强度由一个门控决定：门控值取当前残差流与查表结果的归一化点积，先取绝对值、开平方、再保留原符号，最后过 sigmoid（实现里的「带符号平方根」处理，与训练内核一致）[C4]。

    这个组合决定了两笔账怎么记。查表本身是稀疏的：每 token 只取 24 行、每行 256 维，共 $24\times256=6144$ 个表元素，相对于表的总量可以忽略——两层的嵌入表合计约 196B 参数[N3]，但每 token 实际取回的元素只有六千多。写回的投影是稠密的：每层 157.33M，无条件计入激活参数。于是 Engram 在账上的表现是「表很贵、激活很便宜但并非免费」：它让编码器半栈多出 314.65M（第 4 章），却完全不增加 KV 缓存——它不产生任何需要保存的键值。

    补充：为什么图像 token 被屏蔽

    Engram 的输入是文本 n-gram 的哈希，图像 token 没有对应的 n-gram 语义，因此实现让图像 span 的 token 跳过 Engram 写入。这属于多模态路径的实现细节，本页只说明它的存在，不展开视觉编码器（见文末范围说明）。

    5.2 DSpark：一次前向产出多个草稿位置

    decode 阶段每生成一个 token 都要走一遍全栈。以下为辅助解释：这一步以访存为主、算力用不满，所以先用一个便宜得多的模块猜出后续若干位置、再让主模型一次性校验是划算的。这个归因是常见解释，来源只说明 DSpark 用于提高解码效率[C5]，未给出瓶颈归因，因此不作为本页的结论。

    它的结构是 3 个 MTP 块（multi-token prediction），顺序作用在同一批 5 个位置（块大小 5）上逐层细化，一次前向最终产出 5 个草稿位置。输入不是自回归地一个接一个，而是取主干层 37、38、39 的注意力输入，先在超连接副本维上取均值（该维大小为 4），再把三层结果沿特征维拼接，作为一次性的草稿输入[C5]；块内填充用一个专门的噪声 token（id 128799）占位。草稿块自身是 MoE 结构，128 个路由专家、每 token 激活 3 个——比主干的 384 选 6 更稀疏。

    最后一个块额外带两个头：Markov 头（秩 256）与置信头。Markov 头给草稿序列内部的相邻关系建模，置信头输出每个草稿位置的接受置信度，用于决定接受几个草稿。这两者的具体公式属于训练细节，本页只说明它们的作用位置。

    DSpark 对整机成本的贡献在吞吐，不在缓存：它不产生需要跨步保存的主干缓存，也不改变 890 字节的账。它提高的是「一次前向平均能确认多少 token」这个量——在草稿接受率高的场景下，同一个 decode 步可以推进多个位置。

    本章问题

    1. Engram 每 token 只查 24 行，为什么它还是给激活参数增加了 314.65M？

      解答：查表是稀疏的，但把查到的向量写回残差流的投影是稠密的

      24 行是「$(4-1)\times8$」——阶数取 2、3、4 三段，每段 8 个哈希头，合计 24 个表下标；每行 256 维，所以每 token 实际取回 $24\times256=6144$ 个表元素，相对于两层合计约 196B 的表来说极小。

      真正的开销在后面：取回的向量要经过一个稠密投影才能写回残差流，这个投影矩阵每层 157.33M，只要该层启用 Engram 就要整份参与计算。两层（层 1、14）合计 314.65M，正是第 4 章里编码器半栈比解码器半栈高出的主体。所以「稀疏查表」省的是表访问，「稠密投影」要照常付费——两者要分开记。

    2. 为什么 Engram 与 DSpark 都不改变 890 字节的账？

      解答：890 只统计全局 KV 缓存；这两个模块一个不产生缓存，一个只影响吞吐

      890 字节是「每 token 的全局 KV 缓存（常驻显存）」这个口径下的数字，由主 KV 720 与索引器 K 170 构成（第 1 章），只统计跨层共享后需要保存的压缩条目与索引键。

      Engram 不生成键值——它把查表结果写进残差流就结束了，没有内容需要在解码步之间保存，因此不占缓存槽位。DSpark 是草稿头，它复用主干层的注意力输入来产生草稿（主干缓存照旧由主干产生），自己不新增主干缓存。两个模块影响的是别的账：Engram 抬高激活参数，DSpark 抬高 decode 吞吐。把 890 记作「全模型每 token 的总开销」是常见误解；它只是缓存那一项。

    辅助解释与类比边界

    「两级筛选」是辅助解释：它说明选择过程先在块级别缩小搜索范围、再在位置级别选出 Top-512。边界：它不改变可见性规则（可达性判据与选择是两件事），也不意味着两级筛选一定比单级选得更准——它换的是计算量，准确性仍由索引器的训练质量决定。本页不评价索引器的选择质量。

    另有三处说明同属辅助解释，来源只描述做法、未给出理由：一是「整条用一个缩放因子会让某个大通道迫使其他通道落到低量级」（这是按 16 通道分组的动机，报告只说明选该格式是为兼顾精度与简洁[C3]）；二是「块分取最大值是为了不让高分位置被同块低分位置稀释」（报告只说明块分取块内最大索引分这一做法[C7]）；三是「超连接让读写残差流的路径不止一条，从而分摊单一路径上的干扰」（报告只说明它在相邻层之间维持多条残差流）。这三条都不应被读作来源结论。

    简化条件及其限制

    • 字节账按「每个 source 层各存一份主 KV 与一份索引器 K」计算，不含运行时缓冲（窗口环形缓冲 $128\times512$、候选池掩码、压缩器跨步残态）。这些项随 batch 与实现变化，不影响 per-token 的主账，也不能由本页的 890 推出端到端显存占用。
    • 激活参数按「任意 6 个路由专家」计算（同一层内 384 个专家形状相同），不反映具体 token 的实际选择，也不含专家并行带来的通信开销。
    • prefill 与 decode 的一致性实测使用等比缩小模型（dim 64、7 层），验证的是计算规则而非特定权重输出；缩小模型的绝对值不能外推到真实配置。
    • 可见性与选择规则的核对覆盖 $r\in\{1,2,4\}$、位置范围 $[0,200)$ 与穿越示例的两个点；未覆盖多 batch、chunked prefill 分块边界与张量并行切分。
    • 报告的「接近减半的 prefill 计算」「Bounded Replay」「1/8 持久化」属服务实现或训练实验结论，本页只登记宣称与成立条件，不给推导。
