# ZeroMQ 文章大纲

## 贯穿示例

贯穿全文的具体问题：**一个任务分发系统**——一个进程产出编号 1…6 的任务，若干个工作进程领取任务并处理；同时需要把状态变化广播给若干个监控端。

这个问题足以自然覆盖全部核心机制：

| 章节 | 贯穿示例的推进 | 新增的机制 |
|---|---|---|
| 第 1 章 | 先尝试用裸 TCP 实现，暴露三个具体障碍 | 消息边界、多对端分发、断线重连 |
| 第 2 章 | 用 PUSH/PULL 实现任务分发，观察 1…6 落到哪个 worker | 轮询、公平队列、socket 类型 |
| 第 3 章 | 抓取 worker 收到的第一条消息在 TCP 上的原始字节 | 帧、flags、多段消息、greeting |
| 第 4 章 | 加入监控端，用 PUB/SUB 广播状态；再看 worker 需要回话时改用 ROUTER/DEALER | 扇出、订阅过滤、路由标识信封 |
| 第 5 章 | 让 worker 停止取任务，观察任务分发端与广播端的不同反应 | 每对端队列、HWM、mute 状态、丢弃 vs 阻塞 |
| 第 6 章 | 罗列这个系统里 ZeroMQ 不替应用做的事 | send 语义、slow joiner、断连丢队列、线程安全 |

数字规模刻意很小（6 个任务、3 个 worker、HWM=5），全部可手工追踪。

## 页面开头

- 具体问题引入：任务分发系统。用两句写出裸 TCP 下最先撞上的墙：`send(b"job-1")` 与 `send(b"job-2")` 两次调用，接收端一次 `recv` 可能拿到 `b"job-1job-2"`，也可能拿到 `b"job-1jo"`——TCP 交付的是字节流，消息边界得自己造。
- 概念简要解释：ZeroMQ 是链接进应用进程的消息库（K1 简要定义）。
- 学习目标：Q1–Q5，共 5 条。
- 常见误解：M1（不是 broker）、M2（不保证不丢）、M3（send 成功 ≠ 送达）、M5（过滤在发布端）放页面开头的 misconceptions 组件。M4、M6 放到对应章节处理（M4 → 第 2 章 bind/connect，M6 → 第 6 章边界）。
- 来源摘要 blockquote.meta：ZMTP RFC 23/28/29/30（stable）+ 0MQ API 手册 + libzmq v4.3.5 源码 + 本机实测（pyzmq 27.1.0 / libzmq 4.3.5）。
- 与第 1 章的过渡：把开头的墙具体化成三面，第 1 章逐一说明。

不使用 context-box（本页开头没有需要键值网格呈现的结构化背景）。

## 章节设计

### 第 1 章｜裸 TCP 到消息库之间缺了什么

- 章节问题：要实现任务分发，直接用 TCP socket 需要自己补哪几件事？
- 对应范围：Q1；K2、K8；B1、B2
- 正文要点：
  1. 障碍一：字节流无分隔。给出具体的 `recv` 结果不确定性，说明必须自己设计长度前缀或分隔符。
  2. 障碍二：一条 TCP 连接只连一个对端。3 个 worker 就是 3 条连接，"这条任务给谁"的决策代码必须自己写，还要处理某个 worker 卡住时怎么办。
  3. 障碍三：连接会断。断开后重连、重连期间待发数据放哪、恢复后是否重发，都得自己处理。
  4. ZeroMQ 的定位：这三件事分别对应它的帧、socket 类型的路由策略、每连接队列 + 自动重连。此处只给结论，机制由后续章节展开。
  5. 澄清"MQ"与"Zero"（B1、B2）：没有 broker 进程，队列在应用进程自己的内存里；"Zero" 指的是零 broker、零管理员一类的设计取向，不代表零延迟或零丢失。M1 在此关闭。
- 材料：无公式。ASCII 图示一张——三个障碍与三个对应机制的对照（职责：让读者建立"问题→机制"的映射，后续每章回到其中一格）。
- 前置知识：TCP 字节流特性就地一句说明，不建概念页。
- 验证项：读者应能说出"为什么 ZeroMQ 传输的最小单位不能是字节"。
- 章末过渡：三个障碍中最容易低估的是第二个——"这条任务给谁"。ZeroMQ 的回答很反直觉：`send` 根本不指定收件人。

### 第 2 章｜send 不指定收件人，收件人由 socket 类型决定

- 章节问题：一条消息去往哪个对端，是谁决定的？
- 对应范围：Q2；K1、K3、K5（首次出现）、K8；C1、C3、C4；C15、M4
- 正文要点：
  1. ZeroMQ 的核心反直觉点：`zmq_send()` 只有 socket 和数据两个要素，没有目标地址。目标由 socket 类型的出站策略决定（C1）。
  2. 出站三种策略与入站一种策略的定义：轮询（一条消息只去一个对端，按顺序轮换）、扇出（一条消息复制给所有对端）、按标识定向（从消息里取目标）；入站统一是公平队列（轮流从各对端读，不让某个高频对端饿死其他对端）（C3）。
  3. 贯穿示例落地：PUSH bind + 3 个 PULL connect，发 6 个任务，实测结果 1,4 / 2,5 / 3,6（N2）。
  4. 轮询的关键细节：它只在"队列未满"的对端间轮换，卡住的对端会被跳过而不是拖慢全局（C4）。用 N8 实测展示：慢对端只拿到 0 和 2，其余 8 条全给了空闲对端。这一条同时解释了"为什么一个卡住的 worker 不会阻塞整个分发"。
  5. bind 与 connect 的角色澄清（C15、M4）：两者只决定谁提供端点地址，不决定消息方向、也不要求顺序。实测：PUSH 先 connect 到无人监听的地址并 send，PULL 随后 bind 立刻收到（N7 后半段）。
  6. socket 类型的配对约束：类型之间有兼容表（PUSH↔PULL、PUB↔SUB、REQ↔REP、DEALER↔ROUTER 等），配错会得到无法解释的行为。
- 材料：
  - 对照表格一张：8 种稳定 socket 类型 × （方向 / 出站策略 / 入站策略 / 兼容对端 / 队列满时动作）。职责：本表是全文的索引，第 4、5 章都回到它。数据来自 S1 摘要表，队列满一列在第 5 章展开。
  - 可运行代码折叠块：PUSH/PULL 轮询实验（N2）。
  - 补充折叠块：轮询跳过满队列的源码依据与实测（C4、N8、S10 `lb_t::sendpipe`）。
- 前置知识：无新增。
- 验证项：给定 1 个 PUSH 与 2 个 PULL、发 5 条消息，说出各 PULL 分别拿到哪几条以及依据；说明为什么 PULL 的入站策略必须是公平队列而不是"先到先服务"。
- 章末过渡：路由策略解释了消息去哪，但还没解释"一条消息"到底是什么——worker 收到的 `b"1"` 在 TCP 上并不是一个孤零零的字节。

### 第 3 章｜一条消息在 TCP 上的真实字节

- 章节问题：ZeroMQ 用什么线格式把"离散消息"叠在字节流上？
- 对应范围：Q4；K2、K7；C2、F1、F2；N1
- 正文要点：
  1. 观察方法：写一个普通 TCP 服务端假装 ZeroMQ 对端，完成最小 ZMTP 握手，然后打印真实字节。这样能看到库平时藏起来的东西。
  2. greeting（F1）：连接建立后先发 64 字节固定结构——10 字节签名（`%xFF` + 8 字节无语义 padding + `%x7F`）、2 字节版本、20 字节安全机制名（右侧补零）、1 字节 as-server、31 字节填充。给出实测十六进制并逐段对齐。版本字节实测是 `03 01`（ZMTP 3.1，RFC 37），RFC 23 规定的是 `03 00`，必须写清这个区别。
  3. 握手命令：greeting 之后是 READY 命令帧，携带 `Socket-Type`、`Identity` 等元数据。实测 body：`\x05READY\x0bSocket-Type\x00\x00\x00\x06DEALER\x08Identity\x00\x00\x00\x03cli`。这解释了对端如何知道"你是个 DEALER"。
  4. 帧头（F2）：1 字节 flags + 长度字段 + 帧体。flags 只有三个有效位：MORE（bit 0）、LONG（bit 1）、COMMAND（bit 2），高 5 位保留为 0。长度字段短帧 1 字节（体 0–255）、长帧 8 字节网络字节序。长度不含 flags 也不含自身，所以空帧长度为 0。
  5. 多段消息（C2）：`[b"A", b"BC"]` 在线上是 `flags=0x01 size=1 body=A` 后跟 `flags=0x00 size=2 body=BC`。MORE=1 的帧串 + 一个 MORE=0 的帧 = 一条消息，全收或全不收。
  6. 手算练习：给定字节串 `01 03 61 62 63 00 01 64`，逐字节解析出它是一条两帧消息 `[b"abc", b"d"]`。这是本章的可手算示例。
- 材料：
  - ASCII 图示一张：64 字节 greeting 的字段偏移布局（职责：让 10/2/20/1/31 的切分可视化，正文的十六进制串能对着数）。
  - 公式区：F1、F2 的 ABNF 片段 + flags 位表。
  - 可运行代码折叠块：抓包脚本 + 完整实测输出（N1）。
  - 数值示例折叠块：`01 03 61 62 63 00 01 64` 的完整逐字节手算。
- 前置知识：十六进制与位运算就地说明（"bit 0 是最低位"）。
- 验证项：给定 `flags=0x03`，说出它同时代表什么；说明为什么空帧的 size 是 0 而不是 1。
- 章末过渡：帧解释了消息的形状，路由策略解释了消息的去向。但第 2 章只讲了轮询这一种去向；广播和定向回话需要另外两种。

### 第 4 章｜广播与定向回话：扇出和路由标识

- 章节问题：怎么把状态广播给所有监控端？worker 处理完后怎么让分发端知道是谁回的？
- 对应范围：Q2；K4、K10；C5、C6、C12、C18；M5
- 正文要点：
  1. 广播需求 → PUB/SUB。PUB 的出站策略是扇出：一条消息复制到每个订阅者的队列。
  2. 订阅前缀与过滤位置（C5、M5）：SUB 端调用订阅 API，但过滤不在 SUB 端执行。ZMTP 规定过滤在发布端；SUB 会把订阅前缀作为一个消息发给 PUB（`%x00 short-size %d1 subscription`），PUB 对消息第一帧的起始处做二进制比较。实测证明：只订阅前缀 `A` 时，`B-nomatch` 根本没有出现在 TCP 连接上（N9）。这条既是机制也是 M5 的关闭点。
  3. 订阅是加性、不幂等的（C18）：同时订阅 "A" 和 "" 等于只订阅 ""；订阅两次 "A" 需要退订两次。
  4. 定向回话需求 → ROUTER/DEALER。ROUTER 为每个对端维护带唯一 identity 的队列；入站时在消息前加一帧 identity 交给应用，出站时剥掉第一帧作为目标查找队列（C6）。
  5. 实测对照（N5）：同一个 ROUTER 收到 DEALER 的消息是 `[b'worker-7', b'hello-from-dealer']`，收到 REQ 的消息是 `[b'client-1', b'', b'hello-from-req']`。多出来的空帧是 REQ socket 自己加的分隔帧（C12）——这解释了为什么 ROUTER 代码里经常见到"跳过一个空帧"的处理。
  6. ROUTER 找不到目标时的行为：默认静默丢弃、不阻塞；设 `ZMQ_ROUTER_MANDATORY=1` 改为返回 EHOSTUNREACH（C6）。这是"消息发出去了但对端没收到、也没报错"的常见来源。
- 材料：
  - 可运行代码折叠块：ROUTER 同时接 DEALER 与 REQ 的信封对照（N5）。
  - 可运行代码折叠块：手写 SUB 对端验证发布端过滤（N9）。
  - 补充折叠块：ROUTER identity 的来源（对端可通过 `ZMQ_ROUTING_ID` 显式指定，否则由 ROUTER 生成）。
  - 回到第 2 章的对照表，标出 PUB 与 ROUTER 各自落在哪一格。
- 前置知识：无新增。
- 验证项：ROUTER 要回复刚收到的消息，出站消息的第一帧必须是什么；SUB 订阅空前缀与不订阅任何前缀，收到的消息有何区别。
- 章末过渡：前三章都假设对端跟得上。现实中 worker 会卡住、监控端会掉线——此时消息去哪了，取决于第 2 章那张表最后一列。

### 第 5 章｜队列满了：谁丢消息，谁阻塞

- 章节问题：接收端不读了，消息会丢还是会把发送端卡住？
- 对应范围：Q3；K5、K6；C7、C8、C9、C10、C16
- 正文要点：
  1. 队列的粒度（K5）：ZeroMQ 不是每个 socket 一个队列，而是每个对端一条队列（PUSH/PUB 出站队列，ROUTER/DEALER/XPUB 为双队列）。这决定了 HWM 是"单个对端的上限"，不是全局上限。
  2. HWM 的定义与默认值（C7）：`ZMQ_SNDHWM` / `ZMQ_RCVHWM`，单位是消息条数，默认 1000，0 表示无上限。
  3. 关键限制（C8）：实际容量不保证等于设定值——接收侧可能更高或更低，发送侧可能低至 90%、也可能超过阈值。所以后面的实测条数只能作为"该次运行的观察值"，不能当成规格。这一条必须在实测数据之前给出，否则读者会把实测条数当成保证。
  4. mute 状态与两种反应（C9）：队列满后 socket 进入 mute 状态；PUB/XPUB/XSUB 丢弃且 `send` 永不阻塞，ROUTER 默认丢弃，PUSH/PULL/REQ/DEALER/PAIR 阻塞或返回 EAGAIN 且不丢消息。
  5. 贯穿示例落地（N3）：HWM=5，接收端不读，各发 100 条。PUB：100 条全部被接受，订阅端只收到 5 条，95 条无声消失。PUSH：第 5 条之后返回 EAGAIN，只接受 5 条，PULL 全部收到、零丢失。同一段代码结构、只换 socket 类型，结果性质完全不同——这是 M2 的关闭点。
  6. 丢弃发生在哪一侧（C10）：只把订阅端 RCVHWM 设小并不会丢消息，消息堆在发布端队列里。实测四组对照（N4）：只有发布端 HWM 小时才丢。这纠正了"调大订阅端 HWM 就能防丢"的想法。
  7. 断连时队列被销毁（C16）：对端断开时其队列连带未发消息一起销毁。这是 PIPELINE 规范"除节点意外断开外不丢消息"这句话的确切含义。
- 材料：
  - 可运行代码折叠块：PUB 丢弃 vs PUSH 阻塞对照（N3）。
  - 数值示例折叠块（构造示例）：四组 HWM 组合的对照表（N4），标明这是实测输出而非规格值。
  - 补充折叠块：为什么"实际容量 ≠ HWM"（C8 原文引用 + TCP 传输的解释）。
  - 回到第 2 章对照表填满最后一列。
- 前置知识：阻塞调用与 EAGAIN 就地说明。
- 验证项：一个 PUB 连了 3 个 SUB，其中 1 个卡住，另外 2 个正常——卡住的那个丢消息时，另外两个受影响吗，依据是什么；把 PUSH 换成 PUB 之后，"任务不丢"这个性质还成立吗。
- 章末过渡：至此三个障碍都有了答案。但 ZeroMQ 补的是通信胶水，不是可靠投递——最后需要划清它不做什么。

### 第 6 章｜ZeroMQ 不做什么

- 章节问题：哪些事必须由应用自己实现？
- 对应范围：Q5；C13、C14、C16、C17；B3、B5；M3、M6
- 正文要点：
  1. `send` 成功的确切含义（C13、M3）：只表示消息已入队、库已接管，不表示已上网络、更不表示对端已收到。这就是为什么第 5 章的 PUB 能"成功发送"100 条却只有 5 条抵达。
  2. 消息实际由谁发出（C14、B3）：context 持有 I/O 线程池（默认 1 个线程）；应用线程调用 `send` 只是入队，跨线程交接后由 I/O 线程真正写 socket。纯 inproc 通信不经过 I/O 线程，可把线程数设为 0。这解释了 C13 为什么成立。
  3. slow joiner（B5、N7 前半段）：SUB 建立连接后订阅需要时间才在 PUB 端生效；这期间发出的消息对该订阅者没有匹配订阅，无处可去。实测：connect 后立刻发的 3 条 `early-*` 全丢，等待后发的 3 条 `late-*` 全收。因此"启动即发布"的代码在测试环境常常看起来是对的。
  4. 断连即丢队列（C16）：进程崩溃、对端断开时，内存里的队列随之消失。ZeroMQ 没有持久化、没有重投递、没有确认。
  5. 线程安全（C17、M6）：全部常用类型都非线程安全，跨线程共享是未定义行为。正确做法是每线程一个 socket，用 inproc 在线程间传消息。
  6. 因此必须应用自己做的事：投递确认与重试、幂等设计、超时判定、心跳探活（库提供 `ZMQ_HEARTBEAT_IVL` 等选项，但策略仍由应用定）、消息序列化格式。
  7. 与相邻方案的边界一句话区分：需要消息落盘与消费位点回放，用 broker 型中间件；需要标准化的 RPC 契约与生态，用 gRPC / HTTP；ZeroMQ 的位置是"只搬消息、不管内容、不管持久化"。
- 材料：
  - 可运行代码折叠块：slow joiner 与 connect 先于 bind（N7）。
  - 无新公式。
- 前置知识：无新增。
- 验证项：一个 PUSH socket 在两个线程里被同时使用会发生什么，依据是什么；要保证"任务一定被某个 worker 处理过"，需要在 ZeroMQ 之上补哪些机制。
- 章末：不加过渡（下一节是来源）。

## 讲解顺序依据

知识依赖链：

```
问题（裸 TCP 三障碍）
  → socket 类型与路由策略（回答"去哪"，需要队列概念的最小形态）
    → 帧与线格式（回答"消息是什么"，需要已知有多对端才能理解 identity 的必要性）
      → 扇出与路由标识（第二、三种路由策略，依赖帧概念解释信封）
        → 队列容量与丢弃/阻塞（依赖"每对端一条队列"，第 2 章已铺）
          → 边界（依赖前面全部机制才能说清哪些没做）
```

两处顺序取舍的理由：

- 帧格式（第 3 章）排在路由策略（第 2 章）之后而非之前：先讲帧会让读者面对一堆位定义却不知道用来干什么；先建立"消息要去某个对端"的需求，再看线上字节，ROUTER 信封在第 4 章才有落点。
- ROUTER/DEALER（第 4 章）排在帧格式之后：identity 信封本质是"在消息前加一帧"，不先讲清多段消息就无法准确描述它。
