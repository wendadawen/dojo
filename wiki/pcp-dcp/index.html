    PCP 与 DCP（Prefill/Decode Context Parallelism）：prefill 把长序列计算切到多卡，decode 把 KV cache 切到多卡

    主要依据：vLLM 官方文档《Context Parallel Deployment》（v0.28.0）；vLLM 官方博客《Efficient Decode Context Parallelism with vLLM for Long Context Workloads》（2026-08）；vLLM 源码 vllm/config/parallel.py（main 分支）。来源定位见文末来源与范围说明。

    一条 agent 请求带着大约一百万 token 的输入走进推理引擎——完整代码仓、几十轮对话历史、工具调用轨迹。对发出请求的用户来说这是一次调用；对引擎来说它是两个阶段。prefill 阶段要把这一百万个 token 全部算一遍，用户在等第一个字蹦出来；decode 阶段每步只生成一个新 token，却要背着全部历史的 KV cache（键值缓存）往下走，显存被一条条长请求吃满，新请求挤不进来。

    长序列放大了两个阶段各自的瓶颈，而两个瓶颈要的东西完全相反。张量并行（TP）和流水线并行（PP）切的都是模型——权重矩阵、层；上下文并行（Context Parallel，CP）切的是序列：把一条长请求沿 token 维分到多张 GPU 上。又因为 prefill 和 decode 的瓶颈不同、要优化的指标不同，CP 在 vLLM 中按阶段拆成了两个独立机制[C1]：

    • PCP（Prefill Context Parallel，预填充上下文并行）：prefill 阶段把序列切到多张卡并行计算，缩短首 token 时间（TTFT）[C2]。
    • DCP（Decode Context Parallel，解码上下文并行）：decode 阶段把 KV cache 沿 token 维分片存储，消除张量并行下的重复副本，腾出显存容纳更多并发请求[C2]。

    本文先拆开两个阶段的瓶颈（第 1 章），再看张量并行沿注意力头切 KV cache 为什么会在 GQA 和 MLA 模型上撞到天花板（第 2 章），然后分别展开 DCP（第 3 章）与 PCP（第 4 章）的机制，最后给出取值建议、与 PD 分离的辨析和适用边界（第 5 章）。贯穿构造模型：MLA 式架构、有效 KV 头数 $H=1$、上下文 $T=8$ 个 token、部署 $\mathrm{tp}=4$，用于把重复因子与交错规则变成可数可复算的对象；第 3 章 LSE 手算用更小的 2 卡 / 4 token 子例便于逐步演算。

    核心问题

    1. 同一条长上下文请求，为什么 prefill 和 decode 需要两种不同的上下文并行？

      解答：两阶段瓶颈不同，对应两种切法

      prefill 一次处理全部输入 token，attention 计算量随长度平方增长，瓶颈在 GPU 算力，用户感知的指标是首 token 时间（TTFT）；decode 每步只算一个新 token 的投影（计算量小），却要读全部历史 KV cache，瓶颈在显存容量——容量决定能同时装多少条请求，并发上限决定吞吐。两种瓶颈、两种服务等级目标（SLO, service level objectives），因此 vLLM 把上下文并行拆成两个机制：PCP 切 prefill 的计算，DCP 切 decode 的 KV cache。完整论证见第 1 章。

    2. 张量并行沿注意力头切 KV cache，为什么在 GQA 和 MLA 模型上会重复存储？重复多少倍怎么算？

      解答：头数切尽后按 $t/H$ 倍复制

      TP 把 $H$ 个 KV 头分给 $t$ 张卡：$t \le H$ 时每卡 $H/t$ 个头，无重复；$t > H$ 时头不够分，每个头复制到多张卡，KV cache 总副本数变为 $t/H$ 份（重复因子 $\max(1, t/H)$）。GQA 模型 KV 头数少（如 Qwen3-235B 为 4 个），MLA 把 K/V 压成跨全部 query 头共享的潜向量、有效 KV 头数为 1，潜向量 KV cache 在每个 TP rank 上完整复制。重复倍数决定 DCP 的有效上限：$d = t/H$ 时重复恰好降为 1 份。完整论证见第 2 章。

    3. DCP 沿 token 维怎么分片 KV cache？每步 decode 的通信怎么走？为什么分片计算合并后与整卡计算等价？

      解答：交错落位，三步通信，LSE 合并是恒等式

      dcp 组内每卡只存序列中 $1/d$ 的 token 位置的 KV，按交错规则分配：token $i$ 存到 rank $i \bmod d$，使 decode 中逐 token 增长的 KV 轮流落到各卡、增长均匀。每步 decode 的通信节奏是：AllGather 把 query 聚齐到每卡（每步只有一个新 token，通信量小）→ 各卡对本地 KV 切片算 attention，得到部分输出 $o_r$ 与本地 LSE $l_r$ → 按 $o = \sum_r e^{l_r} o_r / \sum_r e^{l_r}$ 合并。$e^{l_r} o_r$ 恰是该卡全部 token 的 $e^{s_i} v_i$ 加权和、$e^{l_r}$ 恰是该卡 $e^{s_i}$ 之和，合并就是全局 softmax 分子分母的分组求和——恒等式，不是近似。手算与代码验证见第 3 章。

    4. PCP 怎么切分 prefill 计算？为什么不能把序列按顺序等分？PCP 与 DCP 在资源占用上有什么本质区别？

      解答：$2N$ 块首尾配对；PCP 加卡、DCP 不加卡

      PCP 把 $T$ 个 token 的 prefill 切成段，每卡算自己段的 Q/K/V 与 attention 输出；全量 KV 放得下时聚齐 K/V 各算一段 query（partial-Q/full-KV），放不下时用 ring attention 逐块交换（partial-Q/partial-KV）。不能顺序等分的原因是 causal mask：第 $j$ 块的 query 要 attend 第 $0..j$ 块的 KV，计算量随块位置递增，顺序等分会让靠后的卡拿到最重的段；把序列切成 $2N$ 块、rank $i$ 取第 $i$ 块与第 $2N-1-i$ 块的首尾配对，每卡负载 $(i+1) + (2N-i) = 2N+1$ 与 $i$ 无关，恒定均衡。资源区别：PCP 扩展 world size（设备数变为 $\mathrm{PP}\times\mathrm{TP}\times\mathrm{PCP}$，单 PP 级即 $\mathrm{TP}\times\mathrm{PCP}$），花硬件买延迟；DCP 复用 TP rank 不加卡，花每步通信买显存。完整论证见第 4 章。

    5. 什么时候该用 DCP/PCP？dcp 取多少合适？它们和 PD 分离是什么关系？

      解答：先加 tp 再加 dcp；与 PD 分离正交可组合

      官方建议先把 tp 加到性能满意，再取 dcp 消除 KV 重复；dcp 有效范围为 $[1, t/H]$。源码校验（DCP 复用 TP rank 时）要求 $t \bmod d = 0$（main 分支当前逻辑，见第 5 章折叠块）；官方博客按模型架构列出更精细的约束：MLA 可切到整个 TP 度（$t \ge d$ 且 $t \bmod d = 0$），GQA 上界为 $t//H$（$(t/H) \ge d$ 且 $(t/H) \bmod d = 0$）[C10]。收益集中在高并发长上下文场景：实测 Kimi K2.6（8×B200、NVFP4）吞吐从 TP 基线的约 1,863 tok/s/GPU 升到 6,091（约 3.3 倍，页面换算），可支撑并发从 64 到 512，KV 占用 82%。上下文短、无重复可消或互联带宽低时可能负收益。与 PD 分离的区别：PD 分离决定 prefill/decode 放在哪个 GPU 池（部署维度），PCP/DCP 决定池内一条长请求怎么跨卡（执行维度），两者正交可组合。完整论证见第 5 章。

    常见误解

    • "DCP 让单个请求的 decode 快 $d$ 倍"——DCP 消除的是 KV 重复存储，收益路径是显存释放 → 容纳更多并发请求 → 吞吐提升；单请求每步 decode 反而多出组内通信，延迟可能不降反升。实测约 3.3 倍的吞吐提升（6,091/1,863，页面换算）来自并发能力，不是单请求速度（第 3 章）。
    • "PCP/DCP 是 PD 分离的另一种叫法"——PD 分离（disaggregation）决定 prefill 和 decode 跑在哪些 GPU 池上，是部署维度；PCP/DCP 决定池内一条长请求怎么跨卡执行，是执行维度。两者可以同时使用（第 5 章）。
    • "DCP 需要增加 GPU"——dcp 不扩展进程 world size，DCP 组复用已有的 TP rank；PCP 才扩展设备数（$\mathrm{PP}\times\mathrm{TP}\times\mathrm{PCP}$，单 PP 级即 $\mathrm{TP}\times\mathrm{PCP}$）。一个是花硬件，一个是花通信（第 4 章）。

    1. 长请求的两副面孔——prefill 撞算力，decode 撞显存

    标准注意力要求序列中每个位置查询其它位置。自回归推理把它拆成两步：prefill 一次性处理全部输入 token，算出每个位置的 KV cache 并给出第一个输出 token；此后 decode 每步用上一步的输出作为新 token，算它的 query/key/value，与全部历史 KV 做注意力，再吐出下一个 token。两个阶段处理同一条序列，但压力落点完全不同。

    prefill 的压力在计算时间。一百万个 token 的输入意味着一百万个 query 要对序列做注意力，attention 部分的计算量随长度平方增长；GPU 算力是瓶颈，而用户此时正在等第一个字——首 token 时间（TTFT）就是这一阶段的感知指标。vLLM 对长上下文 prefill 的目标，就是把这部分计算摊到各段 query token 上，由多个 rank 并行承担，把 TTFT 压下来[C2]。

    decode 的压力在 KV cache 容量。每步 decode 只新增一个 token，它的 Q/K/V 投影计算量很小；但每一步都要读取此前积累的全部 KV cache——这正是 KV cache 存在的意义，也是它的代价。单条请求的 KV 随生成不断增长，多条长请求同时运行时，显存先于算力被吃满：调度器允许再高的并发也没有意义，因为 GPU 已经装不下新请求的 KV 了。vLLM 对长上下文 decode 的目标，是腾出更多 KV cache 空间，容纳更大的 batch，从而提高吞吐[C2]。decode 的核心问题被官方文档概括为：每一步都是"少量 query token 对大量 KV token"的计算，关键就在于怎么把 KV cache 分片到多张 GPU[C3]。

    一个容易混淆的邻居是 chunked prefill（切块预填充）。它同样处理长 prompt，但按时间切：把长 prefill 分成多个调度步串行执行，让同批 decode 不被一条长请求卡住——每一小步仍在同一组卡上算，不增加并行度。PCP 按空间切：一步之内把序列分给多张卡同时算。一个切时间轴，一个切空间轴，作用于不同的问题，也可以同时使用。两者的区别将在第 4 章展开 PCP 机制时再次对照。

    至此可以给全文的机制定性：上下文并行沿 token 维（序列维）切分一条请求，prefill 侧切计算（PCP），decode 侧切 KV cache（DCP）[C1, C2]。但"沿 token 维切 KV cache"为什么有必要？要回答它，得先看现有的张量并行是怎么切 KV cache 的、又为什么切不动了。

    本章问题

    1. 为什么 prefill 的压力主要落在计算时间（TTFT）上，而 decode 的压力主要落在 KV cache 容量上？

      解答：两阶段的计算形状不同

      prefill 一次处理全部输入 token：每个 token 都要做 Q/K/V 投影（计算量与长度成正比），attention 部分每个 query 要对序列打分（计算量随长度平方增长），算力是瓶颈；用户在等第一个输出 token，所以感知指标是 TTFT。decode 每步只有一个新 token：它的投影计算量可以忽略，但该 token 的 query 要对全部历史 KV 做注意力，KV cache 必须全程留在显存里；多条请求并发时显存先于算力耗尽，容量决定并发上限、并发上限决定吞吐。因此优化 prefill 要切计算，优化 decode 要切存储。

    2. chunked prefill 同样处理长 prompt，它和 PCP 有什么区别？

      解答：切时间轴与切空间轴

      chunked prefill 把一条长 prefill 按时间切成多个调度步串行执行，目的是不让长请求独占机器、卡住同批 decode；每个小块仍在原来的卡组上算，每步的并行度不变。PCP 把序列按空间切到多张卡，一步之内多卡并行计算同一条请求，直接压缩 TTFT。两者解决不同问题（调度公平 vs 单请求延迟），可以叠加：先 chunked prefill 切块，再对每个块用 PCP 跨卡算。

    2. 张量并行沿注意力头切 KV cache，切到头就没得切了

    要看懂 DCP 为什么存在，得先看现有部署里 KV cache 是怎么放置的。单卡放不下模型或想容纳更多请求时，标准做法是 张量并行（TP）：把权重矩阵切开分到多张卡。注意力层的权重沿注意力头这一维天然可切——不同的头本来就是独立的投影，KV cache 也跟着按头切：$H$ 个 KV 头的模型，一条 $T$ 个 token 的请求需要在 KV cache 里存 $H \times T$ 条 key/value 条目[F1]，TP 把这 $H$ 个头分给 $t$ 张卡，每张卡存自己那部分头的全部 token。

    只要卡数不超过头数（$t \le H$），这个切法是干净的：每卡存 $H/t$ 个头，任何一个头的数据只在一张卡上。问题出在 $t > H$：头不够分了，每个头会被复制到多张卡上，同一份 KV 数据出现 $t/H$ 个副本[C4]。合并两种情形，KV cache 的重复因子为

    $$\max\left(1,\ \frac{t}{H}\right)$$

    重复不是抽象的浪费，它直接吃掉能装下的请求数：KV cache 的总占用变成无重复情形的 $t/H$ 倍，而显存容量正是 decode 阶段并发上限的硬约束（第 1 章）。更麻烦的是，现代模型恰恰在往"头少"的方向进化[C5]：

    • GQA（分组查询注意力）为了压缩 KV cache 只保留少量 KV 头——Qwen3-235B-A22B 只有 4 个，tp 加到 4 头就分完了，再加卡就开始复制。
    • MLA（多头潜注意力）更极端：K/V 被压成一个跨全部 query 头共享的低秩潜向量，有效 KV 头数就是 1。TP 对它是 $t > 1 = H$ 的极端情形，潜向量 KV cache 在每个 TP rank 上完整复制[C5]。

    把这个天花板变成可数的例子。构造一个贯穿全文的极小模型（人为构造，只为逐步复算）：MLA 式架构、有效 KV 头数 $H=1$、上下文 $T=8$ 个 token、部署 $\mathrm{tp}=4$。KV 条目总数 $H \times T = 8$ 条；TP 把这唯一的头"分"给 4 张卡的方式只有一种——复制：

    GPU 0GPU 1GPU 2GPU 3
    每卡持有的 KV头 0 · token 0–7头 0 · token 0–7头 0 · token 0–7头 0 · token 0–7
    每卡条目数8888

    四张卡合计 32 个条目，不同的只有 8 个——重复因子 $t/H = 4$，同一条请求的 KV 被原样写了 4 遍。对照一个头数刚好够分的情形：$H=4$（如 Qwen3-235B-A22B）配 tp 4，每卡恰好分到 1 个不同的头，也是各存 8 个条目，但 32 个条目互不相同，重复因子为 1。两种情形每卡的显存占用一样，差别全在"存的是不是重复数据"：

    要澄清一点：$t$ 超过 $H$ 之后 TP 并没有失效——权重矩阵仍然切得好好的，非注意力层照常受益，开始重复的只是 KV cache 这一部分[C4]。所以"KV 重复"不是 TP 用错了，而是 TP 的切法对 KV cache 来说维度不够用：头这一维切到头了，每张卡上还躺着完整的 token 维——一整维都没动过。沿 token 维把 KV cache 继续切下去，就是下一章的 DCP。

    本章问题

    1. TP 下 KV cache 怎么按头分片？$t \le H$ 与 $t > H$ 两种情况每卡各存多少？

      解答：头够分则无重复，不够分则复制

      $H$ 个 KV 头分给 $t$ 张卡，一条 $T$ token 的请求共 $H \times T$ 条 KV 条目。$t \le H$：每卡存 $H/t$ 个头的全部 token，任何一个头只存一份，无重复。$t > H$（整除时）：头数不够"每卡一个不同的头"，每个头复制到 $t/H$ 张卡，每卡存 1 个头的全部 token，同一份数据共 $t/H$ 份。构造模型 $H=1$、$t=4$：每卡 8 个条目，总量 4 份。

    2. 为什么 MLA 的 KV cache 在 TP 下是完整复制到每张卡？

      解答：有效 KV 头数为 1，无头可切

      MLA 把 K/V 压成一个跨全部 query 头共享的低秩潜向量，没有"多个头"可供切分，有效 KV 头数为 1。TP 沿头维切 KV 对它是 $t > 1 = H$ 的极端情形：唯一的头只能整体复制到每张卡，重复因子为 $t$。所以 tp 8 的 DeepSeek-R1 单节点部署会有 8 份完整的潜向量 KV 副本（第 5 章的官方 case）。

    3. "重复因子 $t/H$"怎么来的，它决定什么？

      解答：头在卡上的复制倍数；决定显存膨胀与 dcp 上界

      $t > H$ 且整除时，$H$ 个头放进 $t$ 张卡、每卡恰好一个头槽位，每个头必然落在 $t/H$ 张卡上——这就是重复因子。它决定两件事：一是 KV 显存相对无重复情形的膨胀倍数（直接压缩并发容量）；二是 dcp 的有效上界——$d = t/H$ 时总副本数恰好降为 1 份，DCP 的收益到此用尽，官方因此把上界取在 $t/H$（第 5 章）。

    3. DCP——沿 token 维切 KV cache，用通信换显存

    第 2 章的结论是：沿头维切 KV cache，在头少的模型上到顶了。但每张卡上还躺着一个完整的维度——token 维。DCP（decode context parallel）沿它继续切：DCP 组内每张卡只存序列中一部分 token 位置的 KV，每份数据只落一张卡，不再把容量浪费在副本上，腾出的显存用来接纳更多请求、跑更大的 batch[C6]。用法上它几乎是免费的：命令行加一个 -dcp <size>，不增加需要启动的 GPU 数量，只减少 KV cache 的重复[C7]——DCP 复用已有的 TP rank，不像 PCP 那样扩展设备数（第 4 章）。

    3.1 切法与交错分配

    概念上，DCP 把同一条序列的 token 位置分成 $d$ 份（$d$ 为 dcp size），每张卡负责一份。官方博客用一条 200K token 的请求演示：GPU 0 存 0–50K 位置的 KV，GPU 1 存 50K–100K，以此类推[C13]。但这是概念示意——vLLM 实际的落位规则是交错（interleaving）：token $i$ 存到 rank $i \bmod d$[C11]。用构造模型（$T=8$、$d=4$）把两种方案摆在一起：

    连续切分（博客示意）GPU 0GPU 0GPU 1GPU 1GPU 2GPU 2GPU 3GPU 3
    交错分配（vLLM 实现）GPU 0GPU 1GPU 2GPU 3GPU 0GPU 1GPU 2GPU 3

    两种方案每卡都是 2 个 token。构造模型里，4 份重复恰好降为 1 份——消除全部重复的临界点正是 $d = t/H = 4$。差别在 decode 的增长方式：KV cache 随生成逐 token 变长，而连续区间的示意没有回答"新 token 落到哪张卡"——若按位置顺序落位，新 token 会全部压到负责序列尾部的卡上，那张卡越来越满，其余卡闲着。交错分配的回答是轮流落位：token 8 落 rank 0、token 9 落 rank 1、token 10 落 rank 2……每张卡均匀增长，且任意 token 的归属由位置直接算出（$i \bmod d$），不需要查表[C11]。这一策略由 Moonshot 的 Chao Hong 提出，Helix Parallelism 论文（arXiv:2507.07120）有详细讨论[C11]。

    一般地，在 $t > H$ 的重复情形下，dcp 取 $d$ 后 KV 的总副本数从 $t/H$ 份降到 $(t/H)/d$ 份；$d = t/H$ 时恰好降为 1 份[F2]。若 $(t/H)/d > 1$，说明同一条请求的 KV 还保留多份分片副本——第 5 章 Kimi-K2 取 dcp 8（而非 16）就是这个形态，代价换来的是更小的通信组。

    3.2 每步 decode 的通信节奏

    KV 分开了，attention 却要对着整条序列算：新 token 的 query 得给所有历史 token 打分，而 KV 散在 $d$ 张卡上。DCP 的解法是让每张卡算"自己那段"的部分结果，再用通信把部分结果合并成完整输出。标准路径（ag_rs 后端）一步 decode 的节奏是三段[C12]（AllGather、ReduceScatter 等集合通信原语的机制不在本文展开）：

    第一个 all-gather 看似多余，实则是 DCP 里最便宜的一步：decode 每步只有一个新 token，query 张量的大小是"一个 token 的投影"，组内聚齐它的开销可以忽略；换来的是每张卡都能用完整的 query 对自己的 KV 切片打分[C12]。开销的大头在"重复"：这三段集合通信是按层走的，几十层 transformer 每层都来一遍，通信延迟随层数累积——MLA 的 a2a 后端正是把每层 NCCL 调用从 3 次压到 2 次来省这笔账（本节末的补充折叠块）。而 $d$ 越大组越大，每步通信越多，这正是官方给 dcp 设上界的直接原因（第 5 章）。

    3.3 LSE 合并：分片计算为什么等价于整卡计算

    三段节奏里真正精妙的是中间那次合并。每张卡对自己的 KV 切片算 attention，得到的是"部分 softmax"——分母只含本地分数。设第 $r$ 张卡上的 token 集合记为 $i \in r$，$s_i$ 为 query 对它们的分数，本地计算得到部分输出 $o_r$ 与本地 LSE $l_r$（log-sum-exp）[F3]：

    $$l_r = \ln \sum_{i \in r} e^{s_i}, \qquad o_r = \frac{\sum_{i \in r} e^{s_i}\, v_i}{\sum_{i \in r} e^{s_i}}$$

    全局输出由下式合并[F3]：

    $$o = \frac{\sum_r e^{l_r}\, o_r}{\sum_r e^{l_r}}$$

    这不是近似，是恒等式。原因藏在两个"恰好"里：$e^{l_r}$ 就是第 $r$ 卡的本地分母 $\sum_{i \in r} e^{s_i}$，而 $e^{l_r} o_r$ 恰好是第 $r$ 卡的本地分子 $\sum_{i \in r} e^{s_i} v_i$。把它们代回合并式，分子分母分别变成全部卡本地分子、本地分母的总和——正是全局 softmax 的分子与分母按卡分组求和。部分结果丢弃的只有"归一化"，LSE 把它完整带了回来。

    补充：恒等式的完整代数推导

    记第 $r$ 卡的本地分母 $D_r = \sum_{i \in r} e^{s_i}$，则 $l_r = \ln D_r$，即 $e^{l_r} = D_r$。合并式的分子：

    $$\sum_r e^{l_r}\, o_r = \sum_r D_r \cdot \frac{\sum_{i \in r} e^{s_i} v_i}{D_r} = \sum_r \sum_{i \in r} e^{s_i} v_i = \sum_i e^{s_i} v_i$$

    分母：

    $$\sum_r e^{l_r} = \sum_r D_r = \sum_r \sum_{i \in r} e^{s_i} = \sum_i e^{s_i}$$

    双重求和能并成全局单重求和，是因为分片是划分：每个 token 恰好属于一张卡，不重不漏。于是 $o = \sum_i e^{s_i} v_i / \sum_i e^{s_i}$，正是对全部 token 做 softmax attention 的输出。推导对任意分数值成立。

    用手算验证。构造一个小例子（人为构造）：2 张卡、4 个历史 token、1 个新 query，分数 $s = (1, 2, 3, 4)$、值 $v = (1, 0, 0, 1)$；交错分配下 token 0、2 在卡 0，token 1、3 在卡 1。每卡算自己的部分 softmax：

    卡 0（token 0、2）卡 1（token 1、3）
    本地分数 / 值$s=1,3$；$v=1,0$$s=2,4$；$v=0,1$
    本地分母 $D_r$$e^1 + e^3 = 22.803819$$e^2 + e^4 = 61.987206$
    本地 LSE $l_r = \ln D_r$$3.126928$$4.126928$
    部分输出 $o_r$$e^1 / D_0 = 0.119203$$e^4 / D_1 = 0.880797$

    合并：$o = \dfrac{e^{l_0} o_0 + e^{l_1} o_1}{e^{l_0} + e^{l_1}} = \dfrac{22.803819 \times 0.119203 + 61.987206 \times 0.880797}{22.803819 + 61.987206} = \dfrac{2.718282 + 54.598150}{84.791025} = 0.675973$。整卡基线：$o = \dfrac{e^1 \cdot 1 + e^4 \cdot 1}{e^1 + e^2 + e^3 + e^4} = \dfrac{57.316432}{84.791025} = 0.675973$。两条路走到同一个数——合并分子里的两个乘积 $22.803819 \times 0.119203 = 2.718282$、$61.987206 \times 0.880797 = 54.598150$，正是两张卡的本地分子"乘回 $e^{l_r}$ 撤销归一化"的结果。

    展开：合并式的逐项数值

    四个指数值（6 位小数）：$e^1 = 2.718282$，$e^2 = 7.389056$，$e^3 = 20.085537$，$e^4 = 54.598150$。

    卡 0：$D_0 = e^1 + e^3 = 22.803819$；$o_0 = 2.718282 / 22.803819 = 0.119203$；$l_0 = \ln 22.803819 = 3.126928$。

    卡 1：$D_1 = e^2 + e^4 = 61.987206$；$o_1 = 54.598150 / 61.987206 = 0.880797$；$l_1 = \ln 61.987206 = 4.126928$。

    合并分子：$e^{l_0} o_0 + e^{l_1} o_1 = D_0 o_0 + D_1 o_1 = 2.718282 + 54.598150 = 57.316432$；分母：$D_0 + D_1 = 84.791025$；输出 $o = 57.316432 / 84.791025 = 0.675973$。

    整卡基线分子：$e^1 \cdot 1 + e^2 \cdot 0 + e^3 \cdot 0 + e^4 \cdot 1 = 57.316432$；分母 $84.791025$；输出相同。

    import math

# 构造示例：2 张卡分存 4 个历史 token 的 KV，1 个新 query
# token i 存到 rank i % 2；分数 s_i 与值 v_i 如下
tokens = {
    0: {"rank": 0, "s": 1.0, "v": 1.0},
    1: {"rank": 1, "s": 2.0, "v": 0.0},
    2: {"rank": 0, "s": 3.0, "v": 0.0},
    3: {"rank": 1, "s": 4.0, "v": 1.0},
}

# 整卡基线：直接对全部 4 个 token 做 softmax attention
num = sum(math.exp(t["s"]) * t["v"] for t in tokens.values())
den = sum(math.exp(t["s"]) for t in tokens.values())
o_global = num / den

# DCP：每卡只对本地 token 计算，再按 LSE 合并
partials = {}
for i, t in tokens.items():
    r = t["rank"]
    d, n = partials.get(r, (0.0, 0.0))
    partials[r] = (d + math.exp(t["s"]), n + math.exp(t["s"]) * t["v"])

o_merged_num = 0.0
o_merged_den = 0.0
for r, (d, n) in sorted(partials.items()):
    o_r = n / d           # 本地部分输出
    l_r = math.log(d)     # 本地 log-sum-exp
    print(f"rank {r}: D={d:.6f}  o_r={o_r:.6f}  l_r={l_r:.6f}")
    o_merged_num += math.exp(l_r) * o_r
    o_merged_den += math.exp(l_r)

o_merged = o_merged_num / o_merged_den

print(f"global  o = {o_global:.6f}")
print(f"merged  o = {o_merged:.6f}")
print(f"equal: {math.isclose(o_global, o_merged)}")

    3.4 收益、代价与实测

    收益的因果链：重复消除 → 单卡 KV 占用下降 → 同样显存装下更多请求 → batch 变大 → 吞吐上升。还有一层：DCP 不让任何一张卡闲着——attention 阶段按序列分片，每张卡算自己那段；紧接着 FFN 阶段，同一批 GPU 立刻重组成完整池，把 FFN 权重加载摊到全池上[C16]。decode 的每一步都在 attention 与 FFN 之间交替，两个阶段各得其所。

    官方博客在单节点 8×B200 上服务 Kimi K2.6（NVFP4 量化），把并发从 16 扫到 512。负载为多轮 agentic trace：输入中位数约 67k token、输出约 400 token，约 53% 的请求不小于 64k（重尾到约 1M）[N2]。结果[N1]：

    基线 TPDCP
    KV 使用率并发 64 时达到 100%，撞墙并发 512 时仅 82%
    吞吐平台期约 1,863 tok/s/GPU6,091 tok/s/GPU（并发 512）

    注意收益的来源：基线不是算不动，而是并发 64 时 KV 已经 100%，新请求进不来，吞吐被容量钉死在平台期；DCP 腾出显存把可支撑并发推到 512，吞吐随 batch 涨上去。这是"容量 → 并发 → 吞吐"的链路，不是单请求变快——单请求每步反而多出组内通信。按输入长度分桶看，DCP 在 200k+ 桶仍保持高且稳定的前沿[N1]。

    代价与边界：每步 decode 多出组内集合通信，$d$ 越大组越大、通信越多[C8]；卡间互联带宽低的系统、上下文短（$t \le H$ 时本就无重复可消）、并发低（吞吐不构成目标）的场景，通信开销可能吃掉收益。dcp 的取值建议与硬约束见第 5 章。

    本章问题

    1. DCP 怎么把 KV cache 分到 $d$ 张卡？为什么交错分配而不是连续块？

      解答：token $i$ 落 rank $i \bmod d$，让增长均匀

      组内每卡存 $1/d$ 的 token 位置，交错规则：token $i$ 存到 rank $i \bmod d$。不用连续块的原因：decode 中 KV 逐 token 增长、新 token 位置连续递增，连续切分若按顺序落位会把新 token 全压到负责尾部的卡，负载越走越斜；交错让新 token 轮流落到各卡、均匀增长，且任意 token 的归属由位置直接算出，无需查表。构造模型 $T=8$、$d=4$：token 0–7 依次落 GPU 0、1、2、3、0、1、2、3，每卡 2 个 token。

    2. decode 一步的通信流程是什么？为什么 query 的 all-gather 是便宜的？

      解答：三段节奏；单 token 的张量极小

      ①DCP 组内 AllGather 聚齐 query（TP 下每卡只算出 query 的一片，对本地 KV 打分需要完整向量）；②各卡用完整 query 对本地 KV 切片算 attention，得部分输出 $o_r$ 与本地 LSE $l_r$；③AllGather 共享各卡的部分输出与 LSE，按 LSE 加权合并，ReduceScatter 求和并让每卡取回自己的 head 切片。query 的 all-gather 便宜是因为 decode 每步只有一个新 token，聚齐"一个 token 的投影"开销可忽略；开销大头在于三段集合通信按层重复、随层数累积。

    3. LSE 合并怎么做？为什么合并后与整卡计算完全一致？

      解答：$o = \sum_r e^{l_r} o_r / \sum_r e^{l_r}$，恒等式

      每卡先算本地部分输出 $o_r$（本地 softmax 归一化）与本地 LSE $l_r = \ln \sum_{i \in r} e^{s_i}$，再按 $o = \sum_r e^{l_r} o_r / \sum_r e^{l_r}$ 合并。恒等的原因：$e^{l_r}$ 就是该卡的本地分母，$e^{l_r} o_r$ 就是该卡的本地分子 $\sum_{i \in r} e^{s_i} v_i$；合并即全局 softmax 分子分母的分组求和，分片是划分（每个 token 恰属一张卡），所以精确相等、非近似。手算与代码均验证：两条路都得 0.675973。

    4. DCP 的收益链路和代价各是什么？

      解答：容量换吞吐；代价是每步组内通信

      收益链：重复消除 → 单卡 KV 占用降 → 可容纳请求多 → batch 大 → 吞吐高；且 attention 阶段按序列分片、FFN 阶段同一批 GPU 重组为全池摊薄权重加载，没有卡闲着。实测：8×B200 服务 Kimi K2.6（NVFP4），基线 TP 在并发 64 时 KV 100% 撞墙、吞吐平台期约 1,863 tok/s/GPU；DCP 支撑到并发 512、6,091 tok/s/GPU、KV 82%。代价：每步 decode 多出组内集合通信，$d$ 越大通信越多；互联带宽低、上下文短、并发低的场景可能负收益。

    4. PCP——把长 prompt 的计算摊到多卡

    decode 侧的答案是 DCP，prefill 侧的问题与解法都不一样。第 1 章已经看到：prefill 一次处理全部输入 token，attention 计算量随长度平方增长，算力是瓶颈，用户在等第一个字。PCP（prefill context parallel）把这条长序列的计算本身摊到多张卡上：$N$ 张卡把请求切成 $N$ 段，每卡计算一段的 Q/K/V[C17]。另一个邻居——chunked prefill（第 1 章）——按时间切长 prefill 让同批 decode 不被卡住，不增加每步并行度；PCP 按空间切到多卡，直接压缩 TTFT，两者作用于不同问题也可叠加（第 1 章已对比）。

    4.1 两种策略：聚齐全量 KV，还是逐块传递

    切完之后 attention 怎么算，取决于显存装不装得下全量 K/V，有两种策略[C17]：

    • partial-Q / full-KV：序列中等长、能容纳全量 K/V 时，把所有卡的 K/V 聚齐，每张卡只用自己那段 query 对全量 K/V 算 attention 输出。一次 AllGather 换每卡只算 $1/N$ 的 query，用通信买计算。
    • partial-Q / partial-KV：序列长到放不下全量 K/V 时，每卡只保留自己段的 K/V，用 ring attention 在卡间逐块收发 K/V——任何时刻每张卡上只有一小块别家的 K/V，算完传给下一家。

    两种策略写作时均在活跃开发中[C21]；ring attention 的机制不在本文展开（原始论文 arXiv:2310.01889）。无论哪种策略，切分方式本身还有一个坑要填——负载不均。

    4.2 causal mask 让负载天生不均

    切 prefill 有个 decode 没有的问题：causal mask。第 $j$ 块的 query 只能 attend 第 $0$ 到 $j$ 块的 KV，所以第 $j$ 块的计算量随 $j$ 递增——靠前的块轻（只需要看自己），靠后的块重（要看从头到自己的整段）。等长切块后按顺序分给各卡，排后面的卡天然拿到最重的活[C18]。

    vLLM 的 RFC #26133 给出的解法是首尾配对：把序列切成 $2N$ 块而不是 $N$ 块，rank $i$ 同时拿第 $i$ 块和第 $2N-1-i$ 块[C18, F4]。该 RFC 状态为 closed as not planned，配对设计作为 RFC 描述的设计呈现，不代表已落地实现。每卡负载（$b$ 为块长，单位 $b^2$）：

    $$(i+1)\,b^2 + (2N-i)\,b^2 = (2N+1)\,b^2$$

    $i$ 被消掉了——每张卡的负载与它拿的是哪对块无关，恒定。用手算验证（构造示例：8 个等长块、4 张卡，第 $j$ 块负载 $j+1$ 个单位，总计 36 个单位）：

    首尾配对（卡 $i$ 拿块 $i$、$7-i$）$1+8=9$$2+7=9$$3+6=9$$4+5=9$$9$$36/9 = 4$ 倍

    除了切分方式，两者还有一个资源层面的本质区别：PCP 扩展进程的 world size——设备数变为 $\mathrm{PP} \times \mathrm{TP} \times \mathrm{PCP}$，用更多的卡换更短的 TTFT；DCP 不扩展 world size，复用已有的 TP rank，用每步通信换显存[C19]。一个是花硬件，一个是花通信。对照收尾：

    PCPDCP
    作用阶段prefilldecode
    切的对象序列的计算（每卡算一段的 Q/K/V 与 attention）KV cache 的存储（每卡存一段 token 的 KV）
    设备数扩展：$\mathrm{PP}\times\mathrm{TP}\times\mathrm{PCP}$（单 PP 级即 $\mathrm{TP}\times\mathrm{PCP}$）不变：复用 TP rank

    收益指标TTFT 下降显存释放 → 并发与吞吐上升

    本章问题

    1. PCP 的两种策略分别适用什么场景？

      解答：全量 KV 放得下就聚齐，放不下就逐块传

      partial-Q/full-KV：请求长度中等、显存能容纳全量 K/V 时，AllGather 聚齐所有卡的 K/V，每张卡只对自己那段 query 计算 attention 输出——一次聚齐换每卡 $1/N$ 的计算量。partial-Q/partial-KV：序列长到放不下全量 K/V 时，每卡只保留自己段的 K/V，用 ring attention 逐块收发别家的 K/V，任何时刻卡上只有一小块外来数据。前者通信少但受显存限制，后者能撑任意长度但通信按块重复。

    2. causal mask 为什么造成 prefill 负载不均？首尾配对怎么解决？

      解答：负载随块位置递增；配对让和恒定

      causal mask 下第 $j$ 块的 query 要 attend 第 $0$ 到 $j$ 块的 KV，计算量 $\propto (j+1)b^2$ 随 $j$ 递增；顺序等分把最重的块都堆给排后的卡。解法：切成 $2N$ 块，rank $i$ 拿第 $i$ 块与第 $2N-1-i$ 块，负载 $(i+1)b^2 + (2N-i)b^2 = (2N+1)b^2$ 与 $i$ 无关。构造例：8 块 4 卡，顺序切各卡 $3, 7, 11, 15$（最慢 15），配对切各卡全为 9，总负载同为 36，加速上界从 2.4 倍升到 4 倍。

    3. PCP 与 DCP 在资源占用上的本质区别是什么？

      解答：PCP 加卡，DCP 复用卡

      PCP 扩展进程 world size：设备数变为 $\mathrm{PP} \times \mathrm{TP} \times \mathrm{PCP}$，代价是更多 GPU，买的是 TTFT；DCP 不扩展 world size，无 PCP 时复用 TP rank，代价是每步 decode 的组内通信，买的是显存与并发。一个是花硬件，一个是花通信，所以在部署决策里属于不同性质的投入。

    5. 组合与选型——先加 tp，再加 dcp

    机制看完，回到部署视角：什么时候用、参数怎么取。官方的建议直白：先把 tp 加大到性能满意，再加 dcp 消除 KV cache 重复[C20]。逻辑就是第 2、3 章的结论——tp 在头数之内时一切干净，超过 $H$ 后 KV 开始重复，重复量 $\max(1, t/H)$；dcp 正是消这笔账的，取到 $d = t/H$ 时重复归一。

    dcp 的有效范围是 $[1, t/H]$：越大重复越少、通信开销越大[C8]。这是推荐范围——官方博客按模型架构列出更精细的使用约束：MLA 因有效 KV 头数为 1，序列可切到整个 TP 度（$t \ge d$ 且 $t \bmod d = 0$）；GQA 的切分度被重复因子 $t//H$ 封顶（$(t/H) \ge d$ 且 $(t/H) \bmod d = 0$）[C10]。main 分支源码目前的实际校验只看 $t \bmod d = 0$[C9]，比博客的 GQA 约束更松。理论上 dcp 可以超过 $t/H$ 继续沿 token 维切分，但多出来的 rank 在非 attention 层没有明确分工，为简单起见官方把上界取在 $t/H$[C8]。三个官方 case study 把取值变成实例[N3]：

    模型有效 KV 头数 $H$部署KV 重复dcp效果
    DeepSeek-R1（MLA）1tp 88 份8重复全消
    Kimi-K2（MLA）1tp 1616 份16重复全消
    Kimi-K2（MLA）1tp 1616 份8降到 2 份，DCP 通信只发生在节点内
    Qwen3-235B-A22B（GQA）4tp 82 份2重复全消

    Kimi-K2 的两行展示了一个真实的取舍：dcp 16 把重复消干净，但通信组横跨节点；dcp 8 留 2 份重复，换来通信只发生在单节点内——重复与通信之间的中间点也是合法选择[N3]。注：表格里的 Kimi-K2（MLA）来自官方文档 case study，是 MLA 架构示例；第 3 章实测数字里的 Kimi K2.6（NVFP4）是该模型在博客实测中的量化版本，部署对象与本表格相同但量化与实测条件不同。

    PCP 的组合约束更紧：PCP 目前不支持 DP；PCP 开启后 dcp 只能取 1（禁用）、pcp（跨 PCP 轴）或 $\mathrm{tp}\times\mathrm{pcp}$（跨完整 TP 与 PCP 的块）三者之一[C9]。校验逻辑的具体代码见折叠块。

    vllm/config/parallel.py 的 _validate_parallel_config（main 分支）：

    raise ValueError("PCP does not support data parallelism yet.")

    即：无 PCP 时要求 tp 可被 dcp 整除（DCP 复用 TP rank）；有 PCP 时 dcp 限取 1、pcp 或二者之积。校验逻辑随版本演进可能变化[C9]。

    最后是与 PD 分离的辨析。PD 分离（prefill/decode disaggregation）决定 prefill 和 decode 跑在哪些 GPU 池上——部署维度；PCP/DCP 决定池内一条长请求怎么跨卡执行——执行维度。两者正交、可以组合；vLLM 正在加固 DCP 在分离式部署中的支持[C22]。PCP 与 PD 分离的组合尚无官方支持说明（PCP 本身仍在开发中）。

    什么时候不该用？三类场景直接用 TP 更简单：上下文短或 $t \le H$，没有重复可消；卡间互联带宽低，每步通信的延迟吃掉显存收益；请求并发低，吞吐本来就不构成目标。另外把第 3 章的实测钉在这里：从约 1,863 到 6,091 tok/s/GPU 的提升来自并发能力（64 到 512），不是单请求速度——单请求每步反而多出组内通信[N1]。DCP 买的是吞吐，不是单请求延迟。

    本章问题

    1. dcp 怎么选值？三个官方部署各取多少？

      解答：先加 tp 到满意，dcp 取 $[1, t/H]$ 内的整除值

      官方建议先把 tp 加大到性能满意，再取 dcp 消重复；有效范围 $[1, t/H]$。源码（main 分支）当前只校验 $t \bmod d = 0$[C9]；官方博客按模型架构列出更精细的使用约束：MLA 可切到整个 TP 度（$t \ge d$ 且 $t \bmod d = 0$），GQA 上界为 $t//H$（$(t/H) \ge d$ 且 $(t/H) \bmod d = 0$）[C10]。三个官方 case：DeepSeek-R1（$H=1$）tp 8 → dcp 8；Kimi-K2（$H=1$）tp 16 → dcp 16 全消，或 dcp 8 留 2 份、通信只在节点内；Qwen3-235B-A22B（$H=4$）tp 8 → dcp 2。超过 $t/H$ 理论可行但非 attention 层无明确分工，官方上界取 $t/H$。

    2. PCP/DCP 与 PD 分离是什么关系？

      解答：部署维度与执行维度，正交可组合

      PD 分离决定 prefill 与 decode 放在哪些 GPU 池上（部署维度）；PCP/DCP 决定池内一条长请求怎么跨卡执行（执行维度）。两者正交：分离式部署的 prefill 池内用 PCP、decode 池内用 DCP 在概念上成立，但 PCP 本身仍在开发中、与 PD 分离的组合尚无官方支持说明。vLLM 正在加固 DCP 在分离式部署中的支持（写作时的状态）[C22]。

    3. 什么时候 DCP 反而不划算？

      解答：无重复可消、互联差、并发低

      三类场景：①上下文短或 $t \le H$——没有重复可消，DCP 无收益；②卡间互联带宽低——每步组内集合通信的延迟超过腾显存带来的收益；③请求并发低——吞吐不构成目标，省下的显存换不成 batch。这些场景直接用 TP 更简单。此外单请求延迟敏感的场景也要谨慎：DCP 每步多出组内通信，实测的吞吐提升全部来自并发能力而非单请求速度。

    辅助解释与类比边界

    "两副面孔""撞墙""天花板""花硬件买延迟、花通信买显存"等为修辞表述，对应的技术内容以正文正式定义为准。"新 token 轮流落到各卡"描述的是 token 级交错（interleave_size 为 1）；实现还支持块级对齐（interleave_size 取块大小），此时"轮流"以块为单位。本文未使用其它类比。

    简化条件及其限制

    构造模型与 LSE 例子用标量分数与值，真实模型是向量；恒等性不依赖维度，但数值不可直接对应真实系统。验证代码用 float64 与精确指数，真实实现用 bf16/fp16 且 LSE 计算减去最大值以保证数值稳定（不改变恒等式）。causal 负载只计 attention 块对的计算量（$\propto b^2$），忽略 QKV 投影等与位置无关的项；加速上界假设通信为零、整体时间由最慢卡决定，实际存在通信与残余不均的损耗。副本数公式假设 $t$ 与 $H$（或 $t/H$ 与 $d$）整除；非整除时 GQA 按 $t/H$ 的整数部分约束（C10）。源码约束（C9）与后端选项（C14）以 main 分支当前状态为准，随版本演进可能变化。
