概念概览 · 前缀缓存

前缀缓存（prefix caching）：跨请求复用相同开头的 KV cache

把完成请求的 KV cache 留在显存：开头相同的请求直接复用前缀段、跳过其 prefill 计算——radix tree 组织匹配、LRU 叶子优先逐出、页大小决定命中粒度。

更新于 2026-08-19

这是什么

前缀缓存（prefix caching，也叫 context caching / prompt caching）把已完成请求的 KV cache 留在显存，后续请求开头 token 序列与之前相同时直接复用命中段、跳过其 prefill 计算。既有系统请求完成即丢缓存，SGLang 称这阻止了跨调用复用。

哪些负载能复用

KV cache 只由 token 序列与模型参数决定，因此匹配是精确前缀匹配（从头逐 token 相同），不是语义相似。常见负载可归纳为四类典型来源：系统提示词（全请求共享）、多轮对话历史（上一轮全部内容 $+$ 新消息，含上轮输出）、few-shot 示例、RAG 文档（同文档多问题）。

核心机制

  • radix tree 组织：边标变长 token 段，根到节点路径 $=$ 已缓存序列；新请求沿树匹配到分叉点，即最长可复用前缀，尾部 prefill 后插入为新子边。SGLang 页大小 1 token。
  • LRU 叶子优先逐出：先丢最久未用的叶子，共享祖先存活到所有子分支被逐出为止——共享前缀天然长寿；引用计数非 0 的节点（运行请求在用）不可逐出。
  • 哈希实现（vLLM/Mooncake）：每页指纹 $=$ 哈希(token ID, 前页指纹)，指纹相同即同前缀页，无需树结构，指纹可跨节点共享。

关键结论与边界

  • 命中率 $=$ 负载共享结构 $\times$ 缓存容量 $\times$ 页粒度：按整页计命中，共享 100 token 时页 1 命中 100、页 32 命中 96、页 256 命中 0；实测页 512 配置的 SGLang-HiCache 命中率比 Strata-IO 低 2.4%。
  • 命中还要求页在显存且已算完：CPU/SSD 层命中需搬回（分层传输问题），计算中的前缀不可复用（delay hit）——两者是 Strata 一文的主题。
