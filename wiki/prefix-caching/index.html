    前缀缓存（prefix caching）：跨请求复用相同开头的 KV cache

    主要依据：Zheng et al., "SGLang: Efficient Execution of Structured Language Model Programs"（NeurIPS 2024, arXiv:2312.07104）§3.2（RadixAttention）；哈希实现与页大小-命中率关系另引 Xie et al., "Strata"（OSDI 2026, arXiv:2508.18572v2）§6、§3.1、§5.3.2。

    一个对话服务，每条请求都以同一段 200 token 的系统提示词开头，一天收到一百万条请求——这一百万次对同一段话的 prefill 计算，有没有必要做一百万次？答案是不必：KV cache 只依赖 token 序列（见 KV cache），开头相同的请求可以共用同一份前缀缓存。既有系统在请求完成后把缓存直接丢弃，SGLang 称这"阻止了跨调用复用、显著拖慢执行"[C1]。前缀缓存（prefix caching，文献与商业 API 中也叫 context caching / prompt caching[C6]）就是把完成请求的缓存留下来、供后续请求匹配复用的机制。本文讲清五件事：什么能复用、radix tree 怎么组织匹配、缓存满了先丢谁、页大小为什么影响命中率、以及 vLLM/Mooncake 的哈希实现与 SGLang 的树实现有何不同。

    核心问题

    1. 跨请求到底能复用什么？共享前缀从哪来？

      解答：精确 token 前缀匹配，四类典型来源

      两个请求只要开头 token 序列相同，这段前缀的 KV cache 就是同一份数据，可直接复用——匹配是精确的 token 前缀匹配，不是语义相似。四类典型来源：系统提示词（所有请求共享）、多轮对话历史（新一轮输入 $=$ 前几轮全部内容 $+$ 新消息）、few-shot 示例（同批示例的多个查询）、RAG 文档（同一文档的多个问题）。命中部分完全跳过 prefill 计算且不重复占显存。见「什么能复用」一章。

    2. radix tree 怎么组织前缀缓存？新请求怎么匹配、结果怎么插入？

      解答：压缩前缀树，沿树匹配到分叉点

      radix tree（基数树）是压缩前缀树：边上标变长 token 段，根到任一节点的路径拼接成一个已缓存序列。新请求沿树逐段比对 token：能匹配到的最深节点即最长可复用前缀，其下各页直接取用；未匹配的尾部继续 prefill，算完作为该节点的新子边插入。SGLang 实现中页大小为 1 token、缓存按非连续分页布局存储。见「radix tree」一章。

    3. 缓存装不下时先丢谁？正在使用的怎么办？

      解答：LRU 从叶子逐出，引用计数保护运行请求

      LRU 逐出且叶子优先：先丢最久未用的叶子；叶子被逐出后其祖先（共享前缀）仍留在树上供其他分支复用，直到所有子分支都被逐出才轮到它——共享前缀因被多分支引用而天然长寿。运行中的请求不能被逐出：每个节点维护引用计数，计数为 0 才可逐出。缓存与运行请求共享同一内存池，系统在"多缓存"与"大批次"间动态权衡。见「缓存满了怎么办」一章。

    4. 命中率由什么决定？页大小为什么影响它？

      解答：负载共享结构 $\times$ 缓存容量 $\times$ 页粒度

      命中按整页计：只有完整落在共享前缀内的页才算命中，页命中数为共享前缀长度除以页大小取整。共享 100 token 时页 1 命中 100 token、页 32 命中 96（3 页）、页 256 命中 0。实测页 512 配置的 SGLang-HiCache 命中率比 Strata-IO 低 2.4%、其最优页配置（512）的吞吐也只为 Strata-IO 的 93%。SGLang 取页 1 正为匹配粒度最细。见「命中率」一章。

    5. 除了 radix tree，还有什么实现方式？

      解答：vLLM/Mooncake 用哈希指纹链

      每页由 token ID 与前一页的哈希链式计算唯一指纹，指纹相同即同一前缀页，用哈希表定位，无需树结构。两种实现是"结构化索引 vs 哈希索引"的选择：树天然支持最长前缀匹配与逐出时的祖先复用，哈希实现简单且指纹可跨节点共享（分布式友好）；LMDeploy 用粗粒度 trie 折中。Strata 基于 SGLang 把 RadixTree 扩展为 HiRadixTree。见「两种实现」一章。

    1. 什么能复用——共享前缀从哪来

    复用的可行性来自 KV cache 的一个性质（KV cache 第 1 章）：$k_i=x_i W_K$、$v_i=x_i W_V$ 只由第 $i$ 个 token 的输入与模型参数决定，与哪个请求、哪个查询无关。因此两个请求只要从第一个 token 开始的序列相同，这段前缀的 KV cache 就是逐字节相同的数据，一方的缓存另一方直接可用。反过来，只要开头有一个 token 不同，从那个位置起缓存就不可复用——匹配是精确前缀匹配，不是"意思差不多就行"。

    哪些负载天然满足"开头相同"？四类典型来源：

    来源共享内容典型形态
    系统提示词所有请求相同的开头指令段本文开篇的 200 token 系统提示词，百万请求共享
    多轮对话历史上一轮的全部输入 + 上一轮输出第 $n$ 轮请求 $=$ 第 $n-1$ 轮完整序列 $+$ 新消息
    few-shot 示例提示中同一批示例同一任务的多个查询共享示例段
    RAG / 文档问答同一份检索文档或手册多个用户查询同一份 20,000 token 手册

    多轮对话值得单独说一句：第 $n$ 轮请求的输入恰好以第 $n-1$ 轮的完整序列（提示 $+$ 全部生成输出）为前缀，所以上一轮的生成结果也构成可复用缓存——SGLang 因此把生成结果的缓存与提示的缓存一同留在树上[C9]。复用的收益是双份的：命中部分完全跳过 prefill 计算（省算力），且多个请求指向同一份物理页（省显存——这依赖分页机制提供的页级共享，见 PagedAttention）。

    本章问题

    1. 两个请求满足什么条件才能共用一份 KV cache？"语义相似"算吗？

      解答：从第一个 token 起的精确序列相同，语义相似不算

      KV cache 由 token 序列与模型参数唯一决定，因此只有从头开始完全相同的 token 序列（前缀）才能复用缓存。哪怕两段话意思完全一样，只要 token 有一个不同，从分歧点起的 K/V 就完全不同，不能复用。"按语义相似复用"是另一族工作（近似缓存），与本文的精确前缀缓存不同。判断口诀：命中条件是"逐 token 相同的前缀"，不是"差不多的内容"。

    2. 复用命中后省掉的是什么？

      解答：命中段的全部 prefill 计算与重复显存

      省计算：命中前缀无需再过一遍模型，prefill 只算新增 token（这正是把 $O(n^2)$ 降为 $O(n)$ 的缓存收益在跨请求维度的延伸）。省显存：多个请求的页表指向同一物理页（页级共享），一份缓存多处引用。未命中的尾部照常 prefill 并写入缓存，成为后续请求的复用候选。

    2. radix tree——组织与匹配

    SGLang 的 RadixAttention 用 radix tree（基数树）组织这些前缀缓存[C2, C3]。radix tree 是前缀树的压缩变体：朴素 trie 每条边只标一个元素，radix tree 的边可以标一整段 token 序列，树更矮、查找更快。结构含义：从根到任一节点的路径上各段拼接，就是某个已缓存序列；节点即"到此为止的前缀已缓存"。

    下面用一个构造示例走一遍匹配过程。设系统提示词为 $S$（200 token），两个对话的第一条用户消息分别为 $m_1$、$m_2$。请求 1（$S+m_1$）完成 prefill 后，树上有边 $S$ 到节点「提示词缓存」、再接边 $m_1$ 到「对话 1 全序列」。请求 2（$S+m_2$）到达：沿树比对 token，在 $S$ 段全部匹配（走到「提示词缓存」节点），在 $m_1$ 与 $m_2$ 的第一个不同 token 处停下——「提示词缓存」就是它能匹配到的最深节点，$S$ 段的缓存直接复用，prefill 只算 $m_2$ 段，算完把 $m_2$ 作为「提示词缓存」的新子边插入。这个"能匹配到的最深节点"通常叫分叉点，它到根的路径就是两个请求的最长公共前缀。

    若请求 3 的提示词是 $S'$（与 $S$ 从第一个 token 起就不同），它在根节点就分叉，复用为零——这也解释了为什么"前缀"匹配要求从头相同。SGLang 的实现细节：树上匹配以 token 为粒度（页大小 1 token），KV cache 张量存放在非连续分页布局中，节点关联到具体物理页[C3]。

    展开：三个请求走树的完整过程

    构造示例。设 $S$ 长 200 token、$m_1$ 长 30、$m_2$ 长 40、$S'$ 长 200 token、$m_3$ 长 30 token。初始树只有根。请求 R1 $=S+m_1$：根下无边可匹配，prefill 全部 $200+30=230$ token，完成后插入边 $S$（根 $\to$ 节点 A）与边 $m_1$（A $\to$ 节点 B）。请求 R2 $=S+m_2$：沿边 $S$ 逐 token 匹配 200 个全部命中，节点 A 以下的 $m_1$ 与 $m_2$ 首 token 不同，匹配停在 A；prefill 只算 $m_2$ 的 40 token，插入边 $m_2$（A $\to$ 节点 C）。请求 R3 $=S'+m_3$：$S'$ 的第一个 token 与 $S$ 不同，在根就分叉，prefill 全部 $S'+m_3=230$ token，插入边 $S'$（根 $\to$ 节点 D）。三请求总 prefill 计算量：$230+40+230=500$ token；无缓存则为 $230\times 3=690$ token。R2 省下的 200 token 正是共享前缀的长度。

    本章问题

    1. 新请求怎么在 radix tree 上找到最长可复用前缀？

      解答：沿边逐 token 比对，停在分叉点

      从根出发，把请求的 token 序列与树上各边标签逐段比对：边标签完全匹配则前进到子节点继续；在某条边上遇到不同 token 则停在当前节点——该节点即分叉点，根到它的路径是请求与已缓存内容的最长公共前缀，其关联的物理页直接复用。剩余尾部 prefill 计算后作为分叉点的新子边插入树中。请求 $S+m_2$ 在存有 $S+m_1$ 的树上匹配到 $S$ 段末尾的节点，复用 200 token、只算 $m_2$。

    2. radix tree 与朴素前缀树（trie）的区别是什么？

      解答：边标变长段而非单 token，树更矮

      trie 每条边只标一个 token，长序列对应深链；radix tree 把无分叉的单链路径压缩成一条标变长 token 段的边，树高与查找开销显著降低。语义不变：两种树都表达"根到节点路径 $=$ 已缓存序列"的前缀结构。SGLang 选 radix tree 正是为其空间效率与高效的前缀搜索、插入、逐出[C3]。

    3. 缓存满了怎么办——LRU 逐出与引用计数

    显存有限，不可能把所有历史前缀都留在树上（这正是 KV cache 第 4 章的容量矛盾）。SGLang 的策略是简单 LRU，但逐出顺序有讲究：先逐出最近最少使用的叶子。叶子是没有子节点的节点——对话 2 分支的末端。逐出叶子后，它的父节点（如共享的 $S$ 段）不跟着消失，仍可被对话 1 及未来请求复用；直到某节点的所有子分支都被逐出、它自己成为叶子，才轮到它[C4]。效果：被多个分支引用的共享前缀天然长寿——这正是逐出策略对负载共享结构的自适应。

    两个配套机制。其一，引用计数：continuous batching（连续拼批：请求可动态加入或退出运行中的批次）下，正在运行的请求还在使用某些节点，不能逐出；每个节点维护一个计数器记录有多少运行请求在用它，计数为 0 才可逐出[C5]。其二，共享内存池：系统不划一块固定的"缓存专区"，缓存 token 与运行请求的 token 共用同一内存池——等待请求多时宁可逐出缓存换更大批次，请求稀疏时让缓存尽量多留[C5]。

    本章问题

    1. 为什么逐出叶子优先？共享前缀因此获得什么待遇？

      解答：叶子是最细分支，祖先复用价值更高

      叶子代表单一序列的末端，逐出它只损失一个分支；它的祖先可能被多个分支共享（如 $S$ 段被两个对话共用），逐出祖先会同时毁掉所有子分支的复用机会。LRU 从叶子逐出让祖先一直存活到"所有子分支都被逐出、自己成为叶子"为止——共享前缀的存活期与引用它的分支数成正比，天然保护了复用价值最高的节点。代价是最久未用的长尾分支会完整消失，下次到来需整体重算。

    2. 正在运行的请求占用的缓存会被逐出吗？

      解答：不会，引用计数为 0 才可逐出

      每个节点维护引用计数，表示当前有多少运行中的请求正在使用它（continuous batching 下请求加入或离开运行批都会更新计数）。计数非 0 的节点不可逐出。这保证了运行请求的注意力计算始终能读到自己的缓存。缓存与运行请求共享同一内存池，系统在两者间动态分配：等待请求多时逐出缓存换大批次，空闲时尽量多留缓存。

    4. 命中率——页大小是隐藏的自变量

    前缀缓存的收益最终由命中率决定：命中 token 占总 token 的比例。三个因素共同决定它：负载的共享结构（请求间共享多长的前缀）、缓存容量（逐出压力）、以及一个容易被忽略的变量——页大小。

    页大小影响命中率的机制是按页匹配（PagedAttention 的页）：缓存以页为分配与共享单元，匹配时只有完整落在共享前缀内的页才算命中[C8]。页命中数与命中 token 数为：

    $$\text{页命中数}=\left\lfloor\frac{\text{共享前缀长度}}{\text{页大小}}\right\rfloor,\qquad \text{命中 token 数}=\text{页命中数}\times\text{页大小}.$$[F1]

    构造示例：两个请求共享 100 token 前缀（与 PagedAttention 的页大小权衡同源）：

    页大小页命中数命中 token 数落空部分
    1（SGLang）$\lfloor 100/1\rfloor=100$100无
    32（TensorRT-LLM 默认；vLLM 默认 16，32 是最大支持值）$\lfloor 100/32\rfloor=3$96最后 4 token
    256（大页）$\lfloor 100/256\rfloor=0$0整段：100 token 均不足一页

    共享前缀不是页大小整数倍时，尾巴上不足一页的部分全部落空；页越大落空越多，极端时整段共享归零。这不是理论洁癖：Strata 论文的实验里，页 512 配置的 SGLang-HiCache 命中率比 Strata-IO 低 2.4%，把基线系统调到其最优页大小（512）吞吐也只为 Strata-IO 的 93%[N2]。SGLang 把页大小定为 1 token，正是让匹配粒度细到 token 级、命中率不受页对齐损失[N1]——代价则是管理开销与跨层传输单元（PagedAttention 第 3、4 章的另一半权衡）。

    最后一个边界：命中要求页"已在显存且已算完"。在 CPU/SSD 层的命中还要先把页搬回 GPU（分层缓存，搬运效率是 Strata 的主题）；前缀"正在计算中"时到达的同前缀请求也不能直接复用，反而会引发重复计算——这个 delay hit 现象同样在 Strata 一文中处理。

    本章问题

    1. 同样的共享结构，为什么换个页大小命中率就变了？

      解答：按整页计命中，非整页的尾巴落空

      匹配以页为粒度：只有整页落在共享前缀内才计命中。共享 100 token 时，页 1 全命中；页 32 命中 3 页共 96 token，末尾 4 token 落空；页 256 一页都不满、命中为零。页命中数 $=\left\lfloor\text{共享前缀长度}/\text{页大小}\right\rfloor$。页越大、共享前缀对页边界越敏感，命中率越低。实测页 512 配置的 SGLang-HiCache 命中率比 Strata-IO 低 2.4%（Strata §5.3.2）。

    2. 命中率之外，命中还要满足什么条件才真正省掉计算？

      解答：页在显存中且已计算完成

      两个条件。其一，页必须在显存：分层存储下命中于 CPU/SSD 层的页需要先搬回 GPU，搬运本身有代价（传输效率问题见 PagedAttention 与 Strata 两文）。其二，页必须已算完：前缀正在 prefill 时（缓存未就绪），后到的同前缀请求无法复用，还会与在算请求重复计算——delay hit 现象，其调度缓解是 Strata 一文的 cache-aware 调度部分。本文的命中率讨论默认这两个条件满足。

    5. 两种实现——radix tree 与哈希

    SGLang 用 radix tree，但这是选择而非必然。vLLM 与 Mooncake 用哈希：每个页由其 token ID 与前一页的哈希值链式计算出一个唯一指纹，两个请求的页指纹相同即前缀相同，用哈希表直接定位到物理页，不需要任何树结构[C7]。LMDeploy 则用粗粒度 trie 做折中[C7]。

    维度radix tree（SGLang）哈希指纹（vLLM、Mooncake）
    索引结构压缩前缀树，边标 token 段哈希表，键为页指纹
    匹配方式沿树走到分叉点（最长前缀匹配）逐页算指纹查表
    逐出时的结构推理叶子优先、祖先复用有明确结构依据无树结构，逐出按哈希表项管理
    跨节点/分布式共享树是实例内结构指纹天然可跨节点比对（分布式缓存友好）

    两种实现的对比属于分析性判断（上表后半两行）：树的结构给了最长前缀匹配与逐出策略明确的推理框架，哈希的实现简单且指纹与位置无关、便于跨实例共享缓存——Mooncake 做全局分布式缓存池正是利用这一点。本文不对"哪种更好"下结论，两者在各自系统中都工作良好。Strata 基于 SGLang，把 RadixTree 扩展为 HiRadixTree（作为页表存储各 KV cache 页的元数据），这一谱系的分层扩展在 Strata 一文展开。

    本章问题

    1. 哈希实现怎么判断两个请求的前缀相同？

      解答：token ID $+$ 前页指纹链式哈希

      每页的指纹由该页的 token ID 与前一页的指纹一起哈希得到。因为链式依赖，两个请求从第一个 token 起完全相同时，每一页的指纹都相同；任何位置出现不同 token，其后所有页的指纹都不同。指纹相同即可到哈希表取同一物理页。这把"前缀是否相同"的判断变成每页一次哈希计算，不需要树遍历。

    2. 树与哈希各自的取舍是什么？

      解答：结构推理能力对实现简单与分布式友好

      radix tree 的结构（分叉点、祖先-叶子关系）给最长前缀匹配和"叶子优先逐出、祖先复用"提供了明确的推理依据；哈希实现省去树结构、代码简单，且页指纹与存储位置无关，跨节点比对天然可行，适合 Mooncake 式的分布式缓存池（此对比为分析性判断，两种实现各有论文系统采用）。LMDeploy 的粗粒度 trie 是两者间的折中。

    来源与范围说明

    核心论断与来源

    C1（既有系统完成后丢弃缓存、阻止复用）、C2（RadixAttention 运行时自动复用 + LRU + cache-aware 调度 + 兼容性）、C3（radix tree 压缩边、token-张量映射、页 1 token、非连续分页）、C4（LRU 叶子优先、祖先复用）、C5（引用计数与共享内存池）、C9（生成结果入缓存）：Zheng et al., "SGLang: Efficient Execution of Structured Language Model Programs", NeurIPS 2024（arXiv:2312.07104）§1、§3.2。C6（context/prefix caching 被 OpenAI、Google 等采用）、C7（SGLang RadixTree / vLLM+Mooncake 哈希 / LMDeploy 混合 trie / Strata 扩展 HiRadixTree）：Xie et al., "Strata", OSDI 2026（arXiv:2508.18572v2）§2.3、§6。C8（按页匹配、页大小影响命中率）：Strata 论文 §3.1（"cache matching is performed on a per-page basis"）。"树 vs 哈希"优劣对比为分析性判断，已在正文标注。

    核心公式与来源

    F1（页命中数 $=\left\lfloor\text{共享前缀长度}/\text{页大小}\right\rfloor$）：按页匹配机制（C8）的直接换算，构造算例专用；非论文给出的显式公式。

    外部数字与实验条件

    N1（SGLang 页大小 $=$ 1 token）：SGLang 论文 §3.2。N2（页 512 配置的 SGLang-HiCache 命中率比 Strata-IO 低 2.4%、最优页吞吐为 Strata-IO 的 93%）：Strata 论文 §5.3.2（条件：SGLang-HiCache 基线、Qwen2.5-14B、H200、LooGLE、对照为 Strata-IO）。N3（共享 100 token $\times$ 页 1/32/256 算例）：构造示例。N4（分层系统约 95% 命中率）：Strata 论文 §5.2.1（LooGLE、1TB pinned DRAM；本文未正文引用，仅口径备查）。

    构造示例

    系统提示词 $S$（200 token）与消息 $m_1$（30 token）、$m_2$（40 token）、另一提示词 $S'$：数字为便于手算的构造选择；三请求走树的过程（R1/R2/R3，总计算 500 对 690 token）与 100 token $\times$ 三种页大小的命中表均为构造算例，机制与来源论断一致。

    辅助解释与类比边界

    "共享前缀天然长寿"是对 LRU 叶子优先逐出的效果描述（论文机制原文为叶子先逐出、祖先可继续复用），"存活期与引用分支数成正比"为推断标注。"分布式缓存友好"只解释指纹与位置无关这一局部性质，不构成对 Mooncake 架构的完整描述。

    简化条件及其限制

    其一，树上匹配描述到 token 粒度，SGLang 实现细节（节点锁、异步插入等工程问题）未展开。其二，cache-aware 调度（优先调度与缓存匹配的请求）只在 scope 层面提及一句，策略对比（如 LPM）归 Strata 一文消融部分。其三，近似缓存（CacheGen/CacheBlend）只作一句排除（要求精确前缀），其机制不覆盖。其四，命中条件的两个前提（页在显存、已算完）在第 4 章末尾说明，相关机制（分层传输、delay hit）归 Strata 一文。
