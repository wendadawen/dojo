## 2. 章节设计

### S1 一个字是怎么蹦出来的：token、参数与 Transformer 层

- 主要教学问题：零基础读者需要知道什么，才能听懂"MoE 替换 FFN"？
- 对应范围：C1、C2、N7；服务 Q1 的前置
- 正文要点：
  - token：文本被切成的小块（例：一句话切成若干 token）
  - 参数/权重：模型里存储的大量数字，一次"计算"就是输入逐层流过、与这些数字做乘加
  - 大模型逐字生成：一次前向计算只产出一个新 token（自回归的一句话版本，S5 再展开）
  - Transformer 层堆叠；每层两个模块：attention（token 之间交换信息）与 FFN（每个 token 独立过的小计算器）
  - 手算：Vaswani 配置 d=512、d_ff=2048 → attention 4 个投影 4d²≈105 万，FFN 两个矩阵 8d²≈210 万，FFN 约占 2/3（N7，标注忽略 bias/LayerNorm）
- 材料：ASCII 图 D1（层堆叠：token → attention → FFN → 下一层；FFN 参数占比标注）
- 前置知识安排：全部内联（token/参数/前向计算）
- 完成检查：说出一个 token 经过一层时两个模块各做什么；复算 4d² 与 8d²
- 过渡：既然 FFN 是参数大户，想把模型"撑大"，先动它

### S2 把一个 FFN 换成一排专家：MoE 与 top-k 稀疏激活

- 主要教学问题：为什么 MoE 能让参数暴涨而每 token 计算量几乎不涨？
- 对应范围：C3、C4、F1、N1–N3、E1；完整回答 Q1
- 正文要点：
  - 动机：更多参数≈更强的记忆与表达能力，但稠密模型参数翻倍 → 每个 token 计算量翻倍 → 服务成本翻倍
  - 机制：把那个 FFN 复制成 N 个小 FFN（routed expert），加一个小型"打分器" router；每个 token 只选打分最高的 k 个专家计算，输出按门控权重加权求和（F1）；未选中的专家对该 token 不计算
  - shared expert：所有 token 都经过，与 routed expert 并存（C4）
  - 边界检查：k=N 且权重均匀时退化为"所有专家都算"，失去稀疏意义 → k 必须远小于 N
  - 数字例子 E1（教学示例，正文）：8 个 routed expert、top-2，给定打分表，选出专家 3 与 7，按权重 0.7/0.3 加权
  - 真实数字：V3 的 671B/37B（手算 37/671≈5.5%）、256+1 top-8、61 层中前 3 层稠密（N1–N3）
  - 负载不均一句话：router 可能总偏爱少数专家，训练侧用辅助损失或 bias 缓解（C5 前半，标注"训练问题，本页不展开"）
  - 误解破除：专家不是独立模型（误解 1）
- 材料：F1 公式 + 符号表；E1 表格；折叠块：一句话历史脉络（Shazeer 2017 → GShard top-2 → Switch top-1 → V3 top-8，说明 k 取值无标准）
- 完成检查：用一句话解释"为什么总参数 671B 但每 token 只算 37B"；复算 E1 的专家选择
- 过渡：只激活 5.5% 是省了计算，但 671B 权重一个数字都不能少地存在某处——一张卡放不下

### S3 权重放不下了：专家并行与 all-to-all 搬运

- 主要教学问题：EP 为什么必须存在？dispatch/combine 搬的是什么？
- 对应范围：C6、C7、E2、N4；完整回答 Q2 前半
- 正文要点：
  - 误解破除（误解 2）：激活 5.5% 参数 ≠ 只需 5.5% 显存；全部权重必须驻留（GPU 显存有限，一句话内联解释 GPU/显存 + 占位提示《GPU 执行模型》概念页规划中）
  - EP：把 256 个专家分片到多张卡，每卡只存几个（C6）；与 DP/TP 的一句区分
  - 路由按 token 决定 → token 激活要被送到选中专家所在卡：dispatch；算完送回：combine；通常用 all-to-all（每卡都可能与所有卡换数据）实现（C7）
  - 数字例子 E2（教学示例，正文）：2 卡 × 2 专家、4 个 token、top-2 路由表 → 数 dispatch 发送的 token-expert 对与 combine 返回数；观察：卡 A 收到 3 对、卡 B 收到 1 对 → 负载不均，慢卡拖慢整步（C5 后半在服务端的表现）
  - 真实规模 N4：V3/R1 在线系统 prefill EP32（4 节点）、decode EP144（18 节点）
  - 可运行代码（折叠块，组件 12）：模拟 8 专家 top-2、2 卡 EP 的 dispatch 计数与负载统计，输出与 E2 一致并扩展到随机路由看倾斜
- 材料：ASCII 图 D2（token → router → dispatch → 各卡专家 → combine → 下一层）
- 完成检查：说出 dispatch 与 combine 各搬什么、方向如何；复算 E2 计数
- 过渡：搬运要花时间，通信在路上时 GPU 在干什么？

### S4 通信不能干等：TBO 与 SBO 的重叠

- 主要教学问题：TBO/SBO 怎样把 all-to-all 的时间"藏起来"？
- 对应范围：C8；完整回答 Q2 后半
- 正文要点：
  - 串行时间线：计算 → dispatch → 专家计算 → combine → 下一层，通信期间算力闲置（气泡）
  - TBO：把一批拆成两个微批，微批 A 通信时微批 B 计算（C8；V3 prefill 双批次重叠 N4）
  - SBO：同一微批内，shared expert 计算与 routed expert 的 dispatch/combine 并行（C8）
  - 边界（误解 3）：重叠是"藏"不是"消"；通信仍占带宽与硬件；批内没有可并行工作就藏不住
- 材料：ASCII 时间线图 D3（串行 / TBO / SBO 三条）
- 完成检查：给一条串行时间线，指出 TBO 与 SBO 分别能盖住哪段
- 过渡：模型会算了、卡铺开了、通信藏了——用户的一次请求是怎么流的？

### S5 一次请求的两个阶段：prefill、decode 与 KV cache

- 主要教学问题：为什么服务要分 prefill/decode，KV cache 省掉了什么？
- 对应范围：C9、C10、E3；完整回答 Q3
- 正文要点：
  - 自回归展开：S1 的"逐字生成"现在展开为循环——每次把已有全部 token 过一遍模型、产出一个新 token
  - 朴素做法的浪费：第 t 步要为全部 t 个前缀 token 重算 attention 的 K/V
  - KV cache：每层把算过的 K/V 张量存下来，下一步只算新 token 的 K/V 再拼接（C10）
  - 数字例子 E3（教学简化标注：只数 K/V 投影计算次数，忽略 attention 打分）：prompt 4 token + 生成 3 token，无 cache 时 K/V 计算 4+5+6=15 token 次，有 cache 时 4+1+1+1=7 token 次
  - 由此两阶段分化：prefill 一次性并行处理全部输入、建 cache、出首 token（吞吐导向）；decode 每步 1 token、读 cache（延迟敏感，C9）
  - 折叠块：KV cache 占用随对话变长而增长，是显存管理难题（一句，PagedAttention 留扩展阅读）
- 材料：ASCII 图 D4（prefill/decode 流程与 cache 复用）
- 完成检查：复算 E3；说出 prefill 与 decode 各自读/写 cache 的方式
- 过渡：两阶段脾气不同——怎么量化"服务得好不好"？

### S6 服务好不好怎么量：TTFT、TPOT、SLO 与 goodput

- 主要教学问题：四个指标各量什么、为什么延迟要拆成两个？
- 对应范围：C11、C12、E4；完整回答 Q4
- 正文要点：
  - TTFT = prefill 时长（首 token 延迟）；TPOT = 除首 token 外平均每 token 时间（C11）
  - 为什么拆：应用需求不同——聊天看 TTFT；TPOT 快过人阅读速度（约 250 词/分钟）即可；长文生成看 TPOT（C12）
  - 数字例子 E4（教学示例，正文）：prefill 0.3 s + 5 步 × 0.05 s → TTFT=0.3 s，TPOT=0.05 s，总延迟 0.3+5×0.05=0.55 s（验证 C11 脚注公式）
  - SLO：对 TTFT/TPOT 分别设上限并要求达成率（如 P90 达标）
  - goodput：满足达成率前提下的最大请求率（C12）；与裸吞吐对照（误解 4）：加请求会拖长队列，超 SLO 的请求不算数
  - N6：DistServe 的 7.4×/12.6× 结论一句带过（证明这组指标驱动的设计有效）
- 材料：E4 时间线表格；指标对照表（组件 14）
- 完成检查：给定新时间线复算 TTFT/TPOT/总延迟；说出 goodput 与吞吐量的区别
- 过渡：两个指标由两个脾气不同的阶段贡献——部署上把它们放一起还是分开？

### S7 放一起还是分开：PD 合设与 PD 分离

- 主要教学问题：colocation 与 PDD 各自的动机和基本代价？
- 对应范围：C13、C14、N5、误解 5；完整回答 Q5
- 正文要点：
  - 合设：一份权重、无 KV 传输；但 prefill 步长、decode 步短，互相拖延（干扰，C14）
  - 分离：两阶段各自成实例，消除干扰、按各自目标配资源（C13）；代价：每实例完整副本（MoE 权重大 → 副本贵）、跨实例 KV 传输、按 P:D 配比以部署单元扩容（N5：V3 报告单元 32P+320D；误解 5 破除）
  - 一句展望：两条路线各自的深层局限与更细的混合架构是 ExpertPlex 论文解析页的主题（本页不展开）
- 材料：对照表（组件 14：合设 vs 分离：权重份数 / 干扰 / KV 传输 / 资源配置粒度）
- 完成检查：说出两条路线各付出什么代价换什么
- 过渡：无（接文末来源与教学说明）
