    MoE 大模型推理与服务基础：从"存得多、算得少"到在线服务

    主要依据：DeepSeek-V3 Technical Report（arXiv:2412.19437）、DistServe（OSDI 2024，arXiv:2401.09670）、ExpertPlex 背景章（arXiv:2607.18002 v2 §2）、Shazeer et al. 2017（arXiv:1701.06538）；逐条定位见文末"来源与范围说明"。

    DeepSeek-V3 有 6710 亿（671B）个参数，但它回答问题时，每生成一个字只动用其中约 370 亿（37B）——大约 5.5%[N1]。它是怎么做到"存得多、算得少"的？而这 5.5% 的计算，又如何摊到几百张 GPU 上，支撑起一个在线服务？

    一句话说清本页内容：MoE（Mixture-of-Experts，专家混合）大模型从模型结构到在线服务的最小概念链——为什么把 Transformer 层里的一个模块换成"一排只被选中几个的专家"、专家怎么摆到多张 GPU 上、一次请求经过哪两个阶段、服务好坏怎么量、两个阶段放一起还是分开。

    核心问题

    1. 为什么把 Transformer 层的 FFN 换成 MoE，能让模型存下多得多的参数而每个 token 的计算量几乎不涨？

      解答：稀疏激活把存储与计算解耦

      MoE 把每层的一个 FFN 复制成 $N$ 个专家，再加一个 router；每个 token 只让得分最高的 $k$ 个专家计算，输出按门控权重加权求和。参数总量随 $N$ 增长，每个 token 的计算量只随 $k$ 增长，存储与计算由此解耦。DeepSeek-V3 以 256 选 8 加 1 个共享专家，实现总参数 671B、每 token 激活约 37B（约 5.5%）。完整论证见「2. 把一个 FFN 换成一排专家：MoE 与 top-k 稀疏激活」。

    2. MoE 模型的专家为什么要切到多张 GPU 上，all-to-all 的 dispatch/combine 在搬运什么，TBO/SBO 怎样掩盖这部分通信开销？

      解答：EP 切分引出 all-to-all，重叠掩盖通信

      稀疏激活只省计算不省存储，全部权重必须驻留显存，单卡放不下，因此按专家分片到多卡（专家并行）。分片之后，token 的激活必须送到选中专家所在的卡（dispatch），专家输出要送回原卡加权求和（combine），两者通常用 all-to-all 通信实现。TBO 让一个微批的通信与另一个微批的计算同时进行；SBO 在同一批内让共享专家的计算与路由专家的通信同时进行。重叠是"藏"不是"消"，通信仍占带宽。完整论证见「3. 权重放不下了：专家并行与 all-to-all 搬运」与「4. 通信不能干等：TBO 与 SBO 的重叠」。

    3. 一次对话请求在 prefill 和 decode 两个阶段分别做什么，KV cache 消除了哪部分重复计算？

      解答：prefill 建缓存，decode 读缓存

      prefill 一次性并行处理全部输入 token，逐层写入 key/value 并建立 KV cache，产出第一个新 token，计算密集、追求吞吐；decode 每步只处理 1 个新 token，大量时间花在读 KV cache 上，对延迟敏感。KV cache 消除的是"每生成一步就把全部前缀重新过一遍模型"带来的 key/value 重复计算：前缀不变，其 key/value 只需计算一次。完整论证见「5. 一次请求的两个阶段：prefill、decode 与 KV cache」。

    4. TTFT、TPOT、SLO、goodput 各自衡量什么，为什么"服务快"要拆成两个指标？

      解答：两个阶段贡献两段延迟

      TTFT 是首 token 延迟，约等于 prefill 时长；TPOT 是除首 token 外平均每个输出 token 的生成时间，反映 decode 速度；总延迟 = TTFT + TPOT × decode 阶段生成的 token 数。SLO 是服务方对这两个指标分别承诺的上限与达标比例，goodput 是在满足 SLO 达成率前提下系统能承接的最大请求率。拆成两个指标，是因为两阶段的资源脾气不同，且不同应用对首字等待与出字速度的要求不同。完整论证见「6. 服务好不好怎么量：TTFT、TPOT、SLO 与 goodput」。

    5. PD 合设与 PD 分离各自的动机和基本代价是什么？

      解答：干扰与副本的权衡

      PD 合设让两阶段共享同一批 GPU 与一份权重，省显存、KV cache 就地可用，代价是长短步互相干扰，TTFT 与 TPOT 互相拖累。PD 分离给两阶段各自一组实例，消除干扰并允许独立定制资源，代价是每个实例都要存一份完整模型副本、KV cache 要跨实例传输、容量要按部署单元成组扩缩。完整论证见「7. 放一起还是分开：PD 合设与 PD 分离」。

    1. 一个字是怎么蹦出来的：token、参数与 Transformer 层

    模型不直接读文字。输入的一句话会先被切成若干小块，每块叫一个 token（大致是一个字或一个词片段）。模型看到和生成的，都是一串 token。

    一个大模型本质上是一大批存好的数字，叫参数（也叫权重）。一次"计算"就是让输入逐层流过模型、与这些数字做大量乘加，最后产出一个新 token——这一趟叫一次前向计算。聊天时模型不是一次说完整句话，而是一个 token 一个 token 往外蹦：每次前向计算只产出一个新 token，把它接在末尾再算下一个。这叫自回归生成，第 5 章会展开它带来的后果。

    大模型由几十层相同结构的 Transformer 层堆叠而成。每一层里有两个模块[C1]：

    • attention（注意力）：让 token 之间交换信息。"它"指代谁、哪个词修饰哪个词，靠这一步把前面 token 的信息汇过来。
    • FFN（前馈网络）：对每个 token 独立做同一套变换的小计算器，token 之间在这一步互不打交道。它由两个矩阵（两张"把向量变成另一个向量的权重表"）构成。
    一个 token 穿过一层 Transformer
    token 向量→ attentiontoken 之间交换信息参数 $\approx 4d^2$→ FFN每个 token 独立变换参数 $\approx 8d^2$（约为前者的 2 倍）[C2]→ 送往下一层

    这两个模块谁存的参数多？在 Transformer 原始论文（Vaswani 等，2017）的标准配置里，隐层宽度 $d=512$，FFN 中间层宽度 $d_{ff}=2048$。可以手算（忽略偏置和归一化参数）：

    • attention 有 4 个投影矩阵，每个 $d\times d$，合计 $4d^2 = 4\times 512^2 = 1{,}048{,}576 \approx 105$ 万个参数；
    • FFN 的两个矩阵分别是 $d\times d_{ff}$ 和 $d_{ff}\times d$，合计 $2\times 512\times 2048 = 8d^2 = 2{,}097{,}152 \approx 210$ 万个参数。

    FFN 约占两者之和的 2/3[N7]。也就是说，每一层里存"知识"的大头是 FFN。这个比例是下一章的出发点：想把模型"撑大"，首先动的是 FFN。

    本章问题

    1. 说出一个 token 经过一层 Transformer 时，attention 和 FFN 各做什么。

      解答：attention 跨 token 汇信息，FFN 逐 token 变换

      attention 让 token 之间交换信息：每个 token 从前面所有 token 汇聚信息，解决"它"指代谁、哪个词修饰哪个词这类依赖。FFN 对每个 token 独立做同一套变换，token 之间在这一步互不打交道。标准配置下 attention 参数约 $4d^2$、FFN 约 $8d^2$，FFN 是每层的参数大户。

    2. 复算 $d=512$、$d_{ff}=2048$ 时两个模块的参数量，并说明 FFN 占比。

      解答：105 万对 210 万，FFN 约占 2/3

      attention 有 4 个 $d\times d$ 投影矩阵，合计 $4\times 512^2 = 1{,}048{,}576\approx 105$ 万；FFN 的两个矩阵分别为 $d\times d_{ff}$ 与 $d_{ff}\times d$，合计 $2\times 512\times 2048 = 2{,}097{,}152\approx 210$ 万。FFN 占两者之和的 $210/(105+210)=2/3$。该结果在忽略偏置与归一化参数的条件下成立。

    既然 FFN 是参数大户，"让模型更大"在工程上就是"让 FFN 更大"。下一章的问题是：怎样让 FFN 部分存下几十倍的参数，却不让每个 token 的计算量跟着爆炸？

    2. 把一个 FFN 换成一排专家：MoE 与 top-k 稀疏激活

    直觉上，模型存的参数越多，能记住和表达的东西越多。但稠密（dense）模型里参数翻倍意味着每个 token 的计算量也翻倍——每一层的每个模块对每个 token 都要算一遍。计算量直接就是服务成本：参数翻倍，每个回答都贵一倍。有没有办法让"存得多"和"算得少"分开？

    MoE 的做法是：把每层那个 FFN 复制成一排 $N$ 个小 FFN，每个叫一个专家（expert）；再加一个很小的打分器叫 router（路由器）。每个 token 到来时，router 给所有专家打分，只让得分最高的 $k$ 个（top-k）专家真正计算这个 token，其余专家这一轮完全不碰它。选中的专家各自给出输出，最后按 router 给的权重加权求和[F1]：

    $$y(x)=\sum_{i\in S_k(x)} g_i(x)\cdot E_i(x)$$

    • $x$：该 token 的输入向量；
    • $E_i(x)$：第 $i$ 个专家（一个小 FFN）对 $x$ 的输出；
    • $S_k(x)$：router 为 $x$ 选中的 $k$ 个专家；
    • $g_i(x)$：选中专家的门控权重，由打分归一化而来；
    • $y(x)$：这一层对该 token 的最终输出。

    用一个边界检查这个公式：如果 $k=N$（全部选中）且权重相同，MoE 就退化成"所有专家都算一遍"，稀疏省算力的意义消失。所以 $k$ 必须远小于 $N$——DeepSeek-V3 是 256 选 8。

    构造示例。 构造 8 个 routed expert（按路由激活的专家）、top-2 的情形。某个 token 的 router 打分如下（打分为便于手算构造的数字）：

    专家编号01234567
    router 打分0.10.30.050.90.20.40.10.6

    得分最高的两个是专家 3（0.9）和专家 7（0.6）。把选中专家的得分归一化为权重：$g_3 = 0.9/1.5 = 0.6$，$g_7 = 0.6/1.5 = 0.4$，于是这一层的输出是 $y = 0.6\,E_3(x) + 0.4\,E_7(x)$。其余 6 个专家对这个 token 完全不计算。（教学简化：归一化细节因实现而异——DeepSeek-V3 用 sigmoid 亲和度打分再加偏置选 top-8，见其技术报告 §2.1.2；但"只算选中的 $k$ 个、输出加权求和"这一结构是共同的。）

    除 routed expert 外，还有一类 shared expert（共享专家）：所有 token 都经过它，与按路由激活的专家并存，承载每个 token 都需要的通用变换[C4]。

    现在把开头那个数字落实。DeepSeek-V3 的每个 MoE 层含 1 个 shared expert 与 256 个 routed expert，每个 token 激活其中 8 个（top-8）[N2]；全部 61 层中，前 3 层保留稠密 FFN，其余 58 层是 MoE 层[N3]；模型总参数 671B，每个 token 只激活约 37B[N1]。手算验证：$37 \div 671 \approx 0.055$，即每个 token 只动用约 5.5% 的参数。这就是"存 671B、每 token 只算 37B"同时成立的原因：稀疏激活把总参数量和每 token 计算量解耦了[C3]。

    注意：MoE 不是"几个独立模型在投票"。专家是同一个网络内部的一排小 FFN，与 router 一起联合训练、作为一个模型统一部署——没有任何一个专家能单独回答问题。

    router 可能总偏爱少数几个专家，被选中的累垮、没被选中的白训。训练时要靠额外的均衡机制（辅助损失或偏置调整）拉住，这属于训练侧问题，本页不展开。但负载可能不均这一隐患在服务侧会以另一种形式出现——见下一章。

    补充：稀疏 MoE 的历史脉络（top-k 的 k 没有标准答案）

    （以下为背景补充，非本页核心论断。）稀疏激活的专家混合层由 Shazeer 等人 2017 年提出（带噪声的 top-k 门控，最多 1370 亿参数）[C3]；GShard（Lepikhin 等，2020，arXiv:2006.16668）把它搬进 Transformer 并用 top-2；Switch Transformer（Fedus 等，2021，arXiv:2101.03961）简化为 top-1；DeepSeek-V3（2024）用细粒度专家加 top-8[N2]。k 取多少、专家分多细，至今没有统一答案，是各模型自己的权衡。

    本章问题

    1. 用一句话解释"为什么 DeepSeek-V3 总参数 671B，但每个 token 只算约 37B"。

      解答：稀疏激活解耦容量与计算

      全部 671B 权重都驻留在显存里，但每个 token 只经过 router 选中的 8 个路由专家加 1 个共享专家，因此每个 token 实际计算的参数只有约 37B，占总量的约 5.5%。

    2. 给定 8 个专家的打分表，复算 top-2 的选择与归一化权重。

      解答：选最高两名，按选中得分归一化

      取得分最高的两个专家（0.9 与 0.6），两者得分相加为 1.5，归一化权重为 $g_3=0.9/1.5=0.6$、$g_7=0.6/1.5=0.4$，该层输出为 $y=0.6\,E_3(x)+0.4\,E_7(x)$，其余 6 个专家对这个 token 不计算。归一化细节因实现而异，此处采用的是按选中得分归一化的简化写法。

    3. 说明 shared expert 与 routed expert 的区别。

      解答：全量经过对按分选中

      shared expert 对所有 token 都计算，承载每个 token 都需要的通用变换；routed expert 只有被 router 打分选中的 token 才经过，承载按需激活的专门变换。两者并存于同一个 MoE 层，输出共同参与这一层的加权求和。

    本章解决了"算得少"。稀疏激活省的是计算，不是存储：那 671B 权重，一个数字都不能少地待在某个地方。下一章的问题是：一张 GPU 放不下时怎么办？

    3. 权重放不下了：专家并行与 all-to-all 搬运

    注意："每个 token 只激活 5.5% 的参数，所以模型只需要 37B 对应的显存。"错。稀疏激活省的是每 token 的计算量；全部 671B 权重都必须驻留——因为任何一个 token 都可能选中任何一个专家，哪个都不能缺。

    先补一个事实：GPU 是擅长并行做矩阵乘法的芯片，它的高速存储（显存）容量有限（单卡几十到上百 GB 量级），权重必须放进显存才能算。671B 参数远超单卡容量，必须把模型摊开。（GPU 内部如何执行计算见《GPU 执行模型》；本页只需要"显存有限"这一个事实。）

    MoE 有一种天然的切法：按专家切。把 256 个专家分片到多张 GPU，每张卡只存其中几个——这叫专家并行（EP，expert parallelism）[C6]。顺带区分两个容易混淆的切法（本页不展开）：把整模型复制多份分摊请求叫数据并行（DP），把每个矩阵切开来算叫张量并行（TP）。

    切完之后问题来了：路由是按 token 决定的，而每张卡只持有部分专家。于是每个 token 的中间结果（激活，即它流过这一层时的向量）必须被送到选中专家所在的卡上——这一步叫 dispatch；专家算完，结果要送回来加权求和——这一步叫 combine。由于每张卡上的 token 都可能要去任何一张卡，dispatch 和 combine 通常用 all-to-all 通信实现：每张卡都同时与所有其他卡交换数据[C7]。DeepSeek 为此开源了专门的通信库 DeepEP。

    一层 MoE 在 2 张卡上的数据流（EP=2，8 个专家每卡 4 个）
    卡 0 上的 token卡 1 上的 token → router 打分、选 top-k（每 token 决定去哪 $k$ 个专家）
    dispatch（all-to-all）：把激活送到选中专家所在的卡 ↓
    卡 0：专家 0,1,2,3卡 1：专家 4,5,6,7 → 各卡专家并行计算
    combine（all-to-all）：把专家输出送回原卡、加权求和 ↓
    下一层

    构造示例。 把上一章那 8 个 routed expert 放到 2 张卡上：卡 0 存专家 0–3，卡 1 存专家 4–7。4 个 token 的 top-2 路由结果如下（构造数字）：

    token选中的专家dispatch 到卡 0 的对数dispatch 到卡 1 的对数
    t11, 220
    t22, 511
    t31, 320
    t40, 611
    合计—62

    每个"token–专家"对就是一次搬运：卡 0 收到 6 对，卡 1 只收到 2 对；combine 再按原路把同样数量的结果送回。现在看负载：如果每对的计算时间相近，卡 0 这一步要干的活约为卡 1 的 3 倍，而整层要等所有卡都算完才能继续——卡 1 的算力在空转。上一章"路由偏好导致负载不均"的隐患，在服务侧就长成这个样子：token 的偏好直接变成 GPU 之间的忙闲不均[C5]。真实系统会复制热门专家、定期调整摆放来缓解（DeepSeek 的部署就是这么做的），细节超出本页范围。

    真实规模示例：DeepSeek 的在线推理系统里，prefill 的一个部署单元是 4 节点 32 张 GPU（EP32，每卡放 9 个路由专家加 1 个共享专家），decode 的一个部署单元是 18 节点 144 张 GPU（EP144，每卡只放 2 个路由专家加 1 个共享专家）[N4]。每卡的专家数多于 $256$ 除以卡数，是因为除 256 个路由专家外另设了 32 个冗余路由专家（合计 288）：$288/32=9$、$288/144=2$。256 个专家摊到上百张卡上，每张卡只剩个位数。

    代码：模拟 top-2 路由下的 dispatch 计数，验证上表 
    import random

# 构造示例：8 个路由专家、每 token 选 top-2，专家分片到 2 张卡
NUM_EXPERTS = 8
TOP_K = 2
NUM_GPUS = 2  # 卡 0 放专家 0-3，卡 1 放专家 4-7

def gpu_of(expert):
    return expert // (NUM_EXPERTS // NUM_GPUS)

# 正文构造示例的固定路由表：4 个 token 各自选中的 2 个专家
routes = [
    ("t1", [1, 2]),
    ("t2", [2, 5]),
    ("t3", [1, 3]),
    ("t4", [0, 6]),
]

counts = [0] * NUM_GPUS
for token, experts in routes:
    for e in experts:
        g = gpu_of(e)
        counts[g] += 1
        print(f"{token} -> 专家{e}（卡{g}）：dispatch 1 个 token-expert 对")
print(f"dispatch 计数：卡0={counts[0]} 对，卡1={counts[1]} 对")
print(f"combine 把同样数量的结果送回：卡0={counts[0]} 对，卡1={counts[1]} 对")

# 扩展：路由均匀随机时，1000 个 token 的负载是否仍可能倾斜
random.seed(0)
counts = [0] * NUM_GPUS
for _ in range(1000):

    本章问题

    1. 说出 dispatch 和 combine 各搬什么、沿什么方向搬。

      解答：激活去程，结果回程

      dispatch 把每个 token 的激活从它当前所在的卡搬到其选中专家所在的卡（去程）；combine 把专家算出的输出沿原路送回 token 原来的卡，在那里按门控权重加权求和（回程）。由于每张卡上的 token 都可能要去任何一张卡，两者通常用 all-to-all 通信实现。

    2. 复算上表卡 0 与卡 1 的计数，并解释"卡 1 空转"的原因。

      解答：6 对对 2 对，整层等最慢的卡

      4 个 token 各选 2 个专家，共 8 个 token–专家对：落在卡 0（专家 0–3）的 6 对，落在卡 1（专家 4–7）的 2 对。若每对计算时间相近，卡 0 要干的活约为卡 1 的 3 倍；而这一层必须等所有卡都算完才能继续，卡 1 在等待期间无活可干，算力空转。

    3. 解释为什么"每 token 只激活 8/256 个专家"并不能让模型少占显存。

      解答：任何一个专家都可能被选中

      router 的选择按 token 逐个决定，任何一个 token 都可能选中任何一个专家，因此全部 256 个专家的权重都必须驻留在显存中，缺一个就无法服务可能到来的路由。稀疏激活省的是每 token 的计算量，不是存储量。

    dispatch 和 combine 是真实的网络传输，要花时间。通信在路上时，GPU 在干什么？什么也不干——除非刻意安排。下一章的问题是：怎样把这段通信时间"藏起来"？

    4. 通信不能干等：TBO 与 SBO 的重叠

    把一层 MoE 的各步骤按时间排开，最朴素的执行是串行的：

    串行执行（一层 MoE）
    attention 等计算→ dispatch→ 专家计算→ combine→ 下一层
    dispatch 到 combine 之间：通信期间算力闲置（气泡）。

    通信期间 GPU 的算力在空转，这段空白叫气泡。all-to-all 的规模越大（卡越多、token 越多），气泡越长。两种通行的"藏"法[C8]：

    TBO（two-batch overlap，双批次重叠）：把一个大批拆成两个微批（microbatch），交替执行——微批 A 做 dispatch/combine 通信时，微批 B 在计算；轮到 B 通信时 A 在计算。一个微批的通信被另一个微批的计算盖住。DeepSeek 在线系统在 prefill 阶段用的正是这种"双批次重叠"[N4]。

    SBO（single-batch overlap，单批次重叠）：在同一微批内部找可并行的工作。shared expert 的计算不依赖路由结果，不需要等 dispatch——让它与 routed expert 的 dispatch/combine 同时进行，同一批之内把通信盖住。

    TBO：微批 A 的通信与微批 B 的计算重叠（时间向右）
    微批 A 计算 A通信 A专家 A计算 A′
    微批 B 计算 B通信 B专家 B …
    B 的计算盖住了 A 的通信；轮到 B 通信时 A 在计算。
    SBO：同一微批内，共享专家计算与路由专家通信重叠（时间向右）
    路由专家 计算dispatch/combine路由专家计算合并
    共享专家 shared 专家计算（与 dispatch/combine 同时进行）
    共享专家计算盖住了同批通信。

    注意边界：重叠是"藏"不是"消"。通信本身仍占用带宽与硬件资源；能否藏住取决于有没有足够的可并行计算——批太小、或 shared expert 的计算太短，气泡还是会露出来。TBO/SBO 也没有消除 all-to-all，只是让它与计算同时进行。在 GPU 内部，同一思路还能落得更细：让通信与专家计算在同一段代码里由不同分工同时推进，见 MegaMoE。

    本章问题

    1. 给定串行时间线，指出 TBO 和 SBO 分别能盖住哪一段通信。

      解答：跨批掩盖与批内掩盖

      TBO 把一个大批拆成两个微批交替执行：微批 A 做 dispatch/combine 通信时微批 B 在计算，因此盖住的是"另一个微批的通信"。SBO 在同一微批内部，让不依赖路由结果的 shared expert 计算与 routed expert 的 dispatch/combine 同时进行，盖住的是"本批内的路由专家通信"。

    2. 说出"重叠不能消除通信开销"的两个理由。

      解答：资源仍被占用，掩盖有条件

      其一，通信本身仍占用网络带宽与硬件资源，重叠只是让它与计算同时发生，并没有减少通信量，all-to-all 也依然存在。其二，能否盖住取决于有没有足够长的可并行计算：批太小或 shared expert 的计算太短时，气泡仍会暴露。

    模型会算了、权重铺开了、通信也藏住了。现在换到用户视角：从发出一句话到一个字一个字收到回答，中间到底发生了什么？

    5. 一次请求的两个阶段：prefill、decode 与 KV cache

    第 1 章说过，模型逐 token 生成。把这个过程展开成一个循环：第 1 步，把输入的全部 token 过一遍模型，产出第 1 个新 token；第 2 步，把"输入 + 刚生成的 token"再过一遍，产出第 2 个……直到模型说"完了"。每一步都要看到全部前缀。

    这里藏着一处巨大的浪费。attention 让每个 token 从前面所有 token 汇信息，为此每个 token 在各层都要算出两个向量：key 和 value（可以粗糙地理解为这个 token 的"检索标签"和"信息内容"）。如果每生成一步都把全部前缀重新过一遍模型，前面那些 token 的 key/value 就被一遍遍重算——而它们的内容一模一样，因为前缀从来没变过。

    解法直白：把每层算过的 key/value 张量存下来，这就是 KV cache。下一步只需为那 1 个新 token 算 key/value，再拼到 cache 后面[C10]。

    构造示例。 输入是 4 个 token，模型共生成 3 个新 token（prefill 产出首 token，decode 再产出 2 个，共 3 次前向）。只数 key/value 投影这一项的计算次数（教学简化：忽略 attention 打分与其余计算）：

    • 不存 cache：第 1 步要为 4 个前缀 token 算 key/value；第 2 步前缀变成 5 个，重算 5 个；第 3 步重算 6 个。合计 $4+5+6=15$ 个 token 次。
    • 存 cache：第一步算 4 个并入库；此后两步各只为新 token 算 1 个，重算的只有新的那一个。合计 $4+1+1=6$ 个 token 次。

    对话越长，差距越大——KV cache 把"每步重算全部前缀"变成"每步只算一个"。

    由此，一次请求自然分成两个阶段[C9]：

    • prefill（预填充）：一次性并行处理全部输入 token，建好 KV cache，产出第一个新 token。一次算很多 token，计算密集，追求吞吐。
    • decode（解码）：之后每步只处理 1 个新 token，大量时间花在读 KV cache 上。每一步都很短，但每一步的长短直接决定用户看到的"出字速度"，对延迟敏感。
    prefill：输入 [今][天][天][气] 一次性并行处理
    输入 [今][天][天][气] 一次性并行处理→ 各层 key/value 写入 KV cache→ 产出首 token「真」
    decode：每步只算 1 个新 token 的 key/value
    第 1 步：读 cache + 新 token「真」→ 算 1 个 key/value 追加进 cache→ 产出「好」
    第 2 步：读 cache + 新 token「好」→ 算 1 个 key/value 追加进 cache→ 产出「啊」
    每步只算 1 个新 token 的 key/value，前缀全靠读 cache。
    补充：KV cache 本身会占掉大量显存

    KV cache 随对话长度增长，长对话、多并发下它本身就是显存大户，怎么存放、换入换出、跨请求复用是推理引擎的核心难题之一（例如 vLLM 的 PagedAttention）。这属于引擎实现层，本页不展开。

    本章问题

    1. 复算 4 token 输入 + 生成 3 个 token 时，有无 KV cache 的 key/value 计算次数。

      解答：15 次对 6 次

      不存 cache：3 次前向分别要为 4、5、6 个前缀 token 计算 key/value，合计 $4+5+6=15$ 个 token 次。存 cache：第一步算 4 个并入库，此后两步各只为新 token 算 1 个，合计 $4+1+1=6$ 个 token 次。两侧对应同一组 3 次前向（1 次 prefill 加 2 步 decode，共产出 3 个 token）。该计数只含 key/value 投影一项，是浪费的下界而非全部。

    2. 说出 prefill 和 decode 各自对 KV cache 是"写"还是"读"，以及为什么 prefill 重吞吐、decode 重延迟。

      解答：写缓存求吞吐，读缓存求延迟

      prefill 对 KV cache 以写为主：一次性并行处理全部输入 token，把各层 key/value 写入 cache，一次算很多 token，计算密集，因此追求吞吐。decode 以读为主：每步只处理 1 个新 token，为它追加 1 份 key/value，其余前缀全靠读 cache；每步都很短，但每步时长直接决定出字速度，因此对延迟敏感。

    两个阶段脾气完全不同：一个一次算一大片，一个一次算一丁点但要算很多步。那么"这个服务快不快"该怎么量？一个数字够吗？

    6. 服务好不好怎么量：TTFT、TPOT、SLO 与 goodput

    上一章的两个阶段各贡献一段等待，于是 LLM 服务的延迟天然拆成两个指标[C11]：

    • TTFT（time to first token，首 token 延迟）：从发出请求到看到第一个字，约等于 prefill 阶段的时长（教学补充：线上服务里还包含排队等待）。
    • TPOT（time per output token）：除首 token 外，平均每个输出 token 的生成时间，反映 decode 阶段的速度。

    总延迟 = TTFT + TPOT × decode 阶段生成的 token 数（即不含首 token）。为什么要拆成两个？因为不同应用对两者的要求完全不同[C12]：实时聊天重 TTFT——没人愿意对着转圈等半分钟，而 TPOT 只要快过人的阅读速度（约 250 词/分钟）就够用；批量生成长文档则相反——首 token 等 1 秒还是 2 秒无所谓，TPOT 决定整篇要等多久。

    构造示例。 某请求 prefill 花了 0.3 s，之后 decode 阶段生成 5 个 token（不含首 token），每步 0.05 s（构造数字）。那么 TTFT = 0.3 s；TPOT = $(0.05\times 5)/5 = 0.05$ s；总延迟 = $0.3 + 5\times 0.05 = 0.55$ s。

    服务方对这两个指标分别承诺上限，并要求一定比例的请求达标——这叫 SLO（服务级别目标），达标请求占比的下限叫达成率（比如 90% 的请求满足 TTFT 与 TPOT 上限）。

    最后是衡量系统容量的主指标：goodput（有效吞吐）= 在满足 SLO 达成率的前提下，系统每秒最多能承接多少请求[C12]。注意它不是"尽量快"：请求越挤，排队越久，超 SLO 的请求越多。goodput 问的是"在不让达成率破防的前提下，还能再加多少请求"。构造示例。 若实测 4 req/s 时 95% 的请求达标、8 req/s 时只剩 80% 达标（构造数字），那么 goodput 落在 4 与 8 之间，需要找到仍满足 90% 达成率的最大速率。

    指标量的是什么由哪个阶段主导常见误区
    TTFT首 token 延迟prefill把它当成全部延迟，忽略后续生成
    TPOT平均每输出 token 时间decode用"总延迟/总 token 数"混算，掩盖首 token
    goodput满足 SLO 达成率的最大请求率两阶段共同与裸吞吐混淆——不顾延迟达标的每秒请求数再高也不算 goodput

    这组指标不是纸面定义，它直接驱动系统设计：以 goodput 为目标、把 prefill 和 decode 分开部署的 DistServe 系统，能比当时最优系统多服务最多 7.4 倍请求，或把 SLO 收紧 12.6 倍（>90% 请求达标）[N6]。

    本章问题

    1. 给定 prefill 0.5 s、decode 阶段生成 4 个 token（不含首 token）各 0.1 s 的时间线，算出 TTFT、TPOT 与总延迟。

      解答：0.5 s、0.1 s、0.9 s

      TTFT 等于 prefill 时长 0.5 s；TPOT 为除首 token 外平均每个输出 token 的生成时间，即 0.1 s；总延迟 $=0.5+4\times 0.1=0.9$ s，其中 4 是 decode 阶段生成的不含首 token 的 token 数。

    2. 用一句话说清 goodput 与裸吞吐量的区别。

      解答：以 SLO 达成率为前提

      goodput 是在满足 SLO 达成率（如 90% 请求达标）的前提下系统每秒最多能承接的请求数；裸吞吐量不计延迟是否达标——不顾达标的请求数再高也不算 goodput。

    3. 解释为什么实时聊天应用更在意 TTFT 而不是 TPOT。

      解答：首字决定等待感，出字快过阅读即可

      聊天的体验痛点是发出消息后对着转圈等待，这段等待由 TTFT 决定；而 TPOT 只要快过人的阅读速度（约 250 词/分钟）就基本无感。因此实时聊天对 TTFT 要求严格，对 TPOT 的容忍度相对高。

    两个指标由两个脾气不同的阶段贡献：TTFT 看 prefill，TPOT 看 decode。部署时，把这两个阶段放在同一批 GPU 上，还是分开？

    7. 放一起还是分开：PD 合设与 PD 分离

    两条主流路线[C13, C14]：

    PD 合设（colocation）：prefill 和 decode 跑在同一批 GPU、同一份模型权重上。好处是省显存、prefill 建好的 KV cache 就地可用。代价是互相干扰：一个 prefill 步往往比一个 decode 步长得多，排在一起时 decode 步被拖慢、TPOT 变差；decode 步挤进来也抬高 TTFT。两个阶段抢同一份资源，调度上偏向哪边都伤另一边。

    PD 分离（PDD，prefill-decode disaggregation）：prefill 和 decode 各自用一组 GPU 实例。干扰消失，两个阶段可以按各自目标独立配置资源与并行方式（prefill 求吞吐、decode 求延迟）。代价有三：第一，每个实例都要存一份完整模型副本——对 MoE 模型，权重的大头是专家，副本很贵；第二，prefill 产出的 KV cache 要跨实例传给 decode；第三，两阶段的容量要按配比成组供给，最小供给单位是一整个"部署单元"。这里有两组容易混用的数字，口径不同：第 3 章那个 18 节点 144 张 GPU（EP144）是 DeepSeek 在线推理系统实际运行的实例规模；DeepSeek-V3 技术报告给出的最小部署单元是 32 张 prefill GPU 加 320 张 decode GPU（decode 侧 40 节点 320 卡，EP320）[N4, N5]。不是对半分：配比由两阶段负载的不对称决定。这条路线的一个完整实例是 Mooncake：它把全集群闲置的 CPU/DRAM/SSD 组织成全局 KVCache 池，再由 Conductor 按缓存复用与负载同时最优来路由请求（转述自该论文，arXiv:2407.00079）。

    对比项PD 合设（colocation）PD 分离（PDD）
    模型权重份数一份每个实例一份完整副本
    跨阶段干扰有：长 prefill 步拖慢 decode，反之亦然无：物理隔离
    KV cache 传输不需要prefill → decode 跨实例传输
    资源配置两阶段共享，无法各自定制各自定制，但按部署单元（如 32P+320D）成组扩缩

    两条路线各自的深层局限——分离的副本太贵、部署单元太粗，合设的干扰难消、GPU 内部切分太死——以及一种更细的混合架构，正是论文 ExpertPlex 要解决的问题；其解析页将从本页的概念出发。该页见 ExpertPlex——它跨阶段共享同一份 MoE 专家，attention 按阶段各自独占整卡。

    本章问题

    1. 说出 PDD 用哪三样代价换来了"无干扰"和"各自定制"。

      解答：副本、传输、成组供给

      其一，prefill 与 decode 的每个实例都要存一份完整模型副本，对 MoE 模型尤其贵（权重的大头是专家）；其二，prefill 产出的 KV cache 要跨实例传给 decode；其三，两阶段的容量要按配比成组供给，最小单位是一整个部署单元（DeepSeek-V3 技术报告给出的最小部署单元为 32 张 prefill GPU 加 320 张 decode GPU）。

    2. 解释为什么 PDD 的 P:D 配比不是 1:1，并举出 DeepSeek-V3 的部署单元数字。

      解答：负载不对称决定配比

      prefill 计算密集、decode 显存与带宽密集，两阶段负载天然不对称，所需资源量不同；对半分会造成一边闲置一边拥挤，因此配比由负载结构决定。DeepSeek-V3 技术报告给出的最小部署单元是 32 张 prefill GPU 加 320 张 decode GPU（1:10）。

    3. 说明合设省下的两样东西是什么。

      解答：一份权重与零跨阶段传输

      PD 合设下两阶段共用同一批 GPU 与同一份模型权重，省下的是"每实例一份完整副本"的显存开销；且 prefill 建好的 KV cache 就地可供 decode 使用，省下跨实例传输。代价是两阶段在同一份资源上互相干扰。

    辅助解释与类比边界

    "FFN 是存知识的大头"仅以参数占比（2/3）为依据，不断言知识具体存在哪里。key/value 的"检索标签/信息内容"表述只解释为什么它们可以被缓存复用，不解释 attention 内部机制（超出本页范围）。"气泡"指通信期间算力闲置，不特指流水线并行中的 pipeline bubble。

    简化条件及其限制

    （1）attention 内部 Q/K/V 打分、多头结构未展开，只保留"跨 token 汇信息、产出 key/value"这一功能描述；KV cache 的 E3 只数 K/V 投影计算，实际朴素重算的浪费还包括 attention 打分与全部层计算，因此 15 对 6 是浪费的下界而非全部。（2）router 归一化写法（选中专家得分归一化）是多种实现之一；DeepSeek-V3 用 sigmoid + 偏置，Switch 用 softmax top-1，结构共性是"只算选中的 k 个、加权和输出"。（3）TBO/SBO 时间线为示意图，不反映真实 kernel 调度（见《GPU 执行模型》）。（4）本页所有数字以 DeepSeek-V3 系模型为准；其他 MoE 模型（如 Mixtral 8 专家 top-2）层数、专家数、k 值不同，机制描述仍成立。（5）GPU/显存只用"并行矩阵运算芯片、显存有限"的最小表述，SM、kernel、CUDA Graph 等执行细节不在本页范围。
