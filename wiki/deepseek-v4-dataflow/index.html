DeepSeek-V4-Pro 前向数据流

DeepSeek-V4-Pro 是 1.6T 参数、每 token 激活 49B 的 MoE 模型：61 层主干里两种注意力逐层交替——奇数层 HCA 把每 128 个 token 的 KV 压成一条、偶数层 CSA 把每 4 个 token 压成一条再由 Lightning Indexer 选出 1024 条；两者都只有一个 KV 头（MQA）、都并联 128 长度的滑动窗口。残差不再是单条通路，而是 mHC 维护的 4 份并行残差流，用 Sinkhorn 归一化的混合矩阵在层间重分配。FFN 全为 DeepSeekMoE（384 路由专家 top-6 + 1 共享专家），其中前 3 层改用 token ID 查表的 Hash 路由。上下文 1M。

生成于 2026-08-12 · 依据官方 inference 源码 + config.json + 真实 checkpoint 张量头 + 本机实测

要点

整体结构：两种注意力逐层交替 + 四份残差流

  • 沿序列：61 层里 HCA（compress_ratio=128）与 CSA（compress_ratio=4）交替。compress_ratios 前 12 项为 [128,128,4,128,4,128,4,128,4,128,4,128]——第 0、1 层连续两层 HCA，此后严格奇偶交替，最终 HCA 31 层、CSA 30 层。只有 CSA 层带 Indexer，checkpoint 中恰好 30 层含 attn.indexer.*。
  • 压缩不是池化：每个压缩条目是 wgate 从隐藏状态算出的 softmax 权重对 wkv 结果的加权和，再加可学习位置偏置 ape。实测将其与均值池化对比，相对差异 0.76，确认权重是数据相关的。
  • 沿深度：mHC 把残差流从 1 份扩成 4 份。每个 Block 内 hc_pre/hc_post 各调用两次（attn 前后、ffn 前后）：hc_pre 把 4 份加权归约成 1 份送进子层，hc_post 把子层输出扩回 4 份并叠加经混合矩阵重排的旧残差。子层内部维度不受残差份数影响。
  • 沿宽度：每层 384 个路由专家取 top-6，另有 1 个共享专家恒激活。路由专家占总参数 96.8%（1.547T / 1.599T），但每 token 只激活 6/384。

CSA（Compressed Sparse Attention，30 层）

  • 压缩率 4 且启用重叠：Compressor 中 self.overlap = compress_ratio == 4，使 wkv/wgate 输出宽度翻倍（真实权重 layers.2.attn.compressor.wkv.weight 形状 [1024, 7168]，正好是 HCA 层 [512, 7168] 的两倍）。
  • 重叠的含义：每个压缩条目由 2m=8 个原始条目产生，softmax 在 8 个元素上归一化（实测归一化宽度=8）；但相邻条目复用彼此的一半来源，因此序列长度仍只压到 1/4，而非 1/8。
  • Lightning Indexer 自带一套独立的压缩器（index_head_dim=128，带 Hadamard 旋转 + FP4 量化模拟）。索引分数为 $I_{t,s}=\sum_h w_{t,h}\,\mathrm{ReLU}(q^I_{t,h}\cdot K^{\mathrm{IComp}}_s)$——注意是先 ReLU 再按头加权求和，不是 softmax。
  • Indexer 的 query 与主注意力的 query 共享同一个低秩潜向量 qr（q_norm(wq_a(x))），只是各自用不同的 wq_b 上投影。

HCA（Heavily Compressed Attention，31 层）

  • 压缩率 128、不重叠，softmax 在 128 个元素上归一化（实测归一化宽度=128）。无 Indexer，也无稀疏选择——所有压缩条目全部参与注意力。
  • 正是因为压得足够狠，才可以不做稀疏化：1M 上下文下每层只有 8192 个压缩条目，与滑窗 128 合计 8320，规模已经可控。
  • YaRN 只在带压缩的层生效。model.py 中若 compress_ratio 为 0 则用 rope_theta=10000 且关闭 YaRN；带压缩的层用 compress_rope_theta=160000。压缩条目的位置索引是压缩后的块号，跨度被压掉，因此需要单独的 theta。

两种层共有的四个细节

  • 滑窗与压缩条目同处一个 softmax：model.py 把窗口索引与压缩索引 cat 成一个 topk_idxs 再调用一次 sparse_attn。即两条分支不是各算一次注意力再融合，而是共享同一个归一化分母。实测把压缩索引拼进去后输出变化 1.57，确认其参与同一归一化。
  • Attention sink：每头一个可学习标量，$\mathrm{Exp}(z'_h)$ 直接加进 softmax 分母。实测 sink 取 5 时注意力权重之和降到 0.26，即该头可以选择几乎不看任何 KV。
  • 输出侧反向 RoPE：KV 条目同时充当 key 和 value，输出因此携带绝对位置相位；apply_rotary_emb(o, freqs, inverse=True) 用共轭旋转把它转回相对位置。实测正向再反向的误差为 2.4e-7，是精确逆变换。
  • 分组输出投影：128 头 × 512 维 = 65536 维直接投回 7168 代价过高，故按 o_groups=16 分组，每组先降到 o_lora_rank=1024（wo_a [16384, 4096]）再合并投回（wo_b [7168, 16384]）。

mHC（Manifold-Constrained Hyper-Connections）

  • 每层的混合参数由当前残差流算出，不是静态权重：把 4 份残差拼成 28672 维，经 hc_attn_fn（真实形状 [24, 28672]）投到 24 维，再切成 pre(4) / post(4) / comb(16) 三段。
  • pre 为 $\sigma(\cdot)+\varepsilon$，post 为 $2\sigma(\cdot)$，comb 经 Sinkhorn 迭代投影后作为 4×4 残差混合矩阵。
  • 实测发现：官方 kernel 的迭代顺序是「softmax(-1) → 列归一化 → 19 轮（行归一化 → 列归一化）」，最后一步是列归一化，因此列和精确为 1、行和只是近似。收敛速度强烈依赖 comb logits 的尺度：尺度 ≤0.1 时 20 轮远超所需、行列和都精确为 1；尺度为 3 时 20 轮后行和最大仍偏离 3.5e-2，需约 231 轮才降到 1e-3。hc_sinkhorn_iters=20 是与「门控参数初始化较小、矩阵接近均匀」相匹配的取值，而非在任意输入下都严格双随机。
  • 双随机约束的作用是让残差混合成为压缩映射：实测双随机 comb 混合后 L2 范数比值 0.83；若只做行归一化，列和会散到 [0, 2.62]，某些残差通道被反复放大。
  • 代价很小：每层 mHC 参数约 1.38M，61 层合计 0.084B，占总参数 0.005%。

MoE 路由

  • 评分函数从 V3 的 sigmoid 换成 sqrt(softplus)。实测差异集中在高分区：logit=12 时 sigmoid 已饱和到 0.999994，sqrt(softplus) 仍在按 $\sqrt{z}$ 增长到 3.46。含义是高置信路由之间的亲和度差异不会被压平。
  • bias 只参与选择、不进权重：scores + bias 用于 topk，而权重从未加 bias 的 original_scores 里 gather。实测把专家 0 的 bias 抬到 5 后它被挤进 top-6，但拿到的权重仍基于原始分数 0.73。这是 auxiliary-loss-free 均衡的关键——调节被选频率而不扭曲输出系数。
  • 前 3 层是 Hash 路由：indices = self.tid2eid[input_ids]，专家由 token ID 查表决定，与该层隐藏状态完全无关。真实 checkpoint 中 gate.tid2eid 恰好只出现在第 0、1、2 层（形状 [129280, 6]），且这 3 层没有 gate.bias（61 层中 58 层有 bias，缺的正是 0、1、2）——两处证据互相印证。
  • 专家精度分层：路由专家为 FP4（张量头显示 I8 [3072, 3584]，即沿 K 维两值打包，配 scale F8_E8M0 [3072, 224]），而共享专家是 FP8 [3072, 7168] 未降到 FP4。

长上下文效率的来源

注意力开销由每 token 的候选集规模决定。按官方配置实算：

上下文CSA 层候选集HCA 层候选集
4K128 + 1024 = 1152128 + 32 = 160
64K128 + 1024 = 1152128 + 512 = 640
1M128 + 1024 = 1152128 + 8192 = 8320

CSA 层在上下文超过 4096（= index_topk × 4）后候选集被 topk 钉死在 1152，完全与长度脱钩；HCA 层随长度线性增长但斜率只有 1/128。两者叠加即报告所称 1M 下单 token 推理 FLOPs 仅为 V3.2 的 27%。

KV cache 侧：每条目 64 维 BF16（RoPE）+ 448 维 FP8 = 576 字节，为纯 BF16 的 56.2%（报告称「近一半」）。1M 上下文下主注意力 KV cache 合计 4.36 GiB，相对报告基线 BF16 GQA8（head_dim=128，244 GiB）为 1.79%，独立复现了报告「约 2%」的结论。Indexer 另需 1.88 GiB（30 个 CSA 层各 262144 条目 × 128 维），未计入该口径。

本机实测与核对

官方 inference/kernel.py 用 tilelang 编写，只能在 NVIDIA GPU 上编译。为在本机验证，按其逐行语义用纯 PyTorch 等价复现了 act_quant、fp4_act_quant、sparse_attn、hc_split_sinkhorn，随后直接 import 官方 inference/model.py——架构代码一行未改，仅替换这几个算子，因此跑出的路径就是官方实现的路径。

缩小配置（4~6 层、dim 256、结构与官方同构：HCA/CSA 交替、含 Hash 层、含重叠压缩、含 Indexer、hc_mult=4）下 prefill 与逐 token decode 均跑通，logits 无 NaN/Inf。forward hook 抓到的候选集与手算完全一致：
