Chunked Prefill（分块预填充）

把长 prefill 切成等计算量的块逐块执行，配合 decode 搭车与 stall-free 调度，消除长 prompt 进入时同批 decode 停摆数秒的问题。

更新于 2026-08-19

问题背景

LLM 推理的 prefill 迭代是 compute-bound（LLaMA-13B 在 A6000 上一个 512 token 请求即可饱和单卡算力[1]），decode 迭代是 memory-bound（小批量下每 token 成本可达 prefill 的约 200 倍[2]）。连续批处理把两者混在同一次迭代里，调度器若优先算完新到的长 prompt，进行中的 decode 在整个长 prefill 期间不产出 token——token 间隔从毫秒级跳到秒级（generation stall）。

[1] Sarathi §1：on an A6000 GPU, for the LLaMA13B model, a prefill with a sequence length of 512 tokens saturates GPU compute even at a batch size of just one。[2] Sarathi §1：at small batch sizes, the decode cost per token can be as high as ~200 times the prefill cost per token。

核心机制

  • 切块：把一个 prefill 请求切成近似等计算量的块，逐块执行。块间只靠 KV cache 衔接（后续块的 attention 读前面所有块的 K/V），不传递层输出；切成 $N$ 块时第一块的 KV 被重复读 $N-1$ 次，共 $\frac{N(N-1)}{2}$ 次额外块级读取。
  • 搭车（piggybacking）：一个批次 = 一个 prefill chunk + 尽量多的 decode。权重读一次同时服务两者，搭车 decode 的成本比纯 decode 批最多低一个数量级（前提：chunk 够大以饱和算力）。
  • stall-free 调度：token budget 限制每次迭代的 token 总量，新请求以 chunk 加入当前批次、从不暂停进行中的 decode——迭代时长有上界，token 间隔平稳。
  • CPP：与流水线并行组合，等大的块使各 micro-batch 时长均匀，顺带消掉流水线气泡（Sarathi 在 GPT-3 上气泡缩小 6.29 倍）。

关键结论与边界

  • chunked prefill 不加速单请求 prefill（总计算量不变、访存微升），改善的是延迟结构与批均衡。
  • chunk 越小 token 间隔越稳，但 KV 重复读按平方量级增长、算术强度与固定开销摊薄变差；chunk 257 比 256 的 prefill 时间高 32%（tile 量化），取值须对齐并满足 TBT SLO。
  • 收益依赖场景：MLA 架构在 chunked piggyback 下有重复投影开销；它是 co-located 部署的优化，与 PD 分离是两条路线——什么条件下走哪条，见 完整说明页末尾链接的 Beyond the Buzz 论文。
