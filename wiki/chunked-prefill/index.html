    Chunked Prefill（分块预填充）：让长 prompt 不再卡住 decode

    主要依据：SARATHI（Agrawal et al., 2023, arXiv:2308.16369，chunked prefill 与 piggybacking）；Sarathi-Serve（Agrawal et al., 2024, arXiv:2403.02310，stall-free 调度与 token budget）；Beyond the Buzz（Mitra et al., 2025, arXiv:2506.05508，CPP 在 prefill 池的应用）。

    一位用户正在逐字看着模型输出——以几十毫秒的间隔蹦一个 token（示意值），阅读体验流畅。此刻另一位用户提交了一个 8000 token 的长 prompt。如果调度器决定"先把这段 prefill 算完再说"，第一位用户的输出会停顿数秒：整个长 prompt 的 prefill 计算期间，同卡上所有进行中的 decode 都不产出新 token[C9]。chunked prefill（分块预填充）针对这个问题把长 prefill 切成多个近似等大的块逐块计算，配合"decode 搭车"的批构造与"从不暂停"的调度，让长 prompt 的进入不再卡住任何人。

    本文的学习目标包括：解释长 prefill 为什么卡住同批 decode（generation stall）；说明切块规则与块间依赖（KV cache 累积、不传层输出）；解释 decode 搭车为什么近乎免费、stall-free 调度怎么保证迭代时长有上界；给出 chunk 大小的权衡清单；说明 chunked prefill 与流水线并行组合（CPP）为什么顺带消掉气泡。前置概念：prefill/decode 两阶段与 KV cache 见 MoE Serving，注意力的因果掩码见 因果掩码，memory-bound 与 compute-bound 见 GPU 执行模型，流水线气泡见 模型并行。

    核心问题

    1. 为什么一个长 prefill 会拖慢同机所有进行中的 decode（generation stall）？

      解答：连续批处理混批迭代，prefill 迭代时长被上千 token 主导

      连续批处理中 prefill 与 decode 混在同一次迭代里执行。prefill 并行处理全部输入 token、是 compute-bound，一个 512 token 的请求即可饱和单卡算力；decode 每次迭代每请求只处理一个 token、是 memory-bound，小批量下每 token 成本可达 prefill 的约 200 倍。若调度器优先完成 prefill（vLLM 类做法），进行中的 decode 在整个长 prefill 迭代期间不产出 token，token 间隔被拉长到秒级（实测可持续数秒）。完整论证见第 1 章。

    2. chunked prefill 怎么切块？块与块之间靠什么衔接、不靠什么？

      解答：按等计算量切块，块间只靠 KV cache 衔接

      把一个 prefill 请求切成近似等计算量的块，逐块过全部层。块与块之间唯一的依赖是 attention：每个后续块的 attention 必须读取同一 prompt 前面所有块产生的 KV cache（切成 $N$ 块时第一块的 KV 被重复读 $N-1$ 次）。块之间不传递层输出——prefill 各 token 位置的输出互相独立，每块独立过全部层，FFN 总计算量不变。完整论证见第 2 章。

    3. 为什么 decode 搭 prefill 块的车近乎免费？stall-free 调度怎么保证 decode 不被卡？

      解答：权重读一次服务两者；token budget 限制每次迭代时长

      decode 是 memory-bound：每次迭代的主要时间花在从显存读模型权重上。一个 prefill chunk 与多个 decode 同批时，权重只需读一次就同时服务两者，搭车 decode 的成本比纯 decode 批最多低一个数量级（不是零）。stall-free 调度用 token budget 限制每次迭代允许的 token 总量：新请求以 chunk 形式加入当前批次、从不暂停进行中的 decode，每次迭代时长因此有上界，token 间隔不再有秒级尖刺。完整论证见第 3 章。

    4. chunk 大小（token budget）怎么选？选小了有什么代价？

      解答：TBT 更稳 vs 三项开销上升的权衡

      chunk 越小、每次迭代越短、token 间隔（time-between-tokens, TBT，与 TPOT/TTL 同义）越平稳，但三项代价随块数上升：KV cache 重复读次数按 $\frac{N(N-1)}{2}$ 增长（$N$ 为块数）；算术强度下降导致 GPU 利用率降低；kernel 启动等固定开销摊薄变差。此外 chunk 需对齐 GPU tile（chunk 257 比 256 的 prefill 时间高 32% 的实例），且必须够大以饱和算力（搭车"免费"的论证前提）。工程上由 TBT SLO 与开销的一次性 profiling 决定。完整论证见第 4 章。

    5. chunked prefill 与流水线并行组合（CPP）为什么能同时消掉流水线气泡？

      解答：等计算量切块使 micro-batch 时长均匀，流水线被填满

      PP 气泡的来源之一是各 micro-batch 计算时长不均（FTL = First Token Latency，首 token 延迟）。chunked prefill 把长 prefill 切成等计算量的块，每个块作为 micro-batch 进流水线，各 slot 时长均匀，填充期与排空期之外的空转被显著压缩——Sarathi 在 GPT-3 流水线部署上气泡缩小 6.29 倍、端到端吞吐提升 1.91 倍。Beyond the Buzz 论文中 CPP 是 prefill 池在严格 FTL 约束下兼顾高吞吐的最优策略。完整论证见第 5 章。

    1. 长 prefill 为什么卡住所有人

    先建立两类迭代的负载画像。prefill 迭代并行处理输入的全部 token：一次 8000 token 的 prefill 是一个巨大的矩阵乘，算力直接打满——Sarathi 的实测显示 LLaMA-13B 在 A6000 上一个 512 token 的 prefill 请求（批大小仅为 1）即可饱和 GPU 算力[C3, N2]。decode 迭代相反：每个请求每次只处理一个 token（上一个迭代自己生成的），计算量极小，时间几乎全花在从显存读模型权重上——memory-bound。小批量下 decode 的每 token 成本可达 prefill 的约 200 倍[C2, N1]。两类迭代的详细对比见下表：

    维度prefill 迭代decode 迭代
    每次迭代处理的 token输入序列全部（可上千）每请求 1 个
    瓶颈类型compute-bound（算力饱和[C1, C3]）memory-bound（权重读取主导）
    小批量利用率单请求即可饱和（512 token / A6000 / LLaMA-13B[N2]）很低，靠大批量摊薄权重读取
    迭代时长量级长（随 token 数增长）短（毫秒级）

    现在看 stall 怎么发生。连续批处理（continuous batching，Orca 提出的迭代级调度：每次迭代可加入新请求、移除完成请求）把 prefill 与 decode 混在同一个批里迭代。Sarathi-Serve 观察到：prefill 优先的调度器（如 vLLM 的做法——新请求的 prefill 被尽快执行）会让一次迭代装进整个长 prompt，这次迭代因为上千 token 的计算量而持续很久；期间同批所有进行中的 decode 一个 token 都不产出[C9]。对正在看输出的用户来说，token 间隔从毫秒级跳到秒级——Sarathi-Serve 在 vLLM 上实测到持续数秒的 generation stall[C9]。

    本章问题

    1. prefill 与 decode 的迭代时长为什么差几个数量级？

      解答：compute-bound vs memory-bound，token 数差三个数量级

      prefill 迭代处理输入序列的全部 token（可上千），大矩阵乘把算力打满，属 compute-bound；decode 迭代每请求只处理 1 个 token，计算量极小、时间由权重读取主导，属 memory-bound[C1]。Sarathi 的量化：LLaMA-13B/A6000 上 512 token 的单个 prefill 请求即饱和算力[C3, N2]；小批量下 decode 每 token 成本约为 prefill 的 200 倍[C2, N1]。数量级差异来自"每次迭代处理的 token 数"（全部 vs 单个）与"瓶颈类型"（算力 vs 访存）的叠加。

    2. 为什么"先把长 prefill 算完"不是一个合理的调度选择？

      解答：一次迭代装下整个 prompt，同批 decode 全程停摆

      连续批处理里同一批的请求一起迭代。调度器若优先执行新请求的完整 prefill（vLLM 类做法），这一次迭代就要算完整个长 prompt（数千 token），迭代时长被拉长到远超正常 decode 迭代；期间批内所有进行中的 decode 请求不产出任何 token，它们的用户看到输出停顿——Sarathi-Serve 实测这种停顿可持续数秒[C9]。TBT（相邻 token 间隔）SLO 因此被系统性违反。这不是实现缺陷而是调度策略的结构性代价：不切分 prefill，"尽快开始算"与"不让别人等"就不可兼得。

    2. 把长 prefill 切成块：机制与代价

    chunked prefill 的核心动作：把一个 prefill 请求切成近似等计算量的块（chunk），每块包含固定数量的输入 token，逐块执行[C4]。8000 token 的 prompt 按 512 一块切成 16 块后，单次迭代最多装一块——迭代时长从"整个 prompt"降到"一个块"，第 1 章的 stall 结构被拆掉了（数字为构造示例的整数化设定）。

    2.1 块间依赖：只靠 KV cache 衔接

    块与块之间怎么衔接？关键观察是 attention 的因果结构（见因果掩码）：prompt 内每个 token 的 attention 只看它之前的 token。把 prompt 切成块后，第 $k$ 块的 token 在做 attention 时，需要前面第 1 到 $k-1$ 块所有 token 的 K/V——这些 K/V 已经由前序块算出并缓存在 KV cache 里。所以块间传递的数据是累积的 KV cache：每块进入计算前，前面块的 KV 已经就位[C5]。

    不传递的是层输出。prefill 阶段每个 token 位置在各层的前向输出（最终的 logits 与各层的 K/V）只依赖它自己与之前的 token，不依赖同 prompt 其他位置的输出——这是因果掩码的直接推论（基于证据的推断：由因果注意力结构与 Sarathi 的块数据流图推出）[C6]。因此每块独立过全部层，块之间不需要等待对方的层输出，第 2 块不必等第 1 块"过完最后一层"才能开始过第一层——只需要第 1 块的 KV 就位。

    2.2 切块的三个代价

    切块不是免费的，代价随块数 $N$ 上升：

    • KV cache 重复读。第 $k$ 块的 attention 要读前面所有块的 KV，所以第 1 块的 KV 被读 $N-1$ 次、第 2 块被读 $N-2$ 次……额外读取总次数为[C5]

      $$\sum_{i=1}^{N}(N-i) = \frac{N(N-1)}{2}\ \text{次块级读取}.$$

      • $N$：一个 prompt 被切成的块数；$i$：块序号（第 $i$ 块的 KV 被后续块读 $N-i$ 次）。

      计算量本身不变（FFN 对每块独立计算、总量与不切时相同[C5]），变的是访存量。Sarathi-Serve 同时指出：即便切得很细，attention prefill 仍是 compute-bound 操作，这项开销在实践中可容忍[C5]。

    • 算术强度下降。chunk 越小，每块的矩阵越小，每字节访存对应的计算量越低，GPU 利用率下降[C13]。
    • 固定开销摊薄变差。kernel 启动等固定开销按迭代次数重复，块越多迭代越多、每次迭代越短，固定开销占比上升[C13]。

    此外还有 tile 量化效应：GPU 把矩阵乘切成固定尺寸的 tile 分给线程块，矩阵维度不对齐 tile 尺寸时部分线程块做无用计算。Sarathi-Serve 给出一个量级：chunk 取 257 比 256 的 prefill 计算时间高 32%——只差 1 个 token[C12, N3]。chunk 大小应该对齐到 tile 友好的 2 的幂。

    构造示例：把 4096 token 的 prompt 切成 8 块（每块 512），额外 KV 读取为 $\frac{8\times 7}{2} = 28$ 块次；切成 4 块（每块 1024）则为 $\frac{4\times 3}{2} = 6$ 块次。块数翻倍，重复读次数按 $N^2$ 量级增长（块数翻倍，重复读约 4 倍）——这是"块不能切太细"的第一性来源。

    本章问题

    1. 块之间传递层输出吗？为什么？

      解答：不传递；块间唯一依赖是 KV cache

      不传递。prefill 阶段每个 token 位置的各层输出只依赖它自己和之前的 token（因果掩码的结构），同 prompt 不同位置的输出互相独立，所以第 2 块不需要第 1 块的任何层输出。第 2 块唯一需要的是第 1 块算出的 K/V——第 2 块的 attention 要对第 1 块的 token 做 attention[C5]。因此块间数据流是"KV cache 累积"而不是"层输出接力"：每块独立过全部层，进入前只需前序块的 KV 就位。（后半句"输出互相独立"为由因果结构推出的推断，前半句"attention 读前序块 KV"为 Sarathi-Serve 明确陈述[C5]。）

    2. 把 4096 token 切成 8 块和 4 块，额外 KV 读取分别多少？说明什么趋势？

      解答：28 次与 6 次；块数增长使重复读按平方量级增长

      按"第 $i$ 块的 KV 被读 $N-i$ 次"计数[C5, F1]：$N=8$ 时 $\frac{8\times 7}{2} = 28$ 块次；$N=4$ 时 $\frac{4\times 3}{2} = 6$ 块次。块数翻倍，额外读取从 6 涨到 28（约 4.7 倍），按 $N^2$ 量级增长。趋势：切块越细，KV 重复访存的开销越突出；同时 Sarathi-Serve 指出 attention prefill 本身 compute-bound，实践中该开销可容忍[C5]——所以它只是权衡清单的一项，不是切块的否决项。数字为构造示例（整数化设定）。

    3. 为什么 chunk 取 257 反而比 256 慢？

      解答：tile 量化——维度不对齐 tile 时线程块做多余计算

      GPU 执行矩阵乘时把矩阵切成固定尺寸的 tile 分配给线程块，每个线程块做等量的算术；矩阵维度不是 tile 尺寸整数倍时，最后一个不完整的 tile 也要占用一个完整线程块，其中大部分计算是多余的（tile 量化效应）。Sarathi-Serve 实测 chunk 257 比 256 的 prefill 计算时间高 32%[C12, N3]——多 1 个 token 触发一整列多余的 tile。工程含义：chunk 大小要取 tile 友好的值（如 2 的幂），而不是"随便一个够小的数"。该数字来自特定 GPU 与 kernel 的实例，量级在其他硬件上可能不同。

    3. decode 搭车与不停止的调度

    切块解决"长 prefill 卡人"，还差一半：被切出来的块本身仍是 compute-bound 的迭代，而同卡的 decode 依旧 memory-bound——能不能让它们同批执行、各取所需？这就是 piggybacking（搭车）。

    3.1 piggybacking：一个批次，两种负载

    Sarathi 的 decode-maximal batching 构造一个混合批次：装一个 prefill chunk，剩余槽位全部填 decode[C7]。为什么 decode 搭车近乎免费？因为一次迭代里模型权重只需从显存读一遍：prefill chunk 的巨大矩阵乘正在把算力用满，同批的 decode 请求顺带用同一份权重算自己的小矩阵乘——decode 的边际成本只剩它自己的少量计算与激活访存。Sarathi 的实测：搭车 decode 的成本比纯 decode 批最多低一个数量级[C7]。

    注意"最多低一个数量级"不是零：搭车 decode 仍占批容量与少量计算，说"完全免费"是错的[C7]。这个论证的前提是 chunk 够大以饱和算力——512 token 在 A6000/LLaMA-13B 上就够[C3, N2]，chunk 远小于饱和点时"免费"程度弱化。

    chunked prefill 与 piggybacking 是相互成就的：一个 prefill 只有一次，但切成 $N$ 块就有 $N$ 个搭车机会。不切块时，批里要么是纯 prefill（decode 停摆）、要么是纯 decode（算力闲置）；切块后每个 chunk 迭代都能带上 decode[C8]。

    3.2 stall-free：token budget 上界

    有了混合批次还不够——如果调度器一次塞进太多 chunk，迭代照样超长。Sarathi-Serve 的 stall-free 调度给每次迭代加一个 token budget（token 预算）$\tau$：一次迭代中所有请求的 token 总数（prefill chunk 的 token + 各 decode 的 token）不超过 $\tau$[C10]。新请求到达时，以 chunk 形式加入当前迭代（用剩余预算装下它的第一块或若干块），进行中的 decode 从不暂停[C10]。效果：每次迭代的计算量有上界，迭代时长有上界，token 间隔不再出现秒级尖刺——stall 消失。

    构造示例：批容量按 token 计 512（$\tau = 512$），当前有 64 个进行中的 decode，一个 8000 token 的新请求到达。本次迭代装：64 个 decode token + 1 个 448 token 的 prefill chunk（首块）；下一次迭代同样 64 + 448（第二块）……约 18 次迭代后 prefill 完成，期间 64 个 decode 每次迭代都产出 token。对照不切分的情形：一次迭代装 8000 token，64 个 decode 停摆整个迭代时长。token 间隔从"秒级尖刺"变成"轻微抬升的平稳值"。

    本章问题

    1. 为什么搭车的 decode"近乎免费"？论证前提是什么？

      解答：权重读一次服务两者；前提是 chunk 饱和算力

      decode 迭代是 memory-bound：时间主要花在读模型权重。混合批次中权重只需读一遍，prefill chunk 的矩阵乘在占用算力的同时，decode 请求用同一份权重完成自己的计算，搭车 decode 的成本比纯 decode 批最多低一个数量级[C7]——不是零，它仍占批容量和少量计算。论证前提是 chunk 足够大以饱和算力：LLaMA-13B/A6000 上 512 token 即饱和[C3, N2]；若 chunk 远小于饱和点，prefill chunk 自己也不饱和算力，"搭车免费"的论证弱化。

    2. token budget 怎么同时做到"新请求立刻开始"与"旧请求不被卡"？

      解答：预算限制单次迭代 token 总量，新请求以 chunk 进、decode 不停

      token budget $\tau$ 规定单次迭代中所有 token（chunk 的 + decode 的）总数不超过 $\tau$[C10]。新请求到达时立刻以 chunk 形式进入当前迭代——"立刻开始"由切块保证（第一块不必等整个 prompt）；单次迭代的计算量被 $\tau$ 封顶——迭代时长有上界，进行中的 decode 每次迭代照常产出，"不被卡"由预算保证。两个性质合起来：新请求的进入只把 token 间隔轻微抬高（一次迭代多装了一个 chunk），不再产生秒级停顿。$\tau$ 的取值是第 4 章的权衡主题。

    4. 块要多大：token budget 的权衡

    第 2、3 章给出了 chunk 大小的两端约束，这一章把它们拼成完整的权衡清单：

    维度chunk 越小chunk 越大
    token 间隔（TBT）每次迭代更短，间隔更平稳[C11]迭代更长，间隔尖刺更大
    KV 重复读按 $\frac{N(N-1)}{2}$ 增长[F1]次数少
    GPU 利用率算术强度低，利用率下降[C13]接近饱和
    固定开销kernel 启动等摊薄差[C13]摊薄好
    tile 对齐与大小无关的两端要求：取 2 的幂这类 tile 友好值（257 vs 256 差 32%[C12]）
    搭车"免费"度低于饱和点时论证弱化饱和算力，搭车近乎免费[C3]

    工程决策方式：Sarathi-Serve 的做法是一次性 profiling——对不同的批 token 数测迭代时长，取满足 TBT SLO 的最大值作为 $\tau$[C11]。如果部署是流水线并行，$\tau$ 还要兼顾流水线气泡（见第 5 章）。

    本章问题

    1. 把 chunk 从 1024 改成 256，哪些量变好、哪些变差？

      解答：间隔变平稳；重复读、利用率、固定开销三项变差

      变好：每次迭代的 token 数从 1024 降到 256，迭代时长按比例缩短，进行中 decode 的 token 间隔更平稳、TBT 尾部更小[C11]。变差：同长度 prompt 的块数 $N$ 变为 4 倍，KV 重复读按 $\frac{N(N-1)}{2}$ 从 $N=4$ 时的 6 块次涨到 $N=16$ 时的 120 块次（精确比值 20 倍，按 $N^2$ 量级增长；prompt 长度 4096 的实例）[F1]；每块算术强度下降、GPU 利用率降低[C13]；迭代次数变 4 倍、kernel 启动等固定开销总占比上升[C13]。256 低于该实例饱和点 512[N2]，搭车"免费"论证在该硬件组合上弱化；说明这个取值在该硬件组合上已经偏小。正确做法是按 TBT SLO 与 profiling 定值，不是取"越小越好"。

    5. 与流水线并行合流：CPP

    前面几章都在单卡（或单实例）语境下讨论。当部署是流水线并行（PP）时，chunked prefill 顺带解决了另一个问题：流水线气泡。

    回顾模型并行页的气泡机制：PP 各 stage 串行依赖，气泡来自填充期与排空期的空转；而 Sarathi 的分析进一步指出，LLM 推理的流水线还有第二重气泡来源——各 micro-batch 的计算时长不均（不同请求的 prompt 长度差异大、prefill 与 decode 迭代耗时差异大），快的 micro-batch 被慢的卡住节奏。chunked prefill 把长 prefill 切成等计算量的块，每块作为一个 micro-batch 进流水线：所有 slot 的时长近乎一致，流水线被均匀地填满，双重气泡都被压缩[C14]。Sarathi 在 GPT-3 流水线部署上实测气泡缩小 6.29 倍、端到端吞吐提升 1.91 倍[C14, N4]。这个组合——chunked prefill + PP——就是 CPP（Chunked Pipeline Parallelism）。

    CPP 在 Beyond the Buzz 论文（PD 分离设计的系统性研究）中成为 prefill 池的标准答案：分离部署里 FTL（First Token Latency，首 token 延迟）约束只作用于 prefill 池，DeepSeek-R1 在 ISL（Input Sequence Length，输入序列长度）256K、64 GPU（EP（Expert Parallelism，专家并行）$\times$ PP = 64）的模拟中，增大 PP 维度持续降低 FTL 而吞吐基本保持——CPP 是严格 FTL SLA 下兼顾高吞吐的最优策略[C16]。同一论文还发现 co-located 基线里的 piggybacking 对注意力架构敏感：DeepSeek-R1 的 MLA（Multi-head Latent Attention，多头潜在注意力）在 chunked piggyback 下每个块都要重算 down/up 投影，产生额外开销（可临时缓存上投影 KV 缓解）[C17]——这是第 2 章"切块代价"在特定架构上的又一实例。完整讨论见 Beyond the Buzz 论文页。

    本章问题

    1. 为什么等大的块能消掉流水线气泡，而"不等大的原始请求"不能？

      解答：气泡的第二来源是 micro-batch 时长不均，等大块把它抹平

      PP 气泡有两个来源：一是结构性的填充期/排空期（见模型并行页，靠增大 micro-batch 数摊薄）；二是负载性的时长不均——不同请求的 prompt 长短不一、prefill 与 decode 迭代耗时差几个数量级，一个长 micro-batch 会让后面所有 stage 的节奏被拖住，短 micro-batch 让 stage 空等。chunked prefill 把一切长 prefill 切成等计算量的块，每个 slot 的耗时近乎一致，第二重气泡被消除，第一重也被均匀的 micro-batch 流压缩——Sarathi 实测 GPT-3 流水线部署气泡缩小 6.29 倍、吞吐提升 1.91 倍[C14, N4]。原始请求直接当 micro-batch 时长短不一，两重气泡都占。

    2. Beyond the Buzz 论文对 CPP 的结论是什么？

      解答：CPP 是 prefill 池在严格 FTL 下的最优策略

      在该论文的分离部署模拟中，FTL 约束只作用于 prefill（context）池；为在混合长度序列下压低 FTL 同时维持高吞吐，CPP 被发现尤其有效——DeepSeek-R1、ISL 256K、64 GPU（EP（Expert Parallelism，专家并行）$\times$ PP = 64）的设置里，随 PP 维度增大 FTL 持续降低而吞吐保持[C16]。机制与第 2、3 章一致：切块让长序列能在给定 FTL 内处理（每块小到一次迭代可完成），PP 让块在流水线中并行推进。该结论来自模拟器（论文的方法性质见其页面），适用条件是该模拟设置。

    6. 边界与相邻工作

    chunked prefill 改善的是延迟结构与批内负载均衡，不改善单请求的 prefill 速度：总计算量不变（FFN 不变）甚至微升（KV 重复读、固定开销）[C5, C13]。它的收益依赖场景：chunk 要够大以饱和算力（搭车论证的前提[C3]）；架构敏感性上 MLA 的重复投影开销[C17]、宽松延迟目标与生成密集流量下 chunking 更有利（Beyond the Buzz 的结论）都是边界条件。

    与 PD 分离的关系：chunked prefill 是 co-located 部署内部的批构造优化——prefill 与 decode 仍在同一实例上，只是不再互相卡住；PD 分离则把两阶段放到不同实例、各自独立优化（动机见 MoE Serving）。两条路线是竞争关系也是互补基线：Beyond the Buzz 论文正是把 piggybacked co-located（本文机制）作为分离式部署的对照基线，系统回答"什么条件下该走哪条路"——见 Beyond the Buzz 论文页。

    Sarathi-Serve 的端到端数字（尾延迟约束下的服务容量，相对 vLLM）：Mistral-7B 单 A100 为 2.6 倍、Yi-34B 双 A100 至 3.7 倍、Falcon-180B 流水线部署至 5.6 倍[C15, N5]；Sarathi 原版在 LLaMA-13B/A6000 上 decode 吞吐至多 10 倍、端到端吞吐 1.33 倍，LLaMA-33B/A100 上端到端 1.25 倍、decode 吞吐至多 4.25 倍[N6]。这些数字各自的实验条件不同，不能跨设置比较。

    本章问题

    1. chunked prefill 让 prefill 变快了吗？它和 PD 分离是什么关系？

      解答：没有；它是 co-located 内的优化，与 PD 分离是两条路线

      没有。单请求 prefill 的总计算量不变（FFN 不变），访存还微升（KV 重复读 $\frac{N(N-1)}{2}$、固定开销）[C5, F1, C13]——它改善的是系统层面的延迟结构（decode 不再被卡）与批均衡（搭车、流水线均匀化），不是单个 prefill 的速度。与 PD 分离的关系：chunked prefill 在同一实例内混批 prefill 块与 decode，是 co-located 部署的优化；PD 分离把两阶段放到不同实例分别优化。Beyond the Buzz 论文把 piggybacked co-located（本文机制）作为分离部署的对照基线，结论是分离在 prefill-heavy 流量与大模型下收益更大、小模型与生成密集流量下收益有限——即两条路线各有优势区间，完整论证见其论文页。
