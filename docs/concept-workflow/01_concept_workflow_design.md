# 1. Concept 概念页生成工作流设计

## 1.1 文档状态

- 状态：待审阅
- 目标：设计一套随仓库版本化、可由 CodeBuddy、Claude Code、Codex 等 AI CLI 执行的概念页生成工作流
- 第一版范围：算法 / 数学类技术概念
- 最终正式产物：`content/concepts/<slug>/index.html`

## 1.2 背景

当前 concept 工作流已经拆成研究、大纲、初稿、审计、修复五个阶段，但仍存在以下问题：

1. 阶段说明很多，AI 仍可能遗漏信息或自行改变范围。
2. “内容丰富”容易退化为机械地给每个子概念添加公式、推导、数字和代码。
3. “小白友好”主要依靠作者自查，缺少真正独立的读者审查。
4. 自动检查容易只覆盖格式，无法判断事实、推导和教学路径是否正确。
5. 不同类型概念需要不同写法，不能共用一套固定内容套餐。
6. 工作流目前更像五份说明文档，还没有清晰定义用户如何启动、何时确认以及失败后回到哪里。

本设计不继续增加复杂检查项，而是先把实际使用方式、阶段边界和审查闭环定义清楚。

## 1.3 用户目标

用户 clone 仓库后，在任意受支持的 AI CLI 中用一句自然语言启动：

> 执行 concept 工作流，概念是 PPO。

AI 应自动完成研究、教学设计、HTML 写作、独立审查和修复，只在三个关键节点请求用户确认。

用户不需要填写问卷，不需要理解内部编排，也不需要手动依次运行五个 prompt。

## 1.4 设计原则

1. **仓库内自包含**：工作流规则跟随仓库，不依赖某个 AI CLI 的全局 Skill。
2. **跨 AI CLI**：核心协议使用通用 Markdown 描述，不绑定 CodeBuddy、Claude Code 或 Codex 的专属调用格式。
3. **关键节点确认**：研究范围、大纲和最终发布必须由用户确认。
4. **最小自包含**：正文补足理解主线所需的最小前置知识，不无限展开所有前置概念。
5. **自适应深度**：根据教学需要选择推导、数值例子、图示和代码，不使用固定内容套餐。
6. **机制代码优先**：算法概念优先提供暴露核心机制的最小可运行代码，不用高级 API 隐藏关键过程。
7. **作者与审查者分离**：作者不能自行宣布技术正确或小白友好。
8. **正式产物简单**：用户最终只需要维护和发布 `index.html`；研究材料只服务于生成过程和断点恢复。

## 1.5 设计依据

本设计来自当前仓库的实际演变和用户在本轮讨论中确认的选择：

- `8980b35` 首次把 concept 写作改成阶段流程，并加入自动审计脚本。
- `80c1a4b` 和 `0929cb5` 两次使用阶段流程生成、重写 RLHF，说明仅增加规则仍不能稳定保证内容深度和教学质量。
- `7176e02`、`9602121`、`d4f41c1`、`a9da0a7` 等连续修订分别暴露了模板残留、事实错误、推导不足以及“框架代码真实但隐藏机制”等问题。
- `d66de67` 将现有流程拆成五个独立阶段，但阶段之间仍缺少清晰的用户确认点和失败回路。
- 用户已确认：只输入概念名、三个关键确认点、最小自包含、自适应深度、机制代码优先，以及第一版先支持算法 / 数学概念。

# 2. 第一版范围

## 2.1 支持的概念

第一版只面向算法 / 数学类技术概念，例如：

- PPO
- DPO
- 反向传播
- 交叉熵
- 注意力机制

后续可在共享流程之上增加其他类型的专用规则，例如：

- 系统 / 架构概念
- 工具 / 工程概念
- 理论 / 抽象概念

第一版不提前实现这些类型。

## 2.2 输入

用户只提供概念名，例如：

> 执行 concept 工作流，概念是 PPO。

AI 负责推断初始学习目标、概念边界和读者所需前置知识，并在第一个确认点交给用户修正。

如果概念名存在重大歧义，AI 必须先询问用户，不能自行选择含义。

## 2.3 非目标

第一版不做以下事情：

1. 不编写独立的 Python 模型调用器。
2. 不绑定某一家 AI CLI 的 Agent API。
3. 不设计复杂 YAML Schema 或通用工作流引擎。
4. 不追求一次支持所有技术概念类型。
5. 不要求所有子概念都有完整推导、数字例子和代码。
6. 不自动发布未经用户确认的页面。

# 3. 用户实际使用流程

## 3.1 总流程

```text
用户输入概念名
  ↓
AI 研究概念
  ↓
确认点 1：用户确认研究范围
  ↓
AI 设计教学大纲
  ↓
确认点 2：用户确认教学大纲
  ↓
AI 生成 index.html
  ↓
基础检查
  ↓
独立技术审查 → 修复 → 复验
  ↓
独立小白审查 → 修复 → 复验
  ↓
综合回归检查
  ↓
确认点 3：用户确认最终页面
  ↓
更新 content.json 和首页
```

## 3.2 确认点 1：研究范围

AI 只向用户展示简短、可决策的摘要，不要求用户阅读完整研究材料。

摘要包含：

- 当前概念具体指什么
- 页面准备回答的 3–5 个核心问题
- 必须讲清的核心内容
- 需要补充的最小前置知识
- 明确不展开的内容
- 容易误解的关键点
- 仍需用户选择的歧义

用户可以确认、删除或补充范围。确认后，作者不得在后续阶段擅自扩大文章范围。

## 3.3 确认点 2：教学大纲

AI 向用户展示：

- 章节顺序
- 每章解决的问题
- 贯穿全文的例子
- 哪些内容放正文
- 哪些内容放折叠块
- 哪些位置需要公式、推导、数值例子、图示或代码

用户确认后，文章结构冻结。写作阶段发现范围或结构有根本问题时，必须退回对应确认点，不能在 HTML 中偷偷调整。

## 3.4 确认点 3：最终发布

审查和修复完成后，AI 向用户报告：

- 页面路径
- 技术审查结果及修复数量
- 小白审查结果及修复数量
- 代码和 HTML 检查结果
- 仍保留的非阻断限制

用户阅读页面后可以：

- 确认发布
- 指定局部修改
- 要求重新调整大纲
- 要求缩小或扩大研究范围

只有用户确认发布后，AI 才更新 `content.json` 并重新生成首页。

# 4. 仓库交付结构

## 4.1 工作流文件

第一版预计整理为：

```text
workflows/concept.md
workflows/concept/
├── research.md
├── outline.md
├── write.md
├── review.md
└── fix.md
```

各文件职责如下：

- `workflows/concept.md`：总入口，定义启动方式、阶段顺序、三个确认点和失败回路。
- `research.md`：定义算法 / 数学概念该研究什么、何时停止以及如何给出范围摘要。
- `outline.md`：定义如何把研究范围转成小白学习路径。
- `write.md`：定义如何根据批准后的大纲生成 `index.html`。
- `review.md`：定义技术审查、小白审查和复验方式。
- `fix.md`：定义哪些问题可以自动修复，哪些问题必须退回确认点。

不同 AI CLI 的项目入口文件只需要指向 `workflows/concept.md`，不复制质量规则。

## 4.2 单个概念的文件

```text
content/concepts/<slug>/
├── index.html
└── research/
    ├── scope.md
    ├── outline.md
    ├── technical-review.md
    └── beginner-review.md
```

其中：

- `index.html` 是唯一正式发布产物。
- `scope.md` 保存已经确认的研究范围和主要依据。
- `outline.md` 保存已经确认的教学大纲。
- 两份 review 文件保存独立审查和复验记录。

`research/` 用于本次生成过程的断点恢复和问题追溯，不要求用户日常维护，默认继续由 `.gitignore` 排除。这样仓库只提交正式页面；如果用户确实需要跨机器继续某次未完成的生成，可以临时强制提交对应研究目录。工作流本身始终随仓库提交，clone 后可以直接开始新的概念任务。

# 5. 研究阶段设计

## 5.1 目标

研究阶段只决定“讲什么”，不写 HTML，不设计页面样式。

AI 必须完成四件事：

1. 消除概念歧义。
2. 找到小白真正理解该概念所需的核心问题。
3. 确定最小前置知识和处理方式。
4. 为重要定义、公式、机制和数字找到可靠依据。

## 5.2 内容分级

研究内容分为三级：

- **核心**：不懂就等于没有理解该概念，必须进入正文。
- **辅助**：帮助理解核心主线，可简要说明或放入折叠块。
- **扩展**：不影响主线，第一版可省略。

这种分级替代“列出所有子概念并全部详细讲解”。

## 5.3 最小前置知识

每个前置概念选择一种处理方式：

- 正文一句话解释
- 单独一个短小节
- 折叠块补充
- 明确超出本文范围

判断标准是：读者是否已经获得继续理解主线所需的信息，而不是是否掌握了该前置概念的全部知识。

## 5.4 研究停止条件

不再要求“能查到的都查全”。满足以下条件即可停止：

- 3–5 个核心问题都能可靠回答
- 核心公式和重要论断都有依据
- 主要争议、限制和常见误解已经明确
- 已经具备设计教学路径所需的信息

## 5.5 `scope.md` 内容

`scope.md` 使用普通 Markdown，至少包含：

```markdown
# <概念>研究范围

## 读完应该能回答

## 核心内容

## 最小前置知识

## 不展开

## 容易误解

## 主要来源与对应论断
```

来源必须尽量记录具体章节、公式、源码路径或文档位置，而不只是一个链接。

# 6. 大纲阶段设计

## 6.1 目标

大纲阶段只决定“怎么讲”。它必须基于已确认的 `scope.md`，不能自行扩大研究范围。

## 6.2 贯穿例子

算法 / 数学概念应优先选择一个足够小的例子贯穿全文，例如：

- PPO：两个动作、一次采样、一次更新
- 反向传播：两层标量计算图
- 交叉熵：三个类别的一次预测

后续章节逐步给该例子增加信息，避免每章重新创建互不关联的场景。

## 6.3 每章需要回答的问题

大纲中的每章至少说明：

- 本章解决什么问题
- 读者在此之前需要知道什么
- 使用什么讲解方式
- 哪些内容放正文
- 哪些内容放折叠块
- 本章如何过渡到下一章

## 6.4 自适应内容深度

根据内容特点选择材料：

| 内容特点 | 优先材料 |
|---|---|
| 抽象但可直观解释 | 具体场景、类比或图示 |
| 涉及连续计算 | 小数字手算例子 |
| 核心公式难以理解 | 分步推导 |
| 需要观察变量变化 | 最小机制代码 |
| 只是背景或扩展 | 一句话或折叠块 |

不要求每个子概念固定配齐所有材料。

## 6.5 大纲通过条件

进入写作前只检查四项：

1. 所有核心问题都有对应章节。
2. 每章只承担一个主要教学任务。
3. 前置知识在使用前得到最小解释。
4. 贯穿例子能够连接主要章节。

# 7. HTML 写作设计

## 7.1 作者输入

作者只依赖：

```text
research/scope.md
research/outline.md
templates/concept/index.html
```

作者不参考 `content/concepts/` 下已有页面的写作风格，不重新决定文章范围。

## 7.2 页面必要结构

页面保留以下必要部分：

```text
标题
30 秒摘要
读完能回答的问题
正文
适用范围与常见误解
来源与教学简化说明
```

正文标题和章节数量由批准后的大纲决定，不强制套固定七章结构。

## 7.3 30 秒摘要

摘要只回答：

1. 这个概念解决什么问题。
2. 最核心的做法是什么。
3. 学会后能理解或完成什么。

摘要尽量不使用未解释的专业术语；无法避免时必须就地给最小解释。

## 7.4 正文主线

每章采用以下基本节奏：

```text
提出当前问题
→ 给出直觉或具体场景
→ 解释机制
→ 用合适材料验证
→ 过渡到下一个问题
```

作者不能为了显得丰富而随意插入历史、变体和工程细节。

## 7.5 主文与折叠块

必须放在主文：

- 当前章节解决的问题
- 核心直觉
- 理解后文所需的机制
- 会改变结论的重要限制
- 贯穿例子的关键结果

适合放入折叠块：

- 完整数学推导
- 更长的手算过程
- 可运行代码
- 来源细节
- 非核心变体
- 与真实工程实现的差异

读者不展开任何折叠块，也应能够理解文章主线。

## 7.6 公式

核心公式按三层解释：

1. 公式前先说明要计算什么、为什么需要它。
2. 公式后解释符号和各部分作用。
3. 只有推导能帮助理解时，才在折叠块给完整推导。

允许引用读者已经具备的基础结论，不要求从最底层定理重新证明；关键跳步必须解释为什么成立。

## 7.7 数值例子

数值例子只在它能解决具体理解障碍时使用，例如：

- 概率、符号或更新方向过于抽象
- 读者容易误判结果
- 手算能直观看到机制
- 例子能验证刚讲完的结论

例子必须使用小数字、展示中间步骤、解释结果含义，并区分真实数据与教学构造。

## 7.8 代码

第一版优先机制透明的最小可运行代码：

- 默认 Python
- 尽量只依赖标准库或 PyTorch
- 使用固定小数据或小张量
- 直接展示正文公式如何映射到变量和计算
- 不用高级 API 隐藏核心算法

代码后只需说明：

1. 哪些代码对应正文中的哪些机制。
2. 运行后应该观察什么。
3. 为教学省略了哪些真实工程组件。

## 7.9 事实与教学解释

页面内容分为：

- 来源明确的事实
- 教学构造的例子和代码
- 为帮助理解而写的类比与解释

页面末尾必须明确区分三者。重要或容易争议的论断可以就地标注来源，其余来源集中列在末尾，避免引用干扰主线。

# 8. 独立审查设计

## 8.1 总体顺序

```text
初稿
  ↓
基础检查
  ↓
技术审查 → 修复 → 技术复验
  ↓
小白审查 → 修复 → 小白复验
  ↓
综合回归检查
```

## 8.2 独立性要求

技术审查和小白审查必须由没有参与正文写作的新 AI 上下文执行。

优先顺序：

1. AI CLI 支持子智能体时，分别启动独立审查智能体。
2. 不支持子智能体时，使用不继承作者推理的新上下文执行审查。
3. 如果工具无法做到上下文隔离，必须向用户说明限制，不能让作者直接宣布自己通过。

## 8.3 基础检查

进入 AI 审查前先检查：

- HTML 基本结构是否有效
- 模板占位符是否清理
- 本地资源链接是否存在
- 公式是否可以渲染
- 页面中存在 Python 代码时，代码是否可以运行

基础检查只判断页面能否使用，不评价内容质量。

## 8.4 技术审查

技术审查读取：

```text
research/scope.md
research/outline.md
index.html
研究阶段使用的主要来源
```

检查内容包括：

- 定义和重要论断是否准确
- 是否混淆相邻概念
- 公式、符号和推导是否正确
- 数值例子是否算对并支持正文结论
- 代码是否实现正文声称的机制
- 教学简化是否诚实说明
- 是否遗漏已确认的核心内容
- 是否擅自增加大纲外内容

每个问题必须写清：

- 严重程度
- 具体位置
- 问题是什么
- 为什么会误导读者
- 修改要求
- 判断依据

## 8.5 小白审查

小白审查分两遍。

第一遍只读取 `index.html`，避免提前知道作者意图后自动脑补。重点记录：

- 第一次看不懂的位置
- 当时缺少什么信息
- 产生了什么错误理解
- 后文是否真的解决疑问

第二遍再读取 `scope.md` 和 `outline.md`，检查：

- 开头承诺的问题是否都有答案
- 最小前置知识是否补齐
- 常见误解是否澄清
- 贯穿例子是否真正帮助理解

小白审查不能只说“太难”或“不够清晰”，必须描述具体阅读反应和修改建议。

## 8.6 严重程度

- **阻断**：事实错误、核心推导错误、代码与正文矛盾、主线无法理解，禁止发布。
- **重要**：核心内容缺失、明显认知跳跃、例子无效，必须修复。
- **轻微**：措辞、排版或可选增强，不阻止提交给用户确认。

# 9. 自动修复设计

## 9.1 可自动修复的问题

修复 AI 可以直接处理：

- 局部事实表述错误
- 公式、计算或代码错误
- 缺失的术语解释
- 例子说明不足
- 来源或教学简化声明遗漏
- 局部顺序和过渡问题
- HTML 与样式问题

## 9.2 必须退回确认点的问题

| 问题 | 返回位置 |
|---|---|
| 概念边界或核心问题选择错误 | 研究范围确认 |
| 需要新增、删除或重排核心章节 | 教学大纲确认 |
| 来源之间存在重大冲突 | 询问用户后回研究阶段 |
| 修复会改变已确认范围 | 研究范围确认 |
| 小白友好与当前篇幅无法兼得 | 用户选择缩小范围或扩充大纲 |

## 9.3 修复方式

修复应按根因成组处理，不机械地逐条追加句子。

例如“policy 未解释”“old policy 未解释”“ratio 不知道为何比较两者”可能来自同一个根因：章节开头没有建立比较新旧策略的问题场景。正确做法是重写该章开头，而不是在三个位置分别添加括号。

修复后必须交回原类型审查员复验。修复者不能自行关闭问题。

## 9.4 防止无限循环

技术审查和小白审查各最多进行三轮：

```text
审查 → 修复 → 复验
```

三轮后仍有阻断或重要问题时停止自动修改，向用户报告无法解决的冲突，并给出 2–3 个明确选择。

# 10. 综合回归检查

两类审查通过后检查：

- 技术修复是否让文章变得更难理解
- 小白修复是否损害技术准确性
- 公式、数字和代码是否仍然一致
- 页面是否仍符合批准的大纲
- HTML 和代码是否仍能正常运行

如果小白修复改动了公式、代码或事实，必须重新执行技术复验。

# 11. 最终交付

用户最终看到的报告应简洁：

```text
已生成：content/concepts/ppo/index.html

研究范围：已确认
教学大纲：已确认
技术审查：通过，修复 4 个问题
小白审查：通过，修复 6 个问题
代码检查：通过
HTML 检查：通过

仍保留的非阻断限制：
- 本文不展开完整策略梯度定理
- 代码是教学实现，不是生产训练器
```

用户确认后才执行：

1. 更新 `content.json`。
2. 运行首页生成脚本。
3. 检查首页能否进入新页面。

# 12. 成功标准

第一版工作流成功需要满足：

1. 用户只输入概念名即可启动。
2. AI 只在研究范围、大纲和发布三个节点请求确认。
3. 换用 CodeBuddy、Claude Code 或 Codex 时，核心流程和质量标准不需要复制重写。
4. 作者不能跳过确认点或自行扩大范围。
5. 正文不依赖展开折叠块才能理解主线。
6. 内容材料由教学需要决定，而不是机械套固定套餐。
7. 技术审查和小白审查使用独立上下文。
8. 阻断和重要问题必须修复并复验。
9. 自动修复最多三轮，无法收敛时回到用户决策。
10. 最终产物能够正常打开、公式正常显示；页面包含代码时，代码可以运行。

# 13. 待审阅决策

请重点确认以下设计选择：

1. 第一版只支持算法 / 数学概念。
2. 用户只输入概念名，不填写结构化问卷。
3. 使用研究范围、大纲、发布三个确认点。
4. 采用最小自包含和自适应深度。
5. 代码优先展示机制，而不是优先展示真实框架 API。
6. 页面正文结构由大纲决定，不固定使用七章。
7. 技术审查和小白审查分开进行。
8. 每类审查最多三轮，无法收敛时交回用户决策。
9. 正式产物只有 `index.html`，研究和审查文件只服务于生成流程。
