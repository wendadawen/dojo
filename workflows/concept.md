# 概念学习流程

## Overview

让小白在足够上下文里真正看懂一个概念。

**三个目标：**

1. **先看懂它**：每一步设计都从"读者这一步能不能看懂"出发
2. **有足够上下文**：读者在任何位置遇到新概念时，上下文已经具备
3. **站在小白角度**：默认读者什么都不懂，任何概念第一次出现就必须解释

## Iron Law

```
阶段 1 没完成，不允许碰 HTML
发布前必须做读者审计
```

没有术语清单和数字清单，不允许进入阶段 2。没有读者审计，不允许发布。

## When to Use

写一篇新的 concept 学习页面时。不是论文解读（用 `workflows/paper.md`），不是一次性笔记。

## 七个认知阶段

读者读完一篇 concept 后，必须能回答这七个问题：

1. **它在哪**：知道这个概念属于哪个大流程
2. **之前怎么做**：知道旧方案
3. **为什么不够**：知道旧方案的问题
4. **它改了什么**：知道核心思路
5. **它是什么**：知道定义
6. **它怎么工作**：知道机制
7. **什么时候用**：知道边界

这七个阶段必须覆盖到，但不一定每个阶段都是独立 H1。可以合并、拆分、跳过、自由命名标题。判断标准：读者读完后能不能回答这七个问题。

## Phase 1: 读者理解设计

**不允许碰 HTML，不允许填模板，不允许看已有 concept 页面。**

### Step 1: 确认读者目标

**必须做什么：** 想清楚读者到底想看懂什么。

**怎么做：**
1. 读者到底想看懂什么？
2. 读完要能回答哪 3-5 个问题？

**什么算完成：** 能用一句话说出"读者读完这篇后，能回答……"。

### Step 2: 确认概念边界

**必须做什么：** 搞清楚这个概念指什么、不指什么。

**怎么做：**
1. 这个概念指什么？不指什么？
2. 有没有同名概念、相邻概念或容易混淆的说法？

**什么算完成：** 能区分"这个概念是 X，不是 Y，Y 是相邻概念"。

### Step 3: 收集权威来源

**必须做什么：** 找到所有事实的出处。

**怎么做：**
1. 官方文档是什么？
2. 论文 / 技术报告是什么？
3. 官方源码 / 配置 / 设计文档是什么？
4. 有没有实测或示例？

第三方资料只辅助理解，不作为核心事实来源。

**什么算完成：** 每个关键事实都能追到一个权威来源。

### Step 4: 列术语/符号清单（硬门槛）

**必须做什么：** 把页面会用到的每个概念、符号、术语列出来。

**怎么做：**

```markdown
| 术语/符号 | 小白解释 | 第一次出现在哪里 |
|---|---|---|
| SFT | Supervised Fine-Tuning，用示范数据做监督微调 | callout |
| policy | RL 里的策略，在 LLM 里就是模型本身 | callout |
| π_ref | SFT 后冻结的参考模型 | 第一章 |
| σ | sigmoid 函数，把任意实数压到 (0,1) | 第三章 |
| ... | ... | ... |
```

**什么算完成：** 清单覆盖了页面会用到的所有术语、符号、缩写、专业比喻。写作时对照这张清单，写到任何术语/符号时，从清单取解释，放在它第一次出现的位置或之前。

### Step 5: 列数字来源清单（硬门槛）

**必须做什么：** 把页面会用到的每个数字列出来，标注来源。

**怎么做：**

```markdown
| 数字 | 来源 |
|---|---|
| 10-100 倍成本 | ?（需要查论文或删掉） |
| β = 0.1 | 本文构造 |
| logits [0.5, 0.5, 0.5, 0.4, 0.6] | 本文构造 |
| ... | ... |
```

找不到来源的数字，要么查到来源，要么标"本文构造"，要么删掉。不允许凭印象写数字。

**什么算完成：** 每个数字都有来源标注。

### Step 6: 设计理解路径

**必须做什么：** 设计读者从零到看懂的理解路径。

**怎么做：**
1. 按"七个认知阶段"设计路径
2. 决定哪些阶段合并、哪些拆分、哪些跳过
3. 为每个阶段想一个自然的标题

**什么算完成：** 能用一段话讲清楚"读者从打开页面到看完，会经历哪几步"。

## Phase 2: 写页面

**把 Phase 1 的产出放在手边，对照写页面。**

### Step 7: 拷贝模板

**必须做什么：** 创建目录和文件。

**怎么做：**

```bash
mkdir -p content/concepts/<concept-name>
cp templates/concept/index.html content/concepts/<concept-name>/index.html
```

**什么算完成：** 文件存在，能在浏览器打开。

### Step 8: 写顶部模块

**必须做什么：** 写页面顶部所有固定模块。

**怎么做：**

顶部固定包含，按顺序：

1. **title**：概念名 + 一句话概括
2. **reading time**：自动生成，不用写
3. **callout**：问题 / 方案 / 产物，各一句话。callout 里出现的术语必须在 callout 里就地解释
4. **context-box**：大流程 / 旧方案 / 痛点 / 改变点
5. **读完你能回答**：3-5 个问题
6. **最容易误解**：2-4 个误区
7. **meta**：来源。不设前置列表，所有术语本页解释
8. **小白版一句话定义**：不用术语或少用术语

**什么算完成：** 顶部所有模块都填了真实内容，没有占位符。callout 里的术语都就地解释了。

### Step 9: 写正文

**必须做什么：** 按理解路径写正文，覆盖七个认知阶段。

**怎么做：**

#### 正文结构

- 必须覆盖七个认知阶段，但结构自由
- 每个阶段可以独立成章，也可以合并
- 如果某个阶段不适用，可以跳过
- 每章后用 1-2 句自然导语说明这章推进了哪一步。不写"本章你将知道"

#### 章节标题

- 是一句话，不是单个词
- 告诉读者这章讲什么
- 不用比喻或抽象词（如"旧世界""断点""新想法"）
- 不超过 20 字

#### 检查点

在"它改了什么"阶段末尾，必须有检查点。引导句单独一段，检查项单独列表：

```html
<p>读到这里，你应该已经能解释：</p>
<ul>
  <li>……</li>
</ul>
```

不要把引导句和检查项混成平级 `<li>`。

#### 术语和符号

写到术语/符号时，对照术语清单，遵循：

1. 术语第一次出现时必须就地解释（括号或破折号）
2. 折叠块里的解释不算首次解释
3. 公式里的每个符号必须已解释过
4. 公式后紧跟完整符号说明列表
5. 专业比喻（锚点、环境、baseline）第一次出现也必须解释
6. 顶部 callout 里出现的术语必须在 callout 里就地解释

#### 数字和证据

写到数字时，对照数字清单，遵循：

1. 每个数字必须标注来源：论文/源码/实测/本文构造
2. 本文构造的数字在例子开头就标注
3. 事实和解读者推断分开
4. 源码路径和配置名必须查当前版本
5. 不确定的数字删掉或标"未验证"

#### 公式和推导

写推导折叠块时，遵循：

1. 开头有"问题陈述"（要解决什么）和"核心困难"（为什么不能直接做）
2. 分步骤，每步有标题
3. 每步包含：变换 + 为什么需要 + 验证（关键步骤）
4. 关键步骤分情况讨论
5. 末尾有"一句话总结"（因果链回顾）
6. 末尾有符号总览
7. 每步变换后读者能解释"为什么允许这样变"

#### 代码

写代码折叠块时，遵循：

1. 伪代码和可运行代码可以同时有
2. 可运行代码后必须说明：代码层次、读者容易卡在哪、和真实工程差什么
3. API 必须查当前文档确认真实
4. 超参必须标注来源
5. 默认 Python：`<pre><code class="language-python">...</code></pre>`
6. 其他语言按需：`language-bash`、`language-yaml`

#### 列表呈现

1. 有顺序依赖的内容用 `<ol>`：推导步骤、计算序列、流程步骤。判断标准：跳一步就跟不上
2. 并列内容用 `<ul>`：指标、特征、观察。判断标准：换序不影响理解
3. 叙述性内容用段落：解释、论证、只有一两步不值得列表的内容

#### 跨章节引用

1. 括号引用：`SFT（见第 X 章）的作用是...`，适合只需提一下
2. 文字指引：`SFT 的做法在第 X 章已经讲过，这里不再重复。`，适合需要明确告诉去哪看
3. 不重复解释，不用脚注链接

#### 图示

1. 什么时候该画图：流程有多步文字容易迷路、组件有层级或依赖、数据流有分支或循环
2. 简单流程用 ASCII 图（`<pre class="diagram">`），复杂架构用图片（base64 内联），少量节点用文字
3. 什么时候不该画图：只有 2 个节点、图和文字说同一件事

#### 数值例子

1. "最小"的标准：概念用到的每个角色都出现、每个计算步骤能用小数字手算、读者能在 1 分钟内走完
2. 常见规模：算法类 3-5 个 token / 1-2 步采样；系统类 2-3 个组件 / 1 个请求
3. 超过这个规模就不是"最小"，考虑拆成多个例子
4. 每步必须展示计算，不能跳步
5. 放折叠块

#### 折叠块

适合折叠：完整公式推导、长伪代码/代码片段、源码调用链细节、配置示例、最小数值例子。

不许只放在折叠块：关键假设、核心直觉、会改变结论的限制条件、主路径用到的任何术语的解释。

#### 重复控制

1. 每个概念在一个地方讲完整，其他地方只引用
2. 每章只讲自己负责的侧面
3. 同一公式不重复给（给过就引用）

#### 证据边界声明

正文最后按来源分：

```text
官方文档
论文 / 技术报告
官方源码 / 配置
实测 / 示例
解读者推断
```

**什么算完成：** 正文覆盖七个认知阶段。每个术语第一次出现时已解释。每个公式符号已解释。每个数字有来源。没有重复。检查点结构正确。

## Phase 3: 读者审计

**不是 checklist，是模拟阅读。**

### Step 10: 读者审计

**必须做什么：** 把自己当成完全不懂这个领域的人，从头读到尾。

**怎么做：**

1. 从 callout 开始，逐段往下读
2. 每遇到一个术语/符号，问自己："我在这里能看懂吗？"
   - 如果看不懂 → 标记，回去补解释
3. 每遇到一个数字，问自己："这个数字从哪来？"
   - 如果找不到来源 → 标记，回去标来源或删掉
4. 每遇到一个公式，问自己："每个符号我都认识吗？"
   - 如果不认识 → 标记，回去补符号解释
5. 每读完一章，问自己："这章和前面有重复吗？"
   - 如果有 → 标记，回去改成引用
6. 读到检查点，问自己："我能回答这些问题吗？"
   - 如果不能 → 标记，说明前面没讲清楚
7. 读完，问自己："七个认知阶段都覆盖了吗？"
   - 如果缺 → 标记，回去补章节
8. 所有标记都修完后，再读一遍
9. 第二遍没有新标记，审计通过

**什么算完成：** 第二遍读完没有新标记。

## Phase 4: 发布

### Step 11: 更新 manifest + 运行脚本

**必须做什么：** 把新页面加入首页，运行所有检查脚本。

**怎么做：**

在 `content.json` 的 `items` 增加条目：

```json
{
  "id": "concept-name",
  "section": "concepts",
  "tag": "concept-name",
  "title": "概念名：一句话概括",
  "desc": "读者点进来能学到什么",
  "path": "content/concepts/concept-name/"
}
```

运行：

```bash
python scripts/generate_index.py
python scripts/validate_content.py
python scripts/audit_concept.py
```

**什么算完成：** 三个脚本全部通过。首页能点进新页面。

## Red Flags

以下想法出现时，说明你在偷懒，停止并回到对应步骤：

| 想法 | 现实 | 怎么办 |
|---|---|---|
| "读者应该知道 SFT 是什么" | 默认读者什么都不懂 | 回 Step 4 补术语清单 |
| "这个数字大概是 10-100 倍" | 凭印象写数字 | 回 Step 5 查来源或删掉 |
| "σ 等到推导折叠块里再解释" | 折叠块不算首次解释 | 回正文在公式前解释 |
| "先写 HTML 再想术语清单" | 阶段 1 没完成不能碰 HTML | 回 Step 4 先列清单 |
| "看一眼已有页面参考一下" | 已有页面会污染句式 | 不允许看已有页面 |
| "这个公式上次给过了，再给一遍" | 重复 | 改成引用 |
| "读者审计差不多了" | 没有第二遍就不是审计 | 再读一遍，确认没有新标记 |
| "检查点引导句放 li 里就行" | 结构错误 | 改成 `<p>` + `<ul>` |
| "这个概念太复杂，不适合最小例子" | 最小例子可以很小 | 回 Step 9，3-5 个 token 就够 |
| "推导这步很显然" | 跳步 | 写出为什么允许这样变 |
